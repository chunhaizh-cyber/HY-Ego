# 存在概念两组定义提供者施工记录

计划：`EXISTENCE-CONCEPT-DEFINITION-PROVIDER-REBUILD v0.3`

状态：代码施工完成；本记录不声明运行、恢复、集成验收或业务闭环完成。

## 当前已落地

- 合同头已增加存在概念两组定义的独立 DTO：自身 `FT→FC` 值域组、已知子 `EC` 组、显式完整声明、预算、状态、12 项结构登记交付和读写请求/结果。
- 两组 ABI 与旧 `纯概念定义` variant 分离；调用方不能借由新接口传入 D/O/R、组成角色、关系类型或参与角色。
- 服务头已声明两组定义的结构登记、规范化、有界枚举、精确查询、创建或复用和完整读回入口。
- `登记存在概念两组结构_v1` 已使用概念 owner 的首次写入机制登记 6 个普通节点、5 条类型登记关系和 1 条格式值；原键重放、冲突、发布未知和 12 项历史读回均在该入口内收束。
- 两组定义的规范化、读回、候选有界枚举、精确查询和创建/复用均已实现。创建路径以一个 owner 写集同时建立概念基础事实、两组定义记录、IF 项和全部 FT/FC/子 EC 关系；不经两次写入补边。
- 候选枚举仅接纳具有新 `两组定义成员` 关系的存在概念，跳过未采用新格式的历史普通概念；旧 D/O/R 不会被解释为新定义。

## 尚未完成

- 已恢复仍被现有调用链使用的相关概念、纯概念和特征概念出生结构函数；旧 D/O/R 生产符号在目标 `.h/.cpp` 范围内为零命中。
- `git diff --check`、`check_specs.py --strict`、Debug x64 与 Release x64 均通过。
- 未执行运行、恢复、专项黑盒或集成验收；普通应用长驻启动不是本计划的验证手段。
- 本记录不是构建、运行、恢复、集成验收或业务闭环证据。

## 代码知识变更清单

| 身份 | 变化 | 用途与边界 |
| --- | --- | --- |
| `存在概念两组定义_v3` 及相关 DTO | 新增 | 表达仅有 FT→FC 与子 EC 的已裁决定义；不含旧 D/O/R。 |
| `概念树类数据服务` 两组定义入口 | 新增声明 | 后续只由概念 owner 实现结构登记、读写和精确复用；尚无生产调用边。 |
| `映射两组定义失败` | 新增 | 仅在普通应用装配失败边界将两组状态归类为既有 `纯概念状态`；不伪造结构登记成功。 |
| 旧 `完整存在概念*` 生产实现 | 删除 | 移除 D/O/R 物理布局、公开 DTO 和消费者；不保留兼容层。 |
| `登记存在概念两组结构_v1` | 实现 | 同 owner 12 项结构登记、原键重放与首次材料读回；不登记 D/O/R 类型或属性。 |
| `规范化两组定义内部` / `规范化存在概念两组定义` | 实现 | 完整声明、预算、排序、FT/FC 基础读回和子 EC 类别/生命周期核验；非 I64 未实现或规则缺失零成功收束。 |
| `读取两组定义内部` / `读取存在概念两组定义` | 实现 | 从 C→D、D→IFItem、IFItem→FT/FC、D→子EC 读取完整定义；不读旧 D/O/R。 |
| `枚举存在概念候选` / `精确查询存在概念` | 实现 | 只沿概念族成员做有界枚举，逐候选完整读回；多个精确命中为内部不一致。 |
| `创建或复用存在概念` | 实现 | 单 owner 写集发布基础概念与两组定义；不通过“先纯概念、后补定义”破坏事务边界。 |
