## 2. 实际实现

### 2.1 数据合同

在既有服务合同事实权威数据头新增：

- `服务活动事实发布合同版本_v2`；
- `服务进展事实发布材料_v2`、`服务准备事实发布材料_v2`；
- `发布服务进展事实请求_v2`、`发布服务准备事实请求_v2`；
- `服务活动事实发布状态_v2`；
- `服务进展事实发布结果_v2`、`服务准备事实发布结果_v2`及严格成功谓词；
- 材料完整性、同流身份和首次 G1 投影完整性纯值谓词。

非成功结果不返回部分事实；只有 `已发布` / `精确重复` 且首次 G1 投影、幂等身份和正式读回截止完整时 `成功()` 才为真。`已可能发布` 只保留首次提交代次见证。

### 2.2 服务 owner

在现有唯一 `服务合同事实权威服务` 中增加：

```cpp
服务进展事实发布结果_v2 发布服务进展事实_v2(
    const 发布服务进展事实请求_v2&) noexcept;

服务准备事实发布结果_v2 发布服务准备事实_v2(
    const 发布服务准备事实请求_v2&) noexcept;
```

实现结果：

1. 首次请求由发布材料唯一投影为既有 v2 事实闭包；
2. 同流更新要求请求中的 `预期当前事实` 精确等于规范化退出事实闭包的旧事实节点身份；
3. 替代写集在同一 L1 owner 原子提交内退出旧事实闭包并建立新事实闭包，不退出 task、method、state、dynamic、需求或其它跨 owner 外部端点；
4. 同一活动流最终只保留一个当前事实，旧事实闭包永久可按首次 G1 读回；
5. 同一旧请求在首次事实被替代后仍按首次 G1 历史闭包收束为 `精确重复`；
6. 同键异义、跨入口同键、缺失或错误预期当前事实、坏外部引用、旧 G0 和资源失败均结构化分账；
7. 现有两个 v2 完整读取的锁内主体抽为 `..._已锁定`，发布后正式读回复用该主体，未持锁递归调用公开读取；
8. 提交后正式读回失败返回 `已可能发布`，原请求重试通过首次写入映射与权威读回精确收束。

### 2.3 专项

专项建立第二个真实 L1 owner，正式建立 task、method、选择、冻结、实例方法、状态、动态、准备结果、验证和能力缺口等外部端点。W00—W05 覆盖两个发布入口的首次发布、替代、历史重放、全部状态、证据形状、失败分账、提交后读回失败和持久恢复。

无验证宏构建门禁曾发现 `建立发布测试上下文` 直接引用验证专属 helper。最终只在专项文件给该 helper 增加 `ARCH_INSTINCT_SERVICE_CONTRACT_FACT_AUTHORITY_VALIDATION` 条件编译边界；生产配置根工程随后完整构建通过。
