## 1. 范围与职责

本规范逐个定义本能方法函数的合同：修改什么、为什么修改、达到什么目的，参数，各执行分支的必要条件，条件不足时的筹办去向，执行入口复核，正常结果，业务结果值域和工程故障边界。

所有本能共用的合同不在此重复：任务链是唯一调用路径（3300 §4.1），登记与动作动态（3300 §4.3、5360 §2），参数场景与运行隔离（3300 §5、5360 §3），本次运行条件—结果对（5360 §5），独立观察与任务验证（5360 §6），失败、重入与恢复（5360 §8）。

本规范只规定本能方法函数的机制，配合内部治理闭环（需求—任务—方法—学习）运行。何时行动、是否重复、凭什么认定等更细的取舍属于自我意识，由自我意识依据对服务值或安全值的影响决定，不在本规范规定（2026-11-10 用户裁决）。

结算等内部治理函数不是本能方法（3300 §4.1），不在本规范范围。观察、识别、扫描、跟踪类本能由 6370、6380 规定，代码未实现，本稿不列。

## 2. 合同共同规则

### 2.1 合同条目

每个本能按 AGENTS §1.1 的顺序写出以下条目，缺一项即为合同不完整：

| 条目 | 内容 |
| --- | --- |
| 修改对象、原因、目的 | 修改虚拟存在还是现实世界的特征值；两类都改时分别写出各自的对象、原因和目的，不混写为一个动作 |
| 正常操作与结果 | 本函数实际取得或改变了什么；后续由谁使用；不得把下游治理的变化写成本函数的结果 |
| 参数 | 函数为完成正常操作必须拿到的对象 |
| 方法头 | 作用存在概念、涉及特征类型、可能结果 |
| 执行分支与必要条件 | 每个分支分别列出；每项写明在方法头中的声明位置。条件—结果对中的先天条件不由函数直接预置，由模拟学习依据方法头节点信息（参数规格、初始必要条件、执行分支必要条件）生成 |
| 条件不足的筹办去向 | 可由行动满足的条件转成什么子需求；不可行动满足的条件由哪个替代方法承担 |
| 执行入口复核 | 只复核已声明的条件 |
| 业务结果值域 | 每种返回及触发条件 |
| 结果组 | 方法函数在生成方法头时同时生成结果组：写明每个作用对象及其被改变的特征类型（2026-11-10 用户裁决）；召回依据结果组的结果项。结果的具体取值、方向与关系按方法实际运行结果完善（尝试学习，5370），合同中的“正常结果”是这一结果组的来源，不作为已掌握的效果 |
| 工程故障 | 哪些情况按工程异常路径处理 |

### 2.2 声明完整

1. 函数正常执行所依赖的每一项条件都必须写进方法声明。运行时只复核已经声明的条件。
2. 运行时核对了、声明里没有的条件，属于本能方法函数逻辑不完善。它会使筹办看不出缺什么、求解器无法收窄、失败无法形成学习信号，必须补进声明或删除。
3. 条件的声明位置：
   - 初始必要条件：只表达“参数属于某存在概念”或“参数具备某特征类型”；
   - 执行分支必要条件：值域、前态、数值区间等，每个分支分别声明；
   - 条件结果对：配对自身的条件与结果；
   - 参数关系：参数之间的关系。
4. 现有条件项与关系种类暂时无法表达的条件，在本合同中写为“运行时复核”，遇到时按第4节第1项逐个确定声明方式；不得把它包装成业务结果。

### 2.3 参数只取函数要用的对象

1. 参数是函数完成正常操作必须拿到的对象。
2. 由调用语境就能确定的东西不设参数让筹办去求解。例如询问时“问谁”由所用窗口决定，不设“受询者”参数。
3. 只为表达或判断而需要的信息，若能从已有参数读出，作为执行时材料读取，不另设参数；读取所依赖的条件仍须声明。

### 2.4 目标判定与执行条件分开

1. 函数目标已经达成（如被问字段已有值、自我已在目标场景），属于筹办阶段的目标判定，不作为执行条件，也不进入执行后再返回“已取得”。
2. 执行入口复核发现目标已达成时，零动作返回“目标已满足”，不报“已取得”。

词条归类的目标判定按3100、5170读取“概念名称挂接”F的历史不同值。实际归类写入通过特征owner的添加特征值功能传入单个概念编码，添加后回读该F历史确认。方法头继续声明作用对象和被改变的FT，具体条件/结果依5350保留正式取值位置。执行前已查到目标所需编码时，按本规范第2.4节的目标已满足规则处理。

### 2.5 结果状态一致

1. 进入动作之前的拒绝报“入口拒绝”；进入动作之后的中断报“动作结果未知 / 部分取得”，不得出现“已进入动作”而状态为“入口拒绝”。
2. 工程故障不得作为业务结果、业务值域或条件结果知识（AGENTS §1.1 第5项）。

### 2.6 一个本能内的两类修改

本能内同时修改内部记录与现实世界时，合同须分别写出两类修改；部分完成时按第2.5节报告实际阶段。

## 3. 各本能合同

各节为现行合同。合同与当前代码的差距不在本规范登记，见讨论稿差距分析（`讨论稿/5380_子规范_本能方法函数合同_讨论稿v0.1.md`）及相应施工计划；代码未达到本合同处按本合同施工。

### 3.1 进入场景（`builtin.self.enter_scene.v1`）

- 修改对象：内部世界树中自我的位置——自我“所在场景”特征值与场景成员关系（虚拟存在）。原因：目标要求自我处在某场景。目的：使自我所在场景为目标场景。不修改外设世界。
- 参数：1 自我｛所在场景｝；2 所在场景特征（所属1）；3 目标场景（通用存在）。
- 方法头：作用存在＝自我；可能结果＝所在场景。
- 执行分支（6220）：非空间进入、空间进入。

| 条件 | 分支 | 声明位置 |
| --- | --- | --- |
| 参数1属于自我概念 | 共用 | 初始必要条件 |
| 参数3可沿父场景链到达现实世界根 | 共用 | 运行时复核（按第4节第1项遇到时确定声明方式） |
| 空间进入所需的坐标与边界条件 | 空间进入 | 执行分支必要条件（待6220细化） |

- 目标判定：自我当前已在参数3 → 目标已满足，不执行。
- 正常结果：自我“所在场景”＝参数3，世界树完成迁移。
- 业务结果值域：已取得；入口拒绝（条件不足、停止）；目标已满足。
- 工程故障：时间不可读、动作发布失败、写入或迁入失败、读回不符。

### 3.2 建立连接（`builtin.connection.establish.v4`，改为主动出站本能）

2026-11-10 用户裁决：
1. 保留建立连接，不再写交互者（同日早先裁决）。
2. 建立连接改为主动本能：交互者已打开窗口但没有消息发生时，自我主动发出一条打招呼的话；话语由建立连接调用自然语言相关函数生成，如“你好！”“嗨！”“请问有什么可以帮到你吗？”。

- 修改对象：
  1. 现实世界：经窗口向当前交互者说出一句打招呼的话（外设输出队列新增一条）。原因：交互者在窗口前但双方尚无消息往来。目的：引出对方回应，使双方开始互相收发。
  2. 内部记录：留档出站具体表达（语言场景），建立说话动作动态。
  不写“自我.交互者”，不迁移自我。
- 正常操作：组织打招呼的表达需求 → 表达组织知识 → 含义网 → 成文 → 建立动作 → 留档 → 入列；复用询问指定需求字段已有的出站时序（CONV-EXPR-STRUCT、CONV-EXPR-TEXT）。
- 参数：1 自我（自我范围概念）；2 窗口副本（通用存在｛外设场景标识｝）；3 外设场景标识特征（所属2）。受话者为自我当前交互者，作执行时材料读取，不设参数（第2.3节）。
- 方法头：作用存在＝通用存在；涉及特征类型＝外设场景标识；可能结果＝输出队列类型。
- 目标：与当前交互者已建立连接（双方已有往来）。目标判定：该窗口已收到当前交互者的消息 → 目标已满足，不执行（对方先开口时不需要打招呼）。
- 必要条件：

| 条件 | 声明位置 | 不满足时 |
| --- | --- | --- |
| 自我已取得交互者（参数1交互者值属于交互者类型值域） | 执行分支必要条件 | “有交互者”子需求，由获取交互者满足 |
| 参数2具备外设场景标识 | 初始必要条件 | 进入交互一类子需求 |
| 交互窗口（存在）具备外设场景标识与输出队列等特征，且当前值有效（与外设窗口一一对应） | 由交互窗口的特征声明（初始必要条件/执行分支必要条件，第4节第1项）；入列时据标识作用于外设 | 零动作 |
| 打招呼所需语言知识齐备 | 运行时复核 | 零动作；后续语言学习子需求 |

- 结果：发出招呼后，等待对方消息出现（结果知识按运行结果取得，第2.1节）；连接由对方回应后的场景信息判定达成，本函数不自证。对方消息到达时由场景信息唤醒等待中的任务（同 ASK-READ-SCENE 唤醒机制）。
- 话语选择：由表达组织知识按条件选取（如首次接触、再次接触），不随机、不把几种说法当作完全相同任选（“没有完全相同的存在”）。
- 业务结果值域：已入列；入口拒绝（窗口失效、缺知识、停止）；目标已满足；动作结果未知（已进入动作后留档或入列未完成）。
- 工程故障：投影身份不符、入列回执不全、留档读回不符。
- 依赖：
  1. 招呼按 7240 表达用途“招呼”（v2.6，R110）；带询问内容的说法按其内容为疑问。
  2. 表达组织知识需有招呼条目（施工时补入表达组织知识种子）。
  3. “请问有什么可以帮到你吗？”这类说法不构成冲突（2026-11-10 用户裁决）：建立连接可以用它作为打招呼的话语，询问服务对象需求也可以用相近说法；两者目标不同（前者引出往来，后者取得对方需求），各自由表达组织知识按条件选取话语。
- 消费者：哪些目标以“已建立连接”为条件另行确定；获取服务对象新需求链路中，对方尚未开口时可经此引出对方说话。

### 3.3 获取交互者（`builtin.interactor.acquire.v1`）

按窗取材读取外设所有者的正式窗口、会话、外设场景及该场景内的对端事实。取材不改变外设、实体特征或场景。它为自我提供本窗认知的材料。取材无需等内部交互场景成立，也不以本窗对端已属于现实树为前提。

1. 按明确窗源办理时，只读对应窗口。带明确确认的输入核外设所有者保存的同窗确认、窗口和对端。无来源或多个候选均待定。开页形成的传输与对端材料不等于自我的交互确认。
2. 窗口取材返回同窗来源及对端事实。自我按 [6120 §11.1](6120_子规范_自我存在服务与生存基本因果闭环.md) 核验确认并组织内部临时场景。已核验的对应身份可按其正式来源引用，未核实的对端只作为本窗局部存在。普通网页全局登录人或接纳人不能填入按窗对应结果。
3. 既有治理任务分支的目标是自我“交互者”实例特征。该分支保留现有零参数召回、结果组和执行条件。没有显式窗源时，仅在具有唯一已确认的外设窗源时取材。取材成功只证明本窗来源。服务准备链可以使用经自我认定为人类、且同窗正式可读的局部对端作为自我“交互者”的单引用值，不要求该对端的实名或既有现实存在对应。无法认定人类、窗源不唯一或发生变化时沿原零动作“未取得”返回。该引用保留局部身份。
4. 正式结果分别表示窗口取材及既有治理分支，语言按 [7241 §1](7241_子规范_句子转换与交互场景同步.md) 接收内部临时场景已固定的原消息角色。取材、内部场景建立、服务对象资格及治理需求由各自所有者负责。


### 3.4 从交互窗口获取服务对象（R130）

服务对象的上位资格是有权限的人类，或指定的具有意识的存在。本方法只办理外设窗口的人类分支。外设被动发表新交互场景，自我常驻接收正式新场景事件。每个新窗口只发起一次，无需需求或任务。唯一业务参数是外设交互场景稳定编码。页面、消息和确认的关联由外设正式所有者核实，普通收件不发起新处理。后到的同窗资料可续办原处理。既有临时交互场景的确认与来源规则见 [6120 §11.1](6120_子规范_自我存在服务与生存基本因果闭环.md)。

依正式窗源取得同一个对端存在。通过存在及概念的通用归属判定区分已有正式证明、明确排除、定义材料不足与对象归属材料不足。词典供学习，用户名、昵称、HTTP 或收件不能直接认定人类或权限。自我依 [6120 §11.1](6120_子规范_自我存在服务与生存基本因果闭环.md) 采用本窗对应后，可对同一个对应存在读取既有正式人类归属。对应本身不产生派发、服务写入或宿主权限。未证实跨窗同一身份时保持不同局部存在。

确认人类后经正式所有者读取服务权限。首次派发无符号整数，值越小权限越高。存在性独立于数值，按自我统一顺序保证先派数值严格较小、同一存在只派一次及达到上限时拒绝新分配。服务权限不授予宿主管理权限。正式登记将该存在的稳定引用作为自我服务对象特征的值并选为当前。已有引用复用，已是当前可零写。保留历史值、按成功登记顺序更新当前。

独立的既有需求可读取正式结果。取材、判定、派发与登记不自动建立子需求、任务或结算服务根。旧 v5 六位字段、方法配对和既往采用按历史身份读取。新窗触发不沿旧任务选择或预设人类条件。该分支覆盖第2.1节任务触发的一般时序，记录实际事件来源、已取得结果和缺项。


本分支的写入操作是自我的被动动作「确认并登记本窗服务对象」。新窗通知只取得并等待材料；正式本窗认知发表后的同源事件才续办该动作。唯一业务参数为外设交互场景编码，宿主提供自我与其服务对象特征接口。通过内部场景当前认知及原消息来源核验当期对端；普通重投、相同认知的新消息以及旧窗材料不能触发切换。已有对端仅在新的有效窗口认知确立且与当前不同的时候可切换。同一认知取得已是当前时零写。认知待定、明确否定和恢复门禁均保持原账；实际登记与资格观察分别读回。

动作来源为同窗当前正式认知。登记变化以有明确身份的被动动作回执同组关联服务对象结果状态，与首次权限一起提交；没有实际写入时不构造成功动作回执，不借任务执行 X。普通应用写入受 [4015 §15](4015_子规范_基础数据集.md) 完整数据集恢复门禁约束，具名隔离工程只验证本次活动数据集合同。登记不改变安全值、服务值或宿主权限。

### 3.5 获取服务对象需求节点（`builtin.service_object.demand.acquire_node.v1`）

- 修改对象：服务对象“需求”特征当前引用被认知需求D（自我对对方需求的认知，虚拟存在）。原因：服务链要求服务对象有经确认的完整需求。目的：服务对象需求特征引用D。
- 不修改D的信息完善阶段（2026-11-10 用户裁决“移出由需求owner自动维护”）：完善阶段由需求owner在字段更新的同一次发布中按必需字段是否已全部确定自动维护（5170 §2.2）。
- 参数：1 人类｛对象需求类型｝；2 对象需求特征（所属1）；3 被认知需求D（范围概念为需求根概念的先天下位概念“被认知需求”，3100第1节，R118）。
- 方法头：作用存在＝人类；涉及特征类型＝对象需求类型；可能结果＝完整被认知需求概念。
- 必要条件（现行运行时核对的项应全部声明）：参数1属于人类（已声明）；参数2是参数1的特征；参数3属于被认知需求（由参数规格范围概念保证，归属按5170第2.4节由owner判定）、主体＝参数1；D来源为“旧理解确认”或“首次接收认知”；D信息完善阶段为已完善（各必需字段已有确定值，5170 §2.2，未完善时由补问链路补齐）；D内容确认为已确认（R106，未实现）。
- 正常结果：服务对象需求特征当前引用D。
- 业务结果值域：已取得；入口拒绝（材料待齐、需重新确认、前提已变化）；动作结果未知。
- 不为服务对象新建需求特征：服务对象的“需求”特征由需求owner在建立以该服务对象为主体的被认知需求时同次确保存在（无当前值），不由本函数附带新建（依本规范第2.2节与 R110 推导状态由owner维护）。

### 3.6 询问指定需求字段（`builtin.demand.field.ask.v1`）

依据 2026-11-10 用户裁决（CONV-INSTINCT §6.6、§6.7）与 2026-11-12 用户裁决（问完须等到答案；答案按结构比对；答案由父任务写入，R114）。

- 修改对象：
  1. 现实世界：经窗口说出一句问话（外设输出队列新增一条）。原因：补问需求Q要求被认知需求D的某一栏有确定值，该值只能由交互者提供或由自我找到。目的：自然语言世界中出现该问题的答案。
  2. 内部记录：留档出站具体表达，并由语言owner在出站来源语言场景中建立“问题”存在（7240第5.5节）；建立说话动作动态。
- 三场景分工（7240第1节）：外设场景由外设类管理，记录和执行事实；语言场景把自然语言转换为内部可认知信息；内部场景读取两者并按需求写入。本函数经外设场景说出问话，在语言场景等待答案；答案写入D不在本函数内（第3.7节）。
- 本函数不关心问谁：只关心问什么（Q）和在哪说（窗口）；听的人由窗口所在交互决定；补问对象是自我当前交互者，不是“受询者”角色。
- 参数：1 补问需求Q（范围概念为需求根概念的先天下位概念“补问需求”，3100第1节，R118）；2 自我（自我范围概念）；3 窗口副本（通用存在｛外设场景标识｝）；4 外设场景标识特征（所属3）。
- 方法头：登记声明不变（作用存在＝通用存在；涉及特征类型由参数规格导出；可能结果＝输出队列类型）；“问题答案有值”这一结果经学习生成的新条件结果对表达，不改登记结果组（2026-11-12 用户裁决）。参数1范围概念由需求根概念改为“补问需求”属参数规格修改，按5350第6节随函数声明在登记阶段原地修订，不改登记结果组（R118）。
- 必要条件：

| 条件 | 声明位置 | 不满足时 |
| --- | --- | --- |
| 参数1为引用某被认知需求某一栏（单个受支持字段）的补问需求 | 参数规格（参数1范围概念为“补问需求”；由补问叶子召回按参数范围概念归属区分〔5350第8节第9项〕与参数1正式指定保证，R118） | — |
| 参数3具备外设场景标识 | 初始必要条件 | 进入交互、建立连接一类子需求 |
| 自我已取得交互者（参数2交互者值属于交互者类型值域） | 执行分支必要条件 | “有交互者”子需求 |
| 自然语言世界中该问题尚无答案 | 初始必要条件 | 已有答案则目标已满足，不问 |
| 问话的被问结构可确定：参数1所指栏为载荷栏（目标形式、值域、比较关系、变化方向）时，被认知需求D的目标存在与目标特征类型已有确定值；所指栏为目标存在或目标特征类型时，D的需求主体已有确定值（被问结构见7240第5.5节，R120） | 初始必要条件 | 提出条件子需求（要求D相应栏有值的补问需求），补齐后再问 |
| 交互窗口（存在）具备外设场景标识与输出队列等特征，且当前值有效（与外设窗口一一对应） | 由交互窗口的特征声明（初始必要条件/执行分支必要条件，第4节第1项）；入列时据标识作用于外设 | 零动作 |
| 表达所需语言知识齐备 | 运行时复核 | 零动作；后续语言学习子需求 |

- 先后顺序（R120）：补问之间的先后由条件形成，不另设逐栏先后表；同一被认知需求各栏补问之间没有条件依赖的，不排先后。
- 执行时材料：受话者由所属内部交互场景按本次表达指定（7241）；D主体与受话者是否相同决定其表达角色。
- 目标判定：自然语言世界中该问题已有答案，或D该栏已有值（或不适用） → 目标已满足，不执行。
- 正常操作：
  1. 组织问话、成文并回读，建立说话动作，留档出站具体表达；语言所有者记录参数1补问需求与原实际提问的正式结构及所求项的对应（7240 §5.5）。问话入列交外设执行。
  2. 入列后进入“动作已发出、等待结果”：结果检测按结构比对查询自然语言世界中该问题的答案（7240第5.5节）。未找到时保持等待，不轮询；自然语言世界有新信息生成（消息转换完成或自我写入）时唤醒检测，依赖键为原提问结构或其所在交互。
  3. 正式所求项取得有效答案时，按原提问结构读出类型化答案及来源；询问结束。
- 正常结果：取得正式原提问所求项的答案和来源。保留补问需求与实际结果的关联供学习读回。出站留档及传输事实各自可读；补问需求的满足仍取决于父任务按5260 §5.2首次写回 D 后的正式复核。
- 业务结果值域：已取得（来自交互者／来自自我）；目标已满足（已有答案或D该栏已有值，未问）；等待中（问话已入列，尚无答案）；入口拒绝（窗口失效、缺知识、缺名称、缺指称、多义、停止）；动作结果未知（已进入动作后留档、建立问题或入列未完成）。
- 学习：模拟世界执行不了本函数时，模拟学习只生成条件节点，结果节点为空；真实执行后按“问题的答案有值”补全结果（尝试学习，5370）。
- 工程故障：投影身份不符、入列回执不全等。被问结构不可确定不属工程故障，按上表条件进入筹办（R120）。

### 3.7 答案写入被认知需求（非本能）

### 3.8 网页对话三项（`builtin.web_dialog.read_messages/set_input_text/submit_message`）

已退役：无方法声明，生产代码无端口装配，永远返回“依赖未装配”。按旧代码处置规则（AGENTS §5，2026-11-10 用户规则）直接停用并删除：三个转发函数、登记名、端口槽及装配中的旧登记退役检查一并删除。本规范不为其定义合同。

## 4. 跨本能缺口

1. **世界事实类条件（2026-11-10 用户裁决）**：按实际遇到的情况逐个确定，不预设统一机制。自我内部的逻辑交互场景有对应的存在——交互窗口；交互窗口有自己的特征（外设场景标识、输出队列、接收等），与外设场景中的窗口信息一一对应。窗口相关条件按交互窗口这一存在及其特征声明：交互窗口作存在参数，以参数规格必需特征、初始必要条件或执行分支必要条件声明其特征及当前值要求；本能只在实际作用于外设时（如入列）据标识对应外设。
2. **条件与结果组的来源（2026-11-10 用户裁决）**：方法函数生成方法头时同时生成结果组（作用对象与被改变特征类型），作为召回依据；先天条件根据方法头节点信息在模拟学习中生成；结果的具体内容按方法运行结果完善。召回不到或学错时，先查方法头及其结果组、参数规格与条件规格是否完整。
3. **执行实例与任务状态核对**：服务对象族已核对方法节点、执行实例、任务状态，进入场景未核对；应作为所有本能的统一入口复核（宜并入5360）。
4. **目标判定位置**：各本能“目标已满足”的判定应统一在筹办阶段，入口复核只作兜底。

## 5. 与现行规范与设计的关系

2. CONV-INSTINCT 详细设计中已上升为本规范的内容（§4 出站本能统一形态中的合同部分、§6.6、§6.7 的合同部分）以本规范为准，详细设计只保留施工信息。
3. 已在规范目录登记，3300 §8 子规范路由已增加，0300 登记 R110。
