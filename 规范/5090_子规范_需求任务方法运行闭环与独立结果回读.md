## 1. 定位

本规范规定一个已经确认的需求如何由任务承接、采用方法、执行动作、取得真实结果、形成影响评估并由self决定后继。它只定义对象间运行闭环，不把需求、任务、方法、世界事实、任务结算或学习材料合并成一个对象。

现行闭环为：

```text
具体需求D
-> 建立或复用唯一任务T及任务虚拟存在Vt
-> manager按当前状态筹办：查找方法、检查条件、绑定参数和结果获取方案
-> self执行前综合判断
-> 建立执行实例X
-> W3-A执行一次真实动作
-> W3-B经已绑定渠道取得真实结果
-> 形成实际状态与影响评估A
-> T进入等待自我决议
-> self fresh读回D、T、X、A和当前世界事实
-> 决定完成、继续、重试、重新筹办、等待、失败或取消
-> manager复核并由任务类发布状态
-> 只有正式完成的T可以按任务身份结算一次
```

这条链没有任务轮次、筹办轮次或执行轮次。一次真实方法调用只对应一个执行实例X；筹办是围绕当前T补齐可执行材料的过程，不取得独立业务身份。

## 2. 对象和唯一职责

### 2.1 需求D

D是目标权威。一个D只表达一个状态改变，目标状态可以是复合状态。任务不得复制、改写或重新解释D的目标；每次判断是否仍需治理时都由需求类fresh读取当前目标和当前值。

需求树承担分解关系。任务没有任务树；任务推进中产生的新目标必须先由self确认并通过需求类建立或复用子需求，再由该子需求建立自己的任务。

### 2.2 任务T与任务虚拟存在Vt

一个T恰好对应一个D，一个D最多对应一个T。Vt只承载该T的任务状态实例特征，不是世界存在，不进入世界树。

T是长期治理身份。`已完成`、`已失败`、`已取消`是当前收束状态，不是永久销毁；同一长期需求再次需要治理时，self可以fresh确认后请求manager复核并重新启用原T，但只能回到`待查找方法`或`等待条件`，不得直接进入执行。

### 2.3 方法与执行实例X

方法是可复用动作知识，规定动作、适用条件、参数和需要确认的结果，不证明某次执行已经成功。

每次真实方法调用建立一个X。X至少绑定T、采用的方法、动作开始/结束、预计变化、实际状态和影响评估定位。一个X只允许一次W3-A；W3-B可以在动作后延迟、多次唤醒或更换合法备用渠道，但不得据此重做W3-A。

### 2.4 影响评估A

A回答“本次执行实际发生了什么”，至少区分：

- 预计变化是否出现；
- 计划外变化是否出现；
- 方向、幅度或值域是否可比较；
- 必要结果材料是否缺失或冲突；
- 需求在fresh读回时是否满足；
- 是否出现禁止结果、副作用或安全事件。

A不决定任务终态，也不代替需求满足结论。

### 2.5 治理上下文

治理上下文是self或manager推进当前T时，对D、T、Vt、方法配对、临时只读参数场景、X、结果方案、当前资源/安全材料、等待条件和原请求定位的运行期组合读取。它没有独立稳定编码，不建立“上下文节点”，也不保存第二份目标、任务状态或世界事实。

动作前，任一影响实际调用的对象、参数、方法、结果要求或结果方案变化都使原选择失效并回到筹办。动作已经发出或可能发出后，不得通过改写上下文把旧动作解释为新调用；只能沿X中冻结的原方案及其允许备用渠道继续W3-B。

## 3. current-only读取和一致性

全部业务读取采用current-only fresh读回，不使用事实代次、共同事实截止、历史读回、墓碑或业务历史拼接结论。

需要多个字段共同成立时，提供者必须在一次组合查询或一次受锁保护的完整读取中返回自洽结果；调用方不得用多次独立读取假装取得共同快照。跨领域链路按顺序读取和复核，后一步发现前提已经变化时返回重判或重筹办，不用旧材料覆盖当前事实。

稳定编码只证明身份，不证明节点业务类型、归属或合法状态。每个业务类必须通过自己的完整读取核验结构。

## 4. 筹办与执行前硬门

筹办按当前T状态逐步补齐：

1. fresh读取D的目标；目标已经满足时零动作进入self决议。
2. 按目标特征类型召回方法，再检查完整条件、参数、作用对象和禁止项。
3. 依据自我当前拥有且可用的感知渠道，形成至少一条明确、合法、可实现的结果获取方案；每条方案明确对象和精确特征、具体渠道、正式读取入口、触发时点/等待条件、证据质量、结果判定及不可得处理。
4. 比较可执行性、预期损耗、安全限制和当前资源；无法裁决或并列无法选择时不执行。
5. 冻结本次方法、参数、预计变化、结果要求和获取方案。
6. self结合当前需求、资源和安全事实作执行、暂缓、拒绝或重判决定。

无结果获取方案时，普通、探索和试验任务一律零动作。结果可以延迟、异地或通过视觉、听觉、触觉、设备读回、网络反馈、他人陈述等渠道取得，但必须在执行前明确如何最终获得和判定。仅知道“以后可以观察”、仅登记一种感知能力或只有动作函数返回，不满足本硬门。

## 5. W3动作与结果获取

### 5.1 W3-A动作执行

worker在临近调用前复核T、X、冻结材料、控制状态、安全硬门及必要授权。复核成功后只调用一次动作入口，并记录动作已发出或明确未发出。

函数返回、命令已发送、日志成功或预测命中都不能直接证明现实结果。动作发出后发生记录或投递故障时，必须保留“动作可能已发生”的状态，禁止再次调用来试探。

### 5.2 W3-B结果获取

W3-B只负责按冻结要求取得结果材料：

- 立即可得时，可以在同一worker工作中完成；
- 需要等待时，释放worker，把T和X置于可恢复等待；
- 条件到达后建立新的W3-B工作，不重新进入W3-A；
- 渠道永久失效且无合法备用时，保持结果未知，由self决定等待、失败、取消或重新筹办；
- 多渠道按冻结的任一、共同满足、优先、备用或冲突规则处理，不默认多数表决或任选有利结果。

观察方法的正式输出可以直接成为结果材料。内部治理或仓库动作必须从相应业务类重新读回当前结果，不得用动作函数的局部返回对象代替正式事实。

W3-B只有在冻结方案要求的必要证据均已取得、各渠道按任一/共同/优先/备用规则完成组合、冲突被显式裁决且允许/禁止结果均已得到所需判定时，才形成“结果闭包”。材料已经出现但质量不足、必要渠道缺失、陈述只能证明陈述事件、来源互相冲突或正式读取入口尚未返回时，都属于结果未闭合。

## 6. 结果、评估和self决议

manager收到W3材料后必须独立读回T、X和正式状态材料。结果闭合时结束X并触发A；结果不足时保持等待或结构化非成功，不伪造空结果。

结果获取、影响评估和结果回流严格分账：W3-B只取得证据，A只解释预计与实际及归因，manager消息只通知self读取哪些正式对象。消息成功、A已建立或D当前满足，均不能单独证明本次X成功。

形成A后，T先进入`等待自我决议`。manager只把T、X、A及必要结果定位通知self，不能自行选择终态或后继。

self必须fresh读取：

- 当前D及其目标；
- 当前T和Vt状态；
- X、正式实际状态和A；
- 当前世界事实、资源和安全材料；
- 适用的等待条件或新筹办条件。

self可以形成七类决议：

| 决议 | 含义 |
| --- | --- |
| 完成 | 当前需求目标fresh满足，结果闭包完整，必要验证通过或明确不适用，没有未处理的禁止结果/冲突，且归因满足方法要求 |
| 继续 | 当前方法仍适用，但必须回到合法非执行状态后再建立新X |
| 重试 | 上次动作明确未发出或具名可重试失败；不得重试结果未知的已发动作 |
| 重新筹办 | 方法、条件、参数、方向或结果方案需重新选择 |
| 等待 | 已知合法生产者、条件或结果渠道尚未到达 |
| 失败 | 当前目标在现有能力和条件下明确不能继续达成 |
| 取消 | 目标不再应由该T推进或收到合法取消决定 |

manager复核决议与当前T闭包后，由任务类发布相应状态。旧消息、线程重启、队列重放或时间经过不能自行改变决议。

## 7. 完成结算、需求复核和重新启用

任务状态、任务完成结算、需求当前满足和价值结算必须分账：

1. A中“需求满足”只是一项评估材料，最终仍由self fresh读回D后确认。
2. 只有正式`已完成`的T可以结算；同一T最多成功结算一次。
3. `已失败`和`已取消`不做任务完成结算，但其实际结果、副作用、安全事件和方法反馈仍须处理。
4. 任务完成不删除D；需求以后可能因当前值变化重新变为未满足。
5. 已结算任务重新启用后不得撤销或重复原结算；后续执行实例仍属于同一T的继续治理材料。

任务结果不是容量、份额或可领取资源。一个状态变化可以使多个需求分别满足，但每个需求都必须在实际使用时fresh独立判断，不建立结果共用、争用、分配或剩余量账。

服务值变化是任务完成后的另一项独立内部治理结果。只有本T对应已确认的人类服务需求，且服务对象现实改善、观察验证、归因和防重复材料均符合6190时，self才可提交服务值结算；T已完成、完成结算成功或D当前满足都不能单独增加服务值。6190结算或衰减完成后必须fresh读回账户，不能把本次任务结果直接写成服务根当前值。

## 8. 学习与方法反馈

任务可以把预计与实际差异、条件不适用、方向错误、幅度偏差、结果渠道问题和副作用作为方法学习材料。学习只消费已经正式形成且来源完整的X和A，不阻塞原任务的状态收束或适用的完成结算。

任务、manager、worker和self不得直接改写共享方法知识。是否形成或修改方法由方法治理合同独立裁决。

## 9. 禁止规则

禁止：

- 建立任务轮次、筹办轮次、执行轮次或用计数器模拟这些对象；
- 一个T承接多个D，或用任务树代替需求树；
- 用日志、消息、函数返回、执行报告、状态/动态的后态替代当前事实读回；
- 无结果获取方案仍执行动作；
- 动作结果未知时盲目重做；
- manager、worker或影响评估绕过self决定终态或后继；
- 失败或取消任务伪造完成结算；
- 把执行实例收束、任务完成、任务结算、需求满足和价值结算合并；
- 用事实代次、历史截止、业务历史或旧owner分区恢复旧闭环。

## 10. 验证与声明边界

最低验证应覆盖：

- D与T一对一建立、复用和冲突；
- Vt状态机和收束状态重新启用边界；
- 目标已满足零动作；
- 无结果方案零动作；
- W3-A只执行一次及W3-B延迟恢复不重做动作；
- 多渠道成功、冲突、失效和结果未知；
- 结果材料已到但结果闭包因质量、禁止结果或归因不足而不能完成；
- X结束、A形成、manager定位回流和self fresh决议；
- 七类决议的合法状态迁移；
- 正式完成最多结算一次，失败/取消零完成结算；
- 任务完成结算与6190服务值结算分账，服务证据不足或规则缺失时零增加；
- 重复、乱序、丢失消息及重启后的current-only收敛。

规范发布只证明机器语义已经冻结，不证明代码、生产装配、网页端口、外部观察渠道、跨进程恢复或完整治理闭环已经实现。
