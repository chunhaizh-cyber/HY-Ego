# 7150 子规范 存在信息字段关系与数据操作

编号：7150
日期：20260907
版本：v0.2
状态：正式子规范

直接上级规范：1140、1150。

直接依赖规范：4010、4015、4110。

相关边界规范：1130、2100、3100、4030、4200、4230、6220、6230、6240、7130。

## 1. 定位与承载

本规范展开存在信息的字段、关系及数据操作，不定义存在识别、组成认知、空间计算或需求治理算法。节点、关系、值复用 L1；不建立存在专用事实仓、新结构 owner 或第二权威列表。

存在信息只使用 1140 的三项逻辑字段：存在节点身份、自身特征引用集合、可选内部场景引用。节点身份定位对象；集合和引用通过正式关系取得。读回对象由调用方持有，只是值式投影，修改它不会修改存储事实。

未关联特征时返回空集合，未关联内部场景时返回明确无引用；这些结果不等于存在身份不存在。没有已知直接归属时如实返回无归属，不默认填入世界根、最近场景或自我场景，也不声称已完成现实定位。

## 2. 特征引用

1. 准确特征 F 按 1130 / 4110 独立成立，类型和值固定。存在只引用其节点，不复制内容、不建立旧宿主实例槽，也不把概念名称关系纳入存在的第二写入口。
2. 一个存在可以引用同一特征类型的多个不同特征信息，保存不同轮廓、方向或其它识别信息；不能按特征类型强制覆盖为唯一一项。已知特征引用集合不等于当前观察集合，不能因同时保存正面和侧面轮廓就把两者都当成本次观察；当前观察以准确采用关联确定。同一关系角色下指向同一特征节点的重复引用不重复建立。
3. 特征值可以按其正式合同为内联 I64 或稳定值身份引用。存在类不改写值表示，也不从轮廓、坐标、名称等业务含义发明新字段。
4. 特征结构服务保存固定准确 F；存在类只维护本存在的已知特征与当前采用。新观察使用不同准确值时建立或复用另一 F，再改变采用；解除或替换引用不删除或改写旧 F。
5. 当前特征读回先取得该存在在本次一致读取范围内的当前采用关系，再读取目标 F 的准确类型和值。不同存在可以共享 F，但各自采用独立；仅缓存 F 或读取旧 F 不能证明当前采用。名称改变也不证明存在值发生变化。
6. 已知特征引用集合承接该存在已确认的不同准确特征，用于后续识别；它不等于每次观察的时间档案。需要范围概括时可引用7160共享概念，但须保留该范围适用于本存在的真实依据；全类型概念或其它存在支持的值不能反推为本存在历史。当前变化判断仍使用前后采用的准确内容及正式比较规则，不能只比较概念是否相同。

## 3. 关系分类与唯一直接归属

| 关系 | 逻辑方向及用途 | 归属和操作边界 |
| --- | --- | --- |
| 存在特征引用 | 存在 → 特征信息。 | 存在类维护本存在引用；特征类维护特征本身。 |
| 存在组成关系 | 父存在 → 子存在。 | 存在类维护；反向查询同一事实取得直接父，不另存父列表。 |
| 场景成员关系 | 场景 → 成员存在。 | 场景类维护；反向查询取得存在的直接所属场景。 |
| 内部场景宿主关系 | 场景 → 宿主存在；从宿主反向读取内部场景。 | 场景类维护既有宿主关系；不存在第二条存在 → 场景权威镜像。 |
| 其它具名存在关系 | 存在 → 存在，含义由正式关系类型定义。 | 由该关系所属数据类维护；不得以普通关系冒充组成或场景归属。 |
| 需求所属及目标引用 | 需求 → 所属存在，或需求 → 目标宿主。 | 需求类维护；存在相关需求通过这些事实查询，不复制为本体字段。 |

同一当前结构中，对每个存在，将指向它的组成关系与场景成员关系合计，数量只能为 0 或 1。约束跨全部场景成立，不按场景树、内部 / 外部视角或两种关系类型分别计数。关系尚未建立与已经建立的唯一关系必须分账。

组成与场景范围不等义。例如发动机可以组成汽车；乘客可以是车内场景成员，但不因此组成汽车。父存在的直接子存在只能由组成关系确定，不能把内部场景全部成员当作组成部分。墙面等被分别识别为不同存在时各有各自节点和唯一直接归属；不能以显示面不同让同一个节点取得两个直接父存在。

内部场景宿主关系只表示场景视角由哪个存在承载，不表示宿主位于自己的内部场景中，不计入宿主的直接归属。每个存在至多关联一个内部场景，每个内部场景至多关联一个宿主，仍使用 4230 的同一事实双向查询。

服务对象、协作、使用等具名引用不是容纳关系；空间远近、方向、相对位置按需要读取特征并经二次特征计算，不预存所有存在之间的两两空间边。

## 4. 递归、内部场景与无环

1. 直接归属与递归归属分别查询。螺丝直接组成发动机、发动机组成汽车、汽车直接属于车库时，螺丝间接处于汽车和车库；不为它补写越级组成或车库 → 螺丝的直接归属事实。
2. 内部场景的直接存在视图由“宿主的直接组成子存在”和“该内部场景自身的直接成员”形成；读取必须区分两种来源。递归展开另行沿关系读取，不把全部后代伪装为直接子存在。
3. 已组成宿主的子存在在内部场景中出现只是展开投影，不建立第二条场景成员边。未认定为组成部分的内部成员仍保存自己的唯一场景成员关系，不因展开自动形成组成边。
4. 普通存在的内部场景按应用需要建立，不因节点创建、名称或已知子关系自动预建。组成关系可以先于内部场景存在，数据层不能以尚无内部场景拒绝合法组成关系。自我是否必须初始化内部场景由 7130 规定。
5. 无环检查按包含的展开方向联合执行：父存在 → 组成子存在、场景 → 成员存在、父场景 → 子场景、宿主存在 → 内部场景，以及内部场景 → 宿主的直接组成子存在。后两项分别是物理宿主关系的反向展开和第 2 项的虚拟投影边，都参与检查，但不因此建立第二权威关系。不能只检查物理边方向或组成边；任何组合路径回到原节点均拒绝，包括存在成为自己内部场景的直接或间接成员。
6. 未展开、没有子关系或某观察算法到达停止粒度都不等于客观不可分。具体观察的质量、掩码和像素停止条件由 6230 / 6240 管理，不成为存在类通用创建前置。

## 5. 状态、动态与需求关联

存在本体不保存自身状态和动态集合。状态 / 动态由对应数据类独立保存；存在作为场景时，可以通过场景事实目录组织其内部所描述存在的状态 / 动态引用。每份引用必须能准确定位目标事实、被描述存在及特征上下文，不能仅凭“属于这个场景”推断是谁发生变化，也不能为方便读取给状态本体再加所属字段或另建状态副本。

场景当前成员投影与场景历史事实目录不是同一集合。存在离开、改挂或组成认知修正，不使其已发生状态 / 动态无效；不得依当前成员关系重写历史所属或自动删除历史事实。目录解除只移除引用，目标事实的删除或保留由所属数据类合同处理。

需求独立集中保存，已有需求按所属存在查询。所属存在回答“谁的需求”，目标宿主回答“希望谁的特征达到目标”，二者不能混用。当前自我确认的需求、他者表达的请求以及自我对他者的推测不是同等确定的需求事实；后两者先作为带来源的判断材料，正式需求产生确认仍按 3100。

当甲是服务对象，自我承接让甲达到某目标时，形成的自我需求仍属于自我，甲是目标涉及的存在。存在关系不能直接证明服务有效、任务完成或服务值增加。

## 6. 必须提供的数据操作

下面固定操作语义及责任，不以这些中文类别冒充已经存在的 C++ 函数或 DTO。

| 操作类别 | 定位和必要输入 | 成功后的事实 |
| --- | --- | --- |
| 新建、读取、删除存在 | 新建提交合法初始信息；其它操作按存在节点定位。 | 新建返回稳定节点；读取不隐式补建；删除服从第 7 节。 |
| 特征引用增、删、改、查 | 存在节点，加被操作关系 / 角色及目标特征节点。 | 只改变本存在引用；特征字段仍由特征类操作。 |
| 组成关系建立、解除、替换 | 父 / 子存在节点；替换须明确原关系与新父。 | 保持唯一直接归属、引用完整和无环，不复制子节点。 |
| 直接父、直接子与递归祖先 / 后代读取 | 存在节点；递归读取明确范围与预算。 | 依据同一关系事实形成投影，直接与间接不混淆。 |
| 场景归属建立、解除、替换、反向读取 | 按场景类合同传入存在、场景及被操作关系。 | 与组成关系联合唯一；不在存在类复制场景 CRUD。 |
| 内部场景关联建立、解除、替换、查询 | 场景类按存在节点反向定位宿主关系，修改还需目标场景。 | 使用同一宿主关系，保持两端至多一项及无自包含。 |
| 本类其它具名关系增、删、改、查 | 存在节点、正式关系类型、方向及目标节点。 | 只操作所属关系，不替业务解释真实性或改变端点本体。 |

节点身份是定位起点，不是修改的全部参数：设置新引用仍要新目标，解除或替换仍须能指明原关系；不要求调用方传回整个旧存在对象，也不从名称、内存地址或缓存反推身份。

查询空集合、无可选引用、对象不存在、引用冲突、读取不完整和内部不一致必须分账。查询不能隐式新建或移动对象；索引只能召回，成功必须回读节点及准确关系。预算不足不得把部分组或被截断路径称为完整结果。

存在相关数据操作的完整性不要求存在类反向调用所有其它数据类。特征引用由存在类负责，特征内容由特征类负责；场景关系及其反向查询由场景类负责，需求由需求类负责；上层组合公开能力，不取得私有端口，也不新增纯转发层。依赖和唯一结构分区仍按 4030 / 4230。

## 7. 写入、移动与删除的可靠性

1. 归属写入必须联合检查组成与场景成员两类关系及完整包含路径。组成、场景成员、子场景或宿主关系的任何变更都须重验受影响的实际与虚拟展开路径；不能各自检查本类唯一，也不能用应用层先查再分别写来规避并发冲突。
2. 普通新增归属遇到已有不同直接归属时拒绝，不能偷偷改挂。移动是明确的原关系到新关系替换；场景到场景、场景到父存在、父存在到场景及父存在到父存在都保持同一存在身份。
3. 旧归属移除、新归属建立及必要唯一性 / 无环守卫必须在同一个可靠原子提交边界闭合。L2 形成所需结构组合，L1 执行可靠提交；涉及不同内部结构分区时复用已有中性原子能力，不新增 L1 领域入口，不向普通调用方暴露写集、锁或端口。
4. 提交前拒绝或失败时不产生公开半结构，旧归属保持不变；已确认提交后读回失败，不得宣称旧归属仍有效、回滚已发布关系或换新请求重做，按原请求可靠读回和非成功合同收敛。
5. 特征引用、内部场景宿主、普通关系和节点删除分别操作。解除关系不删除端点；删除存在前必须闭合仍受保护的引用，不能级联删除特征、组成子存在、内部场景、需求或状态 / 动态。仍有合法引用而无法在许可范围闭合时拒绝删除。
6. 索引只是可重建投影，不与关系各存一份权威父、子或所属场景集合。持久保存及重建后仍必须满足同一唯一性和引用规则；可靠性材料不进入存在本体字段。
7. 尚无满足联合守卫与原子替换的提供者时，对应变更能力属于待实现，不得退化为两次普通 CRUD 或返回假成功。具体函数 / DTO、关系稳定类型与物理映射由后继正式设计落实本规范，不借旧存在 ABI 或旧内部成员合同产生继续写入授权。

## 8. 验证语义

验证至少覆盖：

1. 新建后按节点读回；特征或归属改变不换身份；无关联与对象不存在分账。
2. 同类型多个特征可保存，重复引用不重复建立；共享特征的不同存在采用值不串写。
3. 两个场景、两个父存在以及场景加父存在的并存归属都拒绝；跨不同场景树同样拒绝。
4. 四种归属替换逐项读回；并发争用最多一个成功，提交前失败保留旧关系，提交后读回失败不假装回滚。
5. 组成自环、多层祖先环和经内部场景 / 场景父子 / 成员的混合环都拒绝。还须覆盖：P 组成 C，S / T 分别以 P / C 为宿主，T 是 S 的父场景；即使物理关系无环，也必须因虚拟展开 S → C → T → S 成环而拒绝。
6. 内部场景展开能同时展示组成子存在及非组成直接成员，区分来源，且不增加直接归属边。
7. 直接与递归查询区分；清空或重建索引不改变关系；不完整或超预算不返回假完整结果。
8. 移动后历史状态 / 动态不改写；解除目录、特征或需求关联不自动删除目标事实。
9. 删除有引用的存在不会留下悬空关系或误删子存在；他者请求和服务关系不自动生成正式需求或价值结果。

本规范固定字段、关系和操作要求，不声明新数据类已实现、旧代码 / 数据已迁移、构建通过或 DATA-L2 已收口。旧规则正文由新正文取代；追溯使用版本历史，不保留并列生效的旧存在规范。
