# 第 50 项：方法缺口最终分流

状态：依据正式材料和用户授权已裁决；非正式规范。

裁决依据：4050、5150、5200、5230、5250及6180。现行规范已经冻结闭合结果和错误边界，本项只形成唯一分流顺序，不新增运行期自动学习或自动开发权力。

## 裁决口径

任务筹办发现方法相关缺口后按以下顺序裁决：

1. 前置已经通过后发现按正式合同本应存在的任务结构、授权、提交入口、动作入口或写回入口缺失、复义或损坏，属于内部不一致或开发诊断。立即停止依赖路径并形成开发诊断回执，不得包装为能力缺口、合法等待、普通任务失败或学习需求。
2. 当前事实、输入、参数、条件、外设材料、观察证据或授权暂时缺失，但存在具名合法生产者和可验证重新触发条件时，形成来源任务内部闭环、观察验证闭环、外设材料闭环或合法等待。等待不自动建立子任务；只有目标可正式任务化且合法生产者确实通过任务达成时才形成子目标承接。
3. 已有候选方法且缺口精确定位在该方法的条件结果契约、参数绑定、方法证据或生命周期时，形成能力缺口承接，并绑定缺口宿主、缺口角色、合法处理方和回流条件。
4. 只有正式因果或方法能力确有可定位知识缺口，且学习领域是该缺口的合法处理方时，才进入学习闭环。学习回执或学习需求必须经需求领域正常准入，不得由筹办器直接写入需求树。
5. 缺少代码实现、真实函数入口、服务装配、类型合同实现或状态机实现属于开发诊断闭环，不属于学习、观察、服务准备或普通任务。
6. 完全没有候选方法且尚不能定位具体缺口宿主、角色和合法处理方时，只能形成带重新触发条件的 `无确认路径` 合法等待；不得自动建立方法首、泛化学习需求、能力开发任务或通用写入兜底。
7. 缺口满足多类表象时，按 `内部不一致/开发诊断 -> 已知事实生产者等待 -> 精确方法能力缺口 -> 可证明知识缺口 -> 无确认路径等待` 的优先顺序收束，不能多路重复建账。
8. 每次分流必须形成强类型回执，记录来源任务、筹办轮次、缺口分类、证据、处理方、隔离状态、重新触发条件、事实代次和当前状态。日志、文本或线程消息只作通知。
9. 任一处理结果回流后，父任务开启新的筹办轮次并重新读取全部当前事实，不恢复旧冻结或沿用旧候选结论。

## 边界

本项不授予运行期自动修改代码、规范或方法登记的权力，也不冻结具体学习算法和开发流程。它只消除6180中的“方法缺口最终分流”未决项，不证明正式规范、目标流程图或实现已经同步。
