# 8200 子规范 自我内部循环实现

编号：8200
日期：20261006
版本：v2.6
状态：正式子规范

直接上级规范：0050、3100、3200、3300、8000。

直接依赖规范：5090、5170、5260、5350、5360、6100、6140、6150、6190、6340、8100、8121、8210。

## 1. 定位

本规范展开内部治理主循环的初始化、消息处理、任务推进、W3动作与结果、影响评估、self决议、结算和恢复算法。它不复制需求、任务和方法字段全集，也不把逻辑操作名冒充现有C++函数。

全部读取采用current-only。没有任务轮次、筹办轮次、执行轮次、事实截止、历史读回或业务版本。

## 2. 初始化与开门

self线程启动后按顺序调用公开入口：

1. 初始化全局基础数据集。
2. 初始化世界树根、自我所在场景和自我节点并完整读回。
3. 初始化安全FT/实例特征和6190唯一服务值账户，再初始化需求树及安全、服务双根。
4. 初始化方法根和本能函数登记。
5. 装配manager、worker、邮箱和具名运行配置。
6. 对双根当前需求执行首次fresh复核。
7. 只有上述必需结构和调用链成功时开启治理门。

初始化失败、依赖未实现、身份冲突或结构不一致都保持停门。邮箱清空、线程已经创建或消息已经终结不等于可以开门。

## 3. 主循环调度顺序

self每次被消息、条件变化或停止信号唤醒后按以下顺序处理：

```text
停止与已发生动作收口
-> 正式结果/安全事件
-> 等待self决议的任务
-> 已完成但未结算的任务
-> 已具备6190服务值结算材料的服务结果
-> 新需求或需求变化
-> 普通任务调度
-> 低频方法反馈和维护
```

每个消息处理函数只进行一次有界尝试并返回结构化结论。资源不足、依赖等待和结果未到不得在函数内部无限重试；主循环根据重试时点或明确唤醒再处理。

## 4. 需求处理

### 4.1 根需求

self按根角色fresh读取权威当前值：安全根读取自我安全实例特征，服务根调用6190读取已经维护到本次时点的工程服务值账户。两者分别与目标`INT64_MAX`比较；当前值小于目标表示仍需增加，等于目标表示本维护时点当前满足。根值不允许小于零；比较不通过先做减法，不依赖溢出副作用。服务根差距不得制造人类需求、强行服务或取得现实执行授权。

根需求需要治理时，self向manager发送一个具体D的任务意图。消息不区分“单根/双根需求类型”；一次消息可以触发对多个正式根的分别复核，但每个T仍只对应一个D。

### 4.2 普通需求和子需求

self处理外部请求、任务缺口或观察材料时，先识别服务对象、目标宿主、目标特征、目标值/概念、权限、安全边界和合理性。只有形成独立、必要、父域合法且可最终判定的目标后，才请求需求类建立或复用D。

任务需要分解时建立子需求，不建立子任务树。子需求权重按3100从父需求当前直接子节点平分。

## 5. D到T

manager收到任务意图后：

1. 完整读取D；
2. 查询0..1对应T；
3. 零条时通过任务类建立T和Vt；
4. 一条时复用并核验状态；
5. 多条时报告结构冲突；
6. 对收束T只有在self明确重新启用决议时才迁移；
7. 对活动T按当前状态形成下一工作。

这一过程不签发任务初始化包、任务轮次或阶段版本。需要防重复时使用消息身份、原请求和正式T/D结构收敛。

## 6. 筹办

manager根据Vt状态分步调用worker：

- `待查找方法`：按D目标特征类型召回方法；
- `待检查条件`：读取完整方法定义，检查对象、参数、条件、结果要求、安全和资源；
- 选择阶段：绑定实际对象、参数、预计变化和结果获取方案；
- 无适用方法或条件缺失：形成正式缺口/等待材料交self，不直接失败；
- 目标已经满足：零动作进入self决议；
- 唯一方案成立：推进到`待执行`。

同一T可以多次执行这些步骤，但不形成筹办轮次。临时候选不持久化为第二候选账。

## 7. 结果获取方案

方法定义需要确认的对象、特征、允许结果、证据质量和多证据关系；任务依据自我当前拥有的感知渠道绑定具体方案。

方案至少说明：

- 读取哪个对象和精确特征；
- 使用视觉、听觉、触觉、设备、网络、他人陈述或内部正式读回中的哪条具体渠道及哪个正式读取入口；
- 何时可以读取，延迟时由哪个生产者和条件唤醒；
- 要求何种证据质量；
- 允许结果和禁止结果分别怎样判定；
- 成功、未知、冲突和永久不可得如何判断；
- 多渠道是任一、共同、优先、备用还是冲突关系。

没有至少一条可实现方案时保持零动作。仅有抽象感知能力、未装配设备、日志或本能函数局部返回不构成方案；延迟渠道必须能定位正式生产者、等待条件和最终读回入口。

## 8. self执行前综合判断

self读取D、T、方法选择、参数、预计变化、结果方案、资源和安全事实，返回执行、暂缓、拒绝或重判。

执行分支由manager复核当前状态后建立X。X建立成功且T进入`执行中`后才能派发W3-A。发布未知时按T和X正式读回，不另建X。

## 9. W3-A动作

worker收到W3-A工作包后：

1. 完整读取T和X；
2. 核验T为`执行中`、X属于T、工作包未消费；
3. 核验控制状态、安全硬门、参数和必要授权；
4. 调用一次本能函数或组合方法入口；
5. 返回动作明确未发出、已发出、可能已发出或具名技术失败；
6. 不读取长期结果，不改变任务终态。

动作已发出或可能已发出后禁止重做。即时状态可以触发W3-B，但仍须正式读回。

## 10. W3-B结果

manager根据X的结果方案形成W3-B：

- 立即可读：worker执行一次结果读取；
- 条件未到：登记等待定位并释放worker；
- 正式状态通知到达：根据作用对象和特征查找等待X；
- 登记等待后主动补查现有正式状态，关闭通知先到窗口；
- 渠道失效：选择冻结允许的备用渠道，否则保持结果未知；
- 多渠道：按冻结关系组合，冲突不任选。

worker提交结果前必须fresh读取状态，精确核验作用对象、实际特征节点/特征概念、值和时间窗。只匹配存在节点和粗类型根不充分。

请求材料与fresh接受材料必须完全一致。W3-B永远不能调用动作入口。

必要证据齐备、质量达标、渠道关系完成组合、冲突得到裁决且允许/禁止结果均已核验，才算结果闭合。材料已到不等于闭合；未知、冲突和未验证不得折算成成功。

## 11. 结束执行和影响评估

结果材料满足冻结要求后，manager请求任务类结束X并把T推进为`待影响评估`。任务类只接受正式状态节点，检查时间窗、重复、归属和精确特征身份。

随后形成A。至少判断：

```text
预计命中
预计缺失
计划外变化
方向是否一致
幅度/值域是否达到
材料是否不可比或冲突
禁止结果/副作用
必要归因
D的fresh当前满足材料
```

每项验证区分通过、不通过、未验证、冲突和不适用。某项提供者未实现时标记未验证，不能以对象/类型命中代替。当前只能证明粗命中时，未满足分支优先重新筹办，不盲目继续原动作。

A形成后T迁移到`等待自我决议`。

## 12. self结果处理

manager向self发送待决议消息，只携带T、X、A和正式结果定位。self处理时必须再次fresh读取：

- D目标和当前值；
- T/Vt状态；
- X和A；
- 当前世界事实；
- 资源、安全和等待生产者。

self形成完成、继续、重试、重新筹办、等待、失败或取消。完成必须同时满足D fresh满足、结果闭合、必要验证通过或不适用、无未处理禁止结果/冲突和归因充分。manager复核绑定及当前状态后，请求任务类发布合法后继。

继续不等于复用旧X；重试只适用于动作明确未发出或具名可重试失败；重新筹办回到方法查找/条件检查；等待必须绑定已知生产者或条件。

## 13. 完成结算

任务进入`已完成`后，manager保留X、A和运行定位并通知self。self：

1. 读取T当前状态；
2. 读取完成来源、相关X、A和结果闭包；
3. 查询该T是否已有完成结算；
4. 未结算时以原请求调用任务类；
5. 同义重复读取既有结算，异义冲突；
6. 成功后通知manager释放运行定位。

失败或取消不做任务完成结算。完成结算不等待需求结算、价值变化或方法学习。

只有T对应已确认的人类服务需求，且现实结果、服务对象改善、观察验证、归因和防重复材料均已闭合时，self才可另行向6190提交服务值结算。任务完成结算不是服务值结算；普通任务完成、结果未闭合、规则缺失、失败或取消均保持服务值零增加。6190完成原子维护后，self再次读取服务根账户决定当前满足或仍需治理；服务值时间衰减由6190按可信单调时间和当前规则独立维护。

## 14. 重新启用

对`已完成`、`已失败`、`已取消`的T，self只有在fresh读取同一D确认仍需或再次需要治理时才能形成重新启用决议。manager复核后只迁移到`待查找方法`或`等待条件`。

重新启用不删除旧X/A，不撤销既有结算，不允许重复完成结算，也不使用旧W3工作包。

## 15. 消息处理状态

消息运行状态只用于内存调度：待处理、处理中、延后重试、等待依赖、已经终结。它不是任务状态或第二消息事实账。

处理结论：

| 结论 | 主循环处理 |
| --- | --- |
| 成功 | 终结消息并释放容量 |
| 资源暂不可用 | 保留原消息和进度，等待重试时点 |
| 依赖未就绪 | 等待明确唤醒；不能因邮箱非空立即再调 |
| 依赖未实现 | 终结当前尝试并反馈缺依赖 |
| 入口拒绝/身份冲突 | 拒绝新输入并反馈，不删除旧合法输入 |
| 发布未知 | 按原请求查询/恢复，不换身份 |
| 内部不一致 | 停止受影响路径，保留必要退出能力 |

## 16. 停止和恢复

停止时不再派发普通新动作，但必须优先收口已发生动作、安全事件、结果、完成结算和已经准入的服务值账户原子维护。所有等待支持唤醒；同步调用返回前不能销毁依赖或detach线程。

恢复扫描至少检查：

- `执行中`且动作状态未知的X；
- 等待结果的X及已有正式状态；
- `待影响评估`的X；
- `等待自我决议`的T；
- `已完成`但没有完成结算的T。
- 已满足服务结算前提但6190结果未知或尚未提交的服务结果。

恢复只按current-only事实推进，不用运行代次、事实截止或历史材料。当前未实现跨进程恢复时必须明确声明未实现。

## 17. 验证矩阵

最低验证覆盖：

- 初始化成功/停门；
- 根需求与普通需求的current-only复核；
- D-T一对一建立与收束T重新启用；
- 多次筹办但零轮次对象；
- 无结果方案零动作；
- W3-A一次、发布未知不重做；
- W3-B即时、延迟、异地、多渠道、通知先到、渠道失效；
- 精确特征核验；
- 完整与不完整影响评估；
- self七类决议；
- 完成结算恢复；
- 任务完成与6190服务值结算分账、重复服务结果防重、时间衰减后重新出现差距；
- 消息重复、冲突、乱序、容量和停止/join。

本规范只冻结逻辑。静态检查、编译或隔离桩成功不证明普通应用、网页端口、外部观察生产链、跨进程恢复、组合方法或完整业务闭环已验收。
