## 1. 根定位

需求是某一个存在希望某一个确定目标状态成为事实的长期目标契约。

只有存在拥有需求。`自我`在需求结构层首先仍是一个存在；“自我需求”不是第二种需求结构、第二节点族或第二 owner。

为避免把需求所有者与目标状态混为一体，本规范固定三个不同概念：

```text
目标三元组
    = 目标宿主
    + 目标特征
    + 目标状态合同

需求核心契约
    = 所属存在
    + 目标三元组

需求列表精确聚合键
    = 所属存在
    + 目标三元组
```

其中：

```text
所属存在
    回答“这是谁的需求”

目标三元组
    回答“希望哪个存在的哪个特征达到什么状态”
```

所属存在参与需求身份、来源、活动资格、权重、预算和列表聚合，但不属于任务执行时需要比较的目标状态本身。需求的确认、活动和任务化都属于内部治理，不构成现实执行授权。

一个需求只能有一个权威目标三元组。

需求本身就是目标契约，不是：

```text
任务
方法
执行过程
状态枚举
日志
显示摘要
当前世界状态副本
永久满足布尔值
正式结算结果
```

形式化表达：

```text
需求 D
├── 所属存在 E_owner
│     └── 回答“这是谁的需求”
│
└── 唯一目标 G
      ├── 目标宿主 E_target
      ├── 目标特征 F
      └── 目标状态合同 S_goal
```

需求、任务、方法固定分账：

```text
需求
    管“要什么”

任务
    管“为了当前显式关联具体需求互证出的一个确定目标组织一次活动”

方法
    管“在什么条件下执行什么动作会产生什么结果”

需求树
    管“一个目标需要分解成哪些独立子目标”

需求列表
    管“哪些分散的需求树节点表达同一个需求核心契约”

任务方法路径
    管“同一个目标有哪些当前可达手段”

正式结算
    管“某一个具体需求节点基于哪些证据、预算和归因形成了什么历史结论”
```

## 2. 需求核心事实与不可变目标

### 2.1 需求核心事实

需求核心事实必须至少能够稳定证明：

```text
需求身份
所属存在
目标宿主
目标特征
目标状态合同
生命周期
```

### 2.2 所属存在

`所属存在`回答：

```text
这是谁的需求？
```

规则：

1. 创建时必须明确；
2. 不允许为空；
3. 不允许由当前线程、名称、自我缓存、任务身份、父需求或显示文本反推；
4. 创建后不可原地替换；
5. 若另一个存在拥有相同目标三元组，应形成另一个需求身份；
6. `自我需求`不是第二结构类型；
7. 哪个存在当前是自我，由 DATA 外业务层正式裁决；
8. L2需求结构服务不判断哪个存在是自我。

### 2.3 唯一目标三元组

一个需求只能有一个权威目标三元组：

```text
目标宿主
+ 目标特征
+ 目标状态合同
```

复合目标必须拆成多个独立需求或子需求，不得形成多目标需求包。

### 2.4 目标宿主

目标宿主回答：

```text
希望哪个存在发生变化？
```

允许：

```text
所属存在 == 目标宿主
```

也允许：

```text
所属存在 != 目标宿主
```

二者是不同角色，不得合并。

目标宿主必须使用正式强类型存在身份。不得使用方法虚拟存在、任务虚拟存在、线程对象、缓存对象或本地结构地址冒充目标宿主。

### 2.5 目标特征

目标特征回答：

```text
希望目标宿主的哪一方面发生变化？
```

必须使用正式强类型特征定义身份，不得用名称、文本、缓存键或裸值替代。

### 2.6 目标状态合同

目标状态必须使用正式目标状态合同。

目标状态合同负责表达：

```text
目标值
目标集合
方向
区间
比较关系
规则版本
```

不得由以下材料替代：

```text
裸 I64
实例状态身份
显示文本
缓存值
普通 bool
```

### 2.7 核心契约不可变

需求身份一旦建立，下列核心语义不可原地替换：

```text
所属存在
目标宿主
目标特征
目标状态合同
```

其中任一语义发生变化时：

```text
建立新需求
保留旧需求历史
```

原因固定为：

> 需求核心契约改变，本质上已经是另一个需求。

## 3. 当前特征值、当前满足与需求核心分账

需求核心不保存永久：

```text
当前特征值完整投影
当前满足
是否已完成
满足比例
已结算
```

当前特征值事实属于当前世界事实，不属于需求长期目标契约。状态信息和动态信息可以作为历史、变化、来源及审计证据，但不得成为需求长期目标字段或当前比较输入。

当前满足必须实时执行：

```text
读取需求目标三元组
+
冻结非零事实截止并读取目标涉及的当前特征值完整投影
+
正式比较 / 判断收束
=
当前满足裁决
```

因此：

```text
历史上满足
≠
现在满足

任务轮次结算完成
≠
需求当前满足

方法成功
≠
需求当前满足

正式结算曾成功
≠
当前世界仍满足目标
```

当前满足必须携带：

```text
需求身份
目标三元组
同截止当前特征值完整投影
可选状态 / 动态证据引用
来源
事实截止
规则版本
比较或判断证据
```

当前满足是值式裁决或正式治理事实，不是需求节点上的永久布尔值。

## 4. 需求信息的两种正式组织状态

需求信息同时具有：

```text
需求树
需求列表
```

二者共同引用同一批正式需求节点，不形成两套需求事实。

### 4.1 需求树

需求树按父子目标分解关系组织需求节点。

需求树负责保存或可追溯：

```text
目标为什么出现
由哪个父目标分解
来源是什么
处于哪条目标分解路径
本节点自己的权重来源
活动资格来源
预算来源
结算来源
当前性
```

需求树是：

```text
目标分解
+
来源追溯
```

的唯一权威树。

### 4.2 需求列表

需求列表按需求核心契约精确聚合需求树中位置分散的需求节点。

聚合键固定为：

```text
所属存在
+ 目标宿主
+ 目标特征
+ 目标状态合同
```

一个需求列表项至少稳定保存：

```text
列表项身份
精确聚合键
成员需求节点集合
生命周期
```

需求列表是需求树的派生活动视图：

```text
当前需求核心契约枚举入口
同类需求汇总与选择投影
权重查询入口
同类任务查询 / 防重锚点
成员需求查询入口
```

需求列表不是：

```text
普通缓存
显示列表
无身份临时分组
第二套需求事实
第二套结算事实
任务现实执行授权主体
任务目标身份
任务来源需求集合
```

### 4.3 树与列表的权威分工

需求树负责：

```text
父子位置
来源上下文
目标分解路径
权重来源
活动资格来源
预算来源
结算来源
```

需求列表负责：

```text
同核心契约精确聚合
成员需求节点集合
当前目标查询入口
权重查询锚点
同类任务查询 / 防重锚点
```

列表不得：

```text
删除树成员
覆盖树成员
替代树成员身份
吞掉成员来源
吞掉成员权重
吞掉成员预算
吞掉成员结算身份
```

一个当前需求节点必须恰好属于一个当前需求列表项。

## 5. 需求树生长与逻辑路径

### 5.1 唯一目标分解树

需求树固定为：

```text
目标分解的唯一权威树
```

任务不得再建立第二套父子任务树作为另一套目标分解权威。

### 5.2 独立子目标准入

只有独立子目标才进入需求树。

一个目标只有同时满足以下根条件时，task owner 才有资格把 self 的确认记录为正式任务子目标承接，并由需求 owner 发布或复用独立子需求：

```text
它拥有独立目标三元组
并且
任务管理已对筹办发现独立读回，自我已 fresh 确认该目标是父需求的独立必要后继，并由必要条件、正式因果或具名正式材料证明其必要性
并且
它严格缩小父需求及祖先尚未闭合范围，并具有明确且最终可判定的自身目标合同
```

自我确认来源由 task owner 写入既有承接记录的强类型来源联合，不另建方案采用状态、路径占位或第二结果账。承接记录不要求当前路径、实例方法或执行冻结，且不取得执行权。每次筹办处理结束只把一条发现或结构化非成功消息交任务管理线程；任务管理独立读回后，只有自我确认的记录才可编排需求 owner 建立或复用子需求。子需求回流后以新事实截止重新筹办，不得把旧消息或旧记录复活成执行授权。

“需要另一个方法”本身不能自动证明存在新目标。

普通方法步骤不形成需求。

例如：

```text
抬手
移动机械臂
闭合夹爪
```

若只是实例方法内部固定步骤，则留在方法内部。

若其中出现：

```text
必须先取得工具 X
并且“工具 X 已取得”需要独立筹办、执行和验证
```

才形成：

```text
子需求：取得工具 X
```

### 5.3 替代方法不是需求分支

同一目标三元组 `G` 若存在多条方法路径：

```text
P1
P2
P3
```

则：

```text
需求树不变化
```

替代路径属于任务方法路径体系，不得制造：

```text
“使用 P1”需求
“使用 P2”需求
“使用 P3”需求
```

### 5.4 父子拓扑不自动证明业务角色

父子拓扑只说明目标分解关系。

不得仅根据：

```text
子节点数量
父子位置
顺序
历史关系
```

直接推断：

```text
AND 组
OR 组
必须路径
替代方法
执行顺序
当前活动路径
权重分配
任务优先级
```

这些必须由正式路径、当前性、目标语义、业务规则和特征集合共同裁决。

### 5.5 历史路径不得冒充当前路径

历史子需求和历史路径允许保留，但：

```text
活动子需求
活动路径
当前角色
当前权重来源
当前活动资格来源
```

必须根据当前性与版本正式读取，不能按“历史上曾经存在”推断。

## 6. 需求列表聚合

需求业务层在正式需求入树前或同一治理事务中，必须确定该需求核心契约对应的列表项。

### 6.1 已有精确聚合项

```text
已有完全相同聚合键的列表项
→ 新需求节点加入该列表项
```

### 6.2 没有精确聚合项

```text
没有完全相同聚合键的列表项
→ 建立新列表项
→ 新需求节点加入该列表项
```

### 6.3 精确一致性

列表项聚合键与每一个当前成员需求的核心契约必须逐字段完全一致：

```text
所属存在
目标宿主
目标特征
目标状态合同
```

以下均属于内部不一致：

```text
一个需求同时属于多个当前列表项
同一需求重复加入同一列表项
成员核心契约与列表项聚合键不一致
同一聚合键出现多个当前列表项
```

### 6.4 列表项不是树节点替身

列表项只表示同核心契约聚合身份。

它不得保存或代替成员独有的：

```text
父子位置
来源证据
路径
当前性
权重来源
活动资格来源
预算来源
结算身份
```

## 7. 来源材料、自我产生确认与正式写入权

### 7.1 可供 self 裁决的正式材料来源

父需求任务可以接收以下正式材料：

```text
自检
身体反馈
观察
外部输入
任务发现的独立子目标
无可执行方法的结构化裁决结果
既有候选方法的具体结构缺口材料
因果反推
临时因果视图
正式结算后的后继目标
其它正式登记来源
```

这些来源只能形成父需求任务的：

```text
强类型筹办材料
或
子目标分析草案
```

不能直接形成正式需求。只有 self 依据父任务正式材料产生并确认某个独立、必要、父域合法、严格缩小祖先尚未闭合范围且具有明确并最终可判定的自身目标，task owner 才能记录该确认为正式任务子目标承接；需求 owner 只消费该记录发布或复用子需求，不取得产生权或确认权。

#### 7.1.1 C031 发现定位、自我确认与来源联合

方法缺失、条件缺失、输入 / 入口 / 验证 / 归因结构缺口都只能由任务管理独立读回并推进任务状态后，作为具名定位消息交 self；它们既不是需求，也不自动成为学习、方法补齐或条件子目标。

自我线程必须 fresh 读取父需求、目标合同、来源任务 / 轮次、候选方法及其条件组后，区分等待 / 重触发、当前任务结构缺口和真正独立且必要的后继需求目标。只有后一种目标可由 self 产生并确认，再由 task owner 用既有正式任务子目标承接记录的`自我确认来源`幂等记录并读回；需求 owner 只消费该已确认记录发布或复用子需求。粗召回完整为空只是一种供 self 裁决的定位，粗召回非空但当前候选不可用、不可比或尚无适用判断结论，均不得改写为方法能力缺失需求。

自我确认不建立第二需求入口、通用缺口节点、服务合同、持久 outbox 或第二结果账。记录中的`自我确认来源`是 task owner 已完成 fresh 复核后的强类型来源类别和必要正式定位，不是用消息文本、布尔值、裸编码或线程身份替代的证明字段。

### 7.2 方法与条件缺失材料分账

不得建立独立长期“能力缺口节点”，也不得从缺失分类自动推导需求种类。任务筹办只把方法缺失、方法结构缺失、条件缺失及其已覆盖 / 剩余范围补入当前任务材料；对象、方向、结果适用性、当前可用性和代价比较仍由执行前选择裁决。

manager 只能把上述正式任务材料定位给 self。self fresh 读取父需求、目标合同和当前事实后，自行产生并确认等待、普通后继需求或学习需求；task owner 只记录该确认，需求 owner 只发布或复用。筹办、方法域、manager、task owner 和需求 owner 均不得根据`零候选`、`结构缺口`或`条件未满足`直接产生需求结论。

结构缺口、多候选、预算不足、当前性漂移、对象概念待形成、方法条件未满足或输入限制待绑定，均不得自动改写为学习需求、方法补齐需求或其它子需求。

### 7.3 正式写入唯一入口

正式需求必须由需求业务统一入口完成：

```text
来源校验
目标完整性校验
所属存在校验
父域合法性
路径裁决
精确聚合键查询
去重 / 复用裁决
新建列表项或复用列表项
原子入树
列表成员关系建立
正式读回
```

线程、任务管理器、方法执行体、候选生成器、观察中间层、显示层均不得直接写需求结构。

### 7.4 L2需求结构服务边界

L2需求结构服务只执行已经裁决后的强类型结构写入。

它只负责：

```text
身份
结构关系
生命周期
幂等
事实代次
当前 / 历史读取
原子发布
引用闭合
```

它不判断：

```text
需求是否合理
是否应该生成需求
是否是主需求
权重
活动资格
任务化资格
当前满足
方法选择
任务创建
正式结算
普通任务或学习任务分类
```

### 7.5 入树拒绝

入树拒绝必须形成结构化拒绝回执，并进入具名闭环。

至少区分：

```text
业务入口拒绝
引用冲突
证据不足
目标不完整
所属存在非法
父域非法
当前性失效
幂等冲突
事实代次漂移
资源失败
内部不一致
```

内部逻辑错误不得伪装成普通需求拒绝。

### 7.6 按所属存在参数化与当前自我双根治理

需求治理的通用结构按所属存在 `E_owner` 参数化：每个需求唯一属于一个存在，父子需求必须属于同一存在。当前唯一自我的内部治理实例只治理该自我的需求；该自我只有安全根与服务根两个父空普通需求。除这两个冷启动根外，任何自我需求都必须由 self 根据父任务正式材料确认其为独立必要、严格缩小祖先尚未闭合范围且具有明确并最终可判定自身目标状态合同的子目标，再经 task owner 记录和需求域登记，并能沿父关系有限回溯到其中一个根。

1. 每个运行期子需求 `D_child` 必须具有一个当前父需求 `D_parent`，二者必须属于同一 `E_owner`；缺父、跨所属存在挂接或父子循环均为内部逻辑错误。当前自我内部治理消费者还必须校验 `E_owner` 是已锁定的唯一自我，且父链可有限回溯到该自我的安全根或服务根；其它存在的需求只能由其具名治理 owner 按该存在的正式根语义处理，不取得当前自我内部治理入口；
2. `D_child` 的唯一形成来源是 `D_parent` 所承接任务发布的正式任务子目标承接记录。该子目标必须经 self 确认独立必要、严格缩小父需求及祖先尚未闭合范围，并具有明确且最终可判定的自身目标状态合同。记录必须绑定父需求、任务、任务轮次、筹办轮次、self 确认来源、共同事实截止、规范化目标和幂等身份；消息、日志、外部请求、观察、自检或方法 / 条件缺失不能替代该记录；
3. 需求 owner 只消费已由任务 owner 独立读回的任务子目标承接记录，并使用既有任务子目标来源原子入口建立或复用 `D_child`、`L`、成员关系、父子关系和记录到子需求的来源关系。任务 owner 随后按原记录幂等绑定子需求；不得再建通用请求节点、来源事实 `S`、通用 `R→D`、来源 registry 或真实性 provider；
4. 外部存在 `E` 发出的服务请求、观察材料、自检材料、方法缺口和其它事实都只是父任务的输入材料。它们先经各自原领域 owner 正式承接，再交给安全根或服务根及其后继需求的任务筹办；只有父任务正式形成子目标记录后才能建立子需求；
5. 人类只是输入来源存在 `E` 的一种可选分类。分类不参与内部治理需求所有权、父域或子目标准入；外部服务请求由服务根任务消费，所衍生子需求仍属于唯一自我并位于服务根子树；
6. 目标宿主可以是自我、输入来源存在 `E` 或其它已发布存在，不因此改变 `D_child.所属存在`。来源存在与目标宿主是不同角色，均不得反推需求所有者；
7. 安全根 / 服务根本身不因外部材料直接执行现实动作。根需求先建立或复用负责形成任务材料并承接 self 子目标确认的治理任务；普通现实动作只在具体子需求后继任务完成执行前选择、方法冻结和安全门禁后执行；
8. 同一父需求下目标三元组和满足关系相同的活动子需求按 5110 复用或合并。不同外部请求、文本、材料或提出者不自动制造第二个 D；新的正式子目标记录可以按既有来源关系附着到同一子需求；
9. 子目标必须严格缩小父需求及任一祖先尚未闭合的问题范围，不得与父需求或任一祖先目标语义相同、等价或更宽；父链必须无环且不得跨安全树、服务树相互反挂。该约束不以前置方法选择或当前路径为条件。缺方法、缺证据、当前不可验证或任务失败默认形成材料或合法等待，不得递归改名建需。
9. 写入幂等身份只属于工程正确性，由任务子目标记录身份、父需求、筹办轮次和规范化子目标语义在固定命名域稳定形成；它不是业务请求、合同、账户或需求身份；
10. 子需求建立与其后继任务治理分账。子需求已经建立后，后继的已有任务、目标已满足、合法等待或资源失败不能倒推为子目标准入失败，也不能撤销已发布子需求。

既有 L2 需求历史读取 ABI 属于通用结构能力，只负责在显式观察代次和历史截止下读取需求、列表项和成员关系；它们不得包装成请求专用恢复账。任务子目标记录已有当前 / 历史读回和专用来源关系，后继应补齐这些现有合同的消费者，不得再建平行来源体系。

## 8. 普通需求与学习需求统一结构

### 8.1 不建立第二种学习需求

学习需求仍然使用普通需求结构：

```text
需求身份
所属存在
目标宿主
目标特征
目标状态合同
需求树位置
需求列表成员关系
```

不得建立：

```text
学习需求节点族
学习需求 owner
学习需求列表
能力缺口节点
```

### 8.2 学习需求的所有者与目标

学习需求表达：

> 某个存在希望自身具备或改善某项能力。

首版根级映射固定为：

```text
所属存在
    = 发起学习并拥有该能力目标的存在，通常为当前自我

目标宿主
    = 所属存在自身

目标特征
    = 待获得、待补全或待稳定的能力特征

目标状态合同
    = 该能力达到可用、完整、稳定或指定范围的目标合同
```

方法虚拟存在、方法候选、因果材料和练习材料可以作为能力目标的来源证据或后继方法治理材料，但不得冒充世界存在身份成为需求目标宿主。

### 8.3 学习需求的形成

学习需求只能由 self 依据父任务正式材料产生并确认：

```text
任务目标完整
+
任务目标当前未完成
+
目标特征粗召回完整为空并形成“方法能力缺失”
+
不存在预算不足、当前性漂移、对象概念待形成、结构待补齐、多候选待选择证据、
采用方法条件提议、合法等待或应先形成独立子目标的事实
=
self 产生并确认独立必要的学习需求目标
-> task owner 形成正式任务子目标承接记录
-> 需求 owner 发布或复用学习需求
```

筹办方法 / 条件信息不等于实际采用。方法或条件缺失先留作父任务材料；不得把结构缺口、范围未完成、技术失败或多候选降格为“能力缺失”。只有 self fresh 读取材料并产生、确认独立必要的学习目标，由 task owner 记录正式子目标承接后，需求 owner 才能在发布前精确匹配并发布或复用学习子需求。

### 8.4 学习需求不直接结算价值

学习需求及其任务：

```text
不直接增加安全值
不直接增加服务值
不直接证明现实目标已改变
```

学习结果先进入：

```text
学习材料
方法候选
方法补齐候选
方法新代际治理
```

未来普通任务使用新能力并形成正式现实结果后，才可能进入价值结算。

## 9. 权重、活动资格与预算

需求列表项是权重与活动资格查询入口之一，但列表项本身不得保存一个丢失成员来源的不可审计总值作为权威事实。活动资格只是需求当前能否参与选择、承接或结算的治理事实，不授权任何现实动作。

当前查询必须：

```text
列表项
→ 当前成员需求
→ 每个成员的路径 / 当前性 / 权重 / 活动资格 / 预算
→ 按正式规则形成聚合投影
```

聚合投影必须保留：

```text
成员需求身份
成员来源
成员路径
成员当前性
成员权重
成员活动资格
成员预算
规则版本
共同事实截止
```

禁止把多个成员压成一个无法回溯的“总权重”“总活动资格”或“总预算”。

父权重不得在路径展开过程中丢失。

AND / OR、路径继承、组内分配、舍入和预算冻结由 5110、4320 等下位规范具体冻结；本根规范只固定：

```text
权重 / 活动资格 / 预算必须可追溯到具体需求成员和来源。
```

## 10. 任务边界

正式关系固定为：

```text
每次承接输入一个具体需求树需求 D
→ 读取 D 当前所属需求列表项 L
→ 以 L 作为同类任务查询 / 防重锚点查找当前任务 T
→ 无 T 时建立 T，并建立 T→L 查询锚点与 T→D 正式关联
→ 有 T 时机械复核目标与任务语义相同，再幂等建立 T→D 正式关联
```

列表项只帮助查找可能相同的当前任务，不自动把列表全部成员承接给任务。任务需要达成的单一目标必须从任务已经显式关联且当前有效的一个或多个具体需求逐项读取：

```text
目标宿主
+ 目标特征
+ 目标状态合同
```

全部关联需求的目标三元组必须逐字段完全相同；任一不一致属于内部不一致。形成当前任务目标投影至少需要一项当前有效的显式关联需求；全部关联需求失活时不得用列表项聚合键兜底，必须由任务业务形成等待、结束或重新裁决。

任务必须通过自己的正式需求关联回读本任务已经承接的具体需求，以取得各自的：

```text
路径
当前性
权重
预算
结算来源
```

同一需求列表项当前至多一个当前任务；同一任务可逐次关联一个或多个精确同目标的具体需求，但只有收到该具体需求的承接输入才允许建立关联。列表项新增成员不得自动进入任务来源集合。

任务不得：

```text
复制列表项或需求目标
把列表项聚合键当作任务目标权威
把列表全部成员自动吞并为任务来源
把相似目标或名称相同当作任务语义相同
把成员权重压成不可审计单值
```

任务发现独立子目标时：

```text
由 self 证明该目标独立必要、严格缩小祖先范围并具有明确且最终可判定的自身目标状态合同
→ 发布正式任务子目标承接记录
→ 需求业务消费记录并建立或复用子需求
→ 进入对应需求列表项
→ 以具体子需求身份承接或复用自己的任务
```

不得建立第二套持久任务父子树。

## 11. 方法边界与无方法分流

方法回答：

```text
在什么条件下执行什么动作会产生什么结果？
```

方法不拥有需求目标，也不能改变需求核心契约。

同一任务目标允许：

```text
0..N 条当前可达方法路径
```

一轮实际执行只能选择：

```text
0..1 当前选中路径
0..1 当前实例方法
```

方法路径变化、选择、换代不改变需求树。

筹办期发现缺失条件或新的目标材料时：

```text
任务筹办把缺失项补入当前任务材料，manager 独立读回后按任务状态决定继续筹办或等待
-> self fresh 读取正式任务材料，产生并确认目标是否独立必要、严格缩小祖先范围并具有明确且最终可判定的自身目标状态合同
-> 通过时由 task owner 把 self 的确认记录为正式任务子目标承接并读回
-> 需求 owner 消费记录发布或复用子需求
```

方法本身不得形成需求产生 / 确认结论或调用需求入口；普通方法步骤继续留在方法内部。

执行已经开始后发现冻结前本应存在的方法或条件缺口，属于筹办漏检或内部错误；执行期间事实变化导致条件失效，则必须形成该执行轮次的实际结果或具名非成功并完成唯一任务轮次结算。轮次收束后，只有 self 的正式`继续`决议才能建立新任务轮次并重新筹办，不得在同一任务轮次回跳找方法或查条件。

任务筹办形成的缺失材料固定为：

```text
找方法覆盖完整且候选为空
→ 形成方法缺失任务材料

已有候选但方法正式结构、内容版本或条件组无法完整读取
→ 形成方法 / 条件结构缺失任务材料

候选方法的当前条件或输入不成立
→ 形成逐候选、逐条件组的条件缺失任务材料

存在多个候选
→ 全部保留；筹办不做适用性判断、比较、采用或冻结
```

上述材料都不能自行产生需求或自动决定等待、普通后继或学习后继。self 可以依据正式材料产生并确认普通后继需求；只有同时满足 5330 的正式学习准入门槛时，才可以产生并确认学习需求，不满足学习门槛的材料由 self 决定普通后继需求或等待。适用性、实际采用、fresh 可用性复核和综合代价比较只在执行前选择阶段发生。

禁止：

```text
方法成功直接写需求满足
方法成功直接形成正式结算
方法路径直接进入需求树
无方法时自动建立方法首
无方法时建立长期能力缺口节点
```

### 11.1 C031 无方法与条件发现的需求边界

第 11 节中子需求前置统一为第 7.1.1 节的 self fresh 产生并确认门。任务筹办的职责是按状态补全方法和条件信息；执行前选择的失败、未知、不可比或并列也不能绕过 self 的需求产生确认直接扩张需求树。

方法的正常步骤、互斥候选、方法自身结构缺口和暂时不成立的条件仍不是需求。仅当 self 产生并确认独立目标对父需求后继确有必要、父域合法、目标合同可最终判定，且 task owner 已按`自我确认来源`记录正式承接时，需求 owner 才可在发布前精确匹配并发布或复用子需求。

## 12. 当前满足、任务轮次结算、任务生命周期与正式结算分账

### 12.1 四个概念不能合并

必须严格区分：

```text
当前满足
任务轮次结算
任务生命周期结束
正式结算
```

其中：

```text
当前满足
    = 当前世界事实与目标状态合同的实时比较结果

任务轮次结算
    = 一次任务轮次对实际结果、逐需求核算和各 owner 结果引用的结构化收束

任务生命周期结束
    = 自我下达结束或取消后，任务 owner 完成的生命周期迁移

正式结算
    = 某一具体需求节点基于正式证据、归因和预算形成的历史结论记录
```

因此：

```text
任务轮次结算完成或任务生命周期结束
≠
需求当前满足

需求当前满足
≠
正式结算

方法执行成功
≠
正式结算
```

### 12.2 正式结算以需求节点为基本身份单位

同一个需求列表项中的多个成员虽然核心契约完全相同，但它们必须保留各自独立的：

```text
需求身份
来源
父子位置
路径
当前性
权重
活动资格
预算
结算来源
正式结算记录
```

一次当前世界事实比较结果可以被同核心契约的多个成员消费，但以下事项必须逐成员独立裁决：

```text
成员是否有业务资格参与本次结算
成员可领取多少预算
成员来源与路径是否仍当前
成员最终形成什么正式结论
```

### 12.3 列表项不能取代成员结算

列表项可以作为：

```text
同核心契约查询锚点
任务查询锚点
成员集合入口
```

但不能直接生成一个丢失成员身份的“列表项总结合算结果”。

### 12.4 结算证据

正式结算至少必须能够追溯：

```text
需求身份
目标状态合同
参与结算的当前性事实
来源需求路径
任务身份 / 本轮任务材料
实例方法 / 动作证据
目标涉及的同截止当前特征值完整投影
可选状态 / 动态证据引用
可选因果证据
归因材料
权重 / 活动资格 / 预算来源
规则版本
共同事实截止
结算结论
幂等身份
生命周期
```

精确 DTO 和算法由 5160、4320 及其后继规范冻结。

### 12.5 结算历史不替代当前满足

正式结算是历史治理事实。

即使某需求此前已经形成成功结算，仍不能证明目标当前继续满足。

### 12.6 需求满足后继续存在

需求当前满足后仍是正式需求；其身份和目标合同继续存在，可以：

```text
继续保留当前需求
进入等待
失活
形成结算
恢复活动
```

任何满足、结算、任务结束或其它治理状态都不得删除或退出需求身份与目标合同。

## 13. 安全、服务、学习与一般需求根边界

安全需求、服务需求、学习需求和一般需求仍然使用同一需求结构。

### 13.1 冷启动安全根与服务根

唯一自我正式形成并独立读回后，紧随其后的 ARCH-L4 冷启动治理必须幂等建立两个长期普通根需求角色：

- 安全根需求；
- 服务根需求。

这两个角色各自恰好绑定一个当前普通需求身份 D。它们不是第二种需求节点、不是 DATA-L2 固定类别，也不得由根需求组顺序、名称、目标值、列表项、线程字段或缓存反推。角色绑定、初始化版本、幂等收束以及普通需求节点、父子关系、列表关系和生命周期都属于 DATA 之外的 ARCH-L4 治理事实；现有 C++ `L2需求*` 类型、服务和文件名只作兼容 ABI / 实现名，不取得当前 DATA-L2 owner 语义。

冷启动顺序固定为：

1. 唯一自我先正式形成并独立读回；
2. 冷启动治理读取两个根角色绑定；
3. 缺失时经需求正式入口分别建立普通根需求并发布角色绑定；
4. 同义重复只读回原角色和原 D，不建立重复根；
5. 两个角色、两个 D、各自目标合同和初始化版本全部正式读回后，双根初始化才成功。

不得把两个根需求塞入唯一自我形成的底层事务，也不得把“自我已经形成”冒充“双根已经建立”。任一角色重复绑定、多义、引用失效、目标合同不完整、读回漂移或只完成一侧时，冷启动治理必须结构化失败并保持原事实，不得临场选一条根需求继续。

两个根需求分别拥有独立的需求身份、目标合同、当前满足裁决、来源、父子树、结算引用和生命周期。安全值与服务值不得压成综合分数，任一根的满足、缺口或材料失败不得代替另一根的裁决。

每轮治理在同一非零事实截止 G0 分别读取两个角色绑定、两个根 D、各自完整目标合同和各自当前值，并分别形成：当前满足、正差距、方向相反、不可比较、材料不足、当前性漂移、内部不一致。

正差距首先是依据目标合同和具名比较关系得到的方向分类；比较服务没有返回数值差值时，不得伪造数值差。正差距或新到达的合法父任务材料可以建立、唤醒或复用根需求治理任务；材料触发只授权 fresh 重判与材料裁决，不等同正差距，不改变根当前值，也不直接创建具体需求。该任务的内建治理方法只形成任务材料；self fresh 读取材料并产生、确认独立必要目标后，才由 task owner 记录正式子目标承接。根需求本身长期存在；当前满足只表示本轮没有根值正差距，不触发永久退役，也不阻断对新材料的治理重判。

服务根需求是自我长期服务方向的根坐标，不是某个外部请求本身。外部请求经原来源 owner 正式承接后，只能作为服务根治理任务的输入；self 对该任务正式材料 fresh 读取并产生、确认独立必要目标，由 task owner 记录正式子目标后，需求 owner 才在服务根下于发布前精确匹配并发布或复用属于唯一自我的普通具体需求，并按普通需求、任务、方法和正式结果规则治理；不得据此建立服务合同或服务值账。

### 13.2 双根派生需求的复用边界

安全树和服务树派生的两个具体需求即使目标三元组相同，也保留两个独立 D，因为父需求和来源不同。只有所属存在同为该唯一自我且目标三元组完全相同，二者才可以进入同一需求列表项 L；同一任务 T 可以逐次显式建立两条 T→D 关系。不得因此恢复结果容量、消费分配、剩余量或结果争用模型。

### 13.3 当前值比较权威

需求当前满足和差距裁决只能读取目标涉及的特征当前值事实，再按目标状态合同比较。状态信息只记录某时刻的值，动态信息只记录前后状态及来源；二者不得替代当前值进入比较。动态只能提示哪个特征需要重检，消费者仍须冻结 G0 并重新读取当前值。

复合目标必须在同一 G0 读取完整当前特征值集合，再按目标合同规定的成员、比较规则和组合逻辑裁决。为传递而形成的值式当前状态投影可重建，不是第二当前值权威。

不得建立第二种：

```text
安全需求节点
服务需求节点
学习需求节点
```

安全、服务、学习的区别来自：

```text
目标特征与目标状态合同
来源
活动资格与预算规则
后继任务和结算资格
```

而不是名称或固定需求类别字段。

需求权重：

```text
提供路径选择、一般调度和结算预算来源
```

但不直接等于：

```text
实际结算值
安全任务调度优先级配额
压力值
```

安全任务调度优先级配额由 6150 等规范承接；它只参与正常调度排序，不是自我现实执行授权。

学习需求不直接进入安全值或服务值结算。

## 14. 生命周期与当前性

需求创建、父子关系、列表成员关系、路径激活、权重、活动资格、活动承接、当前满足和结算都必须具备：

```text
来源
版本
当前性
生命周期
```

更新必须保留历史，不得覆盖旧事实后丢失来源。

需求至少应分清：

```text
当前满足
失活
恢复
等待
```

这些状态不能互相替代。

路径失活不删除需求历史。

当前满足不退出需求。

正式结算不自动退出需求。

上述状态只改变治理活动性或当前列表视图，不退出需求本体；需求身份、目标合同和历史持续存在。

列表项可在当前成员归零后继续保留稳定聚合身份和历史，是否退役由独立管理合同裁决。

## 15. 事务、幂等与当前 / 历史读取根原则

所有下位结构合同必须遵守以下根原则：

1. 正式需求节点不得以“只入树、未入列表”的半结构存在；
2. 需求节点、核心契约关系、列表成员关系和可选父关系必须按正式合同同代原子发布；
3. 一个当前需求恰有一个当前列表成员关系；
4. 父子关系和列表成员关系完全分账；
5. 所属存在和目标三元组创建后不可替换；
6. 父关系允许按正式治理换代，但必须退出旧关系、建立新关系并保留历史；
7. 当前组合读取必须共享共同事实截止；
8. 历史读取必须显式使用历史截止，不得用当前事实补历史缺项；
9. 同幂等身份 + 同完整请求必须精确重复；
10. 同幂等身份 + 不同完整请求必须幂等冲突；
11. 事实代次漂移必须零变化；
12. 发布未知只能使用原幂等身份和原完整请求收敛；
13. 不得用空值、默认值、缓存或当前线程上下文补齐坏目标；
14. 任一身份复义、单例关系重复、跨代拼装或发布后读回矛盾均属于内部不一致。

## 17. 禁止事项

禁止：

- 没有所属存在的需求；
- 把自我建立为第二种需求 owner；
- 一个需求包含多个权威目标三元组；
- 把所属存在解释为目标状态的组成值；
- 原地修改需求所属存在；
- 原地修改需求目标三元组；
- 在需求节点保存永久“已满足”布尔值；
- 在需求节点保存当前世界状态副本；
- 用任务轮次结算完成或任务生命周期结束代替需求当前满足；
- 用方法成功代替需求当前满足；
- 用正式结算历史代替当前满足；
- 把替代方法路径制造成子需求；
- 仅因“需要另一个方法”就制造子需求；
- 把普通方法步骤制造成子需求；
- 独立子目标不进入需求树；
- 建立需求树之外的第二套权威目标分解树；
- 用拓扑数量直接推断 AND / OR、活动路径或方法路径；
- 一个需求同时属于多个当前列表项；
- 列表项核心契约与成员核心契约不一致；
- 列表删除、覆盖或取代树成员；
- 把需求列表当普通缓存；
- 把列表成员的权重、活动资格、预算压成不可审计单值；
- 把列表成员正式结算压成一个不可回溯总结果；
- 从单个成员需求绕过同类任务查询锚点直接猜测或重复创建任务；
- 把需求列表项解释为自我现实执行授权主体、任务目标身份或任务来源需求集合；
- 未收到具体需求承接输入就把列表成员自动关联到任务；
- 建立第二种学习需求结构；
- 把方法虚拟存在或任务虚拟存在冒充需求目标宿主；
- 建立长期能力缺口节点；
- 无方法时自动建立方法首；
- 任务、方法、观察层直接写需求树；
- L2需求结构服务自行做语义近似去重；
- L2需求结构服务判断主需求、权重、活动资格、任务化、当前满足或正式结算；
- 当前满足自动触发永久退役；
- 任务轮次结算完成或任务生命周期结束自动触发需求永久退役；
- 正式结算自动触发永久退役；
- 结算结构直接生成正式后继需求；
- 用名称、文本、缓存、本地键、日志或显示摘要证明需求身份。

## ARCH-L4 兼容边界（20260824）

需求节点、结构字段、关系、列表和生命周期统一属于 `ARCH-L4` 业务治理，不进入当前 `DATA-L2` 活跃 owner。现有 C++ `L2需求*` 类型、服务和文件名只作兼容 ABI / 实现名，不判断需求成立、目标达成或结算。需求可引用 ARCH-L2 通用虚拟存在、状态、动态和特征，但不得拥有第二份状态 / 动态权威。列表项仍是查询 / 防重视图，D 仍是来源与目标权威；该业务语义不改变 ARCH-L2 通用结构 owner。
