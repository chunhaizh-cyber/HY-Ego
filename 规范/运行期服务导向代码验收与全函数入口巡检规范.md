# 运行期服务导向代码验收与全函数入口巡检规范

工程治理标识：ACCEPTANCE-01

日期：2026-08-02

状态：现行施工规范
规范类别：施工规范

## 1. 目标与边界

本规范规定代码验收如何组合全函数编译接入检查、函数入口巡检、逻辑异常检测和运行期服务验收。它只定义验收施工方法，不定义新的业务机器逻辑，不改变逻辑规范已经冻结的成功、非成功、事务、发布、恢复或事实成立条件。

验收必须区分“代码结构可继续”和“业务能力成立”。空函数、占位函数或尚无业务副作用的函数可以通过其实际满足的弱验收层级，但不得因此形成业务服务完成、正式接线完成或项目目标完成结论。

## 2. 四级验收结论

| 层级 | 结论 | 最小成立条件 | 不证明 |
| --- | --- | --- | --- |
| L0 | `编译接入通过` | 目标函数身份、声明、定义、所有者、目标工程、编译和链接成立，未发现静态逻辑异常合同缺口 | 函数已经被调用、运行结果正确 |
| L1 | `入口巡检通过` | L0 成立；目标函数经安全直接或间接路径实际进入并退出，巡检期间未观察到逻辑异常 | 业务后置条件、权威事实和上级服务完成 |
| L2 | `局部可继续` | L1 成立；直接调用方能够消费结构化结果，副作用和非成功符合函数合同 | 正式消费者接线和完整服务闭环 |
| L3 | `服务验收通过` | 合法消费者经正式入口取得符合逻辑规范的结果，适用权威终态、独立读回、失败与恢复继续性成立 | 其它服务、其它语义层或项目整体完成 |

较高层必须包含较低层适用门禁；较低层通过不能自动升级。验收记录必须使用实际达到的最低充分结论，不得只写笼统的“通过”。

## 3. 全函数范围与清单

每次代码验收必须先冻结函数清单，范围只能是：

```text
本次新增和直接修改函数及其受影响调用闭包
或
具名模块 / 服务的完整当前可达函数闭包
或
全项目当前可达项目函数集合
```

函数清单必须绑定当前提交、函数身份表或等价可回查来源，并为每个函数记录：稳定身份、物理文件、模块 / 类型所有者、签名、目标工程、诊断责任、编译状态、入口巡检状态、排除理由和证据。外部库函数、编译器生成函数和明确不属于项目源码的函数可以排除；项目函数不得因空实现、简单、私有、模板、构造析构或暂时没有调用方而从编译接入检查中消失。

全项目巡检可以按批次运行，但同一验收结论只能覆盖已经形成闭合清单的范围。未进入本批的函数必须列入未覆盖范围，不能用总函数数或覆盖率推导完成。

## 4. 编译接入检查

每个未排除项目函数至少检查：

1. 声明与定义身份一致，不存在错误重载或第二所有者；
2. 文件和模块归属符合 CODE-FILE-01；
3. 目标工程、配置、包含或导入关系正确；
4. 编译和链接成功，没有依赖未实现符号、重复定义或错误可见性；
5. 函数合同备注和诊断责任分类存在且与实现不矛盾；
6. 未通过默认对象、空句柄、固定成功值或吞错伪造更强能力。

满足上述条件的空函数可以记录 `编译接入通过`。该结论只证明代码入口能够进入构建和链接体系，不证明运行时进入过该函数，也不证明函数合同要求的业务动作已经完成。

## 5. 函数入口巡检

入口巡检通过专用自检、测试驱动、合法上级路径、覆盖探针或等价无业务污染的方式，证明目标函数在受控输入下实际进入并退出。不得为了“调用所有函数”而构造违反前置条件、破坏权威事实、触发不可逆外部动作或绕过正式服务边界的请求。

无法安全直接调用的私有辅助、构造析构、回调和高风险函数，可以用合法上级路径的间接进入证据；没有安全直接或间接路径时只能保留 `编译接入通过`，不得伪造入口巡检证据。

空函数在实际进入、正常退出、无未授权副作用且没有逻辑异常信号时，可以记录 `入口巡检通过`。这仍不证明其业务后置条件成立；若正式合同要求它写入、查询、发布、拒绝或返回具名结果，空实现不得进入 `局部可继续` 或 `服务验收通过`。

## 6. 逐函数逻辑异常责任

本规则生效后新增或直接修改的项目函数必须登记一种诊断责任：

- `本地记录`：程序入口、正式服务边界或真正异常的最终责任边界；异常命中时只记录一次安全诊断。
- `向上送出`：通过结构化非成功、异常或明确错误状态把问题送到上级最终责任边界，本函数不重复记录。
- `无适用错误分支`：根据明确输入、输出和实现，机械上没有需要诊断的失败分支；不得仅靠备注自称。

合法未找到、重复、漂移、等待、正常冲突和已处理的合法拒绝不是逻辑异常。诊断宏关闭时错误传播和机器结果仍必须成立；日志写入失败不得改变业务结果。

入口巡检期间没有逻辑异常，只能证明“在本次输入和路径中未观察到异常”。编译成功不能检测运行期异常；入口正常返回也不能证明未执行的分支正确。逻辑异常检测用于暴露问题和裁决弱验收层级，不替代结构化结果、后置条件和权威终态检查。

## 7. 局部与服务验收

`局部可继续` 除入口巡检外还必须证明：

```text
输入前提成立
结构化成功 / 非成功能够被直接调用方消费
合同副作用成立或明确为零
没有半结构、越层写入、权威污染或假成功
受影响上级路径能够继续验证
```

`服务验收通过` 必须从合法消费者或等价正式边界发起，沿真实装配取得结构化结果，并从逻辑规范规定的权威读取边界独立读回。根据风险覆盖成功、精确重复、合法拒绝、外部失败、并发、崩溃恢复、正式读回和正式构建；不适用场景必须写合同级理由。

空函数只有在正式逻辑合同明确规定其动作就是无操作，且返回、副作用和上级可观察结果均符合合同时，才可能进入 L2 或 L3。其它空实现即使编译和入口巡检通过，也必须保持弱结论。

## 8. 验收记录

验收记录至少保存：

- 精确提交、远端身份和输入文件 blob；
- 函数清单范围、来源、总数、排除数、编译通过数、入口巡检通过数、逻辑异常数和未覆盖项；
- 每个失败函数的稳定身份、失败层级、命令、退出码和证据；
- 服务切片、合法消费者、正式入口、结构化结果、权威终态和独立读回；
- 实际结论、允许声明、禁止声明和未覆盖范围。

清单检查器只验证字段、数量关系和结论升级门禁，不证明编译、入口、异常或运行证据真实。验收者必须核对实际命令和证据。

## 9. 禁止事项

禁止：

```text
把编译接入通过写成函数正确、能力完成或服务验收通过
把入口巡检通过写成业务后置条件或权威事实成立
只因函数为空、简单或暂时未调用就从函数清单删除
为了调用所有函数而绕过前置条件、事务、所有者或正式服务边界
用没有错误日志证明没有逻辑异常
用函数数量、入口覆盖率或 PASS 文本累计项目完成
把合法非成功记录为逻辑异常
让诊断或巡检改变业务变量、锁竞争、随机序列、状态机或事务结果
```

## 10. 完成边界

本规范建立只证明验收分级、全函数清单、入口巡检和逻辑异常检测方法已经形成，不证明现有全部函数已经完成巡检，也不证明任何服务已经通过集成验收。历史代码只有在进入具名验收范围并形成证据后，才能取得相应层级结论。
