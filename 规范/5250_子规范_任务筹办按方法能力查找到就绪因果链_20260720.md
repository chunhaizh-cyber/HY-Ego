# 5250 子规范 任务筹办按方法能力查找到就绪因果链

编号：5250
日期：20260903
版本：v0.14
状态：正式子规范

## 1. 定位

本规范定义普通可任务化原子任务如何在多次筹办调用中先完整查找候选方法，再逐候选查找和核验条件，最终把完整筹办信息交给执行前选择。筹办不选择、实例化或冻结方法。

直接上级规范：3200、3300。

直接依赖规范：1190、3100、5230。

相关边界规范：4310、5240、5300。

## 2. 状态闸门

任务筹办只能由任务管理线程根据任务当前筹办状态派发：

- `待找方法 / 继续找方法`只进入方法查找；
- `待查条件 / 继续查条件`只进入条件查找与核验；
- `方法缺失 / 等待方法处理`、`条件缺失 / 等待条件`只在具名重触发事实出现后重新进入相应步骤；
- `待执行前选择`不再调用筹办，转入 5300 的执行前选择；
- 任务已进入执行、结算或轮次已收束时不得调用筹办。

管理、汇总、AND、OR、方法路径、因果支撑和结构治理节点仍应先按自身展开 / 聚合规则处理，不能仅因存在方法索引就冒充普通原子任务。

## 3. 找方法

找方法阶段只依据已确认未满足的任务目标、目标对象、目标特征、所需变化和方法公开能力索引，在明确的有界范围内查找零个、一个或多个候选方法。每次调用必须保存：

```text
任务 / 任务轮次 / 筹办轮次
调用前状态和任务信息预期版本
本次查找范围
累计已覆盖范围和剩余范围
候选方法身份、内容版本和生命周期定位
结果事实截止和任务信息结果版本
```

找方法阶段不读取或核验方法条件，不判断哪个方法最终适用，不比较代价，不形成当前路径。查到第一条候选不等于查找完成；只有有界范围完整覆盖后，manager 才能根据候选是否为空迁移到`待查条件`或`方法缺失 / 等待方法处理`。

`方法缺失`只表示方法查找能力正常、范围完整覆盖且零候选。预算不足、范围未完成、版本漂移、引用冲突、资源失败或代码错误都不得伪装成方法缺失。

## 4. 查条件

查条件阶段只消费 task owner 已登记的完整候选方法集合。筹办对每个`方法 + 内容版本`查找其零个、一个或多个条件组，并按 fresh 正式事实核验每组条件当前是否具备。每次调用必须保存：

```text
候选方法及内容版本
逐方法条件组和组内正式条件关系
每组核验事实截止及具备 / 不具备 / 尚未核验结果
累计已覆盖范围和剩余范围
任务信息预期版本和结果版本
```

不同方法的条件不得摊平成任务总条件表。无条件方法以一个显式空条件组表示“无需额外条件”，不能与“条件结构缺失”混同。条件结构无法读取、组语义不完整或版本冲突属于结构 / 工程非成功，不得写成条件不具备。

即使已经发现一组条件具备，也必须完成当前全部候选方法和条件组的核验；未核验候选可能具有更低执行代价。全部核验完成后，至少一组具备才进入`待执行前选择`；全部不具备才进入`条件缺失 / 等待条件`。

## 5. task owner 与 manager 的双线确认

任务筹办通过 task owner 唯一入口补全当前任务信息，不建立候选账、条件账、筹办结果账、专用线程或 outbox。任务工作线程把本次结果通过唯一消息交给 manager；manager 必须独立读回同一任务、轮次、状态、版本、候选 / 条件信息和覆盖进度，确认结果与调用前状态一致后，再经任务状态正式提交入口迁移。

筹办负责形成信息，manager 负责验证和推进。这是双线确认，不是两套事实。消息、日志、队列位置、线程运行态和 provider 返回值均不能替代 task owner 当前信息或任务状态。

## 6. 业务结果与技术非成功

业务结果仅包括：继续找方法、方法查找完成且有候选、方法缺失、继续查条件、条件核验完成且至少一组具备、条件缺失。它们分别映射到 5210 的筹办业务状态。

技术非成功另行处理：

- 发布未知、队列投递或资源失败：保持原业务状态和原工作项，以原幂等身份读回 / 重试；
- 当前性或版本漂移：本次结果失效，保持同一业务子状态并以新截止重新派发；
- ABI、引用、断言、结构不变量或内部代码错误：停止受影响调用并交工程修复。

技术非成功不得写成方法缺失、条件缺失、合法等待、需求或子任务。

## 7. 缺失信息与需求边界

方法缺失、条件缺失和方法结构缺口首先只是当前父任务材料。manager 可以把具名定位发送给 self；只有 self fresh 读取材料并产生、确认独立且必要、父域合法、目标状态可最终判定的后继目标后，task owner 才记录为正式任务子目标承接记录，需求 owner 再于发布前精确匹配并发布或复用需求。

筹办、任务工作线程、manager 和消息都不得直接建立需求、子任务、方法首或能力缺口节点。外部事实尚未产生、时间未到或已有明确事实生产者时优先形成等待 / 重触发，不因“当前不具备”自动增加需求。

## 8. 执行前选择

当任务处于`待执行前选择`时，执行前入口 fresh 复核每个候选方法、内容版本、条件组、输入 / 参数、动作范围、禁止项、安全硬门、验证 / 归因和当前可用性。只在可比较的可用候选中比较总代价，选择收益与付出综合代价最小的一项；代价至少允许包含安全值或服务值的收益 / 付出、时间成本及方法正式登记的其它可比较成本。

条件在筹办阶段曾具备，不保证执行前仍具备；执行前必须 fresh 复核。未知、不可比或并列最优时不选择。成功后才由 task owner 的唯一组合入口形成选择记录、路径、实例方法和执行冻结；未选候选只保留为本轮任务信息，不形成第二当前路径。

## 9. 回流与验证

新方法发布、条件变化、来源 / 目标 / 方法版本变化或冻结失效只提供重触发事实；manager 必须读取当前任务状态决定回到找方法、查条件或执行前选择，不能沿用旧核验结论。任务已经进入执行或结算时不在同一轮自动重筹办；轮次收束后只有 self 的正式继续决议可以建立新任务轮次。

验证至少覆盖：多次找方法、完整覆盖后才进入查条件、多方法多条件组、全部核验后才进入执行前选择、无条件方法、方法缺失与未完成 / 技术失败分账、条件缺失与结构错误分账、manager 独立读回和条件式状态迁移、消息重投不重复 provider、筹办不选择 / 冻结 / 建需求，以及执行前 fresh 可用性与总代价选择。

## ARCH-L4 方法筹办边界（20260824）

方法查找、条件查找与条件当前具备性核验属于 ARCH-L4 任务筹办；方法服务只提供结构和值式能力投影。适用性、实际采用、代价比较、路径、实例和冻结属于执行前选择。任务 / 方法虚拟存在及治理状态不得成为 ARCH-L2 第二权威。
