# 8100 子规范 自我线程与任务管理线程权责边界

编号：8100
日期：20261009
版本：v1.17
状态：正式子规范

直接上级规范：3100、3200、3300、8000。

直接依赖规范：5090、5260、5350、6100、6120、6340。

相关边界规范：6140、6150、8110、8200、8210。

## 1. 定位

本规范规定self线程、manager和worker之间的职责、消息、状态推进、停止和恢复边界。三者是运行角色，不是新的业务对象或事实仓。

```text
self：决定为什么做、是否做、结果以后怎么办
manager：决定当前调度哪个任务、形成哪种工作包并复核状态推进
worker：执行一次有界功能调用并返回结构化结果
```

## 2. self身份与初始化

self的业务身份是世界树中的唯一自我存在节点。线程对象、线程编号、启动次数和运行代次都不是self业务身份，不进入需求、任务、消息或恢复材料。

self线程初始化过程负责调用正式初始化入口，确保至少建立并读回：

- 全局基础数据集；
- 世界树根场景；
- 自我所在场景；
- 自我存在节点及全局自我指针；
- 需求树及安全、服务双根；
- 方法根和已经登记的本能函数。

初始化只能按各业务类公开入口完成，不得直接拼装底层字段。任一必需结构未建立或无法完整读回时不开启治理门。

邮箱容量、等待时限和普通运行参数由应用具名配置提供，不写入self业务身份。无窗口模式复用现有宿主；控制面板是投影，不是治理事实来源。

## 3. self线程职责

self负责：

1. 处理进入self邮箱的具名消息类型。
2. fresh复核根需求和普通需求，决定是否仍需治理。
3. 产生并确认新的具体需求；不直接写需求结构。
4. 向manager发送建立/复用任务、暂停、取消或重新启用意图。
5. 在执行前综合读取需求、冻结、资源和安全材料，决定执行、暂缓、拒绝或重判。
6. 在影响评估后fresh读回D、T、X、A和当前世界事实，形成七类后继决议。
7. 在任务正式完成后编排一次任务完成结算。
8. 处理真实结果、副作用、安全事件、方法反馈和必要的后继需求材料。

self禁止直接执行普通方法、直接修改任务状态、用消息内容替代业务类读回、用线程局部缓存判定需求满足，或把完成结算与需求/价值结算合并。

self消息线程启动后立即向唯一自我工作线程提交一次需求树全局扫描。工作线程串行调用需求owner与任务owner的结构化全集读取并返回数量、缺T需求、多T需求和孤立T材料；它不向manager发消息。self处理完整结果后，才逐个向manager发送“扫描补齐关联”任务意图。工作完成通知只唤醒self读取共享结果，不携带或持久化业务事实，不能受外部邮箱容量影响而丢失。

self必须在完整处理扫描结果、并取得全部manager终结回执后，向工作线程确认该结果已经接收；只有确认成功才能释放本地请求和结果句柄并回到空闲。确认失败属于内部错误，不得假装释放成功后继续提交下一次扫描。self或工作线程任一启动失败、停止或析构时，都必须请求停止并join已经创建的工作线程，不得以`detach`或仅标记self完成绕过生命周期闭环。

## 4. manager职责

manager负责：

1. 接收self的任务意图并通过任务类建立或复用T和Vt。
2. 按当前需求权重、可执行性、预期损耗、安全限制和正式调度规则动态排序。
3. 根据Vt状态形成找方法、查条件、W3-A动作、W3-B结果等工作包。
4. 读取worker结果后独立读回正式任务和世界材料，不能只信worker返回。
5. 请求任务类执行合法状态迁移。
6. 影响评估形成后，把正式定位发给self并等待self决议。
7. 复核self决议的T、D、X、A和当前状态，再请求任务类发布终态或后继状态。
8. 保存运行期等待结果定位；重启或通知丢失时从正式current-only材料重新发现可推进工作。

manager不产生需求、不代替self决定终态或后继、不直接改写方法知识、不把队列、缓存或“最近错误”当业务事实，也不因队满或超时把技术失败写成任务失败。

## 5. worker职责

worker每次只消费一个不可变工作包，并在一次有界调用后返回。worker可以执行：

- 方法查找；
- 条件检查；
- 参数或结果方案核验；
- W3-A动作；
- W3-B结果获取；
- 其它已登记的纯读取或固定治理功能。

worker不得：

- 等待长期外部条件而永久占用线程；
- 直接决定任务状态、需求满足或后继；
- 产生需求；
- 把局部函数返回当正式现实结果；
- 在动作可能已经发出时重做W3-A；
- 修改不属于本工作包的任务。

## 6. 筹办和工作包

筹办不建立筹办轮次。manager根据T当前状态分步形成工作包，每个工作包只覆盖一种功能。worker返回后，manager独立读回并决定下一合法步骤。

同一T可以先后进行多次找方法或查条件，但临时候选和扫描进度不取得业务身份。进入W3-A以前必须已经形成唯一方法采用、实际参数、预计变化、结果要求、可实现结果获取方案及必要安全材料。

每次真实方法调用建立一个执行实例X，不建立执行轮次。W3-A与W3-B必须使用同一T和X；W3-B不得新建X或重做动作。

## 7. 消息模型

消息以类型路由，不设计一个包含所有业务字段的万能消息。共同信封只含：

```text
消息身份
消息类型
原请求身份
发送方角色
接收方角色
```

具体消息类型按需携带D、T、X、A、工作包或状态定位。至少支持：

| 方向 | 类型 | 用途 |
| --- | --- | --- |
| self→manager | 任务意图 | 建立/复用、暂停、取消、重新启用或调度某T |
| self→manager | 扫描补齐关联 | 为缺少T的正式D建立/复用唯一T；不等于推进执行 |
| manager→worker | 找方法/查条件 | 执行单次筹办功能 |
| manager→worker | W3-A动作 | 对既有X执行一次动作 |
| manager→worker | W3-B结果 | 对既有X获取结果，不执行动作 |
| worker→manager | 工作结果 | 返回结构化结果和正式材料定位 |
| manager→self | 待决议 | 通知T、X、A及结果已经可读 |
| self→manager | 后继决议 | 完成、继续、重试、重新筹办、等待、失败或取消 |
| manager→self | 完成状态定位 | 请求self办理任务完成结算 |

入口接收回执只证明消息已接纳，不证明处理终结。永久拒绝、冲突或内部错误必须反馈原消息和原请求，不能只覆盖全局“最近错误”。消息不是持久事实账。

## 8. 状态推进与独立读回

任何线程都不能直接写Vt字段。manager根据公开任务类入口请求状态迁移；任务类核验状态机并写入。

worker结果、消息和本能函数返回都只是推进材料。manager必须独立读回正式状态；self在终态或后继决议前再次fresh读回。跨多次调用不承诺共同快照，发现当前状态变化时按新状态重判。

## 9. W3和结果等待

W3-A只负责动作。W3-B只负责结果获取。

- 结果立即可得：W3-A后可以继续形成W3-B工作；
- 结果延迟或异地：manager登记等待定位并释放worker；
- 正式状态先于等待登记到达：manager登记后主动补查已有正式状态；
- 多渠道：按冻结规则组合；
- 渠道失效：恢复备用渠道或保持结果未知；
- 动作可能已发生：只恢复W3-B，不重做W3-A。

## 10. self决议、完成结算和重新启用

manager形成A后把T推进为`等待自我决议`。self fresh读取后形成七类决议，manager复核后由任务类发布状态。

manager发布`已完成`后必须保留结算所需X、A和运行定位，直到self通过任务类完成结算并回传确认。失败或取消不建立完成结算。

收束T只有在self fresh确认同一D再次需要治理后才能重新启用；manager复核后迁移到`待查找方法`或`等待条件`。旧消息、线程重启、定时唤醒或队列重放不能直接重开。

## 11. 容量、停止和析构

邮箱容量统计覆盖已经接纳但尚未终结的全部不同消息，包括待处理、处理中、延后和等待依赖；同一消息只计一次。批处理只能有一个推进持有位置。

停止要求：

1. 停止普通新派发，但继续收口已经发生的动作和必要结果。
2. 所有等待均可被停止信号唤醒。
3. worker正在执行的同步调用必须按其合同返回；不得用detach逃避生命周期。
4. join串行化，禁止线程join自身。
5. 区分尚未启动、已经join、启动失败和真实join错误。
6. join完成前依赖对象不得销毁。
7. self停止时同时唤醒唯一工作线程；已经返回但尚未被self处理的扫描结果必须终结或明确取消，禁止detach。

## 12. 恢复与非成功

恢复只依据current-only业务结构和原请求，不依据运行代次或历史快照。

| 情况 | 处理 |
| --- | --- |
| 资源暂不可用 | 保留原消息和已形成进度，等待重试 |
| 依赖未就绪 | 等待明确生产者或控制唤醒 |
| 依赖未实现 | 明确反馈未实现，不忙重试 |
| 发布未知 | 按原请求查询或恢复，不另签请求 |
| W3-A已发出/可能发出 | 只恢复W3-B |
| 完成未结算 | 重新通知self补结算 |
| 结算已存在 | 读回并终结原消息 |
| 内部结构不一致 | 停止受影响路径，保持退出能力和诊断 |

需求扫描运行状态固定为`空闲、等待扫描结果、处理扫描结果、等待manager承接回执、失败、已停止`。扫描执行中再次收到触发只合并为待复核，不建立第二个扫描。

## 13. 验证边界

最低验证覆盖初始化开门、三个角色边界、消息类型路由、活动容量、停止/join、无结果方案零动作、W3-A单次、W3-B延迟恢复、通知先到补查、精确特征身份核验、self七类决议、完成结算定位保留、重新启用和重复/乱序消息。

规范发布不证明当前代码已接通普通应用、网页端口、外部观察生产者、跨进程恢复或完整治理闭环。
