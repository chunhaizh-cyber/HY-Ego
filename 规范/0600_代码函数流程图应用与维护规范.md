# 0600 代码函数流程图应用与维护规范

编号：0600
日期：20260802
状态：现行施工规范
规范类别：施工规范
权威等级：正式规范

## 1. 定位

本规范规定项目源码函数流程图、逐行映射、函数调用关系和函数知识图谱形成后，如何用于理解实现、核对规范、发现缺口、形成目标设计、生成施工计划、验收代码和持续维护。

本规范属于施工规范，只定义项目工程证据与设计治理方法，不定义需求、任务、方法、状态、动态、因果等机器事实，不改变任何逻辑规范。流程图及其图谱是可追溯的工程证据，不是运行期机器事实，也不单独构成代码实施许可。

直接上级规范：无

直接依赖规范：0100

相关边界规范：0050、0300

## 2. 适用对象

本规范适用于下列项目源码产物：

```text
单函数现状流程图
单函数逐行代码映射表
函数清单与覆盖清单
待展开函数队列
函数调用关系图
函数知识图谱
当前能力证据目录
输入契约与调用语境表
非成功返回审查表
规范符合与偏差清单
单函数施工流程图
逐函数逐节点实现分析
函数功能确认
施工计划与验证矩阵
目标业务流程图与业务—能力—函数映射
能力候选队列
```

标准库、操作系统、编译器、第三方库及其它非本项目源码函数只作为边界调用记录，不为其生成内部流程图。

## 3. 三类事实必须分账

流程图治理必须始终区分：

```text
实现事实：冻结版本中的项目源码实际执行路径
规范事实：规范目录登记的正式项目语义
目标事实：经规范裁决后拟形成的函数合同、施工路径和验证结果
```

单函数现状流程图只表达实现事实。单函数施工流程图只表达目标事实。规范符合与偏差清单负责比较两者，但不得把任一方静默改写为另一方。

实现与规范不一致时，先登记偏差并裁决归属：

- 实现错误或冗余；
- 函数职责、位置或边界错误；
- 必需接口或函数缺失；
- 规范缺失、冲突或无法裁决；
- 仅有诊断、自检、验收或测试用途；
- 无调用证据但尚不能直接判定删除。

未经归属裁决，不得直接修改规范或删除实现。

## 3.1 业务流程与代码流程分层

目标业务流程图表达一个业务闭环，至少冻结业务输入、输出、前置、步骤、分支、事实读写、非成功结果、完成条件和验证点。它的节点表达所需业务操作或能力合同，不直接假设某个函数一定存在。

业务图形成代码设计时必须经过：

```text
业务节点
-> 所需能力合同
-> 当前能力证据候选
-> 直接复用 / 组合 / 适配 / 扩展 / 新建裁决
-> 目标函数组与物理位置
-> 目标单函数施工流程图和详细设计
```

业务流程图与单函数代码流程图不一一对应。一张业务图可以映射一个主函数组和多份单函数图；同一共享函数可以被多张业务图引用。执行后形成的现状代码流程图只能按真实代码更新，不得用目标业务图反向伪造实现事实。

## 4. 从根函数建立覆盖图谱

函数图谱从一个或多个具名项目入口开始。普通程序优先从 `main` 及其模式分支开始；独立库、工具或测试从其正式导出入口开始。

每个根函数按源码语句顺序处理：

1. 判断该语句是本函数内具体指令，还是对另一个函数的调用。
2. 本函数内具体指令直接形成当前函数流程节点。
3. 项目源码函数调用形成调用节点和调用边，并把未覆盖的被调函数加入待展开队列。
4. 非项目源码调用只记录边界、参数、返回和异常影响，不加入待展开队列。
5. 被调函数已经建图时建立双向引用，不重复生成第二身份。
6. 递归调用记录回边，不无限展开。
7. 间接调用、回调、函数对象、虚调用或注册表调用无法唯一解析时，记录候选目标、选择依据和待核状态，不伪造唯一调用边。

待展开队列按可重复执行的稳定顺序处理，至少保留函数身份、来源调用节点、层级、状态和唯一图路径。一个项目源码函数在同一覆盖基线中只能有一个现状流程图身份。

## 5. 单函数图的最小合同

每个单函数流程图必须冻结：

```text
唯一函数身份
归属模块和文件
完整签名
参数及所有权
返回结果
实现基线
调用方和被调函数
对应逐行映射
入口前置
结构读取与写入
逻辑内返回
内部错误
生命周期与资源释放
验证入口
```

图内节点只能是：

- 调用另一个具名函数；
- 本函数内一条具体判断、顺序操作、循环控制、读取、写入、事务操作、资源操作或返回指令。

模块、服务、阶段、处理、初始化、执行、校验等抽象名称只能作为分组或归属信息，不能代替可执行节点。

## 6. 各产物的应用方向

| 产物 | 首要用途 | 不能单独证明 |
| --- | --- | --- |
| 单函数现状流程图 | 理解函数实际分支、顺序、资源与返回 | 规范正确、目标合理、代码可继续扩展 |
| 逐行代码映射表 | 证明源码有效语句均已进入节点，定位偏差到精确位置 | 行为已经通过运行验证 |
| 调用关系图 | 判断入口可达性、调用方向、层级穿透和影响传播 | 被调函数内部合同正确 |
| 函数知识图谱 | 汇总函数、文件、模块、调用边、规范、设计、计划和验证之间的可追溯关系 | 图中关联对象已经实现或完成 |
| 当前能力证据目录 | 聚合冻结基线下的提供根函数、合同证据、实现 / 验证状态和缺口，供设计发现候选 | 候选能力对某个新业务可以直接复用 |
| 目标业务流程图 | 冻结一个业务闭环及其业务节点、事实和完成条件 | 具体函数、物理位置或代码已实现 |
| 待展开队列 | 保证覆盖可继续、可去重、可恢复 | 队列中的函数都必须保留 |
| 输入契约表 | 判断入口材料来源、上游保证和允许拒绝 | 所有调用方都满足契约 |
| 非成功返回审查表 | 区分允许返回与内部错误 | 返回分支已经修复 |
| 偏差清单 | 为每个缺口指定唯一治理归属 | 已经取得代码修改许可 |
| 施工流程图 | 冻结目标函数合同和目标路径 | 目标已经实现 |
| 验证矩阵 | 规定静态、构建、运行和结构验收证据 | 未执行的验证已经通过 |

## 7. 调用关系图的使用方法

调用关系图至少用于：

1. 从入口向下确认哪些项目函数真实可达。
2. 从变更函数向上查找直接和间接调用方，确定影响范围。
3. 识别入口承担的领域实现、自检、诊断、模式选择和资源宿主职责，辅助薄入口治理。
4. 识别跨层直接调用、绕过领域服务、反向依赖、循环依赖和装配所有权混乱。
5. 识别只被自检或诊断路径调用、只被生产路径调用、两类路径共用或没有已知调用方的函数。
6. 为函数拆分、模块归属、接口冻结和最终接线计划确定边界。

“没有已知调用方”只形成删除候选。删除前仍须核对导出接口、反射或注册、回调、动态装载、构建条件、平台分支和外部消费证据。

## 8. 函数知识图谱的使用方法

函数知识图谱应以稳定身份记录以下关系：

```text
函数 -> 归属文件 / 模块
函数 -> 调用函数
函数 -> 被调用方
函数 -> 现状流程图
函数 -> 逐行映射
函数 -> 适用规范
函数 -> 施工流程图
函数 -> 逐节点实现分析
函数 -> 详细设计
函数 -> 施工计划
函数 -> 验证项与证据
偏差 -> 受影响函数 / 节点
偏差 -> 唯一治理归属
```

知识图谱用于追踪影响、覆盖和缺口，不得把“存在一条关联边”解释为符合、实现或验收完成。关系状态至少区分已验证、待核、候选、已退出和不适用。

## 8.1 当前能力证据目录

当前能力证据目录是函数身份、调用关系、现状流程图、正式规范和验证证据的聚合投影。它回答“冻结代码基线中有哪些具名能力证据”，不回答“某项新业务是否一定可以复用”。

每项能力至少记录：

```text
稳定能力编号和名称
领域与功能摘要
提供根函数组、完整签名和代码基线
输入事实、前置条件和所有权
输出事实、状态读取 / 写入和副作用
事务、逻辑内结果、内部错误和生命周期
规范、现状流程图、自检 / 验证证据
实现状态、验证状态、具名缺口和待复核原因
```

能力条目不得只由函数名、自然语言搜索、单条调用边或自动摘要形成。提供根函数必须存在于同一冻结基线的函数身份表；合同字段没有源码、正式规范、流程图或验证证据时必须标记 `未知 / 待核`，不得用默认值补齐。接口骨架、声明存在、编译通过和局部自检必须与真实成功能力分账。

能力目录优先登记公开领域服务、运行期组合器、仓库 / 会话公开入口、线程消息入口和外部适配边界。构造函数、简单访问器、运算符、自检辅助和内部算法默认保留为函数图谱节点，只有具备独立业务或基础设施合同证据时才形成能力条目。

计划设计必须为每个所需业务能力另建复用裁决矩阵，至少记录所需合同、候选能力编号、输入 / 输出 / 前置 / 副作用 / 事务 / 错误 / 版本差异、直接复用 / 组合 / 适配 / 扩展 / 新建结论和验证要求。能力目录条目只提供候选证据，不能替代该裁决。

### 8.2 能力候选队列与首批后的持续扩充

能力证据目录必须维护机器可读候选队列：

```text
流程图/主程序可达调用关系/能力证据目录/能力候选队列.json
```

候选状态只允许：

```text
待识别
待补流程图
待补规范证据
待补合同
待补验证
已登记
非独立能力
已排除
```

首批目录完成后不得转为静态清单。每个已发布流程图批次、代码结果提交或正式规范 / 验证证据变化，都触发受影响子图的能力候选扫描：

```text
读取已发布新基线和本批函数变更
-> 提取公开业务、组合、机器事实写入、仓库 / 会话、线程 / 数据库 / 外设、只读查询根函数候选
-> 与现有稳定能力按完整合同去重
-> 新建候选或补充原条目
-> 绑定函数身份、现状流程图、规范和验证证据
-> 更新状态与覆盖统计
-> 发布后继续下一批
```

优先级为：当前计划需要的能力；公开业务服务和组合入口；写机器事实与事务入口；仓库 / 会话入口；线程、数据库和外设边界；只读查询与投影。内部辅助默认标记 `非独立能力`，除非有独立业务或基础设施合同证据。完成标准是每个符合准入条件的 `main` 可达根函数要么进入稳定能力条目，要么具备 `非独立能力 / 已排除` 的可回查理由。

## 9. 逐函数逐节点核规

覆盖完成后，对每个函数及其每个节点依次核对：

1. 函数职责是否属于当前模块和文件。
2. 完整签名、参数、返回、所有权和生命周期是否有正式依据。
3. 每个调用节点的目标函数、实参与结果传递是否明确。
4. 每个指令节点的判断、读取、写入、事务、资源和返回是否符合正式规范。
5. 入口拒绝是否发生在写入前。
6. 前置成立后的内部异常是否被错误包装为普通失败。
7. 是否存在重复实现、不可达实现、测试实现混入生产、诊断参与机器裁决或入口承载领域正文。
8. 是否存在规范要求但图谱中没有任何承载函数、调用路径或验证入口的能力。

核对结果按以下类型登记：

| 类型 | 含义 | 后续归属 |
| --- | --- | --- |
| 符合 | 实现与正式合同一致且证据完整 | 保留并绑定验证 |
| 证据不足 | 暂不能证明符合或偏差 | 补读取、调用或验证证据 |
| 实现缺失 | 规范要求存在，但没有承载函数或调用路径 | 形成目标函数与施工设计 |
| 接口缺失 | 消费路径需要具名函数，但接口尚不存在 | 冻结接口合同并形成提供者需求 |
| 实现偏差 | 函数或节点行为违反正式合同 | 形成施工流程图和代码计划 |
| 归属偏差 | 行为可能需要，但位于错误层级、入口或模块 | 形成拆分 / 搬移设计 |
| 冗余候选 | 无正式职责、无必要调用或与既有能力重复 | 完成删除证据后形成删除计划 |
| 规范缺口 | 无法从正式规范裁决目标行为 | 先修订规范，暂停受影响切片 |
| 设计缺口 | 规范明确，但目标函数、节点或验证尚未冻结 | 补流程图和设计，不交执行裁决 |

## 10. 从偏差形成目标设计

偏差不得直接转换为代码修改。目标设计按以下顺序形成：

```text
偏差身份与证据
-> 正式规范裁决
-> 目标函数职责
-> 完整函数合同
-> 单函数施工流程图
-> 每节点实现分析
-> 调用图中的目标边
-> 数据、所有权、事务、错误和生命周期设计
-> 详细设计
-> 验证矩阵
-> 施工计划
```

需要其它模块尚不存在的函数时，先确认其在正式模块边界内可实现，再冻结最终模块、函数名、DTO、签名、所有权、返回和错误合同，形成具名提供者需求。消费设计可以按该合同继续推演，但不得把待实现接口写成已经存在。

## 11. 计划拆分方法

施工计划优先按以下边界拆分：

- 单一业务对象或领域服务；
- 文件和模块所有权；
- 一个稳定公开接口组；
- 一个可独立验证的调用子图；
- 共享入口、工程登记和最终接线由后继装配计划统一拥有。

计划必须回指受影响函数、流程节点、偏差编号、目标调用边和验证项。多个偏差只有在同一原子事务、同一不可拆文件、同一接口所有权或同一最终切换中不可分割时才合并。

流程图覆盖顺序、文件生成顺序和知识图谱层级不自动构成施工依赖。

计划拆分前必须先按目标业务流程确定闭环边界，再按能力所有权、目标函数组、文件 / 模块、公开接口和独立验证子图拆分。不得直接把代码流程图层级或每一份函数图机械等同为一份计划。

## 12. 代码实施后的闭合

施工完成后必须按目标调用子图回查：

1. 实际函数签名与冻结合同一致。
2. 实际函数内每条有效指令能映射到施工节点。
3. 实际调用边与目标调用图一致。
4. 规范要求的拒绝、内部错误、事务、发布和资源释放路径均有验证。
5. 删除或搬移后没有遗留调用、重复实现、旁路接线或失效工程登记。
6. 验证结果绑定到函数和节点，不只绑定到整个可执行文件。
7. 现状流程图按新实现基线更新，施工流程图保留其目标版本身份。

只有“规范—函数—节点—调用边—验证”能够双向追溯，关联偏差才能关闭。编译通过、流程图生成完成或计划提交均不能单独关闭偏差。

## 13. 增量维护

代码基线变化后，不要求无差别重画全部图谱。先计算受影响子图：

```text
直接修改的函数
+ 签名或返回变化涉及的调用方
+ 调用边变化涉及的调用方和被调方
+ 共享 DTO / 接口合同变化涉及的消费者
+ 规范变化涉及的函数与节点
+ 验证合同变化涉及的验证入口
```

只更新受影响函数、边、映射、偏差和验证状态；未受影响图保持原基线身份。聚合清单和知识图谱在发布前重新计算覆盖数量、重复身份、悬空边和待展开队列。

增量更新不得把不同基线的函数节点合并成同一“当前状态”。每份图和聚合关系必须能回指其实现基线。

能力证据目录按受影响子图增量刷新。能力条目绑定的提供根函数、签名、直接 / 间接行为、规范或验证证据变化时，先把该条目标记为 `待复核`；重新核对完整合同和证据后才能恢复原实现 / 验证状态。未受影响条目保持稳定能力编号，不因制图顺序或文件生成顺序重排。

流程图批次和能力目录批次使用独立所有权与独立提交，但能力目录只消费已经发布的流程图 / 调用图基线。流程图批次先发布函数变更清单和下一续点，能力目录随后按该提交刷新候选队列；不得读取另一维护者尚未提交的 WIP 形成正式能力条目。

## 14. 完成标准

函数图谱“覆盖完成”必须同时满足：

- 全部根函数已登记；
- 项目源码调用边均已分类；
- 待展开队列为空，或剩余项均有具名排除理由；
- 每个覆盖函数有唯一现状图和逐行映射；
- 递归、间接调用和外部边界已明确记录；
- 无重复函数身份、悬空内部调用边或无法归属文件。

函数图谱“应用完成”还必须满足：

- 每个函数和节点已有规范核对状态；
- 每个偏差有唯一类型和治理归属；
- 规范缺口已先行裁决；
- 需要施工的偏差已有目标函数合同、施工图、节点分析、详细设计、计划和验证矩阵；
- 已施工项完成规范—函数—节点—调用边—验证双向追溯；
- 冗余候选均有独立删除证据，未凭无调用方结论直接删除。
- 每个目标业务节点都能双向追溯到所需能力、复用 / 新建裁决、目标函数组和验证。
- 每个符合准入条件的当前可达根函数都已有稳定能力条目，或有非独立 / 排除理由。

覆盖完成不等于应用完成；应用完成也只证明工程治理闭合，不证明整个项目能力或业务阶段完成。

## 15. 禁止事项

1. 禁止为非项目源码函数生成内部流程图。
2. 禁止一张流程图承载多个根函数。
3. 禁止用模块、服务或抽象阶段冒充函数节点。
4. 禁止把现状流程图直接改名为施工流程图。
5. 禁止用流程图覆盖正式规范，或用规范目标伪写实现事实。
6. 禁止仅凭无调用方、行数多、看似重复或只在自检中出现就删除函数。
7. 禁止把知识图谱关联、编译成功、日志输出或图表数量写成能力完成。
8. 禁止遗漏调用边后宣称覆盖完成。
9. 禁止继续新建或要求 HTML 流程图配对文件；Markdown Mermaid 是唯一正式图载体。
10. 禁止在规范、接口或设计未裁决时把缺口交给代码实施者临时决定。
11. 禁止把当前能力证据目录中的候选、函数存在或局部验证直接写成新业务的复用结论。
