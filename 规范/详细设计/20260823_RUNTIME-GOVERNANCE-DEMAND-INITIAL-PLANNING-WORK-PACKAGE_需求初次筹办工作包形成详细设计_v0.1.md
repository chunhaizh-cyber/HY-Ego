# RUNTIME-GOVERNANCE-DEMAND-INITIAL-PLANNING-WORK-PACKAGE 需求初次筹办工作包形成详细设计 v0.1

日期：2026-08-23

## 1. 目标、范围与完成条件

本设计闭合 HY-Ego 当前最早、可以独立施工的任务筹办 provider：

```text
调用方给出需求身份、共同事实截止 G0 和任务建立幂等身份
-> provider 调用已发布的需求当前满足裁决入口
-> 只有同 G0 正式裁决为未满足时，以裁决中的当前成员关系取得完整需求列表项
-> 由任务 owner 在 G0 上保证该列表项当前尚无任务并唯一新增任务
-> 在任务建立后的 G1 权威读回唯一当前任务
-> 形成不含旧路径、旧实例、旧执行轮次和旧实际结果的初次筹办工作包
```

完成必须同时满足：

1. `L2任务结构服务::新增任务`在任务 owner 锁内强制“一个当前需求列表项最多一个当前任务”，并保留同幂等键精确重复收敛；
2. 新的 DATA 外 provider 自己调用`运行期只读查询组合器::裁决需求当前满足`，只在结果为`未满足`且全部载荷来自同一 G0 时继续；
3. 首次成功只发布一个新任务及其任务虚拟存在，筹办轮次固定为 1；
4. provider 在 G1 按需求列表项权威读回唯一当前任务，只有身份、列表项、生命周期和来源全部互证后才形成工作包；
5. 工作包是下一普通筹办入口的不可变输入，不是路径、实例、冻结、执行许可或任务已经筹办完成的事实；
6. 同一任务建立幂等键与同一列表项在原 G1 仍为当前截止且任务仍当前时返回原任务；其后有新发布时返回当前性分流并要求上层重判；同键换列表项、并发新键、已有当前任务、许可、资源和内部错误均具名分账；
7. 任何成功发布后的读回或组包失败都不撤销已发布任务，只能以原幂等键读回收敛；
8. 执行者不需要再决定 DTO、函数签名、物理位置、事务顺序、状态映射、验证矩阵或完成声明边界。

本设计不消费`子需求已回流待父需求重判`记录。该消费者必须等本 provider 和“不依赖任务实际结果的新重筹办轮次 provider”都形成后再设计。

## 2. 明确排除项

本叶不做：

- 不扫描、消费、退出或修改任务子目标承接记录；
- 不读取子需求回流材料，不唤醒记录中的旧来源任务；
- 不调用`任务目标未达成重筹办触发提供者`，不构造`下一筹办工作包`；
- 不填写、猜测或复活旧路径、旧实例、旧执行轮次、旧实际结果、旧冻结、旧治理状态或旧筹办轮次；
- 不实现已有当前任务时的新重筹办轮次；
- 不调用任务特征方法查找，不形成方法候选、路径、实例方法或执行请求；
- 不修改需求、列表项、目标合同或需求满足事实；
- 不进入逐成员结算、结果共用 / 争用、成员分配优先级、价值、预算或归因；
- 不把工作包、函数返回、日志、自检或任务节点存在升级为任务已筹办、需求已满足或生产闭环完成；
- 不修改正式规范、规范目录、共享当前代码图谱、能力证据目录或知识库聚合文件。

### 3.2 当前能力复用裁决

| 所需能力 | 当前入口 | 裁决 |
| --- | --- | --- |
| 需求当前未满足证据 | `运行期只读查询组合器::裁决需求当前满足` | provider 直接调用；不信任调用方拼装的裁决值，不重做裸值比较 |

| 新增任务及虚拟存在 | `L2任务结构服务::新增任务` | 扩展：当前未在 owner 锁内拒绝第二个当前任务，且精确重复状态被读回 helper 压成`已提交` |
| 任务唯一性读投影 | `L2任务结构内部::按需求列表项读取当前任务当前投影` | 在`新增任务`锁内复用；0 合法、1 已有、>1 内部不一致 |
| 初次筹办工作包 | 当前不存在 | 本叶新增独立 DTO 和 provider |
| 任务实际结果后的重筹办 | `任务目标未达成重筹办触发提供者::形成待重筹办与下一筹办工作包` | 不适用；强制旧路径、旧实例、旧结果和正式未达成裁决 |
| 方法查找 | `任务特征方法查找与条件提议提供者` | 暂不消费；当前只接受上述`下一筹办工作包` |

### 3.3 唯一最早缺口

现有代码已经能保存任务结构，但测试直接调用 DATA-L2 `新增任务`，没有 DATA 外“未满足需求无当前任务 → 初次筹办工作包”provider。直接设计子需求回流消费者会迫使执行者在两个缺失分支上临场发明合同：

1. 无当前任务时如何建立唯一任务并形成初次筹办输入；
2. 有当前任务但没有任务实际结果时如何形成新筹办轮次。

因此本轮只闭合生命周期更早、可独立施工的第 1 项。第 2 项和最终回流消费者继续保留为直接后继，不进入计划索引库存。

## 4. 正式依据与不变量

- 0050：运行期已发布代次权威、DATA 与业务解释分权、幂等、当前性、发布后不撤销和结构化非成功；
- 3100：需求当前满足按目标三元组和当前事实实时裁决，任务存在不能替代需求满足；
- 3200、5090、5200：一个当前需求列表项对应唯一当前任务，任务承接需求目标且不修改需求；
- 5210、5230、5250：初次筹办轮次从 1 开始，普通新筹办保留目标实时短路，路径和执行冻结属于后继；
- 5220：子需求回流只触发父需求重新裁决，不自动复活旧任务；
- 0600 与代码施工规范：函数名、变量名和业务成员名使用中文；新业务 provider 位于 DATA 之外并只经公开服务合同访问任务结构。

固定不变量：

```text
初次筹办工作包
= provider 在同 G0 取得正式未满足裁决后投影的来源需求
+ 当前成员和完整需求列表项
+ 任务 owner 在 G0 -> G1 唯一发布的新任务
+ G1 按列表项的唯一当前任务读回
+ 筹办轮次 1
+ 运行代次
```

并且：

```text
初次筹办工作包不含旧路径
初次筹办工作包不含旧实例
初次筹办工作包不含旧执行轮次
初次筹办工作包不含旧实际结果
初次筹办工作包不含待重筹办治理状态或目标裁决证据
```

## 5. DTO、模块与公开函数

### 5.1 新数据合同

新文件：

```text
海中鱼巣/领域/内部治理/任务初次筹办.数据.h
```

由新数据头唯一声明、并由新模块使用`export { #include "任务初次筹办.数据.h" }`唯一导出以下类型；数据头使用专属`任务初次筹办数据_NO_INCLUDES`宏支持模块先 import 正式类型所有者后抑制重复 include，普通头文件消费者不定义该宏：

```cpp
inline constexpr std::uint32_t 需求初次筹办准备合同版本 = 1;

struct 需求初次筹办准备请求 final {
    std::uint32_t 合同版本 = 需求初次筹办准备合同版本;
    std::uint64_t 请求身份 = 0;
    std::uint64_t 运行代次 = 0;
    L2结构请求头 请求头;
    L2需求身份 需求;
    L2结构幂等身份 任务建立幂等身份;
    friend bool operator==(const 需求初次筹办准备请求&,
        const 需求初次筹办准备请求&) = default;
};

enum class 需求初次筹办准备状态 : std::uint8_t {
    已形成 = 1,
    精确重复 = 2,
    目标已满足 = 3,
    已有当前任务 = 4,
    证据不足 = 5,
    当前性漂移 = 6,
    引用冲突 = 7,
    不可比较 = 8,
    入口拒绝 = 9,
    许可拒绝 = 10,
    资源失败 = 11,
    内部错误 = 12
};

struct 任务初次筹办工作包 final {
    std::uint32_t 合同版本 = 需求初次筹办准备合同版本;
    std::uint64_t 运行代次 = 0;
    L2任务事实 任务;
    L2任务身份来源事实 任务身份来源;
    L2需求事实 来源需求;
    L2需求列表成员关系事实 当前成员关系;
    L2需求列表项事实 需求列表项;
    std::uint64_t 筹办轮次 = 1;
    std::uint64_t 原共同事实截止G0 = 0;
    std::uint64_t 任务建立事实代次G1 = 0;
    friend bool operator==(const 任务初次筹办工作包&,
        const 任务初次筹办工作包&) = default;
};

struct 需求初次筹办准备结果 final {
    需求初次筹办准备状态 状态 = 需求初次筹办准备状态::入口拒绝;
    std::optional<需求当前满足裁决快照> 需求裁决;
    std::optional<L2任务事实> 已有当前任务;
    std::optional<任务初次筹办工作包> 工作包;
    bool 成功() const noexcept;
};
```

`需求初次筹办准备结果::成功()`固定只在状态为`已形成/精确重复`、`需求裁决`与`工作包`同时存在且`已有当前任务`为空时返回真。`任务初次筹办工作包`严格只承载新任务及其身份来源、来源需求、当前成员、完整列表项、轮次 1、G0、G1 和运行代次；完整未满足裁决只留在本次 provider 结果中，不复制进工作包。

请求身份只用于本次正式需求裁决的调用关联，不进入任务建立写集或工作包。运行代次由合法后继治理调用方提供，只作为工作包的运行期协调材料原样回显；本 provider 只验证非零，不把它写成 DATA 事实，也不声称仅凭该数值证明当前运行期。任务建立幂等键的 DATA 同义边界固定为现有`L2新增任务请求`完整写集，即同一列表项；调用方不得把同一幂等键复用于另一个列表项。运行代次或请求身份变化本身不构成 L1/L2 幂等冲突，后继在消费工作包时仍须独立验证运行代次当前性。

完整性守卫固定为：

- 请求身份、运行代次、需求身份、任务建立幂等身份非零；
- 请求头合同版本正确，`期望事实代次 != 0`；
- provider 以`{运行期只读查询合同版本, 请求身份, 需求, G0}`调用正式需求裁决；
- 只有裁决状态严格为`未满足`且`成功()`为真时继续，裁决事实截止必须等于 G0；
- 需求、当前成员、完整列表项端点互相一致，三份生命周期在 G0 当前；
- 裁决具名关系的位不命中允许关系位；provider 不重新比较裸值；
- G1 必须大于 G0，工作包任务生命周期创建代次等于 G1，任务列表项等于裁决列表项，筹办轮次严格为 1；
- `已形成/精确重复`只能携带需求裁决与完整工作包且不携带`已有当前任务`；`已有当前任务`携带未满足裁决和当前任务但不携带工作包；`目标已满足`只携带已满足裁决；其它状态零业务载荷。

### 5.3 L2 新增任务合同收紧

不新增第二个任务写入口。收紧现有：

```cpp
L2新增任务结果 L2任务结构服务::新增任务(
    L2新增任务请求 请求) noexcept;
```

固定改动：

1. `L2新增任务结果::成功()`同时接受`已提交`和`精确重复`，并继续要求非零变更代次、完整任务和身份来源；
2. `读回新增任务(...)`增加一个`L2结构状态 写入状态`参数，只允许`已提交/精确重复`并原样回显；首次提交要求五项新事实在 G1 当前，精确重复按原 G1 验证五项事实均在 G1 已建立，允许它们后来同代退出，并按首次 G1 形状重构原任务与身份来源，不把后来的退出改写成首次结果；
3. `新增任务`取得 owner 锁并完成写入代次预检后：
   - 当前代次等于期望 G0 时，在同一锁内调用现有当前任务投影；
   - 0 个当前任务才允许继续；
   - 1 个当前任务返回`引用冲突`且零写；
   - 多个当前任务或投影矛盾返回`内部不一致`且零写；
4. 预检返回“代次漂移但允许直接提交”时，只允许原写集进入 L1 幂等收敛，不用旧 G0 的当前投影猜测当前性：
   - 原键同义只能得到原任务的`精确重复`；
   - 原键异义为`幂等冲突`；
   - 新键或无原发布见证保持`事实代次漂移`，不得写第二个任务；
5. 成功 / 精确重复均按原任务创建代次读回，不分配新身份；精确重复只证明原任务建立写集相同，不证明该任务在调用时仍当前，provider 必须再做当前读回。

此收紧属于 DATA-L2 结构基数保护：只保证列表项到当前任务的 0/1 结构，不判断需求是否应创建任务。是否创建由新 provider 的未满足裁决前置决定。

### 5.4 工程登记与生命周期

新模块在工程和 filters 中各登记一次。provider 借用调用方拥有的查询组合器和任务服务引用，不取得所有权；调用方必须保证二者生命周期覆盖 provider。专项用真实 L2 服务构造查询组合器与 provider。最终生产实例由后继治理编排拥有，本叶不提前增加普通应用 getter 或伪造生产消费者。

## 6. 固定算法、事务和结果映射

### 6.1 入口与 G0

provider 先执行请求纯值守卫，再以请求身份、需求身份和 G0 调用`查询组合器_.裁决需求当前满足(...)`。状态映射固定为：

| 需求裁决状态 | provider 结果与载荷 |
| --- | --- |
| `已满足` | `目标已满足`，携带裁决，零任务写入 |
| `未满足` | 携带裁决继续唯一任务发布 |
| `证据不足` | `证据不足`，零载荷、零写 |
| `当前性漂移` | `当前性漂移`，零载荷、零写 |
| `引用冲突` | `引用冲突`，零载荷、零写 |
| `不可比较` | `不可比较`，零载荷、零写 |
| `入口拒绝/许可拒绝/资源失败/内部错误` | 同名 provider 分账，零载荷、零写 |

未满足裁决取得后，任何 G0 不一致、需求—成员—列表项端点不一致或允许位反证未满足，返回`引用冲突/内部错误`和零写。调用方不能用自行构造的裁决值绕过正式读取、许可或比较。provider 正文以`try`覆盖服务调用和组包；`std::bad_alloc/std::length_error`映射`资源失败`，其它未预期异常映射`内部错误`，均不得异常穿透`noexcept`。

### 6.2 唯一任务发布

provider 形成唯一 L2 请求：

```cpp
L2新增任务请求{
    请求.请求头,
    请求.任务建立幂等身份,
    未满足裁决.所属列表项.身份
}
```

只调用一次`L2任务结构服务::新增任务`。状态映射：

| L2 状态 | provider 结果 |
| --- | --- |
| `已提交` | 继续 G1 读回，最终`已形成` |
| `精确重复` | 继续原 G1 读回，最终`精确重复` |
| `事实代次漂移` | `当前性漂移` |
| `幂等冲突` | `引用冲突` |
| `引用冲突`且返回截止严格等于 G0 | provider 以 G0 调公开`按需求列表项读取当前任务`；结果为`已读取`、截止仍为 G0、恰一任务且列表项一致时返回`已有当前任务`，携带未满足裁决和该任务，不形成工作包 |
| `引用冲突`后公开读回为 0 项 | `引用冲突` |
| `引用冲突`后公开读回漂移 / 资源 / 内部不一致 | 分别映射`当前性漂移/资源失败/内部错误` |
| `引用冲突`返回非零截止但不等于 G0 / 零截止 | 分别映射`当前性漂移/内部错误`，不得用新截止继续读 |
| `入口拒绝/许可拒绝` | 同名 provider 状态 |
| `资源失败/数量预算不足` | `资源失败` |
| 其它、复义或坏读回 | `内部错误` |

`已有当前任务`不是 L2 非成功结果新增业务载荷，也不是失败后自动改走重筹办；它只能由 provider 在 L2 返回`引用冲突`后使用公开读取、按同 G0 精确确认。它把当前任务交还上层，后继必须重新选择“已有任务的新轮次 provider”。本函数不调用旧结果重筹办路径。

### 6.3 G1 权威读回与组包

成功或精确重复后：

1. 取新增结果事实截止为 G1；
2. 要求写入状态与 provider 最终成功状态一致，任务与身份来源完整，任务创建代次等于 G1，列表项等于裁决列表项；
3. 以 G1 调用`按需求列表项读取当前任务`；
4. 要求读取截止等于 G1、唯一当前任务存在且身份等于新增结果；
5. 构造轮次为 1 的工作包；
6. 仅投影新任务及身份来源、来源需求、当前成员、完整列表项、轮次 1、G0、G1 和运行代次，调用工作包完整性守卫；失败返回`内部错误`且不撤销任务。

G1 只可能是从 G0 发布本次任务写集得到的直接后继代次。若中间出现其它发布，L2 写入口返回漂移，本 provider 不取得新截止重试。下游普通筹办入口必须在消费工作包时以 G1 重新裁决目标当前事实；provider 形成工作包前取得的 G0 未满足裁决只证明任务建立前置，不冻结后续世界事实。

### 6.4 并发、重复和发布未知

- 同键同列表项：L1 原幂等见证返回原任务；只有当前截止仍等于原 G1 且该任务仍是列表项唯一当前任务时，provider 才按本次非零运行代次形成工作包，否则返回当前性 / 引用分流并要求上层重新裁决；
- 同键换列表项：`幂等冲突`，不得覆盖首次任务；请求身份和运行代次不属于 DATA 写集同义字段，不得伪造其变化会由 L1/L2 判为冲突；
- 两个不同键同 G0 并发：至多一个在 G0→G1 发布；另一请求只能看到漂移或已有当前任务，不得形成第二任务；
- 已有当前任务的新键：owner 锁内唯一性守卫拒绝，provider 返回`已有当前任务`；
- 发布结果未知：调用方只能使用原请求和原任务建立幂等身份重试；不得换键；
- 原任务已经退出或列表项当前任务已经改变时，旧请求不得恢复旧任务或返回旧工作包，必须返回当前性 / 引用分支并由上层重新裁决。

### 6.5 失败与撤销

```text
第一笔任务写入前失败 -> 零事实写入
任务 G1 已发布后失败 -> 不撤销、不退出任务、不删除关系
读回不一致 -> 内部错误，停止依赖路径
工作包未被下游接收 -> 任务仍是当前事实，原键重试或上层重新裁决
```

本 provider 没有业务撤销入口。任务退出属于后继具名生命周期合同，不能作为本函数异常回滚。

## 7. 下游接口与生命周期

`任务初次筹办工作包`是紧邻后继“普通新筹办入口”的冻结输入合同。后继必须：

1. 以 G1 重读任务、来源需求、当前成员、完整列表项和当前目标；
2. 重新调用需求目标比较，保留普通新筹办的`目标已满足`短路；
3. 确认列表项当前任务仍等于工作包任务；
4. 只以筹办轮次 1 形成方法查找、选择、条件提议和后继冻结；
5. 不把本工作包转换为现有`下一筹办工作包`，也不补造其旧字段。

本轮不修改`任务特征方法查找与条件提议提供者`。它当前专门消费任务实际结果后的工作包，合同保持不变。后继如复用其内部方法查找算法，必须新增普通入口或抽取共享只读核心，不能伪造旧实际结果材料。

## 10. 创建侧自审与完成边界

创建侧从入口、唯一性、幂等、发布、读回、工作包、下游和历史生命周期逐项复核：

- 没有把业务未满足判断放入 DATA-L2；
- 没有让 BIZ provider 直达 L1 或任务 owner 私有端口；
- 没有让并发请求产生两个当前任务；
- 没有把旧结果重筹办 DTO 改造成通用 DTO；
- 没有把发布后失败设计为撤销；
- 没有把普通新筹办的目标重判从下游删除；
- 没有进入子需求回流消费者或成员结算；
- 没有把请求身份、完整未满足裁决、旧路径 / 实例 / 执行轮次 / 结果塞入初次工作包；
- 没有承诺现有 DATA 写集无法判定的“运行代次变化即幂等冲突”。

代码完成只证明：一份同 G0 的未满足需求在没有当前任务时，可以通过唯一业务 provider 建立一个当前任务，并形成轮次 1 的初次筹办工作包。

代码完成不证明：工作包已被普通筹办入口消费、方法已查找、路径 / 实例 / 冻结已形成、任务已执行、子需求回流已消费、已有任务已新重筹办、需求已满足、成员已结算、结果共用 / 争用已裁决或 HY-Ego 最小生命闭环已完成。
