## 1. 本版唯一修订

v0.1 第 4.2 节同时规定：同 `输入FT + 用途`、同定义收敛为`精确重复`；建立成功又必须满足`首次发布H > 请求G`且正式回执与请求匹配。若某绑定已经由旧幂等身份在旧 G 建立，调用方在当前 G 以新幂等身份提交相同定义，旧首发 H 已经不大于新请求 G，绑定事实也不保存新请求的幂等身份，因此不能把旧绑定及旧首发回执证明为本次请求的精确重放。

本版只分开“原始幂等请求重放”和“跨幂等身份的语义重复”。除本文件明确替换的 v0.1 第 4.2 节建立结果字段、建立成功谓词和建立分流外，v0.1、v0.2、v0.3 全部设计继续有效；冲突处以本版为准。不得借此修改当前读取、预算、初始化、准确 F、provider、K、上下文、方向应用、迁移删除集、RC、持久实例、算法或工程范围。

本文件明确废止并完整替换 v0.1 第 4.2 节“同键同定义（包括逐项输出 FT 身份）收敛为精确重复，同键异定义为注册不唯一/幂等冲突”一句。其中旧“同键”指 `输入FT + 用途` 语义路由键；从 v0.4 起，语义路由相同不再足以成立`精确重复`，只有下节所述同 L1 幂等身份的原请求重放才成立。

## 2. `精确重复`的唯一含义

建立操作中的`精确重复`只表示同一个原始幂等请求的原样重放，必须同时成立：

1. 本次请求的幂等身份与 L1 首次写入材料中的幂等身份相同；
2. 本次请求 G 与首次规范化写集的期望事实代次相同；
3. 本次请求定义与由首次材料恢复的原定义逐字段相同；
4. 由本次请求规范化形成的完整写集与 L1 保存的首次规范化写集完全相同；
5. L1 首次写入结果完整，且其 owner、幂等身份、事实代次、发布标志和新编码映射均能证明原首次发布；
6. 原绑定在本次读回截止仍为完整活动事实。

`精确重复`不是按定义内容做语义去重，也不能借用另一个幂等身份的首次写入结果。调用者必须为不确定发布重放原请求；更换幂等身份、G、定义或规范化写集都不再属于重放。

同一幂等身份已经存在首次材料时，分流固定为：

| 首次材料与本次请求 | 返回 | 发布 |
| --- | --- | --- |
| G、定义、规范化写集全部相同，原绑定仍活动 | `精确重复` | 不形成新发布；回显原首次发布材料 |
| G、定义或规范化写集任一不同 | `幂等冲突` | 确认零发布 |
| 原请求相同，但原绑定后来已经退出 | `目标已退出` | 确认零发布，不复活绑定 |
| 首次材料不完整、无法互证或读回未知 | 沿既有`历史材料不可用/内部不一致/已可能发布`边界 | 不伪造成功 |

本调用第一次成功形成原绑定时返回`已创建`；提交竞争或派发未知最终从同一幂等身份、同一 G、同一写集的首次材料收敛时返回`精确重复`。两种成功都使用原首次材料作为规范回执，而不是使用一次后继语义查询拼装成功。

## 3. 跨幂等身份的唯一键冲突

当本次幂等身份尚无首次材料时，建立必须在发布前按请求 G 读取 `输入FT + 用途` 的当前唯一路由并完整比较定义：

| 当前路由 | 返回 | 发布 |
| --- | --- | --- |
| 不存在 | 继续按本次原请求构造、保存并提交规范化写集 | 只有 L1 成功后才成立 |
| 已有活动绑定且定义逐字段相同 | `幂等冲突` | 确认零发布，不建立本次幂等账 |
| 已有活动绑定且定义不同 | `注册不唯一` | 确认零发布，不建立本次幂等账 |
| 多个活动绑定、格式坏、历史不可用、预算不足或 G 漂移 | 沿 v0.3 当前读取及既有映射失败 | 零发布 |

这里的`幂等冲突`表示调用方以另一幂等身份重复提交已经存在的同一绑定；`注册不唯一`表示另一份定义将违反 `输入FT + 用途` 唯一路由。两者都不是成功，不返回事实、首次发布 H 或正式回执，也不能创建“已存在”新状态、隐藏幂等账或别名关系。

已经退出的旧绑定不属于当前路由；本版不新增历史语义去重，也不改变既有当前唯一性、引用保护或退出合同。

跨幂等身份分流只检查`请求 G`下活动的 `输入FT + 用途` 当前绑定。首次材料未找到后必须再次确认 L1 当前事实代次仍等于请求 G，才能开始该扫描；扫描结束到提交前继续使用既有 G 守卫。请求 G 下没有活动绑定时，历史上已退出的同路由绑定不阻止新幂等请求建立新绑定。若请求 G 下已经出现多个活动同路由绑定，返回`注册不唯一`并确认零发布，不尝试比较或选取其中一个。

## 4. 建立结果自包含合同

`特征I64比较绑定结果`在 v0.3 完整结构上增加：

```cpp
std::optional<特征I64比较绑定建立请求> 建立原请求;
```

字段规则固定：

- 只有`操作=建立`允许`建立原请求`存在，且函数入口一开始即完整回显本次建立请求；身份读取、当前读取和退出必须为空。
- 建立的`成功()`只使用结果自身字段，不读取函数参数、线程局部状态或绑定事实中不存在的幂等身份。
- 非成功建立仍保留`建立原请求`用于诊断；成功事实载荷规则不因此放宽。
- 当前读取仍只允许`当前读取原请求`及 v0.3 四项用量；两个原请求字段不得在同一结果中同时存在。

建立返回字段来源固定如下：

| 字段 | `已创建` | `精确重复` |
| --- | --- | --- |
| `建立原请求` | 本次入口请求；已经用本次规范化写集互证 | 本次入口请求；已经与首次材料恢复的原请求逐字段互证 |
| `首次发布H` / `H` | 本次 L1 首次成功回执的事实代次，两者相等 | L1 首次写入材料中原成功回执的事实代次，两者相等 |
| `Gread` | 发布后用于最终活动读回和代次守卫的当前 G | 本轮用于最终活动读回和代次守卫的当前 G |
| `发布确定性` | `确认已发布` | `确认已发布`，表示原首次发布已确定，不表示本轮形成新发布 |
| `事实` | 在 Gread 读回的活动绑定，创建 G 等于首次发布 H | 在 Gread 读回的同一活动绑定，创建 G 等于原首次发布 H |
| `正式回执` | 本次 L1 首次成功回执 | 首次材料中的原 L1 成功回执；不使用本轮重放返回的精确重复回执代替 |

重启后没有内存 pending 时，以本次幂等身份读取 L1 首次材料：从首次规范化写集的期望事实代次恢复原 G，从写入幂等身份恢复原键，从节点/关系/属性规范化内容及新编码映射恢复并解码原定义，再与本次入口请求及按该请求重建的规范化写集逐项相等；首次写入结果提供原首次发布 H 和原正式回执。任一字段不能唯一恢复、解码或互证时不得返回`精确重复`。内存 pending 存在时也必须与同一首次材料互证，不能把内存内容作为更高权威。

建立的完整成功谓词替换为：

1. 版本正确，`操作=建立`，`建立原请求`存在且其版本、G、幂等身份和定义有效；`当前读取原请求`为空且当前读取四项用量全零；
2. 状态只允许`已创建`或`精确重复`，`事实`、`首次发布H`和`正式回执`均存在；
3. `0 < 建立原请求.G < 首次发布H == H <= Gread`；
4. 事实为首次发布 H 创建的完整活动绑定：`事实.创建G == 首次发布H`且无退出 G，事实定义逐字段等于建立原请求定义；
5. 正式回执合同版本、owner、写入幂等身份和事实代次分别正确，其中`正式回执.写入幂等身份 == 建立原请求.幂等身份`、`正式回执.事实代次 == 首次发布H`；
6. `已创建`要求原首次回执状态为 L1 `成功`并确认形成内存权威发布；`精确重复`要求结果已通过 L1 首次写入材料恢复同一原请求和原首次规范化写集，规范回显仍为原首次写入结果，不把本轮零发布冒充首次发布；
7. 本地键映射必须与正式回执及绑定事实完整一致；规范化原写集可由`建立原请求`中的 G、幂等身份和定义，加已初始化的四个绑定结构身份及固定本地键规则唯一重建，并与首次材料相等，再以首次结果映射核对返回事实。

建立失败一律不得满足`成功()`。`幂等冲突`、`注册不唯一`和`目标已退出`必须为确认零发布，清空事实、首次发布 H 和正式回执；派发后无法证明发布与否才保留既有`已可能发布/可能已发布`，并只允许原幂等请求原样恢复。

## 5. 建立执行顺序

建立入口固定按下列顺序执行：

```text
立即回显建立原请求并校验请求形状
-> 读取该幂等身份的 L1 首次写入材料
   -> 已存在：按第2节互证原请求、原写集和原首发结果
   -> 未找到：再次确认当前G=请求G，再按请求 G 读取活动的当前 输入FT+用途 唯一路由
      -> 无当前绑定：构造并保存原规范化写集，再提交 L1
      -> 同定义：幂等冲突，零发布
      -> 异定义：注册不唯一，零发布
-> 对已提交或发布未知分支，只以原幂等身份、原 G、原定义、原写集收敛
-> 从原首次材料恢复事实和规范回执
-> 返回前校验 Gread、事实活动性、映射及完整成功谓词
```

建立不得先使用当前语义绑定代替幂等首次材料，因为当前绑定不能证明原请求身份；也不得先写入新幂等账再发现唯一键冲突。当前路由预检与最终 L1 提交之间发生竞争时，只有同一原幂等请求可以收敛为`精确重复`。若 L1 提交因事实代次漂移等确定未发布结果表明另一幂等身份可能先行发布，本请求恰一次取得最新非零 `Gcurrent`，以 `Gread=H=Gcurrent`扫描该时点活动的当前路由并做尾 G 守卫：同定义返回`幂等冲突`，异定义或多绑定返回`注册不唯一`；0 匹配保留原提交失败映射。重扫期间再次漂移固定返回`事实代次漂移`，不得改用旧请求 G、不得循环或重新提交，也不能借竞争者回执返回成功。
