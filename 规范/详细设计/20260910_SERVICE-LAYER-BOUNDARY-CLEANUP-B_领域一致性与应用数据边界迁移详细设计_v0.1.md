## 1. 目标与完成边界

本设计把三个只读业务应用对核心 `L1事实基座服务` 的直接依赖迁回已有领域服务边界，并同时闭合：

1. 特征、需求、任务服务分别提供一个“指定期望 G 的当前事实代次核验”公开入口；
2. 已经持有实际 L1 引用的服务通过窄谓词证明依赖是否属于同一个实际底座，不返回 L1 地址、引用、token、锁或端口；
3. 存在、任务数据服务的内部依赖在构造期全部完成同底座核验；
4. 三个业务应用删除 L1 成员、构造参数、直接调用和 `绑定于(L1)`，改由领域合同完成首尾 G 守卫与构造绑定；
5. 需求方向结果只使用二次计算模块已经公开的强类型 variant 验证来源可达性，不跨模块调用 `二次计算内部::键/输出键`。

本设计不改变二次计算算法、G/H 映射、预算、结果 DTO、状态枚举数值、owner、事实字段、事务、持久化、工程模块或生产装配。计划完成只证明七个模块的边界迁移和指定验证，不证明生产可达、运行正确、恢复、集成验收或业务闭环。

## 4. 服务专属期望 G 合同

### 4.1 精确 DTO 与签名

三个结果均按“状态、合同版本、期望事实代次、实际事实代次”顺序声明，不增加请求 DTO，不建立公共结果头：

```cpp
inline constexpr std::uint32_t 特征当前事实代次核验合同版本 = 1;
struct 特征当前事实代次核验结果 final {
    特征类标量状态 状态 = 特征类标量状态::入口拒绝;
    std::uint32_t 合同版本 = 特征当前事实代次核验合同版本;
    std::uint64_t 期望事实代次 = 0;
    std::uint64_t 实际事实代次 = 0;
    bool 成功() const noexcept;
};

inline constexpr std::uint32_t 需求当前事实代次核验合同版本 = 1;
struct 需求当前事实代次核验结果 final {
    需求类数据状态 状态 = 需求类数据状态::入口拒绝;
    std::uint32_t 合同版本 = 需求当前事实代次核验合同版本;
    std::uint64_t 期望事实代次 = 0;
    std::uint64_t 实际事实代次 = 0;
    bool 成功() const noexcept;
};

inline constexpr std::uint32_t 任务当前事实代次核验合同版本 = 1;
struct 任务当前事实代次核验结果 final {
    任务类数据状态 状态 = 任务类数据状态::入口拒绝;
    std::uint32_t 合同版本 = 任务当前事实代次核验合同版本;
    std::uint64_t 期望事实代次 = 0;
    std::uint64_t 实际事实代次 = 0;
    bool 成功() const noexcept;
};
```

分别在对应数据服务 `public` 区声明：

```cpp
特征当前事实代次核验结果 核验当前事实代次(std::uint64_t 期望事实代次) const noexcept;
需求当前事实代次核验结果 核验当前事实代次(std::uint64_t 期望事实代次) const noexcept;
任务当前事实代次核验结果 核验当前事实代次(std::uint64_t 期望事实代次) const noexcept;
```

各结果的 `成功()` 恰为：合同版本等于本结果专属常量、状态为本服务既有`已读取`、期望 G 非零、实际 G 等于期望 G。状态枚举不增项、不改号；结果不是事实、节点字段、第二代次权威或 L1 回执。

### 4.2 核验流程和错误映射

每个入口只调用一次本服务保存的 L1 引用之 `读取中性当前事实代次({L1中性CRUD合同版本})`，并按下表返回；不得调用其它领域服务、连续读“最新”或自动换 G：

| 条件 | 返回状态 | 实际 G |
| --- | --- | --- |
| 输入期望 G 为 0 | 对应 `入口拒绝` | 0 |
| L1 状态成功、合同正确、实际 G 非零且等于期望 G | 对应 `已读取` | L1 回显 G |
| L1 状态成功、合同正确、实际 G 非零但不等于期望 G | 对应 `事实代次漂移` | L1 回显 G |
| L1 状态为资源失败 | 对应 `资源失败` | L1 回显 G，允许为 0 |
| L1 其它状态、合同不匹配、成功却回显 0 | 对应 `内部不一致` | L1 回显 G |
| `bad_alloc` / `length_error` | 对应 `资源失败` | 已取得则保留，否则 0 |
| 其它异常 | 对应 `内部不一致` | 已取得则保留，否则 0 |

`noexcept` 边界不得抛出。业务应用只把核验结果映射到既有业务状态；不把实际 G 写回原请求或改用实际 G 继续计算。

- `存在类数据服务` 原构造拒绝条件增加 `!特征服务_.绑定于(第一层服务_)`。
- `任务类数据服务` 原构造拒绝条件增加需求、存在、方法、特征四个服务中任一 `!绑定于(第一层服务_)`。
- 需求类已有两个依赖核验、特征类已有值服务核验，保持不变。
- 拒绝仍使用原构造的 `std::invalid_argument` 配置错误表达，不新增运行期状态或半构造对象。

### 9.1 B03 资源失败注入合同

资源失败不新增测试入口，也不修改 L1。仓库外运行探针必须使用独立临时 `L1事实基座仓库/服务`：先形成非零 G；一个工作线程反复提交合法、彼此独立且足够大的 L1 写请求，使仓库真实写路径取得独占锁，另一工作线程在同一启动栅栏后反复调用三个领域服务的 `核验当前事实代次(G)`。`L1事实基座仓库::尝试读取当前事实代次()` 使用 `shared_lock(..., try_to_lock)`，与独占写锁竞争时会返回 L1 `资源失败`；三个入口必须各自至少实际观察一次本服务 `资源失败`、不抛出、回显合同版本和输入期望 G，且失败结果不满足成功谓词。

探针以“在冻结的迭代上限和总时限内，三个入口全部实际命中”为通过条件；任何入口未命中即 B03 失败，不能记为 `NOT_RUN`、跳过或用源码存在 catch 替代。探针只能写自己的临时底座；对每次已观察到的资源失败调用，记录调用前后 G。并发写线程可能推进临时底座 G，因此 B12 的零写证明另在无并发写线程的正常、0 输入、漂移和内部不一致调用上，以 G 和 owner 范围事实数量前后相等证明；不得把并发线程的合法写入归给核验入口。

“L1 其它非成功”使用一个尚未形成事实的新临时 L1，使其当前代次读取返回非成功且非资源失败的 L1 状态，从而验证领域入口映射为 `内部不一致`；不篡改冻结 L1 合同常量。探针实现若无法构造合法写请求、无法在上限内令三个入口实际命中资源失败，或需要修改 L1/生产 ABI，B03 不通过且本计划不得完成。
