# 需求归属与服务承接闭环详细设计

日期：2026-10-20  
版本：v0.1  
状态：待审设计，未实施；不是可执行计划。  
代码核对基线：`codex/startup-governance-order`，`2215724094a78cc422b0d3b9dc669497eb90a973`。  
本轮范围：仅新增本详细设计，不修改正式规范、生产代码或共享计划索引。

## 1. 目标与核心边界

服务对象的需求和自我的服务需求使用统一的需求信息，但不能混为一条需求。自我理解对方想要什么，不等于对方已请求自我帮助；自我承接服务后，服务目的必须持续指向对方原需求，不能在执行过程中退化为一个失去服务来源的技术目标。

本设计区分三个对象：

| 对象 | 需求主体 | 目标 | 所在组织 |
| --- | --- | --- | --- |
| 对方需求 D | 服务对象 | 具体状态，例如某杯水温度为40℃ | 对方的需求关联集合，不进入自我执行树 |
| 自我服务需求 S | 自我 | 对方需求 D 在承接范围内得到满足 | 自我服务根下的服务需求 |
| 实现子需求 C | 自我 | 达成 D 所需的具体状态 | S 的分解子链 |

`S→D`是服务目标引用；`S→C`是目标分解父子关系。D 不是 S 的父需求，也不是贡献接收任务。需求主体、目标存在和认知者分别表达，不能相互推定。

“周春海希望这杯水达到40℃”是一条需求；“自我执行加热使其需求得到满足”中的动作与效果关联属于后续事实及因果组织，不能塞进需求目标正文替代正式关系。

## 2. 已明确口径与待审技术选择

### 2.1 本窗口已明确的口径

- 对方需求也是需求信息；自我保存的是自己理解或推测的对方需求。
- 每个存在可以关联其需求信息；没有记录不代表该存在没有需求。
- 知道需求但没有求助时，不主动满足，最多询问是否需要帮助。
- 认可需求内容不等于请求帮助；明确求助也不等于自我已承接。
- 自我服务的初心是对方原需求得到满足，具体动作和中间目标不能取代这一目的。
- 父子任务只向直接父任务结算；包装层不得制造额外服务贡献。

### 2.2 本设计建议采用、实施前需审定的选择

1. 在统一需求结构中明确需求主体和执行归属域，外部 D 不自动生成任务。
2. 增加“需求满足目标”分支，正式引用 D；不将 D 编码冒充存在编码，也不为此给每条需求建立虚拟存在。
3. 求助、理解确认与承接保存独立依据，允许同一明确表达同时提供多项依据，但分别校验其含义。
4. 需求满足由需求 owner 依据事实和证据计算，不以直接修改活动状态作为满足事实。

上述选择构成整体方案，不表示已有接口支持，也不授权按本文件直接改变公开合同。

## 3. 当前实现及必须修订的限制

| 当前实现事实 | 本方案影响 |
| --- | --- |
| `新需求信息`有父需求、目标存在、目标定义、来源、确认组等，无独立需求主体和原需求引用 | 扩展归属和目标结构，保持既有字段语义 |
| 普通需求创建校验目标必须是存在节点 | “需求满足目标”须分支校验，禁止把 D 填入目标 E |
| `复核当前满足()`主要按目标 E/F 当前值比较，方向目标需要变化证据 | 增加需求引用分支，保留方向证据要求 |
| `修改活动状态()`写入的是治理字段，不是正式事实特征 | 不可通过写“已满足”完成服务 |
| `查询目标存在需求(E)`表示以 E 为目标，不表示需求属于 E | 新增归属查询，不复用旧查询含义 |
| 自我扫描读取需求全集，任务与列表校验依赖双根可达 | 必须区分自我执行域和对方需求记录域 |
| 旧服务理解路径部分位置要求目标存在等于来源人类 | 解除混同，允许“某人希望某杯水改变” |
| 旧服务确认保存固定目标语义，但未独立表达求助与承接 | 保留固定含义能力，补齐独立门槛 |
| 新有序参数目前提供 E/F；旧获取服务需求仍用理解等材料 | 正式需求参数需要新的类型提供者，不能只增加枚举值 |

代码定位以基线为准：`新_需求类.cpp`的普通需求创建、服务要求采用、查询目标存在需求、复核当前满足、修改活动状态；`新_任务类.cpp`的服务贡献来源识别、服务任务集合查询、任务完成复核；`新_自我工作线程类.cpp`的需求全集扫描；`服务要求.结构化.cpp`的理解及确认入口。

现行《3100_根规范_需求》“所有需求天然为自我、无所属存在”与本窗口新口径冲突，列入后续正式规范修订。每需求唯一任务的要求应限定为自我执行域，不能扩展到所有被认知的需求记录。

## 4. 数据组织与所有权

### 4.1 统一需求记录

建议扩展逻辑结构，物理字段编号待代码计划冻结：

- 稳定需求编码。
- 需求主体存在引用：谁希望该目标成立。
- 执行归属域：自我执行需求或被认知的对方需求；不靠主体是否等于自我隐式替代全部生命周期规则。
- 目标分支：现有状态目标，或本设计的需求满足目标。
- 认知依据引用：信息来源、理解依据及内容确认依据；不得以无依据的推测冒充对方确认。
- 生命周期、来源及既有治理字段。

需求归属关系由需求 owner 唯一写入。存在侧的需求列表是该关系的查询视图，不再维护一个可独立修改的编码镜像。原“目标存在需求”反向索引保留原义，新增“主体存在需求”索引。

外部输入不完整时不能伪造一个完整可执行 D。可保留既有待理解材料，正式 D 发布必须通过其目标结构的完整性校验；待理解材料不进入正式自我需求扫描。

### 4.2 目标分支

状态目标保留目标 E、FT、值域或变化方向。需求满足目标保存被服务的 D、承接时固定的目标含义依据和完成约定引用。目标分支互斥校验，不能同时填写两套相互矛盾的必需字段。

S 固定服务目的；C 是实现方案。更换方法、增加准备子需求或调整 C，不得悄悄替换 S 引用的 D。D 内容改变后先核对固定承接含义，不能让旧授权自动扩展到新范围。

### 4.3 求助与承接

求助依据至少能够确定请求方、被请求方、所针对 D 及其含义、有效性和来源表达。自我承接依据引用求助事实及本次接受范围。它们不复用当前表示父任务来源的 `来源承接节点`。

表达“是的，我想要40℃的水”只能确认内容；表达“请你帮我把这杯水加热到40℃”可同时支持内容与求助判定。沉默、未拒绝、登录成功、知道对方有需求都不是求助依据。

## 5. 从认知到服务的处理流程

```text
交互信息
  → 理解并形成对方需求 D
  → 有效的明确求助／接受帮助
  → 自我检查能力、安全及限制，决定承接
  → 建立 S，固定服务 D 的目的及范围
  → S 的任务筹办，将具体状态目标组织为 C
  → 通用方法查找、条件分解、执行及观察
  → 需求 owner 重新复核 D
  → 满足服务约定后完成 S，沿原贡献链结算
```

没有求助时停留在认知阶段；允许询问，但询问本身不建立代为满足 D 的执行任务。能力不足时按既有挂起和缺失方法机制处理，不假定自我能满足任何请求。

S 的任务不寻找“把 D 的活动状态改成已满足”的方法。它通过需求目标分解取得 D 的具体状态目标，再由普通筹办寻找能改变对应特征的方法。复合目标仍是各分项都满足的“与”关系；方法条件分解仍是针对已选方法的必要条件，两条路径不混用。

子任务报告完成只触发复核，不直接证明父任务完成。父任务重新读取正式世界信息及本次适用证据；不把旧信息包作为长期事实副本。

## 6. 满足判定与服务目的保持

需求 owner 的复核应返回满足结论、采用的目标含义和证据引用。需区分已满足、未满足、证据不足、目标定义变化、需求撤回；具体返回类型在公开合同冻结时确定。工程读取错误走日志、弹窗及工程中断路径，不作为上述正常业务结论。

值目标按真实当前 E/F 及正式值域运算判断。变化方向目标必须关联合法参照、执行前后值和适用时间范围；不能用任意最后一次变化、方法预测值或瞬时当前值替代。

“D 已满足”并不等于“本任务造成了 D 满足”。前者用于状态目标判断，后者涉及动作来源及贡献结算。目标原本已满足或由外部因素满足时，不得虚构本任务执行或子任务贡献。

若服务约定要求对方验收，还需验收依据；不把所有服务强制改为人工验收。完成历史保留当时满足证据，不能因此宣称目标永久成立。

D 撤回、请求撤回或承接范围变化时，停止继续据旧依据发起动作，保留已发生事实；不能标记为成功结算。已开始动作的处理按其可中止性和安全合同执行，不能承诺撤回能够消除已发生效果。

引用校验独立于父子树校验：拒绝 S 自引、服务引用环及通过派生状态递归证明自身满足。首期 D 采用具体状态目标；若未来允许对方 D 也引用另一需求，应另行冻结递归与终止合同。

## 7. 扫描、去重、任务与结算

### 7.1 扫描与任务边界

自我需求树扫描、列表覆盖、缺任务补齐、双向 D/T 检查、计数及孤立节点检查统一使用自我执行域。外部 D 没有任务是正常情况，不能只在最终创建任务时跳过而保留前面的误报警。

S 和 C 继续保持一个需求最多一个对应任务。外部 D 仅被引用，不进入自我任务集合。服务任务分类沿自我父子链追溯，不能沿 S→D 服务关联追溯。

### 7.2 去重

不得只按目标 E/FT/值域合并不同人的需求。D 的复用至少核对主体、来源请求身份及目标含义；仅内容相似不足以认定同一请求。S 的幂等创建绑定已承接的同一请求及固定含义；重复消息复用 S/T，不再次配任务。

来源无法确定是否同一次请求时，保留待确认，不把重复表达自动升级为新服务，也不擅自删除。C 的复用仍遵守父需求作用域，不能因目标相同就把不同承接的服务责任合并。

### 7.3 贡献结算

最终服务来源识别须同步识别 S，而非继续依赖旧材料形状。S 下各服务子任务的贡献只向直接父任务汇总，S 不因包装原需求而额外获得叶子贡献。外部 D 没有任务，不产生贡献、不接受结算。

状态满足证据、执行贡献和服务值入账分别校验。保留既有分级结算门槛及幂等身份，不能以新 D/S 包装重复结算历史任务。

## 8. 方法参数与本能方法职责

本方案本身不新增一个直接修改“需求已满足”事实的本能方法。服务实施修改现实对象特征；承接、任务调度、任务服务值等属于内部治理；状态、动态与因果由正式事实发布自动形成。

“获取服务需求”后续迁移应消费正式 D 和明确求助依据，而不是继续用自定义理解分项替代需求。函数的直接操作、必要条件及自我后续采用必须分别定义，不能将消息投递直接等同服务任务数量增加。

参数规格仍在 Vm 中固定有序保存“信息类型＝范围概念”；具体参数关系由 C 描述，实际引用由参数场景保存。要支持需求参数，必须提供正式需求概念及其范围匹配、owner 读取、参数场景校验、任务消费者、动作记录和学习归档能力。需求编码不能冒充 E/F，也不能以私有类型键冒充概念。

旧 M 首次生成的规格不得原地改变；采用受控新代际，保留旧执行记录及其规格解释。获取服务对象已迁移的 E/F 路径无需为本方案回退。

## 9. 发布、消息与生命周期

建议由需求 owner 提供归属查询、外部需求发布、服务目标校验、满足复核及幂等承接发布接口；自我线程拥有是否承接的裁决，任务 owner 只对已发布的自我需求创建和调度任务。

同一需求 owner 内，S、服务引用、固定承接依据和幂等键应原子发布，禁止留下有 S 无目标的半结构。跨需求与任务 owner 不假设全局事务：先发布合法 S，再发送其稳定引用；任务端幂等建立 T，并利用现有双向复核补齐遗漏。

消息携带正式引用和必要的幂等身份，不以临时信息包作为事实唯一来源。投递失败或返回未知时先查询已发布结果，不能盲目重复创建。处理消息前重新读取求助与承接有效性；旧消息不能恢复已撤回的服务。

外部 D 被 S 引用后不能直接物理删除。失效、撤回和历史保留分别表达；物理删除须经过现行引用保护，不在本设计中授权迁移删除。

## 10. 历史数据迁移

1. 可确认是原自我执行树的需求，保留 D/T/X 编码及父子、完成和结算历史，补齐自我主体信息。
2. 旧外部服务记录须从有效来源材料恢复对方主体，不能由目标存在推定主体。
3. 旧内容确认不自动迁移为帮助请求或自我承接。授权依据不明时禁止新增执行，保留现场并报告，等待裁决。
4. 旧需求同时承担具体目标和服务承接角色时，需逐条确认转换映射；不得无条件复制出新 S/T 再执行或结算一次。
5. 原固定语义快照及来源表达保留。可追溯记录迁移后读回归属、引用、目标和历史身份；无法还原的停止该条迁移，不猜测、不删除。
6. 新旧读取边界须显式区分，不能用“主体为空就当自我”长期吞掉新数据缺字段错误。

## 11. 实施顺序与涉及模块

| 阶段 | 内容 | 主要范围及出口 |
| --- | --- | --- |
| 一 | 审定本方案，修订需求归属、目标分支、任务及结算规范 | 需求、任务、服务、参数相关规范；冻结完整公开合同 |
| 二 | 需求 owner、归属索引、目标联合结构与迁移 | `新_需求类.h/.cpp`及正式数据提供者；外部 D 可存取且不会被配任务 |
| 三 | 同步全集扫描、列表、任务唯一性和服务贡献分类 | 自我工作线程、任务类与管理线程；不存在半迁移扫描 |
| 四 | 求助、承接、S→D 关联及真实满足复核 | 自我线程、服务要求入口、需求及任务消费者；从原需求到执行目的可追溯 |
| 五 | 正式需求参数提供者与获取服务需求迁移 | 方法、参数场景、动作及学习消费者；保留旧 M/X |
| 六 | 获明确测试指令后，实际项目全流程验证 | 以真实入口验证，不建立临时项目 |

第二至四阶段涉及同一公开合同、扫描与生产消费者，必须整体冻结设计后施工，不能为了并行拆成可单独发布的半结构。旧索引、接口或数据的删除须另列准确清单，不能附带清理未知材料。

## 12. 验证矩阵与完成条件

以下是后续获测试指令时的范围，不是本轮运行授权。

| 验证项 | 预期结果 |
| --- | --- |
| 对方为主体、水杯为目标 | 归属与目标查询分别正确，不要求两者相同 |
| 已知需求但无求助 | 不建 S/T，不主动改变目标 |
| 只确认内容，或沉默 | 不推定求助及承接 |
| 明确求助并获承接 | 一条 S、一项对应任务，固定引用原 D |
| 重复交付相同承接消息 | 复用原 S/T，不重复计数或结算 |
| 两个主体具有相同目标 | 不被完整目标键错误合并 |
| 外部 D 没有任务 | 扫描正常，不报孤立执行需求或补建任务 |
| 修改 D 活动标签但事实未满足 | S 不完成 |
| 子任务完成但目标事实已变化 | 父任务重新复核，不盲目完成 |
| 方向目标缺合法参照 | 不以瞬时值或任意历史变化判满足 |
| 原需求变更或求助撤回 | 旧授权不扩大，旧消息不重启执行 |
| S 包装及多级子任务贡献 | 逐级汇总，不额外奖励包装层或重复入账 |
| 旧记录无法还原主体或授权 | 保留并报告，不猜测、不自动执行 |
| 工程读取异常 | 走工程错误链，不当作“不需要帮助”或“已满足” |

业务完成条件：真实信息形成 D，经明确求助和承接建立 S，筹办和执行完成其具体状态目标，依据真实事实复核 D，并按既有贡献链完成一次结算；任一步都能追溯原需求和承接含义。
