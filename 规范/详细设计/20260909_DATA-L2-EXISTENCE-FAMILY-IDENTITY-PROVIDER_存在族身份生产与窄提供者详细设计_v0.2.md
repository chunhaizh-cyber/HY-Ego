## 1. 修订定位

本版完整继承同名v0.1详细设计中存在族生产、窄协议v2、存在类重构、事务、错误、退出恢复、旧逻辑删除集和验证边界；只修订新窄合同对 `L1事实基座服务` 的模块依赖形态。凡本版未明确替换的v0.1条款继续有效，本版与v0.1冲突时以本版为准。

执行基线 `db3cbe9b200f25b3f6df292fcd1d3093fcb8b312` 的具名DRIFT为 `EXISTENCE-NARROW-CONTRACT-L1-SERVICE-TYPE-OWNERSHIP`。

## 2. 现场事实

1. `L1事实基座服务` 的唯一正式定义位于模块 `海中鱼巣.核心.服务.L1事实基座`，不是 `海中鱼巣.核心.合同.L1事实基座` 的导出类型。
2. 新窄合同公开ABI包含 `绑定于(const L1事实基座服务&)`，因此该类型身份必须来自其唯一定义模块。
3. 只导入 `海中鱼巣.核心.合同.L1事实基座` 时，合同单元内无法解析该类，现场得到C4430。
4. 在新named module内写 `class L1事实基座服务;` 会把声明附着到新合同模块，形成与L1服务模块导出类不同的类型；存在类override/链接现场已得到LNK2019，签名显示两种模块归属不同。
5. `数据服务.特征值类.ixx` 已采用 `export import 海中鱼巣.核心.服务.L1事实基座` 并直接使用该服务及其公开类型，证明该依赖方向在现有工程中成立。L1服务模块不依赖领域模块，因此不会形成环。

## 3. 精确裁决

v0.1第3节生产文件1的依赖说明替换为：

```cpp
export module 海中鱼巣.领域.合同.存在结构身份只读;

export import 海中鱼巣.核心.服务.L1事实基座;
```

新窄合同必须：

- 使用且仅使用L1服务模块所导出的 `海中鱼巣::L1事实基座服务` 类型；
- 删除模块内 `class L1事实基座服务;` 前置声明；
- 不再单独import或export-import `海中鱼巣.核心.合同.L1事实基座`；
- 不复制、别名化、包装或重新声明L1服务类型；
- 不修改 `绑定于(const L1事实基座服务&)` 的4203公开ABI；
- 继续零依赖状态、场景、动态、概念或应用层。

裁决采用 `export import` 而非普通 `import`。该服务类型直接出现在导出的纯虚函数签名中，重导出保证仅导入窄合同的派生实现和消费者都能解析同一个类型实体，不增加隐式“调用方必须另行导入L1服务模块”的前置条件。由此可见性扩大仅限已有公开签名不可避免的L1类型依赖，不授予窄provider调用L1或改变L1事实的能力。

## 4. 依赖图与工程顺序

修订后的唯一依赖为：

```text
核心.服务.L1事实基座
        ↓ export import
合同.存在结构身份只读
        ├─→ 数据服务.存在类
        └─→ 合同.场景状态使用绑定 → 数据服务.场景类
```

工程顺序固定为L1服务模块先于新窄合同，新窄合同先于绑定合同和存在类。不得为解决模块类型身份而修改L1、移动 `L1事实基座服务` 定义、增加头文件声明、建立第三个类型模块或在4203合同中恢复旧存在接口定义。

## 5. 验证增量

在v0.1第10节矩阵之外增加：

1. 新窄合同源码精确一处 `export import 海中鱼巣.核心.服务.L1事实基座`，零 `class L1事实基座服务;`，零直接 `核心.合同.L1事实基座` import。
2. Debug/Release均形成L1服务、新窄合同、绑定合同和存在类的IFC/OBJ；不得出现C4430、LNK2019或不同named-module类型签名。
3. 最小消费者只import新窄合同，即可声明接收 `const L1事实基座服务&` 的派生provider并与存在类override形成同一函数类型；无需额外import L1服务模块。
4. 静态检查依赖图无领域到L1之外的新边，且L1源码零修改。

上述验证只证明类型身份、模块可见性和原计划目标实现，不证明场景C、绑定B、动态或业务闭环完成。
