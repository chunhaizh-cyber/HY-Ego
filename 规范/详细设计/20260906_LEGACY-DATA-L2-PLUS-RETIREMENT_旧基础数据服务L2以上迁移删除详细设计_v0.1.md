## 1. 目标与不变量

本设计把旧基础数据服务 L2 以上实现及全部直接、间接代码消费者一次性退出。实际 L1 基座、新数据服务链和新应用服务链继续保留。该迁移是代码物理删除，不产生新 DTO、公开函数、owner、业务事实、兼容层或替代入口。

必须同时满足：

1. 23 个 `服务.L2*.ixx` 旧服务种子、22 个 `L2*.数据.h` 旧结构种子、其反向引用闭包及 12 个旧链专属伴随文件全部删除；
2. 任何仅因 import/include 旧闭包而存在的上层代码一起退出，不能以“只引用 DTO”或“仍可参考”为由保留；
3. 6 个实际 L1 模块、5 个 L1 数据头、12 个 `数据服务.*类` 和 5 个新 `应用服务.*类` 组成的 28 路径工作树保护闭包不得物理删除；其中 `应用服务.特征概念类.ixx` 只允许旧 HEAD source blob 从 index 退出，外部重写版工作树内容必须逐字保留；
4. 当前不依赖旧闭包的主入口、启动壳、数据库、持久事实、稳定编码及全部 Markdown 规范、知识、流程、计划、记录和历史证据保留；
5. 删除后不恢复旧入口，不用新 DTO、适配器、空壳、假实现或迁移服务延长旧 ABI 生命周期；
6. 代码阶段按用户要求不执行编译、运行、测试、扫描或验收，因此完成声明只能是“候选删除源码已发布，未编译、未运行、未验收”。

## 2. 当前事实与闭包裁决

### 2.1 删除闭包

以基线提交中的 23 个 `服务.L2*.ixx` 为 import 种子，以 22 个 `L2*.数据.h` 为 include 种子：

```text
旧服务种子 23
-> 反向 import 闭包 64（62 ixx + 2 cpp）

旧 L2 数据头种子 22
-> 反向 include 闭包 70

两闭包并集 103（64 ixx + 37 h + 2 cpp）
-> 补入 12 个旧链专属/已孤立伴随文件（1 ixx + 8 h + 3 inl）
-> 2 个验证 vcxproj + 2 个验证 ps1 级联退出
-> 物理删除 119
-> 另将旧 HEAD `应用服务.特征概念类.ixx` source blob 从 index 退出，工作树重写版原样保留
-> staged 删除路径 120
```

`合同.L2结构公共.ixx`、`服务.不可变材料.ixx` 和 `不可变材料.数据.h` 落在反向 include 闭包内，保护链不依赖它们，因此本次整体退出。它们的通用名称不构成越过用户“旧 L2 以上及引用代码”范围的保留理由。

精确文件、基线 blob 与入选原因唯一冻结在：

`计划/20260906_LEGACY-DATA-L2-PLUS-RETIREMENT_旧基础数据服务L2以上精确删除清单_v0.1.md`

12 个伴随文件分别承载旧 L2 身份、请求、事实、运行期消费、自我线程生产及旧世界/本体初始化；它们虽未全部落入机械反向闭包，仍是用户所称旧 L2 以上专属实现，不是通用日志或 L1 依赖。

执行者不得按文件名再次自由扩张或缩减清单。若 S0 的已发布基线变化导致旧 source blob 或闭包变化，必须停止并退回计划支撑重新发布清单。

## 3. 物理变更模型

删除清单中的 119 个文件全部从工作树物理退出，其中 113 个是旧生产实现或引用代码，6 个是已无源文件意义的专属验证源/工程/脚本。另有旧 HEAD `应用服务.特征概念类.ixx` 只从 index 退出，工作树同路径外部重写版保留。文件内全部旧函数、DTO 和模块出口随旧 source blob 退出；无需为每个函数制造重复迁移条目，清单的文件路径与 source blob 是函数知识追溯边界。

## 4. 一次性提交与恢复

119 个物理删除、一个旧版本 index 删除、两个工程 XML 修改和施工记录构成一个迁移单元。工作树施工中允许短暂不完整，但不得把任一部分单独提交或推送。禁止通过恢复旧模块、空壳或补偿复制模拟回滚。

失败恢复只使用 Git 中已发布基线和清单 blob：

- 提交前中断：保留已登记 WIP，重新核对后继续；禁止 reset、clean、stash；
- 暂存不完整：从 index 清单识别遗漏，不发布；
- 普通提交失败：保留 index 和工作树，取得发布租约后重试；
- 推送结果未知：先读取本地/远端提交关系再决定，不重复制造提交；
- 发布后如用户决定恢复：另建有正式授权的新迁移，通过普通 Git 提交恢复，不在本计划中自动回退。

现存数据库、事实文件和稳定编码不运行清理。旧持久材料可能继续留在磁盘，但本计划不再提供旧 L2 reader/writer，也不将其解释为新链事实。

## 5. S0 可执行门禁

执行者开工前必须证明：

1. 计划索引登记本计划精确 blob 为 `可执行`，详细设计与清单 blob 匹配；
2. HEAD 是基线加本设计、计划、清单及其索引登记的文档发布后继；120 个旧 source blob 仍与清单一致；其它生产代码后继必须停止并重新冻结清单；
3. 119 个物理删除目标与 1 个旧版本 index 删除目标的 source blob 与清单一致；
4. 28 个保护路径的工作树 blob 与清单附录一致，或外部所有者已发布并由计划支撑重新裁决；
5. 工程/filters 工作树分别仍是交接 blob，六个新链 XML 项完整；
6. 外部六源码、两记录和验证资源仍由原所有者安全暂停；本计划取得工程两文件以及旧 HEAD 特征概念 blob 的 index 删除权，但不取得特征概念工作树重写版写权；
7. index 为空，Git 发布租约未被他人持有；施工期间发布前仍需重新申请；
8. 新增 import/include 消费者、清单路径消失、保护集相交或工程 WIP 漂移均视为设计漂移，停止并退回计划支撑，不能临场扩大删除范围。

## 6. 完成判定

代码发布前只做非验收的边界核对：

- staged name-status 精确包含 120 个删除、2 个工程修改、1 个施工记录；其中 119 个路径物理消失，特征概念旧版本只在 index 删除；
- cached 工程 XML 只比 HEAD 少 114 项且没有外部新增项；工作树工程 XML 少 113 项并继续保留六个交接的新链项；
- 除旧 HEAD 特征概念 blob 以 `D` 退出外，28 个保护源不得以 `A`/`M` 或其它 `D` 进入 index；外部两记录及其它文件不得进入 index；
- cached diff 经人工逐项审读，提交前后 HEAD/远端关系和普通推送结果明确。

这些核对只证明发布范围正确，不替代编译、测试、扫描或集成验收。本设计不授权代码阶段执行构建、运行、专项、静态扫描、代码差异检查、`check_specs.py` 或生成验证记录。
