# RUNTIME-GOVERNANCE-SERVICE-REQUEST-INITIAL-PLANNING-WORK-PACKAGE 真实服务请求材料到服务根初次筹办工作包详细设计 v0.3

日期：2026-09-02

身份：`RUNTIME-GOVERNANCE-SERVICE-REQUEST-INITIAL-PLANNING-WORK-PACKAGE`

状态：执行侧具名设计漂移修订；配套 v0.3 计划登记后取代 v0.2 施工合同。

## 1. 修订裁决

v0.2 关于筹办结束和结果消息的裁决保持不变：任务工作线程每消费一个完整筹办工作包，只调用一次筹办 provider，随后形成五类之一的唯一强类型结果消息并交给任务管理线程；任务管理线程不得同步直调 provider，也不得用返回值、线程槽、日志或调用次数判断筹办结束。

执行侧在 `main@ecb998342dffeec24dc8e4db4c004111ffac602e` 重新 S0 时发现 v0.2 的后继来源合同不可实现：

1. v0.2 要求 `L2任务筹办规范化来源材料`能够统一返回任务轮次，且 P01 工作包消息的任务轮次必须等于来源材料任务轮次；
2. 当前 `L2任务重筹办规范化来源材料`和原始`下一筹办工作包`均没有`L2任务轮次身份`；
3. v0.2 同时要求后继来源只从原工作包纯值映射、helper 不读仓，因此没有合法来源可以补出任务轮次；
4. 当前 manager 虽已在形成后继工作包消息前调用`按任务读取当前任务与轮次`，但只把读回轮次放入消息外层，provider、正式选择来源和执行冻结来源都无法证明它们与该消息属于同一任务轮次。

本修订采用唯一最小修复：给两个 DATA-L2 规范化来源分支都显式保存`L2任务轮次身份`；后继规范化由`下一筹办工作包 + task owner 同 G 正式任务/轮次读回`共同形成。原始`下一筹办工作包`不加字段，不修改它的生产者和持久材料，不恢复服务合同、请求/结果账、第二端口、第二线程、Gseed、游标或替代账。

## 2. 业务闭环与结束定义

```text
初次或后继筹办工作包
-> manager 形成含完整规范化来源的 P01 工作包消息
-> 任务工作线程消费一个工作包
-> 恰好调用一次统一筹办 provider
-> provider 返回五类之一的闭合结果
-> 工作线程形成一个强类型筹办结果消息
-> 向任务管理线程提交同一结果消息
-> 已接收或精确重复确认
-> 本次筹办处理结束
-> manager 独立读回正式事实
-> 进入执行、合法等待或分支收束
```

“provider 已返回”不等于“本次筹办处理结束”。结果队列容量不足时只重投同一结果消息，不重新调用 provider；协议拒绝、同键异义、端口停止或内部状态冲突属于结果交接失败，本次处理不得伪装成已正常结束，也不得补造第二结果消息。

唯一结果消息必须属于以下五类之一：

1. `可执行冻结`；
2. `子目标承接`；
3. `合法等待`；
4. `目标已完成`；
5. `结构化非成功`。

当前性漂移、引用冲突、入口拒绝、资源失败和内部错误按 provider 合同进入`结构化非成功`，不能静默退出。消息只作跨线程定位；正式选择、冻结、路径、实例、子目标记录和任务状态仍由各自 owner 正式读回或提交。

## 3. 正式依据与当前事实

- 4260 §30：manager 只派发不可变筹办工作包；任务工作线程每次处理结束形成一个强类型结果消息；消息至少绑定任务、任务轮次、筹办轮次、来源工作包和 G0/G1。
- 8100 §5—§6：工作线程发送结果消息，未取得唯一筹办权也必须形成结构化拒绝；筹办只有五类闭合结果。
- 5230 v2.0：初次筹办和同一任务轮次内的后继筹办都必须绑定实际任务轮次，执行冻结不得脱离本轮来源。
- 当前 DATA-L2 `L2任务重筹办规范化来源材料`缺任务轮次；公共 helper 只能取得任务和筹办轮次。
- 当前 manager 已在后继工作包形成阶段以`迁移后事实代次`调用`L2任务结构服务::按任务读取当前任务与轮次`，并校验任务、当前任务轮次与本次正式读回截止。
- 当前工作线程已经执行“一次 provider 调用 -> 一个结果消息 -> 队列满重投同一消息”；本计划只把初次来源接入并保证两个来源分支都可证明任务轮次，不建立另一套结果通道。

## 4. 统一规范化来源合同

### 4.1 DATA-L2 字段

当前规范化来源的`L2任务方法选择合同版本`固定由 1 升为 2。当前 v2 正式选择完整请求序列格式固定为 3；该格式尚未在正式代码发布，因此直接把任务轮次和初次本轮来源成员关系纳入格式 3，不再机械制造格式 4。正式 HEAD 既有格式 2 只保留在 legacy 读/审计路径，不取得当前生产资格，也不能进入当前 provider。两个当前分支固定为：

```cpp
struct L2任务初次筹办规范化来源材料 final {
    std::uint32_t 合同版本;
    L2任务初次筹办准备记录身份 首次准备记录;
    L2任务身份 任务;
    L2任务轮次身份 任务轮次;
    L2需求身份 来源需求;
    L2需求列表成员关系事实 本轮来源成员关系;
    L2需求列表项身份 需求列表项;
    std::uint64_t 首次目标比较共同事实截止G0;
    std::uint64_t 任务建立事实代次G1;
    std::uint64_t 筹办轮次;
    std::uint64_t 运行代次;
};

struct L2任务重筹办规范化来源材料 final {
    std::uint32_t 合同版本;
    L2任务重筹办意图幂等身份 原重筹办意图幂等身份;
    L2任务身份 任务;
    L2任务轮次身份 任务轮次;
    // 其余旧路径、旧实例、旧执行轮次、旧实际结果、正式裁决、
    // 正式待重筹办状态、G、筹办轮次和运行代次字段保持 v0.2 语义。
};
```

公共纯值 helper 至少固定：

```cpp
L2任务身份 L2取得任务筹办任务(const L2任务筹办规范化来源材料&) noexcept;
L2任务轮次身份 L2取得任务筹办任务轮次(
    const L2任务筹办规范化来源材料&) noexcept;
std::uint64_t L2取得任务筹办轮次(
    const L2任务筹办规范化来源材料&) noexcept;
```

完整性、逐项相等、正式选择完整请求编码/解码、发布前互证、精确重复比较、读回互证和执行冻结完整性都必须包含任务轮次。禁止从筹办轮次、执行轮次、列表顺序、任务序号、槽、消息身份或裸整数推断任务轮次。

### 4.2 初次来源

原始`任务初次筹办工作包`按 v0.2 补齐首次准备记录、任务轮次和本轮来源成员关系。纯值规范化直接复制这些 task owner 正式读回字段：

```text
规范化来源(任务初次筹办工作包)
-> L2任务初次筹办规范化来源材料
```

不得从服务请求 E/M/D、需求列表项或消息身份补任务轮次。

### 4.3 后继来源

原始`下一筹办工作包`保持不变。manager 在形成后继 P01 请求前使用现有公开入口取得第二输入：

```text
L2任务结构服务::按任务读取当前任务与轮次(
    {期望事实代次 = 下一筹办工作包.迁移后事实代次,
     任务 = 下一筹办工作包.任务})
```

只有下列公式全部成立才可形成后继规范化来源和 P01 工作包消息：

```text
G
= 下一筹办工作包.迁移后事实代次
= 推进请求.请求头.期望事实代次
= task owner.本次正式读回截止

读回任务.身份 = 下一筹办工作包.任务
读回当前任务轮次.任务 = 下一筹办工作包.任务
规范化来源.任务 = 读回任务.身份
规范化来源.任务轮次 = 读回当前任务轮次.身份
P01消息.任务 = 规范化来源.任务
P01消息.任务轮次 = 规范化来源.任务轮次
```

manager 的局部纯值形成 helper 以`下一筹办工作包、读回任务、读回当前任务轮次、本次正式读回截止`为显式输入；helper 不读仓、不访问线程槽、不产生事实。任何错任务、缺轮次、轮次不属于任务或截止不等均使工作包形成阶段结构化失败并零新选择，不得降级到消息外层轮次。此时尚未派发完整工作包，不算一次已经开始后结束的筹办处理，也不得伪造筹办结果消息。

## 5. 统一 provider、P01 与正式选择

`任务筹办推进请求`只保存一个`L2任务筹办规范化来源材料 来源材料`，不再保存只适用于后继的原始工作包。初次和后继都进入同一`推进筹办工作包`入口；方法查找、当前就绪、等待合同、正式选择发布和执行冻结请求沿用同一个来源联合。

P01 完整性固定：

```text
消息任务 = L2取得任务筹办任务(来源材料)
消息任务轮次 = L2取得任务筹办任务轮次(来源材料)
消息筹办轮次 = L2取得任务筹办轮次(来源材料)
消息来源事实截止 = 请求头期望事实代次
消息工作包身份非零且与管理槽幂等身份一致
```

task owner 发布正式选择时必须在请求 G 独立读回任务和当前任务轮次，并逐项比较`来源材料.任务`和`来源材料.任务轮次`。当前 v2 正式选择完整请求序列格式 3 显式编码两个分支的任务轮次；legacy 格式 2 沿旧只读解码/审计路径保留，缺任务轮次时不得补造、不得进入 current 生产、不得与格式 3 同键精确重复。

`需求初次筹办准备合同版本`保持 2，不因本次来源修订再升版。历史版本 1，或版本 2 记录缺服务请求 E/M/D 扩展、首次准备记录、R1/P1 或本轮来源成员关系时，继续返回具名`初次请求版本待迁移`并零写；不得从当前任务、列表成员、消息或线程槽回填历史工作包。

管理端收到`可执行冻结`结果后，仍须以结果 G1 独立读回正式选择、冻结材料、路径和实例，并核对其任务轮次等于消息及来源联合中的任务轮次，之后才形成执行冻结请求。其它四类结果也必须先消费结果消息，再按各自正式事实进入等待或收束；消息本身不写任务完成、任务失败或需求满足。

## 6. 失败、重试与幂等

- 工作包队列满：重投同一工作包消息，不重建任务、首次记录或规范化来源。
- provider 返回不完整：工作线程形成同一工作包身份下的`结构化非成功/内部错误`消息。
- 结果队列满：保留并重投同一结果消息，不再次调用 provider。
- manager 已接收相同消息：返回精确重复并继续同一独立读回链。
- 同消息身份异义：幂等冲突，禁止第二结果和业务写入。
- task owner G/任务/任务轮次读回不一致：结构化当前性漂移或引用冲突，零新选择。
- legacy 正式选择格式 2 缺任务轮次：只走旧读/审计路径，不从当前关系或消息补齐，不进入 current 生产。
- 管理端停止、协议拒绝或内部状态冲突：属于交接失败，本次处理不得标成正常结束。

## 8. 验证与声明边界

服从用户“先完成整条链路，再做统一业务/集成验证”的口径。本叶最低施工门禁保持：Debug/Release 构建、纯值/编译期谓词、`git diff --check`和 strict 规范检查；不要求提前运行完整五分支业务矩阵。

最小静态/纯值覆盖必须包含：

1. 初次和后继来源都缺任务轮次即拒绝；
2. 后继任务读回、轮次所属任务或 G 任一不等即拒绝；
3. P01 工作包与结果消息任务轮次必须等于来源联合任务轮次；
4. provider 每个已消费工作包只调用一次，结果队列满只重投同一消息；
5. manager 只有在结果消息已接收/精确重复并独立读回后才进入执行、等待或收束；
6. 正式选择发布、读回和执行冻结拒绝错任务轮次；
7. 旧编码格式不能被补造为新格式精确重复。

可声明：初次和同任务轮次后继来源均以 task owner 正式轮次事实进入同一筹办 provider、唯一结果消息、管理端独立读回与执行冻结请求链，且没有新增第二账、第二端口或第二线程。

不可声明：运行期五分支、队列压力、跨进程恢复、现实动作、需求满足/结算或整条本能路线已经验收。
