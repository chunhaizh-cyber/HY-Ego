# WORLD-TREE-P1A2G 验证补充详细设计 v0.1

日期：2026-08-03

设计身份：WORLD-TREE-P1A2G

来源问题：`VALIDATION-TOOLING-P1A2G-CLANG-PCM-TRANSITIVE-FRIEND`

## 1. 裁决与替代范围

P1A2G 主详细设计 v0.1 的函数、DTO、许可、读取、排序、错误和自检合同保持不变。
本文件只替代主详细设计 v0.1 §8 中“Debug/Release、完整自检和 AST 调用边”里的
Clang AST 必过解释，并替代 P1A2G 计划 v0.1 的对应验证命令与完成门禁。

裁决如下：

1. P1A2G 使用 MSVC C++ 命名模块构建；Debug/Release x64 的正式编译链接结果是本计划编译接入门禁。
2. `扫描.MSVC模块依赖.ps1` 使用实际 MSVC `/scanDependencies`，其全部工程模块成功、无循环、无仓内缺失提供者是模块闭包门禁。
3. `扫描.Clang模块候选流程图.ps1` 是开发期候选证据工具，不是正式编译器或机器事实提供者。
4. Clang 与 MSVC 对跨命名模块前置声明、定义归属及 friend 私有访问存在已登记兼容差异；
   目标依赖闭包在既有模块 PCM 阶段失败、目标模块未开始解析时，不得把失败归因 P1A2G。
5. P1A2G 的调用边和不变量改由“目标函数源码闭包核对 + MSVC 编译/依赖扫描 + 具名运行自检”组合证明。
6. 不建立 Clang 工具修复提供者前置。工具修复属于独立工程目标，只有用户另行授权时才进入计划；
   它不是 P1A2G 业务中性投影成立的必要依赖。

## 2. 当前工具事实

现行 `tools/clang_ast/README.md` 已冻结：

```text
Clang 与 MSVC 对跨命名模块声明归属的兼容性并不完全一致；
失败或部分成功 JSON 只作候选证据；
不得把 Clang 模块兼容性失败直接裁决为正式接口漂移。
```

现行 `扫描.Clang模块候选流程图.ps1` 的必选入口参数是 `-模块依赖路径`，
不接受 P1A2G v0.1 写入的 `-项目文件`。因此 v0.1 的命令本身不可机械执行。

执行侧已经证明：修正调用方法并补齐传递 PCM 后，失败仍发生于既有
`海中鱼巣.核心.执行器.节点直接身份结构写入` / 会话跨模块前置声明与 friend 私有访问，
尚未到达目标 `海中鱼巣.核心.服务.节点直接结构`。该证据分类为
`TOOLING-NOT-APPLICABLE / TRANSITIVE-PCM-INCOMPATIBLE`，不是目标源码失败。

## 3. 必过验证矩阵

| 验证层 | 必过证据 | 失败归属 |
| --- | --- | --- |
| 规范与范围 | `check_specs.py --strict`、diff check、精确三代码文件/两记录白名单 | P1A2G 范围或文档错误 |
| Debug 编译接入 | x64 Debug Rebuild 0 error | P1A2G 或正式基线编译失败 |
| Release 编译接入 | x64 Release Rebuild 0 error | 同上 |
| 运行行为 | Debug `--self-test-exit` 成功，既有总数与 P1-A13 全部通过 | P1A2G 实现/自检失败 |
| 模块闭包 | MSVC `/scanDependencies` 全部项目 `.ixx` 成功、模块数等于源数、循环0、仓内缺失提供者0 | 工程/模块依赖失败 |
| 根函数入口 | 目标服务函数完整签名唯一，`noexcept`，专项通过合法服务入口调用 | 接口或入口失败 |
| 许可与只读边 | 根函数体内 `事务域_.取得读取许可()` 恰一次；零写入/提交/撤销/发布调用 | 事务或副作用偏差 |
| 依赖方向 | 根函数只读事务域、节点仓、关系仓和类型化值仓；SQL、材料、索引仓、类型合同仓零调用 | 越层依赖偏差 |
| 身份和失败 | 关系/值分组键不含版本；全部非成功结果零部分业务载荷 | 身份或错误合同偏差 |

Debug 自检继续覆盖主详细设计 §8 的完整矩阵，包括正常、空、漂移、许可、资源失败、
内部不一致、稳定排序、去重、目标零值、异常输入和前后六仓/代次不变。

## 4. 目标函数源码闭包核对

验证记录必须固定以下证据，不得只写“人工看过”或全文件搜索结果：

1. 目标文件 blob 和函数完整签名；
2. 从 `读取两级关系与目标当前类型化值(` 定义起点到该函数匹配右花括号的精确行区间；
3. 该区间的源码摘要或完整补丁片段；
4. 区间内 `事务域_.取得读取许可(` 命中数恰为1；
5. 区间内写入类词项与函数调用清单，确认创建、提交、撤销、确认、完成发布、推进代次命中0；
6. 区间内直接访问的成员清单，确认只含 `事务域_、节点_、关系_、类型化值_`，
   `索引_、类型合同_` 命中0；SQL、持久材料和旧特征栈命中0；
7. 关系稳定主键和值记录稳定身份分别是去重唯一键，版本只参与排序/冲突比较；
8. 每个非成功构造点的状态、代次和五个业务载荷字段，确认无部分载荷。

核对必须限定目标函数行区间。其它既有服务函数或宏内适配中的相同词项不得污染结果。
源码闭包核对与运行自检互补：源码证明调用边和不可由合法仓构造的防御分支，
自检证明合法可构造路径及结构化结果。

## 5. Clang 候选工具的可选分流

执行者可以按 README 的正确两步方式额外运行 Clang 候选工具：先生成 MSVC 模块依赖 JSON，
再以 `-模块依赖路径` 和目标模块调用 Clang 脚本。其结果只按下表分流：

| 结果 | 处理 |
| --- | --- |
| 目标模块成功产生 AST 候选 | 作为附加证据，与源码闭包核对交叉检查 |
| 既有依赖 PCM 失败、目标为依赖 PCM 不可用 | 记录工具状态和首个失败模块；不阻断 P1A2G |
| PowerShell 参数、stderr 或工具自身异常 | 记录工具缺陷；不冒充目标代码失败 |
| 已成功建立全部依赖 PCM，目标模块本身报告源代码错误 | 阻断；执行侧在三文件范围内修复，越界则重新退回 |
| AST 候选与 MSVC/源码事实冲突 | 不自动裁决；固定两边证据并退回计划支撑 |

不得为追求 Clang 成功修改执行器、会话、friend、模块所有权或工具脚本，也不得降低 MSVC、运行自检或源码闭包门禁。

## 6. 完成与声明边界

本补充只修正 P1A2G 验证证据的合法来源和失败分类，不改变任何机器语义、公开接口或代码白名单。
通过本矩阵最多证明 P1A2G L1 同许可业务中性投影源码候选满足本计划的编译、运行和源码闭包门禁；
不证明 Clang 全项目模块兼容，不证明 FEATURE-Q、世界树服务或生产接线完成。
