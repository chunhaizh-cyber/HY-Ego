依据：0050、2220、4240 v0.19。起点 `3072a2c408923bb12bc1da7ce2f90226e070cbc6`。现特征 / 存在应用及概念数据提供者含未发布大计划 WIP；本目标只接管三个应用的根绑定增量，不能借机发布或验收旧算法。已有动态设计与静态大计划中的应用构造 / 根引用条款仅在本设计明确范围内被替代，其余业务逻辑不变。

## 1. 结果与公开接口

三个现存应用分别在类的 private 区声明进程内静态根身份变量：`特征概念应用服务::特征概念根节点`、`存在概念树应用服务::存在概念根节点`、`动态概念树应用服务::动态概念根节点`，类型均为 `inline static 概念树概念身份`、零初始化。它们是程序级共享引用，不创建持久根、owner、类型或规则。

构造签名精确改为：

```cpp
特征概念应用服务(概念树类数据服务&, 特征类数据服务&, 存在类数据服务&);
存在概念树应用服务(概念树类数据服务&, const 特征类数据服务&, const 存在类数据服务&);
动态概念树应用服务(概念树类数据服务&, const 场景类数据服务&,
                   const 存在类数据服务&, const 动态类数据服务&);
```

特征原签名不变，存在 / 动态删除外部根参数和旧重载。各类 private 增加 `绑定全局根()` 和 `释放全局根() noexcept`，析构只调用后者。三个类显式禁止默认构造、复制 / 移动构造及复制 / 移动赋值；各增加 `~类名() noexcept`。各实例保存 `const 概念树概念身份 root_`，只能由对应数据 getter 初始化；特征内部原先直接调用 `concepts_.特征根引用()` 形成或核验父根的业务位置改用该实例 `root_`，不改变其它请求、业务算法或结果 DTO。存在 / 动态原 `root_` 改 const。

各类 public 增加且只增加对应只读函数：

```cpp
static std::optional<概念树概念身份> 读取特征概念根节点();
static std::optional<概念树概念身份> 读取存在概念根节点();
static std::optional<概念树概念身份> 读取动态概念根节点();
```

方法属于对应类，按值返回，不返回引用或 provider 指针。不标 noexcept，以免隐藏 mutex 加锁系统异常。返回有值只证明本类当前存在已完成绑定的应用实例，不证明任意仓库同编码对象，也不是 fresh 当前事实读取。真正操作仍走实例保存的同一数据服务和原共同 G 准入。不存在活动实例时返回 nullopt，不返回零身份的有值 optional。

## 2. 构造验证与全局绑定

每类分别持有 private `inline static std::mutex`、`inline static const 概念树类数据服务*`（仅比较地址）、`inline static std::size_t` 活动实例计数。三者与具名根变量构成一个进程内绑定槽，不导出通用注册器、不新增模块或全局事实服务。每个类独立保护自己的根；组合多个应用仍须按已有 same-provider 合同互证，不能仅把三个全局副本拼成同仓证明。

构造按以下固定次序完成，取得根变量锁前不改变任何全局状态：

1. 分别保留原静态启用 / `使用特征存在服务(f,e)`、动态 `使用动态世界服务(s,e,d)` 检查。失败 `std::invalid_argument`。根来自对应 `c.特征根引用()` / `存在根引用()` / `动态根引用()`，无效身份拒绝。
2. 通过同一 c 取得真实非零当前 G。特征 / 存在沿现 `静态概念应用内部::当前(c)` 及 `定义(c,root_,G,G,b,对应角色)` 取得静态根事实；动态沿 `选择读取G(0)`、`根有效(G,b)`，其内部现 `概念(...)` 使用公开 `读取概念`。固定根读预算只把原六字段 `最大概念数/最大关系数/最大来源数/最大支持数/最大世界成员数/最大特征属性数` 设1，其余保持0。已核根分支只读取固定根节点及唯一角色属性，不扫描普通概念 / 来源，不要求历史展开预算；本轮不修改 data 预算合同。
3. 除现读取成功谓词、Gread=H=G及角色互证外，构造必须核验身份与本体根均为 root_、是本体根、创建代次非零且≤G、退出为空、治理活动，无普通定义 / 定义记录 / 来源 / 直接上位。静态结果使用其已有根字段，动态可在 `根有效` 中补齐同一根完整性。再按各自当前 G helper 检查共同截止未漂移。任何读取 / 预算 / 结构错误沿现结构化失败机制传播，资源异常不吞掉；这些步骤都在全局注册前，因此不会修改绑定槽。
4. 所有 provider 调用结束后才锁本类 mutex。计数0时要求槽为空，写入 c 地址 / root_ 并令计数1；计数>0时要求同一 c 地址与相同 root_，否则 `std::invalid_argument`，旧槽不变；计数达到 size_t 最大值时 `std::length_error`，不得回绕。相同绑定只递增。全局提交是构造最后一步，之后不再安排会抛异常的工作；构造失败无须析构，也不留下幽灵计数。

计数与身份在同一 mutex 临界区修改或读取。禁止持本类锁调用 data / L1 / 其它应用或另一类根 getter，不持 data 锁进入本类临界区，不跨类同时加锁。根绑定不产生 L1 写集、幂等键或事实代次；数据读取后其它无关事实代次推进不把静态副本变成新权威，业务操作仍 fresh 校验。

## 3. 析构、重建与并发边界

析构只在本类 mutex 下确认计数非零、provider地址及根均匹配，递减计数；最后实例将根身份清零、provider地址清空。不得调用 provider，不退出根或数据，不把根清零当事实删除。内部计数 / 身份不一致不能静默清掉另一绑定，按不可恢复内部错误终止；noexcept 析构的锁异常不吞掉再继续使用错误槽。

借用服务寿命仍由调用方保证：所有应用先析构，provider 后析构。槽中地址仅比较不解引用，最后实例清空后不残留悬空可用 provider。实例不允许复制 / 移动；并发 getter 与其它实例构造 / 析构受锁保护，但调用方不得让同一实例成员操作与其析构并发。应用对象应由正常受控运行期销毁，不依赖跨模块静态析构次序维持 provider 寿命。

同类还有活跃绑定时，另一 provider 即使给出相同数字根也拒绝；没有活跃实例后，允许新 provider 重新正式校验并绑定。不是永久绑死第一个 c，也不提供强制重置入口。旧 getter 副本可能过期，只能作为人读 / 查询身份材料，不能据此恢复 binding 或推定同库。多进程分别建立自己的进程内槽，重启从未绑定开始，再消费已恢复的正式根。
