## 1. 目标与完成定义

本设计将 C031 收束为前后相接但职责严格分离的完整迁移：

```text
服务请求适配器同 G0 互证 E_source + M + D_service
-> 建立、唤醒或精确复用服务根治理任务 T_root、R_root1、P1 与首个统一筹办工作包
-> T_root 仅多次筹办并形成服务对象、目标、权限/条件等任务材料
-> manager 把材料定位交 self；self fresh 确认独立且必要的子目标
-> task owner 发布正式子目标承接记录
-> 需求 owner 建立或复用普通服务子需求 D_child
-> 普通执行任务 T_exec 承接 D_child
-> T_exec 多次找方法、多次查条件并补全任务信息
-> manager 独立读回，推进到待执行前选择
-> T_exec 的独立选择入口 fresh 复核适用性、可用性、安全硬门和正式成本
-> T_exec 的 task owner 单次发布选择记录、路径、实例方法和执行冻结
```

`T_root` 绝不进入执行前选择，不生成路径、实例、冻结或现实动作；只有 `D_child` 的普通执行任务 `T_exec` 才能沿通用任务链进入选择和执行。服务根任务的“方法”仅是形成、核验和提交治理材料的内部治理方法，不得被解释为现实服务方法。

同次迁移必须物理退役“初次筹办推进 A1 / 筹办调用证明”及其专用治理函数、关系、读写，旧即时初次筹办、自动重筹办 / `下一筹办工作包`、单次纯发现、五类出口、筹办内采用 / 代价比较 / 路径 / 实例 / 冻结、旧 readiness provider，以及子目标回流直接重建初次筹办的全部生产声明、调用、装配、工程登记和测试依赖。执行、结算等仍有合法用途的通用治理函数、治理动作调用结构及其 owner 读写必须保留。

“整体退役”只能在新链替代全部合法消费者、旧生产符号归零、Debug/Release x64 均重建成功后成立；不得先删旧链再留下不可编译基线，也不得用兼容壳换取编译通过。

## 2. 正式口径与当前代码裁决

本设计只落实当前 0050、3200、3300、4260、4270、5090、5210、5230、5240、5250、5300、8100、8200、8300 的已冻结语义，不修改规范：

- 筹办是任务领域内部治理函数，由 manager 根据任务状态派发，不需要初次筹办推进 A1 或筹办调用证明；执行、结算的通用治理动作事实不受影响。
- 筹办需要多次调用；首次和未完成阶段只找方法，方法范围完整且有候选后才查条件。
- 找方法可产生多个候选；查条件必须覆盖每个候选的全部条件组，不能因先发现一组具备而提前结束。
- 筹办只补全任务信息；适用性、实际采用、总代价比较、路径、实例与冻结属于执行前选择。
- 每个工作包只有一条不可变结果消息；manager 必须独立读回 task owner 正式信息后才能迁移状态。
- 方法 / 条件缺失只是任务材料；只有 self fresh 确认后才进入既有任务子目标承接和需求 owner 建需链。
- 轮次收束后的新任务轮次只来自 self 正式后继决议；目标未达成不能自动重筹办。

适配器在同一 G0 独立读回：存在结构服务的现行`读取存在节点`当前分支确认 E，现行`读取存在身份来源`历史分支在 H=G0 读回来源证据；材料服务确认 M 当前可读且`材料.来源节点 == E.值`；D_service 等于已发布服务根锚点。请求不增加任何附加承接记录字段、请求账、registry 或真实性 provider。P04.2 的七族新入口已取消，本计划不恢复、不声明、不调用任何 P04.2 DTO 或入口。

结果分支固定为：

| 状态 | 写入 | 必须携带 |
| --- | --- | --- |
| 已建立 | 允许首次 owner 写 | 同一 `T/R1/P1/来源绑定材料/首个统一筹办工作包/G1` |
| 精确重复 | 零新写 | 与首次完全相同的 `T/R1/P1/来源绑定材料/首个统一筹办工作包/G1` |
| 已有当前任务 | 零写 | 五个 optional 全空；用于同一服务根下已有不同请求的当前任务 |
| 请求 / E / M / D 校验失败、漂移、冲突、资源、内部错误 | 零业务写 | 五个 optional 全空 |
| 发布未知 | 不得换键 | optional 只有在原请求独立读回已确认后才按“已建立/精确重复”收敛，否则全空 |

首个统一工作包由 P1 锚定。精确重复必须返回同一工作包身份、幂等身份、完整字段和步骤，不得重造。已有不同请求的当前任务绝不能被“唤醒”并混入新 E/M，固定返回`已有当前任务`且零写。

## 8. 子目标、回流与重新筹办

- 筹办 provider 与 manager 不得直接建立需求、子任务或任务父子关系。
- self 对方法 / 条件材料 fresh 确认独立、必要、父域合法、严格缩小祖先未闭合范围且目标状态可最终判定后，task owner 才发布 / 重放正式任务子目标承接记录；需求 owner 只消费该记录。
- 需求 owner 建立 / 复用的普通服务子需求随后形成自己的`治理用途=普通执行`任务；它不得复用根治理任务的任务轮次、筹办信息或工作包，也不得把根治理材料当成选择来源。
- 子需求 / 等待条件回流后，manager 读取当前状态和 fresh 事实，决定同一未收束任务轮次内的新筹办轮次与找方法 / 查条件子状态；不得调用旧`需求初次筹办准备`。
- 已执行或已有正式结果时先结算并收束；只有 self 正式`继续`决议可建立新任务轮次，目标未达成、线程回执或消息不能自动重筹办。
