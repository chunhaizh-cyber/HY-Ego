# 当前 WIP 编译恢复详细设计

身份：`CURRENT-WIP-COMPILE-RECOVERY`
版本：v0.3
日期：2026-09-04
状态：待用户 ABI 裁决；不构成代码施工许可。
替代：v0.2 的执行许可已暂停；v0.1 / v0.2 均不得继续用于本计划施工。

## 1. 具名执行漂移

v0.2 已恢复普通应用 module 的可见性，旧 `服务.需求初次筹办准备` 和 E2E canonical
源仍保持删除。随后 `Debug|x64` 的新首错固定为：

```text
海中鱼巣/装配.普通应用.ixx 的 v1 筹办装配合同
    !=
海中鱼巣/领域/内部治理/任务筹办当前就绪与执行冻结.{数据.h,服务.ixx} 的 v2 合同
```

两份根目录未跟踪副本只保留 v1 合同，不能作为 canonical 提供者或恢复来源；恢复它们会
重新引入已停止的旧筹办链，违反本计划原目标。

## 2. 已核对的不兼容事实

1. v1 数据合同含 `任务筹办等待合同登记`、`任务筹办授权安全材料来源`、
   `任务筹办推进请求` 和 `推进下一筹办工作包`；canonical v2 删除这些类型和入口，改为
   `任务筹办当前就绪请求_v2`、`任务筹办当前就绪结果_v2` 及
   `形成当前可执行冻结_v2`。
2. 普通应用的公开 `普通应用配置` 仍以等待合同登记和授权安全来源作为字段，其有效性、
   生产配置形成、上下文构造、成员和装配失败分支均依赖该 v1 语义；它还公开取得同名
   provider 的 getter。
3. v1 provider 构造需要任务子目标承接、方法查找、授权安全来源和等待登记等 11 项依赖；
   v2 provider 只接受任务、需求、方法、状态、特征和场景六项服务。把普通应用的调用改成
   六参可以消除一个 C++ 构造错误，却会无声删除 v1 等待/授权治理材料，不能证明机器语义
   等价。
4. `5260` §2 要求既有公开 ABI 的字段、版本、状态和入口保持；字段删除、改义、版本变化
   或旧入口物理删除必须作为独立 ABI 迁移，经正式设计、同步消费者迁移和验证后登记。

因此，普通应用适配 v2 不是本计划内可唯一裁决的机械编译修复。它至少改变公开配置形状
和 provider 的可调用合同；是否退休 v1 的等待/授权治理语义亦不是编译器可以裁决的问题。

## 3. 最小待裁决问题

是否授权单独形成并实施 `普通应用筹办装配 v1 -> v2 ABI 迁移`：物理删除 v1 的等待合同/
授权安全来源配置与旧推进入口，并以 v2 当前可执行冻结合同重建普通应用装配和全部消费者？

若不授权，必须恢复与 ordinary-application ABI 一致的 v1 provider 合同；两种路径不能在
本计划中混用。用户未裁决前，不得改普通应用、v2 provider、DTO 或正式规范。

## 4. 现有完成边界

已完成的 v0.1/v0.2 范围仅保留为 WIP：工程输入恢复、旧服务 consumer 删除、SELF-FORM
可见性 import 恢复以及 L2 回流函数范围内的编译修补。它们没有证明 Debug/Release 编译
成功，也不证明任务筹办业务、线程、SELF-FORM 或 E2E 能力。
