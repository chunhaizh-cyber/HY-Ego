# 学习改变方法状态详细设计

标识：`METHOD-LEARN-STATE`；版本：v0.3（第4.1节修订稿待用户确认）；日期：2026-11-12；状态：有效（第1—5节用户 2026-11-12 确认；第4.1节为方案A补充）。

来源：ASK-READ-SCENE 诊断运行（获取服务对象模拟学习完成后任务停在“待检查条件”、任务管理线程空闲）；用户 2026-11-12 裁决。

## 1. 用户裁决（2026-11-12）

1. 学习针对的是方法，学习结果改变的应该是方法的状态。
2. 学习改变方法状态，要在内部治理世界形成状态、动态、因果等信息，并且是自动形成的；只需按需要给方法虚拟存在增加相关特征。

## 2. 现状（代码基线：ASK-READ-SCENE 工作树 `3730c748e`）

- 方法虚拟存在只有一个“启用”特征。`完成方法特征变化` 能形成状态和动态，但只用于启用状态的修改，并且不交付因果。
- 运行次数、成功次数、可靠度这几项统计特征不在方法虚拟存在上。
- 学习发布配对时，只把配对写进方法结构，然后另发一条“方法学习结束”消息。任务管理线程收到后，用 `查询受方法学习影响任务` 查出受影响的任务，逐个让它们重新筹办。方法自身不形成状态。
- DEP-READY-WAKE 中，等待方法知识的任务用一个笼统的“方法知识”键，由学习结束消息唤醒。
- 诊断运行 run-2 里，获取服务对象学到配对之后，它的任务一直停着，没有被唤醒。是不是这条“学习结束消息加事后查询”的路径漏了，还没有核实。

## 3. 设计

### 3.1 方法虚拟存在新增的特征

| 特征 | 值 | 什么时候变化 |
| --- | --- | --- |
| 条件结果配对数 | I64，取值不小于 0 | 学习新增、替换、融合或删除配对之后 |
| 已知结果配对数 | I64，取值不小于 0 | 配对中结果非空的那部分数量发生变化之后（例如只有条件的配对补全了结果） |

- 这两个特征由方法 owner 维护，学习不直接写它们。新方法登记时一并建立，初值是当前的实际数量；旧方法在启动时幂等补齐。
- 是否还要增加其它特征，例如“最近学习种类”（模拟发布、尝试补全、融合），按用户“需要时再加”的原则，本次不加；以后有因果或筹办需要时再提出。

### 3.2 学习发布经统一入口改变方法状态

学习发布配对时，方法 owner 按下面的顺序完成一次变化，做法与 TASK-STATE-CAUSAL 的任务状态迁移一致：

```text
发布配对（方法结构）
-> 发布学习记录（动作来源：学习种类、方法、配对、来源执行或样例）
-> 建立治理动作（主体 self；定义按“学习种类 × 改变的特征”登记）
-> 提交方法虚拟存在的特征变化，形成前后状态和原子动态，关联“导致变化”
-> 交付实际发生（内部治理世界按既有前置窗口规则交给因果服务）
```

- 状态、动态、因果都由各自的 owner 按事实自动形成，学习本身只负责发布配对。
- 只有当配对数或已知结果配对数确实变化时才形成状态；值没有变化时，不建立动作，也不交付因果。
- 启用状态的修改也改走这个入口，从而同样交付因果。

### 3.3 等待方法知识的任务由方法状态唤醒

- **有候选方法的等待**（候选还没有配对、等待学习，或者等待配对补全）：以候选方法的虚拟存在节点作为依赖键。方法状态一形成，就按 DEP-READY-WAKE 的节点键唤醒这个任务。
- **没有候选方法的等待**（“尚无方法”）：仍然使用“方法知识”这个笼统键。任何方法虚拟存在的配对数一变化，就唤醒这类等待；以后有了按方法头的精确召回键，再改为精确唤醒。
- 去掉“方法学习结束”消息加 `查询受方法学习影响任务` 这条专门的唤醒路径，统一由方法状态唤醒。学习线程、自我线程之间关于学习复核的消息，按现有分工保留。
