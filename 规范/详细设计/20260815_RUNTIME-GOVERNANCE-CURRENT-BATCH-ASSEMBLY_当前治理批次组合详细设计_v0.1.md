# 当前治理批次组合详细设计 v0.1

日期：2026-08-15

计划身份：`RUNTIME-GOVERNANCE-CURRENT-BATCH-ASSEMBLY`

当前状态：BIZ 详细设计候选；三个直接子 provider 尚未全部形成真实最终结果，本计划只能登记待激活。

## 1. 目标、范围与完成边界

实现 `BIZ-L2-002-01 v0.2`：由唯一 `自我治理批次路由`把邮箱冻结的一个值式消息批次、同一运行配置的完整秒观察/可选区间和单一共享事实截止组合成完整不可变治理批次。

本设计修复 v0.1 的消息守恒缺口：邮箱已经推进批次序号并移出消息后，时间或事实截止失败不能让局部批次随返回销毁。路由必须私有保留同一待完成批次，后继调用优先补齐未完成材料，零再次邮箱读取；只有完整成功候选形成后才无抛出交付并清槽。

本叶只组合非权威消息与只读见证，不读取领域正文、不提交机器事实、不重排消息、不写 DATA、不推进完整秒消费游标、不接入自我线程主循环。普通应用装配、父线程调用、治理批次复核、G0/G1 一致事实、跨进程恢复和优雅停机验收均为 `NOT_RUN`。

## 2. 正式依据与当前事实

- 0050 v1.3：运行期事实权威、DATA 外业务组合和结构化非成功；停机精确实现仍未裁决。
- 4050 v1.4：请求拒绝、资源失败和内部不一致必须分账。
- 8100 v0.6、8200 v0.5：自我线程先冻结本轮治理消息；循环次数、等待超时和消息数量不得成为完整秒或业务变化量。
- `RUNTIME-GOVERNANCE-MAILBOX-BATCH-FREEZE v0.1`：唯一邮箱入口返回前已释放队列锁；成功值式移出完整稳定顺序批次，全部非成功空批次且邮箱零变化。
- `RUNTIME-COMPLETE-SECOND-BOUNDARY-PROVIDER v0.1`：`已读取`携带观察和非空区间；`无新完整秒`携带观察、区间为空；其它状态零载荷。
- `RUNTIME-FACT-CURRENT-CUTOFF-CONSUME v0.1`：只经 BIZ 包装读取同一 L1 的单一非零当前事实截止；资源失败可由父级重试。
- 正式代码目前只有 `有界自我治理邮箱`，没有本路由模块、父 DTO 或父调用点。

### 2.1 v0.1 漂移裁决

| v0.1 问题 | v0.1 风险 | v0.2 裁决 |
| --- | --- | --- |
| 邮箱取出后后继失败直接返回 | 消息销毁、邮箱序号已推进 | 先无抛出接管到路由私有待完成槽，再做后继读取 |
| N04 写“释放队列锁” | 调用方并不拥有邮箱锁 | 删除；邮箱 provider 返回前自行释放 |
| 父函数为 `const` | 实际需要保存待完成批次和最后已完成序号 | 改为非 const `noexcept`成员；对象不可复制、不可移动 |
| 完整秒只分“可用/不可用” | `无新完整秒`被误判失败 | 保存观察和可选区间；无新秒是合法成功 |
| 请求/结果携带停止阶段版本 | 当前无权威读取端口，会形成第二停止事实 | 删除该字段；只消费邮箱的运行中/已停止结果 |
| 重试没有身份 | 可能改绑请求或再次取邮箱 | 新增待重试见证；除等待预算外逐字段匹配原冻结绑定 |
| 路由配置允许非零初始上一序号 | 邮箱只从内部 0 递增且没有恢复/注入来源，首批会被永久判为坏后继 | 删除初始序号配置；每个新路由实例的最后已完成序号固定从 0 开始 |

停止语义固定为：邮箱返回带消息的已冻结批次后，无论邮箱随后是否停止，路由都先完成该待完成批次；待完成槽清空后的下一次调用才可经邮箱得到已停止。不得临场按不存在的停止阶段版本过滤、改绑或丢弃消息。

## 5. 私有待完成槽

私有 `待完成治理批次`固定保存：

```text
原请求冻结绑定（不含最大等待时间）
+ 治理批次待重试见证
+ 邮箱返回的完整自我治理冻结结果（状态、原因和批次）
+ optional<完整秒边界观察>
+ optional<完整秒区间>
+ optional<已发布共享事实截止>
```

路由必须静态证明：完整邮箱结果可无抛出移入待完成槽，父成功结果在候选完整后可无抛出移动返回，消息析构和 optional 清槽不抛出。邮箱一旦返回任何非空/非零批次载荷，父级先无抛出移入待完成槽再验证状态、原因和形状；即使发现 provider 坏形状，也不能让已取出消息随局部结果销毁、重新入队或读取下一批。

每次进入补证状态机前都重新复核保存的完整邮箱结果必须恰为 `已冻结 + 原因无 + 非零序号 + 非空消息组 + 相对冻结绑定严格后继`。由于结果在槽内不可变，复核结果确定；任何状态/原因/载荷坏配对槽只能持续返回内部不一致和同一见证，零时间/截止调用，永远不能在重试中晋升成功。

待完成槽不是机器事实、缓存成功结果或跨进程恢复账；它只是同一运行实例内已经取得但尚未完整交付的非权威消息所有权。对象销毁时仍有待完成槽意味着治理排空没有完成，不能声明优雅停机。

## 6. 固定状态机与映射

入口条件到父结果的唯一映射固定为：

| 条件 | 父状态 / 原因 | 子调用与见证 |
| --- | --- | --- |
| 路由配置的运行代次、时间纪元、时间源版本或事实范围版本为零 | 内部不一致 / 路由配置无效 | 零子调用；锁内有槽则回显原见证 |
| 请求合同错误、必填字段为零、等待为负或上一完整秒边界为负 | 请求拒绝 / 请求字段无效 | 零子调用；锁内有槽则回显原见证 |
| 有效请求的运行代次、纪元、时间源或事实范围与路由配置不等 | 版本漂移 / 固定配置不匹配 | 零子调用；有槽则回显原见证 |
| 无槽且请求上一批次序号不等于路由最后已完成序号 | 版本漂移 / 上一批次序号不匹配 | 零子调用、见证为空 |
| 无槽却携带待重试见证 | 版本漂移 / 无待完成批次却携带见证 | 零子调用、见证为空 |
| 有槽但见证缺失 | 版本漂移 / 待重试见证缺失 | 零子调用、回显原见证 |
| 有槽但见证或除等待预算外的冻结绑定不等 | 版本漂移 / 待重试见证不匹配 | 零子调用、回显原见证 |
| 最后已完成批次序号为 `UINT64_MAX` | 内部不一致 / 批次序号耗尽 | 零邮箱调用；有槽时不适用 |
| 完整结果候选复制抛出 `std::bad_alloc` 或 `std::length_error` | 资源失败 / 结果候选构造资源失败 | 保留原槽并回显原见证 |
| 完整结果候选复制或构造抛出其它异常，或候选逐字段互证失败 | 内部不一致 / 结果候选构造异常 | 保留原槽并回显原见证 |
| 取得路由锁抛出 | 内部不一致 / 内部异常 | 双 optional 空；不得无锁读取槽 |

上述状态不可由执行者按方便互换。

### 6.1 首次调用

```text
取得路由唯一锁
-> 锁内校验配置和请求
-> 确认无待完成槽、请求无见证、上一序号等于最后已完成序号
-> 调用邮箱等待并冻结
-> 无载荷非成功直接映射
-> 任何批次载荷先无抛出接管到待完成槽
-> 复核非空、非零、严格后继和邮箱状态/载荷配对
-> 进入补证状态机
```

若最后已完成序号为 `UINT64_MAX`，在邮箱调用前返回内部不一致/批次序号耗尽。父级已经完成非负等待准入，邮箱再返回 `请求拒绝/等待参数无效/空载荷`属于前置通过后的 provider 不一致，固定映射父内部不一致/邮箱请求拒绝；邮箱 `资源失败/资源失败/空载荷`映射资源失败/邮箱资源失败；邮箱 `内部不一致/正式内部原因/空载荷`映射内部不一致/邮箱内部不一致。`等待超时/等待超时/空载荷`与`已停止/队列已停止/空载荷`分别映射父同名状态。只有 `已冻结/无/非零序号/非空消息组`允许进入待完成成功路径。任何状态携带非零序号或非空消息组时都先接管完整结果，再由基础复核把坏配对固定为内部不一致/邮箱批次形状错误并回显见证；其它空载荷坏配对或未知状态直接返回内部不一致/邮箱批次形状错误，因没有已取出批次而不建立槽或见证。

### 6.2 待完成重试

有槽时：请求除最大等待时间外的冻结绑定必须相等，见证必须存在且完全相等。缺失或错配返回版本漂移，回显槽内原见证；零邮箱、零时间、零事实截止调用，槽保持不变。

见证匹配后必须再次复核槽内完整邮箱结果的状态、原因、批次基础形状和严格后继关系。复核失败固定返回内部不一致/邮箱批次形状错误并回显同一见证，零时间/截止调用；不得因为这是重试而跳过首次发现的坏配对。

匹配时不得调用邮箱。若完整秒材料已保存则跳过时间调用；若共享事实截止已保存则跳过截止调用。失败后只保留已经成功保存的步骤，不清空、不改绑、不回退。

### 6.5 最后发布

三类材料完整后，先从待完成邮箱批次的只读消息组按原顺序完整复制到成功候选，并填完全部标量、观察、区间和截止。`std::bad_alloc`或`std::length_error`固定返回资源失败/结果候选构造资源失败；其它异常或候选逐字段互证失败固定返回内部不一致/结果候选构造异常；两类失败都保留原待完成槽并回显原见证。候选完整并复核全部回显后，再以静态证明无抛出的步骤：

```text
最后已完成批次序号赋为本批序号
-> 清空待完成槽
-> 无抛出移动返回已冻结结果
```

任何可能抛出的检查、消息复制或构造不得放在清槽之后。`std::bad_alloc`、`std::length_error`映射资源失败，其它异常映射内部不一致；若异常发生时槽已存在，必须返回同一见证并保槽。若路由锁取得失败且无法安全读取槽，只返回无载荷内部不一致，不猜测见证。

## 7. 并发、锁序与生命周期

- 公开入口用一个私有 `std::mutex`全程串行；先取得锁，再检查配置、请求、待完成槽和见证。锁覆盖等待、子 provider 调用和最后提交。后到调用在前一调用返回后重新校验上一序号，不能并发冻结第二批。只有加锁自身抛出时允许返回双 optional 空的内部不一致，因为此时不能安全读取槽或见证。
- 路由锁不被任何子 provider 回调取得。邮箱生产者只用邮箱自身锁；邮箱冻结返回前释放邮箱锁。完整秒和事实版本服务不得 import 或回调本路由，因此锁序单向。
- 调用方不得在持有 DATA 锁、邮箱锁、线程生命周期锁或领域事务时调用本入口。
- 新运行代次或时间纪元必须构造新路由实例；旧实例有待完成槽时不得改写配置或把材料迁移到新实例。本叶不提供跨代次/跨进程迁移。
- 普通应用装配只构造一个路由并保证它早于该邮箱第一次冻结；T02只能调用路由，禁止绕过路由直接调用邮箱冻结入口。若已有其它消费者推进过邮箱批次序号，本叶无恢复权，必须拒绝装配而不是构造非零起点路由。
- 待完成状态下邮箱停止不改变槽；先完成同批补证与交付。完成后下一次调用读取邮箱已停止。

时间纪元、时间源或事实范围永久漂移会使旧路由 fail-stop 并继续持有待完成批次；本叶没有跨实例迁移权，不能声明最终交付或优雅停机。只有原配置依赖恢复且同一槽补证成功，或后继正式停机/恢复合同另行承接，才能解除该状态。
