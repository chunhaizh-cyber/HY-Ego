# 方法登记根空域核验预算修复详细设计

身份：`METHOD-REGISTRY-ROOT-EMPTY-DOMAIN-BUDGET-REPAIR`

版本：v0.1

状态：候选施工设计；不修改正式逻辑规范，不证明代码已实施。

代码与事实起点：`8bc4c5527fff6ee9f8458127d96f21e5a27f202e`

## 1. 目标与结论

修复唯一方法登记根首次建立路径对 `读取所有者范围空域` 的错误消费：现行实现固定传入预算 `1`，但 DATA-L1 按4015第9.2节在 owner 幂等账未命中时，必须先以同一预算覆盖当前节点、当前关系、当前值、历史和物理清理墓碑五张权威表的全部条目。初始化前仓库已经存在世界、概念、自我等正式事实，故预算 `1` 不能证明方法登记根 owner 为空。

本修复不改变4015/4080公开合同，不删除空域核验，不新增整库计数接口，不使用 `UINT64_MAX`、事实代次、稳定编码或其它任意常量冒充预算，不绕过 `方法登记根生产初始化提供者`，也不预建方法登记根。唯一合法方向是：由本次调用方明确提供非零有界预算，经生产 provider 原样传入方法根 L2 请求，再由 L2 原样传入既有 L1 空域读取；预算不足结构化返回，零写停止。

预算只约束本次完整空域核验成本，不决定根结构、写集、幂等身份、首次G、根稳定编码或恢复事实。提高预算后允许以新的当前截止重试；不得把预算持久化到首次材料，也不得因预算变化制造幂等冲突。

## 2. 正式依据与当前代码事实

### 2.1 正式依据

- `规范/4015_子规范_L1简化事实基座.md` v2.6 第9.1—9.2节：空域请求必须携带非零 `最大核验事实数`；预算不足返回 `数量预算不足`、清空载荷、零写；只有完整扫描五张表才可返回 `空域=true`。
- `规范/4080_子规范_DATA-L1通用操作全集与冻结门禁.md` v1.2 第2、3.2节：`读取所有者范围空域`是冻结的45项公开操作之一；上层只能组合既有合同，不得新增领域例外或改写DTO。
- `规范/8120_子规范_程序入口启动模式与运行宿主边界_20260726.md` v0.16 第5节第6—8项：阶段19只能经普通应用唯一方法结构聚合与生产provider建立/读回唯一方法登记根；任一非成功结构化短路，禁止绕过provider。
- `规范/详细设计/20260915_METHOD-REGISTRY-ROOT-PRODUCTION-INIT_方法登记根生产初始化详细设计_v0.1.md` v0.4：方法登记根是独立空普通节点；首次建立前必须核验技术owner空域，正常重复正式读回，发布未知按原请求收敛。

### 2.2 当前实现事实与根因

1. `海中鱼巣/领域/数据服务.方法登记根.cpp` 的 `建立或读取方法登记根` 在首次材料缺失时调用：

   ```cpp
   读取所有者范围空域(
       {L1所有者范围空域读取合同版本, owner, 当前, 1});
   ```

2. 4015冻结的 `1` 不是“方法根owner最多写一个节点”的布局预算。L1先计算整个仓库五张权威表的条目总数，再决定是否进入完整扫描；它没有按目标owner预过滤总成本。
3. `L1所有者范围空域读取状态::数量预算不足` 当前没有独立映射，最终落入 `方法登记根结构状态::内部不一致`，既丢失真实原因，也无法让合法调用方增加本次预算后重试。
4. `L2方法登记根初始化请求` 和 `方法登记根生产初始化请求` 均没有空域预算字段；当前provider无法合法向下传递预算。
5. 普通应用现行调用只传 `{1}`。该生产接线位于当前异主RC-P1 WIP范围，本设计不修改它；生产请求通过第3.3节唯一具名默认取得现行空域核验上限，合同版本保持1。直接L2旧调用漏传预算时仍明确拒绝，不能静默继承生产默认。

## 3. 公共合同修订

### 3.1 L2方法登记根初始化请求

只修改初始化请求；单根读取和全组读取仍保持现行版本1与签名。

```cpp
struct L2方法登记根初始化请求 final {
  std::uint32_t 合同版本 = 1;
  std::uint64_t G0 = 0;
  L1所有者范围写入幂等身份 幂等身份{方法登记根首次写入幂等身份};
  std::uint64_t 最大空域核验事实数 = 0;
  friend bool operator==(const L2方法登记根初始化请求 &,
                         const L2方法登记根初始化请求 &) = default;
};
```

入口有效要求：版本1、`G0 != 0`、固定方法根幂等身份、`最大空域核验事实数 != 0`。预算字段放在末尾，含义与 L1 同名字段完全一致，不允许换算、放大或缩小。版本轴保持1；这是对现行源码聚合DTO的末尾字段闭合，不恢复或接纳任何旧持久格式。

旧直接L2调用 `{1, G0, key}` 仍可编译，但因末尾预算默认0只能稳定返回 `入口拒绝`，不能静默使用生产默认预算。只有生产provider或其它合法上层显式填写预算后才能进入空域核验。

### 3.2 方法根结构状态

在现有枚举末尾追加，不重排既有值：

```cpp
数量预算不足
```

它只映射 `L1所有者范围空域读取状态::数量预算不足`。结果必须回显本次请求，`Gread`取L1实际读取截止，`H=0`，`根`为空，且调用链确认没有进入方法根写入。

其它L1空域状态保持分账：

| L1状态 | 方法根状态 |
| --- | --- |
| `成功,false` | `所有者非空冲突` |
| `事实代次漂移` | `事实代次漂移` |
| `数量预算不足` | `数量预算不足` |
| `资源失败` | `资源失败` |
| `入口拒绝/未找到/已退出/范围不支持/内部不一致` | `内部不一致`；这些状态与已绑定活动独占owner的内部前置不相容 |

### 3.3 生产初始化请求与普通应用默认预算

```cpp
inline constexpr std::uint64_t 方法登记根生产默认最大空域核验事实数 =
    1'048'576ULL;

struct 方法登记根生产初始化请求 final {
  std::uint32_t 合同版本 = 1;
  std::uint64_t 最大空域核验事实数 =
      方法登记根生产默认最大空域核验事实数;
  friend bool operator==(const 方法登记根生产初始化请求 &,
                         const 方法登记根生产初始化请求 &) = default;
};
```

生产provider入口要求版本1和非零预算。它的预读、单根读、最终组读算法不变；仅在全组预读为 `尚未建立` 时，把同一预算原样写入L2初始化请求。

在 `方法登记根生产初始化状态` 末尾追加 `数量预算不足`，只映射L2同名状态。所有非成功保持空根；`成功()`要求请求版本1、非零预算、成功状态、非零截止和完整根。

`1,048,576`不是执行者临场填写的“足够大”数字。它复用现行普通应用纯概念结构登记已经冻结并实际使用的空域核验上限；在本模块以具名常量声明，作用仍只是单次核验成本上限。它不证明当前仓库事实总量必然不超过该值；超过时必须返回 `数量预算不足`。现行普通应用的 `初始化({1})` 因聚合初始化采用请求字段默认值而取得该上限，无须修改被RC-P1占用的普通应用文件。

## 4. 预算、幂等与恢复

1. 预算是本次只读资源边界，不进入 `L1所有者范围写集请求`，不进入首次规范化写集、首次写入结果或根事实。
2. 首次材料缺失且预算不足时，方法根owner仍为空，本次零写；调用方可以取得新的当前截止并以更大的明确预算重新调用同一provider合同。
3. 首次材料已经完整存在时，provider仍要求本次请求携带非零预算，但L2不得再次执行空域读取；预算变化不构成幂等冲突，恢复仍按固定方法根幂等身份、首次写集和实际稳定编码读回。
4. `最大空域核验事实数`不能由 `G0`、根节点数、owner预期写集大小、稳定编码或文件大小推导。这些量均不等于L1五表当前总核验成本。
5. 普通应用生产默认来源固定为第3.3节具名常量；显式调用方可以传入其它非零有界值。二者均只是本次资源边界，不改变根业务语义。不得在 `.cpp` 再出现第二个数字字面量或临场默认。

## 5. 精确算法

```text
provider校验版本1请求和非零预算
-> 零代次读取全部当前方法登记根
-> 已有唯一完整根：按现行单根+最终全组读回，返回精确重复
-> 尚未建立：形成L2初始化请求
     G0 = 全组实际Gread
     幂等身份 = 固定方法登记根首次写入幂等身份
     最大空域核验事实数 = provider请求同名字段
-> L2核验请求和当前G
-> 读取当前方法登记根
-> 尚未建立：以请求预算调用L1空域读取
     true：进入现行唯一节点写集提交
     false：所有者非空冲突，零写
     数量预算不足：数量预算不足，零写
     其它非成功：按第3.2节映射，零写
-> 写成功/精确重复：按现行单根和全组同截止读回
-> provider按现行正式读回和发布未知规则收敛
```

不得在预算不足后由同一次调用自动翻倍、循环尝试或改用最大整数。只有调用方明确发起的新请求可以增加预算；每次尝试均重新取得fresh截止。
