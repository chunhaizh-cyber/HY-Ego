# DEMAND-SOURCE-ADMISSION-PROVIDER 需求来源准入提供者详细设计 v0.2

日期：2026-08-16
版本：v0.2

## 1. 目标、范围与完成边界

以同一计划身份替代 v0.1，修复 `DRIFT-DEMAND-SOURCE-ADMISSION-PARENT-CONTEXT-MISSING`：统一 BIZ `需求来源准入服务`的每次非根来源准入必须显式接收一个非零 `L2需求身份 父需求`，并把该父需求贯穿来源对象见证、每项授权见证、业务拒绝证据和每项待补事实定位。任何漏父、错父或混父结果都属于坏 provider 形状，统一收敛为 `内部不一致`。

本版保留 v0.1 已冻结的五项裁决：普通提交不建根；唯一统一 BIZ 来源准入服务按来源种类恰一分派；路径组间 OR、组内 AND；同父目标只按完整目标语义键相等判重；01/04只读且拒绝回执由父提交入口按5150写入。

本叶仍只建立公共 DTO、来源专用 provider 抽象协议、结构化装配 factory 和统一分派服务。当前必需真实来源专用 provider、普通应用装配、01候选准入、04防环、05发布、06读回和需求整体建立均为 `NOT_RUN`。

## 2. 漂移裁决

v0.1请求只有来源、主体和候选子目标；虽然 L4 另持有可空父需求，但它没有进入公共来源调用。两个父需求可拥有完全相同的子目标，因而 provider 可能把属于父A的来源或授权材料回给父B。仅比较子目标语义键不能证明来源属于本次父需求。

固定修正如下：

1. L4父空仍先返回运行期根拒绝，零 provider 调用；只有非空父需求进入公共服务。
2. `需求来源准入请求::父需求`必须是非零 `L2需求身份`，并与 L4 外层父需求、路径意图父需求逐字段相等。
3. 来源对象、授权见证、拒绝证据和待补定位都显式回显同一父需求；成功材料还必须携带至少一项当前 `父需求绑定`事实引用。
4. provider 必须根据父需求从需求结构权威读取父需求完整目标和当前性；统一服务只做公共形状与相等互证，不复制 DATA CRUD，不读取父需求。
5. 父需求身份不进入候选子目标的 `需求目标语义键`。父目标完整语义也不压入当前 I64 子目标键；复合分解等来源后继按父需求读取父目标。
6. 合同版本和公共规则版本升为2。v0.1只保留历史，不得实施或激活。

## 3. 物理位置、所有权与依赖

物理位置保持：

```text
海中鱼巣/领域/服务.需求来源准入.ixx
```

这是唯一真实模块，导出公共值类型、来源专用抽象协议、装配和统一服务；不建立传统 `.数据.h/.cpp`，不建立第二 DATA 来源授权服务。模块私有 `import` L2公共身份、特征和状态结构服务；各具名 provider 自行组合其正式中性 DATA 读取。DATA 不反向依赖 BIZ。

公开函数保持四项：

| 函数 | 责任 | 可见性与调用方 |
| --- | --- | --- |
| `需求来源专用准入提供者::承载来源种类` | 回显具名来源协议身份 | 导出纯虚 `const noexcept`；仅 factory/统一服务调用 |
| `需求来源专用准入提供者::读取并裁决来源授权` | 读取来源事实并按本来源规则形成专用结果 | 导出纯虚 `const noexcept`；统一服务恰一次调用 |
| `装配需求来源准入服务` | 校验完整不可变注册并交付唯一移动服务 | 导出自由函数 `noexcept`；普通应用装配调用 |
| `需求来源准入服务::复核需求来源与主体授权` | 恰一分派和公共父/来源/主体/目标互证 | 导出 `const noexcept`成员；L4等合法BIZ消费者调用 |

`需求来源正式授权事实依据`与`需求来源内在规则依据`保持分型：前者引用当前正式授权事实和非零授权方；后者引用同种类具名规则身份与版本，不伪造 DATA 事实或授权方。

请求 helper 先要求合同/规则版本为2、父需求非零、来源种类/对象绑定、主体、子目标/引用、G0、时间、规则版本和预算全部有效。来源对象的父需求必须等于请求父需求，且 `采用事实`中至少一项角色为`父需求绑定`、生命周期在G0当前。每项授权见证的 `适用父需求`必须等于请求父需求。

来源对象采用事实按“角色、事实身份”稳定排序、零重复；授权见证按“依据分支、正式授权事实或内在规则身份、适用父需求、适用来源、被授权主体、覆盖目标”稳定排序、零重复。两组分别受来源读取预算和授权组预算约束。

拒绝证据父需求必须等于请求父需求；每项待补定位也必须等于请求父需求。完整拒绝矩阵如下，表外组合一律为坏结果：

| 拒绝类别 | 固定失败阶段 | 冲突事实组 | 待补事实组 | 允许 / 必含角色 | 生命周期与版本 |
| --- | --- | --- | --- | --- | --- |
| 来源不成立 | 来源规则 | 非空 | 空 | 只允许且必含`来源内容` | G0当前 |
| 提出主体不匹配 | 来源规则 | 非空 | 空 | 只允许且必含`来源内容` | G0当前 |
| 目标绑定不匹配 | 来源规则 | 非空 | 空 | 只允许且必含`目标绑定` | G0当前 |
| 授权缺失 | 授权读取 | 空 | 非空 | 只允许且必含`授权依据` | 缺口版本有效；所需版本等于请求授权规则版本 |
| 授权范围不覆盖 | 授权规则 | 非空 | 空 | 只允许且必含`授权依据` | G0当前 |
| 授权已退出 | 授权读取 | 非空 | 空 | 只允许且必含`授权依据` | 创建不晚于G0且退出不晚于G0 |
| 来源规则拒绝 | 来源规则 | 非空 | 空 | 只允许且必含`来源内容` | G0当前 |
| 观察或材料待定（来源） | 来源读取 | 空 | 非空 | 只允许`来源内容`、`当前性`或`父需求绑定`且至少一项 | 所需版本等于请求来源规则版本；预期授权方为空 |
| 观察或材料待定（授权） | 授权读取 | 空 | 非空 | 只允许且必含`授权依据` | 所需版本等于请求授权规则版本 |
| 父需求绑定不匹配 | 来源规则 | 非空 | 空 | 只允许且必含`父需求绑定` | G0当前 |

`父需求绑定不匹配`只表示 provider 已读取到明确冲突的父绑定；父绑定材料尚未产生或尚不可判定时使用 `观察或材料待定`与角色`父需求绑定`的待补定位，不虚构零事实身份。

成功只允许完整材料 optional；业务拒绝/待定只允许完整拒绝证据 optional；其它状态两个 optional 为空。成功、业务拒绝、待定、未找到和已退出回显请求G0；当前性漂移回显非零不同截止；其它状态截止为0。上述截止矩阵与专用到公共状态映射不变。

```cpp
        const 需求来源准入请求& 请求) const noexcept;

private:
    struct 提供者登记项 final {
        需求来源种类身份 来源种类;
        std::reference_wrapper<const 需求来源专用准入提供者> 提供者;
    };
    std::vector<提供者登记项> 提供者登记_;
    std::uint64_t 注册版本_ = 0;

    需求来源准入服务(std::vector<提供者登记项>&& 提供者登记,
        std::uint64_t 注册版本) noexcept;
    friend struct 需求来源准入服务装配结果;

        std::span<const 需求来源种类身份> 必需来源种类,

struct 需求来源准入服务装配结果 final {
    需求来源准入服务装配状态 状态 =
        需求来源准入服务装配状态::请求拒绝;

    std::span<const 需求来源种类身份> 必需来源种类,
    std::span<const std::reference_wrapper<
        const 需求来源专用准入提供者>> 提供者,

```

factory 仍以完整 `需求来源种类身份`排序并按固定优先级检查：输入门禁请求拒绝 -> provider无效身份内部不一致 -> 必需来源重复 -> provider来源重复 -> 额外错种类 -> 必需来源缺失 -> 成功。失败零服务，成功交付只移动、不可复制的完整不可变服务；不存在默认构造、半配置和运行期增删 provider。

运行入口固定顺序：

```text
校验v2合同、非零父需求、来源/主体、子目标、G0、时间、版本和预算
-> 按来源种类定位恰一provider
-> 原完整请求恰一次调用provider
-> 校验专用状态、截止和optional
-> 业务拒绝/待定逐字段互证父需求及全部待补定位
-> 成功材料逐字段互证父需求、来源、主体、子目标、时间、G0和版本
-> 逐项互证授权见证适用父需求
-> 一次形成统一值式见证并返回
```

未登记返回`未实现`；专用`请求拒绝`映射公共`提供者拒绝`；其它合法非成功按既定表逐项映射。坏父上下文统一内部不一致，不降级普通来源拒绝。

函数零写、零锁、零等待、零重试、零缓存、零截止重选。不同请求可并发只读；`bad_alloc/length_error`收敛资源失败，其它异常收敛内部不一致。

## 8. 当前能力、后继与数据边界

- 已发布公共 `L2需求身份`，但 DATA-EXT-12精确需求结构服务最终 ABI 仍是后继门禁；统一服务本身不读取 DATA。
- 各来源专用 provider 必须冻结“按父需求、G0和来源身份读取哪些中性事实”，并证明父需求完整目标与候选子目标的来源关系。
- 复合特征分解当前还缺复合定义视图、槽位角色/顺序/基数和父目标到子目标的正式分解合同。现有派生特征“实际阶次 + 直接来源”不得冒充复合槽位。
- 不修改 `计划/数据服务最终需求清单.md`，不发明 DATA 实现 ABI。需要的基础数据公开需求只在对应来源叶详细设计中列出。

## 9. 验证矩阵

除 v0.1 的 factory、恰一分派、13->15状态、optional、截止、拒绝矩阵、资源异常和零写验证外，v0.2必须新增：

1. 请求零父、L4父空、L4外层父与来源请求父不等均在 provider 前拒绝；父空固定零 provider 调用。
2. 成功来源对象漏父/错父、缺少当前 `父需求绑定`采用事实、授权见证漏父/错父/混父，全部内部不一致。
3. 业务拒绝证据错父、任一待补定位错父、`父需求绑定不匹配`的阶段/角色/生命周期错误，全部内部不一致。
4. 同一子目标在父A和父B下分别请求时，任何父A材料不得被父B接受；同父同请求保持值式等义。
5. 父需求不进入目标语义键；改父不改变子目标键内容，但必须改变来源准入请求与全部适用见证。
6. provider 原请求恰一次接收完整父需求；统一服务零需求读取、零 DATA/L1直达。

实现验证仍要求根工程 Debug/Release、生产外专项双配置、diff、strict、UTF-8、工程唯一登记和临时专项独立清理后复验。

## 10. 激活门禁与完成声明
