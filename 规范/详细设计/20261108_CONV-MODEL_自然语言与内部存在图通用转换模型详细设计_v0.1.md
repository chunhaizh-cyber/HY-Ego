# 自然语言与内部存在图通用转换模型详细设计

标识：`CONV-MODEL`；版本：v0.1；日期：2026-11-08；状态：草案，第10节规范修订提案与第12节各项待用户裁决。

依据：0050 §1.4；1100；1110；2210 §2第6项；2300；2310；2320；7230；7231；7232；7233；7240 §1—§6；7260；规范冲突清单第103条。

## 0. 用户裁决与目标

用户裁决（2026-11-07—08）：

1. 先实现通用转换模型，不先进入具体问答。存在、场景、需求、方法、任务已经统一在存在概念下，转换模型围绕存在设计。
2. “存在—特征—值”只适合陈述和疑问。需求、任务、方法通常对应指令或祈使，模型要覆盖。
3. 需求、任务、方法有时一句话说不清，需要段落、文章表达，模型不能以句子为边界。
4. 自然语言世界中的场景用于自然语言与内部世界信息的相互转换。词条作为存在，以“概念名称挂接”特征反向关联概念。
5. 词条、代词概念、指代实例、语言材料范围按存在处理。需求可看作存在，但不按存在处理。转换只在认知层把需求看作存在，不改变需求的处理方式。

目标：建立一个通用模型，把**内部存在图**和**任意长度的文本**互相转换。之后的问答、指令理解、方法学习都作为这个模型的应用，不再各开专门路径。

本设计分两部分：
- 第2—9节定义完整模型；
- 第11节把实施拆成三份计划，本次只把第一份做到可施工深度。

## 1. 修改对象、原因、目的

- **修改对象**：语言知识的含义表示（内部治理侧的语言知识节点内容）；自然语言世界中语言场景的内容。
- **原因**：现有含义操作按场合列举，含义图里设有“正式需求来源”“被询正式内容”等专用槽位，每加一种对话就要新开一条路。生产中，接收入口只认需求陈述和行动请求，输出只有字段询问。
- **目的**：用统一的单元和组合表示任何可解释的含义，输入、输出各走一条通用路径。

本模型不直接修改现实世界、需求、任务、方法的特征。它只产出带来源的**主张草稿**，由各对象 owner 决定是否采用（7240 §1、§4.2第8项）。

## 3. 模型总览

```text
文本（文章 ⊃ 段落 ⊃ 自然句 ⊃ 子句）
   ⇅  语言知识（结构规则：词项、角色项、子规则）
语言场景（一段文本一个）
   ├ 语言实例：本文中被谈到的每个对象一个，带指称方式与绑定
   └ 含义网：单元（静态／动态）＋组合（篇章关系），每个单元带语气
   ⇅  绑定与主张
内部存在图（存在、特征、值、引用型特征；需求、任务、方法、场景都是存在）
```

三层分工：

1. **词条层**：词条是自然语言世界的存在，经“概念名称挂接”特征指向概念。输入时由词得候选概念，输出时由概念选词，首选名称优先。本设计只使用现有名称关系；词条特征化另立计划（第11节）。
2. **语言场景层**：记录“说了什么、出自哪里”。它是转换的工作区和留档，不是现实事实。
3. **存在图层**：内部事实由各 owner 维护。转换只读它，向它提交主张草稿，不直接写。

## 4. 含义网：统一单元、语气、指称与组合

### 4.1 两种内容单元

| 单元 | 必需角色 | 可选角色 | 说明 |
| --- | --- | --- | --- |
| **静态单元** | 主体、谓项 | 时间、场景范围 | 谓项三选一：①特征值（正式特征类型＋准确值／值域／概念条件／方向）；②概念归属（属于某概念）；③同一指认（与另一指称是同一对象） |
| **动态单元** | 主体、动作 | 对象组（按动作定义的角色）、导致变化（一组静态单元）、时间、场景范围 | 动作是已登记的动作概念；导致变化表示动作使对象的哪个特征变成什么 |

存在之间的关系一律用引用型特征表达，不另设关系种类。例如：
- 组成：部分的“所属整体”特征＝整体；
- 场景包含：成员的“所在场景”特征＝场景；
- 需求的目标：需求的“目标信息节点”特征＝水，“目标特征类型”特征＝温度。

因此原来的概念归类、特征描述、特征区间、特征方向、组成描述、场景包含、关系描述、状态描述、需求描述、任务描述、方法描述，都落到静态单元。变化描述和动作落到动态单元。完整映射见第10节表。

### 4.2 语气

语气挂在单元或组合上，不是单元种类。

| 语气 | 含义 | 静态单元的例子 | 动态单元的例子 |
| --- | --- | --- | --- |
| 陈述 | 说话者主张其成立 | 水温是30度 | 我把杯子拿过来了 |
| 疑问 | 某一位置待求，或整体待确认 | 水温多少？ | 谁拿的杯子？ |
| 祈使 | 说话者要求使其成立 | 把水温调到40度 | 把杯子拿过来 |

另有三种限定可叠加在任一语气之上：
- **否定**：必须指明否定哪个单元；
- **条件假设**：只在组合的前件里出现；
- **引述**：保留原说话者。

这与 7240 §2.1 的作用域一一对应：普通陈述→陈述，提问范围→疑问，请求范围与需求目标范围→祈使。

### 4.3 指称：单元角色的值

每个角色的值是一个**语言实例**，有以下几种：

| 指称方式 | 说明 |
| --- | --- |
| 已绑定 | 指向一个内部节点：存在、概念、特征类型、需求等 |
| 名称或描述 | 经名称或修饰形成，尚未绑定，或绑定未唯一 |
| 代词实例 | 1110 的指代实例：已消解的指向目标；未消解的保留候选 |
| 疑问代词实例 | 待求位，有类型和作用域；这就是“疑问”语气的待求位置 |
| 匿名新对象 | 本文首次引入、不与已知对象等同的对象，例如“一个杯子” |
| 值 | 类型化准确值，例如整数加单位 |

同一语言实例可以被多个单元引用，跨句回指靠的就是这一点。例如第二句的“它”与第一句的“这杯水”是两个语言实例，经消解后指向同一绑定目标；两者都保留，不合并。

### 4.4 组合（篇章关系）

| 组合 | 子项 | 说明 |
| --- | --- | --- |
| 顺序 | 有序子项组 | 叙述顺序与事件时间先后分开标注 |
| 并列 | 子项组 | 不蕴含先后 |
| 条件 | 前件、后件，以及共享角色映射 | 前件成立时主张后件；不确认前件或后件在现实中成立 |
| 因果 | 原因、结果 | 是语言主张，不是因果知识 |
| 目的 | 行动、目的 | 祈使句加目的，就是需求的背景 |
| 说明 | 被说明项、说明项 | 补充约束或背景 |

组合的子项可以是单元或其它组合，形成树。整段文本的含义网就是一棵组合树，叶子是单元。量化限定与群体作用（7240 §2.4）作为角色的修饰保留，本设计不改它们的语义，首份计划不实现。

### 4.5 示例

“这杯水的温度是30度。把它的温度调到40度。”

```text
语言实例：I1=这杯水（名称或描述，可绑定）；I2=它（代词实例，消解为与I1同一目标）；V1=30摄氏度；V2=40摄氏度
单元：U1 静态 陈述  主体I1 谓项[温度＝V1]
     U2 静态 祈使  主体I2 谓项[温度＝V2]
组合：C1 顺序（叙述）[U1, U2]
```

“我要喝茶，水要40度，杯子用那个蓝色的。”

```text
U1 静态 祈使（主体E＝我的需求）  谓项[……喝茶目标……]
U2 静态 祈使  主体：水    谓项[温度＝40]
U3 静态 祈使  主体：杯子  谓项[同一指认＝那个蓝色的（代词实例）]
C1 说明[被说明U1；说明U2、U3]
```

## 5. 语言场景的保存

1. 一段输入文本（一条接收消息）或一次输出话语对应一个语言场景。接收侧沿用现有接收来源场景。输出侧新增出站来源场景：以出站消息为来源，入列前先以表达请求为来源，入列后补写出站消息关联。
2. 场景内保存三类内容，都由语言 owner `新_语言类` 维护，场景结构由 `新_自然语言世界树类` 维护：
   - **语言实例**：指称方式、来源原文范围、绑定或候选、代词定义（代词实例）、待求类型（疑问代词实例）；
   - **含义网**：单元、组合、语气与限定，各项的原文范围和所用知识；
   - **采用记录**：本次解释的状态（唯一、多义、缺规则、部分理解）及未解范围。
3. 含义网是这段文本意义的唯一正式承载，U 改为保存含义网，不再另存第二套含义。
4. 指代实例按 1110、7233 是信息存在，持有“指代消解结果”特征，变化时生成状态挂入本场景。场景类普通分支为此新增“信息存在成员”。首份计划只建立代词实例与疑问代词实例两种语言实例的节点，其余语言实例以含义网内的值式记录保存，不单独建节点。
5. 保存不授权写入被描述的现实对象（7240 §1）。

## 6. 输入路径

1. **材料**：固定原文、语言、交互上下文（说话者、受话者、会话），或明确无交互上下文。
2. **切分**：先形成自然句边界候选。句号、问号、叹号、分号是边界线索，引号内的标点不截断外层（7240 §4.2第1项）。段落按换行。
3. **逐句解析**：每个自然句沿用现有回溯匹配算法，但结构规则的含义部分改为第4节的单元与语气。一句可以包含多个子句，规则可以直接产出组合，例如“如果……就……”。
4. **篇章组合**：句与句之间按衔接证据形成组合候选：
   - 衔接词（先、再、然后、如果、所以、为了）由语言知识中的组合规则识别；
   - 没有衔接词的相邻句默认为“顺序（叙述）”；
   - 多种可能时保留候选，不补出文本没有的步骤（7240 §6）。
5. **指称与回指**：
   - 同一语言场景内，后句的代词实例先找前文兼容的语言实例；
   - 再按交互上下文和查询范围找内部节点；
   - 多候选保留未决，不取首项。
6. **结果**：语言场景（实例、含义网、采用记录），以及第8节的主张草稿组。部分理解时，已理解的单元照常产出，未理解的范围保留原文与缺口。

## 7. 输出路径

1. **输入**：一块要表达的存在图片段，加表达目的（陈述、疑问、祈使）与受话者。
2. **规划**：
   - 把片段转成含义网：每个要说的特征值为一个静态单元，每个要说的动作为一个动态单元；
   - 定组合（顺序、说明等），定段落和句子划分。
3. **指称选择**：
   - 首次提及用名称或描述，名称取首选名称（7220 §6.2）；
   - 后续可用代词，但须满足接收方可恢复（7240 §3.2第5项）；
   - 待求位用疑问代词。
4. **成句**：逐单元选结构规则成句，按组合规则连接成段。
5. **回读**：把生成的整段文本按第6节解释，要求恢复同一含义网（单元、语气、组合、指称目标对应）后才交付。
6. **交付**：交付候选话语（7240 §3.3），不发送。

## 8. 与内部存在图的交接（主张草稿）

转换只产出草稿，交对应 owner：

| 含义 | 草稿 | 交给 |
| --- | --- | --- |
| 陈述＋静态 | 某存在某特征的值主张，带说话者和来源 | 存在 owner（7232 主张）；当前场景对象须先绑定现实存在 |
| 陈述＋动态 | 动作事实主张 | 动态与世界 owner，只作材料 |
| 疑问 | 信息请求：待求位的类型、受询者 | 由内部按读取能力回答（输出路径） |
| 祈使＋静态 | 需求目标：提出者、目标信息节点、目标特征类型、目标形式与值 | 需求 owner（被认知需求） |
| 祈使＋动态 | 需求目标＝该动作的导致变化，外加“指定动作”约束 | 需求 owner；任务查找方法时使用约束 |
| 组合 条件/因果＋陈述 | 方法或因果知识的学习材料 | 方法、因果 owner，只作材料 |
| 组合 顺序＋祈使 | 一个需求加有序子目标 | 需求 owner，第三份计划 |

“自我不直接执行本能”保持不变：祈使只形成需求，经任务链查找方法、采用、执行。

### 11.1 计划1的完成条件

1. 第4节的静态单元、三种语气、顺序与说明组合、第4.3节的语言实例落地，成为唯一含义表示，旧操作枚举等全部退出。
2. 23条知识按新表示重写并能初始化；原有句式的解释与生成能力不退化。
3. 以下双向转换均能回读一致（无交互上下文路径，空白语言场景）：
   - “这杯水的温度是30度。把它的温度调到40度。”：两个静态单元，一个陈述、一个祈使，一个顺序组合，“它”回指“这杯水”；
   - “水温多少？”：疑问语气，温度值为疑问代词实例；
   - 现有23条知识的样例句。
4. 接收入口按第8节产出草稿：祈使＋静态交给现有被认知需求建立；其它草稿本计划只记录采用记录、不交接，后续计划接入。
5. 实际项目 Debug/x64 编译链接 0 错误。

### 11.2 计划1需要补的语言知识

- “调到”：祈使动词。计划1中，“把X的F调到V”解释为祈使＋静态单元（X.F＝V），动词只作表达。动作约束留给计划2。
- “多少”：疑问代词定义，新增规则“待求数量值”。
- 衔接：句号分句的默认顺序组合；“然后、再”作为顺序组合的显式词。
- 温度、摄氏度（又称“度”）、水的初始化材料与名称。
- 普通名称关系的首选名称角色，输出时优先使用。
