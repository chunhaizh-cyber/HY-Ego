# 自然语言与内部存在图通用转换模型详细设计

标识：`CONV-MODEL`；版本：v0.2；日期：2026-11-08；状态：草案。第12节为规范修订提案，第14节为待裁决项，均须用户确认。保留v0.1文件路径作为本设计的现行入口。

依据：0050 §1.4；1100；1110 §2（四种对象）；1140 §1第5项、§组成第4项；2210 §2第6项；2300；2310；2320；7230；7231；7232；7233；7240 §1—§6；7260；规范冲突清单第103条。

代码基线：main `b97575683`。

## 0. 用户裁决、审计结论与目标

用户裁决（2026-11-07—08）：

1. 先实现通用转换模型，不先进入具体问答；转换模型围绕存在设计。
2. 模型要覆盖指令和祈使句，需求、任务、方法通常靠它们表达。
3. 模型不以句子为边界，需求、任务、方法常要用段落、文章表达。
4. 自然语言世界的场景用于自然语言与内部世界信息的相互转换。
5. 词条、代词概念、指代实例、语言材料范围按存在处理；需求可看作存在，但不按存在处理。

v0.1 审计（2026-11-08）指出六处会丢失或改变语义，本版逐项修正：

1. 语气不能替代需求、期望和嵌套作用域：→ 第4.3、4.4节。
2. 缺少动态信息模型，变化不一定有已知动作或因果：→ 第4.2节。
3. 特征化只是语言投影，不改变底层权威结构：→ 第4.1节、第8节。
4. 部分理解不能丢掉外层算子；文本顺序不等于执行顺序：→ 第6节第6项、第8节。
5. 原文出现、指代实例、所指目标分开，并预留跨消息引用：→ 第4.5、5节。
6. 验收句须写明预期结果，不能只靠回读一致：→ 第11.2节。

**目标**：建立通用模型，把内部存在图与任意长度的文本互相转换；同时明确哪些含义已经支持，哪些只能保存为未决材料。

## 1. 修改对象、原因、目的

- **修改对象**：语言知识的含义表示（内部治理侧语言知识节点的内容），以及自然语言世界中语言场景的内容。
- **原因**：现有含义操作按场合列举，含义图设有“正式需求来源”“被询正式内容”专用槽位。生产中，接收入口只认需求陈述和行动请求，输出只有字段询问，也没有动态含义。
- **目的**：用统一结构表示可解释的含义，并完整保留说话者、主体、受请求者、作用域与事实地位；输入、输出各走一条通用路径。

本模型不直接写入现实世界、需求、任务、方法、概念。它只产出带来源的主张草稿，按第8节分派给对应 owner 的公开入口，由 owner 决定是否采用。

## 2. 当前事实（路径相对 `海中鱼巣/海中鱼巣/`）

- **含义表示**：
  - 操作 `新语言知识含义操作`（`领域/新_语言类.h:115`）共9种：概念归类、特征描述、组成描述、信息请求、需求描述、缺口登记、特征区间描述、特征方向描述、行动请求。
  - 作用域4种（`:91`）、表达目的3种（`:90`）、子含义用途3种（`:150`）。
  - 含义图由含义节点与子含义边组成（`:177`）。实例化后的 `语言图含义材料`（`领域/语言含义图.数据.h:50`）另带两个专用槽位。
- **迁移面**：
  - 操作枚举约200处引用，作用域、目的、用途合计约150处。
  - 按操作分支的函数在六处：解释、生成、统一层、U采用、知识校验、种子解析。
  - 已保存的采用含义U（含义图、角色树、角色F）也按旧表示存储。
- **知识种子** `初始化材料/最小语言知识种子.txt`（740行）共23条知识，另有结构概念与模式16对。
- **单句局限**：没有分句、分段，生成只出单句，接收入口把整条消息当一句解释。
- **没有动态含义**：动作、变化、动词零命中。“增加/减少”只是目标方向。
- **算法**：解释用回溯匹配，要求整句完整覆盖，结果判为唯一、多义或缺规则；生成按图生成，再整句回读比对。两者都可保留。
- **语言场景**：每条接收消息有一个来源场景，但场景里是空的。U只接受需求描述和行动请求两种根。

## 3. 模型总览

```text
文本：文章 ⊃ 段落 ⊃ 自然句 ⊃ 子句；每段原文是一个“语言出现”
   ⇅  语言知识（结构规则：词项、角色项、子规则）
语言场景（一条消息或一次输出话语一个）
   ├ 指代实例：完整指代表达形成的信息节点，按需建立
   ├ 含义网：内容单元、内容算子、篇章组合、表达用途
   └ 跨场景引用：回应、引用其它场景的单元或指代实例
   ⇅  绑定与主张（语言层特征化投影 → 领域正式结构）
内部存在图：各 owner 维护的正式结构
```

## 4. 含义网

### 4.1 静态单元

| 角色 | 说明 |
| --- | --- |
| 主体 | 一个指称（第4.5节） |
| 谓项 | 三选一：①特征值：正式特征类型，加准确值、值域、概念条件或方向；②概念归属；③同一指认 |
| 时间、范围 | 可选 |

**特征化只是语言层投影，不改变底层权威结构。**组成、场景成员、需求目标等，在语言层可以统一表示成“某特征的值”，这样读取方式一致。但读取与采用必须映射到对应领域的正式结构和公开入口：
- “所属整体”特征与组成关系共同维护，不替代组成关系（1140）；
- 场景成员走场景服务；
- 需求字段走需求 owner；
- 概念归属走概念信息判定。

投影表由第8节的分派规则承载。

### 4.2 事件单元

事件单元替代 v0.1 的“动态单元”。它由三个可选部分组成，至少出现一个：

| 部分 | 角色 | 说明 |
| --- | --- | --- |
| 动作发生 | 主体（可缺）、动作概念、对象组（按动作定义的角色）、方式 | 方式取“尝试”或“完成”。“尝试连接一次”只有动作，不蕴含结果 |
| 状态变化 | 对象、特征类型、前值（可缺）、后值或方向（可缺）、时间 | 允许没有已知动作，例如“水温从30摄氏度降到了20摄氏度” |
| 关联主张 | 动作发生 → 状态变化 | 只在原文给出依据时成立，例如“我把水加热到40度”“因为开了空调，温度降了”；不得为填满结构补造动作或因果 |

规则：
- 没有动作的变化保持无动作；
- 没有关联依据时，动作与变化分列，不自动关联；
- 动作概念未登记时，动作部分保留原文和缺口，不新建动作概念。

### 4.3 内容引用与内容算子

单元和组合都可以作为**内容**被引用。下面的算子作用于一个明确的内容引用，可以嵌套，作用范围必须明确到具体内容。

| 算子 | 角色 | 例子 |
| --- | --- | --- |
| 否定 | 被否定内容 | “不要停止加热”：否定作用于“停止加热” |
| 条件 | 前件内容、后件内容、共享角色映射 | “如果温度超过四十度，就停止加热” |
| 引述 | 原说话者、被引述内容 | “他说周春海需要一杯水” |
| 态度 | 持有者、态度种类、内容；请求类另有受请求者 | 见下表 |
| 量化 | 量化方式（全称、存在、任指）、变量、限制域、谓词内容、绑定范围；数量限制带类型化值域 | 保留量词绑定与范围（7240 §2.4），不压成属性 |

态度种类：

| 态度 | 角色 | 例子 | 说明 |
| --- | --- | --- | --- |
| 需要 | 持有者（需求主体）、内容 | “周春海需要一杯水” | 陈述某人的需求，说话者不是提出者 |
| 期望 | 持有者、内容 | “我希望水温四十度” | 期望某状态成立 |
| 请求执行 | 提出者、受请求者、行为内容（事件的动作部分） | “请让机器人拿杯子” | 受请求者是机器人，不一定是受话者；外层还有一个对受话者的请求，由态度嵌套表达 |
| 请求达成 | 提出者、受请求者、期望状态内容 | “请把水温调到四十度” | 期望状态是水温40度；“调”是行为提示 |
| 询问 | 询问者、受询者、被询内容（含疑问代词实例） | “水温多少？” | — |

“请把杯子拿过来”同时包含请求执行（拿）与请求达成（杯子在说话者旁边）两部分，分别保存。“尝试连接一次”只有请求执行。

### 4.4 表达用途

每个语言出现顶层有一个表达用途：陈述、疑问、祈使。它说明说话者用这段话做什么，等价于“说话者对顶层内容的态度”：

- 陈述：说话者主张内容成立；
- 疑问：顶层为询问，受询者默认是受话者；
- 祈使：顶层为请求，受请求者默认是受话者。

表达用途不替代第4.3节的角色。三句话的区别都由角色保留：

| 句子 | 表达用途 | 内容结构 | 说话者 | 需求主体 | 受请求者 |
| --- | --- | --- | --- | --- | --- |
| 周春海需要一杯水。 | 陈述 | 需要（周春海，[有一杯水]） | 当前说话者 | 周春海 | 无 |
| 请给周春海一杯水。 | 祈使 | 请求达成/执行（说话者→受话者，[周春海有一杯水]，给） | 当前说话者 | 周春海是受益方 | 受话者 |
| 他说周春海需要一杯水。 | 陈述 | 引述（他，需要（周春海，[有一杯水]）） | 当前说话者，原说话者是他 | 周春海 | 无 |

### 4.5 语言出现、指代实例与所指目标

按1110的四种对象分开：

1. **语言出现**：原文中的一段范围及其解析。同文多次出现不合并。
2. **指代实例**：完整指代表达形成的信息节点，例如“这杯水”“它”“那个蓝色的杯子”“多少”。它采用代词定义和修饰约束，保存作用域、约束和指向情况，持有“指代消解结果”特征。不同出现可以复用兼容的已有实例，例如“它”关联“这杯水”的实例；也可以保留不同实例。
3. **所指目标**：具有明确类型和身份的节点，或有界的目标成员组。它与指代实例不是同一身份；变量未绑定时没有虚构的目标。
4. **其它指称**：已绑定引用、名称（专名或类名的泛指用法）、类型化值、匿名新对象（“一个杯子”）。

单元中每个角色的值，是上面某一种的引用。疑问就是某个角色引用了疑问代词实例（待求，有类型和作用域）。

**是否建立节点**：按需要决定，不按词面划分。满足下列任一条件的指代实例建立节点：
- 需要独立身份；
- 被其它单元、场景或需求引用；
- 需要维护“指代消解结果”状态。

其余记在含义网内。完整指代表达与单个代词用同一规则。

### 4.6 篇章组合与跨场景引用

| 组合 | 子项 | 说明 |
| --- | --- | --- |
| 文本顺序 | 有序子项 | 只表示原文排列 |
| 时间顺序 | 有序子项 | 事件先后，须有语言依据（先、再、然后、之后） |
| 并列 | 子项组 | 不蕴含先后 |
| 因果 | 原因、结果 | 语言主张，不是因果知识 |
| 目的 | 行动、目的 | — |
| 说明 | 被说明项、说明项 | 补充约束或背景 |

条件见第4.3节。组合的子项可以是单元、算子内容或组合，一整段文本的含义网是一棵树。

**跨场景引用**：含义网允许带类型的引用指向其它语言场景的单元或指代实例：

| 引用 | 说明 |
| --- | --- |
| 回应 | 回答、确认所指、赞同、纠正、拒绝请求；被回应项是另一场景的询问或请求内容 |
| 引用 | 引用另一场景的单元或指代实例，例如“刚才说的那杯” |

v0.1 中的“语言回应”单元并入回应引用，模型闭合为：两种内容单元、五种内容算子、六种组合、表达用途、两种跨场景引用。

## 5. 语言场景的保存

1. 一条输入消息或一次输出话语对应一个语言场景。接收侧沿用接收来源场景；输出侧新增出站来源场景，入列前以表达请求为来源，入列后补写出站消息关联。
2. 场景内容由语言 owner `新_语言类` 维护，场景结构由 `新_自然语言世界树类` 维护：
   - 语言出现：原文范围、所属解析；
   - 指代实例：按第4.5节需要的建节点，持有“指代消解结果”特征，变化时生成状态挂本场景；场景类普通分支新增“信息存在成员”；
   - 含义网：单元、算子、组合、表达用途、跨场景引用，以及各项的原文范围和所用知识；
   - 采用记录：唯一、多义、缺规则、部分理解，以及未解范围和外层算子是否确定。
3. 含义网是这段文本意义的唯一正式承载。U改为保存含义网。
4. 保存不授权写入被描述的对象（7240 §1）。

## 6. 输入路径

1. **材料**：固定原文、语言、交互上下文（说话者、受话者、会话、近期语言场景），或明确无交互上下文。
2. **切分**：形成自然句边界候选，标点只是线索，引号内的标点不截断外层。段落按换行切分。
3. **逐句解析**：沿用回溯匹配，结构规则的含义部分改用第4节结构。一句可以产出算子和组合。
4. **篇章组合**：
   - 衔接词由语言知识中的组合规则识别；
   - 没有衔接词时只建立“文本顺序”；
   - 多种可能时保留候选，不补出文本没有说的内容。
5. **指称**：
   - 后文的指代实例先在本场景中找兼容的已有实例；
   - 再在近期语言场景中找（跨场景引用）；
   - 最后按交互上下文和查询范围找所指目标；
   - 多候选保留未决。
   - 无交互上下文时只做篇章内共指，所指目标保持待绑定。
6. **部分理解的边界**：
   - 已理解的片段可以保存；
   - 只有外层否定、条件、引述、态度、量化都已确定的完整内容才产出主张草稿；
   - 外层未解释清楚时，只保留片段和缺口，不交接。
   - 例：“如果温度超过四十度，就停止加热”只理解了后半句时，不得交成无条件需求。
7. **结果**：语言场景（出现、指代实例、含义网、采用记录），以及第8节的主张草稿组。

## 7. 输出路径

1. **输入**：要表达的存在图片段（或已有内容），表达用途，受话者。
2. **规划**：转成含义网，确定组合与段落、句子划分。时间顺序须来自材料，不由叙述顺序推断。
3. **指称选择**：
   - 首次提及用名称或描述，取首选名称（7220 §6.2）；
   - 后续可用代词，前提是接收方能恢复所指（7240 §3.2第5项）；
   - 待求位用疑问代词。
4. **成句**：逐单元选结构规则成句，按组合规则连接成段。
5. **回读**：整段按第6节解释，要求恢复同一含义网。回读一致是必要条件，但不充分，正确性另由第11.2节的独立预期结果核对。
6. **交付**：候选话语（7240 §3.3），不发送。

## 8. 主张草稿与分派

分派按“被谈论对象 × 主张类别”进行，不按单元种类一刀切：

| 内容 | 草稿 | 分派 |
| --- | --- | --- |
| 陈述：普通存在的特征值 | 值主张（说话者、来源、时间） | 存在 owner（7232 主张）；当前场景对象须先绑定现实存在 |
| 陈述：组成、场景成员 | 组成或成员主张 | 组成走存在 owner 的组成入口，成员走场景服务 |
| 陈述：概念归属 | 归类主张 | 概念信息判定（只读核对）或概念学习材料 |
| 陈述：同一指认 | 同一性主张 | 只作材料，不合并稳定身份（7240 §2.2） |
| 陈述：需要（某人） | 关于他人需求的主张 | 需求 owner 的被认知需求入口；需求不按普通存在处理 |
| 陈述：任务、方法、能力 | 关于任务、方法、能力的主张 | 对应 owner，只作材料 |
| 陈述：事件 | 动作事实、变化事实或关联主张，三者分开 | 世界与动态 owner，只作材料 |
| 祈使：请求达成 | 需求目标（提出者、需求主体、目标信息节点、目标特征类型、目标形式与值） | 需求 owner；目标对象未绑定时不交付可执行的具体对象需求 |
| 祈使：请求执行 | 需求目标＝该行为已执行（方式为尝试或完成），附动作概念 | 需求 owner；不推出结果状态 |
| 疑问 | 信息请求（待求位类型、受询者） | 内部按读取能力回答（输出路径） |
| 回应 | 对被回应项的回答、确认、纠正、拒绝 | 被回应项的提出方，例如原问题的提问者 |
| 引述 | 带原说话者的嵌套内容 | 只作材料，不按当前说话者的主张交接 |
| 条件、因果、目的组合 | 方法或因果知识学习材料；带条件的需求 | 方法、因果 owner；带条件的需求由需求 owner 判断是否支持，不支持时保留材料 |
| 时间顺序 ＋ 多个请求 | 一个需求加有序子目标 | 需求 owner，第4份计划；只有文本顺序时不建立有序子目标 |

“自我不直接执行本能”不变：请求只形成需求，经任务链查找方法、采用、执行。

## 9. 与现有代码的承接

### 11.2 预期结果表（独立于回读）

每个样例的对象、角色、作用域、单位与未决项独立列出，作为验收依据。以下为计划1、计划2的代表样例，其余在计划中补全。

| 样例 | 计划 | 预期 |
| --- | --- | --- |
| 周春海需要一杯水。 | 1 | 陈述；态度“需要”，持有者为周春海的指称（待绑定）；内容为静态单元：主体是“一杯水”（匿名新对象），谓项为存在；说话者为当前说话者；不交成说话者自己的需求 |
| 请满足以下需求：水温40摄氏度。（等价现有行动请求构式） | 1 | 祈使；请求达成，提出者为说话者，受请求者为受话者；期望状态是水的温度＝40摄氏度；目标对象“水”待绑定时，草稿标为不可执行 |
| 水温多少？ | 1 | 疑问；询问，受询者为受话者；被询内容为静态单元：主体是水（待绑定），谓项是温度＝疑问代词实例（类型：温度值，单位摄氏度） |
| 这杯水的温度是30摄氏度。把它的温度调到40摄氏度。 | 2 | 两个语言出现，一个语言场景；单元1为陈述、静态，主体是指代实例A“这杯水”；单元2为祈使、请求达成，主体是指代实例B“它”，B与A篇章内共指；所指目标待绑定；组合只有文本顺序；需求草稿标为不可执行；“调”记为行为提示 |
| 水温从30摄氏度降到了20摄氏度。 | 3 | 陈述；事件单元只有状态变化：对象为水，特征为温度，前值30、后值20；无动作，无关联主张 |
| 尝试连接一次。 | 3 | 祈使；请求执行，动作为连接，方式为尝试；没有期望状态 |
| 如果温度超过四十摄氏度，就停止加热。 | 4 | 条件算子包住祈使内容；计划1—3中只理解后半句时，不产出无条件需求 |

“30度”这类不带明确单位的说法，计划1—2不做推断，样例直接写“摄氏度”；单位推断另行设计。
