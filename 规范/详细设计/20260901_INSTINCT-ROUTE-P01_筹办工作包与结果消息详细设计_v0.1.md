## 1. 目标、范围与完成条件

本设计只闭合一个线程边界：任务管理线程派发不可变筹办工作包，现有任务工作线程消费工作包并调用筹办 provider，每个已消费工作包在一次处理结束时恰好形成一个强类型结果消息，任务管理线程幂等接收消息、独立读回消息定位的正式事实后再推进。

固定链路为：

```text
任务管理线程形成后继筹办工作包
-> 通过任务筹办工作包提交端口交给现有任务工作线程
-> 工作线程只调用一次筹办 provider
-> 五类闭合结果之一
-> 形成一个不可变结果消息
-> 通过任务筹办结果提交端口交给任务管理线程
-> 管理端已接收 / 精确重复
-> 工作包处理结束
-> 管理线程在自己的循环中独立读回并编排后继
```

完成必须同时满足：

1. 每个已经从工作队列取出的筹办工作包，无论结果是可执行冻结、子目标承接、合法等待、目标已完成还是结构化非成功，均恰好对应一个结果消息；
2. provider 返回只表示“结果消息已经形成”，不表示处理结束；只有结果提交端口确认`已接收`或`精确重复`后才结束本次处理；
3. 任务管理线程生产路径不再同步调用`任务筹办当前就绪与执行冻结提供者::推进下一筹办工作包`，也不以同步返回值、内部槽、轮询、日志或队列顺序替代结果消息；
4. 消息只作进程内不可变交接，不建立持久筹办回执、业务账、状态、动态、因果或第二结果事实；
5. 现有任务工作线程改为串行消费强类型判别联合，不新增筹办专用线程；
6. 正常停止不丢失已接收工作包对应的唯一结果消息；
7. 既有任务实际结果尾部能力保持可用且不改变其业务语义。

协议 v1 的合法生产来源只覆盖当前已存在的`下一筹办工作包`。初次筹办生产链尚未接入任务管理线程，P03 必须通过同一提交端口接入；不得把`任务初次筹办工作包`伪装为`下一筹办工作包`。这不改变“每个已消费工作包必须有一个结果消息”的规则。

`工作包身份`由任务管理线程在形成合法`下一筹办工作包`后取其非零`原重筹办意图幂等键`，并与任务、当前任务轮次、`新筹办轮次`、运行代次和完整请求逐项互证。`结果消息身份`固定等于`工作包身份`的值，作为管理端结果幂等身份；换任务、换任务轮次、换筹办轮次、换 G0、换请求或换分支仍使用同值即为异义冲突。

工作包必须绑定一个正式非零`L2任务轮次身份`。任务管理线程在派发前以工作包 G0 调用本设计 §3.1 的公开入口，且只有任务、截止和当前轮次逐项相等才可取`当前任务轮次.身份`。禁止用筹办轮次、执行轮次、任务序号或整数猜测。

## 5. 任务工作线程

`任务工作线程`实现`任务筹办工作包提交端口`，构造新增借用：

```cpp
任务工作线程(
    std::uint64_t 统一工作队列容量,
    任务管理线程& 任务结果上行目标,
    任务筹办结果提交端口& 筹办结果上行目标,
    任务筹办当前就绪与执行冻结提供者& 筹办提供者) noexcept;
```

队列只保留一个并复用既有容量：

```cpp
using 任务工作线程输入 = std::variant<
    任务工作结果材料,
    任务筹办工作包消息>;
```

不得为筹办新增线程或第二持久队列。原`提交已形成任务工作结果`保持为兼容薄入口，内部转换为联合项；新`提交任务筹办工作包`同样只校验、入统一有界队列和返回结构化状态。

筹办分支状态机固定为：

```text
从统一队列取出一个筹办工作包
-> 保存到进程内“当前处理中工作包”临时槽
-> 调用 provider 恰好一次
-> 规范化为五类之一并形成唯一不可变消息
-> 清空当前处理中槽，进入“待上交筹办结果”临时槽
-> 提交结果
   ├─ 已接收 / 精确重复：清空待上交槽，计为处理结束
   ├─ 资源等待 / 队列已满：保留同一消息，等待通知后重试提交
   └─ 协议拒绝 / 幂等冲突 / 已停止 / 内部错误：保留诊断快照并把线程置为内部错误
```

重试结果提交时不得再次调用 provider、不得重新形成消息、不得换身份或 G1。临时槽只存在于进程内线程对象，不写仓库、SQL、文件或业务事实；它不是 outbox 或第二结果账。

任务实际结果尾部分支保持既有语义。联合队列严格串行消费，不能让筹办重试越过当前待上交消息后继续处理后项，否则会用完成顺序改变编排顺序。

## 6. 任务管理线程

`任务管理线程`实现`任务筹办结果提交端口`，并持有一个可绑定的`任务筹办工作包提交端口*`。运行包在两对象构造完成、启动前完成一次绑定；零端口、重复绑定、启动后换绑均拒绝。

管理线程对后继筹办槽的阶段压缩为：

```text
待形成工作包
待派发工作包
等待结果消息
结果消息待独立读回
待执行冻结队列准备
合法等待终态
目标已完成终态
子目标待后继终态
结构化非成功终态
内部终止
```

现有`当前就绪与执行冻结结果`和 provider 同步返回值不得继续保存在槽中。`读取任务重筹办处理槽`只返回观察快照，不触发 provider、不改变阶段、不作为完成条件。`请求重试任务重筹办处理槽`只允许重派尚未被工作端接收的同一工作包，或按正式等待合同形成新的处理身份；一旦工作端接收，禁止重调 provider。

结果端按`消息身份`幂等：首次完整消息进入槽并把槽键重新排入管理循环；同键完整值相等返回精确重复；同键任何字段或载荷不同返回幂等冲突。槽必须已经处于`等待结果消息`且来源工作包完整相等，否则内部状态冲突。提交函数只做协议校验、幂等准入和排队，不在工作线程调用栈内执行分支业务。

管理循环消费消息后的独立读回矩阵：

| 分支 | 必须独立读回 | P01 后继 |
| --- | --- | --- |
| 可执行冻结 | 正式选择、路径、冻结材料、实例方法；任务、任务轮次、筹办轮次和 G1 逐项互证 | 形成既有`任务执行冻结请求`并走准备/确认队列；消息自身不授权执行 |
| 子目标承接 | 每个正式任务子目标承接记录及精确`T→D_parent`定位 | 只进入`子目标待后继终态`；P02/P03 才拥有准入和需求编排 |
| 合法等待 | 等待合同的对象、合法生产者、重新触发条件和来源工作包 | 进入合法等待终态；不得自动新筹办 |
| 目标已完成 | 正式目标裁决证据及当前任务/轮次绑定 | 进入目标已完成终态；不直接写任务完成或需求满足 |
| 结构化非成功 | 不从日志补事实；互证消息与槽来源 | 进入具名非成功终态；资源失败只能由外层按同一工作身份恢复 |

## 7. provider 结果规范化

`任务筹办收束类别`改为五类顶层分支；原`学习需求承接`、`方法补齐承接`退出顶层枚举。`任务筹办推进结果`必须始终可规范化为一个消息，不再使用“只有执行冻结才成功”的`成功()`语义。建议改为`完整()`，只检查一个分支与一个载荷相符。

P01 不得替 P02 临场补子目标准入算法。当前 provider 能读回正式选择/冻结时返回可执行定位；能证明正式子目标承接记录时返回记录定位；等待合同完整时返回合法等待；目标当前命中且正式裁决证据存在时返回目标已完成；其它入口拒绝、漂移、冲突、资源和内部问题返回结构化非成功。没有正式记录的旧子目标草案、学习草案或方法补齐草案不得包装为子目标承接；HEAD 中“记录后直接建立需求”的旧分支必须从 P01 生产路径退出，不能以等待 P02/P03 为由继续写入。

## 8. 并发、失败与正常停止

统一容量继续使用运行包现有`工作结果容量`，不新增配置项。工作包提交队列满时，管理槽保持`待派发工作包`并在管理线程后续重试；工作端确认接收后才转`等待结果消息`。

正常停止固定为：

```text
解除外部重筹办意图生产并停止任务管理新派发
-> 管理线程把已经形成但尚未提交的工作包提交完，禁止再形成新包
-> 任务工作线程停止接收新输入并排空统一队列
-> 每个已接收筹办工作包的结果消息均获管理端已接收 / 精确重复
-> 管理线程排空结果消息和既有任务结果上行
-> join 工作线程
-> 停止管理结果接收端并 join 管理线程
```

运行包不得先停管理结果接收端。工作端出现协议拒绝、幂等冲突、管理端提前停止或内部错误时，运行包进入`收口失败`并保留快照，不能把工作包静默算作结束。

## 10. 验证矩阵

专属验证至少覆盖：

1. task owner 当前任务/轮次读取：任务未找到、当前关系 0/1/>1、轮次事实缺失/退出/错 owner/错任务、读前/读后 G0 漂移、许可/资源/内部状态；全部非成功零载荷；
2. 五类 provider 结果各一项，均形成且只形成一个消息；
3. provider 调用计数恒为每个已消费工作包一次；结果队列连续两次满后第三次接收，仍只调用一次 provider、消息全字段不变；
4. 同消息首次/精确重复、同键异义、错槽、错任务/轮次/G0、协议版本错误；
5. 子目标草案未形成正式记录时只能`待实现能力`或等待，不能形成子目标承接消息；
6. 可执行消息经管理线程独立读回后才入执行请求队列，读回漂移时零派发；
7. `读取槽`反复调用不触发 provider、不改变阶段；
8. 停机时已有工作包全部形成并确认结果，先停管理端的故障注入必须收口失败；
9. 原任务实际结果尾部首次、重复和拒绝矩阵不回退；
10. 源码断言：管理线程零同步调用`推进下一筹办工作包`，零专用筹办线程，零持久筹办回执/账；
11. Debug/Release 全量构建、严格规范检查和工程/filters登记一致。

## 11. 完成声明边界

P01 只证明当前进程正常运行和正常收口期间：每个已被工作线程消费的筹办工作包，经一次 provider 调用形成唯一消息，并由管理端幂等接收和独立读回。它不证明 P02 子目标准入、P03 子需求/初次筹办生产接线、现实动作、任务实际结果、需求满足或整条本能路线闭环。

本设计明确不建立持久 outbox。因此进程在 provider 已产生正式事实但消息尚未被管理端确认时崩溃，恢复只能依据同一工作幂等身份重放并从 provider 正式事实独立读回收敛；P01 不宣称跨进程 exactly-once 投递或零丢失窗口。
