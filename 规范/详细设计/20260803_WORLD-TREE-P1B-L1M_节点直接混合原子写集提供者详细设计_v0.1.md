## 1. 目标、依据和当前事实

目标是在现行 L1 公开 `提交` ABI 下补齐一个业务中性的固定混合创建形状，供 WORLD-TREE-P1B-W0 消费。直接依据：

```text
规范/4010_子规范_统一仓库稳定句柄与通用关系索引边界.md
规范/4030_子规范_基础信息服务分层与领域写授权.md
规范/4040_子规范_不透明结构事务候选确认撤销与最后发布.md
规范/4050_子规范_入口拒绝逻辑内结果与内部逻辑错误.md
规范/4070_子规范_权威结构快照恢复候选与运行期原子发布.md
流程图/20260803_WORLD-TREE-P1B-L1M_节点直接混合原子写集业务流程图_v0.1.md
流程图/20260803_节点直接类型化结构提交服务提交混合原子写集_函数流程图_v0.1.md
```

当前接口行为核对：

1. `节点直接类型化结构提交服务::提交` 逐字段转交数据操作并把下层八状态同义映射；无需改公开函数、DTO或服务模块。
2. `节点直接类型化结构数据操作::提交` 以空参与者组调用 `执行节点直接类型化结构事务`；无需改数据操作模块。
3. `节点直接身份结构写入执行器::执行带参与者类型化结构事务_` 已统一完成静态校验、独占许可、幂等、代次、计划身份、写集编码/SHA-256、持久准备和侧账，再按写集形状进入互斥分支。
4. 已有成功形状包括仅类型合同、仅值发布、仅节点关系索引创建等；没有同时含类型合同、节点、初始值和关系的分支。目标8项当前会进入末尾不支持收口并返回内部不一致。
5. 四仓均已有候选建立、候选读回、确认、撤销和最后发布 API；缺口是执行器内的同许可编排，不是新仓库、新DTO或第二提交入口。
6. 核心专项自检当前报告固定89项，由顺序170的 `WORLD-TREE-P1A2-S01` 顶层适配消费；本叶原位扩充该报告，顶层自检登记和顺序不变。

## 2. 能力范围和固定形状

本叶只支持以下固定输入顺序：

| 顺序 | 变体 | 额外约束 |
| ---: | --- | --- |
| 0 | `节点直接类型合同发布项` | 合同版本非零、当前可写；与值项合同身份/版本相等 |
| 1 | `节点直接节点创建项` | 唯一新节点；局部身份有效 |
| 2 | `节点直接类型化值发布项` | 所属=写1局部身份；无预期当前版本；来源=当前已发布节点见证 |
| 3—7 | `节点直接关系创建项` | 源端=写1局部身份；目标端=当前已发布节点见证 |

读回固定：当前节点写1、当前类型化值写2、当前关系写3—7，顺序相同，预期版本全部1。参与者组必须为空。任一数量、顺序、变体、局部配对或版本不同均在持久准备前返回入口拒绝。

该形状不检查类型合同是不是“状态时间”、节点是不是“状态”、关系是不是19或角色是不是1—5；这些由L2消费者裁决。它也不接受索引、失效、退役、删除、重挂、第二节点、第二值、非空参与者或任意其它混合。

## 4. 新增私有谓词

在 `执行器.节点直接身份结构写入.ixx` 的执行器类 private 区新增：

```cpp

    const 节点直接类型合同发布项& 写项,
    const 类型合同读回& 读回) noexcept;

static bool 是固定混合创建形状_(
    const 节点直接类型化结构数据操作请求& 请求,
    std::span<节点直接类型化结构事务参与者* const> 参与者组) noexcept;

    const 节点直接类型化结构数据操作请求& 请求) noexcept;
```

第一个函数比较合同身份、命名空间、版本、表示、值域、所有者服务、生命周期和直接兼容组，明确忽略读回的首次/当前发布代次。第二个函数逐项执行 §2 全部数量、顺序、引用和读回配对检查。第三个函数在“至少一个合同发布项且另有非合同项”或“至少一个值发布项且另有非值发布项”时返回true；这覆盖目标形状及其残缺/扩张形状，但不截获现行仅合同、仅值或节点+关系+索引形状。第三个函数为true而第二个为false时统一入口拒绝，不进入持久准备或旧分支。

三个函数无分配、无仓读取、无日志、`noexcept`。其它形状判断不复用“W0”业务名称。

为使确认、撤销、发布和读回失败可重复验证，在同一执行器模块增加唯一自检控制面：


对象序号固定：合同1、节点2、值3、关系1—5为4—8、幂等9、代次推进10；发布后读回阶段只接受1—8。执行器私有成员固定为 `mutable std::atomic<std::uint16_t> 下一次混合原子写故障_{0};`，高8位编码阶段、低8位编码对象序号；设置函数先验证组合，非法值写0，合法值以release存入；目标分支在任何候选前以acq_rel `exchange(0)`一次取得并清除，非目标请求不消费。该函数只允许核心专项自检在自检专属、未进入生产装配的执行器实例上调用，不是提交、仓库或生产诊断入口；AST必须证明生产调用者0，构造签名不变。候选建立后注入映射资源失败并走撤销；确认前映射内部不一致并走撤销；撤销前使具名撤销判为失败并隔离；发布前在尚无对象发布时走撤销、已有对象发布时隔离；发布后读回前使具名互证失败并隔离。

## 5. 合同与端点准备前复核

在取得许可、幂等未命中且代次相等后，扩充现有 `请求动态准备前完整_`：

- 若类型合同尚未发布，按请求写项形成计划合同供同事务值材料校验；
- 若同身份同版本已经发布，必须调用 `类型合同写项静态内容等于读回_`；同义继续，异义返回false；
- 值来源节点、五关系目标节点必须以请求见证在本许可视图中当前有效；
- 值所属局部节点和关系源局部节点只检查引用写1局部身份；
- 值材料必须符合已发布或计划合同；
- 当前代次、幂等、端点或合同发生变化不得通过时钟、SQL或重试补偿。

该步骤失败映射入口拒绝且持久准备调用0。预期事实截止代次与当前代次不同仍优先映射版本漂移。

## 6. 计划身份和候选登记

复用现行 `形成计划身份映射_`，不得手工读取高水位或由L2指定稳定主键。目标局部身份分别映射到节点、值记录和五关系的正式命名域、计划键和初始版本1。

候选建立顺序固定：

1. 合同：读取同身份同版本。不存在时以 `当前代次+1` 作为两个发布代次调用 `结构化发布合同未发布候选`；已发布静态同义时记录“合同已满足”且不建立候选；异义已在准备前拒绝。
2. 节点：用计划映射调用 `结构化创建节点未发布候选`，形成节点句柄和稳定身份见证。
3. 值：所属身份替换为步骤2计划见证，合同使用步骤1的已发布或计划合同，来源使用已验证当前节点见证；形成值记录身份、版本1、当前=true、首次/当前发布代次=`当前代次+1`，调用 `结构化发布值未发布候选`。
4. 五关系：源端解析为步骤2节点句柄/见证，目标端逐项解析为当前节点句柄/请求见证；依输入顺序调用 `结构化创建关系未发布候选`，形成五个版本1见证。
5. 按7项读回规格组装计划记录；计算结果摘要后建立幂等候选。

每次候选建立后必须立即在同一事务序号下完成候选读回并逐字段互证：新合同使用 `读取候选合同()`；节点使用候选句柄和节点仓事务视图 `读取节点(句柄,事务序号)`；值使用 `读取候选值()`；关系使用计划稳定主键和关系仓事务视图 `读取稳定主键当前关系(主键,事务序号)`。任一候选读回缺失或与计划材料不等均映射内部不一致，并进入完整逆序撤销；不得只信建立函数的状态码或在发布后补证。

任何容器分配异常映射资源失败。计划身份缺失、引用错配、材料非法映射入口拒绝；仓高水位或预期版本变化映射版本漂移；仓报告资源失败映射资源失败；仓内部矛盾或候选读回不等映射内部不一致。

## 7. 候选读回和结果材料

计划记录固定保存：

```text
节点组：1项，读0对应见证
类型化值组：1项，读1对应见证
关系组：5项，读2—6对应见证
索引组：空
发布代次：当前代次+1
材料格式版本：2
写集规则版本：2
```

结果摘要基于现行确定性写集材料，追加固定分组标签和数量后，依次编码节点见证、值读回、五关系见证。整数网络字节序；复用现行执行器私有编码/SHA函数，不新增算法或外部依赖。计划记录、候选读回和最终公开读回必须逐字段相等。

## 8. 确认、撤销和最后发布

确认顺序：新合同候选（若有）→节点→值→关系输入序1—5→幂等。无领域参与者。

任一候选建立或确认失败时，撤销顺序固定为：幂等→关系5—1→值→节点→新合同。随后调用持久端口标记已撤销未发布并清理同尝试临时侧账。三者全部成功才返回首次失败状态；任一撤销、见证或侧账清理不完整，标记事务域隔离并返回内部不一致。已发布静态同义合同不是候选，不参与确认或撤销。

全部确认后，最后发布顺序：新合同→节点→值→关系1—5→幂等→推进普通已发布代次。全部操作仍在原独占许可内。任一完成发布或代次推进不完整都隔离并返回内部不一致，禁止尝试把已经发布的部分回滚成普通可用状态。

## 9. 原许可读回与持久旁路

代次推进后、释放许可前逐项复核：

- 新/既有合同静态内容符合写项；新合同时两个发布代次等于本次发布代次；
- 节点稳定主键、类型、版本1、当前有效及计划句柄相等；
- 值的所属、合同、记录身份/版本、材料、来源、当前性及两个发布代次相等；
- 五关系的稳定主键、类型、版本1、源/目标、角色和当前性相等；
- 幂等记录为已发布、发布代次和1+1+5结果摘要相等。

任一矛盾隔离并返回内部不一致。完整时形成现行数据操作结果。随后持久端口 `标记已发布`：成功/精确同义使持久状态为已与内存代次一致；结果未知/资源失败保留内存 `已提交`，持久状态为结果未知；冲突/损坏则隔离并返回内部不一致。SQL内容不能覆盖内存读回。

## 10. 八状态与优先级

| 条件 | 状态 |
| --- | --- |
| 合同/摘要/形状/端点/材料/读回非法 | 入口拒绝 |
| 同幂等身份异意图 | 幂等冲突 |
| 同义已发布 | 幂等读回 |
| 预期代次不同、候选高水位/版本变化 | 版本漂移 |
| 独占许可无效 | 许可拒绝 |
| 分配、SHA、仓或持久端口资源故障 | 资源失败；撤销不完整则升级内部不一致 |
| 同义未发布幂等、仓矛盾、发布/读回矛盾、撤销失败 | 内部不一致并按适用情况隔离 |
| 全部闭合 | 已提交 |

优先顺序沿现行根：静态准入→许可→幂等→代次→准备前事实→编码/持久准备→候选。不得因后续错误覆盖更早已裁决的逻辑内返回，撤销失败除外。

## 11. 所有权、并发和诊断

- 事务域独占许可由执行器取得并覆盖全部仓候选和读回；仓内部继续持有私有锁。
- 上层只传值式请求/结果；不得暴露许可、锁、候选、事务序号或计划句柄。
- SQL/持久端口只作证据旁路，不是权威数据源；内存仓和普通发布代次是权威。
- 本叶不增加日志点。执行器继续以结构化状态向服务边界送出；仓或端口已有诊断不重复记录。
- 同幂等调用由幂等记录返回原结果，不再次形成候选或消耗稳定身份。
