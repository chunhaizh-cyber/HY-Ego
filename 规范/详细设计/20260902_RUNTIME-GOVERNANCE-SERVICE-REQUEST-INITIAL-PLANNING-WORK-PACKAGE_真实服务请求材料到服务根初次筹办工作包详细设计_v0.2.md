# RUNTIME-GOVERNANCE-SERVICE-REQUEST-INITIAL-PLANNING-WORK-PACKAGE 真实服务请求材料到服务根初次筹办工作包详细设计 v0.2

日期：2026-09-02

身份：`RUNTIME-GOVERNANCE-SERVICE-REQUEST-INITIAL-PLANNING-WORK-PACKAGE`

状态：执行侧设计漂移修订；配套 v0.2 计划登记后取代 v0.1 施工合同。

## 1. 修订裁决

v0.1 已正确冻结 `E + M + D_service -> 初次筹办工作包 -> P01 唯一结果消息`，但把“初次来源进入同一筹办 provider”停在名称级，没有冻结下列直接消费合同：

1. `任务特征方法查找请求`、`任务筹办当前就绪请求`和等待合同仍把来源固定为 `下一筹办工作包`；
2. `任务执行冻结请求.来源工作包`仍固定为 `下一筹办工作包`，导致初次来源即使形成`可执行冻结`，管理端也无法形成合法执行冻结请求；
3. DATA-L2 已有初次 / 后继规范化来源判别联合，但初次分支没有完整承接任务轮次和本轮来源成员关系，原始初次工作包也必须显式携带首次准备记录身份后才能机械映射；
4. v0.1 白名单没有包含上述 ABI 所在文件，执行者不能在计划内自行补齐。

这些问题都属于原目标内的直接消费链设计缺口，不建立新目标。本修订采用一个既有判别联合贯穿查找、就绪、正式选择、等待和执行冻结；不再建立第二层来源联合、第二 provider、第二结果端口或任何账。

## 2. 目标、范围与完成条件

目标链保持不变：

```text
已发布存在 E + E 携带的不可变材料 M + 正式服务根 D_service
-> 同一 G0 强类型读回与互证
-> task owner 建立或精确复用服务根任务 T、R1、首次准备记录 P0
-> 初次筹办工作包 W0
-> W0 机械规范化为 DATA-L2 初次筹办来源 S0
-> 同一 P01 工作线程恰好调用一次统一筹办 provider
-> 五类之一的唯一结果消息
-> 管理端独立读回；若为可执行冻结，则以 S0 形成同一个执行冻结请求
-> 结果消息已接收或精确重复后，本次筹办处理结束
```

完成条件：正常进程内，初次来源和既有后继来源都能通过同一强类型协议进入统一 provider；初次来源的五类结果均可由管理端收束，其中`可执行冻结`能够形成通过完整性复核的执行冻结请求。消息仍只是线程交接，正式选择、冻结、路径和实例必须由 task owner 独立读回。

本叶不证明方法动作已执行、现实动作已发生、任务完成、需求满足 / 结算、服务成功、安全值 / 服务值变化、学习或跨进程 exactly-once。

## 3. 正式依据与当前事实

- 3100 v1.5、3200 v1.5：真实请求先进入服务根父任务；每次筹办处理恰好形成一个强类型结果消息，消息不能替代正式业务事实。
- 4260 现行规范 §5：task owner 的正式选择来源已经是 `L2任务初次筹办规范化来源材料 | L2任务重筹办规范化来源材料`；两个分支不得用 optional 拼盘或无类型整数互换。
- 5230 v2.0：初次筹办和同任务轮次后继筹办都可形成正式选择与执行冻结；执行请求必须回到本轮实际来源和冻结事实。
- 6120 v0.12：服务请求只触发服务根任务 fresh 治理，不建立服务合同、请求账、Gseed、游标、替代账或服务根自动维护。
- 正式基线 `main@db2170682e7d450b4d193bcc9b378cdf3e457f7d`：P01 消息仅能携带后继推进请求；task owner 已有 DATA-L2 来源联合及初次正式选择发布 / 读回合同；执行冻结协议只接受 `下一筹办工作包`。
- 隔离候选仅用于定位漂移，不是规范或实现事实；其中给初次 provider 固定返回待实现、把初次分支跳过执行冻结或把原始工作包强制转成后继工作包都不成立。

## 4. 唯一来源合同

### 4.1 原始初次工作包

`任务初次筹办工作包`至少携带并逐项完整互证：

```text
合同版本、运行代次
任务完整事实、任务身份来源完整事实
任务轮次身份、筹办轮次 = 1
首次准备记录身份
来源需求完整事实、本轮来源成员关系完整事实、需求列表项完整事实
首次目标比较共同事实截止 G0、任务 / 轮次建立事实代次 G1
可选服务请求来源 E/M/D（存在时必须完整）
```

首次准备记录身份由 task owner 首次 / 精确重复读回结果给出，必须进入工作包本身；不得依赖服务请求返回对象的旁路 optional、线程槽或消息身份补齐。工作包完整性必须证明记录、任务、任务轮次、来源成员、列表项、G0/G1 和运行代次同源。

### 4.2 DATA-L2 规范化来源联合

唯一跨内部治理、task owner 与执行冻结使用的来源合同保持：

```cpp
using L2任务筹办规范化来源材料 = std::variant<
    L2任务初次筹办规范化来源材料,
    L2任务重筹办规范化来源材料>;
```

初次分支字段补齐为：

```text
合同版本
首次准备记录身份
任务身份
任务轮次身份
来源需求身份
本轮来源成员关系完整事实
同类任务查询锚点（需求列表项身份）
首次目标比较共同事实截止 G0
任务 / R1 建立事实代次 G1
筹办轮次 = 1
运行代次
```

后继分支保持现行字段与语义，不在本计划改变其生产资格或来源规则。公共 helper 必须按判别分支取得：来源幂等身份、任务、任务轮次、筹办轮次、运行代次、来源事实截止和执行轮次。初次来源幂等身份是`首次准备记录身份`，计划执行轮次固定为 1；后继来源保持原后继幂等身份和`旧执行轮次 + 1`。

### 4.3 机械规范化

内部治理提供两个纯值映射：

```text
规范化来源(任务初次筹办工作包) -> L2任务初次筹办规范化来源材料
规范化来源(下一筹办工作包)     -> L2任务重筹办规范化来源材料
```

映射只取原工作包中的强类型字段，不读仓、不写事实、不生成身份。规范化后必须重新运行 DATA-L2 完整性谓词；失败返回结构化非成功，禁止降级到另一分支。

## 5. 统一筹办 provider

### 5.1 请求与公开入口

现有`任务筹办推进请求`不再保存原始`下一筹办工作包`，改为保存：

```text
合同版本
L2结构请求头（期望事实代次 G）
L2任务筹办规范化来源材料 来源材料
现有全部有界扫描 / 召回 / 状态 / 场景 / 条件 / 来源需求预算
```

公开入口统一为：

```cpp
任务筹办推进结果 推进筹办工作包(
    const 任务筹办推进请求& 请求) noexcept;
```

不保留“初次入口固定未实现”的生产分支。若为降低调用侧一次性改动保留旧`推进下一筹办工作包`薄适配，只允许机械规范化后调用统一入口，不能拥有第二套业务逻辑或第二结果形成。

### 5.2 方法查找分流

`任务特征方法查找请求.来源材料`和结果的`已互证来源材料`使用同一个 DATA-L2 判别联合。公共后半段仍复用当前目标读取、状态与目标合同比较、特征类型粗召回、方法适用性筛选和条件提议。

分支前置固定为：

- 初次来源：在 G 独立读取任务、任务轮次、首次准备记录、本轮来源成员关系和列表项；逐项互证 S0，证明筹办轮次为 1、任务轮次仍在筹办阶段且没有旧选择 / 路径 / 实例。不得读取或伪造旧实际结果、旧治理状态、旧路径和目标未达成证据。
- 后继来源：保持现行旧实例、旧实际结果、旧筹办轮次及合法后继来源互证，不因本修订放宽。

比较 / 条件幂等种子使用强类型来源幂等身份的稳定值，仅作同次调用键；不能把两个 variant 分支压成同一种来源语义。

### 5.3 当前就绪、等待和正式选择

`任务筹办当前就绪请求`、`任务筹办等待合同`和授权 / 安全材料来源接口的工作包参数统一改为`L2任务筹办规范化来源材料`。公共当前就绪检查继续读取任务、来源需求、方法、条件、输入、限制、场景和冻结材料；来源特有检查按分支执行：

- 初次：首次准备记录是稳定来源与冻结归因；不要求目标未达成治理状态、旧实际结果或旧路径。
- 后继：保持现行目标裁决 / 治理状态及旧结果检查。

发布`L2发布任务筹办正式选择请求`时直接传递同一个规范化来源联合。稳定来源证据和`冻结材料.归因证据`必须与分支一致：初次使用首次准备记录；后继保持正式后继来源证据。发布后按`L2取得任务筹办来源幂等身份`与原完整请求独立读回，才可形成`可执行冻结`定位。

合法等待载荷保存规范化来源联合，不再把等待固定成后继原工作包；任务管理不因等待自动创建下一筹办。

## 6. P01 消息、管理端与执行冻结

### 6.1 P01 工作包消息

协议版本 2 的`任务筹办工作包消息`继续只保存一个`任务筹办推进请求`；初次 / 后继判别由`请求.来源材料`承担，不再在 P01 外层建立第二个同义 variant。消息完整性逐项要求：

```text
消息任务 == L2取得任务筹办任务(来源材料)
消息任务轮次 == 来源材料中的任务轮次
消息筹办轮次 == L2取得任务筹办轮次(来源材料)
消息来源事实截止 == 请求头期望事实代次
请求头截止满足对应来源分支的当前性合同
工作包消息身份非零且与提交槽幂等键一致
```

管理端的`提交初次筹办工作包`只做：验证原始工作包、机械规范化、按现有预算形成统一推进请求、登记同一槽并提交同一工作端口。它不拥有第二队列、第二 outbox 或第二结果端口。

工作线程对每个已消费消息只调用一次`推进筹办工作包`，随后只形成一次结果消息。结果队列满只重投同一消息，不重调 provider。

`提交任务筹办结果`首次接收初次结果或判定精确重复后，必须像后继结果一样把对应槽转为`结果消息待独立读回`并排入现有结果待处理队列；只有队列消费者完成下述独立读回后才能进入执行、等待或分支收束。只修改槽阶段却不排队会使初次处理永久停住，不是合法等待。任务管理线程不得直接调用筹办 provider，也不得用 provider 返回值、调用计数或槽状态绕过结果消息。

### 6.2 执行冻结请求

`海中鱼巣/线程/协议.任务执行请求.ixx`中的`任务执行冻结请求.来源工作包`改为`L2任务筹办规范化来源材料`，协议版本递增。公共完整性继续校验正式选择、冻结材料、实例方法、任务、筹办轮次、方法、路径、内容版本和形成截止；来源分支另行校验：

- 初次：正式选择记录来源 = 首次准备记录，任务 / 任务轮次 / 筹办轮次 1 同源，冻结归因 = 首次准备记录，实例执行轮次 = 1；
- 后继：保持原后继来源幂等身份、任务、新筹办轮次和实例执行轮次 = 旧执行轮次 + 1。

请求编号与请求幂等键仍使用 P01 结果消息身份；它们不充当 task owner 的筹办来源身份。管理端在`可执行冻结`分支独立读回正式选择、冻结材料和实例方法后，把原消息中的同一个规范化来源联合放入执行请求并运行完整性复核；不得因来源为初次而跳过，也不得重新调用筹办 provider。

其它四类结果按现行收束；消息载荷不能替代正式事实。初次`合法等待`不自动重筹办，`目标已完成`不写任务完成，`结构化非成功`不伪装任务失败。

## 7. E/M/D、task owner 与失败收口

v0.1 的 E/M/D 合同保持：E 由存在服务在 G0 独立读回；M 由不可变材料服务在同一 G0 读回且`来源节点 == E`；D 必须等于正式根锚点并由需求服务读回。材料内容不在本叶解析。

task owner 完整请求继续保存可选`服务请求来源材料{E,M,D}`。新服务请求必须携带；旧记录缺扩展来源返回具名`待迁移`，不得自动补造。首次 / 精确重复结果形成原记录与原工作包，工作包必须带回同一个首次准备记录身份。

发布前拒绝、漂移、引用冲突、资源失败均零写；发布未知只允许原键原完整请求读回收敛。工作包提交队列满只重投同一工作包消息；已形成任务 / 记录不得重复建立。
