# RUNTIME-DEMAND-TASK-SUBGOAL-RECORD-CONSUMPTION 需求消费任务子目标承接记录详细设计 v0.1

日期：2026-08-23
版本：v0.1

## 1. 目标、范围与完成条件

本设计闭合任务子目标承接记录发布后的直接需求侧代码叶：

```text
读取一份已发布任务子目标承接记录
-> 以记录中的显式父需求为唯一父域与所属存在来源
-> 在需求树中复用同父同目标当前子需求，或建立新的正式子需求
-> 精确复用已有需求列表项，或建立新的列表项
-> 在需求 owner 内原子建立“子需求 -> 任务子目标承接记录”强类型来源引用
-> 在任务 owner 绑定记录与正式子需求
-> 在同一最终事实截止双向权威读回
```

完成必须同时成立：

1. 普通应用可以取得唯一 `需求任务子目标承接服务` 实例；
2. 一份状态为`待绑定子需求`的当前记录只能收敛到一个正式子需求；
3. 同父、同所属存在、同目标宿主、同目标特征、同目标状态合同的当前子需求必须复用；
4. 没有同父同目标子需求时，已有精确列表项则复用列表项，否则建立列表项；
5. 需求建立/复用与来源引用在需求 owner 内形成一个原子写结果，不出现“新需求已发布但来源引用缺失”的半结构；
6. 任务记录绑定是第二个 owner 的独立发布；最终成功只在两个 owner 的权威读回互相一致后成立；
7. 崩溃、返回丢失或事实代次漂移后的重试不建立第二需求、第二列表项、第二来源引用或第二任务绑定；
8. 实现不需要执行者再决定 DTO、函数、物理位置、幂等来源、顺序来源、错误映射或读回标准。

## 2. 明确排除项

本叶不做：

- 不恢复已否决的 `RUNTIME-DEMAND-CHILD-CANDIDATE-UNIFIED-ENTRY` 身份、文件、DTO、状态机或计划；
- 不建立通用多来源注册表、来源种类枚举、BIZ 私有账、BIZ 幂等账、跨 owner 事务协调器或发布见证仓；
- 不让记录成为父需求、需求 owner、需求列表项或目标三元组的第二权威；
- 不从记录身份、稳定编码、遍历顺序或当前子数量推导父子顺序；
- 不执行父需求当前满足重判、来源任务唤醒、任务重新筹办或旧筹办轮次复活；
- 不创建子需求承接任务；
- 不实现成员逐需求结算、结果可共用/争用裁决、优先级分配、共享证据复用、预算或归因份额分配；
- 不实现普通业务拒绝回执治理、开发诊断持久结构或通用 `提交或复用单目标需求` 总入口；本叶只消费已经由任务 owner 形成并验证的具名记录，结构化非成功继续向合法上层送出；
- 不把专项自检、日志、返回摘要或聊天说明当作双 owner 机器事实。

### 3.2 正式逻辑依据

- 0050：强类型事实、来源、失败与完成声明必须分账；不得以日志或输出代替机器事实。
- 3100、5100：一个需求只有一个目标三元组；所属存在与来源上下文分账；任务发现独立子目标只能形成候选，正式需求由需求侧统一消费；同父同目标不得因来源不同建立第二需求。
- 5110：同父同目标活动子需求必须复用或合并；父子循环、损坏端点和模糊兜底禁止；子需求结束不等于父需求满足。
- 4010：跨 owner 稳定引用不转移所有权；关系端点必须使用稳定身份并保留唯一 owner。
- 4030：DATA-L2 只负责强类型结构、基数、引用、生命周期、幂等和原子发布；业务编排位于 DATA 外；跨 owner 引用不授权跨 owner 修改。
- 4040：每个 owner 的完整中性写集在本 owner 内原子发布；未知发布只按原幂等身份和权威读回收敛。
- 4050：入口拒绝、许可、漂移、幂等冲突、引用冲突、资源失败和内部不一致必须分账；发布后坏读回属于内部不一致。
- 5090：正式子需求及其列表项先于子任务；任务记录不能直接建立任务或第二任务树。

4250、4260 当前为待确认材料，只用于定位现有字段与接口，不作为本设计唯一机器语义依据。

## 4. 核心机器不变量

### 4.1 父域和目标来源

记录中的 `父需求` 是唯一父域输入。业务服务必须在同一事实截止读取：

```text
记录
+ 父需求完整事实
+ 父需求当前成员关系
+ 父需求完整列表项
```

子需求核心契约固定为：

```text
所属存在 = 父需求.所属存在
目标宿主 = 记录.子目标.目标宿主
目标特征 = 记录.子目标.目标特征
目标状态合同 = 记录.子目标.目标状态合同
```

`条件场景`只保留在任务记录来源材料中，不加入需求目标三元组，不新增需求场景字段。

### 4.2 来源引用

需求 owner 新增一种当前强类型关系：

```text
源端点 = 正式子需求
关系类型 = 任务子目标承接记录来源关系类型
目标端点 = 已发布任务子目标承接记录
```

关系事实只表达“该正式需求由该任务记录提供准入/来源证据”。它不表达：

- 记录拥有需求；
- 记录替代父子关系；
- 记录目标覆盖需求目标；
- 子需求已经满足；
- 任务记录已经回流；
- 父需求应当重判。

基数固定为：

- 一份当前任务记录最多对应一个当前需求来源引用；
- 一个当前子需求可以有零到多份不同任务记录来源引用；
- 同一`子需求 + 记录`不得存在第二当前关系。

### 4.3 两 owner 顺序

固定发布顺序：

```text
D：需求 owner 原子发布需求结构与来源引用
-> 权威读回 D
-> T：任务 owner 绑定记录与子需求
-> 权威读回 T
-> 在同一最终事实截止重新读取 D 与 T
```

禁止先绑定任务记录再发布需求来源引用。当前记录已经绑定但需求来源引用缺失时，固定`内部不一致`，不得静默补写或把既有旁路升级为本入口成功。

### 5.2 类型登记与本地键

`L2需求结构类型登记规则版本`从 1 提升为 2；`L2需求结构类型登记`新增字段`L2需求任务子目标来源关系类型身份 任务子目标来源关系类型`，登记完整性和精确重复比较必须包含该字段。类型登记新增：

不得建立来源引用节点、属性镜像、BIZ 状态属性或第二类型登记模块。

### 5.3 原子写集

1. 新列表模式：复用现有“2 节点 + 12/13 关系”写集，追加一条`新需求 -> 来源记录`关系；列表项、需求、成员、父子和来源引用同代发布。
2. 既有列表模式：复用现有“1 节点 + 7/8 关系”写集，追加来源关系；需求、成员、父子和来源引用同代发布。
3. 既有子需求模式：只新增一条来源关系；写前在同一 G 读取并互证子需求、父关系、成员关系和完整列表项。

三类写入共用需求 owner 的既有 move-only 写端口和 owner-scoped 幂等域；不建立第二端口或第二 owner。请求中的`来源稳定编码`固定等于来源记录稳定编码。

### 5.4 旧 G 与未知发布

三类新写入口沿用需求 owner 现有行为：

- 当前 G 等于请求 G：形成完整写集并提交；
- 当前 G 不等于请求 G：仍以原幂等身份和原完整写集交 L1 收敛；
- 已发布同义请求返回首次`精确重复`和原发布截止；
- 没有首次成功结果返回`事实代次漂移`且零载荷；
- 同键异义返回`幂等冲突`。

业务层不得读取 L1 幂等账、首次材料、owner 或写端口。

- DATA 的`入口拒绝`与`许可拒绝`分别映射为同名业务状态，任何路径不得合并二者。

## 7. `承接任务子目标记录` 固定算法

### 7.1 取得预读共同 G

1. 校验合同、G0、记录、父子顺序和两幂等身份；失败零 DATA 调用。
2. 以 G0 读取任务记录；记录不存在、已退出或坏成功形状按 DATA 状态映射，不得生成默认父需求或目标。
3. 若记录读取返回`事实代次漂移`且回显非零当前 G，只允许用该 G 对同一记录再读一次；第二次仍漂移则返回`事实代次漂移`，不循环。
4. 以记录读回截止读取需求来源。若该读取回显新的非零当前 G，则只允许用该 G 将“任务记录 + 需求来源”完整预读组重做一次；任一项再次漂移、两项截止不同或载荷不完整均返回`事实代次漂移`或对应内部不一致，不再逐项追赶。
5. 两项成功且截止相同后，将该截止命名为`预读共同 G`；后续父域、选择和首次需求写都只使用该 G。

### 7.2 读取需求来源与记录状态

在`预读共同 G`下裁决记录与来源组合：

- 记录为`待绑定子需求`且来源空：进入新承接；
- 记录为`待绑定子需求`且来源唯一：解释为需求 owner 已发布、任务 owner 待绑定，来源分类固定`需求侧事实已存在`，进入收敛；不得猜测首次需求写模式；
- 记录为`等待子需求`或`子需求已回流待父需求重判`且来源唯一并与记录子需求相同：进入已有双向事实读回；
- 记录已带子需求但来源空：`内部不一致`；
- 来源子需求与记录子需求不同、来源复义或坏端点：`内部不一致`。

记录为`待绑定子需求`且来源唯一时，在调用任务绑定前必须以`预读共同 G`完整读取来源关系中的子需求、父需求、当前父关系、当前成员关系和完整列表项，并逐项验证：来源端点、父需求身份、父子顺序、父需求/子需求/列表项所属存在、列表项身份及目标三元组与记录一致。成功后把六份需求侧材料作为本次恢复载荷，来源分类固定`需求侧事实已存在`；任一读取漂移返回`事实代次漂移`，任一结构矛盾返回`内部不一致/父域冲突/目标冲突/父子顺序冲突`，不得直接进入任务绑定。

### 7.3 新承接选择

同一 G 读取父需求完整、父需求成员关系和完整列表项，验证父需求所属存在、目标和成员链自洽。随后：

1. 以父需求所属存在和记录目标三元组调用`按精确目标查询需求列表项`；零项或唯一项合法，多项`内部不一致`。
2. 调用`读取需求直接子(父需求)`，筛选目标三元组与记录完全相等的当前直接子；零项或唯一项合法，多项`内部不一致`。
3. 唯一同目标子存在时：
   - 它必须属于精确列表项；
   - 当前父关系的顺序必须等于请求`父子顺序`；
   - 调用`为既有需求建立任务子目标来源`。
4. 没有同目标子、精确列表项存在时，调用`新增需求并加入既有列表项及任务子目标来源`。
5. 两者都不存在时，调用`新增需求并建立列表项及任务子目标来源`。

任何模式都不得按列表项中其它父域成员复用子需求。列表项只复用聚合身份；父子需求身份仍按显式父域裁决。

### 7.4 任务绑定

需求 owner 成功/精确重复并完成读回后，以其事实截止形成：

```cpp
L2绑定任务子目标承接记录子需求请求{
    {L2结构合同版本, 需求侧事实截止},
    请求.任务绑定幂等身份,
    请求.记录,
    子需求身份
}
```

任务 owner 返回：

- `已提交/精确重复`且记录载荷完整：继续最终读回；
- `事实代次漂移`：先按任务服务既有旧 G 规则确认没有原绑定结果，再返回`需求已发布待任务绑定`；调用方用同一业务请求重试；
- `资源失败`：返回`需求已发布待任务绑定`并保留需求侧载荷；不得换绑定键；
- `幂等冲突/引用冲突/入口拒绝/许可拒绝`：精确映射，不撤销已发布需求；
- 坏成功形状：`内部不一致`。

最终业务状态由任务绑定写结果唯一决定：任务绑定`已提交`且最终双读回成立返回`已承接`；任务绑定`精确重复`且最终双读回成立返回`精确重复`。调用开始时已有一致双向事实不再调用绑定，最终双读回成立后固定返回`精确重复 + 已有双向事实`。

### 7.5 最终双读回

最终 G 候选来源固定且只有两种：

- 本次发生任务绑定写入或精确重复：取任务绑定结果的事实截止；
- 调用开始时已经存在一致双向事实：取第 7.1 节建立的`预读共同 G`。

不得从单个需求载荷生命周期、稳定编码或本地当前 G 猜测最终 G。以该候选执行：

1. 重新读取任务记录；
2. 重新按记录读取需求来源；
3. 重新读取子需求完整、父需求完整、当前父关系、成员关系和完整列表项；
4. 互证：
   - 任务记录状态为`等待子需求`或更后的`子需求已回流待父需求重判`；
   - 记录子需求等于来源关系子需求；
   - 来源关系目标等于记录身份；
   - 子需求当前父需求等于记录父需求；
   - 父需求身份等于记录父需求，父需求、子需求和列表项所属存在逐项相等；
   - 子需求、列表项与记录目标三元组逐字段相等；
   - 所有结果截止等于最终 G。
5. 任一读取报告漂移，只允许用其非零最新 G 对完整最终读回组重做一次；重做成功且全部截止相同则以该最新 G 替换最终 G，再次漂移或截止分叉返回`事实代次漂移`。

只有上述全部成立才返回`已承接`或`精确重复`。

## 9. 失败映射

| 事实 | 业务结果 | 副作用边界 |
| --- | --- | --- |
| 请求字段无效 | `入口拒绝` | 零 DATA 调用 |
| DATA 许可不成立 | `许可拒绝` | 零本次发布；不得并入入口拒绝 |
| 记录当前不存在/退出/非待绑定且无一致双向事实 | `记录不可承接` | 零新写入 |
| 父需求、父成员或父列表项与记录父域不一致 | `父域冲突`或`内部不一致` | 零新写入 |
| 同父子目标与列表项/记录目标不同 | `目标冲突` | 零新写入 |
| 复用子需求的既有父子顺序与请求不同 | `父子顺序冲突` | 零新写入 |
| DATA 期望代次不再当前且无首次结果 | `事实代次漂移` | 零本次发布 |
| 同键异义 | `幂等冲突` | 保留首次事实 |
| 外部引用未闭合 | `引用冲突` | 零本次发布 |
| 分配失败 | `资源失败`或`需求已发布待任务绑定` | 按发生阶段分账 |
| 复义、半结构、坏成功载荷、双 owner 不对称 | `内部不一致` | 停止依赖路径 |

不把`内部不一致`包装成普通等待、需求拒绝或学习缺口。
