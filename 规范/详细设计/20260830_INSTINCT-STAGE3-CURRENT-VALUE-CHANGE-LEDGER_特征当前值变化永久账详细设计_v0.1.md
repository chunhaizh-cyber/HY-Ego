# INSTINCT-STAGE3-CURRENT-VALUE-CHANGE-LEDGER 特征当前值变化永久账详细设计 v0.1

日期：2026-08-30

执行期修订：2026-08-30 R3。R2 的墓碑互证已使 S16 清理后永久账读回通过；随后的 S11 暴露本能根恢复提供者仍把“当前值等于冷启动初值且当前状态选择存在”当作恢复门禁，违反 6130 已冻结的当前值权威边界。R3 只修正既有恢复私有验证，不改变公开 ABI、永久账 owner、固定键或安全根定义。

## 1. 目标与完成边界

在现有 `L2状态动态原子发布服务` 和特征实例 owner 内，为真实特征当前值变化增加 v2 永久变化账，并提供按特征实例和 UTC 半开区间读取完整 `0/N` 变化组的公开入口。

本叶解决的唯一问题是：实例状态 / 动态会按 TTL 和数量上限清理，因此后继不能以“当前动态为 0”证明某个完整秒没有发生变化。永久账必须与新当前值、状态、动态共享同一三分区提交 G1，且不成为第二当前值。

本叶不解释主动安全、服务被动维护或其它业务来源，不计算同秒主动安全裁决，不改变 `A/V`，不修改安全根定义。当前生产安全根定义版本 1 保持：值域 `0..I64_MAX`，`L=2,767,011,611,056,432,742`，`H=7,378,697,629,483,820,645`；运行期不自动调节。

## 2. 正式依据与当前代码事实

正式依据：4230 v0.19、6170 v0.7、0050 的当前值唯一权威和同截止完整读回规则。

创建基线：`main == origin/main == 81c3c9f869a699f5c989ee5b6c6a3a83fd291a3c`，index 空。

当前代码已经具备：

1. `发布特征当前值变化与中性记录_v1`，固定三分区参与者为特征、状态、动态；
2. 新当前值、前后状态、当前选择、状态迁移动能和可选动作致变动态的同 G1 发布；
3. `读取特征当前值变化记录_v1` 的按身份历史读回；
4. L1 owner 按来源完整读取全部当前值，以及各参与者首次幂等写入材料读回；
5. 旧式中性实例状态 / 动态具备 TTL 和数量清理；三分区当前值变化入口形成的关系式状态 / 动态具备公开读取兼容，但创建基线的清理内部闭包尚未识别关系式动态，也未把关系式上下文关系纳入退出和物理清理闭包。
6. L1 持久状态完整性检查已经允许 owner 幂等账映射命中墓碑，但 `所有者范围首次记录完整` 仍要求每个首次稳定编码恰命中当前或历史完整事实。状态 / 动态完整物理清理后该局部读取因此返回内部不一致，不能按 1160 第 6 节保留的紧凑幂等账继续证明原规范请求、首次映射和首次 G1。
7. `本能根运行初始化提供者::验证已存在根值记录` 在已有当前值时仍要求值等于冷启动初值，并继续读取中性或 legacy 当前状态选择。合法当前值变化后第一项不成立；当前状态 / 动态按 TTL 清理后第二项也不成立，导致重启不能恢复不变的根身份锚点。

当前缺口：v1 没有永久变化索引；生产调用为 0，只有阶段二专项调用。扫描动态不能形成永久完整性见证。执行期专项进一步证明：若不补齐关系式状态 / 动态清理兼容，`执行中性实例材料清理_v1` 会在枚举关系式动态时返回内部错误，因而不能真实证明永久账独立于可清理材料。

## 3. 复用与版本裁决

1. 不新建 owner、module、工程登记或普通应用成员；永久账物理归属特征实例 owner。
2. v1 DTO、函数和行为保持源码兼容；v1 不写永久账，生产调用必须保持 0。
3. 新生产 ABI 使用专属版本 2。登记完成事实代次是覆盖起点；不得把登记前 v1 历史纳入 v2 完整声明。
4. 继续复用现有三分区事务和单项正式读回；不复制状态 / 动态本体或当前值材料。
5. 账节点、载荷及登记锚点为永久审计事实，不进入实例状态 / 动态清理闭包。
6. 不新增清理 ABI 或第二清理入口。扩展现有状态、动态 owner 的 module-private 物理闭包，使同一清理入口同时识别旧式载荷与三分区关系式记录；旧式记录行为保持不变。
7. 不新增 L1 DTO、公开入口或第二幂等账。只修正仓库私有 `所有者范围首次记录完整`：首次映射对应事实允许恰好一种权威存续形态为当前、历史或物理清理墓碑；墓碑只证明身份、事实种类、owner 分区和首次创建代次，不恢复已删除的完整事实载荷。
8. 冷启动与恢复继续共用现有本能根初始化入口。目标特征实例尚无当前值时仍建立固定首值和初始状态；已有当前值时只验证该当前值在同 G 下完整、活动、属于具名根实例且 I64 值位于 `0..I64_MAX`。状态、动态及当前状态选择不再是根身份恢复前置，也不得从其载荷反推当前值。

## 4. 固定身份与物理键

固定登记写入幂等身份：

```cpp
inline constexpr L1所有者范围写入幂等身份
    L2特征当前值变化账登记写入身份_v2{
        0x4E53'4356'4C45'4432ULL};
```

固定本地键：

```text
0x0203'1301  变化账锚点
0x0203'1302  单次变化账节点
0x0203'1303  单次变化账载荷
```

候选常量在创建工作区零命中。账载荷复用特征 owner 已登记的 U64 组属性类型；载荷来源节点固定为变化账锚点。其它值不得使用该锚点作为来源。

### 5.3 永久账载荷

U64 组物理顺序固定为：

```text
1  合同版本 2
2  特征实例稳定编码
3  旧当前值稳定编码
4  变化UTC纳秒
5  来源存在稳定编码
6  来源方法稳定编码，缺省为 0
7  组合幂等身份
8  特征参与者幂等身份
9  状态参与者幂等身份
10 动态参与者幂等身份
```

账身份、新当前值稳定编码和形成 G1 从首次写入结果与生命周期投影，不存入载荷。账节点必须恰有一项由锚点作为来源的上述 U64 组属性；多值、额外当前属性、错 owner、错来源或错类型均为不闭合。

## 6. 登记算法

1. 验证专属版本、共同头和 G0；执行读前守卫。
2. 读取固定登记幂等首次材料；已有时逐字段验证唯一普通锚点并正式当前读回。
3. 未登记时在特征实例 owner 用固定幂等身份建立一个普通锚点；不建立关系、值或属性槽。
4. 提交后按首次 G1 历史读回、按 Gread 当前读回并执行读后守卫。
5. 提交后读回失败返回 `已可能登记`；相同请求重试精确收束。

## 7. v2 原子发布算法

1. 验证 v2 请求；读取账登记，未登记返回材料不足。
2. 执行与 v1 相同的 G0、旧当前值、主体 / 场景 / 来源和可选方法读回。
3. 新旧材料相等时返回 `无变化`，零账、零三分区写。
4. 形成特征参与者时，在原新当前值写集之外增加：变化账普通节点、十字段 U64 载荷和账节点属性槽；载荷来源固定为账锚点。
5. 状态和动态参与者完全复用 v1；按固定顺序提交三分区事务。
6. 从参与者 1 映射取得新当前值和账身份，从账节点 / 载荷取得 G1；三个参与者首次写入均必须为同一 G1。
7. 复用 v1 单项读回验证当前值、状态和动态，再独立验证账事实逐字段绑定请求。
8. 提交后任一读回失败返回 `已可能发布`；原 v2 完整请求原键重放。

## 7.1 关系式状态 / 动态清理兼容

1. 动态 owner 的当前枚举先按族索引取得候选。旧式 `8+` 字段动态载荷继续走现有解码；关系式 `4` 字段载荷必须读取同截止动态上下文关系，验证角色 `1/2/3/4/5/9` 完整，动作致变额外要求 `6/8` 同时存在，并以角色 `4/5` 恢复有序前后状态成员。
2. 动态物理闭包增加关系式上下文关系身份组。逻辑退出与物理清理必须覆盖节点、族索引、载荷值及全部上下文关系；旧式动态的上下文关系组为空，行为不变。
3. 状态 owner 继续复用现有状态载荷解码，但枚举闭包必须识别三分区状态上下文关系。关系式状态要求同截止角色 `1/2/3/4` 各恰一项；其逻辑退出与物理清理覆盖节点、族索引、载荷值及四项上下文关系。旧式状态没有该组时保持现有闭包。
4. 当前选择关系仍由现有状态清理阶段独立退出，不合并进状态本体闭包。任何上下文缺项、多义、错 owner、错源、错类型、已退出边界冲突或载荷 / 类别不一致均按现行结构化不闭合 / 内部错误失败，不得忽略孤儿关系。
5. 清理完成后，专项必须以 v2 返回的具名动态 / 状态身份核对墓碑，并在新的正式截止重新读取三项永久账；永久账锚点、账节点、账载荷和当前特征值均不得进入清理请求。
6. 清理前后使用相同状态 / 动态参与者幂等身份读取首次写入材料。每项首次映射必须恰命中当前、历史或墓碑之一；墓碑须与首次写集中本地键对应的节点 / 关系 / 值种类一致，内部结构分区等于该 owner，创建事实代次等于首次 G1，且清理代次不晚于本次读取截止。命中 0 项、命中多种形态、种类 / owner / G1 错配均为内部不一致。成功仍返回紧凑幂等账保存的原规范化写集和原首次结果，不从墓碑重建业务载荷。

## 8. 完整组读取算法

1. 验证合同、G0、非零特征、`0 < 起始 < 结束 <= I64_MAX` 和非零数量预算。
2. G0 读前守卫；验证特征实例在 G0 当前且未退出。
3. 读取账登记；未登记返回 `账未登记`。
4. 调用 L1 owner 按来源完整读取全部当前值，来源固定为账锚点。
5. 每个来源值必须唯一落在一个当前普通账节点上，且节点恰有这一项账属性。逐项解码十字段载荷。
6. 通过特征参与者首次写入结果恢复新当前值身份和账身份；通过状态 / 动态参与者首次写入结果证明同一 G1 和完整三参与者提交。状态 / 动态已清理时，该首次材料读取只由原紧凑幂等账和逐项匹配墓碑继续成立，不要求完整事实仍在当前 / 历史表。
7. 任何锚点来源坏载荷、孤儿节点、额外属性、重复身份、同特征同 G1 多项或幂等材料错配均返回 `集合不闭合`，不得忽略。
8. 筛选特征和 UTC 半开区间；排序、去重、数量预算和见证。
9. G0 读后守卫后返回。全部非成功空组、空见证、截止 0。

## 8.1 本能根跨进程恢复兼容

1. 新进程仍通过两组固定业务幂等身份恢复根定义、特征实例、目标合同、根需求与列表项，并最终形成同截止值式 `本能根运行锚点_v1`；不持久化或扫描第二角色索引。
2. 若根特征实例没有当前值，沿现有冷启动分支建立 `I64_MAX/2` 首值和初始状态，零动态；该首次形成合同不变。
3. 若已有当前值，`验证已存在根值记录` 只验证 `L2特征值事实截止投影完整`、生命周期当前、特征实例一致、材料为 I64 且位于 `0..I64_MAX`。来源可以是后继正式变化的来源存在或方法，不再强制等于根定义身份。
4. 恢复不得要求当前值等于冷启动初值，不得要求任一当前状态选择、状态或动态仍保留。状态 / 动态仍可供审计与解释，但其缺失或墓碑化不改变根当前值和根角色身份恢复。
5. 最终读回继续在一个 Gfinal 下复核唯一自我、定义、实例、当前值、比较注册、目标合同、需求和列表项；任一当前值坏类型、越界、退出、错实例或同截止漂移仍结构化失败。

## 9. 失败映射

| 事实 | 结果 |
| --- | --- |
| 坏合同、零 G0、坏范围、零预算 | 入口拒绝 |
| 登记不存在 | 账未登记 / 写入口材料不足 |
| 读前或读后代次变化 | 当前性漂移 |
| L1 许可拒绝 | 许可拒绝（写）或内部错误（只读现行矩阵） |
| 同键异请求 | 幂等冲突 |
| 特征、旧值、主体、场景或来源不一致 | 引用冲突 / 材料不足 |
| 完整成员数超过预算 | 数量预算不足 |
| 锚点来源坏项、重复、首次映射墓碑错配或三参与者不同 G1 | 集合不闭合 |
| bad_alloc、length_error、L1资源失败 | 资源失败 |
| 未分类异常 | 内部错误；提交后为已可能发布 |
