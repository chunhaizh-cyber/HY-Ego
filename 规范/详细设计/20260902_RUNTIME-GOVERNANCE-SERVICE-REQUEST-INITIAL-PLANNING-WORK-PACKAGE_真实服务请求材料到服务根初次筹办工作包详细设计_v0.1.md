# RUNTIME-GOVERNANCE-SERVICE-REQUEST-INITIAL-PLANNING-WORK-PACKAGE 真实服务请求材料到服务根初次筹办工作包详细设计 v0.1

## 1. 目标与完成边界

本设计闭合一条最早生产链：已发布来源存在 `E` 携带的不可变材料 `M`，经同一 `G0` 强类型互证后，驱动服务根治理任务 `T` 的建立 / 唤醒 / 精确复用，形成初次筹办工作包，并通过 P01 已发布的唯一任务工作线程、结果消息和管理端结果提交端口完成一次筹办处理。

```text
E + M + D_service + 幂等键
  -> G0 读取并互证
  -> task owner 建立/唤醒/复用服务根治理任务 T
  -> T、当前任务轮次 R、初次筹办记录和 M 绑定
  -> 初次筹办工作包
  -> P01 同一工作线程（来源判别联合）
  -> 一个 provider 调用、一个结果消息、管理端已接收/精确重复
```

本叶完成仅表示上述进程内工作包消息闭环在正常收口下可调用；不表示目标达成、路径验证、方法动作、需求满足、需求结算、价值回流、安全值 / 服务值、学习或跨进程 exactly-once 已完成。

## 3. 不变式与禁止项

1. `E` 必须是 `L2存在身份`；`M` 必须是 `不可变材料身份`。材料服务读回的 `来源节点` 与 E 的稳定值相等，并由 L2 存在服务独立读回 E；非零编码、路径、摘要、日志或缓存不足以通过。
2. `D_service` 只能来自已发布 `本能根运行锚点_v1.服务根需求`。请求可携带该身份用于完整请求相等比较，但 provider 必须与锚点和 L2 需求正式读回逐项相等；调用方不能选择其它需求。
3. 材料内容在本叶不解析，不从文本推导对象、目标、权限、方法、成功或结果。M 仅作服务根治理任务的输入材料和后续 fresh 重判依据。
4. 不建立服务合同、请求账、来源 registry、真实性 provider、游标、Gseed、第二任务 / 需求 / 结果事实或独立 outbox。
5. 一个幂等键同时作为外层服务请求适配键与 task owner 初次准备记录键；同键同完整请求返回首次记录和同一工作包，异义冲突零写。
6. 已存在不同请求的当前服务根任务时不覆盖、不新建第二任务；返回`已有当前任务`，不生成初次工作包。只有已有初次记录的精确重复才返回原工作包。
7. 初次工作包与后继工作包在 P01 线程中共享容量、锁、结果消息和结果提交端口，但来源使用强类型判别联合。禁止将初次工作包转换为 `下一筹办工作包` 或填充虚假路径 / 旧重筹办意图。
8. 任何拒绝、漂移、引用冲突、资源失败、内部不一致和发布未知均不写半结构；发布未知只能用原幂等键和原完整请求读回收敛。

### 4.3 初次来源判别联合

在既有 `海中鱼巣/线程/协议.任务筹办工作与结果.ixx` 中新增协议版本 2 的值式来源：

```cpp

struct 任务筹办初次来源 final { 任务初次筹办工作包 工作包; };

```

`任务筹办工作包消息`改为携带该联合，并增加来源分支与完整性守卫；身份、任务、任务轮次、G0、消息幂等和结果载荷规则保持 P01 v1 语义。管理端以消息身份 + 完整来源联合做精确重复 / 异义冲突比较；初次来源不得被解码为后继来源。

## 5. 业务 provider 与调用顺序

新模块 `海中鱼巣/领域/内部治理/服务.服务请求初次筹办.ixx` 导出唯一业务入口：

```cpp
服务请求初次筹办结果 形成服务请求初次筹办工作包(
    const 服务请求初次筹办请求& 请求) noexcept;
```

provider 构造依赖：`本能根运行锚点_v1`（只读）、`L2存在结构服务`、`不可变材料服务`、`L2需求结构服务`、`L2任务结构服务`、`任务管理线程` 的初次工作包提交端口。调用顺序固定：

1. 校验合同、非零身份、锚点完整性和 D_service 等于锚点服务根需求；失败入口拒绝，零写。
2. 在 `请求头.期望事实代次 = G0` 读取 E 当前存在事实；E 缺失、退出、代次漂移或 owner / 身份冲突返回具名非成功。
3. 在同一 G0 读取 M 当前不可变材料事实；M 缺失、退出、格式 / 身份不完整或 `材料.来源节点 != E.值` 返回`来源材料不匹配`，不得只按编码放行。
4. 在同一 G0 读取服务根 D 当前需求事实和锚点；D 不匹配、退出或当前性漂移返回`服务根不匹配` / `当前性漂移`。
5. 先调用 task owner `按初次筹办准备幂等身份读取首次记录`。已有记录逐字段比较本请求的 E/M/D 扩展来源与旧完整请求；同义返回原记录 / 原工作包，异义返回幂等冲突。不得先重新裁决或刷新 G0。
6. 无记录时把 E、M、D 和原请求作为扩展来源材料交给 task owner 的既有 `新增任务与首次初次筹办准备记录` 原子入口。任务 owner 在同一 G1 建立 / 唤醒 / 复用服务根治理任务、R1、初次准备记录和来源绑定；不得建立请求账。
7. task owner 发布后独立读回任务、任务身份来源、初次准备记录和工作包；形成 `任务筹办初次来源` 消息，并通过管理端注册的初次工作包入口交给同一任务工作线程。
8. 仅在管理端确认初次工作包`已接收`或`精确重复`后返回`已形成` / `精确重复`。队列满返回资源等待并由调用方重提同一消息；provider 不重复创建任务或记录。

“唤醒 / 复用”只允许复用同一服务根治理任务及其当前轮次；若现有任务来源不同且没有同义初次记录，返回`已有当前任务`，由后继治理循环 fresh 重判，不自动吞并请求。

## 6. P01 线程与管理端接线

### 6.1 工作线程

保持一个 `任务工作线程`、一个有界队列和现有任务结果尾部。队列项变为：

```cpp
using 任务工作线程队列项 = std::variant<
    任务工作结果材料, 任务筹办工作包消息>;
```

处理筹办消息时按来源联合分派：后继来源调用现有 `推进下一筹办工作包`；初次来源调用同一 provider 类新增的 `推进初次筹办工作包`，输入为 `任务初次筹办工作包`，不得构造 `下一筹办工作包`。两者都规范化为既有五类 `任务筹办推进结果`，调用计数每个工作包恰好一次。

### 6.2 管理线程与运行包

管理线程新增 `提交初次筹办工作包` 入口，先登记来源联合工作槽（等待结果消息），再调用已绑定的工作包提交端口；结果端继续复用 P01 `提交任务筹办结果`，按消息身份 + 完整来源联合幂等接收、独立读回和后继编排。运行包新增同名薄转发，不保存第二队列或 outbox。

初次来源结果的独立读回与后继来源相同：任务、轮次、筹办轮次、来源材料、选择 / 路径 / 等待 / 目标裁决分支逐项回读；消息载荷不能替代正式事实。目标已完成不写任务完成，合法等待不自动新筹办。

### 6.3 普通应用与自我线程

普通应用只装配一个服务请求 provider、既有材料 / 存在 / 需求 / 任务服务和 P01 运行包；自我线程或外部接收入口只提交 `服务请求初次筹办请求`，不得裸写 task owner 或 worker。服务根锚点由根初始化正式读回提供，禁止硬编码 D 或在进程缓存中当权威。

## 7. 事务、幂等与失败收口

### 7.1 G0/G1 与写集

- G0 只由 L2 中性当前代次读取确定；E、M、D 和任务前置均在 G0 互证。
- task owner G1 写集包含任务（新建时）、任务虚拟存在（新建时）、R1、初次准备记录及其 E/M/D 来源扩展材料；同一 owner 原子提交并独立读回。
- 发布前任何闭包、来源、D、当前任务或关系冲突均整笔零写、不推进代次、不写幂等账。
- 发布后独立读回失败返回`已可能发布`或`内部不一致`；不得声称回滚。调用方只能以原幂等键 + 原完整请求重放并读回收敛。

### 7.2 分支矩阵

| 条件 | 状态 | 写入 | 重试 |
| --- | --- | --- | --- |
| 首次互证和 task owner 原子成功、消息已接收 | 已形成 | 一次 | 原键精确重复 |
| 同键同完整请求且记录 / 工作包读回 | 精确重复 | 零新增 | 返回原结果 |
| 同键异请求 | 幂等冲突 | 零写 | 必须换合法请求身份 |
| 现有不同当前任务 | 已有当前任务 | 零写 | fresh 重判，不自动建包 |
| E/M 来源不匹配、D 非服务根 | 引用冲突 / 服务根不匹配 | 零写 | 修正输入 |
| G0 漂移 | 当前性漂移 | 零写 | 重新取 G0 后重发原业务意图 |
| 队列满 | 资源失败/资源等待 | 任务事实不重复写 | 重投同一消息 |
| 发布后读回未知 | 已可能发布 | 不声称零写 | 原键原请求读回收敛 |
| 消息协议拒绝、同键异义、管理端停止 | 内部不一致 | 不补写 | 运行包收口失败 |
