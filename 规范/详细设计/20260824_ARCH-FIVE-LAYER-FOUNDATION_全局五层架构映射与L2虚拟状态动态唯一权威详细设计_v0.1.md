# ARCH-FIVE-LAYER-FOUNDATION 全局五层架构映射与 L2 虚拟存在、状态、动态唯一权威详细设计

版本：v0.1
状态：设计候选，未取得代码实施许可
基线：`main@efc91db91814ed882f8853fcfafbdcafa1822bf6`
计划身份：`ARCH-FIVE-LAYER-FOUNDATION`

## 1. 目标与边界

本设计把全局架构命名空间 `ARCH-L1`—`ARCH-L5` 正式映射到现行 `DATA-L1`—`DATA-L3`，并冻结第一份可施工提供者的机器合同。两套层级不是同一枚举，也不能互相替换：`DATA` 描述基础数据服务实现，`ARCH` 描述全局结构与业务职责。

本叶只覆盖最早提供者：

```text
通用虚拟存在结构
    + 通用状态结构唯一 owner
    + 通用动态结构唯一 owner
    + 状态迁移及动态整理的同代原子发布
    + 正式当前/历史读回
```

不实现世界树或概念空间聚合、需求/任务/方法业务编排、任务完成/需求满足、自然语言名称、学习、结算、价值回流、自我线程或真实消费者接线。交接的任务来源需求三件套仍归 `ARCH-L4` 业务迁移输入，不在本叶提前施工。

## 2. ARCH 五层与 DATA 三层映射

| 全局命名空间 | 责任 | 现行 DATA 映射 | 兼容边界 |
| --- | --- | --- | --- |
| `ARCH-L1` | 统一事实内核：节点、关系、值、事实代次、owner、事务和恢复证据 | 对应 `DATA-L1` | 现有 L1 ABI 保留；不得让 L1 识别 ARCH 业务族 |
| `ARCH-L2` | 场景、存在、特征、状态、动态、因果、二次至 n 次特征及语言/名称承载所需通用结构；现实与虚拟调用者一视同仁 | 对应 `DATA-L2` | 现有六类世界、语言、概念结构服务是兼容实现；本叶新增通用虚拟存在结构 |
| `ARCH-L3` | 世界树、概念树/概念空间等聚合 | 对应 `DATA-L3` | 只能编排 L2 公开 CRUD，不持第二权威、不直达 L1 |
| `ARCH-L4` | 需求、任务、方法及其路径、实例、冻结、结果、轮次、结算等业务治理 | 不对应 `DATA-L4`；现行 L2 需求/任务/方法模块是兼容 ABI | 业务 owner 可保存业务关系，但虚拟存在、状态、动态必须复用 ARCH-L2 |
| `ARCH-L5` | 自然语言理解/表达、词条/名称/别名/定义绑定裁决 | 不对应 `DATA-L5` | 机器身份和类型由下层 owner 发布；L5 只能经公开服务提交绑定请求 |

依赖固定为 `ARCH-L5 -> ARCH-L4/ARCH-L3/ARCH-L2 -> ARCH-L1`，禁止反向依赖。概念身份语言无关；概念基础结构在 L2，概念空间聚合在 L3，名称关系在 L5。二次至 n 次特征复用同一特征身份、真实阶次、直接来源和适用范围，不按阶次建立新服务层。

## 3. 当前代码事实与迁移裁决

### 3.1 已存在且可复用

- `领域/L2存在结构.数据.h` 与 `服务.L2存在结构.ixx` 已提供存在身份、单例角色、完整当前/历史读取和场景成员引用。
- `领域/L2状态结构.数据.h` 与 `服务.L2状态结构.ixx` 已提供状态身份、状态合同、状态新增、当前/历史读取、值换代、引用替换和退出；其 owner 交付绑定一个 L1 写端口。
- `领域/L2动态结构.数据.h` 与 `服务.L2动态结构.ixx` 已提供动态新增、当前/历史读取、时间值换代、引用替换和退出；动态端点当前只接受 `variant<L2存在身份,L2状态身份>`。
- `装配.普通应用.ixx` 已持有状态/动态服务及其 owner 交付，未提供通用虚拟存在服务。

### 3.2 已确认的偏差

- `L2任务结构.数据.h` / `服务.L2任务结构.ixx` 自有 `L2任务虚拟存在身份`、任务治理状态身份、状态关系和迁移证据，形成任务 owner 的第二状态权威。
- `服务.L2方法结构.ixx` 自有方法治理虚拟存在和方法 owner 治理状态；它不是世界存在，也不能继续被解释为 DATA-L2 业务状态权威。
- 目标未达成链路仍由任务服务直接写治理状态，没有统一调用通用状态/动态唯一 owner。
- 动态 DTO 对虚拟存在作为主体/来源的承载方式尚未冻结；不能由执行者临场扩展 `variant` 或跨 owner 写集。
- 4230 与当前 L1 端口只允许 owner-scoped 写入，状态节点、动态节点及跨 owner 关系目前没有已证实的统一原子写入口。

### 3.3 迁移原则

旧任务/方法身份、字段和 C++ 文件名在迁移完成前保留为兼容身份；不机械改名、不复用其私有状态作为新权威。任务/方法 owner 只发布业务关系和引用，通用虚拟存在、状态、动态由 ARCH-L2 owner 读写。旧私有状态必须在有真实替代消费者和历史保留证据后由独立清理计划退出。

## 4. 第一份提供者合同

### 4.1 通用虚拟存在

建议新增结构族 `L2通用虚拟存在`（正式名称、类型身份和 ABI 在执行前按本节冻结，不得以任务/方法专名复用）。其强类型事实至少包含：

```cpp
struct L2通用虚拟存在事实 final {
    L2通用虚拟存在身份 身份;
    L2虚拟存在 owner类别;             // 业务 owner 的不透明强类型类别
    L2结构引用 业务宿主;               // 任务、方法或后继 ARCH-L4 对象
    L2生命周期 生命周期;
    std::uint64_t 建立事实代次;
};
```

公开入口由唯一 `L2通用虚拟存在结构服务` 持有，物理 DTO 位于 `领域/L2通用虚拟存在结构.数据.h`，服务位于 `领域/服务.L2通用虚拟存在结构.ixx`。入口集合为：新增、当前/历史完整读取、退出；请求必须携带非零期望事实代次、稳定幂等身份和强类型业务宿主引用。虚拟存在不进入现实世界场景树、不承载名称、不产生业务状态结论。

### 4.2 状态/动态唯一权威

现有 `L2状态结构服务` 与 `L2动态结构服务` 继续分别拥有状态、动态节点族及其结构身份来源。新增合同不新增第二状态服务或第二动态服务：

- 所有现实与虚拟主体均以公开强类型引用接入；调用者类别不改变结构 owner。
- 任务/方法私有治理状态改为迁移兼容来源，不能被当前读取解释为 ARCH-L2 当前状态。
- 动态的主体、前状态、后状态引用必须在同一截止完成强类型端点回读。若虚拟存在需成为动态主体，执行前必须在 DTO 合同中选择“扩展动态引用联合”或“通过通用状态/存在桥引用”，不得临场选择。

### 4.3 原子状态迁移写集

一次状态迁移只能由一个公开 ARCH-L2 迁移 provider 发起，写集必须在同一事实事务中闭合：

1. 旧当前状态退出；
2. 新状态节点及主体/特征端点关系建立；
3. 当前状态关系切换；
4. 前后状态关系、来源方法关系和共同事实截止建立；
5. 动态节点及动态主体、前状态、后状态关系建立；
6. 动态时间/来源值建立；
7. 全部写集的幂等见证和迁移证据建立；
8. 原子发布后按同一截止逐项读回全部写集。

现有状态 owner、动态 owner 与 L1 owner 端口不能安全承载跨 owner 写集时，必须扩展 `ARCH-L1/DATA-L1` 中性多参与者事务合同或明确重组选定 owner；计划已冻结此门禁，执行者不得任选跨 owner 写法。任一参与者拒绝、代次漂移、幂等冲突、端点不完整或读回不一致时零发布；发布未知只用原幂等身份和完整首次写集见证收敛。

## 5. 公开结果与错误分账

成功结果必须返回不可变完整 DTO、唯一非零事实截止和（写操作）变更事实代次；当前/历史读取不可返回可变仓库对象。结构化非成功沿用 4230：入口拒绝、许可拒绝、未找到、已退出、事实代次漂移、幂等冲突、资源失败、内部不一致。非成功零载荷、零变化；坏形状（非成功带载荷/截止、成功缺载荷/截止）映射为内部不一致。

本叶不定义业务结果“任务完成、目标达成、方法成功、需求满足”。数据 owner 只校验字段、关系、基数、生命周期、引用、期望代次、幂等和事务。

## 6. 装配与物理白名单

计划允许执行者修改的生产文件仅为：

```text
海中鱼巣/核心/仓库.L1事实基座.ixx
海中鱼巣/核心/服务.L1事实基座.ixx
海中鱼巣/领域/L2通用虚拟存在结构.数据.h       (新增)
海中鱼巣/领域/服务.L2通用虚拟存在结构.ixx       (新增)
海中鱼巣/领域/L2状态结构.数据.h
海中鱼巣/领域/服务.L2状态结构.ixx
海中鱼巣/领域/L2动态结构.数据.h
海中鱼巣/领域/服务.L2动态结构.ixx
海中鱼巣/装配.普通应用.ixx
海中鱼巣.vcxproj
海中鱼巣.vcxproj.filters
```

`L2任务结构.*`、`L2方法结构.*` 仅在直接接线需要且由后继业务计划授权时修改；本叶默认不改它们，避免把 ARCH-L4 消费者夹入提供者施工。专属施工记录和验证记录各一份，路径在计划正文冻结。`.codex-build`、验证工具、知识库、流程图代码目录和计划索引不属于代码白名单。

普通应用只持有一套 L1 运行包、一套通用虚拟存在服务、一套状态服务和一套动态服务；所有 ARCH-L4 provider 通过 const/non-const 同实例 getter 取得它们。不得在任务、方法或线程内部构造第二 provider。

## 7. 验证矩阵与边界

执行后必须覆盖：

| 维度 | 证据 |
| --- | --- |
| 通用虚拟存在 | 新增、精确重复、同键异义、当前/历史读取、退出、引用保护、权威逐字段读回 |
| 状态/动态 | 现有成功/漂移/许可拒绝/资源失败回归、状态与动态端点同截止验证 |
| 原子迁移 | 旧当前退出、新当前建立、关系切换、动态和来源关系全写集同代发布；任一失败零变化 |
| 并发 | 同义幂等、异义冲突、期望代次漂移、跨 owner 拒绝、发布未知收敛 |
| 架构 | 任务/方法私有状态不再生成当前第二权威；虚拟存在不进入世界树；L3/L4/L5 无反向调用 |
| 工程 | 根工程 Debug/Release、`D:\TEMP` 隔离专项、strict、diff-check、生产目标无专项痕迹 |

未证明边界：任务/方法业务迁移、目标裁决消费者、世界树/概念空间聚合、L5 名称绑定、自我线程、跨进程恢复和真实 ARCH-L4/L5 合法消费者累计证明。

## 8. 设计结论

本设计冻结了 ARCH 命名空间和最早提供者的机器合同，但当前代码尚未实现通用虚拟存在或跨 owner 原子迁移。只有本设计与代码计划正式发布、取得真实 plan blob 并由执行侧完成验证后，才能把该叶登记为可执行；文档本身不证明 ARCH 五层或 L2 provider 已实现。
