# RUNTIME-GOVERNANCE-TASK-RESULT-CONSUMPTION-ALLOCATION 任务结果消费关系与争用分配详细设计 v0.1

日期：2026-08-23
版本：v0.1

## 1. 裁决结论

本叶把第四层缺失合同闭合为一个不可拆的公开结果：

```text
正式成员分配优先级证据形成
+ 任务结果消费关系裁决
+ 争用结果逐成员分配与立即扣减
+ 同一事务发布关系、顺序、逐项结果和最终剩余
+ 按幂等身份、记录身份的当前 / 历史独立读回
```

三项使用同一 task owner、同一公开请求、同一成员集合与规则版本、同一生产文件、同一原子写集和同一验证矩阵，因此不得拆成“先优先级、再关系、再扣减”三份可执行计划。拆开会产生未绑定正式结果的游离优先级账、先排序后猜关系或关系已发布但剩余尚未扣减的半状态。

本设计只形成第四层 provider。它不裁决任务是否完成，不进入逐需求目标满足，不创建 5160 正式结算，不写价值、预算或归因，也不激活旧 `BIZ-L2-004-06`。第四层入口直接服从 5090 §5.2、5160 §4 和现行分层详细设计 §7 的完整输入合同；现行路线表中“已完成任务”只约束未来合法生产调用顺序，不在当前尚无任务完成事实时伪造一个 ABI 字段。本叶保持生产零接线，后继集成必须在任务生命周期 owner 已形成完成事实后再接合法消费者。

## 2. 目标、范围与完成条件

目标闭环：

```text
按 G0 独立读回正式任务实际结果及来源需求列表项当前成员组
-> 互证调用方冻结成员集合与每成员目标、消费资格
-> 复核结果容量 / 范围 / 所有权 / 有效性合同及关系规则版本
-> 可重复引用且四维都不扣减：形成可共用关系和逐成员结果引用，不读取优先级
-> 存在任一扣减维度：要求完整正式优先级证据和同级顺序
-> 按优先级序号、同级顺序序号逐成员复核并分配
-> 每项写入分配前剩余、实际分配、分配后剩余并立即更新事务内剩余
-> task owner 一次提交完整不可变记录
-> 以同一发布 G1 独立读回
```

完成必须同时成立：

1. 正式结果、列表项、成员集合、目标合同和成员关系全部来自同一 G0 权威读回；
2. 冻结成员集合版本固定等于 G0，成员身份采用规范化升序仅用于集合互证，不代表分配优先级；
3. 结果合同显式给出消费形态、初始可用单位、扣减维度、范围合同、所有权合同、有效性合同及版本；
4. v1 只接受成员消费合同与结果三个合同身份精确相等；需要范围包含、所有权转换或有效期换算时具名返回合同不支持，不猜测兼容；
5. `可重复引用`要求扣减维度为空，不建立优先级队列；成员优先级材料必须为空；
6. `可分割单位`或`不可分割资格`至少有一个扣减维度，必须为每个成员提供且只提供一份正式优先级证据；
7. 优先级证据明确绑定正式结果、需求、成员集合版本、来源规则身份、优先级规则版本和同级规则版本；
8. 排序只按较小的`优先级序号`优先、同级时较小的`同级顺序序号`优先；两个序号均是具名正式规则的输出，不从其它数值计算；
9. 每个争用成员用`最低合法分配单位`和`期望分配单位`裁决：剩余达到期望则分配期望；不足期望但不低于最低则分配剩余；低于最低则不分配；
10. 不可分割资格固定初始可用单位为 1、成员最低和期望均为 1；首次合法分配后剩余为 0；
11. 每个分配步骤保存分配前、实际分配和分配后剩余，后一步的分配前必须等于前一步的分配后；
12. 关系、正式优先级证据、逐项引用 / 分配和最终剩余在一个不可分割写集中发布，不存在部分成功；
13. 同一幂等身份同一完整请求精确恢复；同键异义冲突；同一裁决元组换键冲突，不能形成第二分配账；
14. 发布结果未知只允许用原完整请求和原键恢复；不得换键、刷新 G0 或按最新成员集合重放；
15. 按记录身份和幂等身份均可读回，历史读取显式指定截止；读回坏形状不得补成成功；
16. 实现者不需要再决定 DTO、函数、物理位置、事务顺序、错误映射或验证标准。

## 3. 明确排除项

- 不修改现有 `L2任务实际结果事实`，不把可共用 / 争用固化成结果永久属性；
- 不读取或复用任务执行优先级、治理消息优先级、队列顺序、需求权重、预算、创建时间或稳定编码作为成员分配顺序；
- 不计算需求目标是否满足，不发布 5160 结算记录；
- 不形成价值、预算、归因、安全值或服务值变化；
- 不让列表项聚合键替代单需求身份；
- 不在可共用路径建立优先级证据或剩余账；
- 不支持非零初始已分配账；v1 新裁决记录只能从零分配开始，既有记录必须按原键恢复；

- 不接自我线程、任务管理线程、运行包或旧 004-06；
- 不修改共享知识库、能力证据目录或代码流程图；

## 5. owner 与物理边界

### 5.1 合并裁决

最终业务 owner 为 `任务结果消费关系与争用分配提供者`。它拥有：

- 正式成员分配优先级输入完整性与证据形成；
- 可共用 / 争用关系裁决；
- 争用顺序、逐项分配和事务内立即扣减；
- 业务状态映射与发布未知恢复；
- 对 DATA-L2 记录服务返回结果的业务互证。

DATA-L2 只拥有强类型记录结构、引用互证、CAS、幂等、原子写集和当前 / 历史投影；它不得决定哪一业务优先级更高、结果是否满足需求或后继是否可以结算。

两层必须在一份计划闭合，因为公开 provider 的第一次成功必须同时取得 DATA-L2 原子记录及读回；单独发布任一层都不是可用代码结果。

扣减维度组必须按枚举值严格升序且无重复；它只声明哪个正式合同维度会因消费减少，不是优先级。范围、所有权、有效性合同身份必须在结果和每成员材料中精确相等；v1 不做隐式换算。

### 6.2 完整记录与请求

### 7.2 恢复优先

入口先校验纯值形状，再按幂等身份读取既有记录：

- 存在且完整请求逐项相等：按原记录和原发布截止独立读回，返回精确重复；
- 存在但任一字段不同：`幂等冲突`，零写；
- 不存在：才按请求 G0 读取正式结果和成员事实。

同一裁决元组定义为：

```text
正式结果
+ 来源列表项
+ 成员集合版本
+ 容量合同身份 / 版本
+ 消费关系规则版本
+ 优先级规则版本 / 同级规则版本
+ G0
```

task owner 对该元组反查全局 0..1 条记录。同元组换键返回引用冲突，不建立第二分配账。

### 7.3 可共用算法

仅当：

```text
消费形态 = 可重复引用
扣减维度组为空
初始可用单位 = 0
每成员最低 / 期望单位 = 0
正式优先级组为空
```

才形成`可共用`。provider 按规范化成员身份逐项形成`已形成共同引用`，`处理顺序`只用于结果数组稳定输出且不具有业务优先级；各项三个剩余字段为 0。后继逐需求满足必须自行读取每个需求，不能把本记录的共同引用当成满足结论。

### 7.4 正式优先级证据

争用路径要求正式优先级组与冻结成员组一一对应，并且全部绑定同一正式结果、成员集合版本、来源规则身份、优先级规则版本和同级规则版本。`优先级序号`和`同级顺序序号`均非零；同一优先级内同级顺序序号全局唯一。

provider 不读取任何现有优先级字段，不计算加权分数。它只把具名规则已经给出的序号形成强类型正式证据并绑定本次完整裁决。来源规则身份或任一版本缺失、成员漏项 / 多项、同级序号重复、证据绑定错误均为`优先级合同缺失`或`优先级冲突`，关系、证据和分配全部零写。

### 7.5 争用分配与立即扣减

排序键唯一为：

```text
(优先级序号升序, 同级顺序序号升序)
```

`剩余`初始化为容量合同初始可用单位。逐项：

1. 重新互证该成员仍在 G0 冻结集合、需求目标合同相等、资格证据和三个消费合同身份完整；
2. 若剩余为 0，形成`结果已耗尽`，前后剩余均为 0；
3. 若剩余小于最低合法单位，形成`未获分配`，实际分配 0，剩余不变；
4. 否则实际分配为`min(期望分配单位, 剩余)`；
5. 在形成下一成员前立即执行`剩余 -= 实际分配单位`；
6. 记录分配前、实际分配、分配后剩余。

任一加减溢出、顺序断链、资格互证失败、当前性漂移或坏成功形状都终止整个事务且零写。最终允许成功记录同时含`已分配`、`未获分配`和`结果已耗尽`；这些成员状态不改变顶层事务成功，也不是需求未满足或任务失败。若没有任何成员取得分配且最终剩余为 0，顶层可映射`结果耗尽`并仍携带完整成功记录；否则业务成功状态为`已形成争用分配`或精确重复。

## 8. DATA-L2 原子写集与读回

task owner 在现有任务 owner 私有互斥体下：

1. 按幂等身份恢复首次规范化请求；
2. 核对全局当前事实代次仍为 G0；
3. 按裁决元组反查 0..1 条既有记录；
4. 验证正式结果存在且任务 / 列表项引用一致；
5. 提交一个 L1 所有者范围写集：一个记录节点、结果 / 任务 / 列表项 / 成员关系、合同与规则版本值、完整冻结材料、优先级证据、逐项分配链、初始 / 最终剩余、幂等身份和完整请求摘要；
6. 以 G1 读回记录；任何必需关系、字段、成员、证据或分配步骤缺失均为内部不一致。

记录不可变，不建立“当前分配余额”第二可变槽。所谓立即扣减是同一事务候选内每一合法分配后更新唯一局部剩余，并把完整步骤链一次发布；不是先发布分配、稍后另写余额。这样并发者只能看到提交前无记录或提交后完整记录。

当前读取以当前事实截止返回不可变记录；历史读取要求显式历史截止不晚于请求 G，并重建在该截止已经存在的完整记录。按幂等身份读回用于发布未知恢复，不接受新的合同或成员材料。

## 11. DRIFT 与停工条件

只在以下情况退回计划支撑：

- 当前结果独立读回不能在同一 G0 提供正式结果、列表项和完整成员组；
- task owner 无法在一个 L1 所有者范围写集中保存完整步骤链和最终剩余；
- 新记录类型必须取得需求 owner 或其它 owner 的第二写租约才能原子提交；
- 正式规范要求从某个现有优先级字段计算成员顺序；
- 范围、所有权或有效性必须在 v1 做非精确身份换算才可完成目标；
- 同裁决元组全局唯一性无法在现有 task owner 反查中保证；
- 必需验证持续失败且无法在白名单内安全归因。

普通编译错误、格式问题、无关 dirty、一次工具波动和白名单内的机械调整不是设计 DRIFT。
