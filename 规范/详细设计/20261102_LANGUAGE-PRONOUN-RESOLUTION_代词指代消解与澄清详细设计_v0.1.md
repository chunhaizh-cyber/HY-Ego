## 1. 总原则（已确认）

1. **代词概念定义**保持现状，留在**概念空间**（1110／2220）；不按词面另建归类树。
2. **场景中的指代实例与绑定**放在**自然语言场景**内（1110 §2／§3；7230 §4），不写入自我内部世界权威材料作为代词定义。
3. **代词词条不建归类子需求**。不得因代词已有概念名称关系就对「我／你／他／她／它／这／那／谁／什么」等走 LANGUAGE-LEMMA-CLASSIFY。
4. 判定「获取服务对象需求信息」必要条件「必需字段有确定值」时：若字段出现的是**代词**（或完整指代表达中的代词中心），须先完成**指代消解**，落到**自然语言场景中的目标信息节点**（或有界集合的明确成员组）。**仅有名称关系／代词概念定义，不算确定值。**
5. 指代未决时该条件不满足。条件分解提出**指代澄清补问子需求**（例如「你说的『它』是哪个？」），与字段补问子需求、归类子需求**同级**，均为完整需求，经自我确认后进入任务链。
6. **多候选不得取首项**；须澄清或保留未决。
7. 服务对象不回答或离线时：等待，或用其它方法满足该需求——与其它需求相同。

## 2. 三种「场景／上下文」统一说法（已确认）

禁止再混用裸称「交互场景」。正文须按下列三者之一具名：

| 正式名称 | 含义 | 权威落点 |
| --- | --- | --- |
| **自然语言场景** | 自然语言世界树中的场景；承载描述、假设、问题、请求、**指代实例**与解析绑定 | 1110 §3；7230；7240 |
| **调用期交互上下文** | 一次理解／表达调用期内的说话者、受话者、窗口／消息、参考中心、活动指代与待解候选等；可引用自然语言场景，本身不是世界树节点 | 7230 §4.2；ACTION-REQUEST 的 `语言图交互上下文` |
| **现实交互场景** | 现实世界树中的交互窗口场景（如网页对话框场景）；成员、外设事实、输出队列归属于此；**不等于**自然语言场景 | 1150；6120 §11；PERIPHERAL-DIALOGUE-FACTS |

说明：旧文「交互场景」若指对话框窗口，改为**现实交互场景**；若指当次说话者／受话者绑定，改为**调用期交互上下文**；若指语言主张与指代实例所在，改为**自然语言场景**。

## 3. 「确定值」对代词的判定

在 5170 自然语言学习口径「确定值＝词条对应概念信息节点」之上，增加代词例外（不改普通非代词词条规则）：

```text
若字段词条／中心是代词用法：
  已有代词概念定义与名称关系 → 只说明「这是代词」，不足以使字段确定
  须存在可读的指代消解结果：语言出现 → 指代实例 → 强类型目标信息节点（或合法有界成员组）
  目标须经对应公开服务核验可读；失效则视为未决
否则（普通词条）：
  仍按 LANGUAGE-LEMMA-CLASSIFY／5170：经概念名称关系挂到存在／特征／动态根树概念节点
```

代词与普通新词可同时出现在同一字段组：代词走本节消解／澄清；普通新词走归类；缺字段走补问。三者同级，不得互相吞并。

## 4. 指代澄清补问子需求

### 4.1 触发

「获取服务对象需求信息」重读字段时，发现代词出现尚未消解到唯一可读目标（或集合用法未明确成员范围）→ 条件不满足 → 通用筹办提出指代澄清补问子需求。

### 4.2 目标形状（草案，机制待确认点见文末）

与补问／归类同级完整需求。建议形状（**待用户确认后方可冻结为唯一合同**）：

| 槽 | 建议含义 |
| --- | --- |
| 目标存在 | 本次未决的**指代实例**（或该语言出现所关联的指代实例） |
| 目标特征类型 | 「指代已消解」：实例已绑定到可读强类型目标（或合法有界成员组） |
| 目标形式 | 值目标 |
| 目标值域 | 「已消解且目标可读」 |
| 比较关系 | 按既有值目标合同表达「已消解」 |

不得把未决指代写成归类子需求，也不得把待完善被认知需求本身送进任务链。

### 4.3 与条件子需求消息闭环

TASK-SUBDEMAND-MESSAGE-LOOP：在 I64 与「词条归类」之外，是否**另立**第三种平行消息种类「指代澄清」，或并入字段补问种类而只分载荷——**待用户确认**（见 §10）。确认前本设计只要求：闭环步骤同构（提议→self确认→owner建立／复用→任务承接），载荷不得塞进 I64 区间字段，也不得冒充词条归类。

## 5. 新本能：询问指代澄清

写法对齐 DEMAND-FIELD-QUESTION「询问指定需求字段」：想／做分离；产出正式表达需求与候选话语；发送判断后再入列；自我不直接执行本能。

| 项 | 内容 |
| --- | --- |
| 名称 | 询问指代澄清（施工名；正式名若需另定见 §10） |
| 语义输入 | 一个或多个未决指代实例／语言出现；调用期交互上下文（说话者／受询者／现实交互场景窗口／输出队列）五参分账口径同字段询问 |
| 直接产物 | 正式**表达需求**对象；**不是**已入列消息 |
| 问句形状 | 「你说的『它』是哪个？」；可按出现换成『这／那／他／她』等；多个未决可在表达生成阶段合成一句（**不算**自然语言批量合句） |
| 不做 | 不等待回复、不写消解结果、不取候选首项、不入列 |

## 6. 新本能：指代澄清回答写回

| 项 | 内容 |
| --- | --- |
| 名称 | 指代澄清回答写回（施工名；正式名待确认，见 §10） |
| 条件 | 对应澄清子需求有效；回答已解析为对候选／描述的选定或纠正；指代实例仍为当前待写目标 |
| 写入 | 按 1110：更新／发布指代实例的指向（来源实例／出现、作用域、带种类目标引用、采用依据）；目标经公开服务核验可读 |
| 不做 | 不把回答当「X是一种Y」归类写回；不直接改自我内部世界权威以代替消解；不自证父字段已齐全 |

写回成功后，「获取服务对象需求信息」**重读**字段；代词已落到目标信息节点则「确定值」对该出现满足，父方法继续。失败或目标不可读：保持未决，可再次澄清或改用其它方法。

## 7. 入站「帮我…」的「我／你」绑定（已确认方向）

前提：代词概念定义不改；绑定发生在**调用期交互上下文**，实例落在**自然语言场景**。

| 词面 | 绑定 |
| --- | --- |
| **我** | 绑定到调用期交互上下文的**当前说话者**；在获取服务对象需求信息路径上，该说话者即**服务对象** |
| **你** | 绑定到调用期交互上下文的**受话者**（本会话中通常为自我存在） |

缺说话者或受话者上下文时：返回对象待绑定／指代未决，**不**默认取 self、焦点或窗口身份冒充。不得因「我」已有代词概念名称关系就跳过绑定。

**范围说明（待确认，见 §10）**：本条只冻结「帮我…」句式下的代词绑定口径。是否另登记「帮我…」为与「请你满足以下需求：」平行的行动请求根壳／语言证据，**不在本条自行拍板**；未确认前不得宣称该句面已获完整行动请求解释支持。

## 8. 与归类／补问／行动请求的分账

| 路径 | 何时 | 不做什么 |
| --- | --- | --- |
| 指代消解／澄清 | 字段中心为代词且未落到目标 | 不建归类子需求；不靠名称关系充确定值 |
| 词条归类 | 普通新词条无概念节点 | 不对代词词条建归类 |
| 字段补问 | 字段缺值／路径未填 | 不代替消解；不取多候选首项 |
| 行动请求「你」 | 已有 ADDRESSEE 绑定自我 | 与入站「帮我」的「我」说话者绑定分账，不得混成同一角色 |

## 9. 验证边界（规范层）

至少区分：代词有名称关系仍未消解→不确定；消解到场景目标→确定；多候选不取首；澄清问句生成与发送分账；写回后重读；「我」→说话者／服务对象、「你」→受话者；缺上下文不默认；三种场景／上下文用语不混用；与归类／补问并行不互相吞并。

本文件不证明代码、初始化种子或运行闭环已实现。

## 10. 待用户确认（本包不自行拍板）

1. 指代澄清补问子需求的**正式目标形状**是否采纳 §4.2 建议，或另定。
2. TASK-SUBDEMAND-MESSAGE-LOOP 是否**另立**消息种类「指代澄清」，或并入字段补问种类。
3. 询问／写回本能的**正式名称**是否固定为「询问指代澄清」「指代澄清回答写回」。
4. 「帮我…」是否登记为**新的行动请求根壳／语言证据**（本包仅写代词绑定）。
5. 「我」在**服务对象尚未正式确立**时，是否允许仅按调用期说话者绑定，抑或必须先完成获取服务对象。
6. 澄清候选池：仅自然语言场景已提对象，是否包含现实交互场景成员／其它只读范围。
