# 任务状态迁移形成因果详细设计

标识：`TASK-STATE-CAUSAL`；版本：v0.2；日期：2026-11-11；状态：有效（用户 2026-11-11 确认，含第7节拟定项；规范修订同日落文）。

来源：用户 2026-11-11 裁决“任务状态的变化要形成因果信息”，并要求另起设计；只读调研报告（基线 main `6531b46f4`）。

## 1. 用户裁决（2026-11-11）

| 序号 | 裁决 | 替代的旧口径 |

| 2 | 允许内部治理动作，在任务筹办和任务执行的各个迁移处增加 | 0050、4220、4190 规定“动作的唯一来源是执行实例 X，内部治理函数不形成动作动态” |

| 4 | 原因与因素通过任务虚拟存在新增的特征进入任务治理场景，从而成为因果条件 | 场景里现在只有任务状态和服务值 |
| 5 | 性能问题以后再解决 | — |

## 2. 事实基础（调研结论）

1. **现在没有任何任务状态迁移交付因果。**
   - `交付实际发生`（`业务/内部治理.世界.cpp`）只被 `完成任务状态变化` 调用；
   - `完成任务状态变化` 只被 `新_任务类::标记任务已结算` 调用，而 `标记任务已结算` 全仓没有调用者；
   - 实际的 9→12 走贡献阶段的收尾，建了动作，但不交付因果。
2. 写入任务状态的路径有四类，共约 25 个调用点（第 4.1 节）。其中两处绕过迁移表直接写，撤销路径“执行中 → 待查找方法”也不在规范迁移表里。
3. **任务治理场景只放任务自身虚拟存在的状态和动态。**
   - 候选、条件核验、执行实例、影响评估、自我决议、子需求这些原因，目前都不是场景状态，进不了因果条件；
   - 需求按 R99 不生成状态。
4. **因果服务按实例分组。** 只有同一任务内同样的迁移发生两次，才可能形成因果；首例只保存在内存里。
5. 贡献阶段的做法：
   - 先原子发布阶段节点 J，J 持有原因材料引用；
   - 再以 J 为来源建治理动作，执行主体为 self；
   - 然后提交特征变化，生成后状态和原子动态，并关联“导致变化”。

   本设计沿用这一做法。

## 3. 总体做法

每次任务状态迁移按同一顺序完成，收口到一个统一入口：

```text
写入因素特征（任务虚拟存在，生成场景状态）
-> 发布治理迁移记录（动作来源，持有原因材料引用）
-> 建立治理动作（定义＝该“前→后”配对的迁移定义，主体＝self）
-> 提交任务状态特征，建立前后状态与原子动态，关联“导致变化”
-> 交付实际发生（前置窗口取场景内动作前的状态与动态，交因果服务）
```

## 4. 设计

### 4.1 迁移清单与统一入口

- 所有写入任务状态的调用点（调研第1节表中第1–25项，含“子需求不合法”的进入和离开）都改走统一入口 `迁移任务状态(任务, 后状态, 迁移原因)`。
- 统一入口校验封闭迁移表，按第3节顺序完成迁移。
- 现在绕过迁移表的两处直写（撤销未进入动作执行、重新启用服务任务）也改走统一入口。
- 规范迁移表补全现在缺的迁移：
  - 撤销：执行中 → 待查找方法；
  - 重新启用：已完成、已结算、未执行但目标已满足、放弃结算 → 待查找方法；
  - 放弃结算：已完成 → 放弃结算；
  - 执行前收束：→ 未执行但目标已满足。
- 贡献阶段的直属结算收尾、最终结算收尾（9→12）也走统一入口：J 作为迁移记录，同样交付因果。
- 死代码 `标记任务已结算`、`建立任务状态动作`、`完成任务状态变化` 被统一入口取代，按 AGENTS §5 直接删除。

### 4.2 迁移动作定义（按前后状态配对）

- 封闭迁移表中每一对“前状态 → 后状态”登记一个任务状态迁移动作定义。登记方式同贡献定义：初始化时挂在任务集合根下，并由动作方法投影服务生成动作概念。
- 定义只登记迁移表允许的配对，数量以修订后的迁移表为准，约 40 余个。
- 同一配对由不同治理操作触发的（例如“等待条件 → 待查找方法”可能来自自我复核放行、学习后重新筹办、因果等待放行），定义仍只有一个，操作的区别由迁移记录中的原因种类和因素特征体现。

### 4.3 治理迁移记录（动作来源）

- 每次迁移先原子发布一个迁移记录节点，作为治理动作的来源。字段包括：
  - 任务、前状态、后状态、动作时间；
  - 原因种类（触发这次迁移的治理操作）；
  - 原因材料引用：候选材料节点、执行实例、影响评估、重启记录、贡献阶段、自我决议种类等，按原因种类取用。
- 迁移记录是持久结构，供追溯“为什么迁移”。
- 执行主体统一为 self（服务根目标存在），与贡献阶段一致。

### 4.4 因素特征（进入因果条件）

- 任务虚拟存在新增以下实例特征。它们由任务 owner 在迁移之前写入，写入时自动生成场景状态，因而落在前置窗口里，成为因果条件：

| 特征 | 值 | 写入时机 |
| --- | --- | --- |
| 承接依据 | 自我首次复核、状态变化复核、条件子需求、因果子需求、复合子需求、外部服务要求、行动请求、扫描补齐 | 承接迁移前 |
| 候选结论 | 有候选、无候选 | 消费方法候选前 |
| 条件结论 | 具备、等待条件、需子需求 | 条件核验结果形成后 |
| 执行进入结论 | 已进入动作、零动作 | 开始执行或零动作恢复前 |
| 影响评估结论 | 按影响评估的需求结果取值 | 影响评估完成后 |
| 后继决议 | 继续查找、等待条件、完成、失败、取消 | 发布后继决议前 |
| 不合法子需求 | 引用子需求节点组 | 收到“子需求不合法”或“恢复合法”通知时 |

- “不合法子需求”成为持久特征后，DEP-READY-WAKE 中“挂起依据只存运行期、重启后重新筹办一次”的做法由它取代：重启时从特征读回排除依据。这需要同步修订 5260 §5.5 第6项（见第6节）。
- 特征只引用任务自身的材料，不为需求生成状态（R99 不变）；“不合法子需求”只存引用，不在需求侧生成任何状态。
- 每个特征的值域、概念登记在施工 S0 按现有特征登记方式确定；具体枚举值以施工时的代码为准，增减须回到本设计修订。

### 4.5 交付因果

- 迁移完成后同步调用 `交付实际发生`，与现有实现一致。
- 前置窗口规则不变：取本场景中上一次同结果之后到本次动作时间之间的状态和动态。因素特征的状态因此进入条件。
- 因果服务分组规则不变（同一任务内归纳）。跨任务归纳不在本设计范围内。

### 4.6 性能

按用户裁决以后再解决。本设计不做异步交付、首例持久化、索引和场景删除，只在施工记录里记录实际耗时（用已有的调试切片），作为以后的输入。
