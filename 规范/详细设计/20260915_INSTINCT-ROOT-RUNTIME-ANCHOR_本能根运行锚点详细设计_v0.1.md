# 本能根运行锚点详细设计 v0.1

状态：执行退回，等待剩余物理合同裁决。基线：`5e50fb99ac7d190c7f71c7dc4a5a1f4627fa0c05`。本设计不使用旧候选中的`.ixx`路径。

## 执行 DRIFT（2026-09-15）

`INSTINCT-ROOT-RUNTIME-ANCHOR` 的执行 S0 已证实下列问题，故本设计的“施工对象”与后续步骤不能作为当前实施依据：

1. 8121 的根特征材料未给出 4110 / 4205 所要求的 `C/P/主holder/已发布FC`。新准确 F 不能无位置建立；其类型和值一经建立不可变，当前采用由存在 owner 维护。因此“特征 owner 预形成当前值选择”的原表述不成立。
2. 首值、初态与“当前状态选择”没有冻结唯一 owner、关系形状、参与者写集、本地映射和发布未知的原请求回放。现有状态服务只公开单 owner 状态创建，不能由两个旧写入口顺序拼接。
3. 根目标合同、独立根需求 D、根列表项 L 和成员关系只有逻辑语义，尚无可实施的 ARCH-L4 DTO、关系形状、原子写集和读回合同；当前需求头仍是已退役的“方向二次特征”记录。已裁决的边界是：双根 D 不写入所属存在、目标宿主、自我字段、关系或 owner；其逻辑归属只由阶段21入口和最终运行锚点表达，且阶段21不处理任务实体或任务物理关系。
4. `M-X` 二次概念定义与即时差值投影必须保留；禁止创建持久化方向差值实例、当前值、状态或动态。需求服务承载根 D/目标合同，不是 M-X 定义的替代者。
5. “首次初态 UTC 纳秒”未确定是两根状态共用的实例绝对强时间还是其他材料，亦未冻结时钟提供者、读取失败映射和首次材料编码。它不能与状态服务自行记录的首次形成 UTC 混同。

在剩余合同裁决前，禁止按下文的旧“施工对象”“步骤”新增 DTO、跨 owner 入口、需求服务、普通应用装配或启动调用。8121已经按独立双根 D 口径修订；不得再把该已裁决边界回填为自我物理绑定。

## 已裁决边界与待冻结合同

已裁决：安全 / 服务双根 D 是物理独立根节点，各自仅有独立身份、根特征、根目标合同、父空、顺序0和根列表闭包；不得写入任何自我物理绑定。阶段21入口与值式双根锚点表达其逻辑归属。任务逻辑属于普通需求层级`自我 → 根需求 → 任务`，不在阶段21处理。

仍待冻结、不能由本设计推测的是：

1. 两个根准确 F 的 `C/P/主holder/FC` 分别是什么？固定十类幂等身份的版本化命名域和完整规范化请求字段是什么？
2. 阶段 21 是否先按 4205 的四 owner 定位创建 F，再由哪个唯一 owner（或哪些明确参与者）原子发布首值、初态和当前状态选择？当前状态选择的物理关系和 owner 是什么？
3. 在不改变已裁决的独立根 D 边界、`I64_MAX`目标、父空/顺序0、独立 L、当前成员恰一的前提下，目标合同、D、L、成员的 ARCH-L4 DTO、关系、写集、恢复和读回合同是什么？
4. 首次初态 UTC 是否由普通应用在阶段 21 起点只读取一次，作为两个根状态共同的`实例绝对UTC纳秒`并纳入完整幂等请求；状态服务仍独立记录自己的首次形成 UTC？若是，正式时钟提供者及读取失败映射为何？

## 原施工设想（已暂停，不可作为施工依据）

新增`业务/本能根运行初始化.数据.h/.cpp`与`业务/应用服务.本能根运行初始化.h/.cpp`；扩展`领域/数据服务.特征类.h/.cpp`、`状态类.h`、`需求类.h`，以及`装配.普通应用.h/.cpp`、`启动.应用程序.cpp`、项目文件。禁止线程文件与旧`L2*`模块。

ARCH-L2新增：按幂等身份正式读取特征定义/实例/比较注册；状态服务的“首值+初态+当前状态选择”跨owner单事务入口。ARCH-L4需求服务新增：目标合同CRUD和按幂等身份读回、独立根D（父空、顺序0且无自我物理绑定）建立/读回、根列表项及当前成员建立/读回；所有请求携带G0和固定键，所有成功回显完整实体与截止。

业务provider按8121顺序逐步补齐；每一步读当前G0，提交后重新读取。最终只在同一Gfinal形成双根锚点；调用方不得从中取得可写端口。普通应用增加`初始化普通应用本能根()`，启动在阶段19成功后调用，成功仍停在阶段20以前。

非成功逐层保留来源状态并归一为8121结果；资源失败、异常、代次漂移、幂等冲突、引用冲突、材料未闭合、已可能发布均零锚点。时间首次锁定在首次请求材料，重复和重启不重置根值。
