# FEATURE-CONCEPT-MODEL-CUTOVER 准确特征与特征概念模型切换详细设计

日期：2026-09-08
版本：v0.5
身份：`FEATURE-CONCEPT-MODEL-CUTOVER`
正式修订基线：`9708a7beb5fb2dd60d07fa4ae3771f5f8ea0d664`

## 1. 修订范围

本版本继承 v0.4 未被本文件明确改写的准确 F、特征概念、EC、DC、场景投影、预算、EC 扩展交付、迁移删除、源码白名单及验证合同，只闭合执行者具名退回的三个接口漂移：

1. `应用服务.存在概念树类.ixx` 仍从特征概念应用模块取得四个通用旧 DTO，导致特征概念模块不能完成旧共享 DTO 物理清零；
2. `应用服务.动态概念树类.ixx` 未公开区分新概念 provider 的五个失败状态；
3. v0.4 让场景层保存并直接收敛 `特征概念写请求`，但该请求是五分支 variant，场景请求不能机械证明任意分支曾由特征概念应用派发；直接调用 `收敛特征概念写入` 会允许未绑定原键的陌生请求首次执行。

正式 0050 v3.6、7110 v1.5、7140 v1.6、7150 v0.3、7160 v0.2、4230 v0.34、4240 v0.24，连同当前 provider DTO 和公开入口，足以在原目标内唯一裁决。本次不修改正式规范，不新增 owner、持久账、写入口、恢复入口或跨 owner 事务。

## 2. EC 专用公开合同

### 2.1 所有权与类型

以下四个类型唯一导出于 `海中鱼巣/业务/应用服务.存在概念树类.ixx`。它们只描述 EC 应用自己的预算、可选场景守卫、业务结果和阶段，不属于特征概念应用，也不供 DC 或新场景 v2 复用。

```cpp
struct 存在概念应用预算 final {
    概念树共享预算 数据;
    std::uint64_t 最大派发步骤 = 0;
    std::uint64_t 最大保留尝试 = 0;
    std::uint64_t 最大遍历节点 = 0;
    friend bool operator==(const 存在概念应用预算&,
                           const 存在概念应用预算&) = default;
};

struct 存在概念场景限制 final {
    概念树场景引用 S{};
    概念树存在引用 E{};
    std::uint64_t 原场景H = 0;
    friend bool operator==(const 存在概念场景限制&,
                           const 存在概念场景限制&) = default;
};

enum class 存在概念业务状态 : std::uint8_t {
    完成 = 1,
    待继续,
    被后继覆盖,
    需显式治理,
    不支持,
    入口拒绝,
    数量预算不足,
    历史材料不可用,
    资源失败,
    内部不一致
};

enum class 存在概念阶段状态 : std::uint8_t {
    未派发 = 1,
    部分确认,
    先前阶段待核验,
    全部确认
};
```

字段和顺序固定，不追加 F、FT、形成宿主、线程槽、剩余预算或恢复标志。`存在概念形成请求::预算`、`存在概念上位请求::预算` 使用 `存在概念应用预算`；形成请求的可选场景字段、两个场景重载参数使用 `存在概念场景限制`；继续请求的本次预算同样使用 `存在概念应用预算`；操作结果只使用两个 EC 专用枚举。

`概念树共享预算` 仍是各 DATA provider 的结构读取/写入预算；EC 外层三个计数只限制本次最多派发的阶段、继续材料保留的尝试和应用遍历，不改 provider 计量。继续可以给出新的本次预算，但不得改写继续材料中保存的原业务、原幂等键或已派发请求。

### 2.2 EC 状态映射

现有 EC 行为保持，仅类型归属和两个枚举名收敛：

| provider / 应用事实 | `存在概念业务状态` |
| --- | --- |
| 全部必要定义、支持或接边完成并读回 | `完成` |
| 事实代次漂移、外层本次派发额度用尽、可安全换 G 重备 | `待继续` |
| 原场景成员、原见证、支持或接边已被后继事实覆盖 | `被后继覆盖` |
| 命中退役概念且须显式恢复 | `需显式治理` |
| provider `不支持` | `不支持` |
| provider 数量预算不足 | `数量预算不足` |
| provider 历史材料不可用 | `历史材料不可用` |
| `std::bad_alloc`、`std::length_error` 或 provider 资源失败 | `资源失败` |
| 合同入口非法及未具名的普通拒绝 | `入口拒绝` |
| provider 内部不一致、差异不可表示或不可能结果形状 | `内部不一致` |

`存在概念阶段状态` 的四项语义不变：零派发、已有确定子结果、可能已发布须先核验、全部确认。`存在概念操作结果::成功()` 必须改为只认 EC 专用 `完成` / `全部确认`，其它既有 G/H、继续材料、已确认事实和 `可能已发布` 守卫不变。

### 2.3 物理删除

`共享特征应用预算`、`共享场景限制`、`共享特征业务状态`、`共享特征阶段状态` 的定义和生产消费全部为零；不得保留别名、`using`、转发壳或在特征概念模块中继续导出。旧场景 v1 对这些类型的消费随 v0.4 场景整体替换一并删除，不迁移为 EC 新类型。

## 3. DC 公开失败分账

`动态概念应用状态` 保留现有 1..14 的数值和含义，并在末尾追加：

```cpp
enum class 动态概念应用状态 : std::uint8_t {
    // 既有 1..14 不变；内部不一致 == 14
    不支持 = 15,
    旧格式不支持 = 16,
    规则缺失 = 17,
    类型不相容 = 18,
    前次写入待收敛 = 19
};
```

`动态概念树应用服务::映射(概念树数据状态)` 必须显式增加下表；不得落入 `内部不一致`，也不得并入外层 `待继续`：

| `概念树数据状态` | `动态概念应用状态` |
| --- | --- |
| `不支持` | `不支持` |
| `旧格式不支持` | `旧格式不支持` |
| `规则缺失` | `规则缺失` |
| `类型不相容` | `类型不相容` |
| `前次写入待收敛` | `前次写入待收敛` |

`待继续` 只表示 DC 外层尚有合法后继阶段但本轮停止；`前次写入待收敛` 表示 provider 自己已有未收敛写入，二者不可互换。其它现有映射保持；成功状态、`无须变更` 或未在失败路径允许的状态进入映射仍为 `内部不一致`。

## 4. 场景与特征概念应用的恢复边界

### 4.1 继续 DTO 收紧

场景不再拥有、保存或直接收敛概念 owner 的五分支 `特征概念写请求`。v0.4 的 `场景成员概念继续阶段_v2` 和 `场景成员概念继续材料_v2` 改为：

```cpp
enum class 场景成员概念继续阶段_v2 : std::uint8_t {
    特征应用 = 1,
    存在采用 = 2,
    最终读回 = 3
};

struct 场景成员概念继续材料_v2 final {
    std::uint32_t 版本 = 2;
    场景成员概念继续阶段_v2 阶段 =
        场景成员概念继续阶段_v2::特征应用;
    场景成员概念请求_v2 原请求;
    std::optional<存在当前采用写请求> 采用原请求;
    friend bool operator==(const 场景成员概念继续材料_v2&,
                           const 场景成员概念继续材料_v2&) = default;
};
```

同步删除 `场景成员概念状态_v2::待概念写入收敛`。`特征应用` 阶段要求 `采用原请求` 为空；`存在采用` 阶段要求它存在并通过 v0.4 已冻结的 E/FT/F、幂等身份、原预期和预算逐字段互证；`最终读回` 阶段要求它为空。形状不符返回入口拒绝。

### 4.2 唯一调用顺序

1. 初次处理只调用 `特征概念应用服务::处理类型观察(原请求.观察)`。
2. 处理结果为 `待原请求确认` 时，场景只保存完整原场景请求并返回 `特征应用` 继续阶段；`特征概念处理结果::待确认请求` 可以作为当次结果中的诊断事实原样返回，但不得复制到场景继续材料、改写或直接派发。
3. `特征应用` 续行只调用 `特征概念应用服务::收敛类型观察(原请求.观察)`。同一应用实例由该入口核对 `pending_input_` 后收敛自己的内部请求；若实例已有其它观察的 pending，该入口返回前次待收敛，不得碰触该请求。
4. 换应用实例时，只有原观察已经能由正式 `读取类型观察` 找回，特征概念应用才可按现有事实继续推进；原观察仍不可见且本实例没有原 pending 时返回不支持。场景不得为扩大恢复能力直接调用概念数据服务写入口。
5. 特征应用完成后，场景按 v0.4 读回 F/C/名称并进入可选存在采用；存在采用仍只使用已保存、可完全互证的 `存在当前采用写请求` 调用其 provider 收敛入口。

### 4.3 五分支所有权

五种 `特征概念写请求` 均只由特征概念应用内部生成和核验：

| 分支 | 必须由特征概念应用核对的关联 |
| --- | --- |
| `类型观察登记请求` | 观察键、准确 F、时间、最大保留数和预算来自完整 `特征概念观察请求`；读取同键观察时输入必须完全相等。 |
| `特征概念建立请求` | FT/规范化域、形成依据、直接上位和子父替代来自同一观察推进中的正式类型规则、现有图和包含判定。 |
| `特征名称变更请求` | F 是该观察唯一确认 F，C 是本次确认概念，预期名称来自同截止公开读取。 |
| `特征概念命中请求` | 观察记录来自同键观察，完整命中组由同截止全图及正式域判定形成。 |
| `特征概念组织请求` | 只允许特征概念应用按完整图形成；当前场景链不建立该分支，也不接受它作为继续输入。 |

场景不重复上述算法，也不根据 `特征概念写请求` 中看似相等的字段判断它“应该已派发”。因此 `收敛特征概念写入` 在场景模块的直接调用为零；这同时关闭任意五分支陌生幂等键的首次执行入口。

## 5. 其余 v0.4 合同不变

准确 F、C/名称结果、场景请求、最终投影、存在采用意图、成功谓词、F 内部 pending 同实例边界、名称窄读预算、EC 扩展交付、14 个源码消费者和旧 ABI 物理删除均继续依 v0.4。场景服务仍可持有概念数据服务用于只读 F/C/名称互证和最终读回，但不得借此接管特征概念应用的内部写分支。
