# SELF-GOVERNANCE-CLOSURE L4 消费者需求与提供者验收合同 v0.7

日期：2026-08-25

状态：L4 需求权威；同身份 v0.6 的增量替代合同

## 1. 来源与裁决

本版本只收口执行期具名漂移：

```text
DRIFT-L4-PRODUCTION-ACTION-PORT-FINAL-REREAD-AND-REALITY-ATTRIBUTION-UNFROZEN
```

现行 v0.5 已经冻结 method v2、派发门控、强类型队列和待验证材料，但尚不能证明：

1. worker 在真实动作开始前重新确认全部正式事实仍处于同一当前代次；
2. 生产动作端口具有明确来源、稳定键、所有权和生命周期；
3. 动作返回先形成不可变完成消息，再经权威状态/动态独立读回和唯一归因；
4. 只有上述读回成立后才写 `L2任务实际结果事实`。

v0.7 不改变任务 owner、任务轮次、主阶段四分支、授权 owner、安全硬否决、逐需求核算、轮次收束或自我后继语义。

## 2. L4 对动作提供者的唯一需求函数

L4 只定义消费合同，不替具体业务方法发明动作语义。每个实际业务动作提供者必须满足：

```text
F_action(
  稳定动作键,
  完整强类型执行请求,
  执行幂等身份
)
-> 技术许可
-> 依据冻结的预期结果/验证/归因合同形成非权威预计动态
-> 幂等执行
-> 不可变动作完成定位
-> 可由正式 L2 公开读取独立互证的
   {场景, 主体, 实际状态, 动态证据, 事实截止}
```

约束：

- 同一稳定动作键只有一个活动生产端口；空组允许普通应用启动但所有动作确定性返回`端口不存在`，不得伪装成功。
- 同一执行幂等身份的精确重复只能返回首次动作完成定位，不能再次执行动作。
- 动作端口返回的状态/动态身份只是定位候选；L4 必须通过正式公开 L2 读取互证，不能信任返回值本身。
- `动态证据.来源稳定编码 == 稳定动作键.值`，`动态证据.主体存在 == 主体`，`动态证据.后状态 == 实际状态`；否则归因失败。
- 多动作方法逐项发布并验真动作完成消息；最后一个有序动作是本次任务结果的主结果动作。前序动作仍须逐项读回成功，但不另造第二任务结果。
- 每个 method v2 动作入口必须同时冻结`预期结果材料、结果验证合同、动作归因合同`三项非零稳定编码；预计动态只是值式预测，不能作为正式状态、动态或任务结果。
- 具体外设、外部系统或业务方法的动作语义属于该方法提供者；本计划只提供稳定注入、执行、验真和任务结果收束。验证可使用真实 L2 状态动态迁移提供者，不能使用 fake/no-op 成功端口冒充生产闭环。

## 3. 动作前最终当前性

worker 从确认队列取出请求后，不得直接调用动作端口。调用方不得用原派发冻结重新包装 fresh 证据；唯一最终复核顺序为：

```text
任务动作前最终证据读取端口取得 Gnow
-> 在同一 Gnow fresh 读取阶段、冻结、控制态、调度资格、method v2、逐项技术许可、适用授权及有效时间、安全事实
-> fresh 形成动作前最终硬否决请求/结果
-> 返回一份完整的新任务执行派发门控请求
-> 重新调用派发门控并取得一份新的完整派发冻结
-> 新冻结除最终复核读取证据外与队列原请求逐字段同义
-> 才允许进入动作
```

任何代次变化、动作入口变化、端口变化、许可变化、授权失效、硬否决命中、资源失败或结构不一致都返回结构化非成功并保持零动作。

## 4. 返回到正式结果的唯一顺序

```text
动作端口完成
-> worker 形成不可变动作完成消息
-> 消息端口按 {执行幂等身份, 动作顺序} 幂等发布
-> 独立读取同一消息并验证任务/三轮次/冻结/实例/方法/动作键/时间
-> 用消息中的候选定位按同一 Gread 读取场景、主体、状态、动态
-> 验证状态/动态引用闭包和动态来源稳定键
-> 全部动作逐项通过；选择最后动作的权威结果定位
-> worker 只形成不可变任务工作结果定位并提交任务管理槽
-> 任务管理独立取出并再次读取消息与权威事实
-> 上行桥以执行幂等身份映射的任务结果写入幂等身份调用 task-owner v2
-> 提交后独立读回；失败只以原键重放收束
```

动作完成消息发布失败只重发同一消息，不能重做动作。worker 槽必须保留原待验证材料和已经形成的预计动态；权威状态已改变但消息或归因不足时保留世界事实并返回具名`任务动作归因缺口定位`；不得写任务实际结果、不得推进结算或后继。

task-owner v2 必须区分交换前失败和提交后读回失败。四字段提交见证唯一为：

```cpp
struct L2任务实际结果提交见证 final {
    L1结构所有者身份 所有者;
    L2结构幂等身份 幂等身份;
    std::uint64_t 提交事实代次 = 0;
    std::uint64_t 提交结果序号 = 0;
};
```

只有正式事实独立读回成功才返回首次/精确重复成功，并回显首次事实与首次见证；L1 已确认提交但正式读回失败返回`已可能发布 + 仅提交见证`，完整事实为空。同一完整请求以原幂等身份重放时先命中首次账，零应用、零新代次并从首次 G1 正式读回收敛。既有 v1 写入口只保留源码可编译的确定性拒绝，生产消费者必须归零。

## 5. 完成与声明边界

最终统一验收必须覆盖：

- 动作前 Gnow 漂移、技术许可变化、最终硬否决命中均零动作；
- 内部治理/纯观察零授权，现实改变只有一份自我授权；
- 动作完成消息精确重复不重做动作；
- 权威状态/动态读回成功、引用冲突、归因等待、资源失败；
- 多动作只以最后动作形成一个任务实际结果；
- 提交后读回失败以原键收束；
- 连续两轮从任务轮次到结算、停驻和正式继续决议。

本合同不证明任意外设或任意外部业务动作已经实现。只有具名动作提供者通过本合同并由普通应用合法注入时，才可声明该动作的生产闭环。
