# RUNTIME-GOVERNANCE-DEMAND-INITIAL-PLANNING-WORK-PACKAGE 需求初次筹办工作包形成详细设计 v0.3

日期：2026-08-23

## 1. 修订来源、目标与完成条件

来源具名漂移：`DRIFT-DEMAND-INITIAL-PLANNING-FIRST-RESULT-UNRECOVERABLE`；局部验证合同漂移：`DRIFT-DEMAND-INITIAL-PLANNING-V04-ILLEGAL-INJECTION`。

v0.3 只修正验证注入边界；v0.2 已冻结的机器语义、DTO、ABI、生产入口顺序、事务和代码白名单全部保持不变。不得为了让测试到达幂等账而新增合同版本、放宽请求守卫、解除双幂等键一致性或建立测试专用生产 seam。

v0.1 只让外层 provider 复用 `L2新增任务请求` 的任务建立幂等键。该写集不保存外层准备完整请求、首次需求裁决来源和首次工作包来源；任务退出、当前任务变化或其它发布发生后，原请求只能重新裁决或被当前读回分流，不能遵守 3200 第 23 节“同幂等身份 + 同完整请求返回首次结果”。用 G1 重新裁决不是首次结果恢复，不能作为修复。

v0.3 目标闭合为：

```text
同一外层初次筹办准备幂等身份 + 同一完整请求
-> 先读 task owner 的首次准备记录
-> 已存在则从首次 G0/G1 历史材料返回首次裁决与首次工作包
-> 不存在才在 G0 做正式需求裁决
-> 未满足且列表项无当前任务时
-> task owner 将任务、列表项引用、任务虚拟存在和首次准备记录在 G0->G1 同代原子建立
-> 发布后直接读回并返回首次结果
```

完成必须同时满足：

1. 外层请求具有独立强类型准备幂等身份，并冻结完整请求相等边界；
2. task owner 具有强类型首次初次筹办准备记录和按准备幂等身份的前置读回；
3. 首次准备记录、任务、需求列表项引用和任务虚拟存在由同一 owner 在同一 G1 原子建立，记录通过强类型关系由任务虚拟存在承载；
4. 记录保存足够的不可变材料，能够恢复首次未满足裁决、来源身份 / 版本、成员、完整列表项、运行代次、任务身份、轮次 1、G0 和 G1；
5. 同键同完整请求即使任务已退出、列表项当前任务改变或世界事实已进入 G2+，仍返回首次结果；
6. 同键异完整请求返回幂等冲突，发布未知只允许原键原请求收敛；
7. 记录支持按身份的当前 / 历史读取和按准备幂等身份跨生命周期唯一查找；
8. 并发只能留下一个任务和一个首次记录，不出现裸任务、无记录任务或记录绑定第二任务；
9. 执行者不需要决定 DTO、物理位置、事务、读回顺序、错误映射和验证边界。

## 2. 范围与排除项

本设计只修订初次筹办准备闭环。明确排除：

- 父需求回流、子目标承接记录消费；
- 已有任务的新筹办轮次和任何重筹办 provider；
- 方法候选、路径、实例、冻结、执行和结果；
- 成员结算、结果共用 / 争用、价值、预算和归因；
- 成员分配优先级。当前没有该具名 provider，禁止把需求优先级、任务基础优先级或遍历顺序写成成员分配优先级；
- 修改正式规范、规范目录、共享代码图谱、能力目录或知识聚合索引；
- 修改或暂存执行侧未发布候选 WIP，计划侧只形成 v0.3 设计包。

## 3. 权威依据、基线与切分裁决

### 3.1 权威依据

- 3200 §5.2：任务运行状态必须由 task owner 的强类型治理记录表达并由任务虚拟存在承载；
- 3200 §23：任务核心与虚拟存在同代建立，列表项当前任务基数 0/1，同键同完整请求返回精确重复和首次结果，异义冲突，发布未知原请求收敛，历史可读；
- 4260 §11、§15、§40、§43：任务虚拟存在唯一状态宿主、任务核心原子形成、当前 / 历史读取分账和 0/1 基数；
- 5200：结构锚点与任务治理特征分账，筹办轮次属于 task owner；
- 5210：待初次筹办必须由需求列表项、成员视图、授权和初次触发事实共同成立，不得用单一阶段枚举替代完整状态。

## 4. 业务不变量与首次结果定义

```text
完整请求 = 外层合同版本
         + 外层准备幂等身份
         + 请求身份
         + 运行代次
         + L2结构请求头(合同版本,G0)
         + 需求身份
         + 任务建立幂等身份

首次成功结果 = 首次未满足裁决完整快照
             + 首次任务及任务身份来源
             + 首次来源需求、成员关系和完整列表项
             + 首次准备记录身份
             + 任务虚拟存在
             + 筹办轮次1
             + G0/G1
             + 首次请求的运行代次
```

外层准备幂等身份与任务建立幂等身份必须映射到同一非零 64 位值；前者是 BIZ 强类型，后者保留为 L2 请求材料和兼容字段，不得形成第二次独立提交。融合写集使用该唯一值映射到 task owner 的 L1 写入幂等身份。

同外层键异完整请求只有在本次请求先满足生产入口合法性时才进入逐字段比较；请求身份、运行代次、G0、需求任一合法变化均为冲突。合同版本和任务建立幂等身份仍属于完整请求材料，但当前唯一合同版本与双键数值一致性使其单字段变化成为非法请求，先返回入口拒绝，不得越过守卫升级为幂等冲突。v0.1“只换请求身份或运行代次不构成冲突”失效；那只描述内层 L2 旧写集，不能裁决外层完整请求。

首次记录是不可变历史材料，不是第二份当前需求 / 列表项 / 特征权威。当前事实仍由各 owner 的正式当前读取裁决；精确重复只是在回答首次操作结果。

本设计中的“首次结果”特指已经发布任务与首次准备记录的首次成功结果。入口拒绝、目标已满足、证据不足、漂移、许可或资源失败发生在任务发布前并保持零写，不消费准备幂等身份；调用方确认零写后可以用新的当前请求重新发起。若发布是否成功未知，则不得按“零写非成功”处理，必须以原键原完整请求先做记录读回并收敛。

### 5.3 物理结构与原子性

首次融合写集至少包含：

```text
节点：任务、任务虚拟存在、首次准备记录
关系：任务族归属、任务->需求列表项、任务->虚拟存在、
      准备记录族归属、准备记录->任务、准备记录->任务虚拟存在、准备记录->需求列表项
值：完整请求全部字段、首次裁决全部值式材料、筹办轮次1
```

全部节点、关系和值使用同一 task owner、同一外层幂等身份、同一期望 G0 和同一提交，创建代次必须同为 G1。记录到虚拟存在的强类型关系证明承载边界；记录到列表项只证明首次来源，不是当前关系。

任务退出时，记录的任务 / 虚拟存在强关系随任务核心在同一退出代次闭合，记录历史和值不得删除。按准备幂等身份的前置读回必须跨当前与历史唯一定位原记录，因此任务退出和新当前任务都不能使首次记录不可见。

## 6. 公开 ABI 与调用顺序

### 6.1 task owner 融合写

```cpp
L2新增任务与首次初次筹办准备记录结果
L2任务结构服务::新增任务与首次初次筹办准备记录(
    L2新增任务与首次初次筹办准备记录请求 请求) noexcept;
```

请求包含`L2结构请求头`、完整请求材料和首次需求裁决材料。列表项、需求、G0、请求身份、双幂等身份必须逐字段互证。该入口只做强类型结构校验和融合发布，不重新裁决需求是否满足。原`新增任务`保留为既有 DATA-L2 结构入口及现有测试边界；外层 provider 禁止再调用它。

### 6.2 直接读回

```cpp
L2按初次筹办准备幂等身份读取首次记录结果
L2任务结构服务::按初次筹办准备幂等身份读取首次记录(
    L2按初次筹办准备幂等身份读取首次记录请求 请求) const noexcept;

L2任务初次筹办准备记录读取结果
L2任务结构服务::读取首次初次筹办准备记录(
    L2任务初次筹办准备记录读取请求 请求) const noexcept;
```

第一入口是 provider 的强制前置读回：按准备幂等身份跨记录完整生命周期返回 0/1，>1 为内部不一致；返回记录、首次任务和身份来源的 G1 历史投影。第二入口按记录身份支持`当前/历史 + 具名历史截止`，历史读取不得拿当前任务或当前列表项补项。

### 6.3 provider 固定顺序

1. 纯值守卫完整请求，并确认双幂等身份非零且数值相同；
2. **首先**按准备幂等身份前置读回；不得先调用实时需求裁决；
3. 记录存在：逐字段比较完整请求；异义=`幂等冲突`，同义则用记录保存的首次材料与 G0/G1 历史投影重构首次裁决 / 工作包并返回`精确重复`；
4. 记录不存在：确认本次观察截止和请求 G0 相同，再调用正式需求当前满足裁决；
5. 只有`未满足`且裁决完整才形成融合写请求；
6. task owner 在锁内验证列表项基数 0/1 并提交一次融合写；
7. `已提交`按 G1 直接读回融合结果并返回`已形成`；`精确重复`转入步骤 3 的首次重构；
8. 发布后读回失败返回内部错误，不撤销已发布事实；调用方只能原键原请求重试。

## 7. 同义、并发、发布未知与后继变化

| 场景 | 唯一裁决 |
| --- | --- |
| 同外层键 + 同完整请求，记录已存在 | `精确重复`；返回首次裁决和首次工作包 |
| 同外层键 + 异完整请求 | `幂等冲突`；零写，不返回当前替代工作包 |
| 不同键同 G0 同列表项并发 | 至多一个融合写发布；输家为漂移或已有当前任务 |
| 发布结果未知 | 原键原请求先读记录；有完整记录即精确重复，无记录才按当前性分账 |
| 首次任务后来退出 | 返回首次 G1 历史任务和工作包；不得复活任务，也不得改成漂移 |
| 列表项后来有新当前任务 | 仍返回首次任务；不得用新任务替换首次结果 |
| 需求 / 成员 / 目标 / 特征后来变化 | 仍返回首次 G0 裁决快照；不得用 G2+ 重裁决覆盖 |
| 首次记录缺字段、复义或与 G0/G1 不一致 | `内部错误`；停止依赖路径 |

首次结果返回不声明该任务当前有效，不授权后继继续执行。后继消费前仍须按自己的当前性合同重新读当前任务和目标；该重读不得反向改变本接口的首次结果。

## 8. 错误映射

外层状态至少严格区分：`已形成、精确重复、幂等冲突、目标已满足、已有当前任务、证据不足、当前性漂移、引用冲突、不可比较、入口拒绝、许可拒绝、资源失败、内部错误`。

- 前置记录未找到不是错误，只有观察截止仍等于 G0 才可继续；
- 前置记录异义为`幂等冲突`，不得映射引用冲突；
- 融合写 L1 精确重复必须读回首次记录，不能只返回任务；
- 0/1 基数中的 1 为`已有当前任务/引用冲突`，>1 为内部错误；
- 权限拒绝向上保持许可拒绝，数量预算与分配异常映射资源失败；
- `std::bad_alloc/std::length_error`为资源失败，其它未预期异常为内部错误；
- 任何 G1 后失败都不撤销、不退出、不删除记录。

## 10. 验证矩阵

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| V01 | 任一完整请求字段非法或双幂等身份数值不同 | 入口拒绝，零写 |
| V02 | 合法未满足需求、无当前任务、无首次记录 | 任务、虚拟存在、记录和全部关系 / 值在同一 G1 发布；轮次1工作包完整 |
| V03 | 原键原完整请求立即重放 | 前置读回命中；不调用新写；返回首次 G0/G1 载荷 |
| V04 | 原键下分别改变仍保持生产入口合法的请求身份、运行代次、G0、需求 | 每项均先命中首次记录再返回幂等冲突；首次记录不变 |
| V05 | 记录按身份当前读、历史读以及按准备键跨生命周期读 | 唯一、同源、无混代；历史不拿当前补项 |
| V06 | 两个不同准备键从同 G0 并发写同列表项 | 恰一任务和一首次记录；输家零写 |
| V07 | 需求裁决已满足 / 证据不足 / 不可比较 / 许可拒绝 | 具名状态；零任务 / 记录写入 |
| V08 | 前置记录未找到后 G0 漂移 | 当前性漂移；不刷新、不重试、不写 |
| V09 | G1 后记录、任务、虚拟存在、来源身份或裁决材料任一缺失 / 复义 | 内部错误；不撤销发布 |
| V10 | 首次任务退出、列表项建立新任务、成员或特征变化后原请求重放 | 仍返回首次结果；不复活、不替换、不重裁决 |
| V11 | DATA-L2 原`新增任务`和融合入口竞争同列表项 | 0/1 基数不破坏；融合入口不得形成无记录成功 |
| V12 | 发布未知模拟后原键原请求重放 | 由首次记录收敛；第二次事实发布为0 |
| V13 | 工作包与记录静态字段检查 | 只含首次请求 / 裁决 / 任务来源所需材料；无旧路径、实例、结果、重筹办、优先级 |
| V14 | Debug / Release 隔离 Rebuild 与两配置`--test-治理` | 命令 0；新增用例逐项 PASS；stderr 空 |
| V15 | 许可、资源、内部破坏无法由合法 seam 注入 | 保留 NOT_RUN，并给源码控制流 / 静态证据 |

V01/V04 的可注入边界固定如下：

- 当前只有外层合同版本 1；同外层键改变合同版本会先违反纯值守卫，只能验证`入口拒绝、零写`，归 V01。不得增设第二合同版本或绕过守卫制造 V04。
- 任务建立幂等身份必须与外层准备幂等身份数值相同；保持同外层键而只改变任务建立键会先违反双键一致性，只能验证`入口拒绝、零写`，归 V01。若同时改变两键则已不是“原键”场景。
- 因而“合同版本异义返回幂等冲突”和“任务建立键单字段异义返回幂等冲突”在当前合同下均为 NOT_RUN；验证记录必须给出生产守卫、provider 固定顺序和唯一合同版本的源码静态证据。
- 请求身份、运行代次、G0、需求只要各自保持非零、强类型和请求头合法，即可在不改变外层键的前提下通过入口守卫；这四类是 V04 的合法动态注入集合，必须逐项 PASS。

执行记录必须逐项给 PASS / FAIL / NOT_RUN、命令、退出码和证据路径。V04 不能以汇总 PASS 掩盖两个 NOT_RUN 子断言，总数不能替代矩阵逐项对账。

## 11. 创建侧自审与完成边界

创建侧确认：没有用 G1 / 当前投影重做首次裁决；没有拆 task 写和 record 写；没有让 DATA 裁决需求是否满足；没有把历史快照写成第二当前权威；没有把成员分配优先级写成需求优先级；没有进入父回流、重筹办、结算或结果共用争用。

代码完成只证明：合法初次筹办准备请求能原子形成唯一任务和可恢复的首次结果，原键原请求在后继变化后仍返回首次载荷。

不证明：工作包已被普通筹办消费、路径 / 实例 / 冻结 / 执行已形成、父回流或重筹办已实现、成员已结算、结果已共用 / 争用、成员分配优先级已裁决，或 HY-Ego 闭环完成。
