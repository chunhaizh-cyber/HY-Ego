# L1-DATA-LAYER-COMPLETE-P1-NEUTRAL-CRUD 业务中性 CRUD 公共闭环详细设计 v0.2

日期：2026-08-07

## 1. 目标与完成边界

本叶在现有唯一 `L1事实基座服务 / L1事实基座仓库` 上建立第一条符合 4015 v0.5 的业务中性普通 CRUD 公共闭环：调用方只提交节点、关系、值、属性槽、退出项、期望事实代次和不透明幂等键；L1 在同一内存权威仓内完成候选、原子代次发布和精确读回，并通过具名当前 / 历史入口返回不可变结构化结果。

本叶不建立独立 L1 自证门、专用外部 L1 黑盒驱动或独立 L1 验收提交。代码结果只形成可被合法 L2—L5 消费者使用的中性数据能力候选；以后每个合法消费者在真实服务运行与验收中，经正式 L1 公开入口、结构化调用结果和最终权威状态读回证明自己的合同与实际覆盖。只有消费者集合累计覆盖增、查、改、退 / 历史、幂等、原子性和非法请求零变化，且相关消费者都完成自身合同，才能认定 L1 足以支撑当前消费者集合。

单个消费者、单条成功路径、构建、静态检查、日志或历史记录都不能证明整个 L1。消费者不得改写 L1 中性语义、降低数据不变量，或把业务标签、意图组、执行证据、领域见证带回普通 CRUD。

本叶不迁移既有领域消费者，不删除 legacy 接口或旧仓，不实现完整快照、审计、持久恢复、崩溃、重启、断电或跨进程恢复。

## 4. 公共 DTO 合同

`L1中性CRUD.数据.h` 只依赖 `L1公共事实.数据.h` 和标准库。合同版本固定：

```cpp
inline constexpr std::uint32_t L1中性CRUD合同版本 = 1;
```

### 4.1 基础类型与事实副本

```text
L1中性写集本地键 { uint32 值 }
L1中性写集幂等键 { uint64 值 }
L1中性独立材料引用 { 稳定编码 编码 }
L1中性事实引用 = variant<稳定编码, L1中性写集本地键>
L1中性原始值材料 = variant<I64, I64组, U64组, L1中性独立材料引用>
L1中性值表示种类 = I64 / I64组 / U64组 / 独立材料引用

L1中性属性槽 = 属性类型节点 + 当前值
L1中性节点事实 = 编码 + 节点种类 + 可选值表示种类 + 创建事实代次 + 可选退出事实代次 + 升序唯一当前属性
L1中性关系事实 = 编码 + 源节点 + 目标节点 + 关系类型节点 + 角色或顺序 + 创建事实代次 + 可选退出事实代次
L1中性值事实 = 编码 + 所属节点 + 属性类型节点 + 原始值材料 + 来源节点 + 创建事实代次 + 可选退出事实代次
L1中性事实副本 = variant<上述三类事实>
```

这些类型只是值式边界投影，权威状态仍唯一保存于现有事实仓。

### 4.2 写请求

```text
L1中性节点新建项 = 本地键 + 节点种类 + 可选值表示种类
L1中性关系新建项 = 本地键 + 源 / 目标 / 关系类型引用 + 角色或顺序
L1中性值新建项 = 本地键 + 所属 / 属性类型引用 + 材料 + 来源引用
L1中性属性槽变更项 = 所属 / 属性类型引用 + 新当前值本地键

L1中性写集请求 =
  合同版本
  + 期望事实代次
  + 非零不透明幂等键
  + 节点新建项组
  + 关系新建项组
  + 值新建项组
  + 属性槽变更项组
  + 退出事实稳定编码组
```

请求不得出现摘要版本、操作标签、意图组、领域合同、执行证据、提供者见证、领域结果见证、审计、恢复或调用方自定读回计划。读回项目由仓库按规范化完整写集机械形成。

规范化顺序固定：节点 / 关系 / 值按本地键升序；属性槽按所属引用、属性类型引用、新值本地键升序；退出事实按稳定编码升序。同组重复、跨三类重复本地键、重复退出编码和空写集均在锁前拒绝。幂等同义比较使用除合同版本外的全部规范化字段逐字段比较，摘要不得替代。

### 4.3 写入与读取结果

```text
L1中性写入状态 = 成功 / 精确重复 / 入口拒绝 / 未找到 / 已退出 /
                   事实代次漂移 / 幂等冲突 / 资源失败 / 内部不一致
L1中性重试边界 = 不适用 / 原请求可重试 / 修正请求后可重试 / 原幂等键读回收敛
L1中性写入结果 = 状态 + 合同版本 + 幂等键 + 事实代次
                 + 是否形成内存权威发布 + 重试边界 + 升序新编码映射
```

成功返回新代次且已发布；精确重复返回首次代次与首次映射且未形成新发布；写前非成功均未发布。发布后读回矛盾返回内部不一致、新代次和已发布，并隔离现有仓。结果不返回审计、恢复材料、执行证据、领域见证或全快照。

读取状态固定为成功、入口拒绝、未找到、已退出、属性未设置、资源失败、内部不一致。结果回显合同版本、查询身份和适用读取代次；非成功不带事实副本。历史成功返回当前或已退出的一条完整事实。

## 5. 公开函数合同

全部函数归属 `L1事实基座服务`，在 public 区、legacy `提交写集` 之前声明并内联定义：

```cpp
L1中性写入结果 提交中性写集(const L1中性写集请求& 请求);
L1中性节点读取结果 读取中性当前节点(const L1中性事实读取请求& 请求) const;
L1中性关系读取结果 读取中性当前关系(const L1中性事实读取请求& 请求) const;
L1中性值读取结果 读取中性当前值(const L1中性事实读取请求& 请求) const;
L1中性属性读取结果 读取中性当前属性(const L1中性属性读取请求& 请求) const;
L1中性历史读取结果 读取中性历史事实(const L1中性事实读取请求& 请求) const;
L1中性事实代次读取结果 读取中性当前事实代次(const L1中性事实代次读取请求& 请求) const;
```

仓库只新增同签名的唯一写根 `提交中性写集`。服务只校验合同版本并转发 / 映射，不持有第二状态。中性读取调用现有仓库精确读取后逐字段转换；完整快照、审计、恢复和索引调用均为零。转换辅助只存在于服务模块匿名命名空间，不导出、不访问仓库。

## 6. 中性提交事务与幂等

仓库状态新增同锁 `中性幂等账`：键为不透明 `uint64`，值为规范化完整中性写集、首次发布代次、首次新编码映射和首次中性写入结果。它与 legacy 幂等账处于同一仓库状态、同一锁和同一次候选复制 / 交换，不是第二事实仓或业务事实。

中性与 legacy 两账的幂等键不得交叉复用；任一方向命中均返回幂等冲突且不推进代次。legacy 入口除此交叉检查外保持原行为、DTO、审计和结果。

事务顺序固定：

```text
锁前规范化和形状拒绝
-> 取得唯一仓库独占锁
-> 隔离 / 当前状态完整性
-> 双账键占用与中性完整写集逐字段比较
-> 期望事实代次
-> 同代次校验引用、类型、端点、槽、退出项和编码占用
-> 复制同一仓库状态形成候选
-> 节点、关系、值确定分配全局不可复用编码
-> 应用退出和属性槽替换
-> 候选完整性与机械精确读回
-> 写入中性幂等首次结果
-> 一次交换候选与当前状态并关闭撤销能力
-> 按原身份、映射和新代次从已发布状态逐项读回
-> 返回成功，或隔离并返回发布后内部不一致
```

所有可能分配的结果、映射和候选材料必须在最后交换前准备。交换后只做不分配的查找、比较、隔离标记和结果移动。候选前或候选内失败均丢弃局部值，当前代次、三类事实、历史、永久编码和两账零变化。

当前阶段不实现中性幂等账恢复导出。中性账非空时，现有 `导出恢复材料`、`建立恢复候选`、`确认恢复候选` 必须结构化入口拒绝且零变化；`撤销恢复候选` 只可清除中性发布前已存在的候选。该守门防止假成功，不声明恢复能力。

## 7. legacy 共仓过渡

1. 现有带标签重载、无标签 legacy 重载、幂等探测、审计、恢复和领域见证类型不删除、不改签名；现有 10 文件 16 调用点零修改。
2. 新消费者只能 import 新中性合同并调用七个入口；禁止新增带操作标签的 `提交写集` 调用。
3. 两条入口共享同一仓、锁、代次、编码分配器、当前 / 历史事实和永久占用空间；禁止平行容器。
4. 旧四仓和节点直接五仓只读保留；本叶不迁移、不对账、不删除。
5. 后继消费者由自身领域服务负责业务请求中性化、结果解释和合同验证；L1 不拥有领域充分性结论。

## 8. 合法消费者运行覆盖合同

P1 v0.2 不创建验收驱动、第二程序、专用 L1 验收记录或集成验收角色任务。代码发布后，交互侧从正式消费者调用图选择最早合法 L2—L5 消费者；每个消费者计划必须冻结其自身业务合同、实际调用的中性入口和适用覆盖维度。

| 覆盖维度 | 合法消费者必须留下的实际证据 | 不足以证明 |
| --- | --- | --- |
| 增 | 正式消费者提交中性创建写集，取得结构化成功并经公开读取获得新事实 | 更新、退出、幂等或其它消费者 |
| 查 | 消费者经精确当前 / 属性 / 历史入口取得合同所需事实 | 未调用入口或全仓完整性 |
| 改 | 新事实发布与旧事实退出在一个代次成立，读回新当前与旧历史 | 其它更新形状 |
| 退 / 历史 | 当前读取返回已退出，历史入口返回完整生命周期 | 删除、回收或恢复 |
| 幂等 | 同键同义精确重复、同键异义冲突且权威代次符合合同 | 未测试键域或跨消费者同义 |
| 原子性 | 消费者适用并发或组合读只见完整旧代次或新代次 | 崩溃、跨进程恢复 |
| 非法请求零变化 | 结构化非成功，调用前后公开权威代次与相关事实不变 | 未构造的非法类别 |

消费者覆盖记录必须绑定消费者身份、合同版本、代码提交、请求类别、L1 入口、结构化结果、最终权威读回、服务合同结论和未覆盖项。覆盖只能累计真实发生的格；不能用专用 L1 直调补格，不能从日志、编译、静态扫描、历史验收或相邻消费者推断。

“L1 足以支撑当前消费者集合”要求七类维度均至少被一个合法消费者实际覆盖，所有相关消费者均完成自身合同，且没有以降低 L1 中性不变量或加入业务字段换取通过。“L1 完整完善”还要求目标内全部合法消费者已迁移；本叶和任一单个后继均不能单独声明。
