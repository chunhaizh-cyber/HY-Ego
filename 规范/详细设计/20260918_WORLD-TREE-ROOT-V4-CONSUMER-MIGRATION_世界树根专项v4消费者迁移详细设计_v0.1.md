设计身份：`WORLD-TREE-ROOT-V4-CONSUMER-MIGRATION`

日期：2026-09-18
版本：v0.1
状态：待上游发布

## 1. 依赖闭合与问题归因

世界树根脚本的 `.h/.cpp` 探针已可独立迁移，但该脚本实际构建的专项在进入程序前有三个独立问题：D455 翻译单元的 SDK 头边界、专项 C++ 的 v3/v4 ABI 漂移、概念树对象的 `/bigobj` 缺失。前者由 D455 提供者独立消除；后两者都是本专项消费者的职责。故脚本路径计划不能把构建/运行失败作为自身失败或修改范围。

本计划激活前，路径迁移和 D455 条件编译必须在正式 HEAD 发布；只有它们共同成立时，专项 Debug/Release 成功才可归因于 v4 迁移。

## 2. Fixture 的 v4 概念服务装配

在当前 Fixture 已完成特征、存在、状态、场景和世界根服务后，追加一个概念 owner。严格复用普通应用的结构登记顺序和同一 L1：

```text
登记纯概念结构_v2(key 0x1401)
-> 登记存在概念两组结构_v1(key 0x1403, 依赖纯结构)
-> 登记特征概念出生使用结构(key 0x1402, 依赖纯结构)
-> 构造概念树类数据服务(features, existences, values, scenes, port,
                           pure, featureBirth, twoGroup)
```

专项使用自身不与既有 owner 冲突的稳定幂等身份；每一步仍以当前 `generation(l1)` 作为 `G0`，结构登记返回交付与成功谓词必须同时成立。概念服务保存为 Fixture 成员，其生命周期长于世界树应用服务。

## 3. v4 请求和断言映射

建厂增加 `*fixture.concepts`。创建请求不得用旧的 `{三键,父,预算}` 聚合初始化，必须显式字段赋值，避免 DTO 增减时静默错位：

| 原专项目的 | v4 请求与读回 |
| --- | --- |
| 子场景 | `世界树场景创建请求_v4`；`父场景=root`；`定义=通用存在概念定义{1,不预设特征}`；`组织=显式顶层`；空上位；概念定义键和 `存在场景概念创建键_v2` 均完整 |
| 存在成员 | `世界树存在创建请求_v4`；合法 `存在初始绑定` 指向 root；同一通用定义及顶层组织；概念定义键和 `已发布概念绑定键_v2` 均完整 |
| 成功 | `结果.成功(request)`、`结果.投影->E`、`投影->世界根`、`投影->位置`、`投影->内容`、请求回显 variant 同类 |

每个新请求的概念定义键和世界键必须不同，重放仅重放同一完整 v4 请求。预算不足断言仍构造 v4 的读取请求；既有 v2 根验证和场景角色启退合同不在本轮升级。

## 4. 工程和验证

专项工程每个配置的 `AdditionalOptions` 追加 `/bigobj`，因为概念树实现已超过 COFF 节限制。这是局部编译器物理选项，不改变源码 ABI。不能把 `/bigobj` 写到脚本命令行或生产工程来规避专项工程合同。

先作专项源的旧 v3 名称扫描和 v4 字段静态审查，再以脚本做 Debug、Release 独立输出验证。若编译越过 D455 后发现额外失配，记录第一个决定性错误；不得以删除专项覆盖、减小概念树或改生产代码收口。成功的两个 JSON 与日志是唯一运行证据。
