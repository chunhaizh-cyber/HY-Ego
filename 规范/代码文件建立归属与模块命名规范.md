本文件已登记为施工规范，只约束代码文件归属、模块命名和工程实施方法；它不是逻辑规范，不定义对象语义、事实来源、写入权、业务状态、合法业务分支或完成判定。机器逻辑和代码语义只能来自 `规范/规范目录.md` 登记的现行逻辑规范。

本文件也不单独授权建立、修改、迁移、删除或重命名代码。代码实施仍须具备：

```text

-> 已登记现行计划和任务队列
-> 知识库与当前代码互证、既有能力复用裁决

```

若本文件与 `AGENTS.md`、现行正式规范、有效设计、现行计划或实际接口冲突，必须停止对应实施并退回设计治理；不得用本文件补造机器规则或扩大代码许可。

## 2. 总体工程裁决

```text
现有目录和代码文件默认原地保留，迁移必须另有专项计划。
新建数据结构文件使用同名“功能.分类.h/.cpp”。

```

## 3. 文件类型与建立方式

### 3.1 数据结构文件

只有同时满足以下条件，才可按数据结构文件建立：

```text
主要职责是声明稳定值类型、记录布局、容器布局或该结构自身的不变式。
需要由传统头文件向既有 .h / .cpp 代码公开完整类型。
实现内容只属于该结构本身，不承担领域编排、线程编排、初始化流程或自检流程。
```

数据结构文件使用：

```text
功能.分类.h
功能.分类.cpp
```

两者必须同名配对。只有声明且无需独立实现时，可以只建立 `.h`，但现行计划必须说明没有 `.cpp` 的原因。

以下内容不能仅因为内部使用结构体就归为数据结构文件：

```text
领域服务
仓库操作流程
协议复核流程
初始化流程
线程或上行桥
适配器
显示流程
自检与验收场景
```

### 3.2 真实模块文件

不属于 3.1、且不满足 3.3 所述“既有模块所属模板实现片段”全部条件的新代码文件必须建立为：

```text
功能.分类.ixx
```

真实模块必须同时满足：

```text
文件包含唯一且匹配的 export module 声明。
工程以 ClCompile 登记该 .ixx。
使用方通过 import 使用模块。
不得把 .ixx 作为 ClInclude 登记后再用 #include 引入。
模块公开面只导出调用方需要的类型和入口。
```

仅使用 `.ixx` 扩展名但不满足上述条件，不视为真实模块，也不得作为新文件范例。

### 3.3 既有模块所属模板实现片段

只有同时满足以下全部条件，才允许建立：

```text
功能.分类.inl
```

1. 正文是编译期类型变化确属合同组成的函数模板或类模板定义，并且必须由两个或更多翻译单元分别实例化；普通函数、只被一个翻译单元使用的模板、可移入既有 `.ixx` 的实现不得使用本类别。
2. 该片段具有唯一既有模块所有者。详细设计和计划必须冻结所属模块、包含位置、允许实例化方及依赖方向；`.inl` 不形成命名模块、分区、翻译单元、第二实体所有者或独立公开能力。
3. 文件不含 `module`、`export`、标准库或项目头文件 `#include`；包含方必须在包含前提供完整依赖。文件只声明和定义所属模块内部命名空间中的模板及其直接私有辅助，不得放入全局工具命名空间。
4. 生产模块在自身 module purview 内普通包含该片段；其它获计划授权的翻译单元可以在取得相同公开类型依赖后普通包含同一片段。不同翻译单元形成的是从同一源码正文实例化的不同实体，不得宣称为同一二进制实例。
5. 工程只以 `ClInclude` 登记 `.inl`，不得以 `ClCompile`、模块扫描、分区或手工模块依赖登记；使用方不得 `import` 该片段。
6. 片段不得包含测试宏、脚本状态、故障选择、计数器、调度让行、验收输出、测试配置、替代生产 provider 或只为验证存在的分支。生产入口不得因片段存在而增加公开 ABI、友元、私有状态出口或运行期模式。
7. 验证只能分账声明：生产翻译单元和生产外专项实例化同一模板源码正文；真实生产对象、正式服务同址、生产包装入口和构建物理仍须分别以真实路径、静态源码和根工程证据证明。

`.inl` 是 C++ 模板跨翻译单元实例化的窄工程形态，不是传统数据头、通用实现头、自检模块或规避真实模块要求的后缀。若模板并不需要跨翻译单元实例化，或可以通过既有公开合同黑盒验证，则必须继续同置既有 `.ixx`，不得为了便于测试拆出 `.inl`。

## 4. 文件名、路径与模块名

### 4.1 文件名格式

新文件基本名采用：

```text
功能.分类
```

第一段说明文件做什么，第二段说明文件服务于哪一类对象、领域或流程。例如：

```text
初始化.世界树
初始化.需求
上行桥.概念命名治理
自检.概念命名治理
```

不得把功能和分类揉成一个无法稳定拆分的长词，也不得用切片号、阶段号、临时任务号或完成状态作为生产文件名的一部分。

### 4.2 路径和模块名映射

文件放在现有职责目录，不因本文件重排目录。模块名由项目名、项目内相对目录、功能和分类逐段组成：

```text
文件：海中鱼巣/线程/上行桥.概念命名治理.ixx
模块：海中鱼巣.线程.上行桥.概念命名治理

文件：海中鱼巣/线程/自检.概念命名治理.ixx
模块：海中鱼巣.线程.自检.概念命名治理

文件：海中鱼巣/自检.运行器.ixx
模块：海中鱼巣.自检.运行器
```

文件路径、`export module` 名称、工程 `ClCompile` 登记和调用方 `import` 必须四处一致。

### 4.3 新函数物理位置裁决

新建、移动或改变可见性的函数，必须先完成函数合同，再按以下顺序唯一确定物理位置：

```text
冻结完整签名、输入输出、副作用、事务和生命周期
-> 确定函数直接读取、写入或拥有的权威事实
-> 确定该事实的唯一领域 / 结构所有者
-> 查询知识库函数用途、当前能力证据目录、现有模块、同类函数和调用方向
-> 对照当前源码与生产调用点复核知识条目基线
-> 判断既有所有者模块能否在不扩大职责、不制造循环依赖的条件下承载
-> 能承载：扩展既有精确文件
-> 不能承载：记录具名原因并建立新的唯一所有者模块 / 文件
-> 冻结函数形态、最小可见性、声明 / 定义位置和插入锚点
-> 复核工程登记、import / include、实体所有权、依赖方向和验证入口
```

函数形态按状态所有权裁决：

- 需要访问对象不变量或对象私有状态时，优先为该对象所有者的成员函数；
- 不拥有对象状态、只组合公开合同且有明确领域所有者时，放入该所有者模块的自由函数；
- 仅服务本文件实现且不构成公开能力时，保持模块 / 文件内部最小可见性；
- 只有编译期类型变化确属合同组成时才使用模板，不得以模板回避模块所有权；
- 不得因某调用方最先需要、文件较短、路径较近或修改方便而放置。

详细设计和计划必须逐函数冻结：

```text
完整签名
功能分类
权威事实所有者
唯一领域 / 结构所有者
精确文件路径与模块身份
成员 / 自由 / 静态 / 模板形态
导出 / 模块内部 / 类私有可见性
声明位置、定义位置和稳定插入锚点
允许 / 禁止调用方
新增依赖与调用边
新建文件时的具名必要性
```

当前能力证据目录是查重和候选证据，不直接裁决物理位置。无法证明既有模块可承载或无法排除重复能力时，保持设计缺口；执行智能体不得临场选择文件。

### 4.4 新增与直接修改函数的诊断责任

本规则生效后，每个新增或直接修改的项目函数必须在合同备注、详细设计或计划的逐函数合同中登记一种诊断责任：

| 分类 | 适用边界 | 施工要求 |
| --- | --- | --- |
| `本地记录` | 程序入口、正式服务边界或真正异常的最终责任边界 | 异常命中时经统一安全出口记录一次；成功和合法非成功不记录错误 |
| `向上送出` | 内部辅助或非最终责任边界 | 通过结构化非成功、异常或明确错误状态携带足够上下文，不逐层重复记录 |
| `无适用错误分支` | 明确合同下机械无失败的纯计算、简单转换或特殊成员 | 由输入、输出和实现证明，不得只写备注或吞掉错误 |

每个适用错误必须形成 `本地记录` 或 `向上送出 -> 最终责任边界本地记录` 的唯一链。诊断宏关闭时，检查、错误传播、返回值和机器结果仍须成立。函数能编译、没有日志或正常返回都不能单独证明诊断责任成立；实际验收按 ACCEPTANCE-01 分级裁决。

### 4.5 代码知识读取与回写

新建、移动、改变可见性或直接修改函数前，必须读取 `知识库/README.md`、`知识库/代码编写与既有函数复用知识.md`、`知识库/当前代码知识状态.md` 及目标函数已有用途条目，并完成：

```text
核对用途条目绑定提交或源码 blob
-> 核对完整签名、DTO、物理位置和可见性
-> 核对生产调用者、直接被调者和依赖方向
-> 核对事实读写、副作用、事务、并发和生命周期
-> 对照正式规范、有效设计、现行计划和当前代码
-> 裁决直接复用 / 组合 / 适配 / 扩展 / 新建 / 证据不足
```

知识条目低于正式规范和当前代码。条目基线落后或相关代码变化时必须重新核对；条目缺失不等于函数不存在；过期条目不得作为复用或物理位置依据。不能用智能体记忆、短函数名、注释、日志、界面或未发布 WIP 替代当前源码和调用点。

源码注释只解释签名和实现不能清楚表达的设计原因、不变量、锁与事务前置、特殊生命周期或外部边界；不得逐行改写代码，也不得只靠注释建立机器语义。公开入口或复杂内部函数的合同不直观时，应在声明或定义附近保留简洁说明，并在代码变化时同步复核。

代码施工记录必须列出新增、直接修改和退出函数的知识变更清单，包含完整签名、用途与非职责变化、调用边变化、正式依据、验证状态和结果提交。共享用途卡及聚合索引由取得知识库切片所有权的维护者基于已发布代码更新；执行者未经计划明确授权不得在代码提交中顺带修改共享知识索引。

## 5. 职责、入口与实体所有权

### 5.1 生产模块与自检模块分离

生产逻辑和自检逻辑不得写入同一新模块：

```text
生产模块：功能.领域.ixx
自检模块：自检.领域.ixx
```

自检模块可以构造隔离测试材料、并发场景和人读验收输出，但不得成为生产调用路径、机器事实来源或运行期修复入口。生产模块不得为了自检导出可写内部状态；需要验证的行为必须通过正式公开入口或只读材料观察。

### 5.1.1 验证代码零生产增量与完成后清理

生产源码、生产模块和生产工程目标不得为了验证增加额外公开函数、DTO、友元、私有状态出口、故障注入、调度让行、计数器、验收分支、测试配置或人读 PASS 聚合。一个生产实体只有在现行逻辑规范和正式设计独立要求其业务合同，即使没有当前验证也必须存在时，才可以进入生产代码；“便于测试”“提高窗口命中率”或“方便读取内部状态”不是合法生产职责。

逐计划临时建立在生产目标之外的验证源码、独立工程和运行脚本只拥有施工期生命周期。具名验证已经完成、结果和未覆盖边界已经写入验证记录、结果提交已经发布且计划退出后，必须在后续清理提交中删除这些临时文件；验证记录、施工记录、计划、结果提交和 Git 历史继续保留，用于追溯当时实际证据。

确需长期保留并重复运行的验证工具必须另有正式施工计划，具名其长期所有者、适用合同、维护入口、版本和回归责任，并保持生产目标外隔离；不得把一次施工叶的临时夹具默认升级为永久仓库资产。

### 5.1.2 仓库外验证根、任务隔离与残留分账

本项目后续新建的仓库外临时验证源码、独立工程、构建中间件、模块产物、可执行文件、PDB、日志和运行材料统一使用：

```text
D:\TEMP\海中鱼巣\<计划或任务身份>\<本轮唯一标识>\
```

`<计划或任务身份>` 使用现行计划身份；没有计划的具名治理验证使用稳定任务身份。`<本轮唯一标识>` 必须使并发轮次目录互不重叠，可以使用时间戳或随机唯一标识。各验证者只创建、读取、覆盖和清理自己的本轮目录，不枚举、复用、删除或评价其它任务目录。

后续验证不得把系统 `%TEMP%`、仓库根、当前工作目录、仓库内 `.codex-build`、生产数据目录或其它所有者目录作为临时验证根。Debug / Release、不同工具链或不同并发进程仍须在本轮目录下使用独立子目录；固定根不等于共享输出目录。

验证完成、相关进程退出并释放文件句柄后，应删除本轮临时实际文件；无法自动删除时记录精确目录、文件数量、残留性质和清理所有者。普通残留不改变已经取得的编译、运行或结构化读回证据，也不得单独阻断功能结果提交、计划退出或下一代码叶。只有残留仍占用进程、文件锁、端口、数据库、外设或其它共享验证资源，或者包含凭据、个人信息、未脱敏业务材料等敏感内容时，才停止受影响切片并优先清理。

本规则从发布后的下一次 S0 生效。历史计划、记录和已经发生的系统临时目录证据保持原样，不迁移、不改写，也不能据此继续为新验证选择 `%TEMP%`。

### 5.2 `入口.cpp` 边界

`入口.cpp` 只允许承载：

```text
命令行参数解析。
运行模式选择。
顶层模块导入与最小组合装配。
启动、停止、顶层调用和退出码映射。
按现行设计调用统一自检入口并汇总顶层结果。
```

`入口.cpp` 禁止新增：

```text
领域算法或领域服务实现。
协议构造与复核实现。
大段初始化实现。
完整自检场景正文。
并发压力测试循环正文。
逐项验收输出正文。
只为某个切片存在的局部业务类型和辅助算法。
```

自检接线必须服从现行统一自检设计；入口只能保留最小导入、装配和一次顶层调用，不得因接线方式变化把自检正文展开回入口。

### 5.3 命名模块实体单一所有权

同一个 C++ 类、结构、枚举、请求或结果实体只能由一个命名模块声明和定义。首次对外声明的模块是该实体的唯一所有者；其它命名模块不得通过同名跨模块前置声明、重复声明、文本包含实现或平行声明模块建立第二所有权。

工程分层固定为：

```text
服务.*.ixx：唯一拥有业务服务类、服务请求和服务模块自有的包装结果。
数据操作.*.ixx：唯一拥有数据操作类、结构写入规格、数据操作状态 / 结果和仓库读回值式材料。
组合.*.ixx / 路由.*.ixx：只 import 正式所有者，不重新声明服务或数据操作实体。
自检.*.ixx：只通过正式模块公开面构造对象，不成为生产实体友元或声明所有者。
```

服务可按值使用数据操作模块已经唯一归属的类型，但不得重复声明。数据操作模块不得前置声明跨模块业务服务，也不得把跨模块服务类设为私有规格的构造友元。

私有写入规格需要封闭构造时，构造权只能授予同模块的数据操作类。数据操作类可以提供窄规格形成入口供对应服务调用，但该入口不得接收服务模块定义的请求或结果，不得反向 `import` 服务模块，不得取得许可、写仓库或请求提交。

确需跨模块共享稳定值类型时，必须先裁决唯一结构所有者，再由其它模块 `import` 使用；不得为了消除链接错误复制声明、复用旧 BMI、文本包含实现或新增只声明不定义的平行服务模块。

## 6. 并发与锁工程边界

锁只保护运行期内存结构一致性，不承载机器事实，不生成动作来源，也不替代事务、自我现实执行授权、方法执行或因果证据。

### 6.1 仓库公开入口

```text
读入口使用共享锁，只读内部结构，返回记录副本、句柄组、只读材料或快照。
写入口使用独占锁，先完成正式规范要求的入口拒绝，再修改内部结构。
公开入口不得返回可写内部引用、长期裸指针或可跨锁生命周期持有的可变对象。
普通公开入口原则上只持有一个仓库锁；跨仓写入只由现行正式事务边界编排。
```

### 6.2 跨仓事务锁序冻结

通用附属仓库退出后，不再维护一条固定“四仓”锁序。确需在已授权事务实现中同时持有节点、关系、领域类型化记录参与者或索引等多个内部锁时，必须由对应事务详细设计和施工计划根据参与者依赖图冻结唯一顺序，并满足：

```text
同一参与者集合只有一条获取顺序
依赖者撤销先于被依赖者
普通领域服务不直接取得多仓锁
新增参与者必须重新验证顺序无环
锁序不能由运行时类型、地址、线程或容器遍历顺序决定
```

禁止反向获取；禁止在持有后序参与者锁时再请求前序参与者锁；普通领域服务不得临时发明多仓同时持锁路径。未形成正式锁序设计时必须拆分或停止，不得以忙等、循环重试或日志轮询充当防死锁机制。

### 6.3 禁止共享锁升级

公开入口不得在持有共享锁后升级为独占锁。读取后发现需要写入时，必须：

```text
取得只读快照或稳定句柄材料
-> 释放共享锁
-> 通过领域服务或正式事务入口重新进入
-> 重新执行身份、版本、权限和业务前置条件拒绝
-> 取得写入所需的独占锁并写入
```

快照不是持续有效的写许可；重新进入时不得沿用锁内旧判断跳过版本与前置条件复核。

### 6.4 内部 `已加锁` 辅助

`已加锁` 辅助函数只能由已经持有对应锁的同一仓库或同一对象内部函数调用，并同时满足：

```text
不再次获取同一把锁。
不暴露给领域服务、显示层、自检入口、全局工具或外部模块。
不调用可能反向进入本仓库公开入口的函数。
不跨仓库调用其它公开入口。
不把锁、锁守卫、可写引用或内部容器传出当前持锁范围。
```

需要跨仓协作时必须回到正式事务设计与已冻结锁序，不得用 `已加锁` 命名规避公开入口和事务边界。

### 6.5 持锁期间禁止的操作

持有仓库锁期间不得执行：

```text
上层领域服务调用。
显示、控制台输出、日志落盘或弹窗。
文件、数据库、网络或其它持久化 I/O。
外设访问、用户回调、线程等待或任务等待。
可能反向进入任一仓库公开入口的调用。
```

需要上述操作时，先在锁内形成最小副本、句柄组或快照，释放锁后执行；若随后需要写回，必须按 6.3 重新进入并复核。

## 7. 公共辅助函数归属与准入

### 7.1 候选分类

任何“公用函数”“公共辅助函数”或跨文件辅助入口必须先分类：

| 类型 | 定义 | 唯一落点 |
| --- | --- | --- |
| 纯通用函数 | 不依赖项目领域类型，不读写机器结构，只做通用计算、格式化、边界转换或轻量辅助 | 经计划确认的公共工具模块 |
| 仓库内部辅助 | 只服务同一仓库的结构维护、查找、重挂、快照、序列化或恢复准备 | 对应仓库内部私有或受控辅助入口 |
| 领域正式入口 | 涉及领域对象、业务准入、事实读取或结构写入 | 对应领域服务或仓库正式入口 |
| 流程编排 | 跨多个服务形成应用逻辑步骤 | 对应组合、路由或领域编排模块 |
| 禁止候选 | 绕过领域服务、仓库锁、入口拒绝、事务确认或计划范围 | 拒绝并退回设计治理 |

不得为了“迁移公用函数”主动搬运旧函数体、旧全局共享类或旧双向链表模板，也不得在没有具体调用方、用途、允许文件、禁止文件和验证方式时建立公共工具层。

### 7.2 触碰领域类型不得进入全局工具

只要候选函数直接接触以下任一项目结构或其句柄、容器、快照、事件材料，就不得归入全局纯通用工具：

```text
节点、关系、领域类型化记录、索引、特征、特征值、存在、场景、状态、动态、二次特征、因果引用、词条、概念名称关系、需求、任务、方法、动作入口、非权威缓存、事件日志、仓库快照。
```

此类函数即使只读、只转换或仅被多个调用方复用，也必须回到对应仓库、领域服务、组合路由或受控序列化辅助的唯一所有者。不得用“无状态”“静态函数”“只读”或“方便复用”绕过领域归属。

纯通用工具只可处理不依赖项目领域类型的数值计算、边界转换，以及不承载机器事实的字符串、路径和诊断文本整理；不得创建、修改或删除项目结构，不得裁决需求满足、任务完成、方法成功或世界事实。

### 7.3 新增准入清单

新增或扩大任何公共辅助入口前，现行计划和设计至少必须明确：

```text
1. 已搜索当前代码，确认不存在同等功能入口。
2. 用途、唯一所有者、允许调用方和禁止调用方。
3. 读写类型：纯计算、只读、候选读取、写结构、序列化或恢复。
4. 触碰的类型、结构及其正式权威来源。
5. 入口前置拒绝和内部逻辑错误边界。
6. 拒绝后结构不变化的验证方式。
7. 是否需要锁、由谁持锁、是否存在内部已加锁辅助和固定锁序。
8. 生命周期：临时材料、运行期结构、持久化快照或审计材料。
9. 允许文件、禁止文件、公开面和调用路径。
10. 构建、自检、回归和失败收口方式。
```

已有仓库、领域服务或组合模块可以承载时，优先扩展既有入口；执行窗口不得临时改变分类或新建全局替代入口。

## 8. 快照、序列化与恢复辅助门禁

### 8.1 只读快照

只读、快照和候选读取函数只返回记录副本、句柄组、只读材料、非权威候选或快照结构。禁止返回可写内部引用、长期裸指针、可绕过仓库入口修改的容器引用，或会被上层误认为权威事实的临时缓存。

只读访问不得隐式创建、修补或确保结构存在。需要写入时必须走正式入口，并按 6.3 释放读取锁、重新进入和复核。

### 8.2 序列化辅助

触碰项目领域类型的序列化、快照或格式辅助属于对应仓库或对象所有者的受控辅助，不得进入全局纯通用工具。其设计和计划必须明确：

```text
格式标识与版本。
记录数量、字节长度和容器容量上限。
必需字段、可选字段和字段边界。
句柄、版本、关系端点和索引表示。
截断、重复、越界、未知版本和多余尾部的处理。
写出失败与读取失败后的临时材料清理。
```

序列化结果、文件和数据库记录只按现行正式规范作为快照、恢复候选、审计或人读材料处理；本文件不赋予其运行期事实身份。

### 8.3 恢复辅助

恢复辅助只负责形成和校验恢复候选，不得绕过正式恢复入口直接发布。替换当前结构或请求提交前，必须完成：

```text
格式和版本校验。
数量、长度、容量和字段边界校验。
稳定身份、句柄生命周期和版本校验。
关系端点、索引边界和结构一致性校验。
现行正式规范要求的业务准入与恢复拒绝矩阵。
失败候选和临时容器清理。
正式发布后的结构读回验证。
```

禁止先替换当前结构、先发布半结构或先污染索引，再依靠扫描器、日志、弹窗或事后校验发现坏数据。恢复准入、提交、发布和回退语义必须由现行正式规范、有效设计和计划明确；公共辅助函数不得自行裁决。

## 9. UTF-8 与中文标识符

### 9.1 文件编码

```text
Markdown 文档和 C++ 源文件必须是有效 UTF-8。
Markdown 和 C++ 源文件允许带 BOM 或不带 BOM，但不得包含非 UTF-8 字节；不得因普通编辑无意义地反复切换 BOM。
工程 XML 文件必须保持 XML 声明 encoding="utf-8"，并以 UTF-8 保存。
PowerShell 读取或写出中文文本时必须显式使用 UTF8 编码参数。
搜索中文路径和内容优先使用 rg。
源文件、文档、工程文件和日志格式不得依赖 Windows 本地代码页解释。
```

Windows 本地代码页只可作为外部接口或终端显示的受控边界。确需与本地代码页 API 交互时，必须在边界处显式转换，不得让本地代码页字节进入 UTF-8 文件、模块名、项目路径或机器结构。

### 9.2 中文标识符与允许英文边界

函数名、变量名和类内业务成员名必须使用中文。新建的业务类名、结构名、枚举名、命名空间名和项目文件名应优先使用中文；不得仅为输入方便、工具习惯或临时规避编码问题新增英文业务命名。

英文只用于：

```text
C++ 关键字和语言要求的固定拼写。
标准库类型与标准 API。
第三方 API、外部 SDK 和不可控制的外部类型。
构建系统、工程 XML 和工具链固定字段。
不可避免的外部协议固定字段。
```

确需保留外部英文名称时，边界适配代码必须说明其外部来源和不可改名原因；进入本项目业务公开面后不得继续扩散为新的英文业务命名。不得为了显示临时文本新增机器字段，也不得把乱码标识符、乱码路径或乱码输出作为验收证据。

### 9.3 工程配置与乱码验收

`海中鱼巣.vcxproj` 的以下四个配置必须都保留 `/utf-8` 编译选项：

```text
Debug | Win32
Debug | x64
Release | Win32
Release | x64
```

任何工程配置修改都必须逐配置复核，不能用单一 Debug x64 构建代替四配置工程选项检查。现行计划要求完整构建时，应在授权角色和允许环境中验证对应配置；本文件本身不授权构建。

编码验收至少确认：

```text
中文路径和文件内容可按 UTF-8 无损读取。
中文标识符在计划要求的配置中可编译。
工程 XML 仍是有效 UTF-8，四配置均保留 /utf-8。
文档、源码、模块名、构建诊断和保存后的文件不出现乱码。
```

控制台因终端编码显示乱码时，只能判定为显示层问题。必须通过 UTF-8 文件内容、工程配置、编译诊断或结构化输出重新取证；不得用乱码控制台文本证明机器逻辑成功或失败，也不得因切换终端代码页而改变程序机器行为。

## 10. 既有文件兼容与不恶化

本文件不自动要求：

```text

移动现有目录。
一次性拆分入口.cpp。
```

现有以 `.ixx` 命名、但由工程按 `ClInclude` 登记并由 `#include` 使用的文件属于历史兼容文件。它们可以按现行计划原地保留，但不得作为新模块范例，也不得据此宣称模块化完成。

旧设计或计划与本文件不一致时，执行前必须退回设计治理；不得由执行窗口自行兼容或扩大范围。
