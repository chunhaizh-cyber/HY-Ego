# 5260 子规范 任务治理详细合同

编号：5260
日期：20261112
版本：v3.13
状态：正式子规范

直接上级规范：3200。

直接依赖规范：3100、3300、4015、5170、5350。

相关边界规范：1190、4211、4220、5090、5360、5380、6100、6150、6190、7240、8000、8100、8200、8210。

## 1. 适用范围

本规范展开3200的任务建立、筹办、执行、结果获取、影响评估、状态推进、完成结算、重新启用、消息恢复和失败边界。

现行任务模型只含：

```text
任务T
+ 建立需求D；同一需求列表项的其它需求也由本任务服务（3200第4节，R108）
+ 唯一任务虚拟存在Vt
+ Vt上的当前任务状态
+ Vt上的本任务方法筹办条件信息
+ 0..n执行实例X
+ 每个已评估X对应0..1影响评估A
+ 0..1任务完成结算
```

不得建立任务轮次、筹办轮次、执行轮次、任务树、调用槽、任务信息版本或任务业务历史。旧规范中的同名对象和身份全部退出。

## 2. 身份与结构不变量

T、D、Vt、方法、X、A、状态节点、工作包、消息和原请求分别使用自己的稳定编码或强类型身份，不能互相冒充。

一个完整T必须满足：

1. T在任务集合根下恰有一个成员引用。
2. T恰好引用一个可读D；D最多反查出一个新版T。
3. T恰好引用一个Vt，Vt准确反向引用T。
4. Vt恰好持有一个任务状态实例特征，其当前值属于3200封闭状态枚举。
5. 每个X只属于一个T并引用一个方法节点。
6. X结束后必须有结束时间；改变型X具有完整实际状态组，读取型X以本次返回的读取材料结束（第10节）；X已评估时恰好引用一个A。
7. A中的T、D、X和方法必须与来源结构一致。
8. 任务完成结算按T唯一；没有成功结算不得伪造结算身份。

稳定编码唯一不等于业务资格成立。任务类必须读取完整结构核验类型、归属、基数和状态。

T、Vt、方法、X和A是内部治理世界场景中的信息存在。它们持有的实例特征F（如Vt上的任务状态）当前值变化时，按1160生成状态并挂入所在场景的状态列表，不另设世界树外的信息状态列表。D可看作存在，但不按存在处理，不归属场景，其F（如字段“有确定值”）更新不生成状态（0050第1.4节）。

## 3. 建立、复用和current-only读取

服务对象新需求发生按5170第2.1节读取正式S及本次真实操作来源；H侧同D可以有多次发生，S不是self需求、任务或完成结算。self/任务调用者明确执行再次需要操作后，经实际业务来源适用的既有合法治理路由判定承接；不额外要求新M/U，不把非语言来源强套行动请求。H同D不强制同self Ds/T，同次来源重投按原合同复用。不得按H D身份或首次来源去重吞掉已核验的新发生，也不得仅因收到新S就跳过完整性、当前来源及self承接复核。已结算T不因本规则重结算，普通读取/重试不自动成为新操作。

建立任务只接受一个已经可由需求类完整读取的完整需求D。补问、归类、指代澄清、分界等子需求都是普通完整需求，目标信息节点与目标特征F按3100、5170；任务侧不改写其目标，也不套用双根初始化例外。待完善的被认知需求本身不建任务、不进入查找方法。

- 没有对应T时建立T、Vt和`已建立`状态；
- 恰有一个结构完整的T时返回既有T；
- 多个T对应同一D时返回结构冲突，不任选；
- 不复制D的目标存在、完整目标定义或权重；
- 不因D当前已经满足而删除T，是否零动作由self fresh判断。

全部任务读取current-only。基础数据集不提供事实代次、历史截止、业务历史、墓碑、调用者owner分区或任务版本。需要一致读取T、D、Vt、状态、最近X和A时，由任务类在一次组合读取中形成自洽值式结果；上层不得分步拼成虚假快照。

## 4. Vt状态机

任务状态只由Vt上的任务状态实例特征当前值表达。合法状态及迁移读取3200，任何消息、队列位置、线程状态、日志、最近方法或最近X都不能反推或覆盖任务状态。

状态推进遵守：

1. 同状态写入返回无变化。
2. 入口先完整读取T和当前状态，再判断迁移是否合法。
3. 底层当前值已经变化而后续通用聚合失败时，必须重新读回；当前值等于目标状态则按已生效收敛，否则返回结构不一致。
4. 技术失败、依赖缺失、资源不足或消息失败不能改写成`已失败`。
5. 收束状态（`已完成`、`已失败`、`已取消`、`已结算`、`未执行但目标已满足`、`放弃结算`）只有经self fresh决议和manager复核才能重新启用，且只能迁移到第4.1节所列的`待查找方法`或`等待条件`。
6. `子需求不合法`只能由manager依self的“子需求不合法”通知写入，不是收束状态；其离开只按第5.5节，不得直接进入`待执行`或`执行中`。

### 4.1 状态迁移表

| 原状态 | 允许后继 |
| --- | --- |
| 已建立 | 待查找方法、等待条件、未执行但目标已满足、已取消 |
| 待查找方法 | 待检查条件、等待条件、子需求不合法、未执行但目标已满足、已失败、已取消 |
| 待检查条件 | 待执行、待查找方法、等待条件、子需求不合法、未执行但目标已满足、已失败、已取消 |
| 待执行 | 执行中、待查找方法、等待条件、未执行但目标已满足、已取消 |
| 执行中 | 待影响评估、待查找方法 |
| 待影响评估 | 等待自我决议 |
| 等待自我决议 | 待查找方法、待检查条件、待执行、等待条件、已完成、已失败、已取消 |
| 等待条件 | 待查找方法、待检查条件、待执行、子需求不合法、未执行但目标已满足、已失败、已取消 |
| 子需求不合法 | 待查找方法、待检查条件、等待条件、已取消 |
| 已完成 | 已结算、放弃结算、待查找方法、等待条件 |
| 已失败、已取消 | 待查找方法、等待条件 |
| 已结算、未执行但目标已满足、放弃结算 | 待查找方法 |

各行补充约束：

- `执行中`→`待查找方法`只用于撤销尚未进入动作的执行（W3-A尚未调用、未形成动作动态）；已进入动作的执行只能经`待影响评估`推进。
- →`未执行但目标已满足`是执行前收束：执行前fresh确认所服务需求目标已满足，未建立执行实例即收束。
- `已完成`→`已结算`为结算收尾（普通子任务由直接父任务正式接收贡献，最终服务来源在服务值实际入账并读回，6190第3.3、3.4节），经贡献阶段完成；`已完成`→`放弃结算`在结算时所服务需求已无活动需求时写入（R108）。
- 收束状态离开均为重新启用，按第12节由self fresh决议、manager复核。

状态修改只写Vt的唯一任务状态实例特征，且只经第4.2节统一入口；不得在状态已经前进后回滚或删除与该状态对应的执行结构。

### 4.2 任务状态迁移形成因果

每次任务状态迁移都形成一次内部治理动作并交付因果（1190、4220第2节）。

1. **统一入口。** 写入任务状态的全部调用点只经任务owner的统一迁移入口，入参为任务、后状态和迁移原因；入口读取当前状态，按第4.1节封闭迁移表校验，不合法返回状态不允许。不得在入口之外直接写任务状态特征。
2. **迁移顺序。** 入口按以下顺序完成一次迁移：

```text
写入因素特征（任务虚拟存在，生成场景状态）
-> 发布治理迁移记录（动作来源，持有原因材料引用）
-> 建立治理动作（定义＝该“前→后”配对的迁移定义，主体＝自我）
-> 提交任务状态特征，建立前后状态与原子动态，关联“导致变化”
-> 交付实际发生（前置窗口取场景内动作前的状态与动态，交因果服务）
```

3. **迁移记录。** 治理迁移记录的字段与持久性按4211第4.1节：任务、前状态、后状态、动作时间、原因种类、原因材料引用。经贡献阶段完成的结算收尾（`已完成`→`已结算`的直属结算收尾与最终结算收尾）以已发布的贡献阶段为迁移记录，同样交付因果。
4. **迁移定义。** 第4.1节每一对“前状态→后状态”登记一个任务状态迁移动作定义，初始化时挂在任务集合根下，由动作方法投影形成动作概念；同一配对由不同治理操作触发时定义仍只有一个，区别由原因种类与因素特征体现。执行主体统一为自我（服务根目标存在）。
5. **因素特征。** 任务虚拟存在持有以下实例特征，由任务owner在迁移之前写入；写入时按1160生成场景状态，落在前置窗口内成为因果条件：

| 特征 | 值 | 写入时机 |
| --- | --- | --- |
| 承接依据 | 自我首次复核、状态变化复核、条件子需求、因果子需求、复合子需求、外部服务要求、行动请求、扫描补齐 | 承接迁移前 |
| 候选结论 | 有候选、无候选 | 消费方法候选前 |
| 条件结论 | 具备、等待条件、需子需求 | 条件核验结果形成后 |
| 执行进入结论 | 已进入动作、零动作 | 开始执行或零动作恢复前 |
| 影响评估结论 | 按影响评估的需求结果取值 | 影响评估完成后 |
| 后继决议 | 继续查找、等待条件、完成、失败、取消 | 发布后继决议前 |
| 不合法子需求 | 引用子需求节点组 | 收到“子需求不合法”或“子需求恢复合法”通知时 |

   因素特征只引用任务自身的材料；“不合法子需求”只保存引用，不在需求侧生成任何状态（R99不变）。各特征的值域与概念按现有特征登记方式登记，枚举值增减须修订本表。
6. **交付时机。** 迁移完成后同步交付实际发生；前置窗口规则不变（1190第5节），取本场景中上一次同结果之后到本次动作时间之间的状态与动态，因果服务按同一任务内归纳。
7. **失败分账。** 迁移记录、动作、状态提交或交付中的工程故障按第14节处理，不改写成任务业务结果；动作已建立而后续步骤失败时保留已发生材料，不重做迁移。

## 5. 筹办材料与方法选择

筹办是manager围绕当前T分步调用现有能力的运行过程，不形成独立节点或轮次。它可以多次执行以下步骤：

1. fresh读取D目标与满足状态：按目标信息节点持有的目标特征F当前值（关系型目标同样读取其owner维护的F，3100方案A）；
2. 按目标特征类型查找能改变该F的方法（5350第8节），不按名称或函数名直接调用；方法头、必要条件、参数及结果获取须真实存在，缺配对沿既有按需学习，不预造方法头或C/R；
3. 对候选方法逐一读取完整条件—结果配对；
4. 实例化交付方法条件到Vt，依据Vt条件信息查找并绑定实际对象和参数；
5. 核验条件、能力、权限、安全、资源和预期损耗；
6. 按方法结果要求和自我当前感知渠道形成具体结果获取方案；
7. 选择唯一适用方案，或形成等待、缺方法、条件不满足、不可比较、并列无法裁决等结构化结果。
8. **尝试执行。** 按目标特征类型查找到的候选方法只有一个，而其条件—结果对的结果为空或不能确认适用于当前目标时，以该方法已有条件节点为依据选为尝试执行；条件节点多于一个时取条件区间最小值所在的条件节点。条件照常筹办和核验，执行标记为尝试；执行后把本次方法执行信息（实际条件、实际结果及动作前后场景）传递给模拟世界，由学习据此验证或补全条件—结果对，来源为尝试（5370第5.3节）。候选方法多于一个时不尝试，按第7项保留并列。

候选列表、扫描游标、线程局部缓存和队列位置都不是任务事实。需要长期保存的选择结果必须进入T或X的正式字段；本任务方法筹办条件要求由Vt按第5.1节承载，不能只停留在线程临时材料中。临时材料在决定完成后可以释放。

找不到方法不等于任务失败。self按第5.3节确认方法能力缺口后登记缺失方法列表并保留任务等待，不能仅凭无方法宣布失败、取消或完成。可行动的条件缺口仍按既有合同确认子需求；有独立合法依据的失败、取消裁决不受此限制。manager和worker不能自行产生需求。

### 5.1 方法条件交付与参数场景

本节按20261015用户裁决，固定通用链路：方法声明/条件结构 → 方法实例化并交付Vt条件信息 → 筹办查找实际信息 → 临时参数场景 → 本能方法执行。它修改内部治理的任务条件组织，目的为让任务明确还需查找和满足什么；不直接修改现实世界特征，不预造状态、动态、因果或方法经验。

1. **条件交付。** 方法owner负责完整方法实例；任务owner在将实例绑定/交付给任务时，将执行需要的条件信息组织到该任务Vt。Vm按5350第6节提供固定有序的信息类型及范围概念，C提供具体参数的值、值域、状态和关系，并保留方法共同约束及各条件分支。任务不修改规格，也不把规格的对象范围当作具体条件值域。完整图复制本身没有任务身份时不写Vt；任务实例化交付成功必须同时满足实例绑定及Vt条件信息可完整读回。仅有任务到实例根的引用不算完成交付。
2. **要求内容。** Vt条件信息保留来源方法实例、条件分支/配对（已存在时）、固定参数位置，以及对应信息类型、范围概念和具体条件引用；允许的参数类别不限于存在或特征。未找到实际对象时保留要求，不用虚构对象编码填空。没有经验配对的声明不得为交付而补造配对。条件要求与实际当前值分开；Vt不成为外部事实或抽象方法定义的第二权威。
3. **分支与关联。** 多方法和多分支分别组织；同一分支必要条件共同核验，不把全部备选分支按AND合并。选定分支后使用该分支及其共同约束。有关联的条件按C引用的固定参数位置绑定，例如先从自我服务任务集合找到成员T，再核验同一个T的完成状态；不得以另一任务的完成状态补足，不从参数邻接推导所属关系。要求引用的值域或关系定义改变时必须重新筹办，不能沿用旧就绪结论。
4. **查找与缺口。** 筹办读取Vt条件信息，通过相应世界树及正式owner查找存在、特征等信息。现实实参只在自我所在场景及其子场景内查找，不向父场景上溯。需求节点等不归属场景的信息节点不在场景中直接查找，而是取场景内存在持有的引用特征所指向的实际节点。存在位置的候选须同时满足：属于规格的范围概念、具有规格声明的全部必需特征类型、特征值落在所选分支C的值域内并满足C的跨位置值约束；特征位置取其所属存在位置的已选对象上该类型的特征。任务/方法虚拟存在的特征通过其正式治理入口取得，不将其伪装成现实存在或跨世界复制事实。条件能区分出唯一候选时直接绑定；条件区分不出多个候选时，说明已知差异与本方法目的无关，任选其一执行，实现固定取稳定编码最小者以便复现，所选是否合适由本次结果验证并经学习收窄值域（世界上没有完全相同的存在，差异若影响结果终会经学习进入条件）；本条只适用于参数候选，不改变第5.2节因果分支多解保留。业务条件尚缺时保留具体缺口；可通过行动补齐的必要条件由筹办返回manager，再由manager通知self判断、建立或复用子需求。读取失败、损坏引用等工程故障走工程保障，不生成业务子需求。子任务报告完成后，父任务重新读取正式信息，不以完成通知代替条件事实。
5. **参数场景。** 实际调用前，任务依据当前有效Vt条件信息，将已找到并核验的实际信息节点引用按规格的相同顺序装入临时参数场景，不按类型或概念去重合并位置。各信息类型经其正式owner读取；特征值为内联存储时，经对应特征节点读取，不虚构独立值节点。函数实际需要的全部业务输入均通过此场景提供，不能再从隐藏的调用材料取得必需输入。容器不进入世界树、不持久化到Vt；任务负责组装，执行函数只读其绑定，用完释放。它保存引用而非外部当前值的长期副本，读取时取得节点的最新正式内容；引用信息的修改权限仍按5360执行。
6. **执行前复核。** 引用仍存在不等于条件仍满足。任务和函数在动作开始前依各自合同复核固定位置、信息类型、概念范围及C中的取值、状态和关系；业务条件已变化则回到筹办或等待，零动作，不记录虚假执行。规格与函数不一致、结构损坏或读取失败按5350/5360走工程诊断，不伪装成待补条件。当前值通过参数场景读取可以更新，但不因此擅自替换所选方法、对象或分支；实际动作前取值和后续结果仍由同次执行X留存，不能用后来读取的值重写动作前事实。
7. **一致性与生命周期。** 绑定与条件交付共同构成可用任务实例状态，由task owner负责发布和读回；重复采用也须核验两者完整一致。未完整交付不进入条件就绪或执行，工程失败不得伪装为业务条件不足。方法候选扩充、实例切换或所选分支变化时，同步更新相应Vt条件关联并重新核验；旧要求不得混入新分支。Vt条件随任务治理保存，临时参数场景随调用释放；已开始X的输入和来源不受后续Vt更新改写。退出条件引用不得删除其引用的世界节点、共享概念或仍被X使用的来源。

本节替代“绑定只写任务到实例根”“筹办仅从方法读取而不交付Vt”的旧限制；保留完整方法复制及方法定义owner边界。

### 5.2 因果辅助筹办

本能力属于内部治理：解释当前需求的实现途径及方法条件缺口，向self提供可核验的子需求建议；不直接修改现实存在，不生成预测状态、虚构动作或新的因果知识。正常结果是筹办材料及必要的正式任务治理推进，实际改变仍由各任务的方法负责。

筹办的真正目的为根据所需条件向前追溯方法或更前置条件。它不是先判断某个被动处理已经在途再补解释，也不是仅查询因果图后返回等待。原需求目标和选定方法尚缺的条件均可作为反向追溯的所需结果。

通用顺序为：

```text
fresh读取需求目标和当前正式事实
→ 优先直接查找能改变目标特征且结果适用的方法
→ 核验所选方法分支的条件
→ 对未满足条件反查因果；无直接适用方法时从需求目标反查
→ 主动动作追溯可调用方法及其条件；被动动作继续追溯完整触发条件
→ 对更前置条件继续查询，真实满足则停止该分支，无路径/未知/循环等保留具名缺口
→ worker返回筹办材料，manager复核并发消息，self确认后建立或复用子需求
```

1. **查询范围。** 输入保留目标、共同场景、实际参与者与明确值/值域；当前事实通过正式owner取得。不得将条件声明、预测结果或最新状态记录冒充实例当前值。内部治理与现实世界的实例范围分开，概念可以共享。对象绑定缺失、多义或冲突时不任选存在、不造占位编码。
2. **分支组织。** 每条分支的全部必要条件共同核验，不同可选分支分别筹办。按现行选择规则不能唯一确定时保留多解，不按遍历顺序或稳定编码任意选择，也不把各分支缺项全部派成AND子需求。环、无已知路径、动作能力缺失、未支持的目标表达与未知使用方式分别保留。
3. **主动与被动。** 依据因果内部动作的触发方式决定追溯方向：主动链必须定位真实可调用方法并继续检查其条件，仅有动作概念不算取得执行能力；被动链继续追溯其完整触发前提，不建立空方法头，不伪装为可调用动作。未知动作及触发方式尚未确定不能按被动路径跨过。分类及预测边界唯一依1190第3.3—3.4节、4320第4—5节；因果图覆盖不能替代执行前真实条件复核。筹办可以在触发尚未发生时得出所需前提，不把本次已触发证明作为反向分解的先决条件。
4. **子需求依据。** 能够通过行动补齐、实际对象和目标可明确表达的状态缺口才可形成提议。因果追溯所得前端不是原方法直接条件，必须保留“需求/方法原缺口→来源因果及所选分支→角色绑定→前端目标”的完整值式依据。不能覆盖原条件项冒充直接投影。self发布前重新读取来源、关系和当前目标；依据变化则重新筹办，不以旧提议发布。一个需求仍至多关联一个任务，重复筹办复用已有同义子需求。
5. **被动等待。** 只有实际处理方正式信息能证明本次触发已被接纳、对象和分支相符且仍有效时，才进入等待该结果；未知触发不解释成在途。等待期间保留来源定位并释放工作线程，不重复触发已在途动作；结果或有效性变化后重新读取真实条件。触发失效、所选因果或绑定变化时回到筹办。既有等待复核不得以“目标尚未满足”为由重复启动仍有效的被动处理。
6. **结果分流。** 已定位真实方法且其条件真实具备时，才可进入既有执行前核验；逆向追溯得到缺少的可行动状态则提出子需求；被动前提已具备但目标尚未出现时进入相应条件等待，只有满足第5项证据时才称为被动在途。其余边界保留明确的未解释材料，不伪造任务失败、已触发、条件就绪或执行成功。没有可用因果知识时，保留原有合法直接方法和直接条件分解能力，不能因辅助查询为空将其阻断。最终结果仍由当前世界信息独立复核，不能用筹办路径替代结果。
7. **生命周期与职责。** 查询请求、图、路径选择和缺口解释只作调用期筹办材料，不另建因果任务、业务轮次、被动方法或长期材料副本。manager、self消费时独立复核；工程错误进入日志/弹窗和中止路径，不形成业务子需求。任何实际动作前仍按5.1节与第6—7节读取当前条件并完成已有安全判断。

尚无分类依据、触发读取或可表达目标的分支必须保留具名缺口，不能以保守占位结果宣称因果辅助筹办全闭环。

**需他方材料的目标。** 目标F的值需要他方提供材料时（如分界、归类、指代澄清、字段补问），筹办采用同一通用模式：

1. 先读目标F当前值；已满足时只取正式材料，不为取得相同结果再次询问或写回。
2. 已有正式规则、适用范围和充分判读材料时，筹办写回类方法的规则分支直接写回，不要求先问人。
3. 规则依据不充分且确需他方材料时，由输出类（询问）方法的真实操作提出询问子需求，经self确认后由子任务执行；输出类方法的直接结果是输出材料的F，不是依赖回答的目标F，不得以“能输出”冒充“能直接满足”。
4. 已有本目标及来源匹配的实际输出时，复用正式关联并等待明确回答，释放worker，不重复发问；询问不承诺回答必然到来。
5. 同目标、同会话及主体的明确回答关联到达后，筹办写回类方法的回答分支；与规则分支择一核验。不得取最新消息、时间邻近或正文相似代替来源关联。
6. 子任务完成、输出、发送都不满足父目标；父目标只按owner维护的目标F当前值判定，写回后由任务独立fresh读回。
7. **字段补问的答案写入（R114）。** 字段补问由询问方法问出问题并等到答案（5380第3.6节）。子任务（询问）结束后，父任务（分解出该补问需求的任务）重新筹办时读取补问需求“答案”项所引用的信息（消息转换生成的值陈述，或自我写入的信息，7240第5.5节），按补问所指字段经需求owner写入被认知需求的该栏，字段内容来源记录指向该答案信息；写入后补问需求按第6项经当前满足复核达成。写入前复核该栏仍未知、该答案仍未被采用；复核不通过不写。答案有多条且值不同时不写，补问需求保持未达成，记录日志。写入是父任务筹办中的内部治理操作，不是本能方法，不经第3、5项的写回类方法与回答关联；需求不生成状态（R99），写入由需求owner完成并记录字段内容来源，不另形成治理动作与因果。答案来源为自我写入时是否先向交互者确认属于自我意识，本规范不作规定，按同样方式写入。

### 5.3 缺失方法确认与知识等待

完整查找范围内无候选，或候选已完整核验且任务选择没有适用结果，分别交self确认能力缺口；不能把粗召回命中本身当作适用性裁决。参数缺失、对象缺失、当前值未知、方法条件未齐、候选未核验完、查找未完成、结构缺口及工程故障均不得降格为“缺失方法”，仍按各自材料、条件或工程处理路径处理。

self消费结论时fresh核对T→D、当前目标、原工作请求、候选核验完整性与对应候选材料；无候选须对应原工作完整空结果，无适用结果须对应已完整核验的候选集合。材料已过期时不登记旧缺口，交由现有状态变化复核路径处理。确认后调用方法owner登记[5350第2.1节](5350_子规范_方法治理详细合同.md#21-独立缺失方法列表)，**不为此建立方法学习正式需求节点**，也不假定所有目标都可实现。本条只约束缺失方法登记路径；归类等子需求是普通完整需求（5170），不属于本条禁止范围，确认后可进任务链。

任务保留并进入调度层知识等待，不忙循环重复筹办同一缺口；知识等待是等待原因和软筹办阻塞，不新增Vt任务状态。不同阶段保留各自合法状态，无适用结果的任务可以仍处于待检查条件，但不得持续派发同一工作，也不得设成阻断未来复核的永久硬阻塞。

manager在派发原筹办工作前保存相关方法知识基线，技术重试不覆盖该基线；登记等待时使用原基线，避免吞掉派发至等待登记期间已发生的知识变化。比较等待条件时关注任务/需求身份、目标和相关正式方法知识闭包，不把轮询、命中计数、阶段变化、候选材料编号或条件当前值变化单独当成缺方法恢复依据。完整无候选保留空候选闭包，缺失头的登记也不等于可用方法知识增加。

相关正式方法知识的变化以方法状态表达（5350第6.3节），等待由方法状态唤醒：有候选方法的等待（候选尚无配对等待学习，或等待配对补全）以候选方法的虚拟存在节点作为依赖键，该方法虚拟存在形成状态即按节点键唤醒该任务；没有候选方法的等待（尚无方法）仍以笼统的“方法知识”键登记，任何方法虚拟存在的配对数发生变化即唤醒这类等待，以后有按方法头的精确召回键时再改为精确唤醒。被唤醒的任务直接按既有路径重新筹办并清除相应软阻塞，manager不把学习结果交self复核，也不等待self决议是否允许重新筹办；方法状态唤醒只提示重读，不是恢复执行、任务完成或目标满足的充分依据。不设“方法学习结束”消息加事后查询受影响任务的专门唤醒路径；学习线程与self之间的学习提交、学习结束接收按现有分工保留。任务重新筹办后仍须正常选择方法、核对条件和执行前规则，学习线程不能代替任务与self推进状态。

### 5.4 参数位置关系的筹办与结果消费（20261021）

方法C/R的同一、不同和集合成员关系，按同一固定参数位置交付Vt并联合核验；特征所属按5350第6节规格声明绑定，同属场景由第5.1节取实参范围保证（20261106 R97）。方法结果选择必须证明关系效果覆盖当前D实际目标；观察沿同一X及冻结绑定核验实际结果，集合含目标不能用非空集合、任意固定成员或I64成功标志替代。模拟学得知识供后续筹办使用，不等于现实执行效果已成立。该规则不改变任务准入、现实动作授权或身份采用来源。

### 5.5 子需求合法性判定与“子需求不合法”挂起

是否为某个需求生成任务由self经需求合法性判定裁决（3100第1节）。本节规定判定在任务链上的作用，判定依据属于自我意识，现阶段不规定，默认合法。

1. **判定位置。** self在每个会使manager为某需求建立任务的发送点之前调用需求合法性判定（8100第3节）。判定只读，不修改需求、任务或世界事实，不发消息。判定合法时按既有承接路径发送；判定不合法时不发送该需求的承接消息，manager因此不为它建立任务。被判不合法的需求照常保留，不改其活动状态。
2. **无父任务的承接。** 双根复核、显式请求、外部服务要求、行动请求和全树扫描补齐判定不合法时，只不承接，本条self消息按需求不合法未承接结束，不重试。
3. **有父任务的子需求。** 条件子需求、复合目标子需求和因果子需求判定不合法时，不合法子需求不放入提交的组或裁决；self向manager发送“子需求不合法”通知，携带父任务定位和不合法子需求节点组。同组其余合法子需求按该提交入口的完整性合同处理：入口要求逐项齐全时整组不提交，只发通知。
4. **进入。** manager收到通知后，只在父任务处于`待查找方法`、`待检查条件`或`等待条件`时写入`子需求不合法`；父任务已离开这些状态时，通知按任务状态已变化丢弃，不写状态。
5. **挂起与重新筹办。** 挂起的是依赖不合法子需求的筹办路径，不是整个任务。处于`子需求不合法`的任务重新筹办时，排除需要这些子需求才能满足条件或完成分解的候选方法及对应的复合分解、因果路径，其余候选照常查找、核验和执行；找到其它可用方法时按既有路径迁移到`待检查条件`等合法位置；没有其它可用方法时留在本状态，按第5.3节知识等待方式等待相关方法知识变化后再筹办，不按扫描周期轮询。本状态不结算、不清理。
6. **挂起依据。** 挂起依据由父任务虚拟存在的“不合法子需求”持久实例特征承载（第4.2节）：收到通知时由任务owner写入不合法子需求节点组，重新筹办据此排除依赖这些子需求的候选，解除时据此核对。重启时从该特征读回排除依据，按读回结果继续挂起与重新筹办，不需要self对已判不合法的子需求重新判定。
7. **恢复只由self改判。** 同一子需求再次经过发送点并被判定合法时，self照常发送承接消息，并发送“子需求恢复合法”通知；manager据此经任务owner从“不合法子需求”特征中移除对应子需求，不合法子需求全部恢复合法且父任务仍处于`子需求不合法`时，把父任务写回`待查找方法`重新筹办，被排除的候选重新可选。时间经过、扫描或manager自身都不能解除挂起。
8. **通知可靠性。** 两种通知经manager既有邮箱接纳；接纳失败由self按既有重投间隔重投；重复通知幂等，状态已是目标值即视为完成。

被判不合法的子需求不形成永久硬阻塞：父任务始终可经其它方法、方法知识变化或self改判离开挂起。该子需求不参与权重分配（3100第8节），父任务归集时按零贡献计入（第12节）。

## 6. 执行前冻结和结果获取硬门

进入`待执行`以前必须冻结：

- T、D和采用的方法；
- 实际作用对象和参数；
- 预计变化阶段组；
- 方法要求确认的对象、特征、允许结果和证据质量；
- 至少一条当前明确、合法、可实现的结果获取方案；
- 多渠道的组合、优先、备用和冲突处理规则；
- 必要安全硬门、资源条件和现实执行授权要求。

每条具体渠道方案必须具有：渠道类型或能力身份、正式读取入口、读取目标、触发时点或等待条件、证据质量、顺序/优先关系，以及暂不可用和永久不可得的分支。整体方案还必须冻结允许结果、禁止结果、多渠道关系和冲突裁决规则。没有禁止结果时显式表达“不适用”，不得用未读取或空集合猜测没有禁止项。

无明确可实现结果获取方案时零动作。结果不要求立即取得，但必须说明由哪个现有感知渠道、在何种条件下、以什么正式材料最终判定。“可实现”要求当前已有合法读取入口，或者已有明确结果生产者和不会丢失的等待/唤醒路径；能力目录中的抽象名称、未装配外设、预期未来能力、日志或局部返回值都不满足。

冻结材料只能服务本次X。条件、参数、作用对象、方法或结果方案发生实质变化时，回到筹办重新形成材料；不得原地把旧动作解释成新方案的执行。方法知识此后被原地修订，不追改本次X已冻结的方法、配对、参数和预测。

### 6.1 预计影响结构

预计影响采用“阶段串行、阶段内并行”：

1. 至少有一个阶段；阶段顺序从0开始连续递增；每个阶段至少有一个变化项。
2. 同阶段内，同一作用对象和同一实例特征F不能重复；同阶段变化没有先后关系，不同阶段按顺序推进。
3. 预计项字段：作用对象、实例特征F（执行冻结时把“作用对象+特征类型”解析为具体F并保存）、可选预期变化关系、可选预期值域、必须出现标记。
4. 作用对象、F、可选变化关系和可选值域必须是当前存在的节点；预计项保存已经绑定的实际作用对象，不保存抽象角色。
5. `必须出现=false`表示该变化可以缺席；缺席时不进入预计缺失组。
6. 预计变化只存在于X的预计项中，不是状态。

## 7. self执行前判断

self读取当前D、T、冻结材料、整体资源、安全事实和必要授权，形成：

```text
执行
暂缓
拒绝
重判
```

只有`执行`可以由manager建立X并派发W3-A。该判断不是动作成功预测，也不允许self直接调用方法、裸写任务状态或修改世界事实。

含现实改变的普通方法必须在动作前取得适用的正式现实执行授权；内部治理的固定代码和纯观察按各自合同执行，不伪造现实改变授权。

## 8. 执行实例与W3-A

每次真实方法调用建立一个X。建立X时保存T、方法、开始时间和预计变化阶段组，并把T推进为`执行中`。

建立X后、W3-A调用前，在执行主体所在场景形成动作动态，其唯一来源为该X（1170、3200）；挂接只核验执行主体属于该场景。动作动态对目标信息节点的引用以及结果动态与它的“导致变化”关联可以跨场景、跨世界，但不因此建立跨世界父子或成员关系。动作动态建立失败不得调用动作。

W3-A工作包只允许完成一次动作调用：

1. worker复核工作包、T、X、冻结、停止状态、安全硬门和授权；
2. 前提不成立时不调用动作，返回具名非成功；
3. 前提成立时调用一次本能函数或组合方法入口；
4. 明确记录动作未发出、已发出或发布状态未知；
5. 已发出或可能已发出后不得因回执丢失、队满、超时或记录失败重做动作。

动作函数返回只证明调用结果，不证明目标世界状态已经改变。

## 9. W3-B结果获取

W3-B按冻结的结果要求读取真实材料，不执行动作：

- 即时结果可以在W3-A返回后直接触发；
- 延迟、异地或外部条件未满足时，把X登记为等待结果并释放worker；
- 正式状态通知到达时，manager先按等待X补查已有材料，再形成W3-B工作，避免通知先到造成丢失；
- 多渠道材料按冻结规则组合；来源冲突必须保留冲突，不任选有利材料；
- 渠道失效后可以采用冻结允许的备用渠道；没有合法渠道时保持结果未知。

W3-B在结束X以前必须fresh复核本次请求材料与正式读回材料一致。状态材料至少核验作用对象、实例特征F、固定值和时间范围；仅匹配对象和粗特征类型不足以接纳兄弟特征状态。

只有必要渠道证据全部取得、证据质量达到要求、渠道关系完成组合、冲突已经按冻结规则裁决、允许结果和禁止结果均得到所需判定时，结果方案才闭合。任一条件未知都保持X等待结果或进入具名不可继续分支，不得用空值补齐。

## 10. 执行结束与影响评估

X结束按方法类型接受结果材料。共同要求：X属于T且仍为可结束状态；结束时间不早于开始时间；相同请求重复提交精确收敛，异义重复拒绝。

改变现实的普通方法（改变型）只接受正式状态节点作为实际结果，另须：

1. 状态使用合法实例绝对UTC强时间，事实发生时间位于执行时间窗内；
2. 状态身份不重复，按强时间升序、相同时间按稳定编码排序；
3. 状态的作用对象与F和本次结果要求一致，且其结果动态与本X动作动态存在“导致变化”关联。

读取方法（观察型）的正常结果就是本次返回的读取材料（作用对象、实例特征F、读到的准确值及渠道），由影响评估和后续治理消费，不要求为此生成状态或结果动态，也不以状态闭合作为结束条件：

1. 本次观察取得时间就是本X读取动作的时间，不另设载体；被观察事实的发生时间可以早于执行开始，不因本次观察改写；
2. 读到的值与F当前值不同时，由该F的事实owner按1160另行生成状态，不由本X补造或冒充；
3. 以获取信息为目的的需求不靠观察生成状态满足：治理把读取材料写入待完善D后，该字段“有确定值”F由未确定变为确定，需求随之满足（5170）。

合法结束后X进入`已结束待评估`，T进入`待影响评估`。影响评估至少形成：预计命中、预计缺失、计划外变化、方向/幅度/值域比较结果或不可比较、多渠道验证结论、禁止结果验证结论、副作用/安全事件、归因充分性和D的fresh当前满足材料。每一项必须区分已验证通过、已验证不通过、未验证、冲突和按合同不适用，不能用单个总布尔值吞掉未知。

当前比较能力如果只能证明对象、类型和阶段命中，就必须明确标记未验证方向、幅度和值域；不得据此盲目继续原动作。保守后继是回到self决议，通常重新筹办或等待更完整材料。

影响评估完成后T进入`等待自我决议`。A不直接发布完成、失败、取消或下一次执行。

### 10.1 预计与实际匹配

匹配键为：作用对象节点相同、实例特征F相同、实际状态时间不早于当前阶段允许起点。按阶段顺序处理；每个预计项选择尚未使用且满足键的最早实际状态，同一时间按状态稳定编码确定；同阶段内不要求预计项之间有时间顺序；本阶段至少命中一项时，下一阶段允许起点推进到本阶段全部命中的最晚时间；必须出现但没有命中的预计项进入`预计但未发生项组`；已命中的实际状态进入`符合预测状态组`，全部未使用的实际状态进入`计划外状态组`。预期变化关系与预期值域须经正式二次特征求值核对；未核对时“符合预测”只表示对象、F和时序命中。

## 11. self后继决议与状态发布

manager只向self发送T、X、A和正式结果的定位。self fresh读取完整当前材料后形成完成、继续、重试、重新筹办、等待、失败或取消。完成要求结果方案闭合、必要验证通过或明确不适用、没有未处理的禁止结果/冲突，并且归因达到方法要求；D因其它来源恰好满足时不能伪造本次X成功。

manager复核：

- 决议绑定同一T、D、X和A；
- T仍处于允许消费该决议的状态；
- 决议所要求的目标、等待生产者或可重试原因仍成立；
- 没有旧消息覆盖较新的current-only状态。

复核成功后由任务类发布状态。继续、重试和重新筹办必须先回到`待查找方法`、`待检查条件`、`待执行`或`等待条件`中的合法位置，再重新形成执行前材料并建立新的X；不得复用旧W3-A工作包。

## 12. 完成结算与重新启用

正式完成任务的结算满足：

1. 只接受`已完成`的T；
2. 绑定完成来源、最后相关X和A以及完整结果闭包；
3. 完成结算按轮计（3200第10节）：同一轮（建立或一次重新启用至其后首次正式完成）内只结算一次；已结算任务重新启用后再次正式完成，按新的一轮再结算一次（R108），此前各轮的结算既不撤销也不重复；
4. 同义重复返回既有结算，异义重复冲突；
5. `已失败`或`已取消`不结算；
6. 需求当前满足、需求结算、价值到账和方法学习不是任务完成结算前置。

结算只向直接父任务交接，接收者必须由D的直接父需求反查唯一T确定；父任务尚未建立时保留原完成结算待补齐，不跳级或丢弃。无父需求的根任务不生成虚构接收者。服务结算值按6190计算，父任务只接收自己的直接子任务结算，不按子孙任务总数重新计值。

任务owner核验并保存来源子任务、唯一完成结算及直接父任务的关联；接收事实与父任务汇总一致发布，重复消息只触发正式事实读回，不重复累加。父任务可以接收多个子任务的结算，但只能在自身正式完成且直接子结算完整归集后向自己的父任务交接一次。完整归集指该D全部直接子需求的T均已收束：已完成者其完成结算已被本任务接收，已失败、已取消者按零贡献计，已清理者以其清理前已交接的结算为准，被self判定不合法、未承接的直接子需求没有T，按零贡献计入，不阻止归集；归集门禁按6190第3.3节，不以消息已收小计提前封口。接收子结算仅触发条件、结果和需求复核，不自动改变为完成。服务值更新由自我直接调用6190结算治理函数完成（内部治理函数，不是本能方法），不恢复“结算服务需求”任务作为必需接收者。

manager发布`已完成`后，在任务完成结算（self编排、任务owner发布）发布前不得释放结算所需的X、A和运行定位；任务完成结算发布后，manager才释放相应运行定位。服务值结算由self另行调用6190，不属于此处的任务完成结算。

收束任务重新启用时：

- 必须由self fresh确认同一D仍需或再次需要治理；
- manager复核后迁移到`待查找方法`或`等待条件`；
- 重新启用本身不删除旧X或A，其清理按第12.1节；
- 不撤销既有完成结算；
- 同一轮内不允许同一T再次完成结算；重新启用后再次正式完成按新的一轮结算一次（3200第10节）。

### 12.1 X/A生命周期

X、A在以下任一期间受保护：T尚未完成结算且X/A为其结算来源；被方法学习采纳为来源且本次学习处理未结束；以X为唯一来源的动作动态仍存在期间X受保护（含该动作动态被因果概念保留为代表实例）；仍被其它正式事实引用。其余X、A按0050 §1.5定期、定量删除，阈值与时机由维护规则统一配置；清理先核验引用、再解除关联、最后删除节点，不改变任务状态与已结算事实。叶子需求按5170第5.1节清理（已满足或已失活、T已收束、已完成者完成结算已交接直接父任务、无其它正式引用）时，其T、Vt随之清理，且须先满足其全部X/A不再受保护。

## 13. 消息、幂等与恢复

消息按类型交给对应处理函数。共同信封只保存不可变消息身份、消息类型、原请求身份和必要路由定位；具体字段由各消息类型定义，不建立万能消息对象或第二业务账。

消息接收只证明工程交接，不证明业务操作完成。消费者必须独立读回正式current-only状态。

重复与恢复规则：

- 同消息身份同义重复收敛；异义重复拒绝新输入，不删除先前合法输入；
- W3-A可能已执行时只查询或恢复原X，不新建X、不换键、不重做动作；
- W3-B等待可以在重启后根据T、X和正式状态材料重新发现；
- 已完成但尚未结算的T必须继续可被self发现；
- 已存在正式结算时，即使manager运行定位已经释放，self也可以按结算事实收束原消息；
- 不具备跨进程恢复能力时必须明确返回未实现，不得假装恢复成功。

## 14. 失败分账

至少区分：

| 类别 | 处理 |
| --- | --- |
| 入口拒绝/身份冲突 | 零业务写入，终结冲突输入并反馈 |
| 资源暂不可用 | 保留原请求和已形成进度，等待重试 |
| 依赖未就绪 | 只有业务材料尚未形成（状态材料不足、无具备内容的方法、来源前驱材料未形成）才是合法等待：等待明确生产者或就绪唤醒，不忙循环；结构类依赖（读取接口未装配、owner结构未初始化、先天特征类型槽或正式概念未就绪）在运行期出现属装配缺陷，进工程诊断并中止受影响路径，停机期间按已停止处理，不登记等待 |
| 依赖未实现 | 明确返回未实现，不靠定时重试变成功 |
| 动作明确未发出 | 可以由self决定重试或重新筹办 |
| 动作已发出、结果未知 | 只恢复W3-B，禁止重做动作 |
| 业务目标无法继续 | 由self决定失败或取消，再由manager复核发布 |
| 内部结构不一致 | 停止受影响路径并保留诊断，不改写成业务失败 |

## 15. 验证与完成声明边界

最低验证覆盖：

- T/D/Vt结构不变量和状态机；
- 统一形状子需求入链、按目标F筹办及fresh求值；需他方材料目标的通用模式中询问／发送不替代满足；
- current-only组合读取，不依赖事实代次或历史；
- 多次筹办不产生轮次对象；
- 无结果方案零动作；
- 等待方法知识的任务：有候选按候选方法虚拟存在节点由方法状态唤醒，无候选按“方法知识”键由任何方法配对数变化唤醒，值未变不唤醒，被唤醒后直接重新筹办、不经self学习复核；
- X建立和W3-A单次调用；
- W3-B即时、延迟、异地、多渠道、通知先到和渠道失效；
- 实例特征F身份核验；X开始形成以X为唯一来源的动作动态；改变型以“导致变化”归因、读取型以返回材料结束；观察取得时间即读取动作时间；
- 预计项保存F及按作用对象+F匹配；X/A保护条件（动作动态存在期间X受保护）与定期定量删除；父任务子结算完整归集（失败/取消零贡献）；
- 方向、幅度和值域未实现时的保守后继；
- self七类决议、manager复核和合法状态发布；
- 子需求合法性判定的调用位置、判不合法不承接、`子需求不合法`进入与丢弃、排除候选重新筹办、只由self改判恢复及通知幂等；
- 完成状态到唯一结算之间的定位保留；
- 需求父链决定唯一接收者、缺父任务保留待交接、只结算一级、父未完成不向上结算、重复接收不重加；
- 收束任务重新启用后同一轮内不重复结算、再次正式完成按新的一轮结算一次且此前各轮不撤销不重复；
- 重复、乱序、发布未知、停止和重启分支。

通过静态检查或编译只证明结构可接受，不证明网页动作端口、外部观察生产者、延迟结果链、跨进程恢复、组合方法或完整内部治理闭环已经工作。
