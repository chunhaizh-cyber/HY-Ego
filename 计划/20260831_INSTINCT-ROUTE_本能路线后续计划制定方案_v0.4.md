## 1. 本次唯一覆盖范围

本文件只覆盖 v0.3 的四个冲突口径：

1. `Gseed` 激活必须先区分“从未成功维护”和“已有成功维护”，不能把“旧游标早于 `Gseed`”直接等价为允许新纪元；
2. 阶段七必须先区分等待、子目标、能力缺口、内部治理、纯观察和现实改变，只有现实改变分支需要正向业务授权；
3. 当前值变化必须有正式来源存在，但来源方法只在事实确实由方法产生时才必需；
4. v0.3 第 9.1 节的旧场景不能再作为合法激活场景。

其它阶段目标、有限前视、横向门禁、禁止宣称和完成边界继续读取 v0.3。

## 2. `Gseed` 激活的 A / B 强制分流

现行 6170 第 526—528 行要求先判断是否存在成功维护提交。路线统一改为：

```text
读取维护游标 owner 的成功维护提交权威事实
|
+-- A：权威事实明确证明从未发生成功维护提交
|     -> 允许建立新维护纪元
|     -> 完整秒边界显式初始化到新纪元当前完整秒边界
|     -> 服务历史事实水位显式初始化到 Gseed
|     -> 主动安全事实水位按原水位继承；全新实例才取主动安全永久账登记起点
|     -> 明示 Gseed 前服务历史不补算
|     -> A/V、状态、动态零变化
|
+-- B：权威事实证明已经存在成功维护提交
|     -> 禁止重置或跳过旧水位
|     -> 只有旧完整秒、旧主动安全水位和旧服务历史水位后的全部未消费历史
|        已按正式秒序完整迁移，才允许切换 v2
|     -> 当前秒序映射尚未冻结，因此本叶只返回结构化 fail-closed
|     -> 三个水位保持原值
|
+-- U：旧 v1/v2/v3 格式或坏格式无法证明是否成功维护
      -> 不得从游标存在、形成代次、水位值、运行代次、日志或调用历史反推
      -> 按旧格式证明缺失结构化 fail-closed
      -> 三个水位保持原值
```

A 的“建立”只适用于 owner 证明当前游标槽从未产生过任何值的全新实例；已经存在成功序号为 0 的 v4 激活事实时，本叶只允许同一维护纪元的恢复 / 精确重复，不以另一个幂等键连续建立第二维护纪元。

### 2.1 成功维护提交的唯一权威

成功维护提交事实归维护游标 owner 所有，必须持久、可恢复并由公开读回取得。新格式至少同时携带：维护纪元身份、三水位、成功维护提交序号和本事实形成代次。`成功维护提交序号 == 0` 是允许 A 分支的唯一正面证明；序号大于零时，本事实形成代次同时是最近一次成功维护提交代次。缺字段、旧格式、部分写、坏版本和无法恢复都不是“零次”，统一 fail-closed。

未来真正的维护成功提交必须在同一原子事务中同时推进三水位、递增成功维护提交序号并发布新的权威游标事实。失败、材料不足、已可能发布未收束或独立读回不闭合时，四者都不能局部变化。

### 2.2 当前叶的完成上限

当前叶只允许交付：

```text
A 分支：全新且有显式零成功证明的生产激活、持久恢复和独立读回
B 分支：已有成功维护时结构化 fail-closed、三水位不动
U 分支：旧格式无法证明时结构化 fail-closed、三水位不动
```

因为五类服务事实到完整秒、同秒阶段和正式发布序的映射尚未冻结，本叶不得宣称已经实现 B 分支完整兼容迁移，也不得提前设计或登记秒序后继。

## 3. 替换 v0.3 第 9.1 节的端到端场景

v0.3 第 9.1 节“当前 v3 游标服务历史水位早于 `Gseed` -> 建立新维护纪元”整体退出。现行场景改为：

```text
场景 A：全新实例，无 v1/v2/v3/v4 游标
-> 建立维护 owner 新格式显式零成功事实
-> 读取 v2 边界完整快照，绑定 Gseed/G0/self
-> 读取主动安全永久账登记见证和新纪元当前完整秒边界
-> 原子建立 v4 激活事实
-> 独立读回维护纪元、三水位、成功维护提交序号 0 和 Gseed 前放弃边界
-> A/V、状态、动态零变化
-> 进程重启后逐字段恢复同一事实

场景 B：v4 权威事实的成功维护提交序号 > 0
-> 请求新纪元激活
-> 返回“已有成功维护需完整迁移”
-> 独立读回确认三个水位和成功序号均未变化

场景 U：存在 v1/v2/v3 旧游标，或新格式缺失成功提交字段
-> 返回“旧格式成功维护历史不可证明”
-> 不从旧水位是否早于 Gseed 推断
-> 独立读回确认旧事实未被覆盖
```

同键精确重复、同键异义、读前 / 读中 / 读后漂移、`Gseed` 变化、已可能发布、持久恢复和坏格式均必须纳入专项验证。

## 4. 阶段七固定顺序修订

v0.3 第 6.7 节中“方法冻结后统一进入授权”过宽。正式顺序改为：

```text
读取任务、轮次、T->D 和目标合同
-> fresh 判断目标是否已满足
-> 未满足时读取本轮筹办准备与正式方法 / 路径材料
-> 先形成下一步作用分类
   1. 等待
   2. 子目标形成或下级任务准备
   3. 方法能力缺口处理
   4. 自我内部治理
   5. 纯观察
   6. 现实改变
-> 等待 / 子目标 / 能力缺口 / 内部治理 / 纯观察：
   不申请现实执行授权，按各自 owner 合同形成结构化结果
-> 现实改变：
   fresh 当前性复核
   -> 自我业务 owner 发布唯一正向授权
   -> 安全硬否决与真实资源 owner 复核
   -> 动作执行和正式结果读回
-> 当前值目标裁决、直接调用关系结算和轮次结论
```

“无需现实执行授权”不等于任意写入许可。五个非现实改变分支仍须满足各自的需求、任务、方法、所有权、预算、幂等和事实发布合同；安全 / 服务调度量也不产生第二份正向授权。

## 5. 当前值来源口径修订

路线统一采用：

```text
每个当前值首次形成或真实变化：来源存在必有
来源方法：可选
```

“来源存在”必须绑定能够对该形成或变化负责的正式存在 / owner 事实，不能用日志、线程、空身份或自然语言代替。若变化由正式方法执行产生，必须绑定该方法和动作事实；若是初始化、外界自然变化、外设观察或其它不经过方法执行的合法来源，则不得为满足字段形式虚构来源方法。状态 / 动态记录这个来源，但仍不能代替当前值权威。

## 6. 当前下一步与禁止宣称

最早叶保持为 `Gseed` 显式激活与维护游标兼容迁移，但其当前可实现边界收紧为 A 生产激活 + B/U 结构化 fail-closed。候选设计和计划只有在目标代码文件所有权释放、重新 S0 且正式登记后才可能进入执行。

新增禁止宣称：

```text
旧 v1/v2/v3 游标存在证明从未成功维护
服务历史水位早于 Gseed 自动授权重置
本叶已经完成已有成功维护实例的完整兼容迁移
非现实改变分支需要或已经取得现实执行授权
每个当前值来源都必须虚构一个方法
```
