### 0.1 已确认的语义漂移

用户确认的新目标口径是：

```text
筹办先找方法
-> 对每个找到的方法查找其自己的条件组
-> 保留 方法 M → 条件组 C 的关系
-> 方法缺失 / 条件缺失只形成定位消息
-> 任务管理独立读回后交自我确认和管理需求；需求领域服务才可合法写入或复用正式需求
-> 执行前才 fresh 读回、以安全为硬可用性门槛，并在可用候选中选择和冻结实际执行项
```

这与 v0.4 当时继承的旧机器语义存在不能由测试适配修复的冲突：

- v0.4 当时依赖的 `3200` §9.3、`5230` §5、`5250` §3—§4曾要求筹办先完成适用判断、只读取或为实际采用方法形成条件处理；`5090` §2.3与`5250` §4还把一轮筹办写成只形成一条当前活动方法路径。
- v0.4 当时依赖的 `3200` §9.4、`5230` §4和`4260`筹办结果合同曾把每轮筹办固定为五类唯一闭合结果，并使`可执行冻结`、`子目标承接`成为筹办结果；`4250` §14只消费已发布的正式任务子目标承接记录建立或复用子需求。
- v0.4 当时依赖的 `5300` §7把选择权授予取得筹办执行权的任务领域，`5240` §4、`5300` §7和`4260` §31虽提供结果一致、条件 / 输入闭合、禁止 / 风险、运行质量 / 成本等分层选择依据，却没有把新口径下的执行前候选对象、未知 / 并列 / 不可比值处理和选择入口冻结为可施工合同。
- v0.4 当时依赖的 `8100`已规定任务管理不得直接写需求、需求由自我线程编排并由需求领域服务正式写入；但其消息和需求来源边界仍以筹办闭合结果 / 正式子目标承接记录为前提，不能直接把“缺失定位”当作正式需求。

因此，v0.4 原先关于“每个已消费工作包一次 provider 调用、五类结果消息、manager 接收后结束”以及测试消费者机械迁移的假设，都不能证明新口径已经实现，也不能继续作为施工依据。
