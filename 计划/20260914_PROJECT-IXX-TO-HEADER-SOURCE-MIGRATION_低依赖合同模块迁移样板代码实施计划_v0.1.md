## 1. 目标、边界与完成条件

本计划只实施全仓 `.ixx -> .h / .h + .cpp` 迁移路线的第一个可独立验证叶：将四个无运行期状态、只负责导出既有 L1 数据头的低依赖合同模块，转换为四个传统头文件，并把它们的全部直接生产模块消费者、主工程、filters 与五个现有验证工程同步到头文件消费。

本叶不把任何大实现模块改成头文件，不拆分仓库或服务实现，不迁移线程、领域、业务、装配或启动模块；后续模块仅由本叶的编译结果驱动重新设计。它不改变 L1 事实、DTO、函数、模块所表达的机器语义、所有权、生命周期、事务、代次、错误枚举或链接入口。

本计划的函数、文件、映射、失败收口和验证合同均已冻结，执行者无需临场补设计；但它与当前索引中的 `WORLD-TREE-STRUCTURE-B` 同时占有 `海中鱼巣.vcxproj`、`海中鱼巣.vcxproj.filters` 及主工程隔离构建资源。此共同工程所有权是直接结构依赖：在该计划退出当前候选并释放其工程 / filters 占用前，本计划不得施工或改为 `可执行`。

代码完成条件同时成立：

1. 四个目标 `.ixx` 已物理删除，四个同基本名 `.h` 已形成，生产源码、主工程、filters 与五个验证工程不再引用其 `.ixx` 路径或模块名。
2. 四个头只复用既有 `*.数据.h` 的类型与 inline 函数；不复制、删改或重定义任何 DTO / 函数实体。
3. 三个直接模块消费者不再 `import` / `export import` 目标合同，且通过传统头文件获得完全相同的编译期声明。
4. 五个验证工程与主工程的项目 XML 可解析；五个验证工程在隔离 Debug x64、Release x64 重建并链接通过。
5. 静态扫描确认本叶四个旧路径、四个旧命名模块及其 `import` 直连全部归零；全仓其余 `.ixx`、`module`、`export`、`import` 命中是后继迁移对象，不被伪称为已退出。

## 4. 精确接口与依赖合同

### 4.1 四个新头的形状

每个新头均以 `#pragma once` 开始，随后只使用 §2 表中冻结的双引号相对 include。不得保留 `module;`、`export module`、`export import`、`export {}`，不得另行复制标准库 include 或定义新宏。

既有 `*.数据.h` 的 include guard 和自身依赖是唯一去重机制。执行者不得沿用旧模块转发临时定义的 `L1_PUBLIC_FACT_NO_INCLUDES`、`L1_FACT_BASE_NO_INCLUDES`、`L1_NEUTRAL_CRUD_NO_INCLUDES`、`L1_OWNER_SCOPED_CRUD_NO_INCLUDES`，也不得为本叶修改这些宏的既有含义。

### 4.2 legacy 模块的头桥接

三名直接消费者继续作为 named module 编译。为使它们内部使用的声明继续属于唯一全局头声明集合，所有新 `#include "合同.L1*.h"` 必须置于其已有 `module;` global module fragment 内、`export module ...;` 之前；不得在 module purview 后 include，也不得写成 header unit 或 `import`。

冻结映射如下：

| 消费者 | 删除的模块依赖 | 加入 global fragment 的头 |
| --- | --- | --- |
| `仓库.L1事实基座.ixx` | `合同.L1事实基座`、`合同.L1中性CRUD`、`合同.L1所有者范围CRUD` | `合同.L1事实基座.h`、`合同.L1中性CRUD.h`、`合同.L1所有者范围CRUD.h` |
| `服务.L1事实基座.ixx` | `合同.L1中性CRUD`、`合同.L1所有者范围CRUD`、`合同.L1事实基座` | `合同.L1中性CRUD.h`、`合同.L1所有者范围CRUD.h`、`合同.L1事实基座.h` |
| `数据服务.状态类.ixx` | `合同.L1事实基座` | `合同.L1事实基座.h` |

该映射只替代名称可见性来源：公共类型、值式 DTO、inline 函数及其实体仍只来自现有数据头。若任一剩余 named-module 消费者无法经该 global-fragment 头桥接完成编译或公开声明可达性检查，属于本计划的实现错误，执行者必须在本计划允许范围内修正 include 位置或顺序；不得借此增加模块兼容壳或改变类型所有权。

## 5. 实施顺序与失败收口

1. 执行 S0：复核本计划版本、正式规范、`main` / HEAD / `origin/main` / index、外部占用表、目标文件 dirty 与工程 / 构建资源。逐项登记本计划实际改动文件。任何其它所有者占用、同文件异主 WIP、发布租约或构建根冲突，只停止本叶并保留现场。
2. 创建四个新头，先用单独最小翻译单元只 include 四头并编译，确认现有数据头可经普通 include 闭合。
3. 依 §4.2 迁移三名直接消费者；以静态扫描证明四个旧模块名不再被生产源码 import。
4. 修改主工程、filters 和五个验证工程的项目项；逐文件 XML 解析并扫描确保旧 `.ixx` 项归零、新 `.h` 仅为 `ClInclude`。
5. 在四头、三个直接消费者、两个工程文件及五个验证工程的本叶闭包上执行 §6 验证。仅验证成功后删除四个旧 `.ixx`，再重复静态与编译验证。
6. 记录精确改动与验证事实，取得发布租约后只提交本计划允许文件和两份记录，普通推送；更新本计划索引状态由执行者的正式结果流程处理。

非成功收口：

- 头 include 自身循环、重复定义、未声明、公开可达性或链接失败：只在四新头及三个桥接消费者内更正 include 次序/位置；不得修改数据头或扩大为其它模块迁移。
- 项目 XML 解析失败、遗漏旧路径或漏掉验证工程：只修正本计划明确的工程文件，再从头验证。
- 当前已有根工程或范围外模块构建失败：记录 exact before/after 前沿和差异；只有本叶引入或改变的错误可修复。本叶不声称根工程总体成功。
- 需要修改模块 ABI、数据头、机器语义、其它消费者、正式规范或启动/装配时：停止并具名退回计划支撑；不得临场扩大。
