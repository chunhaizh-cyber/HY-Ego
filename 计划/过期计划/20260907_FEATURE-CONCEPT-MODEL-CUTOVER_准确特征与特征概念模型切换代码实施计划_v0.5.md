## 1. 目标和完成条件

继承 v0.4 全部未改写合同，并完成三项退回：EC 四个旧共享 DTO 改为 EC 自有类型并从特征概念模块物理删除；DC 对新 provider 五个失败状态公开分账；场景不再保存或直接收敛五分支 `特征概念写请求`，只经特征概念应用的原观察入口续行。

完成必须同时满足：

- 四个旧共享 DTO 的定义和生产消费为零，EC 专用替代的 owner、字段、枚举和映射与详细设计一致；
- DC 既有状态数值不变，新增 15..19 与 provider 五项一一映射；
- 场景继续材料无概念 provider 原请求，场景对 `收敛特征概念写入` 零调用，陌生请求不能经场景首次派发；
- v0.4 的准确 F、C/名称、存在采用、最终投影、EC 扩展交付、消费者迁移和物理删除仍全部完成；
- 精确静态检查、`git diff --check`、严格规范检查和隔离 Debug/Release x64 Rebuild 全部通过。

编译不证明运行、数据库、生产装配、跨进程 F pending 恢复、存量迁移或业务闭环。

## 4. 机械实施顺序

1. 从正式 v0.5 计划、设计 blob、当前 HEAD、18 项登记和保留 WIP 重新 S0。
2. 在存在概念应用模块定义 `存在概念应用预算`、`存在概念场景限制`、`存在概念业务状态`、`存在概念阶段状态`；按详细设计逐字段迁移全部 EC DTO、签名、helper、状态赋值和成功谓词。
3. 在特征概念应用模块删除四个旧共享类型；不得保留别名。旧场景 v1 消费随场景整体替换删除，不迁移到 EC 类型。
4. 在 DC 枚举末尾显式追加 15..19，并在 `映射(概念树数据状态)` 加入五个精确 case；其它 case 和默认内部不一致保持。
5. 将场景继续阶段收敛为特征应用、存在采用、最终读回三项；删除 `概念原请求` 和待概念写入状态。
6. 初次场景只调用 `处理类型观察`；特征应用续行只调用 `收敛类型观察`。删除场景对 `收敛特征概念写入` 的直接调用和所有五分支判断；保留特征概念结果中的 provider 诊断事实，不把它升级为场景写授权。
7. 存在采用继续仍保存精确 `存在当前采用写请求`，按 v0.4 逐字段互证后调用其 provider；最终读回与其它消费者迁移继续按 v0.4。
8. 扫描并物理删除 v0.4/v0.5 规定的全部旧 DTO、旧 ABI、旧场景阶段机和兼容壳；保留合法新实现。
9. 完成精确符号扫描、两配置隔离 Rebuild、施工记录和编译记录。
