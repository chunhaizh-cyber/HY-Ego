# 需求扫描与部分承接恢复

身份：`SELF-SCAN-RECOVERY`；版本：v0.1；日期：2026-10-12。
起点：`b26b54053b1795236713b2ae6327736eff9dd1a5`；分支 `main`，初始工作区及 index 干净，远端 0/0。计划执行资格以索引登记的精确 blob 为准。

## 1. 目标与范围

用户已授权修订扫描恢复：明确资源失败可延后重试；依赖未就绪等待既有有效治理消息再探测；首次完整扫描不能被数量相等替代；已经建立 T 的部分承接不能因后继扫描只查缺 T 而丢失补齐机会。不是定期扫描，也不把未知同步失败都判为资源失败。

依据：[0050](../规范/0050_项目通用机器逻辑与禁止性规则总纲_20260721.md)完整材料/具名失败、[8100](../规范/8100_子规范_自我线程与任务管理线程权责边界_20260720.md)第3、11、12节、[8200](../规范/8200_子规范_自我内部循环实现_20260720.md)第5.1、15节。只改进进程内调度，不改变 D-T 唯一性、任务完成/重新启用、服务结算或扫描补齐不授执行资格的语义。

允许生产文件只有：

- `海中鱼巣/线程/新_自我线程类.cpp`；
- `海中鱼巣/线程/新_任务管理线程类.cpp`；
- `海中鱼巣/领域/新_任务类.cpp`，仅`建立需求任务关联`的资源状态透传。

另允许专属记录`验证记录/20261012_SELF-SCAN-RECOVERY_需求扫描与部分承接恢复验证记录_v0.1.md`。禁止修改公开头/DTO、工程登记、worker、同步回调 ABI、规范、方法、实际任务完成判定及新增生产消息类型。一个代码切片，root 为代码/Git/构建唯一所有者。

## 2. 现状与复用裁决

- self `提交需求工作已加锁`除已有扫描外统一置失败，`请求数量复核已加锁`仅允许空闲恢复，失败态会长期停留。
- 全扫描结果和承接向量分配失败统一进入失败；向量可能保留部分前缀，后续又当成完整批次处理。
- manager 扫描调用`建立需求任务关联`；当前只重试零写资源失败，扫描已经写入 T 的资源失败被终结为需核查。
- task `建立或取得任务`已有一D一T fresh复用路径，复用会再次尝试服务任务集合同步。可复用，不新建补偿入口。
- `同步服务任务集合已加锁`仅返回 bool，混合来源读取、回调失败及写后失败；不能据此推定资源原因。
- manager 扫描补齐消息终结后不加入`最近自动决议`缓存；self可保留原消息，在明确事件后再次提交同编号，由task fresh复用既有T。普通自动任务决议缓存不变。
- worker扫描结果、确认、停止和完成唤醒已经具备，不改worker或新增就绪合同。

## 3. self私有状态和入口

在`新_自我线程类::实现`内新增（不进入持久事实及公开快照）：

```cpp
enum class 扫描恢复方式 : uint8_t { 无, 资源延后, 等待事件, 硬失败 };
bool 首次全扫描已闭合 = false;
扫描恢复方式 扫描恢复 = 扫描恢复方式::无;
optional<新自我工作种类> 待恢复工作种类;
optional<steady_clock::time_point> 扫描重试时点;
```

扫描承接项增加仅自身使用的`bool 等待恢复事件=false`，可以扩展现有私有`自动承接项`（其它用途保持默认false）。修改私有签名`void 请求数量复核已加锁(bool 允许恢复=false) noexcept`。新增私有`void 安排扫描恢复已加锁(扫描恢复方式, 新自我工作种类) noexcept`和`optional<steady_clock::time_point> 最近扫描推进时点已加锁() const noexcept`；前者只登记下一次有界重试，后者合并扫描恢复及未挂起承接项截止。局部辅助函数允许拆分，但不增加公开能力。

`首次全扫描已闭合`仅在成功完整映射扫描、所有缺T承接成功、worker确认成功后置true；没有缺T也必须经过确认。初次、服务未就绪后恢复、首次构造承接材料失败后的重试，必须再次全扫描；不能先数量核对并因相等跳过首次完整映射。后续数量核对资源失败重试同种类；后续全扫描资源失败也重试全扫描。

## 4. 精确失败分类

| 来源与已有状态 | 处理 |
| --- | --- |
| 提交worker明确`资源失败` | 不持活动句柄，保存原工作种类，按现有资源重试间隔延后再提交；下一次编号可新建，业务仍是同一完整扫描范围 |
| worker正常结果`资源失败`，原请求匹配 | 先确认并释放本次结束结果，再安排同种类资源重试；不采用失败载荷/数量 |
| worker正常结果`需求服务未就绪/任务服务未就绪` | 确认释放后等待事件；保持需要的扫描种类 |
| worker接收`尚未启动` | 等待事件重新探测；不定时检查未就绪 |
| worker接收`已停止接收/内部错误/身份冲突/入口拒绝`或无合法future | 硬失败；日志，不自动恢复 |
| 无本地活动却worker返回`已有扫描` | 所有权/身份不一致，硬失败；不能只置待复核而永久等待未知future |
| worker结果请求不符、结构错误、停止取消、内部错误；future非资源异常 | 硬失败；不把错误映射成重试资源 |
| 全批扫描承接材料构造`bad_alloc` | 释放全部未派发前缀，确认释放worker结果，再延后重做全扫描 |
| 其它构造/逻辑异常 | 清理未派发前缀；按硬失败收口，不泛化资源 |
| manager接收`邮箱已满/资源失败` | 保留原消息延后重试提交 |
| manager接收`尚未启动`，或正式结果`服务未就绪` | self保留原扫描承接项，等待有效事件再提交，不轮询依赖 |
| manager承接明确资源失败（详见第6节） | manager保留原活动消息、promise、容量，延后fresh重入；self继续等待同future |
| `建立结果.状态==服务任务集合同步失败` | 原因未知；manager终结本次尝试，self保留原扫描承接项并挂起等待有效事件；不得自动定时重试 |
| 多T、孤立T、已确认结构/身份冲突、manager停机、其它未分类需核查 | 硬失败并记录原身份；不自动重试，不误当同步暂不可用 |

已知资源异常捕获`std::bad_alloc`；不通过catch-all制造可恢复结论。worker已有catch-all结果`资源失败`按其公开状态消费，本叶不修改其原因合同。`任务操作未完成`不能作为统一可重试类别。

## 5. self批次、确认、触发与等待

### 5.1 材料与确认顺序

接收结果只先验证原请求/状态。仅成功结果更新最近数量；失败结果保留上次完整数量或空，不写失败时的零当当前数目。

读取共享future结果时用本地共享future保持生命周期，以`const&`消费避免不必要全量复制。形成待承接消息采用独立局部vector，完整构造成功后swap进正式`扫描承接`，之后才派发第一条。任何构造失败不得派发局部前缀；销毁/swap释放其容量后处理确认与恢复。

一条manager成功终结回执须原消息匹配，且为`已承接/已重新启用/既有终结`；沿现有核验边界消费，不添加执行授权。明确等待事件的失败项保留完整原消息与已建事实定位，清空已终结future，`等待恢复事件=true`，不删除。其余未挂起项仍可推进，不能因队首挂起而阻塞整批。

资源失败由manager保留future时self不另发第二份消息；self可用现有有界间隔检查future，不做数量核对或全扫描。所有承接项真正终结成功或硬失败并移除后才确认worker结果。只要仍有等待事件项，不ack、不释放扫描请求、不启动第二次扫描。

确认仅接受既有worker`已完成`；确认失败保留本地句柄，进入硬失败，禁止继续新扫描。不得把`无变化`擅自视为完成证据。停止时沿现有stop/join处理，释放自己暂存vector/future，但不能宣称manager已取消其接受的消息或业务已收口。

### 5.2 明确事件，不是自激活

`请求数量复核已加锁(true)`只从已经处理的有效真实治理消息调用，或同一消息处理已正式确认新增子需求的入口调用。有效指现有入口身份校验及本次处理没有`入口拒绝/内部不一致/内部错误/工程停止`，不是依赖已经就绪。纯扫描收尾、首次资源重试、future轮询、学习完成、定时唤醒调用默认false。

true可唤醒`等待事件`的扫描请求，以及保留的同步失败/未就绪承接项；将它们标为一次待重试，复用原承接消息编号，不产生新业务请求。实际再执行仍fresh读取，失败可再次挂起。true不解除已确认结构/身份/worker停机硬失败，不变更任务后继决议。扫描忙时其它触发只合并`数量复核待触发`，不另扫。

正常批次收尾只调用默认false的数量复核；它不能唤醒本批未知同步失败。没有显式事件时未知同步失败保持挂起并有诊断，不声称自动修复所有半成品。

### 5.3 主循环

每轮最多提交一次到期扫描恢复或推进一个可处理承接项；失败重新把截止放到未来，不在调用内循环。全扫描和数量工作仍最多一个。资源恢复定时器仅在具名失败后存在，成功/等待事件/硬失败后清除，不是周期扫描。

所有self等待分支取原截止、方法问题投递截止与最近扫描推进截止的最小值。没有截止且所有承接项都挂起时，条件等待真实治理消息/其它ready结果/停止；不得对队首的过期时点持续wait_until。worker扫描future就绪仅在`需求扫描阶段==等待扫描结果`时才进入ready predicate；所有承接行挂起、或ack失败保留旧future而进入硬失败时，旧ready扫描future不能唤醒主循环，防止忙循环。学习future仍按现有未消费条件判断。恢复截止到达只重试已登记工作，不能顺便扫描。等待扫描结果/结果处理中/等待任一manager回执时禁止额外数量读取。

## 6. manager与task局部状态透传

manager `实现::运行`原承接调用之后，增加私有纯判断`bool 扫描承接可资源重试(const 新任务承接处理结果&) noexcept`，同时满足原消息依据为`自我全树扫描`，并且：

1. `承接.状态==新任务治理承接状态::资源失败`；或
2. `承接.状态==任务操作未完成`且存在`建立结果`，其状态严格等于`新任务操作状态::资源失败`。

该分支无论`写入已尝试`都保留同一`消息项`、原消息及同future，使用既有`可处理时点`延后，回到正常调度；不提前set_value、不释放容量，不伪造完成。重试再次调用`建立需求任务关联(D)`，通过正式一D一T来源fresh建立或复用，不额外新建T，不重开终结任务。普通显式/自动/条件子需求原重试策略不变。停止时沿原`终结待办`返回取消。

`新_任务类::建立需求任务关联`中`修改任务状态(T,等待条件)`失败，目前把确切资源原因吞成`任务操作未完成`。仅当该返回严格为`新任务操作状态::资源失败`，把现有`读回.状态`设成已有`新任务治理承接状态::资源失败`；其它非成功仍任务操作未完成。保留`读回.任务/虚拟存在/建立结果/写入已尝试`，不回滚已经建立T，不新增错误枚举或字段。

同步bool失败仍为`服务任务集合同步失败`，不得映射为资源；不修改回调、特征/状态/动态同步算法。恢复能力只证明可再次调用同一正式同步路径，不证明此前部分写已经原子或全部可恢复。
