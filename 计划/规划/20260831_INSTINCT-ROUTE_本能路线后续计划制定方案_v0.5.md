## 1. 本次固定的最小定义

### 1.1 自我、需求与存在身份

当前内部治理只治理唯一自我的需求。安全根需求和服务根需求是自我的两个根需求；后续需求只能沿其父需求的治理链形成。

需求、任务、方法和消息都必须绑定其所属的实际存在身份。这里不额外建立“真实人类身份”认证入口：存在节点及其已登记的分类信息才是身份和归类依据。人类只是可被归类的一类实际存在，不是另建一套需求根或授权体系的理由。

### 1.2 筹办

筹办是一次只读的执行准备发现：

```text
任务 / 当前父需求 / 同一事实截止
-> 粗召回可能影响目标的正式方法
-> 对每个方法分别读取其内容版本、条件、输入、参数、限制、动作范围、验证与归因材料
-> 形成候选方法与条件组的对应关系、以及缺口定位
-> 通过既有强类型消息交任务管理线程
```

筹办可以发现方法缺失、条件缺失、输入或合同结构缺失、当前性漂移和资源失败；这些都是发现或定位，不是正式需求、子任务、方法能力事实、服务账或任务完成事实。

筹办**不**：

```text
判断某个候选实际适用
选择或采用一条方法
形成当前路径、实例方法或执行冻结
直接建立需求、子需求、子任务或父子任务关系
把条件缺失自动升级为需求
把目标已完成、等待、子目标承接或冻结作为自身五类互斥业务结果
```

### 1.3 方法与条件组不能摊平

候选必须保留方法—条件组关系：

```text
M1@内容版本1 -> C11 / C12
M2@内容版本7 -> C21
```

一个条件组内部的条件共同成立；同一方法的多个条件组之间是可替代、可组合或其它关系，必须由该方法内容版本的正式合同显式声明。没有强类型组身份或组合语义时，只能报告结构缺口，不得把多个组默认当作可替代执行选项。条件不得被汇总为任务级总清单。

因此，`M1 -> {A}`、`M2 -> {B}` 中即使 B 当前缺失，只要 A 满足，M1 仍是后续可用性判断的候选。条件缺失必须精确落在“方法身份 + 内容版本 + 条件组 + 条件身份”上。

执行前的最小比较对象为：

```text
执行选项 = 方法身份 + 方法内容版本 + 条件组 + 输入/参数绑定 + 动作范围
```

这只是值式选择对象，不新增持久候选账、条件历史账或第二选择记录。

## 2. 消息、任务管理和自我需求治理

### 2.1 保留一个筹办消息，不保留五类筹办结果账

复用既有任务工作线程、强类型筹办结果消息、结果提交端口和“队满只重投同一不可变消息”的规则。消息只表达一次筹办发现及其定位：任务、任务轮次、筹办轮次、工作包、来源 / 结果事实截止、候选方法与条件组身份、逐项缺口类别和必要的正式来源引用。

它不是持久回执、第二结果账、五类历史记录或新的线程 / 队列。任务管理收到后必须按任务、轮次和同一事实截止独立读回既有正式方法、条件、输入与任务事实；消息、日志和缓存都不能代替这些事实。

“一个已消费工作包最终必须向任务管理交一条消息”的协议不变；但消息顶层不再把下列业务后果伪装成筹办自身的唯一分支：

```text
可执行冻结
子目标承接
合法等待
目标已完成
```

目标已满足由任务 / 需求的正式目标比较链处理；等待、需求承接和执行冻结分别由后继 owner 处理。结构化非成功仍必须显式传递，不能静默结束工作包。

### 2.2 管理线程只读回、路由和编排

任务管理线程不重跑筹办裁决、不直调筹办 provider、不创建需求或子任务。它在独立读回后仅作以下路由：

```text
筹办发现中的方法 / 条件 / 结构缺口
-> 扩展既有“任务管理 -> 自我”治理消息协议的一条具名筹办发现缺口定位分支
-> 自我线程 fresh 复核
```

当前正式 HEAD 尚无方法 / 条件缺口的 manager -> self 消息；这里要求的是既有自我治理消息通道的一条强类型分支，而非第二消息通道、持久 outbox 或新的结果账。

合法的等待不是“队列满”或“资源紧张”这样的线程状态；它必须由后继治理在正式事实基础上形成等待对象、合法生产者、重触发条件、版本和事实截止。消息端口容量不足只重投同一消息，绝不重新调用 provider 或改变业务结论。

### 2.3 自我确认需求，需求领域服务写入或复用

自我线程收到缺口定位后，必须 fresh 读取父需求、任务 / 轮次、候选方法和条件事实，并区分：

```text
外部事实尚未产生、时间未到、材料漂移
-> 等待 / 重触发，不建立需求

候选方法已存在但入口、输入、验证或归因合同不完整
-> 当前任务材料或具名结构缺口，不自动建立需求

完整方法粗召回为空，或已知条件目标确为独立且必要的父需求后继
-> 仅在自我确认其目标合同、父域和独立性后，进入既有正式子目标承接记录链
```

筹办不能直接发布该正式子目标承接记录。自我确认后的既有任务 / 需求正式入口才可以发布或复用它；需求领域服务仍是建立或复用子需求的唯一正式写入者。随后才由普通任务承接链创建或复用对应任务。

这复用现有“子目标承接记录 -> 需求领域服务”的一条正式链，只把需求确认前移回自我治理；不增加子需求创建入口、持久 outbox、服务合同或第二账。

## 3. 执行前选择和冻结

### 3.1 时序

实际选择在执行阶段、真实动作之前发生：

```text
任务进入执行前治理
-> fresh 读回筹办发现所定位的全部执行选项
-> 逐选项进行可用性 / 适用性判断
-> 过滤不可用选项
-> 在仍可比较的可用选项中按现行规则选择
-> 原子形成既有选择记录、当前路径、实例方法和执行冻结
-> 按现有授权、安全硬否决、调度和动作规则继续
```

筹办阶段不允许预先把“候选”写成“已采用”。同一任务的一次真实执行仍只能冻结并运行一个执行选项；未选候选不被删除，也不与当前执行并列。

### 3.2 可用性是硬过滤，不是可相抵的代价

每个执行选项必须在同一 fresh 截止通过至少以下门槛：

```text
目标 / 结果合同允许
方法生命周期与内容版本当前
该选项自己的完整条件组满足
输入、参数、动作入口、作用范围、验证和归因合同闭合
禁止项、结构拒绝和安全硬否决未命中
生存安全根控制态允许普通执行竞争
```

任一项不满足，该选项不参加选择。安全硬否决绝不能被服务收益、时间节省、调度倍率或自我授权抵销；安全根 `A=0/1` 也不能由普通服务目标或候选收益越过。

6150 的调度倍率仍只在冻结完成后、真实派发前参与安全任务之间的调度排序，不是方法选择、成本、授权或服务配额。

### 3.3 选择规则：复用分层比较，不新造总成本账

在硬过滤后的可用选项之间，沿用现行 5240 / 5300 已有的分层顺序：结果目标一致、条件与输入闭合、禁止与风险、运行质量。前两层和硬禁止原则上已经在可用性过滤中完成；实际比较只使用仍有区分度的、正式可读的运行质量材料，例如复现、失败、稳定证据、预计单调执行时长、资源和已有定义的成本。

不把安全根值、分层安全原始值、服务根当前值、服务合同余额、服务进展、服务准备、线程数量、队列长度或维护时间伪装成同一数值“代价”。

特别是：

- 安全的实际值只在动作后按 6100 / 6140 的正式结算或维护链变化；执行前最多使用既有安全门槛、硬否决和可审计风险材料，不能预结算或跨层相加。
- 服务根当前值只是长期普通需求的根特征坐标；服务合同和服务值账已经退出，不能把“服务收益 / 付出”重新定义成自动比较余额。
- 预计耗时必须是同一单位、同一作用范围的执行时长材料；6140 的有效未复发时间和 6150 的预计发生时间不能挪作方法成本。

未知、不可比或并列的选项不得按遍历顺序、稳定编码、哈希或线程顺序任选。保留候选和理由，并向自我提交待裁决定位；只有具名后继 owner 才能形成正式等待，自我也不得凭消息或偏好伪造一个新比较规则。

选择一经完成，复用既有选择记录和执行冻结承载方法版本、条件组、输入、动作范围、来源事实截止与规则版本；不再另建“代价账”“预期收益账”或筹办历史账。动作前任一绑定事实变化使选择与冻结失效，必须重新进入执行前判断。

## 5. 最早后继和禁止宣称

C031 正式规范与详细设计已经完成收口，但尚未产生可执行代码计划。最早代码叶不是局部代码适配，而是以下同 owner 合同的完整设计、S0 和精确施工计划：

```text
筹办发现值合同与既有消息复用
+ manager -> self 缺口定位和 fresh 读回
+ 自我确认后复用既有子目标承接 / 需求领域写入链
+ 执行前执行选项可用性过滤、分层选择、选择记录与冻结
```

该计划必须明确读取 owner、写入 owner、正式入口、幂等身份、同一事实截止、非成功 / 等待 / 并列处理和读回边界；在其完成前，不登记新的消费者代码计划。

禁止宣称：

```text
筹办已经执行方法或产生实际执行结果
筹办发现自动等于正式需求或子任务
方法缺失、条件缺失或队列满自动产生子需求
服务根当前值能够抵销安全硬否决或组成通用方法代价
预期安全 / 服务影响已经写入正式安全或服务值
当前五类筹办结果模型仍与本路线兼容
本路线输入已经完成代码、构建、运行或整条本能路线验收
```
