## 1. 目标与本轮授权

用户要求依据分层检查制定调整或拆分方案，并明确：

1. 数据服务提供基础数据操作；应用服务组合数据操作，提供带业务语义的服务；内部治理使用应用服务。
2. 内部治理的直接业务服务依赖位于 `海中鱼巣/业务`；业务应用的下层项目服务依赖位于 `海中鱼巣/领域`，不直接依赖核心 L1。
3. **允许同层调用。**保留职责合理的公开服务复用，不把同层调用等同于反向依赖，不要求为了消除同层调用复制算法或下沉业务判断。
4. **旧代码彻底物理删除。**本方案核定的旧实现不搬入备用目录、不保留空壳、旧入口、兼容实现或另一份中性句柄头；Git 历史不改写。

本轮只交付本方案。未修改正式规范、生产代码、工程、计划索引或共享知识库；六份旧源码尚未删除。实际施工涉及公开接口和物理删除，须形成完整代码计划。不得因本方案发布就宣称代码计划已登记、接口已实现或旧代码已清除。

## 2. 目标职责边界

```text
内部治理编排
    → 业务应用公开合同（允许同层公开复用）
        → 领域服务公开合同（允许必要的同层结构协作）
            → 核心 L1 事实操作
```

- 数据服务可验证结构类型、引用、基数、域、同底座、一致性、完整请求和原子发布条件；不裁决需求成立、任务完成、方法适用、安全策略或世界真实性。
- 业务应用负责输入绑定、比较求值、概念选择、目标判断及跨服务业务步骤；业务不取得核心 L1 引用、仓库、锁、写端口或内部事务。
- 同层调用通过具名公开合同形成无环依赖；不穿透对方内部索引、键编码或私有实现。运行期回调方向与编译依赖方向分别检查，不仅凭文件名判断反向调用。
- 启动装配、线程、日志、时钟、外设采样属于运行技术职责；其真实依赖按各自合同核验，不把技术设施误写成治理事实，也不借技术入口绕过业务的数据边界。
- 目录映射是本次调整目标。0050 第3.1节第1条现行条款仍区分架构层、目录和调用深度；本方案不在未修订正式文件时声称该目录限制已成为全部现行 ABI 的要求。

五份安全源码均 include 旧句柄头，仅在组内互相消费。对跟踪 C/C++ 源码、主工程、现存验证工程和构建脚本的扫描未找到组外真实依赖；旧节点句柄、关系句柄、主信息句柄及旧枚举没有必须迁出保留的使用方。现行 L1 使用自己的 `稳定编码`、`节点种类` 等类型，不依赖该旧头。

- `海中鱼巣.vcxproj`：只删除指向 `海中鱼巣\核心\句柄.h` 的 `ClInclude` 条目。

删除旧安全实现不等于删除安全业务需求。6140/6150 等现行安全逻辑保留，后继若要实现，依据新业务边界重新设计；本包不把旧算法搬入业务以冒充新实现。

不删除 Git 历史、现行 L1 恢复/持久解码、有效 DTO 和节点字段；不清理 `.codex-build`、其它所有者临时副本、历史验证材料或两份业务 WIP。凡施工前新发现的真实组外消费者，先核清并纳入经批准的删除/迁移闭包，不留悬空引用，也不擅自扩大删除集。

验收至少包括：六路径均不存在、两工程条目均消失、剩余生产源码不 include/import 旧组、旧类型真实消费归零、项目 XML 可解析，以及删除前后相关构建影响对比。历史文档引用可以保留为明确的退役证据，不能用“全仓字符串零命中”要求删除历史。

## 6. B：领域一致性提供者与三业务应用共同迁移

### 6.1 需要保住的行为

1. 请求开始与返回成功前均核验所要求的 G；中途读取仍使用现有 G/H、预算、来源闭包和强类型结果检查。
2. `资源失败`、`内部不一致`、`事实代次漂移`分开，不能统一返回 false/nullopt，也不能自动接受新的 G 后继续旧计算。
3. 顶层尾 G 漂移仍返回非成功；现行合同允许保留的完整子结果不变，但不能被解释为顶层业务成功。
4. 同底座必须证明为同一个实际 L1 基座，不能只比较数值 G。不同基座可以碰巧有相同 G。
5. 同底座不等于同一个服务对象。原合同允许的“同一底座上不同合法服务对象”不因本次迁移被机械拒绝；只有原合同确需同一服务实例时才比较服务实例。
6. 三个应用保持只读计算，不新建事实、owner、缓存权威、事务或写端口，不执行现实动作。

### 6.2 提供者设计方向

首选在已有且被该调用链真实使用的领域服务中承接“指定读取环境的一致性确认”和“相关服务的同底座核验”。需要冻结的是这些完整结构保证，而不只是新增一个转发 `L1.读G()` 的外壳。

三个应用本次实际需要的是“当前 G 是否仍等于请求给定 G”。因此优先设计各自领域服务的期望代次核验入口，不同时增加读取、守卫、快照三套入口；输入非零期望 G，输出成功或具名非成功，优先复用各服务已有结果类型。此为待冻结的候选合同，不是现有函数签名。

- 特征服务已有私有 `当前G()`；需求服务已有私有代次读取；任务服务已有私有代次检查。它们可复用内部机制，但不能原样公开。
- 需求私有代次读取把部分失败压成空值，不能直接作为新公开合同，否则会丢失原业务的错误分账。
- 不为三业务借用概念树，不另建通用结果头、通用 owner 注册表、全项目一致性中心或绕过唯一服务的新写入入口。
- 不在领域 factory 中反向构造业务对象；跨层装配由外层合法装配位置完成，运行期业务只持有领域或同层业务合同。
- 公开合同不得回传 L1 对象地址、raw 端口、锁或可变内部对象。领域可以在内部比较所属底座，技术证明不成为新的业务事实字段。

最终最小公开签名、结果布局、状态映射及绑定形成方式由 B 的详细设计在代码开工前冻结。本方案不把上述逻辑能力名当作现有函数，也不声称已经给出可直接编译的 ABI。

### 6.3 补齐实际依赖的绑定核验

本轮进一步核对发现：

- `海中鱼巣/领域/数据服务.存在类.ixx` 第757—771行构造保存特征服务，但未在该构造检查中核验其同底座；第559行 `绑定于` 只比较本服务的 L1。
- `海中鱼巣/领域/数据服务.任务类.ixx` 第385—415行保存需求、存在、方法、特征服务，但所示构造检查只核验自身写端口和关系类型，不能独自证明内部依赖全部同底座。

因此 B 不能仅在应用外侧换参数后宣称绑定闭包完成。详细设计应沿本次方向读取实际触达的服务依赖逐项互证，并对存在/任务的相关内部依赖补齐核验。此拒绝条件与错误表达的变化必须写入合同，不能伪装为纯机械重命名；不得借此扩张到方法执行、治理线程或全部生产装配重建。

### 6.4 业务同层链与内部辅助解耦

保留：`任务目标方向 → 需求目标方向 → 二次特征计算`。保留概念应用之间正式允许的同层公开协作，不因为同层调用而复制代码。

需求方向目前直接使用 `二次计算内部::输出键/键`，耦合 `pair<bool,uint64_t>`。这些函数处于导出 namespace，不能称为 C++ 私有越权，但不应成为跨模块承诺。

优先让需求结果按已公开的强类型来源/节点 variant 完成自身来源核验，不再转换到对方内部键；如确需共享行为，则在计算结果所属模块冻结窄的公开查询/互证能力，并保留同层消费。不新建无归属公共工具，不把调用期计算整体下沉 DATA，也不改变来源闭包成功谓词。

### 6.5 预计文件范围与明确排除

候选生产修改范围集中为：

- `海中鱼巣/领域/数据服务.特征类.ixx`

- `海中鱼巣/领域/数据服务.任务类.ixx`

- `海中鱼巣/业务/应用服务.任务目标方向.ixx`

这是详细设计定位清单，不是获准代码白名单；最终集合由实际公开合同与消费者扫描收敛。不为形式另建模块，不顺带改核心 L1、特征值/状态/动态/因果本体或新方法配对树。

三个应用的旧 L1 构造参数、旧 `绑定于(L1)` 入口和消费者必须同次退出，不长期保留双构造或兼容重载。领域服务内部仍可使用 L1；装配侧按现行合同使用的领域 `绑定于(L1)` 不在应用旧入口删除集中，不能按同名全仓删除。

### 6.6 验证矩阵

| 验证项 | 必须证明 |
| --- | --- |
| 依赖方向 | 三业务无核心 L1 服务成员、构造参数、直接方法调用；无领域反向依赖业务；同层公开调用保留 |

| 计算与自证 | 方向、多结果、共享子图、来源闭包、G/H、自包含成功谓词和尾漂移子结果规则不退化 |

| 工程 | 提供者与三真实应用同一验证闭包通过 Debug/Release；不以单个替身 provider 成功代替组合验证 |
