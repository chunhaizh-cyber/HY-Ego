## 1. 内部治理的目标与主线

内部治理的主要工作是分解需求、完成任务。

安全根需求、服务根需求分别作为两条需求来源，向下展开具体需求。每个需求都有对应的任务承接其处理目标；是否要求每个需求独占一个任务，不从“有对应任务”直接推导，见第 10 节。

用户所说的自我内部治理因果链闭环，包含以下关系：

```text
安全或服务需求确定目标方向
→ 根据需求组织方法及其所需条件
→ 完成对应任务，使相关特征沿需求方向发生实际变化
→ 核定需求满足情况
→ 通过任务结算反馈到相应安全值或服务值
→ 形成可追溯的动作、变化和因果信息
→ 后续治理利用这些信息改进需求分解、方法选择和任务完成能力
```

线程运行、阶段推进和函数调用本身不能替代上述实际效果。因果信息既用于解释哪些条件与动作造成了结果，也用于后续分析当前状态应该调用什么应对函数。

本轮先讨论系统逻辑。具体代码组织、接口、工程错误及恢复实现应在后续实施设计中单独处理，不能用代码问题定义需求分解和满足的业务含义。

## 2. 需求分解的具体机制

分解需求，是根据需求找方法、找方法所需条件的过程。

```text
当前需求
→ 查找能够实现目标的方法
→ 查找并核验方法需要的条件
→ 识别需要主动达成的条件
→ 确认相应子需求
→ 子需求由对应任务处理，继续找方法、找条件
→ 子需求满足后，重新核验上级任务的方法条件
→ 条件具备后推进上级任务
```

需求分解与方法查找相互联系，不再表述为“先独立分解完全部需求，再开始找方法”。

讨论中的分析边界包括：

- 方法之间、条件组之间可能存在替代关系，不能把所有候选方法的条件一并解释为必须完成的子需求。
- 子需求处理结果为上级提供重新核验的依据，不能直接代替上级目标满足。
- 条件未查明、条件确实不具备，以及需要等待实际条件形成，是不同情况。
- 具体哪些条件缺口值得成为子需求，仍需自我确认其必要性与目标可判定性。

## 3. 方法、任务虚拟存在与治理动作

### 3.1 方法的系统定义

方法是改变特征值的函数。

根据需求找方法，是寻找能够直接或通过因果链，使目标特征值沿需求方向变化的函数。

### 3.2 内部治理方法改变什么

内部治理方法改变的是任务虚拟存在中的相关特征值。本文以 `Vt` 简称任务虚拟存在，以 `Vm` 简称方法虚拟存在；二者不能混为一个对象。

这种改变必须以任务的真实情况和该方法实际造成的任务变化为依据，不能为了推进流程任意写值。例如，不能通过写入“条件具备”使实际条件成立，也不能通过写入“执行完成”证明需求已经满足。

内部治理函数的真实执行构成内部治理动作。动作记录需要能够解释本次处理所依据的任务情况、调用的方法以及实际处理结果；特征真实变化形成相应动态，为后续因果分析提供材料。

### 3.3 动态形成的分析边界

用户要求函数执行结束时根据实际执行情况生成治理动作动态信息。后续设计需要落实以下区别：

- 处理完成不必然等于进入下一一级状态；候选信息、条件信息或实际进展发生变化，也可能形成有效治理动态。
- 一次调用没有改变任何相关特征时，不为证明“调用过”而制造变化。动作过程记录与动作致变动态分别解释。
- 同一调用改变多个特征时，应保留各自真实前后状态及共同来源；必要时再关联为复合治理过程。
- 函数内部已经发生的有效变化不能仅用结束时的最终阶段覆盖；“结束时生成或汇总”不表示变化只在结束时发生。
- 治理方法对 Vt 的变化、具体业务方法对目标特征的变化、结算对根值的变化分别记录，并保留来源关联。
- 动态为因果分析提供材料；单有调用或时间先后关系，不直接证明因果成立。一次有效经验也不直接等于稳定、普遍适用的能力。

上述记录方式属于待细化的分析建议，不在本文中新增独立证明账、调用证明节点或第二套任务状态。

## 4. 六项一级状态成立条件

用户将先前混合过程与状态的 11 项表述修正为以下六项：

| 一级状态条件 | 系统含义 |
| --- | --- |
| 目标明确 | 明确任务所承接需求、目标对象、目标特征及要求达到的目标 |
| 有方法 | 已有用于实现任务目标的方法关联 |
| 方法条件具备 | 本次方法所需条件经核验实际具备 |
| 执行条件具备 | 本次实际执行所需的准备与约束已经满足 |
| 执行完成 | 本次方法执行已经结束，并能够取得实际执行结果 |
| 结算完成 | 本轮实际效果与需求满足情况已经得到相应结算处理和反馈 |

这些状态由 Vt 中的真实特征情况表达。是否采用累积成立条件、互斥主阶段或两者组合，以及各条件的精确定义，属于后续设计，不在本次汇总中确定编码方式。

必须保留的判断边界：

- “正在找方法”“正在查条件”“执行中”“结算中”等过程描述不再列入本轮确定的六项一级状态。
- 执行完成不等于需求全部满足；结算完成不等于安全值或服务值必然增加。
- 方法条件具备与执行条件具备需要分别明确，不能仅以字段名称区分而缺少实际判定依据。
- 等待、停止、取消、部分完成等情况需要在后续系统设计中有位置，但不在本文中擅自扩充为用户已确认的一级状态。

## 5. 三个基础治理方法与逐步成长

复杂任务在一级状态下还可能存在二级、三级直至更深的状态差异，需要不同应对方法。用户提出先采用任务筹办、任务执行、任务结算三个基础方法函数，覆盖基本处理与推进，使系统先能够运行。

```text
三个基础方法处理实际任务
→ 留下真实治理动作、状态变化与结果
→ 因果分析识别不同条件下的有效应对
→ 形成并验证更具体的方法
→ 后续根据状态与因果信息调用细分方法
→ 没有适用细分方法时，由基础方法按其职责继续处理
```

三个基础方法承担基本治理能力，不要求启动前穷尽所有层级的状态和应对函数。进一步细分应以是否需要不同判断、动作或完成条件为依据，不按层数机械增加函数。

兜底的含义是仍有基本处理规则，不是遇到任何情况都强行推进。无进展时如何等待、重判或交自我决定，属于需要明确的系统规则。

初始固有能力如何获得、如何与后续可学习方法区分，仍需正式设计。不能把尚无因果经验时的基础治理，又完全依赖于先学习这些治理方法。

## 6. 任务相关线程的最终分工

任务相关线程分为两类：任务管理线程、任务工作线程。任务工作线程采用线程池形式，由管理线程管理并派发工作。

| 部分 | 职责 |
| --- | --- |
| 任务管理线程 | 读取任务真实状态，机械判断需要筹办、执行还是结算，选择并派发对应工作 |
| 任务工作线程池 | 接收工作，实际调用相关治理函数，完成具体处理并返回结果定位 |
| 内部治理函数 | 依据任务真实情况实现治理能力，按实际结果改变相应 Vt 特征并形成动态 |
| 自我 | 产生确认需求目标，并对结算后的继续、等待、结束等后继方向作出治理决定 |

```text
任务当前状态
→ 任务管理线程判断并派发工作
→ 任务工作线程调用对应治理函数
→ 实际治理结果、特征变化与动作动态
→ 任务管理线程重新读取任务状态
→ 决定后续派发
```

管理线程不直接在自身循环中执行筹办、执行、结算的业务处理。工作返回也不能代替任务真实状态。

讨论提出的运行约束包括：同一任务同时至多一个工作线程处理；不同任务可以并行；已有执行尚未结束时不能重复启动同一次动作；事实不变且仍在等待条件时不能靠重复调用制造进展。这些约束的具体实现留待后续设计。

本轮已经明确“按状态机械派发”的原则，但执行前选择、执行条件准备究竟归筹办尾部还是执行入口准备部分，尚未最终确认，见第 10 节。

## 7. 任务筹办输入与参数核验的最新口径

### 7.1 输入与直接目标

任务筹办以任务头节点为输入。

其直接目标是补齐任务头节点中的方法节点；已有方法节点时，继续核对本次执行该方法所需条件是否齐备。不能把筹办仅表述为“返回候选名单”，而遗漏任务头的方法关联要求。

### 7.2 核验对象的最终修正

用户最后将核验对象明确为：

> 任务虚拟存在中，对应方法的参数特征部分。

因此，不能直接读取方法虚拟存在中的抽象条件，就认定本次任务的方法条件已经满足。

当前讨论中的结构关系为：

| 材料 | 在核验中的作用 |
| --- | --- |
| 方法虚拟存在中的参数规格 | 提供可复用的参数要求，是规格来源 |
| 任务虚拟存在中对应方法的参数特征 | 承载本次任务的方法参数实例及实际绑定，是本次核验对象 |
| 世界树中绑定对象的当前事实 | 提供本次核验依据；涉及值比较时读取实际特征当前值，不能以历史状态记录替代 |

核验路径为：

```text
任务头节点
→ 检查并补齐其中的方法节点
→ 定位任务虚拟存在中该方法的参数特征部分
→ 核对所需参数特征、具体特征绑定及对应关系
→ 读取绑定对象在世界树中的当前事实；涉及值比较时读取实际特征当前值
→ 按本次方法要求比较
→ 据实改变 Vt 中的方法及条件具备情况
→ 形成相应治理动作动态
```

参数项是否齐备、实际特征是否绑定、绑定对象的实际状态是否满足要求，需要分别判断。定义不完整或实际状态未查明，不能直接归为“已经确认条件不具备”。

多个候选如何确定任务头中的方法节点、参数特征何时实例化及绑定、缺失条件如何形成子需求，均需进一步明确；本文不把这些尚未讨论完的规则写成既定能力。

## 8. 治理函数模块与职责建议

用户指定内部治理函数集中实现在 `内部治理.治理函数类.ixx`，由任务工作线程实际执行。具体仓库相对路径、类的构造方式和接口签名尚未确定。

保存前的只读查找未发现该同名源码或其工程登记；本文只保存建立意向，不表示已创建该文件或已实现函数。

### 8.1 三个主入口

| 主入口 | 已明确的职责方向 | 内部步骤建议，尚非冻结函数清单 |
| --- | --- | --- |
| 任务筹办 | 以任务头为入口，补齐方法关联，核验任务 Vt 对应方法参数特征及实际条件 | 查找方法；确定并关联任务头方法节点；准备参数核验；核验参数与实际条件；形成缺失条件材料 |
| 任务执行 | 实际调用方法实现本次动作，取得实际结果 | 核验本次执行条件；实施本次方法；推进并收束执行；取得实际结果；执行前选择的归属待明确 |
| 任务结算 | 以真实需求满足情况为依据，完成相应结算及安全值或服务值反馈 | 核定需求满足；核定贡献与副作用；确定结算内容；完成反馈；收束本轮任务 |

表中“确定并关联方法节点”是需要实现的职责，不预先裁决它是候选关联、采用关联还是执行实例关联。

### 8.2 共用处理能力建议

可在内部共用“根据本次真实结果确认任务特征变化”和“形成治理动作动态”的处理能力。它们随具体治理步骤使用，不另派“生成动态”的任务，也不提供任意指定任务状态的入口。

需求目标的产生确认、任务建立、线程池管理与工作派发，在本轮建议中分别由对应职责承担，不塞入这三个主入口。模块是否还承载其它自我治理函数，需要新的明确范围；本文不扩张。

### 8.3 三个入口与精细函数的关系

三个入口承担可派发的基本能力；内部步骤在职责明确后可进一步实现为函数，再逐步成为更细的因果应对能力。函数数量由实际职责决定，不再依据先前 11 项过程描述强制建立 11 个函数。

## 10. 待细化规则与现行规范衔接

下列事项保留为后续设计输入，不在本次汇总中代替用户作出新的机器语义裁决。

1. **任务头中的方法节点是什么关联。** 要明确它是一个还是多个，如何从多个方法确定，以及与候选方法、本次采用方法和执行实例的关系。现行 5260 区分筹办信息补全与执行前选择，不能在没有对应解释时把“补齐方法节点”直接等同于已选择并冻结。
2. **参数实例形成时机。** 筹办需要核验任务 Vt 对应方法的参数特征，因此这些参数特征必须先有合法来源。需要确定何时实例化、何时绑定、如何处理改选方法和不同执行轮次，不能让本次核验引用其它任务或旧轮次材料。
3. **方法条件与执行条件的边界。** 要分别定义实际依据，以及哪些函数负责使其成立。还需确认执行前选择归哪个主入口：助手曾建议归任务执行的准备部分，这尚未取得用户的最终确认。若采用该建议，管理线程应能派发执行准备，不能等执行入口尚未完成的条件先成立，形成互相等待。
4. **六项状态的表达方式。** 明确每项对应哪些 Vt 特征、合法值及成立条件，哪些可同时成立，实际条件变化后如何重新判断。等待和取消等事实也需有清晰位置，但不预先恢复被删除的过程状态表。
5. **方法查找与需求分解。** 明确查找范围及完成条件、条件表达与求值、多个方法的比较、哪些缺失条件确需自我确认成子需求。
6. **双根反馈规则。** 用户目标包含安全值和服务值反馈。现行 6100 只承载主动安全结算，8100 保留服务根且不授权新的自动写入。后续需要明确实际贡献、归属、部分满足、副作用、防重复及服务根反馈规则；不能把当前规范缺口解释为用户目标被否定，也不能用固定加值替代设计。
7. **广义任务结算与各独立结论。** 本文按用户口径把需求满足到根值反馈放入整体结算链；现行 5090 / 5260 将任务轮次结算、需求满足、价值结算分别承载。后续组合必须保留各自真实依据，不能把一个完成标记代替其它结论，也不能强行等待所有受益需求全部核算才收束本轮。
8. **治理动作来源及动态合同。** 需要确定内部治理函数作为动作来源的身份、参数、作用特征及前后状态关联。现行规范对内建筹办动作、任务状态和世界动态有各自边界；不得仅凭函数名建立新的证明节点或第二动态权威。
