## 1. 目标、范围与可行性结论

目标是依托保留的 L1 和新数据服务，建设从现实事实读取、需求确认、任务筹办、方法执行到结果读回、任务结算、自我后继决策的闭环，不恢复已删除的旧 L2 及其上层实现。

结论：逻辑上可行，不需要把概念树纳入主动治理主线；当前新代码尚不能直接串成完整闭环。已有的是结构、记录和参数传递能力，还缺少治理判断、执行控制和结果反馈。

这不是要求数据类承担治理逻辑。闭环运行会产生任务状态、执行轮次、参数冻结、执行结果和结算等新的事实，必须补齐相应数据操作接口，再由应用服务组织起来。

本规划的边界：

- 概念树视为被动形成过程，不作为本轮目标生成、方法选择、任务调度或结算的主动环节，也不成为闭环启动前提。
- 现有其他切片的概念相关未提交源码和工程变更不作为已发布能力，不由本规划接管。
- 保留新数据服务的分工；应用服务通过新数据服务读写事实，不绕过它们直接调用 L1，也不调用旧 L2。
- 本文保存路线和待细化事项，不冻结最终函数签名、DTO、物理文件、所有权或事务合同，不授权直接开工。
- 后续实施须按届时正式规范、当前源码及所有权重新扫描，形成范围清楚、合同完整的代码计划。

## 3. 闭环中的结构职责

### 3.1 世界树：现在是什么

世界树保存现实存在及其当前事实，是行动前条件检查和行动后结果判断的依据。治理读取应绑定一致的事实版本，避免把不同版本的目标、当前位置、参数和当前特征混合使用。

世界树应用服务负责现实信息的语义操作和读回组织，不承担需求优先级判断或任务调度。

### 3.2 需求树：希望达到什么

需求目标仍然是一次特征。目标与当前状态之间计算出的二次特征表达行动方向，不代替目标，也不直接等于方法或执行路径。

需求树保存目标及其分解关系；需求查询 / 去重列表只能是同一批需求事实的投影，不形成第二套目标权威。需求暂时满足或退出活动状态，不等于删除原目标和身份记录。

任务绑定具体需求。需求的父子关系承载目标分解，不再由任务父子关系重复保存一套目标树。

### 3.3 任务方法结构：准备怎样实现

本规划将“任务方法树”理解为任务目标下的方法候选、条件依赖与执行路径组织。方法本身作为可复用信息保存，不与任务执行历史混为一体。

方法继续保持头节点、条件节点和结果节点三类信息，并具有方法虚拟存在。函数绑定是执行连接，不必因此新增第四类方法知识节点。

方法虚拟存在保存抽象参数规格；任务虚拟存在承载实例化后的参数与本任务材料。待复制的特征类型数量不固定，实例化和绑定必须支持相应数量及确定的参数对应关系。

任务虚拟存在和方法虚拟存在属于治理与执行材料，不作为现实存在挂入世界树。当前按“任务中的方法节点”去重的实例结构，还需要补充跨轮次隔离设计：究竟复用实例还是逐轮创建，应在详细合同中裁决，但旧轮次冻结参数不能被新绑定覆盖。

## 4. 主闭环与非成功分支

```text
读取同一事实版本下的世界当前状态与需求目标
    ↓
自我判断差距，确认或复用需求
    ↓
建立 / 复用任务，准备任务虚拟存在
    ↓
查找方法，完整核验方法条件
    ↓
按当前事实选择方法，实例化并绑定参数，冻结本轮材料
    ↓
执行方法，取得并记录实际结果
    ↓
独立读回世界事实，结算本轮任务
    ↓
自我重新判断需求，决定继续、等待、结束或取消
    ↓
后续事实变化或合法后继决议触发下一次治理
```

需要保持的判断边界：

1. 方向不等于方法。“需要增加、减少或改变什么”只是查找依据，还要检查方法条件、参数、可用性和安全性。
2. 条件不足不直接生成需求。先形成缺失条件材料，由自我确认是否成为子需求，再进入需求和任务承接。
3. 方法查找与条件核验属于筹办，不能以第一个匹配项代替完整候选范围，也不能在筹办未完成时提前冻结执行实例。
4. 函数返回成功不等于实际结果成立，更不等于需求满足。必须独立读回实际世界事实，再比较原目标。
5. 目标未满足不等于立即重试。已开始的执行轮次先形成唯一结算，再由自我决定继续、等待、结束或取消。
6. 无方法、条件不足、材料等待、事实版本陈旧、安全拒绝、执行失败和结果未知必须显式区分，不能统称成功或无限重试。
7. 跨数据服务的分步提交须有阶段记录、幂等身份和独立读回，不能假设天然存在跨所有者原子事务。
8. 消息、线程变量、日志和队列位置不是任务状态、执行结果或结算事实。

## 5. 应用服务职责建议

以下是职责建议，不是已创建文件或已冻结接口。

| 应用职责 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 世界树应用服务 | 现实信息一致读取、语义修改和结果读回组织 | 需求选择、任务调度 |
| 需求应用服务 | 目标与当前状态比较、方向计算、需求复用、关系维护和满足判断 | 代替自我确认新目标、直接执行方法 |
| 方法应用服务 | 方法查找、条件求值、参数要求解析、可执行函数绑定与调用 | 决定需求满足或提交任务轮次结算 |
| 任务应用服务 | 筹办、实例化、参数绑定、轮次冻结、执行结果处理及结算 | 自行生成需求、自行授权现实改变 |
| 自我治理应用服务 | 确认需求、确定优先级、发出治理意图、消费结算并决定后继 | 绕过数据服务写入事实、以消息替代独立读回 |

数据服务负责记录合法性、一致性和提交，不替自我决定目标，也不自行调度方法。方法函数在执行时，从本轮冻结的方法实例参数中取得场景、存在、特征等实际数据，才能真正运行。

## 6. 分阶段实现路线

### 阶段一：冻结最小闭环合同

先解决会直接影响实现的事项：

- 第一批正式方法从哪里来，如何绑定实际方法函数。
- 条件组的身份、组合、比较和读取合同；无条件方法的显式表达。
- 任务状态、执行轮次、参数冻结、实际结果和结算如何关联。
- 方法与参数规格的版本如何绑定到本轮实例，如何阻止冻结材料被覆盖。
- 不同数据服务分步提交时，失败、重放和恢复如何处理。
- 涉及现实改变的方法，其效果范围、授权、安全检查及结果未知如何处理。

首批方法来源是真实设计缺口：[3300 方法根规范](../../规范/3300_根规范_方法.md)第 105 行明确记载“没有来源方法的首代发布合同当前未闭合”。必须先完成相应裁决，不能用临时测试方法或未经裁决的来源节点冒充正式方法来源。

阶段出口：最小闭环所需语义与接口合同可供详细设计使用；仍有关键选择时保持为设计输入，不标成可执行计划。

### 阶段二：补齐最小运行记录的数据操作

沿一个具体闭环补齐，不先建设完整通用框架：

- 需求：归属、父子关系、当前状态、目标查询与复用所需数据操作。
- 方法：显式条件组、版本和执行绑定信息。
- 任务：状态、轮次、冻结材料、执行结果和结算记录。
- 方法实例：跨轮次参数隔离、冻结版本和历史读回。
- 分阶段编排：各所有者的提交结果、恢复定位和幂等重放信息。

阶段出口：上述正式记录可以通过新数据服务建立、查询和受控迁移；重复请求不重复创建或重复结算，部分失败可定位恢复。该出口不等于生产治理闭环完成。

### 阶段三：实现单目标应用闭环

选择一个正式来源、真实可观察、效果有界的方法，打通：

```text
一个需求 → 一个任务 → 一个方法 → 实际执行
    → 世界结果独立读回 → 本轮结算 → 自我再次决策
```

先不做复杂方法搜索和递归子目标，但必须保留条件不满足、无方法、执行失败、结果未知和目标未满足等分支。对外部副作用不得通过盲目重试制造重复执行。

阶段出口：实际结果能够改变下一次治理判断，重复结果不会造成重复结算；应用组件可通过受控入口调用。方法被调用或返回成功本身不构成出口证据，也不等于正常启动已接通。

### 阶段四：接入正常启动与运行组织

完成世界根、自我和安全 / 服务根的初始化，将应用闭环接入正常入口。根需求和初始方法的形成必须遵守正式合同，不靠硬编码“提高安全值 / 服务值”的测试动作证明生命闭环。

初期可以只允许一个活动任务、一个工作线程，但保留自我、任务管理和任务工作的职责分离及异步交接：

- 自我形成不可变治理意图，由任务管理独立接收并回读。
- 任务管理按正式状态派发筹办或执行工作，不在自身循环同步直调筹办并把返回值视为状态事实。
- 工作线程执行绑定工作，结果消息只提供定位；任务管理独立读回后再提交任务状态和结算。
- 自我独立消费结算及当前事实，决定需求状态与合法后继。
- 涉及现实改变的方法，在冻结后、执行前取得所需授权，并接受独立安全检查。

上述运行边界见 [8100 自我线程与任务管理线程权责边界](../../规范/8100_子规范_自我线程与任务管理线程权责边界_20260720.md)第 85、87、97 行附近。同步单函数只能证明应用组件，不能命名为生产治理闭环。

阶段出口：正常启动可达一个真实任务闭环，并能有界等待、停止和恢复；不以空宿主循环或日志输出替代结果证据。

### 阶段五：扩展为持续治理闭环

单目标链路成立后，再增加：

- 多方法候选、完整条件检查与选择；不能按列表顺序任意选择不可比较或并列候选。
- 缺失条件经自我确认形成子需求，子任务完成后重新判断原任务。
- 多需求优先级、需求 / 任务复用与资源竞争。
- 等待唤醒、取消、重启恢复和结果未知处理。
- 多轮稳定运行，以及重复消息不重复执行、不重复结算。

概念形成继续作为旁路过程，不成为上述链路的启动前提。

阶段出口：依照正式验收范围证明持续多轮稳定性，而不把单目标工程里程碑等同于全部自我内部治理能力完成。

## 7. 后续验证与完成声明边界

本节是未来实施的验证要求，不表示本轮已经运行这些验证。

| 验证面 | 必须证明的结果 |
| --- | --- |
| 目标与方向 | 目标仍为一次特征；同一事实版本下计算方向，世界变化后重新判断 |
| 方法条件 | 条件组完整读取与求值；显式无条件与缺失条件材料不会混淆 |
| 实例与参数 | 可变数量参数正确对应；冻结版本和参数不会被后续轮次覆盖 |
| 执行与结果 | 方法返回、实际世界结果、任务目标及需求满足分别判定 |
| 结算与重放 | 每个已开始执行轮次形成唯一结算；重复消息和请求不重复推进 |
| 失败与恢复 | 等待、拒绝、陈旧、失败和结果未知分支明确；恢复不盲目重做副作用 |
| 正常入口 | 从真实启动入口可达应用与任务工作链，而非只从测试直接调用 |
| 持续治理 | 结算后自我依据当前事实作后继决策，多轮运行有边界且可停止 |

## 8. 建议的实施起点

第一份正式实施计划建议聚焦“单需求—单任务—单方法的受控治理闭环”。先冻结必要合同，再沿数据记录、应用判断、执行、读回、结算和启动逐段完成，不先把所有应用类的函数外壳建齐，也不恢复旧 L2。

本节是后续计划选题建议，不是执行队列登记。若最早缺口只能先由提供者独立交付，应先冻结并实施该提供者的完整合同和读回边界，将尚不具备条件的消费侧保留为路线输入；不得把本路线的五个阶段机械登记成多层待激活计划库存。
