# PROJECT-IXX-TO-HEADER-SOURCE-MIGRATION：核心公开类型连通组件迁移代码实施计划

日期：2026-09-14

版本：v0.4

状态：暂停（`FUNCTION-PHYSICAL-LOCATION-DRIFT`）

计划身份：`PROJECT-IXX-TO-HEADER-SOURCE-MIGRATION-CORE-COMPONENT`

## 1. 目标、边界与完成条件

本计划只退出以 L1 公开类型为根的完整源码连通组件，消除它内部所有 C++20 命名模块和两份 `.cppcpp` 实现。它是“全项目 `.ixx` 改为 `.h/.cpp`”的首个可施工叶，不是全项目退出声明。编辑顺序固定为“启动/装配 → 业务 → 领域 → L1”；它不改变本组件必须原子构建、验证和发布的边界。

完成时：

1. 下表 43 个 `.ixx` 均由同目录、同基本名的一对 `.h`、`.cpp` 取代；两份已有 `.cppcpp` 均以对应目标 `.cpp` 唯一承接，不能保留第二实现单元。
2. 本组件内、`入口.cpp`、四个直接消费本组件的验证源不再有 `import`；本组件不会保留任何 `.ixx` 消费新头的桥接形态。
3. 主工程、filters 与五个验证工程不再把本组件旧格式登记为 `ClCompile`；新 `.h` 是 `ClInclude`、新 `.cpp` 是 `ClCompile`。
4. 旧文件实际由 Git 删除，源码、工程登记和验证工程对本组件的扫描均无 `.ixx`、`.cppcpp`、`export module` 或 `import` 语句；根工程及五验证工程 Debug/Release x64 均可编译和链接。

不在本计划范围：其余 14 个独立 `.ixx`（D455/线程/时钟组件）、它们的消费者、业务逻辑、公开签名、DTO、状态机、事务、生命周期、持久化、运行行为或业务验收。它们由后续独立连通组件计划承接。

## 2. 正式依据与当前事实

- [代码文件建立归属与模块命名规范](../规范/代码文件建立归属与模块命名规范.md) v4.0 §2、§3.2、§3.4：生产代码只能为 `.h/.cpp`，既有模块必须同步迁移消费者与工程登记，非 inline 定义唯一落入 `.cpp`。

- 基线 `6fbd2a7159d43a17039b13d97e03e3e7498f2e04`：57 个跟踪 `.ixx`，其命名模块 import 图无环。以 `核心/服务.L1事实基座.ixx` 进行无向闭包得到 42 个模块；再加入唯一普通入口消费者 `启动.程序入口.ixx`，本计划固定为 43 个模块。`装配.普通应用.cppcpp` 与 `业务/应用服务.自我形成.cppcpp` 是其中两个接口模块的唯一实现单元，必须同时退出。

这证明首叶不能再按“合同孤岛”拆分。组件内源文件必须同一代码结果迁移；仍保留 `.ixx` 的其他连通组件不包含本组件模块 import，故不是新头的模块消费者。

## 4. 代码与依赖合同

“非 inline”在本计划中严格指上表第三、四、五行的词法与语言形态：不能仅因为函数目前在类体内、被一个调用方使用、名称含 `static` 或编译未报 ODR 而把它归为 `.h`。反之，类体内定义不得为了追求 `.cpp` 数量被拆出并改变可见性。执行前以基线 blob 逐项列出命中的函数头和源行号，施工记录只允许**复述**此清单，不得新增分类；源行号变动不构成语义漂移，签名文本或所属类不一致才构成漂移。

所有目标 `.cpp` 的稳定骨架固定为：`#include "同基本名.h"` → 仅该实现需要的原私有标准库 / Windows / 项目 `#include` → 原命名空间块 → 上表命中的定义按基线相对顺序。所有目标 `.h` 的稳定骨架固定为：`#pragma once` → 公开布局、模板和 inline 正文所需的最小 `#include` → `namespace 海中鱼巣 {` → 上表第一、二行及第三行的声明。任何 `module;`、`export`、`import`、旧模块壳、文本包含 `.cpp` 或双路径均不是插入锚点。

迁移期间不新增函数、DTO、调用者、调用边、异常分支、诊断责任或机器事实；原有诊断责任和用途保持不变。没有现成用途卡的实体标记“当前无用途卡”，由本计划施工记录的知识变更清单交给后续知识维护，而不是由执行者创造第二实现。

### 4.2 声明、定义和 ODR

每个新 `.h` 使用 `#pragma once`，保留原命名空间、公开类型、成员布局、枚举值、别名、常量、函数签名、默认实参、`noexcept`、访问控制和可见 API 的逐字符语义；仅删除模块声明和 `export` 关键字。任何原本由调用方必须可见的模板、`constexpr` 与显式 `inline` 定义仍在唯一 `.h`；所有其它自由函数、静态数据定义、非 inline 成员函数、非模板辅助和匿名命名空间辅助由唯一同名 `.cpp` 定义。类的非 inline 成员在头声明、在 `.cpp` 以完整限定名定义；不得把原大段实现复制进多个头或多个 `.cpp`。

每个 `.cpp` 第一条项目包含必须为同名 `.h`。只为实现私有的标准库 / Windows / 项目依赖放入该 `.cpp`；为完整公开类型、成员布局、模板或 inline 定义所需的依赖放入 `.h`。发生不完整类型错误时，只能按此规则将真实布局依赖提升到拥有该布局的头，不得用前置声明隐藏值成员、继承基类或 inline 函数依赖。

### 4.3 `import -> #include` 的唯一映射

表 3 的每一行同时是 import 映射：旧模块名 `海中鱼巣.X` 一律改为对应的 `X.h`。项目内部包含统一使用从包含文件到目标头的相对双引号路径：同目录 `"名称.h"`；领域到核心 `"../核心/名称.h"`；业务到领域 `"../领域/名称.h"`；业务应用服务到业务计算 `"../计算.二次特征.h"`；装配到子目录 `"业务/...h"`、`"核心/...h"`；根目录启动、入口使用 `"启动....h"`、`"装配.普通应用.h"`。`export import` 与普通 `import` 均直接替换为该 include；不存在 global module fragment、兼容 module 壳、`#if` 双路径、宏别名或旧模块前置声明。

在组件最终源中，`module;`、`module 名称;`、`export module`、`export import`、`import` 必须为零。组件之外的旧模块不得 include 本组件新头；按基线 import 图它们无此依赖。若 S0 或施工中发现一个未列出的 `.ixx` 需要本组件头，则停止本计划并由计划支撑扩大连通组件，不能建立临时桥。
