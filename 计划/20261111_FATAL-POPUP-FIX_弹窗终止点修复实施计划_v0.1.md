## 1. 用户裁决（2026-11-11，替代旧口径）

| 范围 | 旧口径 | 当前裁决 |
| --- | --- | --- |
| 依赖未就绪 | 多处按工程错误终止，或被改写为“内部不一致”“未支持” | 在运行期属于合法等待，不得弹窗终止 |
| 并发变化 | 节点被删除、预期不符、读回已变化时终止 | 内部世界允许随时变化，并发变化属于正常情况，返回既有的“前提已变化”类状态（沿用既有裁决） |
| 获取类读取 | 获取特征、获取动态概念、获取特征概念、读取任务贡献对应：做并发重读一致性核验，重读耗尽后终止 | 获取动作只负责取值，不负责判定是否变化：读一次就返回所读值；真实结构损坏仍按工程错误处理 |
| 登记缺失方法返回“方法头不合法” | 抛出异常后终止 | 保留终止；施工时在弹窗和日志中写出具体返回值 |
| 需求建立的合同拒绝（会形成环、同来源目标冲突、需重新确认） | 需求owner拒绝，调用方抛出异常后终止 | 所有需求都应当建立。由自我线程按规则决定是否生成实现任务；不能满足时向任务发送“当前需求不能被满足”，任务随之阻塞（第8节阶段3） |
| 等待的唤醒 | 无，“执行依赖未就绪”进入阻塞后不会被唤醒 | 新增“依赖就绪消息”唤醒等待者（第8节阶段3） |

交互窗口依规范补充的裁决（逐条表的“设计说明”列已注明）：

- 读取历史动作时，只核对记录本身和冻结定义，不按目标存在当前的特征组核对。依据 AGENTS §1.1 第6项“保留事实”。适用于新_动态类.cpp 1593 行和 1601 行。
- 重新启用任务时，先发布重启记录，再写“待查找方法”状态。依据 AGENTS §1.1 第4项“先记录本次动作，再执行”。适用于新_任务类.cpp 10700 行。
- 资源失败按 §4.4 属于工程故障：发布链维持终止，不为它追加枚举值。适用于新_需求类.cpp 6314 行和 6365 行。
- 新需求筹办资格状态在末尾追加“依赖未就绪”。适用于新_需求类.cpp 7571 行。
- 负服务值依据规范 3100：差异溢出时饱和到 INT64_MAX，状态为“需增加”；同时删除与规范冲突的代码注释。适用于新_需求类.cpp 7985 行。

## 2. 修复规则

| 规则 | 做法 | 条数 |
| --- | --- | ---: |
| R1 | 函数状态枚举里已有对应值，终止改为返回该值；调用方已能处理 | 31 |
| R2 | 同 R1，并同时修改未处理该值的调用方 | 13 |
| R3 | 在枚举末尾追加值（只追加，不重排），并修改所有调用方 | 5 |
| R4 | 在 `catch(...)`／`catch(std::exception)` 之前增加对具体业务状态的捕获，映射为入口既有的业务状态 | 7 |
| R5 | 并发重读耗尽时，返回“前提已变化”类状态 | 1 |
| R6 | try 区内把合同非成功 `throw std::logic_error` 出去的抛出点，改为就地按业务状态返回 | 19 |
| Q1/Q2/Q3 | 按第1节对应裁决处理 | 7 |
| N | 复核后确认只有代码错误才会触发，不改 | 22 |
| X | 待裁决（第8节） | 1 |

各规则共同的约束：

1. 不得把工程故障改为 false、空材料或默认值。只有已有业务语义的值才能作为返回值。
2. bool、optional 这类没有状态通道的函数，若需要表达业务非成功，按逐条表的设计迁到已有的状态化入口或追加状态，不得用 false 兼作工程失败。
3. 枚举只追加，不改变既有数值。
4. 判为 N 的条目和资源失败，仍走工程终止。

## 3. 共性修复（一次修改，覆盖多条）

1. **需求目标核验（新_需求类.cpp）**
   - `投影需求目标实例` 在非枚举模式下，与枚举模式一样抛出 `核验状态::依赖未就绪/前提已变化`，不再改写为“内部不一致”。

   - 13 处 `catch(核验状态 s){要求需求物理(s==前提已变化);...}` 改为映射成状态，避免在 noexcept 函数里直接 `std::terminate`。这 13 处位于 2198、3621、3704、3837、4819、4854、4907、5350、5687、5759、5860、5920、6045 行。

   - 以上四项必须同一次施工，否则会出现新的终止路径。
2. **场景核验批（新_任务类.cpp）**
   - 在内部结构 `新任务本次场景核验批` 中增加字段 `依赖未就绪`。
   - `准备本次场景核验批` 和 `读取本次场景核验批` 遇到“依赖未就绪”时，置位后正常返回，不再重抛。
