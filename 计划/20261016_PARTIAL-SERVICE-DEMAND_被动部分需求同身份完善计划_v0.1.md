## 1. 目标与最新裁决

本轮修改内部治理中的需求结构和任务推进；原因是外部要求可能不完整；目的是在不虚构未知目标的情况下先建立正式 D/T，逐步补齐后沿原 D/T 执行服务。网页结构化输入只取得外部信息，不代替实际服务动作；不新增本能动作、状态、动态或因果事实。

用户已经明确：

1. self 收到部分服务要求时，直接在结算需求子链建立待完善 D，是任务筹办以外的第二种子需求来源。
2. manager 为 D 建立唯一 T；同份补充沿原身份，不另建 D/T。
3. 完善阶段采用固定内部治理，直接判断必填字段有无值；不新建完整度、阶段目标或其它特征类型。
4. 信息完整且服务对象明确确认后，原 D/T 重新筹办实际服务。完善信息不完成 T，不增加服务值。
5. 未知使用 optional 表达，不能写空稳定编码、默认目标形式、虚构特征或伪目标。

本轮交付基础治理闭环：结构化部分提交→D/T→缺项显示→同份补充→明确确认→原 D/T 正常筹办。未实现自动自由文本理解、自动追问和缺项本能方法；不得把等待用户补充说成已有自动方法补齐能力。

### 5.1 来源、合并和冲突

- 首次提交必须有非空来源要求标识，浏览器开始一份新要求时生成，首 POST 重试复用。键为已绑定人类+公开会话+来源要求标识；首次响应丢失也精确取得原 R。该键只服务这一要求来源，不是全局幂等账。
- 后续显式提交 R 编码及同一来源键；owner 重新核验。不同人、不同会话或不同来源键不能补充原 R；不按相似文字或完整目标自动合并不同 R。
- nullopt 表示本次不补充；不清空旧值。未有值可追加；同值精确重复；已知值冲突整次零写并返回冲突字段，不采用后写胜出。形式为值却给方向、形式为方向却给域/比较，属于输入矛盾，零写。
- 已给节点逐项核验真实存在/概念类型；跨字段语义在相关字段均具备时核验。字段缺失不是工程故障。
- 首次完整时扩展复用 `建立或取得理解()`生成完整不可变预览并关联 R：`服务要求理解请求`与`服务要求理解信息`尾部追加`optional<稳定编码> 来源要求节点`，R来源理解以R身份+原目标固定语义查重，必须匹配R已知完整目标和来源人/会话；无R的旧调用维持原查重。不同R即使同目标也形成不同理解/确认，保留“一个确认最多采用到一个D”合同。确认只针对R当前完整预览，不能拿其它R的同义预览代替；固定语义变化继续走既有重新确认合同。
- R写入口持有原非递归mutex，完整理解和确认复用抽为私有已加锁实现，不在持锁时调用再次加锁的公有函数。新建理解闭包与R理解引用同次追加发布；新确认节点与R确认引用同次追加发布，已有理解/确认精确复用时也须在同次预期核验后关联，不发布悬空半关联。
- `新服务要求确认目标`尾部追加`optional<稳定编码> 来源要求节点`，读取确认身份/语义完整交付该来源。固定语义比较仍比较含义，不以R相同替代语义相同；采用入口另行按R身份选择原D。
- R确认后不允许换义或撤销已知字段；精确重投可复用。新诉求必须显式新要求。本轮不实现跨会话续接、改写目标或撤回协议。
- 概念定义后来改变时，保留原R/理解/确认固定含义，返回`需重新确认`并阻止执行，不清目标、不把完整D退回未知。不得将当前概念扩大后的含义覆盖为原目标；本轮不自动替换旧预览/确认，也不声称实现同固定含义刷新能力，保持阻塞并明确显示。不自动创建替代R或补造确认。

### 5.2 完整性固定算法

必需：来源人类、目标存在、目标FT、目标形式。值形式另外需要域+比较且无方向；方向形式需要方向且无域/比较。全部字段具备并合法后，才生成完整理解；明确确认独立检查。未完整时仍发布 R/D/T；完整未确认仍停留完善阶段。缺项从正式材料现场计算，不持久化完整度或伪布尔特征。

结果含状态、新/既有 D、可选完整目标列表项、缺项和是否首次转为完整；该转换信号只用于控制，消费方仍 fresh 读取。按来源 R 反查 D：0则建立，1则复用/补齐，多个为工程不一致。需求owner从只读接口 fresh 读取 R，在底座完整预期中核验 R相关字段、确认/理解、D、根和已有列表；预期漂移重新读回，不覆盖后来事实。

完整目标列表仅索引已明确 D。部分 D 仍是正式需求，参与树全集、数量、父子、权重、D/T关联检查、服务任务集合；不为它建立伪目标列表。来源 R→D 通过 D 的正式来源引用反查，终身保留，不单独持久化一份待完善列表。

`查询全部需求列表()`的`需求组`改为统一治理 DTO 全集，`列表项组`只覆盖完整 D；必须核验每个完整 D 恰一列表项，部分 D 无列表项。`新需求列表任务对应项`列表身份改 optional。完整目标查找、冲突比较、方向检查仅消费完整子集；若本次目标本身未完整，返回具名`需求信息待完善`而非结构错误/满足。

确认后同 D 一次发布目标及目标列表；旧完整采用入口先按确认/关联 R 查询此 D，若存在则复用，不再以来源类型不同建立第二 D。同目标不同 R 不强行合并 D，但共享完整目标列表项。全部常规 D 行为保持不变。

## 7. self 与 manager 消息闭环

`新自我消息类型`追加`外部服务要求变化`，载荷为正式 R 定位，不带未核验目标、假 T/X 或自由文本。self 公共窄入口：

```cpp
新自我消息接收结果 提交外部服务要求变化(稳定编码 要求节点) noexcept;
```

`新自我治理消息`尾部新增`optional<稳定编码> 外部要求节点`，仅新类型允许有值，其余互斥载荷和来源状态必须为空。`新自我消息处理结果`尾部新增`optional<新部分服务需求处理结果> 部分服务需求处理`，沿现有承接结果携带T。处理函数为self私有`处理外部服务要求变化`，遵守既有消息处理函数的运行项参数形状，不新建并行邮箱。

由已绑定结构化装配调用；通过既有邮箱、容量和停止机制。消息仅唤醒：处理时读取当前 R，验证人类/结算父和材料来源，再调用需求owner建立/更新 D。每个 R 的同时处理串行，同 R重复消息允许合并唤醒但不得丢失后续补充；不可只按 R永久去重。使用原有消息编号区分投递，不新增业务版本。

self 通过现有`新任务承接依据`追加`外部服务要求=7`，`新任务承接消息`尾部追加`optional<稳定编码> 外部要求节点`，仅该依据携带R，其它依据必须为空。manager fresh复核来源再调用唯一任务建立入口。self不阻塞等待manager，复用现有future轮询/唤醒结构。队满/停止不得回滚已建立 R/D；后续同输入重试以及既有全树关联检查能恢复唯一 T。处理结果只报告已写入/已交接/待补充，不能伪称任务完成。

manager新增self友元专用私有签名`新任务承接接收结果 提交外部服务需求承接(const 新任务承接消息&) noexcept`；公共一般提交不得接受该依据。它共享现有承接邮箱/容量/停止检查，不新增保留通道或独立队列。self先发布D再交接，队满保留运行项重试；没有取得有效回执不冒称已建T。

manager 对任意 D 在安排方法筹办前调用任务owner固定检查：

```cpp
enum class 新任务需求准备状态 : std::uint8_t {
    待完善=1, 可筹办, 任务不存在, 工程故障
};
struct 新任务需求准备结果 final {
    新任务需求准备状态 状态 = 新任务需求准备状态::工程故障;
    稳定编码 任务节点;
    std::optional<稳定编码> 需求节点, 外部要求节点;
    std::vector<新服务要求缺项> 缺项;
};
新任务需求准备结果 复核任务需求准备(稳定编码 任务节点) const noexcept;
```

结果区分`待完善`（缺项）、`可筹办`、身份/工程错误。部分D建T后进入`等待条件`，明确等待R补充或确认事件，不反复派worker查不存在FT。已完整时按原通用资格决议进入`待查找方法`。不新增任务业务状态、轮次或阶段特征。

`新任务等待原因`在`未分类`前追加`需求信息待完善`，作为当前读取的治理原因，不创建特征。`新任务调度材料项`尾部追加`optional<新需求治理信息> 需求治理`，旧`需求`仅完整D有值；完整性先判，partial不得落`需核查`。manager普通等待扫描遇该原因只保留定位/缺项，不派W1/W2、不因定时扫描唤醒；R变化消息或fresh发现该D已经完整且确认有效时才进入恢复分支。

task公开新增`新任务治理承接结果 承接外部服务要求(稳定编码 需求节点, 稳定编码 要求节点) noexcept`，仅manager消费self该依据时调用。入口fresh核验D/R并建立/复用唯一T：部分D将新建T置等待；完整D只有T无X/无候选且在`已建立/等待条件`时可按资格前推到`待查找方法`；其余活动或终结T只读幂等返回，不借消息重新启用。该函数复用既有承接结果，不新增任务事实账。

新事件到来时，self/manager始终fresh读取同D/T。仍部分则更新缺项；首次由待完善转完整且T处于`已建立/等待条件`时，按合法状态迁移同T到`待查找方法`。在待完善阶段不得产生方法候选或X，若确有此矛盾才进入工程诊断，不强行清除正在执行的事实。已完整且T正在查方法/查条件/执行/评估/等待self或已终结时，同R重复事件只读复用原T，不清候选、不重筹办、不错误报错、不重新启用；后继仍由原通用治理负责。已完整但通知曾丢失而T尚在`已建立/等待条件`时可以按fresh完整目标重新核验普通承接资格并唤醒，不靠一次通知标志决定。旧部分事件晚到读取到完整D，不得把T倒退到等待。目标/当前T定位不匹配时本次事件失效，不覆盖旧X。

方法召回、条件提议、目标复核、执行前、self完成裁决、task完成发布和服务值结算各有完整性硬门。信息补齐只是可筹办，绝不发布已完成或结算。现有最多10个活动worker限制不变，完善等待不占worker。

## 8. 网页实际入口及生命周期

沿现有活跃且明确绑定第一权限人的结构化网页通道；匿名/失效会话不能提交。不把普通聊天消息当要求。

在 `宿主.网页对话.h`增加 `网页部分服务要求提交`（optional要求编码、来源要求标识、optional FT/形式/域/比较/方向）及部分结果（R、可选D/T、已知字段、缺项、可选完整预览、交接状态）。空字段映射nullopt，非法数字不是未知。

HTTP本轮可选D/T默认不提供：回复必须准确报告R与“消息已接纳/等待重试”，不等待self/manager，不宣称任务已建立。不得为填写D/T绕过owner扫描私有schema或新增装配缓存。缺项、理解及确认状态都来自R正式查询。

`网页服务输入回调组`增加提交部分要求与查询部分要求函数指针，签名分别为 `(string_view,const 网页部分服务要求提交&) noexcept`和`(string_view,uint64_t) noexcept`。由`启动.应用程序.cpp`绑定到`装配.普通应用`新增同形入口。

新增 `POST service/request` 与 `GET service/request?id=...`。首POST来源标识由页面在“新要求”时生成并在重试保留；编辑只更新已知字段，不更换R/来源键；明确“新要求”才清除旧R/预览并生成新来源键。UI去除尚未知字段的强制required，显示缺项、输入冲突和交接状态。完整后仍使用现有重述/确认界面，不默认确认。

装配提交：先核验会话→owner保存/补充R→投递self定位；查询可重新投递未交接/待刷新R，不假定一次通知可靠。完整预览确认成功后同样投递R，不能只返回确认而断链。已有完整预览/确认API保持可用；若关联R则按本链刷新原D，不关联R的旧主动入口保持原语义。

启动时装配只读接口、self消息依赖及已有结算父定位，接口必须在线程启动前就绪；shutdown先停止网页接收，再停止并join使用线程，最后解除接口并销毁owner。调用owner期间不持装配锁等待self/manager；不得引入专属运行服务或工作线程。

## 9. 工程异常、并发和结算隔离

- 外部字段非法、来源不符、同R已知字段冲突是输入结果；节点损坏/读回异常/双D双T是工程错误，日志、弹窗、终止受影响链按既有工程保障，不能伪装缺项。
- 各owner锁顺序保持现有方向；消息携定位，不在self锁内同步等manager；R/D发布靠完整预期与owner序列化，不持业务锁跨异步等待。
- R补充成功而消息失败，R仍保留；D出生而manager消息失败，扫描及重投补齐；确认成功而D未转完整，原确认可重读重投；转换后重投精确复用。
- 服务任务集合包括部分D对应T，但该T不具备完成/结算资格。旧获取动作的数量贡献仍要求同X来源；新外部D没有伪造X，不归因到其它获取动作。
- `核验直接服务结算来源`增加外部来源合法分支：父仍为结算D，R/来源人/完整确认/目标一致，T正式完成及现有结果闭包全部成立。不得仅因来源承接T为空拒绝，也不得取消现有确认/完成/去重硬门。
- 不实现目标换义、取消旧确认后改目标、跨会话合并、恢复新旧库迁移或持久化格式升级；若本轮字段随现有current-only持久化自动保留，只报告实际已有覆盖，不宣称恢复已验证。
