## 1. 已确认的设计口径

1. 系统有相互关联的外设世界、自然语言世界和现实世界，不再另设第四个“自我世界”。此前所说“同步到自我世界”统一理解为自我处理后按信息性质发布到自然语言世界或现实世界。
2. 外设世界描述实际取得的窗口、通信、输入输出及收发信息；自然语言世界描述材料、结构、指代和表达主张；现实世界描述自我认识的现实存在、特征、关系、状态和动态。
3. 外设世界树类只负责更新外设场景信息。本能方法通过正式信息读取能力直接读取外设场景，不经外设类另设的本能专用供数接口。
4. 信息以交互场景为范围。一个交互者形成一个交互场景，外设世界和现实世界分别有对应场景；自然语言场景按材料与解释需要建立并明确关联，不要求每个交互者只能有一个语言场景。场景建立不以已识别现实身份为前置，接入期按可确认的对象关联组织，具体归并合同见后文。
5. 客户端窗口、输入区、输出区、服务端端点等是场景中的存在，不因参与交互就预设为自我的子存在。组成、场景归属、连接和控制关系分别描述。
6. 有什么信息就使用什么信息，以自我实际读取到的信息作为处理依据；身份认证、真假判断、证伪及需求理解是其上的逻辑，不作为原始信息进入自我处理链的门槛。
7. 原始表达的取得不等于表达内容已被证明为现实事实。不得把“我是周春海”预先过滤，也不得由外设类将其直接裁定为已认证身份。
8. 外设场景需要状态和动态。由既有机制根据实际特征变化及真实动作形成，不手工复制一套状态、动态或因果事实。

本节记录本窗口最新明确裁决。旧材料把窗口本身等同交互场景的口径，在本方案具名交互范围内由本节替代；不据此修改其它场景规则、引用生命周期或数据权限。

## 2. 目标、范围与完成条件

目标：建立外设场景的更新通路，使连接、收发、服务对象识别和需求交互所需材料能够成为正式可读的信息，并经本能读取衔接另两个世界。

近期范围：网页交互场景。首批覆盖场景成员及关系、访问入口、会话、输入输出、收发材料及相应状态动态；登录、多窗口和超时按实际消费者扩展，不把它们都设为首批运行前提。

完成条件：实际外设变化可以在正确场景发布；本能可按明确范围读取并追溯来源；重复读取不会制造重复发生；实际接收、提交、发送和显示分别表达；处理结果能够通过正式接口进入相应世界并保持来源关联。文档保存和编译均不证明上述运行条件已达成。

## 3. 职责与依赖方向

```text
实际外设与宿主 → 实际材料 → 外设世界类 → 外设交互场景
                                              ↓ 本能直接读取
                                      自然语言材料与解释
                                              ↓ 明确对象和来源关联
                                         现实世界认识
```

图中是常见文字输入路径。非语言材料不必经过自然语言世界；输出则由表达形成待发材料，经获准外设操作实际发送，再由外设类更新可确认事实。

外设世界类是更新编排者，通过场景、存在、特征、状态、动态等正式能力完成发布，不直接操作基础存储，不成为第二事实所有者。不负责需求、任务、方法调度、语言真假裁决，也不自动复制全部外设数据到现实世界。

拟选代码位置为 `海中鱼巣/业务/新_外设世界树类.h/.cpp`，组合复用通用世界树及领域公开能力。名称、完整签名、根场景初始化方式和工程登记在首个代码设计包中冻结；此处不把候选位置冒充已存在代码。

## 4. 外设场景信息模型

| 信息组 | 需要维护的信息 | 来源及边界 |
| --- | --- | --- |
| 成员与关系 | 窗口、输入区、输出区、端点、收发载体及明确组成、关联 | 实际外设定位；不凭同名认定同一对象 |
| 访问入口 | 公布网址、可观察的协议、地址、端口 | 配置或实际连接信息；不是交互者身份 |
| 会话 | 标识、两端关联、已知对端关联、实际开始和结束依据 | 通信事实；会话不等同一个人 |
| 输入输出 | 当前内容、可编辑性、可提交性、实际可见范围 | 实际读取或客户端报告；未知不补空值 |
| 接收队列 | 当前有序材料、来源、会话、容量及消费变化 | 真实接收与消费；线程邮箱不在此列 |
| 发送队列 | 待发材料、目标、会话、顺序及队列变化 | 入队、发送、取消事实 |
| 收发材料 | 消息身份、原文、方向、两端、顺序、同次过程关联及实际反馈 | 不用时间接近拼接过程；相同文字可有多次发生 |
| 身份接入材料 | 对方提供的标识、登录名、实际认证结果及依据（如采用） | 保留材料，不先裁决现实身份；秘密不公开复制 |
| 配置 | 各类已生效超时时长、适用对象及配置变化 | 区分请求等待、通信空闲、输入空闲；不猜默认值 |
| 状态动态 | 实际特征初始状态、变化状态、动作及变化动态、明确关联 | 复用领域机制；没有变化不重复制造状态 |

队列是否独立为存在，由其实际操作和生命周期决定，不为每个实现容器机械建存在。具有独立业务作用的消息材料与队列成员资格分开，材料承载位置、身份和保留合同须在首包明确。

各更新入口必须包含或唯一定位外设交互场景，并核验相关对象属于该范围。下列为功能职责，不是冻结的C++签名。

| 功能 | 输入 | 发布内容 |
| --- | --- | --- |
| 建立或复用交互场景 | 场景组织依据及来源 | 场景与必要关联 |
| 登记外设对象 | 场景、实际对象定位、初始特征和关系 | 对象、关系、初始状态 |
| 更新入口与配置 | 对象、实际生效值 | 对应特征及真实变化 |
| 更新会话关联 | 会话和两端的实际材料 | 当前关联与明确失效事实 |
| 更新输入输出 | 对象、实际内容和覆盖范围 | 当前特征、状态及动态 |
| 更新接收材料 | 原文、来源、会话、顺序、过程关联 | 材料及接收载体变化 |
| 更新发送进展 | 指定提交或消息及实际反馈 | 分阶段可确认事实 |
| 更新消费结果 | 实际消费材料及明确依据 | 队列成员变化及合法引用维护 |
| 更新关闭或断开 | 实际反馈或已冻结配置的成立依据 | 可确认失效信息；不默认删除场景 |

采集可由宿主适配器实施，再交更新入口发布；不把网络等待或真实发送隐藏在纯场景更新中。输入设置、提交和发送仍由其获准操作入口执行。

| 方法 | 直接读取的外设信息 | 后续边界 |

## 7. 状态、动态与更新过程

初始特征和真正改变的当前值由正式机制形成状态；同一主题和特征的合法前后状态形成变化动态。同值重复采集不重复形成状态，但不同消息发生必须通过独立材料及队列变化加以保留。

真实本能观察或改变先按正式合同登记动作。后台被动接收不伪造自我执行；没有动作来源的变化仍可如实成立。观察取得与导致变化分账，不能把自我观察写成外部变化的原因。

一次更新：核验实际来源和范围 → 确定对象对应 → 校验完整结构及当前前提 → 组合发布必须共同成立的信息 → 形成和挂接相应状态动态 → 返回实际发布位置 → 必要时发送定位通知。

跨多字段必须共同成立的结构使用组合发布，不能用多个独立成功码冒充原子完成。已有世界树入口可能阶段性发布；后续首包必须查明是否满足所需完整性，不预先宣称所有更新天然原子。

工程故障与业务结果分离。动作后故障保留可确认事实，不吞错、不伪装空队列、不为补记录重发外部动作。通知只唤醒，本能重新读取正式信息。

## 8. 三世界关联与信息处理

以“我是周春海”为例：外设世界保存实际原文、通信来源及关联；本能读取后，自然语言世界承载句子、当次指代与身份主张；现实世界承载交互者及依据该信息形成的认识。后续判断、证伪和修正有各自方法，不阻止原始信息取得，也不把尚未判断等同于假。

三世界通过明确来源材料、解释引用和对象指向关联。不是三份无条件镜像，不要求自然语言实例与现实存在相同，也不按名称或时间对齐。

外设世界树与现实世界树中的普通存在、状态和动态分别维护。不得让同一普通存在双挂两个直接归属场景，也不得改写源状态的被描述存在来复用。共享合法概念或只读材料与共享世界实例身份分开裁决。

现有动作结果接口有同场景、同目标及观察时间要求；外设观察动作、源动态与现实认识变化不能直接塞进一条既有“导致变化”关系。跨世界来源关联的正式类型、字段和发布顺序在消费者实施前冻结，不新增没有独立用途的工程见证节点。

## 10. 分阶段实施

1. 冻结首批场景、存在、特征概念与来源材料合同，明确匿名接入组织及真实可观察范围。
2. 建立外设根和具名交互场景，接入对象、实际内容更新及状态动态，先交付一个会话的完整数据更新结果。
3. 补真实收发、过程关联、队列消费及必要客户端反馈，支撑连接方法所需证据。
4. 先冻结跨世界来源、对象对应、发布顺序和失败边界合同，再接通本能直接读取、自然语言处理及现实场景认识发布。
5. 沿获取服务需求方案接服务对象及需求消费。登录、多会话、复杂超时按实际缺口逐步进入，不先批量登记远期计划。

每阶段先复核已有能力，再冻结允许文件、精确接口、依赖、所有权、发布和失败合同。整份路线不直接登记为可执行；最早代码缺口闭合后按仓库规则形成计划。
