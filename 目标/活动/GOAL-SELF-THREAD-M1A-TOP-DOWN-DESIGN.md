## 1.1 目标问题与优先级

现有方案已经明确自我线程的上层治理流程，但若先从底层能力清单建设，会再次失去真实消费者边界。用户确认采用自顶向下方法：先设计并实现自我线程上层代码，在具体调用点遇到缺失能力时，再按该调用的输入、输出、时机、事实来源和完成结果建立最小下层提供者。

本目标不先完成全部G0底层合同库存，而是只闭合足够启动M1-A上层施工的线程生命周期、窄依赖端口、控制分支、失败边界和验证合同。已知的本能根运行锚点仍是候选提供者缺口，但只有在上层实际调用合同固定后才恢复其设计目标，避免脱离消费者再次独立扩张。

## 2. 目标结果、完成条件与证据下限

目标结果是一份能够先施工上层自我线程的设计就绪计划，范围覆盖合法启动壳、唯一线程生命周期、停门/开门、停止/唤醒/`join`、最小强类型消息循环和M1-A治理主流程骨架，并为下层缺口规定统一回退方式。

完成条件：

1. 冻结`线程_自我.h/.cpp`中上层控制流、线程生命周期、运行门、邮箱消费、停止优先级、每轮治理阶段及返回状态；不把业务事实保存在第二套线程账中。
2. 按调用点冻结自我线程可见的窄上层依赖端口和值式DTO；禁止直接或借getter下钻DATA-L1/DATA-L2，禁止暴露仓库、事务写端口或可变节点。
3. 对每个首包调用点裁决：现有公开服务可直接复用、需要上层适配，还是缺少真实提供者；不为尚未到达的远期G5—G8一次性设计全部下层能力。
4. 缺提供者时只允许两种合法分流：能够零业务事实运行的分支明确返回`待实现/依赖未就绪`；必须成功才能开放治理的分支保持运行门关闭并形成最小提供者子目标。任何占位都不得返回伪成功、默认业务值或执行事实写入。
5. 冻结生产装配、工程登记、依赖生命周期、失败候选回收、线程压力和停止验证、静态越层检查、构建及真实入口最小验证；明确当前阶段不能宣称的范围。
6. 完成设计复核、`git diff --check`、路径/内部链接/计划blob读回，并只登记一份最早可执行计划；更远下层目标只有在施工遇到真实调用缺口时建立。

最低证据为现行规范和当前代码支撑的完整首包设计、正式代码计划及计划索引登记。目标记录和方案文件不证明代码、编译、线程运行、恢复或M1-A能力完成。

## 3. 自顶向下施工合同

固定推进循环：

```text
实现上层自我线程当前步骤
→ 调用现有具名上层公开服务
→ 能力存在：继续上层流程
→ 能力缺失：固定该调用点的最小需求
→ 建立并完成所属下层提供者目标
→ 独立读回提供者结果
→ 回到原上层调用点继续
```

约束：

- “先写上层”不等于先编造底层机器语义；公开ABI、owner、事务和失败合同缺失时，受影响调用点停止并形成设计/提供者目标。
- 可链接占位仅在工程确有需要时存在，必须标注`待实现`并返回结构化未实现，零机器事实写入；需要真实成功的治理门不能由占位解除。
- 下层实现只覆盖已经由上层调用证明必要的最小能力；不顺带建设同类通用功能。
- 提供者完成后必须回到原消费者接线、删除或退出占位分支并做独立读回，不能把“下层已完成”当作上层闭环完成。
