## 1. 首先确定本能方法的目标

方法名称：获取服务需求。

| 项目 | 定义 |
| --- | --- |
| 要改变的存在 | 自我 |
| 要改变的特征 | 自我的“服务任务”特征 |
| 变化前后材料 | 同一特征节点的当前值及相关历史状态；值为正式任务稳定编码的集合 |
| 要达到的变化 | 因本次动作，集合新增一个服务任务 |
| 数量表达 | 集合成员数量及其变化量由二次特征表达，不维护另一份可独立改写的任务数量 |
| 为什么需要 | 自我通过取得可以服务的需求，建立服务任务，才能开展实际服务 |

“获取服务需求”不是单纯返回信息包的工具函数。它有自己的目标和执行条件，并通过明确的操作及后续治理促成上述目标。

目标自我是现实世界中的自我存在，不是任务虚拟存在。方法以自我服务任务特征的变化为目标，不能仅因经过线程与消息就把整个方法归为只修改虚拟存在的内部治理方法。中间若修改任务或方法虚拟存在的运行状态，属于内部治理，须在各自治理场景处理，不能与自我现实特征的变化混写。

需求节点与任务节点仍由各自领域能力维护。“服务任务”特征是正式任务关联的被动集合投影，不替代任务节点，不成为另一条独立建任务入口。

## 2. 然后确定执行条件

### 2.1 条件一：自我有服务对象

自我的“交互对象”是特征节点，当前值为已经与自我建立连接的存在引用集合，并保留特征历史值。成员可以是人类、外设或其它存在。服务对象从其中满足人类概念的成员筛选，本次绑定一个明确对象，不另设可独立改写的第二套服务对象事实。

当前代码仍保留单个存在引用的旧“服务对象”特征及初始化值；新交互对象集合提供者已接入生产空集合初始化，但不自动把旧对象纳入新集合，连接与本能消费仍有迁移差距。历史连接或历史集合值不能代替当前事实；加入引用集合不改变对象在世界树中的场景归属。

不满足时，由通用筹办提出“需要服务对象”的静态子需求，经自我确认后建立子任务。子任务选择“获取服务对象”：复用合适人类交互对象，或在交互场景中定位存在、核对人类概念全部特征、建立连接，再将其纳入自我交互对象集合。完成状态是集合中具有符合人类概念的存在，不是方法仅返回一个对象编码。

“需要服务对象”是需求；“获取服务对象”是实现这个状态的方法，不因换一种动作说法再生成一条同义需求。

### 2.1.1 交互场景与逐项筹办

网页窗口是交互场景中的存在，不是场景本身。客户端窗口、输入区、输出区、服务端端点等在外设世界的交互场景中分别描述，不预设它们都是自我的子存在；组成、场景归属、连接和控制关系分别保存。

外设世界与现实世界分别组织对应交互场景，自然语言场景按材料与解释需要建立并明确关联。用户明确限定：通过对话框生成的交互场景只有一个交互对象；不外推为所有类型场景只能有一个对象。该范围内不再以按人分组或身份认证作为接收入口前置。对象身份尚未明确时，仍记录实际取得的外设信息，不据此虚构现实人类；多窗口归并不作为首包前置。

页面、渠道、会话与现实交互者不能互相替代。先保存实际取得的原文与来源，再由本能读取、理解和后续逻辑形成或修正认识；不能因尚未判断身份或真假而拒绝原始信息进入处理链，也不能由外设类将“我是周春海”直接写成已认证身份。

自我的认知判断依据已有信息：已有判断依据且材料充分时直接判断；已有依据但缺少必要材料时才要求交互者补充；没有判断依据时接受交互者提供的信息作为当前认识，后续可以随新依据修正。这个采信过程属于自我处理，不是外设更新职责，也不把陈述采信升级为已经通过身份认证或获得执行权限。

获取服务对象所需场景、存在、人类归属及连接事实应指向同一对象和适用场景。已具备的直接复用，缺少且可行动补齐的条件才交自我确认子需求。连接前称待连接存在，不能把“已有交互对象”和“仍未连接”重复拆成两个独立缺项；非人类对象不派生“变成人类”的需求。

### 2.1.2 建立连接

建立连接是最小本能方法，目标是自我与指定对端的连接状态成立，而非修改任务虚拟存在。必要材料是交互场景、可定位的对端或会话、可用收发渠道。

通过“发→收→发”或“收→发→收”过程确认；消息无需实际意义或语言理解，只核对同一场景、同一对端或会话、同次过程的真实收发及顺序。不能把无关消息拼成连接，也不能将最后一次发送冒充对端已接收。

连接成立表示自我根据本侧真实收发确认连接可用，不要求证明对方也已完成确认。它不证明人类身份、需求、求助或权限。会话未能唯一映射现实存在时，连接事实与存在识别分别处理，不虚构人类身份。断连治理仍见第10节。

建立连接消费外设场景中同次真实收发材料，连接判断属于材料之上的方法逻辑。实际收到消息、实际发送完成、关闭或失败等已知信息先如实更新；是否据此判定连接失效、重新确认或移除交互对象，另按冻结的连接合同处理。连接生命周期尚未明确，不构成原始材料采集、场景更新和读取支撑的全局停工条件；但依赖该策略的连接消费者不能提前执行未确定的语义。

建立连接作为工作线程中的方法刷新读取外设窗口的状态、动态，以本次过程起点之后的真实收发数量变化及顺序判断“收→发→收”或“发→收→发”。它不需要理解正文，也不要求每次计数变化必须关联正文状态后才能判断。具体调度沿用任务工作线程的运行与挂起机制，不额外建立全量消息消费任务。

### 2.1.3 三世界信息来源与本能支撑

| 承载位置 | 本方案所需信息 | 消费边界 |
| --- | --- | --- |
| 外设世界 | 窗口、端点、会话、输入输出、收发载体、原文、同次过程及实际反馈 | 外设世界类只编排更新；本能通过正式数据接口直接读取指定场景，不另建专用供数通道 |
| 自然语言世界 | 原文对应的语言材料、句式、当次指代、候选含义和表达主张 | 供理解、消歧和需求重述，不把主张自动等同现实事实 |
| 现实世界 | 自我认识的交互者、人类归属、连接认识、服务对象及其需求 | 按来源形成、采用和修正认识，供服务对象与需求本能消费 |

三世界是本交互链的分工，不取消已有内部治理世界或模拟世界，也不新建“自我世界”。任务和方法虚拟存在仍归内部治理。

常见输入链为“实际外设→外设场景更新→本能直接读取→自然语言解释→现实认识”；非语言信息不必经过自然语言世界。输出链为“从正式含义生成表达→准备待发材料→执行实际外设操作→更新可确认的收发事实”。更新场景不等于执行发送，也不隐藏网络等待。

来源材料、语言解释和现实对象通过明确引用关联，不靠同名、时间接近或参数相邻匹配；不要求三份完整镜像，不让同一普通存在跨世界双挂直接归属场景。各世界分别形成状态和动态；跨世界来源不冒充同场景的动作因果，正式关联合同在消费者实施前冻结。

### 2.1.4 外设特征更新与按需读取

外设负责存储实际取得的数据并更新数据，自我负责根据需要读取；不是每一条外设数据都必须由自我处理。自我线程自动刷新获取所需信息，不等于必须逐条确认、清空队列或消费全部历史。

对话框的接收信息数量、接收信息内容可以分别作为特征。每次真实接收使数量增加，内容更新为本次实际正文；当前值及历史按特征机制维护，状态和动态由正式变化链形成。相同正文再次收到仍使数量增加，不虚构正文变化；重复读取不冒充再次接收。发送侧只按实际可确认的发送事实更新，不将排队或HTTP空轮询等同具体消息发送完成。

消费者分别选择所需数据：建立连接读取收发数量的状态、动态及顺序；语言理解按本次需要读取正文；需求确认另须关联具体被确认内容。不能将后继语言消费者的来源关联要求倒置为外设更新或连接判断的前置，不新增“每条消息都必须处理”的机制。

当前代码核对发现：特征历史保存不同值及命中次数，不是完整发生顺序日志；接收计数与正文目前在不同入口更新；宿主未向上传递实际发送结果。这些是首包设计应解决或明确消费边界的工程差距，不是追加独立消息存在、扩展动态关联状态字段或要求全量处理的授权。

### 2.2 条件二：该服务对象有完整需求信息

判断依据是：**该服务对象的“需求”特征当前引用集合中，新增了一个完整且经确认的服务需求节点。** 父任务重新读取正式集合及该节点，不能只凭子任务完成通知、临时返回包或集合总数判断。新增须与本次取得需求信息的动作及来源对应，不能冒认其它交互的新增。

服务对象没有需求树，只有一个“需求”特征节点，其当前值保存该对象所有服务需求节点的引用集合，并按特征规则维护历史值。需求节点的主体归属该服务对象；需求主体不同于需求所指的目标存在。这里只保存同一节点的引用，不复制节点内容，也不把对方节点挂入自我需求树。

加入正式集合之前，必须由前置过程保证：

- 需求主体确为该服务对象，不与目标存在混同。
- 对象、特征类型、目标值或概念约束、比较关系等对应目标形式的必需信息完整。
- 自我已经消除本次理解的歧义，不存在尚待选择的多个含义。
- 服务对象已经确认自我重述的具体内容；当前需求含义与确认内容一致。
- 信息可通过正式节点引用读取，不能只存在于临时消息字符串中。

集合组织已经确定，不再把“单条还是集合”“是否建立服务对象需求树”列为未决问题。字段编码、公开读写接口、节点与集合关联的发布一致性、历史维护及旧记录迁移仍须冻结；这不证明现有代码已经具备相应能力。

条件不足时，通用筹办提出所缺状态，经自我确认形成子需求，其任务选择“获取服务对象需求信息”本能方法。父方法不重复承担原始文字理解和字段补齐。对子需求的完整目标表达必须使用正式数据结构，不能把“理解一下”等过程命令当成已定义目标。

### 2.2.1 子方法：获取服务对象需求信息

| 项目 | 合同 |
| --- | --- |
| 修改对象及类别 | 现实世界中的服务对象；不是任务或方法虚拟存在，属于普通方法 |
| 修改特征 | 服务对象的“需求”特征 |
| 目的 | 将交互中理解并确认的需求落实为该对象的正式需求信息，为父方法提供条件 |
| 直接操作 | 经需求能力建立或复用归属该对象的需求节点，经特征能力将节点引用加入其需求特征集合 |
| 目标结果 | 集合新增一个完整、经确认的服务需求节点；不是仅返回节点编码 |
| 必要条件 | 服务对象明确；对应目标形式的必需字段具有确定的具体值；服务对象已确认这些值所表达的同一份需求 |
| 数据来源 | 自我与该服务对象交互所得自然语言，经理解、对象绑定、消歧、补问和内容确认取得 |

必需内容包括需求主体、目标存在、目标特征类型，以及目标形式所要求的目标值/概念约束和比较关系，或目标变化方向；沿用需求合同的二选一规则，不要求互斥分支字段同时有值。确认依据与具体内容关联，不能用另一份需求的确认填补。最终物理字段映射随需求owner合同冻结，不另造平行需求结构。

字段不足时先筹办：已知字段直接复用；缺项、歧义或未确认内容由子任务通过交互处理。父方法“获取服务对象需求信息”此时尚未真正执行，补问、发送和读取分别保留实际动作来源，不伪装为父方法已经完成。

字段具备后，执行顺序为：

1. 从参数场景引用重新读取该对象、字段具体值及对应确认依据；内容变化或身份未确定时，不进入实际动作。
2. 按本能执行规则记录动作，再调用所属能力建立或复用需求节点，落实其主体归属及需求特征集合关联。
3. 返回已落实节点及动作、结果引用供任务重读；状态、动态和因果由系统根据真实事实变化形成，不由函数编造。
4. 子任务完成触发父任务重新读取服务对象需求特征；该正式结果对应父方法第2.2节条件。

未完整或未确认的候选内容可以在待确认阶段承载，但不能提前加入上述正式集合。候选承载与发布生命周期仍待设计；不得为生成确认问句先伪造一条已确认需求。

同一需求节点已在集合中时复用，不重复加入，不将复用声明为本次新增。新增目标尚未达成与材料可被复用分别表达；重复输入的具体后继筹办策略须在实施合同中明确，不为了满足新增目标制造副本。

### 2.2.2 对方需求与自我需求分离

对方需求节点加入其需求特征集合，不等于自我承接，也不直接为对方需求建立执行任务。后续“获取服务需求”读取该节点并转换，自我决定承接后，另建或复用属于自我的服务需求，挂入自我需求树并关联对方原需求；原节点仍归属服务对象，不迁移、不改主体。

### 2.3 条件属于方法，筹办属于任务

方法条件节点保存完整条件及关联关系。参数规格按现行有序参数规则表达所需信息类型与概念范围，具体条件由条件节点表达；实际执行参数场景保存找到的正式信息引用。

任务读取方法条件并与场景实际信息比较，缺少必要条件则提议子需求。子任务完成只触发父任务重新检查；父任务重新读取当前特征值和需求信息，条件真实满足后才执行。

### 2.4 必须保留的条件充分性问题

上述两项是用户确定的两组上层条件，但不能据此宣称任何输入都必然产生新任务：

1. 内容确认不等于请求自我帮助。已有“未求助不主动满足”的边界仍有效。
2. 同一需求可能已有自我需求和任务。重复处理不能为了达到新增目标而制造副本。
3. 自我仍负责是否承接及其限制，方法不能替自我预先保证通过。

后续具体设计须明确这些限制是在所选条件分支中提前核验，还是作为后续自我处理的正常结果保留。本文不擅自新增第三组条件，不把业务拒绝当工程故障，也不把两组必要条件写成“100%新增”的充分条件。

## 3. 条件满足后，方法中间做什么

### 3.1 执行前复核

通过参数场景重新读取服务对象及其需求、确认依据。筹办后发生对象切换、内容变化或引用失效时，不沿旧材料开始实际动作，也不记录虚假执行。

### 3.2 记录本次动作

满足执行条件后，按通用方法执行规则记录本次动作，保存方法、执行身份、作用场景及目标特征的关联。记录动作不表示任务已经新增。

### 3.3 转换需求并落实到场景

读取服务对象的已确认需求，形成待自我确认的服务需求转换材料：

- 服务对象及其原需求引用；
- 本次采用的明确目标含义；
- 自我服务目的与原需求的关联；
- 本次执行、动作及来源引用。

转换不改写对方原需求，也不是简单把需求主体从对方换成自我。必须保留“服务哪个对象、满足哪份原需求”的含义。

由所属信息能力将转换结果落实为场景中的可读取节点。此材料尚不是自我线程已确认建立的正式自我需求，不借用任务虚拟存在复制服务对象事实。材料节点的正式信息类型、场景归属、发布与保留边界须在后续施工合同中冻结。

### 3.4 返回正式材料引用

方法向任务执行侧交付已落实材料的定位，不将临时信息包作为唯一事实来源。此时可以确认“转换材料已经落实”，不能直接确认“服务任务已经新增”。

## 4. 再明确中间过程如何实现

| 承担方 | 职责 | 不得代替的职责 |
| --- | --- | --- |
| 实际宿主及外设适配 | 取得实际收发、对象定位和可观察内容；执行获准的外设操作 | 不把入队当发送，不推定页面显示或人已阅读 |

| 方法类与本能函数 | 维护方法头、固定参数规格、条件和目标描述；条件具备后执行转换与落场景 | 不直接代替自我确认或任务建立 |
| 任务类 | 通用条件筹办、执行与结果读取；将本次执行及材料定位保留下来 | 不凭通知认定条件或目标已满足 |
| 任务管理线程 | 将正式材料引用通过消息交给自我；消费确认后的自我需求并建立任务 | 不自行确认服务对象原意或产生自我需求 |
| 自我线程 | 重新读取材料，按求助、承接、重复及限制判断，调用需求能力建立或复用自我需求 | 不将内容确认自动当作求助或已完成服务 |
| 需求类 | 唯一维护对方需求、自我需求、来源与服务目的关系 | 不让语言解析器直接写需求内部字段 |
| 任务及特征相关能力 | 正式建任务，按关联变化被动同步服务任务集合 | 不靠函数直接把计数加一冒充建任务 |
| 状态、动态、因果能力 | 根据实际发布的事实及明确来源形成和关联信息 | 不凭时间先后推断本次动作造成任务增加 |

按当前用户口径，消息路径应为“方法落实材料→任务管理线程→自我线程”，不是本能运行服务直接等待自我建任务。迁移必须同步处理原执行等待、结果读回和停止收束，不能只换一个调用点。

方法头仍用正式方法信息表示；首次调用缺自身登记时建立，已有则复用核验。固定参数规格不能为新增句式随意改写。方法用途声明不等于长期条件结果知识，不能在没有实际或模拟依据时预造配对。

## 5. 如何判定本次目标达成

自我确认后建立自我需求，任务管理建立对应服务任务，集合被动同步，最后由任务类读取正式结果。

必须同时确认：

1. 有一个新服务任务进入自我的服务任务特征当前集合。
2. 它通过转换材料、自我需求及任务建立来源，可以明确追溯到本次动作。

不能只检查集合总数前后差：其它任务同期增减可能掩盖本次结果。来源路径与集合成员事实共同证明新增，不建立第二套独立服务数量账。

已有需求或任务的复用不算新增；信息保存、消息接收、自我确认、任务建立和目标达成分别表达。工程故障进入日志、弹窗及调试处理链，不伪装成需求不满足；动作后出错保留已发生事实，不补造结果。

对方实际需求的最终满足发生在后续服务任务中，不是本次“获取服务需求”任务的完成条件。本次只负责取得可开展服务的任务。

## 6. 为第二项条件准备自然语言能力

本节是前置条件实现路线，不是父方法执行体的一部分。

### 6.1 内部含义固定，表达结构开放

内部需求含义区分需求主体、目标存在、目标特征与目标约束。同一含义可有多个句式，同一句式可有在该语境下等义的词。希望、想、需要等由语言知识解释，不作为代码中的固定触发词清单。

匹配可产生多个候选；只有结合场景、对象绑定及询问消歧后，才能确定本次唯一理解。唯一理解不等于对方已经认可，也不表示不同主体或不同次请求要合并为同一节点。

### 6.2 正向理解与反向确认

复用最简句式已有的对象、特征、数值及概念解析；新增需求描述含义，使内层目标处于期望范围，而不是当前事实陈述。

顺序为：外设场景实际接收原文及来源→本能读取→自然语言世界中的候选含义→消歧及现实对象绑定→待确认需求节点→重新读取节点内容→自然语言重述→实际发送→取得并理解服务对象对该内容的确认。发送完成不等于对方确认，收到“确认”文字也必须关联到被重述的具体需求。

重述必须从需求节点生成，不能直接回显原文。确认关联被重述的具体内容；内容修改后重新确认。现有被认知需求建立接口要求已有确认，需要补齐待确认阶段，不能形成“先确认才能有节点、先有节点才能重述确认”的循环。

正式语言知识可逐步增加等义句式及适用条件。当前方案不要求同时实现学习算法；新增表达不能靠修改需求转换函数硬编码，也不能改变需求含义。

### 6.3 目前可复用与尚缺能力

- 已有：自我“服务对象”特征及初始化当前值；需求主体/执行域和已确认被认知需求存取；服务任务集合及部分来源读回；六类最简句式双向转换。
- 已发布提供者：`0b7fc3814f4ce30c83452142b718296423a2e269`实现被认知需求加入主体需求特征集合、去重、确认保护、动作/状态/动态及来源读回，普通应用已持有并初始化服务；当前没有本能业务调用。实际项目编译链接通过，未运行测试，不能据此宣称对方需求已自动进入集合。
- 尚缺或未接通：需求描述语义、待确认需求生命周期、从需求节点重述及确认关联、服务对象需求特征的完整接入、本次转换材料场景发布和新消息路径。
- 当前S09仅支持归类确认，不能直接等同需求确认问句。
- 当前六句式在语言场景建立对象及主张，不证明它们已绑定现实对象，也不代表需求已成立。

## 7. 分步实施路线

1. **先闭合外设信息首包**：按外设方案冻结首批场景、对象、特征和来源材料合同，明确接入期组织及真实可观察范围。复用已有世界能力形成一个会话的实际信息更新结果，不以人类认证、复杂超时或多窗口策略作为全部首包前提。
2. **接通实际收发及按需读取**：外设更新正式窗口特征，自我和本能沿既有参数场景按需读取当前值、历史、状态或动态；补齐实际收发反馈和消费者需要的过程定位，不要求逐条处理或全量队列消费。读取和移出队列、入队和发送、发送和显示分别处理。
3. **接通三世界关联与服务对象取得**：先冻结来源、对象对应、发布和失败边界，再接语言解释与现实认识；连接方法核对真实三步收发，获取服务对象方法核对其条件并改变自我交互对象集合。连接失效和多端策略只阻断依赖它们的范围，不倒置为原始信息入口条件。
4. **实现获取服务对象需求信息**：补待确认承载、需求语言知识、正反向转换、交互补项及确认；字段具备后由该本能方法落实对方需求节点及其需求特征集合，父任务重新读取。前置补项不冒充父方法执行。
5. **实现获取服务需求及治理消费**：在实施前闭合第2.4节条件充分性和转换材料合同；父方法复核、记录动作并落材料，manager交接、自我确认建需求、manager建任务、集合被动同步及来源核验，同步收束旧直连等待链。
6. **验证完整目标**：相关代码整组修改后统一实际项目编译；仅在明确测试指令下运行相应真实入口验证。最终仍须证明本次动作促成一个正式服务任务新增，不能以外设支撑、读取或编译通过代替。

一次只推进当前直接依赖，不将复杂语言、自动学习、结算重写或全仓迁移混入本轮主线。本文不登记远端后继计划，也不授权尚未冻结接口的代码施工。

## 8. 最终效果与验收关注项

最终应能观察到：父任务缺条件时先筹办；服务对象与已确认需求具备后，获取服务需求本能函数执行；转换材料由自我重新读取确认；合法新服务需求形成唯一任务；集合变化根据来源关联回本次动作。

验收重点：条件属于同一对象；历史值不冒充当前值；多义先消歧；重述不改变目标；确认后变更须重确认；重复处理不重复建任务；其它动作新增不冒认本次成果；未求助不主动满足；停止或故障不制造结果。

子方法另须关注：服务对象无需求树；需求特征保存全部正式服务需求节点引用；未完整/未确认材料不进入集合；目标形式所需字段分别核验；字段不足时父方法零实际动作；重复节点复用不报新增；对方需求新增不自动生成自我执行任务；父任务只重读正式结果，不重新解析原文代替节点内容。

外设与三世界链须另验证：身份未明确仍能接纳实际材料；相同文字的不同接收不被误去重；重复读取不冒充新接收；消息移出队列不破坏已持有的来源；未知显示不补造成功；不同世界的场景、对象及动作不混用；源材料、理解、确认、对方需求、自我需求和新任务具有可追溯关联。源动态与认识变化不是同一个动态。未发生变化的轮询不反复制造状态。
