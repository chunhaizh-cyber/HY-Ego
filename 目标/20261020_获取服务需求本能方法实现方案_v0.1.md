# 获取服务需求本能方法实现方案

日期：2026-10-20  
版本：v0.1  
事实基线：main `749855f7eeebc4baead0397f90f9477726862e85`。

性质：用户要求保存的实现方案与后续设计输入。按“目标→条件→操作→实现”组织，不是可直接施工的冻结接口合同，不宣称能力已经接通。本文只新增方案，不修改规范、代码、计划索引或目标账状态，不启动产品目标模式。

## 1. 首先确定本能方法的目标

方法名称：获取服务需求。

| 项目 | 定义 |
| --- | --- |
| 要改变的存在 | 自我 |
| 要改变的特征 | 自我的“服务任务”特征 |
| 变化前后材料 | 同一特征节点的当前值及相关历史状态；值为正式任务稳定编码的集合 |
| 要达到的变化 | 因本次动作，集合新增一个服务任务 |
| 数量表达 | 集合成员数量及其变化量由二次特征表达，不维护另一份可独立改写的任务数量 |
| 为什么需要 | 自我通过取得可以服务的需求，建立服务任务，才能开展实际服务 |

“获取服务需求”不是单纯返回信息包的工具函数。它有自己的目标和执行条件，并通过明确的操作及后续治理促成上述目标。

目标自我是现实世界中的自我存在，不是任务虚拟存在。方法以自我服务任务特征的变化为目标，不能仅因经过线程与消息就把整个方法归为只修改虚拟存在的内部治理方法。中间若修改任务或方法虚拟存在的运行状态，属于内部治理，须在各自治理场景处理，不能与自我现实特征的变化混写。

需求节点与任务节点仍由各自领域能力维护。“服务任务”特征是正式任务关联的被动集合投影，不替代任务节点，不成为另一条独立建任务入口。

## 2. 然后确定执行条件

### 2.1 条件一：自我有服务对象

自我关联“服务对象”特征节点，该节点具有当前值及历史值。检查当前值是否引用有效的服务对象存在，不以“场景中有一个人”替代。

当前代码该特征的值类型为单个存在引用，范围由人类概念限定；不是集合。本文不附带将它扩为多对象集合。历史值只用于追溯，不能代替本次当前值。

不满足时，由任务筹办根据方法条件提出“需要服务对象”的静态子需求，经自我确认后建立子任务。子任务选择“获取服务对象”方法完成必要操作，使自我服务对象特征的当前状态满足条件。

“需要服务对象”是需求；“获取服务对象”是实现这个状态的方法，不因换一种动作说法再生成一条同义需求。

### 2.2 条件二：该服务对象有完整需求信息

从同一个服务对象的“需求”特征当前值定位需求信息，要求：

- 需求主体确为该服务对象，不与目标存在混同。
- 对象、特征类型、目标值或概念约束、比较关系等对应目标形式的必需信息完整。
- 自我已经消除本次理解的歧义，不存在尚待选择的多个含义。
- 服务对象已经确认自我重述的具体内容；当前需求含义与确认内容一致。
- 信息可通过正式节点引用读取，不能只存在于临时消息字符串中。

服务对象“需求”特征的物理值类型、单条或集合组织、当前/历史引用更新以及旧记录迁移，需要在对应提供者设计中核对冻结；不能把本方案中的目标表达当作当前代码已有能力。

条件不足时，筹办其所缺状态，由子任务获取描述、理解、补问和确认。对子需求的完整目标表达必须使用正式数据结构，不能把“理解一下”等过程命令当成已定义目标。

### 2.3 条件属于方法，筹办属于任务

方法条件节点保存完整条件及关联关系。参数规格按现行有序参数规则表达所需信息类型与概念范围，具体条件由条件节点表达；实际执行参数场景保存找到的正式信息引用。

任务读取方法条件并与场景实际信息比较，缺少必要条件则提议子需求。子任务完成只触发父任务重新检查；父任务重新读取当前特征值和需求信息，条件真实满足后才执行。

### 2.4 必须保留的条件充分性问题

上述两项是用户确定的两组上层条件，但不能据此宣称任何输入都必然产生新任务：

1. 内容确认不等于请求自我帮助。已有“未求助不主动满足”的边界仍有效。
2. 同一需求可能已有自我需求和任务。重复处理不能为了达到新增目标而制造副本。
3. 自我仍负责是否承接及其限制，方法不能替自我预先保证通过。

后续具体设计须明确这些限制是在所选条件分支中提前核验，还是作为后续自我处理的正常结果保留。本文不擅自新增第三组条件，不把业务拒绝当工程故障，也不把两组必要条件写成“100%新增”的充分条件。

## 3. 条件满足后，方法中间做什么

### 3.1 执行前复核

通过参数场景重新读取服务对象及其需求、确认依据。筹办后发生对象切换、内容变化或引用失效时，不沿旧材料开始实际动作，也不记录虚假执行。

### 3.2 记录本次动作

满足执行条件后，按通用方法执行规则记录本次动作，保存方法、执行身份、作用场景及目标特征的关联。记录动作不表示任务已经新增。

### 3.3 转换需求并落实到场景

读取服务对象的已确认需求，形成待自我确认的服务需求转换材料：

- 服务对象及其原需求引用；
- 本次采用的明确目标含义；
- 自我服务目的与原需求的关联；
- 本次执行、动作及来源引用。

转换不改写对方原需求，也不是简单把需求主体从对方换成自我。必须保留“服务哪个对象、满足哪份原需求”的含义。

由所属信息能力将转换结果落实为场景中的可读取节点。此材料尚不是自我线程已确认建立的正式自我需求，不借用任务虚拟存在复制服务对象事实。材料节点的正式信息类型、场景归属、发布与保留边界须在后续施工合同中冻结。

### 3.4 返回正式材料引用

方法向任务执行侧交付已落实材料的定位，不将临时信息包作为唯一事实来源。此时可以确认“转换材料已经落实”，不能直接确认“服务任务已经新增”。

## 4. 再明确中间过程如何实现

| 承担方 | 职责 | 不得代替的职责 |
| --- | --- | --- |
| 方法类与本能函数 | 维护方法头、固定参数规格、条件和目标描述；条件具备后执行转换与落场景 | 不直接代替自我确认或任务建立 |
| 任务类 | 通用条件筹办、执行与结果读取；将本次执行及材料定位保留下来 | 不凭通知认定条件或目标已满足 |
| 任务管理线程 | 将正式材料引用通过消息交给自我；消费确认后的自我需求并建立任务 | 不自行确认服务对象原意或产生自我需求 |
| 自我线程 | 重新读取材料，按求助、承接、重复及限制判断，调用需求能力建立或复用自我需求 | 不将内容确认自动当作求助或已完成服务 |
| 需求类 | 唯一维护对方需求、自我需求、来源与服务目的关系 | 不让语言解析器直接写需求内部字段 |
| 任务及特征相关能力 | 正式建任务，按关联变化被动同步服务任务集合 | 不靠函数直接把计数加一冒充建任务 |
| 状态、动态、因果能力 | 根据实际发布的事实及明确来源形成和关联信息 | 不凭时间先后推断本次动作造成任务增加 |

按当前用户口径，消息路径应为“方法落实材料→任务管理线程→自我线程”，不是本能运行服务直接等待自我建任务。迁移必须同步处理原执行等待、结果读回和停止收束，不能只换一个调用点。

方法头仍用正式方法信息表示；首次调用缺自身登记时建立，已有则复用核验。固定参数规格不能为新增句式随意改写。方法用途声明不等于长期条件结果知识，不能在没有实际或模拟依据时预造配对。

## 5. 如何判定本次目标达成

自我确认后建立自我需求，任务管理建立对应服务任务，集合被动同步，最后由任务类读取正式结果。

必须同时确认：

1. 有一个新服务任务进入自我的服务任务特征当前集合。
2. 它通过转换材料、自我需求及任务建立来源，可以明确追溯到本次动作。

不能只检查集合总数前后差：其它任务同期增减可能掩盖本次结果。来源路径与集合成员事实共同证明新增，不建立第二套独立服务数量账。

已有需求或任务的复用不算新增；信息保存、消息接收、自我确认、任务建立和目标达成分别表达。工程故障进入日志、弹窗及调试处理链，不伪装成需求不满足；动作后出错保留已发生事实，不补造结果。

对方实际需求的最终满足发生在后续服务任务中，不是本次“获取服务需求”任务的完成条件。本次只负责取得可开展服务的任务。

## 6. 为第二项条件准备自然语言能力

本节是前置条件实现路线，不是父方法执行体的一部分。

### 6.1 内部含义固定，表达结构开放

内部需求含义区分需求主体、目标存在、目标特征与目标约束。同一含义可有多个句式，同一句式可有在该语境下等义的词。希望、想、需要等由语言知识解释，不作为代码中的固定触发词清单。

匹配可产生多个候选；只有结合场景、对象绑定及询问消歧后，才能确定本次唯一理解。唯一理解不等于对方已经认可，也不表示不同主体或不同次请求要合并为同一节点。

### 6.2 正向理解与反向确认

复用最简句式已有的对象、特征、数值及概念解析；新增需求描述含义，使内层目标处于期望范围，而不是当前事实陈述。

顺序为：文字→候选含义→消歧及绑定→待确认需求节点→重新读取节点内容→自然语言重述→服务对象确认。

重述必须从需求节点生成，不能直接回显原文。确认关联被重述的具体内容；内容修改后重新确认。现有被认知需求建立接口要求已有确认，需要补齐待确认阶段，不能形成“先确认才能有节点、先有节点才能重述确认”的循环。

正式语言知识可逐步增加等义句式及适用条件。当前方案不要求同时实现学习算法；新增表达不能靠修改需求转换函数硬编码，也不能改变需求含义。

### 6.3 目前可复用与尚缺能力

- 已有：自我“服务对象”特征及初始化当前值；需求主体/执行域和已确认被认知需求存取；服务任务集合及部分来源读回；六类最简句式双向转换。
- 尚缺或未接通：需求描述语义、待确认需求生命周期、从需求节点重述及确认关联、服务对象需求特征的完整接入、本次转换材料场景发布和新消息路径。
- 当前S09仅支持归类确认，不能直接等同需求确认问句。
- 当前六句式在语言场景建立对象及主张，不证明它们已绑定现实对象，也不代表需求已成立。

## 7. 分步实施路线

1. **先闭合方法合同**：按第1—5节冻结目标、两组条件、关联角色、直接操作与后续结果边界；解决第2.4节条件充分性以及转换材料身份问题。
2. **复用并补齐条件读取**：核对服务对象当前值读取、获取服务对象子任务的正式更新，以及对象需求定位；只补直接缺口。
3. **完善需求理解与确认**：实现待确认节点、需求语言知识及正反向转换、交互确认，并接入服务对象需求特征。
4. **实现父方法执行**：复核条件、记录动作、转换、材料落场景、返回引用。
5. **接通治理消费**：manager交接、自我确认建需求、manager建任务、集合被动同步及来源核验，同步收束旧直连等待链。
6. **实际验证**：整组相关代码修改后统一编译；收到明确测试指令后，用实际项目和真实入口验证，不另建临时工程或虚构需求。

一次只推进当前直接依赖，不将复杂语言、自动学习、结算重写或全仓迁移混入本轮主线。本文不登记远端后继计划，也不授权尚未冻结接口的代码施工。

## 8. 最终效果与验收关注项

最终应能观察到：父任务缺条件时先筹办；服务对象与已确认需求具备后，获取服务需求本能函数执行；转换材料由自我重新读取确认；合法新服务需求形成唯一任务；集合变化根据来源关联回本次动作。

验收重点：条件属于同一对象；历史值不冒充当前值；多义先消歧；重述不改变目标；确认后变更须重确认；重复处理不重复建任务；其它动作新增不冒认本次成果；未求助不主动满足；停止或故障不制造结果。
