## 3. 服务合同与正式边界

- 具名服务：`需求初次筹办准备服务 / 形成唯一任务与初次筹办工作包`。
- 合法消费者：普通应用运行期的需求与任务治理编排。候选未实现该生产消费者。
- 公开服务入口：`需求初次筹办准备提供者::形成唯一任务与初次筹办工作包(...)`。
- 成功结果：`已形成`或`精确重复`，携带首次需求裁决、首次准备记录身份和轮次 1 工作包。
- 权威终态：task owner 在同一 G1 建立任务、任务虚拟存在、首次记录、关系和值。
- 独立读回：按准备幂等身份跨生命周期读取首次记录，并按记录身份与 G1 历史截止读取首次任务和身份来源。
- 禁止假成功：仅自检可达、构建成功、日志、退出码或 Release 携带自检入口都不构成正式服务事实。

## 5. 函数巡检与诊断责任

具名服务闭包冻结 5 个公开运行期函数：provider 入口、task owner 融合写、按准备键读取、按记录读取和任务退出历史闭合。候选自带的双配置 Rebuild 记录可证明这 5 个函数已编译接入；本轮没有重跑构建。

普通应用正式入口巡检为 `0/5`。自检调用不计正式入口巡检，因此没有用施工自检的动态进入数填充该数字。

按 CODE-FILE-01，provider 与 task owner 公开函数都是非最终责任边界，诊断责任为`向上送出`。源码使用具名结构化状态向上返回，provider 将资源与未预期异常映射为`资源失败/内部错误`。但候选缺少普通应用最终消费者，唯一结构化传播链没有到达正式最终责任边界；这也是不能形成正式接线结论的组成部分。
