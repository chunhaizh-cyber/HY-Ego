## 2. 编译与入口巡检分账

精确候选 Release fresh Rebuild 退出 `0`，provider 模块和治理测试模块均实际编译。可以记录 17 个生产函数的编译接入事实。

治理专项退出 `0`，证明公开 provider 和 task-owner 入口在专项材料上实际进入并返回。它没有逐函数入口探针，也没有为 17 个生产函数逐项证明进入 / 退出；更重要的是，计划、详细设计和施工记录均没有登记 CODE-FILE-01 要求的三类诊断责任。故本验收的机器清单保持：

```text
目标函数数 = 18（17 个生产函数 + 1 个排除的治理专项函数）
排除治理专项函数数 = 1
编译通过数 = 17
入口巡检通过数 = 0
观察到的逻辑异常数 = 0
```

`入口巡检通过数 = 0` 不等于函数没有运行；它表示现有证据不足以对逐函数闭包授予该结论。治理专项动态进入事实单独保留，不升级。

## 3. 诊断责任缺口

CODE-FILE-01 §4.4 要求每个新增或直接修改的项目函数在合同备注、详细设计或计划逐函数合同中登记以下之一：

```text
本地记录
向上送出
无适用错误分支
```

对计划、详细设计和施工记录全文扫描，三类登记均为 0。源码确有结构化非成功映射与异常捕获，这说明部分传播形状存在；但不能由验收者代替设计者逐函数补判责任，更不能以“没有日志”或治理专项退出 `0`证明唯一异常传播链已经闭合。

该缺口不抹除编译或治理专项事实，也没有证据证明已经发生运行期逻辑异常；它限制函数巡检结论强度，并构成后续正式接线候选应补齐的工程门禁。
