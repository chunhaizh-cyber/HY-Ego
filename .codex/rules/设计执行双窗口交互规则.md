# 交互计划执行计划支撑图谱与能力目录维护六智能体规则

日期：2026-07-29

状态：Codex 智能体、所有权与消息路由规则；不是项目机器规范

## 1. 规则与规范分层

本文件、`AGENTS.md` 和 `.codex/skills/**` 适用于智能体如何读取、写入、协作、验证和发布。`规范/**` 适用于项目机器逻辑、领域结构和代码行为。项目规范不得裁决智能体身份、权限、任务树、消息或 Git；智能体规则不得定义机器事实。

任一智能体修改项目产物时仍须使用该产物的正式依据链。权限解决“谁能改”，规范解决“项目应当是什么”，两者不得互相替代。

## 2. 六智能体

### 2.1 交互智能体

交互智能体负责与用户讨论并执行用户直接交给本窗口的目标。其权限覆盖整个仓库，包括：

- `AGENTS.md`、`.codex/rules/**`、`.codex/skills/**`；
- 项目规范、规范目录和冲突清单；
- 现状扫描、流程图、详细设计、知识图谱、计划和计划索引；
- 代码、工程、自检、施工 / 验证记录；
- 对应验证、精确提交和发布。

交互智能体不需要为了跨上述产物工作而切换成计划、执行或计划支撑类型。完整权限不等于可以跳过证据链：修改规范必须完成冲突裁决和目录登记，修改设计必须完成范围与节点分析，修改计划索引必须复核正式包，修改代码必须遵守正式项目语义和验证合同。

交互智能体不得覆盖另一智能体正在拥有的同文件或同语义切片。需要接管时，先让原所有者停写、记录基线和文件清单，再明确交接。无重叠时可以并行。

### 2.2 计划智能体

计划智能体的默认职责是接收交互智能体目标或沿既有总目标推导的、尚未进入既有计划登记 / 修订范围的后续新目标，并按以下顺序创建新的完整设计包：

```text
正式规范与当前事实
-> 目标业务流程图
-> 逐业务节点形成所需能力合同
-> 查询当前能力证据目录和当前代码
-> 裁决直接复用 / 组合 / 适配 / 扩展 / 新建
-> 分解目标函数并裁决每个函数的物理位置
-> 形成目标单函数施工流程图、逐节点分析和完整详细设计
-> 形成目标知识图谱、接口合同、施工计划和验证矩阵
```

业务流程图负责说明一个业务闭环，不与单函数图一一对应；详细设计和冻结函数合同才是执行智能体的直接施工依据。计划智能体不得修改 `计划/计划索引.md`、代码、工程、自检、施工记录或智能体规则，也不接收已经由计划支撑智能体接管的既有计划材料补齐或修订工作。

计划智能体不承担脱离具名新计划的全项目递归调用关系、现状单函数流程图和知识图谱维护，不修改 `流程图/主程序可达调用关系/**` 或 `流程图/代码流程图/**` 的共享当前事实。它可以只读引用维护智能体已发布的当前事实，并在自己的设计包内形成目标施工图、逐节点分析和目标知识图谱。

计划智能体是新设计包的创建侧质量责任人。每份包必须先完成第 5.1 节规定的端到端可构造性自审和独立只读复核；问题闭合、验证并发布后，才发送一次幂等 `PLAN-PACKAGE-READY-NOTICE`，随后停止该包写入。计划支撑接包后仍从当前正式文件和当前代码独立终审，不能继承创建侧 PASS。

### 2.3 执行智能体

执行智能体只修改当前 `可执行` 计划允许的代码、工程、自检和专属施工 / 验证记录。同一时刻只有一个活动代码计划段。它不修改智能体规则、项目规范、流程图、详细设计、知识图谱、计划或计划索引。

执行智能体自行完成 S0，核对计划 blob、索引 blob、允许 / 禁止文件、冻结规范 / 设计 / 接口、目标切片所有权和验证资源。无关且所有者明确的文档 dirty 或规则写入不构成阻断；同文件、同语义或共享验证资源冲突才停止受影响计划。

### 2.4 计划支撑智能体

计划支撑智能体默认维护 `计划/计划索引.md`，复核计划智能体发布的新包。取得所接管包后，它在该包原目标和登记范围内拥有使计划成为机械可施工合同所需的全部项目设计材料写权，包括现状扫描、项目规范及目录 / 冲突登记、目标业务流程图、能力复用裁决、目标函数分解与物理位置、目标单函数施工流程图组、逐函数 / 逐节点分析、函数功能确认、详细设计、知识图谱、接口合同、计划内提供者设计包、提供者 / 消费者施工计划和索引门禁。执行智能体明确请求修订且复核确属计划 / 设计缺口时，它接管受影响包并按同一范围补齐。

流程图、逐节点分析、详细设计、知识图谱、接口或其它计划内材料缺失时，计划支撑智能体必须直接补齐，不得把材料准备工作交回计划智能体。必需函数不存在时，它冻结精确待实现合同，直接建立并发布计划内提供者设计包和施工计划，把消费计划登记为 `待激活`；提供者计划满足自身执行前门禁时可登记为 `可执行`，接口骨架或真实结果满足消费验证矩阵后再恢复消费计划。计划支撑智能体不得实现代码。

计划支撑智能体不是形式审阅者，而是代码计划登记或恢复 `可执行` 前的最终设计质量门。文档齐全、局部签名匹配、未决项为空或本次具名缺口已修复都不能单独通过该门；必须完成第 6.2 节规定的端到端可构造性终审。任何一项终审证据不闭合时，受影响计划保持 `待激活`。

计划支撑智能体不得修改智能体规则、代码、工程、自检或施工记录。交互智能体按用户指令接管计划索引或设计切片时，计划支撑智能体必须停止该重叠切片；无关支撑工作可以继续。

### 2.5 流程图与知识图谱维护智能体

流程图与知识图谱维护智能体只维护当前代码事实。它接收交互智能体给出的具名维护目标，或沿已正式移交的全项目维护总目标继续，只读源码、工程、正式规范和已发布设计材料，独占写入：

- `流程图/主程序可达调用关系/**`，但排除 `能力证据目录/**`；
- `流程图/代码流程图/**`。

其产物包括当前可达函数身份、项目调用边、外部边界、未解析调用、现状单函数流程图、逐行映射、制图队列、覆盖统计和当前代码知识图谱。当前代码基线前进时，它必须先重读 Git 和目标源码，再刷新受影响调用边、函数身份、队列和图谱。每个发布批次必须记录新增 / 变更 / 退出函数、公开根函数候选、基线和下一续点，并向交互智能体发送维护进度；不得直接写能力目录。

### 2.6 能力证据目录维护智能体

能力证据目录维护智能体独占写入 `流程图/主程序可达调用关系/能力证据目录/**`。它只读已发布的函数身份、调用图、现状单函数流程图、逐行映射、源码、正式规范和验证证据，维护稳定能力条目、能力候选队列、去重关系、状态和覆盖统计。

首批目录不是一次性产物。每当收到交互智能体转交的已发布流程图批次或代码基线刷新目标时，它必须：

```text
读取新 HEAD 与本批函数变更清单
-> 扫描公开业务 / 组合 / 仓库 / 会话 / 线程 / 外部边界根函数
-> 写入或更新能力候选队列
-> 与稳定能力条目按完整合同去重
-> 补齐函数、流程图、规范和验证证据
-> 更新候选状态、能力状态和覆盖统计
-> 验证、精确提交并推送
```

候选状态固定为 `待识别 / 待补流程图 / 待补规范证据 / 待补合同 / 待补验证 / 已登记 / 非独立能力 / 已排除`。每个符合准入条件的 `main` 可达根函数最终必须进入稳定能力条目，或具备 `非独立能力 / 已排除` 的可回查理由。能力目录只提供当前能力候选证据，不裁决某个新业务一定可以复用；复用裁决仍由计划智能体或计划支撑智能体在目标设计包内完成。

## 3. 所有权与并行

默认角色权限限制自动窗口，不限制用户直接指挥的交互智能体。所有写入都必须声明：

```text
目标
+ 文件范围
+ 语义范围
+ 所有者
+ 起点 HEAD
+ 输入事实版本
+ 验证 / 发布边界
```

下列切片不得同时写：

- 同一文件或同一聚合入口；
- 同一规范口径及其偏差审计；
- 正在被执行计划冻结消费的规范、流程图、设计、计划或接口；
- 同一接口合同的提供者定义与消费者接线；
- 会改写同一构建、生成、数据库、缓存或运行资源的验证。

其它路径和语义均独立的切片可以由不同智能体、不同任务树或同一交互任务树的不同后代并行写入。Git 暂存、提交和推送仍按单工作区规则取得唯一发布租约。

## 4. 消息路由

自动窗口的跨智能体消息默认只允许：

```text
交互智能体 -> 计划智能体
交互智能体 -> 流程图与知识图谱维护智能体
交互智能体 -> 能力证据目录维护智能体
计划智能体 -> 唯一登记的计划支撑智能体
执行智能体 -> 配对的计划支撑智能体
计划支撑智能体 -> 来源计划智能体（只允许登记结果 / 新目标写入释放，不得请求补齐既有计划材料）或配对执行智能体
流程图与知识图谱维护智能体 -> 交互智能体
能力证据目录维护智能体 -> 交互智能体
```

交互智能体为协调用户直接授权的仓库切片，可以向任何相关智能体发送暂停、释放、刷新或恢复通知；这些协调消息不得替代正式计划、S0、设计修订或机器事实。维护智能体只向交互智能体返回 `GRAPH-MAINTENANCE-PROGRESS`、`GRAPH-MAINTENANCE-DRIFT`、`GRAPH-MAINTENANCE-BLOCKED` 或 `GRAPH-MAINTENANCE-HANDOFF`，消息必须列明基线、文件边界、队列统计、续点和所有权状态。用户直接向任一窗口发送消息不属于跨智能体消息。

消息合同：

- `PLAN-PACKAGE-READY-NOTICE`：新包已发布，携带创建侧代码基线、四矩阵 / 机械推演产物路径和独立复核摘要，等待支撑从正式文件独立复核登记；创建侧 PASS 不等于支撑终审通过。
- `PLAN-INDEX-RESULT`：支撑已完成或拒绝登记。
- `PLAN-AVAILABLE-NOTICE`：正式索引出现新的 `可执行` 版本，执行智能体重新扫描。
- `PLAN-SUPPORT-NOTICE`：受影响设计包可能已正式修订，执行智能体重新 S0。
- `DESIGN-DRIFT-CONFIRMED`：支撑只读确认设计缺口，执行智能体可按规则形成安全断点。
- `GRAPH-MAINTENANCE-PROGRESS`：现状流程图 / 调用图批次已经发布，携带基线、函数变更清单、覆盖统计和下一续点；只发给交互智能体。
- `CAPABILITY-CATALOG-REFRESH-NOTICE`：交互智能体把已发布的代码或图谱基线交给能力目录维护智能体重新扫描。
- `CAPABILITY-CATALOG-PROGRESS`：能力目录批次已经发布，携带基线、候选状态统计、稳定条目变化和下一续点；只发给交互智能体。

任何消息只用于唤醒和交接，不证明能力实现、计划完成或取得发布租约。

## 5. 计划包与计划内提供者

新设计包必须形成一致的规范、目标业务流程图、业务节点—所需能力合同表、能力复用裁决、目标函数分解与物理位置表、目标单函数施工流程图组、逐函数 / 逐节点实现分析、详细设计、目标知识图谱、接口合同和叶子计划。执行智能体不得承担节点分析、物理位置选择或设计裁决。计划智能体可以引用两个维护智能体已发布的当前代码图谱和当前能力证据目录，但必须在本包内逐项建立所需能力合同、候选能力、合同差异、复用方式和验证证据矩阵；当前能力证据只用于发现和核验候选，不能替代计划内目标施工图、节点合同、详细设计或复用裁决。

计划智能体完成创建侧自审、发布后停止该包；计划支撑从正式提交和当前代码重新复核最终 blob、自审产物及全部终审项，并自行补齐当前包原目标内缺少的任何项目设计材料。接口骨架缺失或验证矩阵尚不满足时，消费计划登记为 `待激活`；计划支撑直接形成所需提供者设计包和施工计划。提供者计划具备自身执行前事实时可独立登记为 `可执行`；全部消费执行前事实成立时再把消费计划登记为 `可执行`。计划索引只记录计划路径、版本、状态和具名依赖，不控制执行顺序。

计划内提供者需求必须记录来源计划、调用理由、最终模块 / 文件、最终函数名与签名、DTO、所有权、返回 / 错误、骨架的零机器事实 / 零半结构 / 零假成功合同、提供者、消费者、验证和漂移点。骨架存在不等于真实能力完成。缺少计划内材料或必需函数不触发向计划智能体的工作请求；只有目标超出当前计划原目标时，计划支撑智能体停止扩展并等待用户形成独立新目标。

## 5.1 计划智能体创建侧端到端可构造性自审

计划智能体发送 `PLAN-PACKAGE-READY-NOTICE` 前，必须以本包冻结的当前代码基线、正式规范和完整设计材料完成：

1. **业务—函数全闭合矩阵**：枚举全部业务流程和业务节点，逐项绑定所需能力合同、复用 / 新建结论及目标函数组；再枚举计划内全部非平凡公开 / 内部根函数，绑定物理位置、单函数施工流程图、逐节点分析、功能确认、详细设计、调用图和验证。
2. **逐字段来源矩阵**：沿公开请求、内部请求、提供者回显、算法输入、事务候选到发布后读回，冻结每个必选字段的唯一来源、转换、版本、可选 / 不适用条件和输出去向；禁止空句柄、零版本、默认构造或隐式“读取最新”。
3. **提供者—消费者可构造性矩阵**：核对 DTO、完整签名、模块 / `import`、构造注入、所有权、生命周期、返回 / 错误、身份与版本回显。当前接口不存在时，冻结精确待实现合同和具名缺口，不得伪写成已实现。
4. **全分支事务矩阵**：至少覆盖主动、被动、无变化、精确重复、空候选、材料缺失、版本漂移和内部失败；逐分支冻结读取集、写集、参与者、执行器入口、确认、撤销、发布和读回，不适用必须给出依据。
5. **当前真实接口行为核对**：读取当前代码的签名与实现行为，核对拒绝、空写集、幂等、排序、版本、事务和生命周期；不得仅凭流程图名称、旧实现或预期接口形成当前事实。
6. **零代码机械施工推演**：逐根函数、逐分支模拟执行计划，证明施工者不需要决定字段、函数 / DTO、调用顺序、事务入口、错误映射、撤销或读回规则。
7. **创建侧独立只读复核**：由未参与正文写入的同类型只读子智能体从正式文件独立复核前六项；无法安排时，以新上下文完整重读代替。发现的问题必须在交包前闭合并重跑自审。

四张矩阵、机械推演、独立复核发现与闭合结果进入当前详细设计和 / 或叶子计划，并与函数、节点、接口和验证项双向引用；不得另建 Markdown 状态台账。任一项不闭合时不得发送 `PLAN-PACKAGE-READY-NOTICE`。创建侧自审只证明计划智能体认为设计包已可交付，不替代计划支撑第 6.2 节的独立终审、计划索引登记或执行 S0。

## 6. 业务流程到施工合同

目标业务流程图必须先冻结：

1. 业务输入、输出、前置条件和完成条件；
2. 业务步骤、判断、循环、并行 / 顺序和非成功结果；
3. 每个节点读取 / 写入的机器事实、事务边界和验证点；
4. 每个节点所需的能力合同，不直接把自然语言节点当函数；
5. 业务节点到候选能力、复用方式、目标函数组和验证项的双向映射。

业务流程不要求与代码流程图一一对应。一张业务图可以映射一个主函数组和多份单函数图；一个共享函数也可以服务多张业务图。执行智能体不得直接从业务节点猜测代码结构。

目标 / 现状代码实施类流程图必须一图一函数。每个节点只能是调用另一个具名函数或本函数内一条具体指令。设计者逐函数、逐节点确认：

1. 完整签名、参数、返回和所有权；
2. 节点类型及输入输出传递；
3. 事实读写、事务、版本、并发和生命周期；
4. 逻辑内返回、内部错误、撤销和发布后读回；
5. 代码文件、调用图、节点映射和验证矩阵。

任何未冻结项仍要求执行智能体决定时，计划不得登记为 `可执行`。

## 6.1 新函数物理位置裁决

每个待新建、移动或改变可见性的函数必须按同一顺序裁决，禁止按“离调用者最近”“文件最短”或执行智能体临场方便放置：

```text
冻结函数能力合同
-> 确定函数直接读取 / 写入或拥有的权威事实
-> 确定该事实的唯一领域 / 结构所有者
-> 查询能力证据目录、当前模块、同类函数和调用方向
-> 判断既有所有者模块是否能在不扩大职责、不产生循环依赖的前提下承载
-> 可以：冻结既有精确文件和插入锚点
-> 不可以：说明不可承载原因并建立新的唯一所有者模块 / 文件
-> 冻结成员 / 自由 / 静态 / 模板形态和最小可见性
-> 冻结声明位置、定义位置、工程登记、import / include 与允许 / 禁止调用方
-> 复核实体所有权、依赖方向、循环依赖和验证入口
```

详细设计和计划必须逐函数记录：完整签名、功能分类、权威事实所有者、精确文件路径、模块身份、函数形态、可见性、声明 / 定义位置、插入锚点、允许 / 禁止调用方、新增依赖 / 调用边，以及新建文件的具名理由。任一项为空即为设计缺口。

## 6.2 计划支撑端到端可构造性终审

计划支撑智能体在登记新代码计划、恢复消费计划、发布任何设计 DRIFT 修订版本之前，必须以当前正式规范、完整设计包、当前代码和正式验证证据完成以下八项终审。计划智能体的创建侧矩阵和复核结果只是待审材料，不得直接继承其 PASS：

1. **业务—函数全闭合矩阵**：枚举全部业务流程和业务节点，逐项绑定所需能力合同、复用 / 新建结论、目标函数组和验证；再枚举全部非平凡公开 / 内部根函数，逐项绑定唯一物理位置、单函数施工流程图、逐节点实现分析、函数功能确认、详细设计合同、调用图入口 / 出口及验证项。计划授权文件或模块中存在未纳入矩阵的非平凡目标函数时不得登记。
2. **逐字段来源矩阵**：从公开请求开始，沿内部请求、提供者回显、算法输入、事务候选到发布后读回，记录每个必选字段的唯一来源、转换规则、身份 / 规则 / 事实版本、可选或不适用条件和输出去向。禁止以空句柄、零版本、默认构造、未冻结枚举或隐式“读取最新”填补来源缺口。
3. **提供者—消费者可构造性矩阵**：逐条核对 DTO 字段、完整签名、模块 / `import`、构造注入、所有权、生命周期、返回 / 错误、身份与版本回显，并区分预冻结合同、已验证接口骨架和真实实现。消费者必须能只用冻结输入机械形成提供者请求并处理全部返回。
4. **全分支事务矩阵**：至少覆盖主动、被动、无变化、精确重复、空候选、材料缺失、版本漂移和内部失败；逐分支冻结读取集、写集、参与者、执行器入口、准备 / 确认、撤销、发布、发布后读回与结果映射。不适用分支必须给出正式依据，不得静默省略。
5. **当前真实接口行为核对**：除签名外，读取当前实现和正式验证证据，核对拒绝条件、空写集、幂等、排序、版本、事务和生命周期等会影响施工的实际行为。不能证明行为兼容时保持 `待激活`；若缺口在原目标内，直接建立计划内提供者设计包和施工计划。
6. **零代码机械施工推演**：按计划步骤对每个根函数和每条分支逐步模拟一次，证明执行智能体无需决定字段来源、函数 / DTO、调用顺序、事务入口、错误映射、撤销或读回规则。推演中出现任一临时选择即为设计缺口。
7. **独立只读终审**：由未参与本轮正文写入的同类型只读子智能体从正式文件独立复核上述六项。无法安排子智能体时，计划支撑智能体必须切换到新上下文并完整重读，不能沿用写入时的局部判断。发现的问题必须闭合后重新终审。
8. **DRIFT 全包回归**：每次设计 DRIFT 修订、提供者接口骨架落地或真实结果回填后，重新运行全部七项终审；不得只验证具名缺口或把旧版本局部 PASS 继承给新版本。

四张矩阵、机械推演结论、独立终审发现与闭合结果必须进入当前详细设计和 / 或叶子计划的正式章节，并与函数、节点、接口及验证矩阵双向引用；不得另建 Markdown 状态台账。全部终审通过只证明设计包可登记，不证明代码已实现、构建通过或能力完成。

## 7. 执行问题闭环

正常 S0、正常施工、完成回执、纯代码错误和环境问题不转移设计包所有权。只有执行智能体明确写“请求设计包修订：是”，且计划支撑只读确认确属具名设计缺口时，受影响设计包才进入修订闭环。

活动代码切片与待修设计存在语义依赖时：

```text
执行停止扩大范围
-> 支撑确认 DESIGN-DRIFT
-> 执行形成并发布安全 DESIGN-DRIFT-WIP
-> 执行进入 DESIGN-DRIFT-WAIT
-> 支撑修订并发布设计包
-> 支撑对修订后的完整设计包重跑第 6.2 节全部终审
-> 执行收到 PLAN-SUPPORT-NOTICE 后重新 S0
```

其它无关写入切片不必停止。

## 8. 子智能体

可以把两个以上边界明确、无真实依赖的只读或写入子任务交给子智能体并行。写入子智能体必须获得明确的文件和语义切片，不得暂存、提交或推送；统一由顶层任务复核后取得发布租约。不得用子智能体数量扩大其它角色的默认权限或制造伪并行。

## 9. 停止条件

受影响切片出现以下任一情况时停止：

- 身份或默认职责不成立；
- 用户目标、项目语义或所有权无法裁决；
- 同文件 / 同语义切片重叠；
- Git 发布租约或验证资源冲突；
- 计划、规范、设计、接口或实际代码漂移；
- 验证失败且不能在既定范围内修复。

无关切片可以继续。禁止以全仓 dirty 作为无差别停工理由。
