# 智能体协作与计划生命周期规则

日期：2026-08-02
状态：代理协作规则；不是项目机器规范

本文件补充 `AGENTS.md`，只规定角色之间怎样形成、登记、执行和验收工作。角色职责以 `AGENTS.md` 的简表为入口；Git 操作读取 `单工作区串行执行与发布规则.md`。本文件不复制项目机器逻辑，也不要求为形式完整重复生成材料。

## 1. 主动判断

交互、计划和计划支撑智能体必须把用户方案当作待审输入，结合当前事实检查假设、替代方案、重复入口、职责重叠、迁移残留和长期成本。结论应明确说明推荐、不推荐或成立条件。

审查深度与风险相称。简单机械任务直接完成；涉及数据权威、领域边界、事务、所有权、公开接口、删除或重构时进行完整审查。事实不足但可以低风险验证时先验证，不把一般工程判断推给用户。

## 2. 新目标形成计划

尚未进入既有计划范围的新目标由计划智能体处理。形成顺序原则上是：

```text
正式规范和当前事实
-> 业务闭环与完成条件
-> 所需能力和现有能力差异
-> 复用 / 组合 / 适配 / 扩展 / 新建裁决
-> 函数、DTO、物理位置和接口合同
-> 详细设计、施工范围和验证合同
```

非平凡代码设计必须足以让执行智能体机械施工，但产物形态按复杂度决定。可以用业务图、单函数图、表格或正文表达；同一事实只保留一个权威定义，其它材料引用它。设计包至少回答：

1. 做什么、不做什么、何时算完成；
2. 当前事实和可复用能力证据是什么；
3. 哪些函数、类型、字段、文件和调用关系会变化；
4. 每项数据从哪里来、由谁拥有、何时有效和如何发布；
5. 正常、拒绝、空结果、失败、撤销、并发和读回如何处理；
6. 如何证明实现符合目标，以及哪些范围没有被证明。

计划智能体应在交付前从头复核设计包，确认没有把关键选择留给执行者。高风险或大范围设计宜使用独立只读复核；不再强制每个计划生成同名“四矩阵”或固定数量文档，只要上述合同可追溯且完整闭合。

计划智能体发布新包后通知计划支撑智能体并释放该包。计划智能体不修改计划索引，也不直接要求执行智能体开工。

## 3. 计划支撑与登记

计划支撑智能体是计划进入或恢复 `可执行` 前的最终设计责任人。它从当前正式规范、代码、接口和 Git 独立复核新包，不继承创建侧结论。

在所接管计划原目标内，计划支撑智能体可以直接补充或修改完成施工合同所需的规范、流程图、函数分析、详细设计、接口合同、提供者计划、消费计划和索引项。缺少材料或必需函数不是把工作退回计划智能体的理由。

只有当所需工作已经改变原目标、引入独立业务目标或需要用户作新的机器语义裁决时，计划支撑智能体才停止扩展并向用户说明。它不得实现代码。

登记前必须确认：

- 目标、范围、依赖、接口和验证彼此一致；
- 当前代码能构造设计中的调用和数据流，或缺失提供者已被明确拆出；
- 执行者无需决定机器语义、物理位置、字段来源、事务或错误处理；
- 计划版本、路径、依赖和状态可被索引唯一识别。

存在真实提供者缺口时，提供者计划可独立登记；消费计划在其执行前事实尚不成立时保持 `待激活`。接口声明或显式“未实现”骨架只证明边界存在，不证明真实能力完成。

## 4. 执行生命周期

执行智能体从计划索引自主选择一份依赖满足的 `可执行` 计划，并完成 S0：

```text
刷新正式仓库和远端
+ 核对计划 / 索引精确版本
+ 核对真实接口和允许范围
+ 核对目标切片、Git index 和验证资源
```

S0 通过后直接实施，不等待聊天接受。执行者可以在计划范围内修复自身代码错误、调整机械实现和补充被计划授权的自检；不得临场发明机器语义、扩大白名单或修改设计和索引。

问题分流：

- 代码实现错误：执行智能体修复并继续。
- 环境或验证资源问题：保留证据，重试或按风险收口；不自动触发改设计。
- 真实接口 / 计划 / 设计漂移：停止受影响范围，向计划支撑智能体提交事实和修订请求。
- 无关 dirty 或无关规则 / 文档工作：只要所有者明确且无语义或资源冲突，可以继续。

执行完成或安全收口后提交结果和结构化摘要。若索引仍有其它可执行计划，执行智能体重新 S0 后可以继续；收到新计划通知时也必须重新读取正式状态，而不是沿用旧候选判断。

## 5. 当前事实维护与集成验收

流程图与知识图谱维护智能体只描述已发布代码事实；能力证据目录维护智能体只基于已发布代码、图谱、规范和验证维护能力证据。两者不能把候选、名称相似或接口存在写成业务能力完成，也不能修改目标设计或计划状态。

集成验收与回归智能体只验证交互智能体给出的已提交并推送基线，并按 `.codex/skills/hai-zhong-yu-chao-integration-acceptance/SKILL.md` 从合法消费者、正式入口、结构化结果、权威终态和独立读回组织服务导向验收。验收目标必须具名并提供范围、输入、环境、命令、矩阵和证据路径。失败时固定证据并归因，不临场改代码或降低标准；PASS 只证明该提交的具名服务切片通过该矩阵。

## 6. 所有权与消息

文件、语义、接口、聚合索引和验证资源都按明确切片分配所有者。不同切片可以并行；重叠时先暂停受影响切片并交接。交互智能体可以协调任何用户授权切片，但不能覆盖正在写入的所有者现场。

默认消息方向：

```text
交互 -> 计划 / 流程图维护 / 能力目录维护 / 集成验收
计划 -> 计划支撑
计划支撑 <-> 执行
流程图维护 / 能力目录维护 / 集成验收 -> 交互
```

交互智能体可以向相关所有者发送暂停、交接、刷新和恢复通知。消息使用自然、简洁、结构化的内容即可，至少说明目标、基线、事实、结果、剩余问题和希望接收方做什么；固定消息名是兼容标记，不是强制模板。任何消息都不能代替正式计划、索引、S0、Git 或机器事实。

## 7. 新函数与接口位置

新建或移动函数时，设计者按以下原则裁决，而不是让执行者按方便选择：

1. 先确定函数负责的事实和能力合同；
2. 找到该事实的唯一领域或结构所有者；
3. 优先扩展职责匹配且不会形成循环依赖的现有模块；
4. 只有现有模块无法合理承载时才建立新模块；
5. 冻结最小可见性、声明 / 定义位置、工程登记、允许调用方和依赖方向。

具体记录粒度以能消除实施歧义为准，不为每个显然的局部辅助函数重复整套表格。

## 8. 子智能体与停止条件

可以把边界明确、彼此独立的只读或写入工作交给子智能体并行。写入切片必须预先分配，子智能体不得自行暂存、提交或推送；顶层所有者统一复核和发布。

仅在目标或关键语义无法裁决、权限需要扩大、所有权或资源冲突、正式依据发生实质漂移、或必需验证无法安全归因时停止受影响切片。普通格式问题、可在原目标内补齐的设计材料、一次性工具波动和无关 dirty 不构成机械停工理由。
