# 交互计划执行计划支撑四智能体规则

日期：2026-07-25

状态：Codex 智能体类型、写入所有权与消息路由规则；位于 `.codex/rules/`；不是项目机器规范，不构成代码实施许可

## 1. 目标

本项目固定使用四类智能体：

```text
交互智能体
计划智能体
执行智能体
计划支撑智能体
```

四类智能体分别承担智能体协作规则、新计划及其前置设计工作、代码施工和执行问题退回计划修订。全部智能体共享唯一主工作区并严格串行写入；智能体权限不因物理窗口、模型、分支、智能体名称、子智能体层级或 Full access 合并。

验证、发布和只读复核是上述智能体在自身权限内进入的技术工作模式，不另行建立第五类写智能体。代码构建、运行、集成级验证和发布属于执行智能体的技术范围，并在同一计划段提交前完成；智能体协作规则、新计划设计包、执行问题退回设计包和代码的独立只读复核分别由交互、计划、计划支撑和执行智能体在对应切片中完成。只读模式不产生写权。

本规则不属于 `规范/规范目录.md` 登记的机器规范，不定义机器事实或代码语义。机器逻辑仍以现行正式规范为准；唯一主工作区、写入占用、Git 身份、执行验证和发布合同由 `.codex/rules/单工作区串行执行与发布规则.md` 定义。

不存在活动代码计划段时，暂停且所有者、基线和文件清单明确的设计文档 WIP 可以按单工作区规则的 `DIRTY-PRESERVED-HANDOFF` 原地保留，由交互智能体串行取得完全不重叠的协作规则写权。这不是并行写入；保留 WIP 的原所有者在交互规则提交期间必须停写，交互智能体不得暂存、修改或验证该 WIP。

## 2. 四智能体职责

### 2.1 交互智能体

交互智能体负责：

```text
与用户讨论、澄清目标和裁决；
形成或修订智能体协作规则和工具行为规则；
维护 AGENTS.md、.codex/rules/ 和 .codex/skills/；
用户明确要求本窗口直接修复其当前未提交代码时，在暂停其它写入者后独占完成该精确切片的代码、工程、自检修改和构建 / 运行验证；
只有目标需要形成项目设计包时，才向计划智能体发送结构化目标消息。
```

交互智能体是智能体协作规则的唯一写入者。项目机器规范、流程图、详细设计和知识图谱属于设计包，不属于交互智能体的规则写入范围。其它智能体发现 `AGENTS.md`、`.codex/rules/` 或 `.codex/skills/` 缺失、冲突或必须修改时，都不得代改；必须停止受影响切片，在自身用户可见窗口列出问题并等待用户把问题交给交互智能体。

除用户明确要求本窗口直接修复其当前未提交代码外，交互智能体不得修改项目机器规范、流程图、详细设计、知识图谱、计划、计划索引、代码、工程、自检或施工记录。直接修复只允许保留用户修改意图、排除该精确代码切片的编译 / 链接错误并恢复既有行为；不得 reset、checkout、clean、stash 或整文件恢复用户现场，不得扩大为新功能或机器语义设计。交互智能体不得替计划智能体形成新设计包，也不得替计划支撑智能体修订因具名计划 / 设计问题明确退回且复核成立的设计包。单纯协作规则修订或直接代码修复不向计划支撑 / 执行智能体发送消息；只有确实需要新增项目设计包时才向计划智能体发送目标。

### 2.2 计划智能体

计划智能体负责：

```text
接收交互智能体给出的已明确目标；
根据既有总目标自行推导后续计划目标；
接收计划支撑智能体正式发布的 DERIVED-REQUIREMENT-NOTICE，为派生需求创建新的提供者设计包；
创建新的计划；
为创建新计划执行必要的现状扫描、规范治理、流程图、逐节点实现分析、函数确认、详细设计、知识图谱、接口冻结和计划拆分；
在新计划正式发布前建立和维护完整设计包；
根据单函数流程图组逐函数、逐节点完成实现分析和函数功能确认，再形成可直接编码的详细设计；
建立或修订项目机器规范及目录、冲突登记、流程图、详细设计、知识图谱和新计划，但不修改计划索引；
冻结目标、依据、依赖、允许 / 禁止范围、施工记录路径、失败收口和验证合同。
每份完整设计包验证、提交并推送后，向唯一登记的计划支撑智能体发送 `PLAN-PACKAGE-READY-NOTICE`。
```

计划智能体只向计划支撑智能体发送 `PLAN-PACKAGE-READY-NOTICE`，不得修改 `计划/计划索引.md`、直接通知执行智能体或发送计划选择、开始、继续、停止、S0 结论。计划智能体可以接收 `DERIVED-REQUIREMENT-NOTICE`，但只能据此创建一份新的提供者设计包，不得改写来源消费包或计划索引。通知不能替代已经推送的正式设计包。

计划智能体不得修改智能体协作规则、代码、工程、自检或施工记录，不接收或处理执行侧问题。新计划精确版本正式发布后保持不可变和冻结；计划智能体不得因为计划被选择、S0 通过、正常实施或完成而继续修改该包，也不得修订已经由执行问题请求转给计划支撑智能体的设计包。确需形成后续功能时创建新的计划；发现协作规则不足、需要改变用户目标或机器语义无法裁决时停止并等待用户处理。

### 2.3 执行智能体

执行智能体负责：

```text
自主读取计划索引和可执行计划；
以完整详细设计为代码实施直接依据，以流程图复核过程覆盖，不根据流程图自行补设计；
完成 S0、代码实施、工程登记、自检、构建、运行和计划授权的 Git 收口；
只修改当前计划明确允许的代码、工程、自检、专属施工记录和验证记录；
把计划段选择、S0、完成、漂移、失败和计划修订请求发送给配对的计划支撑智能体。
```

执行智能体只能向配对的计划支撑智能体发送跨智能体消息，不得向交互智能体或计划智能体发送消息。执行智能体不得修改智能体协作规则、项目机器规范、流程图、详细设计、知识图谱、计划或计划索引。专属施工记录和验证记录可以使用 Markdown，但只记录已发生的实施事实，不得成为机器语义、设计合同、计划状态或执行许可。

执行智能体发现设计包问题时必须停止受影响计划并交给计划支撑智能体；计划支撑只读确认缺口成立后，可以按单工作区规则以 `DESIGN-DRIFT-CONFIRMED` 触发安全 `DESIGN-DRIFT-WIP` 收口，clean 后再接管设计修订。发现智能体协作规则问题时不得把它伪装成普通设计缺口，必须在消息中明确标记 `RULE-BLOCKED`。计划支撑智能体可以修订原目标内的项目机器规范和设计产物，但不得代改智能体协作规则。

### 2.4 计划支撑智能体

计划支撑智能体独占维护计划索引，并与执行智能体固定配对，负责：

```text
接收计划智能体的 PLAN-PACKAGE-READY-NOTICE，复核正式提交中的新计划设计包；
接管登记后可在该计划原目标和登记范围内按需新建或修改必要设计文件；
若设计包发生变化，形成、验证、提交并推送新的精确版本 / blob；
合格且执行前真实接口完整时，独占把最终精确计划版本登记到计划索引并标为可执行，提交推送后通知执行智能体；
发现当前目标必需但不存在的函数时，核对可实现性、冻结待实现接口合同、建立派生需求，并把消费计划登记为待激活；
派生需求记录提交推送且工作区 clean 后，向来源计划智能体发送 DERIVED-REQUIREMENT-NOTICE；
提供者实施后只读复核最终身份、签名、真实能力，或结构化未实现与零机器事实写入 / 零半结构 / 零假成功合同；只有消费计划显式传播或收口未实现，且当前阶段验证矩阵确实可由该结果满足时，才独占把消费计划转为可执行；
向来源计划智能体返回 PLAN-INDEX-RESULT；
只读接收执行智能体的结构化执行事实；
识别执行消息是否明确请求设计包修订，以及问题是否确属计划 / 设计缺口；
只有某个既有计划在执行过程中出现具名计划 / 设计问题、执行智能体明确请求修订且支撑侧复核成立时，才接管该计划关联设计包的修订权；
只在原目标内新建或修订被退回设计包所需的项目机器规范、目录 / 冲突登记、流程图、详细设计、知识图谱、既有计划及其计划索引项；
核对实际接口、范围、依赖、验证合同和 Git 证据；
修订完成后只向来源执行智能体发送正式设计包路径、计划版本、blob、状态和影响范围。
```

计划支撑智能体只能向来源计划智能体返回 `PLAN-INDEX-RESULT`、`DERIVED-REQUIREMENT-NOTICE` 或 `PLAN-WRITE-RELEASE`，并向配对执行智能体发送 `DESIGN-DRIFT-CONFIRMED`、`PLAN-AVAILABLE-NOTICE` 或 `PLAN-SUPPORT-NOTICE`；不得向交互智能体发送消息。`DESIGN-DRIFT-CONFIRMED` 只是在 dirty 现场上的只读缺口裁决，不取得设计文件写权。它接管新计划登记或既有计划修订后，可以在当前包原目标和授权范围内按需新建或修改必要设计文件，并可为该目标必需的缺失函数建立派生需求；不得自行设计或实施派生需求的提供者计划，不得独立发起无关新计划、扩大用户目标，也不得修改智能体协作规则、代码、工程、自检、施工记录或验证记录。

下列事实不得触发计划支撑智能体写入：

```text
计划被执行智能体选择；
S0 PASS；
正常代码施工或完成回执；
执行智能体可以在计划白名单和现行设计内自行修正的代码实现错误；
纯环境、权限、构建工具或执行通道问题；
没有明确写明“请求设计包修订”的一般 Git / 验证事实。
```

计划支撑智能体先只读复核请求。只有问题需要改变现行计划、规范、流程图、详细设计、知识图谱、接口合同、允许范围、依赖或验证合同，才取得该设计包的临时独占修订权；修订发布后设计包重新冻结。纯代码问题仍归执行智能体，不能用修改计划掩盖实现错误。

计划支撑智能体遇到以下情况时必须停止：

```text
需要改变用户目标；
需要新增或修改智能体协作规则；
项目机器规范之间存在无法按现行权威顺序消解的冲突；
现有证据不足以裁决接口、范围、依赖或验证合同；
继续修订会替用户作业务选择。
```

停止时必须在自身用户可见窗口列出：

```text
问题；
已确认事实；
冲突或缺失内容；
为什么不能自行裁决；
需要用户决定的具体事项；
受影响计划和当前 Git 现场。
```

随后等待用户直接发送消息。不得跨智能体转发、猜测用户意图或自行扩大目标。

## 3. 文件写入所有权

| 文件或工作范围 | 唯一写入智能体 | 其它智能体权限 |
| --- | --- | --- |
| `AGENTS.md`、`.codex/rules/`、`.codex/skills/` | 交互智能体 | 其它智能体只读 |
| 尚未正式发布的新计划及为创建该计划形成的规范、流程图、详细设计、知识图谱、接口合同和对应索引切片 | 计划智能体 | 交互、执行、计划支撑只读 |
| 计划支撑接管的当前包内派生需求记录、消费合同与对应索引切片 | 计划支撑智能体 | 交互、计划、执行只读；正式发布并 clean 后只把新的提供者设计目标交给计划智能体 |
| `DERIVED-REQUIREMENT-NOTICE` 后新的提供者设计包 | 来源计划智能体 | 交互、执行、计划支撑只读；不得改写来源消费包 |
| 已正式发布且未发生具名执行问题修订请求的设计包 | 无写入者，设计包冻结 | 四类智能体均只读；计划选择、S0 PASS 和正常执行不改变该状态 |
| 已由执行智能体具名请求修订、且支撑侧复核确属计划 / 设计缺口的关联规范、流程图、详细设计、知识图谱、既有计划及对应索引切片 | 配对的计划支撑智能体 | 交互、计划、执行只读；修订发布后重新冻结 |
| 用户明确交给当前交互窗口的未提交代码直接修复切片 | 交互智能体 | 其它智能体停止写入；只允许代码、工程、自检和验证，不含规范、设计、计划、索引或施工记录 |
| 计划允许的 C++、工程文件和自检 | 执行智能体 | 其它智能体只读 |
| 计划唯一专属的施工记录和验证记录 | 执行智能体 | 其它智能体只读；不得作为设计或状态权威 |
| 唯一主工作区中的代码结果提交、构建、运行、集成级验证和发布 | 执行智能体 | 其它智能体只读；执行计划段占用期间不得写入 |

计划智能体与计划支撑智能体都具有项目设计文档写权，但不能写同一设计包或同一物理文件切片：

```text
计划智能体拥有尚未正式发布的新计划设计包及其全部前置设计任务；
新计划正式发布后设计包冻结，计划智能体停止写入；
计划选择、首次 S0、S0 PASS、正常实施、完成或一般事实回执都不产生所有权转移；
执行侧具名报告计划 / 设计问题并明确请求修订，且计划支撑智能体复核成立后，受影响设计包修订权才转给配对计划支撑智能体；
计划支撑智能体不扩展到无关新目标，修订发布后该设计包重新冻结；
当前包必需函数缺失时，计划支撑智能体只冻结合同和建立派生需求，不设计提供者实现；派生需求发布并 clean 后，新提供者设计包写权转给来源计划智能体；
规范目录、冲突登记、知识图谱总入口、计划索引等共享物理文件必须串行写入，每次只修改本智能体拥有的条目；
即使条目互不重叠，两个设计智能体也不得同时暂存、提交或推送同一共享物理文件；
需要用无关新目标替代既有目标时，必须由用户重新把目标交给计划智能体。
```

## 4. 消息路由

跨智能体消息只允许以下关系：

```text
交互智能体 -> 计划智能体
计划智能体 -> 唯一登记的计划支撑智能体
执行智能体 -> 配对的计划支撑智能体
计划支撑智能体 -> 来源计划智能体或配对的执行智能体
```

消息矩阵：

| 发送方 | 唯一允许接收方 | 允许内容 |
| --- | --- | --- |
| 交互智能体 | 计划智能体 | 需要形成项目设计包的目标、范围、成功标准、禁止项和协作规则依据 |
| 计划智能体 | 唯一登记的计划支撑智能体 | `PLAN-PACKAGE-READY-NOTICE`：已推送的新计划设计提交、路径、版本、plan blob、具名依赖、影响范围和治理验证 |
| 执行智能体 | 配对的计划支撑智能体 | 计划段选择、S0、完成、DRIFT、失败、WIP、计划修订请求和 RULE-BLOCKED；每条消息明确是否请求设计包修订 |
| 计划支撑智能体 | 来源计划智能体 | `PLAN-INDEX-RESULT`：登记成功及索引提交 / blob，或不登记的具名差异；`DERIVED-REQUIREMENT-NOTICE`：当前包内已正式记录的派生需求及新提供者设计目标；`PLAN-WRITE-RELEASE`：执行 clean 终止后释放下一轮计划写入权 |
| 计划支撑智能体 | 配对的执行智能体 | `DESIGN-DRIFT-CONFIRMED`：只读确认具名设计缺口及 WIP 安全收口边界；`PLAN-AVAILABLE-NOTICE` 或 `PLAN-SUPPORT-NOTICE`：正式索引 / 修订提交、计划版本、blob、状态、影响范围和重新 S0 要求 |

明确禁止：

```text
交互智能体 -> 执行智能体或计划支撑智能体；
计划智能体 -> 交互智能体或执行智能体，或向计划支撑智能体发送 PLAN-PACKAGE-READY-NOTICE 之外的内容；
执行智能体 -> 交互智能体或计划智能体；
计划支撑智能体 -> 交互智能体，或向计划智能体发送 PLAN-INDEX-RESULT / DERIVED-REQUIREMENT-NOTICE / PLAN-WRITE-RELEASE 之外的内容，或向执行智能体发送 DESIGN-DRIFT-CONFIRMED / PLAN-AVAILABLE-NOTICE / PLAN-SUPPORT-NOTICE 之外的内容；
用消息替代正式规则、计划、计划索引、Git 事实或执行许可；
为发送消息而自动创建或派发新的顶层任务。
```

计划智能体只向当前唯一登记且用户未撤销的计划支撑顶层任务发送通知，不直接通知执行任务，也不自行选择或创建接收任务。计划支撑智能体只有在计划索引登记提交已经推送后，才向唯一登记的执行任务发送 `PLAN-AVAILABLE-NOTICE`。通知目标登记是平台路由事实，不写入计划索引或其它 Markdown；任务标题、分支、智能体名称不能建立登记。没有唯一可识别计划支撑接收方时，计划智能体保持已推送设计包事实，在自身窗口报告通知不可达；不得因此自行修改计划索引。

用户直接向任一用户可见智能体窗口发送消息不属于跨智能体消息，不受上述路由限制。智能体向用户报告本窗口结果、问题或阻塞也不属于跨智能体消息。

## 5. 消息格式

### 5.1 交互目标消息

```text
INTERACTION-GOAL
来源交互任务
唯一既有执行顶层任务平台身份，或明确写无
目标
背景和成功标准
禁止项
现行规则依据
需要形成的计划范围
不构成代码执行许可
```

交互智能体仅在确实需要形成项目设计包时发送该消息。协作规则修订、讨论、解释和只读检查不发送。

### 5.2 新计划设计包完成消息

```text
PLAN-PACKAGE-READY-NOTICE
来源计划任务
正式设计提交
新计划路由、路径、版本和 plan blob
具名依赖和影响范围
治理验证
计划智能体已经释放单工作区写入权
请求计划支撑智能体复核并登记计划索引
```

计划智能体只能在完整设计包通过治理验证、本轮精确提交已经推送且工作区 / index clean 后发送。发送后必须停止新一轮文件写入，直到计划支撑智能体明确返回登记失败需要修正、正式发送 `DERIVED-REQUIREMENT-NOTICE` 授权创建一份新的提供者设计包，或在执行智能体 clean 收口后发送 `PLAN-WRITE-RELEASE`。不得一边形成下一份计划，一边让计划支撑智能体登记索引。

### 5.3 计划索引登记结果

```text
PLAN-INDEX-RESULT
来源计划支撑任务
来源计划任务
来源正式设计提交与 plan blob
登记结果：成功 / 拒绝
成功时：最终设计提交与 plan blob、新增 / 修改文件、计划索引提交与 blob、状态、具名依赖
拒绝时：具名差异、未修改索引的证明
当前写入权：执行智能体 / 退回来源计划智能体修正消费包 / 来源计划智能体仅获派生提供者包写权 / 无当前写入者
```

登记拒绝时，计划支撑智能体不通知执行智能体，并把写入权退回来源计划智能体修正该设计包。登记为 `可执行` 时，计划智能体只读等待，不因收到结果开始下一份计划；计划支撑智能体随后发送 `PLAN-AVAILABLE-NOTICE`，把写入权交给执行智能体。登记为 `待激活` 且同时正式发布派生需求时，`PLAN-INDEX-RESULT` 必须把当前写入权写为“来源计划智能体仅获派生提供者包写权”，来源计划智能体只能按配套的 `DERIVED-REQUIREMENT-NOTICE` 创建该需求的一份新提供者设计包；不得把消费包修正权或普通下一计划写权一并退回。

消费包因接口骨架缺失而完整设计但不可施工时，计划支撑智能体可以把它登记为 `待激活`，在 `PLAN-INDEX-RESULT` 中列明派生需求和解除条件；此时不发送 `PLAN-AVAILABLE-NOTICE`。派生需求正式发布后，按第 5.8 节把新的提供者设计写权交给来源计划智能体。

### 5.4 新计划可用消息

```text
PLAN-AVAILABLE-NOTICE
来源计划支撑任务
正式设计提交
计划索引路径、提交和 blob
新计划路由、路径、版本和 plan blob
计划状态必须为可执行
具名依赖和影响范围
计划支撑智能体已经释放单工作区写入权
通知只触发执行智能体重读正式仓库和候选扫描
```

计划支撑智能体只能在正式设计包复核通过、计划索引登记为 `可执行`、索引提交已经推送且工作区 / index clean 后发送。消息正文只是定位线索，执行智能体必须自行核对正式中央分支、计划索引和 Git。

### 5.5 执行消息

```text
EXECUTION-SUPPORT-NOTICE
来源执行任务与唯一主工作区
计划路由、路径、版本和 blob
计划段起点、main、HEAD、origin/main 和 dirty state
S0 PASS / S0 DRIFT / 完成 / 验证失败 / WIP / RULE-BLOCKED / 具名终止码
实际接口、实际变更文件、验证和提交
专属施工记录与验证记录路径
是否请求设计包修订：是 / 否
请求为“是”时：精确计划 / 设计缺口及其证据
请求为“否”时：代码、环境、Git 或一般执行事实分类
完成边界
```

`是否请求设计包修订` 是设计包所有权转移的必要条件，但不是充分条件。计划支撑智能体还必须只读确认问题确实需要修改计划或其上游设计材料。计划选择、S0 PASS、正常完成、纯代码实现错误、环境问题和 `RULE-BLOCKED` 必须写 `否`；不得为了让支撑智能体接手代码问题而虚报计划缺口。

### 5.5A 设计漂移确认消息

```text
DESIGN-DRIFT-CONFIRMED
来源计划支撑任务
目标执行任务
计划路由、版本、plan blob 和计划段起点
只读确认的具名设计缺口与证据
允许形成 DESIGN-DRIFT-WIP 的现有白名单
必须通过的安全断点验证
不得宣称完成，不授权扩大范围或修改设计
计划支撑智能体仍未取得设计文件写权
```

计划支撑智能体只在执行智能体明确请求修订且只读复核确认缺口确属设计时发送。消息不授权新代码目标，只允许执行智能体按现有白名单和单工作区规则尝试形成安全断点；无法达到安全条件时不得提交。执行智能体推送断点并恢复 clean 后，以 `EXECUTION-SUPPORT-NOTICE` 返回 `Plan-Segment-Result: DESIGN-DRIFT-WIP`，随后进入 `DESIGN-DRIFT-WAIT`。计划支撑智能体此时才可取得设计包修订写权。

### 5.6 计划支撑消息

```text
PLAN-SUPPORT-NOTICE
来源计划支撑任务
受影响计划路由、路径、旧版本和新版本
新计划 blob 和计划状态
修订的规范、流程图、详细设计、知识图谱、依赖、合同、允许 / 禁止范围和验证边界
执行智能体必须在通知唤醒的同一轮重读正式仓库并重新 S0
通知不预先裁决计划选择、S0 PASS 或实施结果
```

`PLAN-SUPPORT-NOTICE` 不是执行授权，也不能用消息正文替代正式计划、计划索引或 Git；但它是既有执行任务的正式状态变化触发事件。除非用户已经在执行智能体自身窗口明确暂停，执行智能体收到通知后不得只确认收到、推迟到“下次恢复”或等待另一条“继续”，必须立即从正式仓库重新计算受影响计划和全部候选。用户已明确暂停时只保持 `USER-PAUSED`，不得借通知恢复施工。

### 5.7 下一轮计划写入权释放消息

```text
PLAN-WRITE-RELEASE
来源计划支撑任务
目标计划任务
执行智能体具名终止码
main / origin/main / dirty state
不存在活动计划段和其它写入者的复核
允许计划智能体开始下一份新计划设计包
```

计划支撑智能体只有在执行智能体已经以 `NO-CANDIDATE`、`USER-PAUSED` 或其它不保留 dirty 活动计划段的具名终止码收口，并且计划支撑智能体复核 `main == origin/main`、工作区 / index clean、三个自动窗口均无写入占用，且不存在已经发布但尚未由计划智能体形成并交回提供者设计包的 `DERIVED-REQUIREMENT-NOTICE` 后，才能发送 `PLAN-WRITE-RELEASE`。派生提供者包优先于普通下一计划；存在未消费派生授权时，不得用 `PLAN-WRITE-RELEASE` 另行授权普通计划。计划智能体收到后仍须重新核对 Git；条件漂移时不得写入。

### 5.8 派生需求消息

```text
DERIVED-REQUIREMENT-NOTICE
来源计划支撑任务
目标来源计划任务及平台任务 ID
幂等关联键：来源消费 plan blob + 派生需求唯一编号 + 派生需求记录 blob
来源消费计划路径、版本、plan blob 和状态
派生需求唯一编号、正式记录路径、提交和 blob
缺失接口的当前代码证据与可实现性依据
最终模块 / 文件、函数名、完整签名、DTO 和版本
输入输出所有权、生命周期、逻辑内返回和内部错误
提供策略：直接实现真实能力 / 先实现接口骨架
接口骨架形式：不适用 / 仅声明 / 显式未实现定义
显式定义的零机器事实写入、零半结构、零假成功合同
提供者、消费者、验证矩阵和漂移退回点
来源计划支撑智能体已经提交推送并释放单工作区写入权
只授权计划智能体创建一份新的提供者设计包
不证明接口骨架或真实能力已经实现
```

计划支撑智能体只能为当前登记或修订包原目标内必需、当前代码确实不存在、正式规范足以裁决且合同能够冻结的函数发布派生需求。无法裁决机器语义、函数身份、模块所有权或错误合同，或者需求会扩大用户目标时，必须停止等待用户，不能发布通知。

通知前必须把派生需求、消费合同和 `待激活` 门禁写入正式文件及计划索引，完成治理验证、精确提交、普通推送并确认工作区 / index clean。目标计划任务必须取自来源 `PLAN-PACKAGE-READY-NOTICE` 中的正式平台任务身份，不得按标题、模型或智能体名称猜测；同一幂等关联键只能授权同一份提供者设计包。通知送达后，来源计划智能体只能为该派生需求建立新的提供者设计包；不得修改消费设计包、派生需求记录或计划索引。提供者设计包仍须走正常 `PLAN-PACKAGE-READY-NOTICE` 登记流程。

提供者计划可以直接实现真实能力，也可以在派生合同明确允许时先实现接口骨架。接口骨架必须使用最终模块、函数名、DTO 和签名；仅声明可以满足计划目标时不得增加定义，其验证覆盖最终声明、DTO / ABI、模块导入 / 头文件消费及不需要链接定义的编译边界。全工程链接确需定义时，只能结构化返回“未实现”，不得返回假成功、有效句柄、默认业务对象或伪数据，不得写仓库、关系、索引、数据库或其它机器事实；其验证追加全工程链接、调用返回“未实现”和零机器事实 / 结构变化。骨架实现、真实能力实现和最终接线是三个不同完成边界。骨架完成后，只有消费计划显式传播或收口“未实现”、当前阶段明确允许该逻辑返回且验证矩阵不要求真实成功行为时，才能解除待激活门禁。

消息发送失败不改变正式文件和 Git 事实，也不扩大权限。发送方只可对唯一允许接收方幂等重试，并在自身窗口报告不可达。

## 6. 计划形成、执行和修订闭环

新目标：

```text
用户
-> 交互智能体澄清目标或修订规则
-> 确实需要计划时发送 INTERACTION-GOAL
-> 计划智能体形成完整新目标设计包，不修改计划索引
-> 设计包验证、提交并推送
-> 计划智能体发送 PLAN-PACKAGE-READY-NOTICE 后停止写入
-> 计划支撑智能体复核正式设计包
-> 计划支撑智能体可在当前包原目标内按需新建 / 修改必要文件
-> 设计包变化时形成、验证、提交并推送新的精确版本 / blob
-> 所需接口真实存在：独占登记计划索引为可执行，提交并推送
   -> 计划支撑智能体发送 PLAN-INDEX-RESULT 和 PLAN-AVAILABLE-NOTICE
-> 所需函数不存在但可精确合同化：
   -> 冻结待实现接口合同并建立派生需求
   -> 独占登记消费计划为待激活，提交并推送
   -> 计划支撑智能体发送 PLAN-INDEX-RESULT 和 DERIVED-REQUIREMENT-NOTICE
   -> 计划智能体创建新的提供者设计包，按合同直接实现真实能力或先实现接口骨架
   -> 提供者计划按正常登记与执行链实施
   -> 提供者执行提交推送并 clean 收口；计划支撑智能体先只读复核正式实现和消费验证矩阵
   -> 等待执行智能体不存在活动计划段且工作区 / index clean 后，计划支撑智能体取得索引写入占用
   -> 结果足以满足当前消费阶段时，把消费计划转为可执行，验证、提交并推送
   -> 工作区恢复 clean 后向执行智能体发送消费计划的 PLAN-AVAILABLE-NOTICE
   -> 结果不足时消费计划保持待激活，不修改索引、不发送 PLAN-AVAILABLE-NOTICE
-> 执行智能体从正式中央分支和计划索引自主发现、选择并 S0
```

执行计划：

```text
执行智能体读取计划索引和目标计划
-> 核对唯一主工作区、main、Git、计划 blob、允许范围和实际接口
-> S0 PASS：向配对计划支撑智能体报告后直接实施
-> S0 DRIFT：停止受影响计划；属于计划 / 设计缺口时明确请求设计包修订，属于代码、环境、通道或规则问题时按对应归属处理且不得触发支撑写入
```

计划修订：

```text
计划支撑智能体先只读核对执行事实、明确修订请求和问题归属
-> 没有明确修订请求，或问题属于代码实现 / 环境 / 通道：不取得设计文件写权，不修改设计包
-> 有明确修订请求且确属计划 / 设计缺口，并可在原目标和现行协作规则内解决：接管并修订受影响设计包和计划索引
-> 向来源执行智能体发送 PLAN-SUPPORT-NOTICE
-> 通知送达既有执行任务并产生新轮次：执行智能体当轮重读正式仓库并重新 S0，不等待用户继续指令

需要改变目标、智能体协作规则或无法裁决机器语义：
-> 计划支撑智能体停止
-> 在自身窗口列出问题
-> 等待用户直接消息
```

计划智能体只负责创建新计划及其前置设计任务，不修改计划索引、不处理执行退回；计划支撑智能体独占计划索引登记，并可在接管的新计划登记包或执行侧具名退回且复核成立的既有计划包内按需新建、修改必要文件，但不得独立发起无关新计划或扩大用户目标。计划、计划支撑、执行三者通过写入权消息串行推进，任一时刻只允许一个窗口写仓库。

### 6.1 从流程图形成详细设计

流程图是详细设计的上游函数过程合同，详细设计是执行智能体写代码的直接依据；施工计划只选择详细设计中的实施切片并冻结范围和验证，不重新设计机器逻辑。后续流程图只使用包含 Mermaid fenced block 的 Markdown，HTML 不再是生成、配对或验证要求；历史 HTML 只作非权威旧载体，不随 Markdown 修订。代码实施类流程图的正式单位固定为一个函数：一张图只描述一个根函数，多个函数共同完成的业务过程由单函数流程图组和调用图表达。固定形成顺序为：

现有设计包不因形成于本合同之前而豁免。尚未正式发布的新计划设计包由计划智能体按新合同复核；已经正式发布的精确版本保持冻结，只有执行侧因具名计划 / 设计问题明确请求修订且计划支撑智能体复核成立后，才由配对计划支撑智能体修订。计划被选择或 S0 PASS 本身不触发复核或写入。缺少单函数流程图、参数 / 结果或节点分类的精确计划版本不得保持或恢复 `可执行`；历史已退出材料只保留为历史证据，不原地伪装成新合同产物。

```text
现行正式规范
-> 按函数冻结流程图版本、完整签名、节点身份、边和全部终止路径
-> 逐函数、逐节点实现分析
-> 函数功能确认与共享合同归并
-> 完整详细设计
-> 流程图函数—节点（被调函数 / 指令）—结构—验证双向覆盖审查
-> 施工计划和计划索引
-> 执行智能体按详细设计机械编码
```

计划智能体或计划支撑智能体必须按下列方法从流程图形成详细设计：

1. 先建立本轮函数清单和调用图。每个需要表达内部过程的根函数各有一份流程图；禁止把多个函数的内部步骤混入同一张图，也禁止用一张“大业务流程图”替代函数清单。
2. 冻结每份流程图的路径、版本、根函数中文名、归属模块 / 文件 / 层级、现有或待新增身份、完整签名、参数列表和返回结果。每个参数必须记录名称、类型、方向、所有权 / 生命周期和非法值；返回结果必须记录类型与语义。无参数或 `void` 也必须显式写明，不能省略。
3. 冻结节点编号、全部边、分支条件和终止结果。图内每个节点只能是 `函数调用` 或 `本函数内指令`：函数调用节点冻结被调函数身份、完整签名、实参与形参绑定、返回接收和异常 / 逻辑返回去向；指令节点写明本函数内实际执行的判断、顺序操作、循环控制、赋值 / 构造、读写、事务操作或返回。模块、服务、仓库、阶段、目标和人读说明只能作元数据、泳道或注释，不能成为执行节点。
4. 被调函数有非平凡内部过程时，为其建立独立单函数流程图，并在调用节点与被调函数流程图之间双向引用；简单外部 / 标准库调用也必须在函数合同表中给出精确签名和不另画图的理由。不得用“处理”“校验”“服务”“写入”等抽象动词隐藏未冻结的函数或多条指令。
5. 对每份根函数及每个节点读取对应正式规范、相邻边、当前代码入口 / 调用者 / 结构和预冻结合同，区分真实能力已实现、接口骨架已实现、待实现合同、待复用函数、待新增函数和禁止假定。
6. 为根函数形成函数级实现分析；为每个调用节点形成调用分析，为每个指令节点形成指令分析。分析必须明确进入条件、输入 / 参数绑定、读取事实、写入事实、结果 / 返回接收、状态前后变化、分支谓词、调用顺序、事务边界、成功 / 拒绝 / 内部错误、撤销 / 发布后读回和验证。
7. 优先复用语义、签名、所有权和生命周期完全匹配的现有函数，不按旧函数一对一迁移，也不因名称相似判定复用。逐个确认根函数和被调函数合同，归并共享 DTO、事务和版本合同；共享合同只设一个所有者。
8. 先冻结数据结构、身份、字段、类型、枚举、版本和所有权，再冻结函数签名、参数 / 结果传递和调用图；不得用实现代码反向补造尚未裁决的机器语义。
9. 将确认结果写入详细设计，建立 `根函数流程图 -> 节点 -> 被调函数或具体指令 -> 结构 / 事实 -> 返回 / 错误 -> 验证` 正向映射，以及函数、指令、结构和验证项到流程节点的反向引用。
10. 对全部参数、结果、流程边、拒绝、内部错误、撤销、提交、恢复和返回作覆盖检查；未被详细设计覆盖的节点、没有流程来源的新增函数、未处理的参数或返回值都属于缺口。
11. 用当前代码或精确预冻结待实现合同复核每个文件、符号、签名、行为和所有权；预冻结合同只允许继续完成设计，不能代替执行前真实接口骨架。合同内容本身不得缺项。
12. 若当前目标必需函数不存在，计划支撑智能体按第 5.8 节建立派生需求；提供者设计必须明确直接实现真实能力，还是先建立仅声明 / 显式未实现定义的接口骨架。消费计划在提供结果足以满足其当前阶段验证矩阵前保持 `待激活`。
13. 由设计包所有者作可实施性复核：常规执行模型应能在不决定新字段、类型、函数、参数、返回、条件、版本、所有权、调用顺序和错误语义的情况下写出代码。不能满足时保持 `待激活`。

代码实施类详细设计至少必须记录：

```text
文档身份：目标、范围、正式规范、单函数流程图组路径 / 版本 / 根函数 / 节点、当前代码或合同基线；
函数流程图合同表：每图唯一根函数、模块 / 文件 / 层级、完整签名、参数、返回结果、节点清单、被调函数流程图和调用图引用；
节点实现表：节点类型只能为函数调用或本函数内指令；记录节点职责、进入条件、参数 / 结果绑定、事实读写、状态前后、分支谓词、调用 / 事务、结果和验证；
函数合同表：中文函数名、模块 / 文件 / 层级、现有或新增、完整签名、参数与返回类型、前后条件、读写方、所有权 / 生命周期、幂等 / 版本 / 并发、结果和错误、根流程图 / 调用节点引用与验证；
派生需求与骨架合同：来源消费计划、派生需求编号、预冻结合同版本、提供者 / 消费者、仅声明或显式未实现定义、零机器事实写入 / 零半结构 / 零假成功、按骨架形式分支的验证、真实能力计划和漂移退回点；
数据合同：DTO / 记录 / 规格字段、顺序、宽度、枚举稳定值、身份 / 主键 / 关系 / 索引、默认和非法值、所有权、生命周期和版本；
调用与事务：调用者 / 被调用者、依赖注入、构造和销毁、锁 / 会话 / 参与者、提交 / 撤销 / 最后发布、发布后读回和恢复；
失败合同：入口拒绝、逻辑内返回、内部错误、零变化要求、半结构禁止、诊断边界和追根因入口；
代码映射：允许的新建 / 修改文件、模块与工程身份、import / include、生产 / 自检依赖方向和共享文件唯一所有者；
验收与自检日志合同：人读过程信息和结果展示只经统一日志系统输出；冻结具名预编译宏、宏开 / 关行为、关闭时不求值仅供日志参数，以及日志关闭不改变自检执行、结构化结果、失败计数、退出码、机器事实或生产行为；禁止控制台、弹窗、界面文本或另建文件旁路；
验证矩阵：每个节点、分支、边界、拒绝、内部错误、撤销、版本 / 并发、发布后读回、恢复，以及候选级 / 集成级 / 生产级证据；
未决项：必须为空；任何影响代码选择的待定、可选、按实际、必要时或等价表述都会使设计不可执行。
```

施工计划只引用详细设计的精确版本、章节、节点和函数合同，冻结本切片允许 / 禁止范围、开工条件、步骤、失败收口和验证；不得复制后重新解释详细设计，也不得把缺失的设计选择交给执行智能体。

## 7. 计划状态与执行自主性

`计划/计划索引.md` 的计划状态仍只允许：

```text
待激活
可执行
已退出
```

`可执行`只证明精确计划版本和 blob 可供选择，不是执行命令。执行智能体自主读取计划索引、选择自身范围内依赖已满足的计划并完成 S0；它不需要等待 `PLAN-AVAILABLE-NOTICE` 才能选择已经正式存在的候选，也不能因收到通知而跳过自主选择和 S0。

执行智能体发送消息后不等待计划支撑智能体接受 S0。PASS 后直接实施，且该 S0 消息不触发设计包写权转移；DRIFT 或计划失败后停止受影响计划，只有属于计划 / 设计缺口时才明确请求计划支撑修订。普通合法 WIP clean 收口后继续检查其它候选；`DESIGN-DRIFT-WIP` clean 收口后进入 `DESIGN-DRIFT-WAIT`，必须把单工作区写权交给计划支撑，不得选择其它计划。计划支撑智能体登记新计划后，`PLAN-AVAILABLE-NOTICE` 只负责触发候选扫描；计划支撑智能体完成执行问题修订后，`PLAN-SUPPORT-NOTICE` 只负责触发受影响计划重新评估。执行智能体必须以正式计划、计划索引和 Git 为准选择和 S0，不能仅凭消息正文继续。

### 7.1 执行继续门禁与终止码

计划段结果或计划允许的普通 WIP 断点已经提交、非强制推送到 `origin/main` 且单工作区 / index 恢复 clean 后，执行智能体必须在输出最终答复前运行一次继续门禁。`DESIGN-DRIFT-WIP` 不进入该门禁，而是进入 `DESIGN-DRIFT-WAIT`：

```text
重读 origin/main 的计划索引并固定索引 blob
-> 重读每个 `可执行` 计划的路径、版本、blob 与具名依赖
-> 读取当前 main / origin/main / dirty state
-> 从 Git 计划段提交和结构化回执排除本通道已经固定的计划
-> 核对当前没有第二活动计划段
-> 逐项判断剩余计划是可进入 S0，还是有具名排除原因
```

只要存在一份当前通道所有权内、真实依赖满足且未由本通道固定的 `可执行` 计划，继续门禁结果就是 `CONTINUE-REQUIRED`。此时禁止输出最终答复；执行智能体必须立即以当前累计 HEAD 建立下一计划段、发送计划选择 / S0 回执并继续实施或具名退回。单份计划完成、完成回执已送达、计划支撑智能体无须回复、模型发生上下文压缩、单轮耗时较长或没有收到新消息，都不构成停止条件。

只有下列代码允许结束当前执行任务：

| 终止码 | 成立条件 |
| --- | --- |
| `NO-CANDIDATE` | 已逐项扫描正式计划索引，当前通道没有可选择计划 |
| `USER-PAUSED` | 用户在执行智能体自身窗口明确暂停 |
| `DESIGN-DRIFT-WAIT` | 安全设计漂移 WIP 已推送并 clean，等待计划支撑修订和 `PLAN-SUPPORT-NOTICE` |
| `DIRTY-BLOCKED` | 单工作区 / index 存在无法归属于当前活动计划并合法提交或撤回的改动，或没有活动计划段却已经 dirty，因而不能安全开始 / 切换计划 |
| `MAIN-DRIFT` | main、origin/main、计划段起点、所有者或共享接口失配 |
| `WRITE-OCCUPIED` | 另一智能体或活动计划段尚未释放单工作区写入占用 |
| `RULE-BLOCKED` | 智能体类型、消息路由或协作规则冲突，不能在现行规则内继续 |
| `ENVIRONMENT-BLOCKED` | 计划要求的权限、工具或环境不可用，且无其它无关候选可检查 |

终止回执必须同时列出终止码、计划索引 blob、当前 HEAD / upstream、dirty state、最近计划段起点—结果提交，以及全部剩余 `可执行` 计划的选择或排除结论。缺任一项时不得把最终答复解释为合法停机。

平台轮次或上下文上限迫使当前轮让出时，只能发送 `EXECUTION-YIELD`，固定当前活动计划或下一候选、HEAD、dirty state 和精确续点；它不是终止码，也不证明任务完成。仓库文件本身不能在 Codex 任务已经进入 idle 后产生新轮次；用户直接消息、`PLAN-AVAILABLE-NOTICE`、`PLAN-SUPPORT-NOTICE` 或另行授权的同任务调度器可以唤醒既有执行任务，但不得因此创建新的顶层任务、改写计划 / Git，或把唤醒解释为执行许可。

### 7.2 新计划可用通知唤醒门禁

既有执行任务收到 `PLAN-AVAILABLE-NOTICE` 并实际产生新轮次时，无论上一轮是 `NO-CANDIDATE`、`EXECUTION-YIELD` 还是普通 idle，都必须先核对用户暂停和活动计划段：

```text
用户已经在执行智能体自身窗口明确暂停
-> 保持 USER-PAUSED，不进入 S0，通知不得解除暂停

当前没有活动计划段、单工作区 / index clean 且没有其它写入占用
-> 刷新并重读 origin/main、计划索引及其 blob
-> 自行核对通知所述正式设计提交、计划版本 / blob、状态和具名依赖
-> 扫描全部可执行候选，不把被通知计划强制置顶
-> 有候选：自主选择一份并立即 S0，PASS 后直接实施
-> 无候选或发生阻断：只按第 7.1 节给出具名终止码和完整证据

当前没有活动计划段、用户未暂停但单工作区 / index dirty
-> 不开始 S0，不 stash、不清理、不覆盖现场
-> 固定 dirty 文件、index、HEAD / upstream 和来源证据
-> 以 DIRTY-BLOCKED 和完整候选扫描证据收口

当前已有活动计划段
-> 不暂停、不切换、不修改当前计划段的白名单或所有权
-> 仅保留通知中的提交、索引 blob 和 plan blob 作为后续定位线索
-> 当前段合法收口、提交推送且单工作区 / index clean 后，立即运行第 7.1 节继续门禁
-> 从正式仓库重新扫描，包括通知所述计划在内的全部候选
```

通知正文中的计划状态和依赖结论不是机器事实。执行智能体不得回复“已收到”“下次恢复时处理”或等待用户另发“继续”后结束，也不得为了响应通知中断一个正在实施且尚未 clean 收口的计划段。计划智能体只能通知唯一登记的既有执行任务；一旦通知已经使该任务产生新轮次，就是允许消息路由内的唤醒。

### 7.3 计划支撑通知唤醒门禁

既有执行任务收到 `PLAN-SUPPORT-NOTICE` 并实际产生新轮次时，无论上一轮是 `NO-CANDIDATE`、DRIFT、`EXECUTION-YIELD` 还是普通 idle，都必须执行：

```text
先核对用户是否已经在执行智能体自身窗口明确暂停
-> 已暂停：保持 USER-PAUSED，不进入 S0
-> 未暂停：刷新并重读 origin/main、计划索引及其 blob
-> 核对通知所述计划版本 / blob、正式设计提交和当前通道累计 HEAD
-> 受影响计划当前可选择：立即重新 S0，PASS 后直接实施
-> 受影响计划仍不可选择：重新扫描其它全部可执行候选
-> 有候选：CONTINUE-REQUIRED，禁止最终答复并立即进入下一 S0
-> 无候选或发生其它阻断：只能按第 7.1 节给出具名终止码和完整证据
```

通知正文中的版本、blob、状态和完成描述都是定位线索，不是机器事实；执行智能体必须自行验证。禁止以“通知不构成继续指令”“下次恢复时再处理”“已接收并记录”作为结束理由。计划支撑智能体只能向既有配对执行任务发送通知，不得为此创建新的顶层任务；一旦通知已经使既有任务产生新轮次，这就是允许消息路由内的同任务唤醒，不需要用户重复发送“继续”。如果通知到达时执行智能体正在实施其它活动计划段，仍不得中断该段；必须在该段合法 clean 收口后优先重新评估被修订计划及全部候选。

## 8. 顶层任务树与子智能体

一个顶层任务及其全部直接和递归协作代理构成一个顶层任务树。每棵树固定继承交互、计划、执行、计划支撑中的一种写类型；同一顶层任务树同一时刻不得出现两种写类型。

子智能体只能：

```text
继承所属顶层任务树的同一种智能体类型和写权限；
或保持严格只读。
```

子智能体、模型、分支或名称不能规避智能体类型边界。单工作区写入占用、Git index、暂存、提交、推送和活动计划段仍由唯一指定智能体串行收口。

存在两个以上边界清楚的只读子任务时，可以使用只读子智能体并行；全部写入任务必须在唯一主工作区串行，不得跨类型派发或让两个智能体同时写文件、计划、接口或验证切片。

流程图和详细设计生产可以按互不重叠的根函数组交给只读子智能体形成分析候选，但仓库写入只由当前计划 / 计划支撑顶层智能体串行完成。主智能体必须先冻结函数清单、调用图、每图唯一根函数、共享结构、共享函数合同和唯一所有者；不得把同一函数或节点交给两个候选分析者。共享函数、DTO、事务、版本、规范目录、计划索引和 Git index 均由唯一写入者收口。候选在主智能体完成跨函数去重、调用图闭合、双向覆盖和可实施性复核前不取得正式设计身份。

## 9. 集成、只读复核与 Git

代码的集成级验证和发布仍属于执行智能体，并必须在当前活动计划段提交前于唯一主工作区完成。执行智能体核对固定输入、文件范围、计划段起点、验证矩阵、main 漂移和写入占用，不得借验证或发布修改规则或计划。

智能体协作规则只读复核由交互智能体负责；新计划设计包和执行问题退回设计包的只读复核分别由计划智能体、计划支撑智能体在各自所有权内负责；代码与施工记录只读复核由执行智能体负责。只读复核不修改、构建、运行、暂存、提交、推送或改变状态。

main、origin/main、计划段起点、dirty state、写入占用或远端状态漂移时，只停止受影响切片。执行智能体把具名 DRIFT 发给计划支撑智能体；规则或目标问题由计划支撑智能体停下等待用户。

## 10. 模型路由

模型选择不改变智能体类型或权限：

| 工作 | 建议模型 |
| --- | --- |
| 智能体协作规则讨论、修订和目标澄清 | 高推理模型 |
| 新计划规范、流程图、详细设计、计划生成和审查 | 高推理模型 |
| 成熟计划实施、构建和验证 | 中等推理模型 |
| 执行问题退回计划修订、接口漂移和计划冲突 | 高推理模型 |
| 明确重复的只读整理 | 低消耗等效模型 |

执行智能体不能通过升级模型自行修改设计包或智能体协作规则。计划支撑智能体不能通过升级模型改变用户目标或智能体协作规则。

## 11. 验证

协作规则或设计包文档治理至少运行：

```powershell
git diff --check
python .\tools\check_specs.py --strict
```

协作规则修订不运行代码构建。设计包文档验证不证明任何代码计划已经实施、构建通过或业务闭环完成。施工记录只能记录执行智能体实际运行的验证，不得补写未发生结果。

## 12. 完成边界

本规则只证明以下协作边界已经建立：

```text
交互智能体独占智能体协作规则修订，并可在用户明确要求时独占直接修复其当前未提交代码切片；
计划智能体创建新计划及其前置设计产物，不修改计划索引；推送设计包后只向计划支撑智能体发送 PLAN-PACKAGE-READY-NOTICE 并停写；
执行智能体实施代码并维护专属施工 / 验证记录，只向计划支撑智能体发送消息；
正常执行期间设计包冻结，计划选择、S0 PASS、正常施工和完成不触发任何设计智能体写入；
计划支撑智能体独占计划索引登记，可在当前登记或修订包内按需新建、修改必要文件；缺失函数可在原目标内冻结合同、建立派生需求并发送 DERIVED-REQUIREMENT-NOTICE，但不自行设计提供者；提供结果足以满足消费计划当前阶段验证矩阵后，才把消费计划转为可执行并向执行智能体发送 PLAN-AVAILABLE-NOTICE；同时接管执行侧具名请求且复核成立的既有计划修订；
无法由现行规则解决的问题停下并等待用户。
```

它不证明任何计划已形成、代码已实施、构建已通过、候选已集成或项目能力已经完成。
