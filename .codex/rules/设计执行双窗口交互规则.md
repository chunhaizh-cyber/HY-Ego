# 智能体协作与计划生命周期规则

日期：2026-08-02
状态：代理协作规则；不是项目机器规范

本文件补充 `AGENTS.md`，只规定角色之间怎样形成、登记、执行和验收工作。角色职责以 `AGENTS.md` 的简表为入口；Git 操作读取 `单工作区串行执行与发布规则.md`。本文件不复制项目机器逻辑，也不要求为形式完整重复生成材料。

## 1. 主动判断

交互、计划和计划支撑智能体必须把用户方案当作待审输入，结合当前事实检查假设、替代方案、重复入口、职责重叠、迁移残留和长期成本。结论应明确说明推荐、不推荐或成立条件。

审查深度与风险相称。简单机械任务直接完成；涉及数据权威、领域边界、事务、所有权、公开接口、删除或重构时进行完整审查。事实不足但可以低风险验证时先验证，不把一般工程判断推给用户。

## 2. 新目标形成计划

尚未进入既有计划范围的新目标由计划智能体处理。形成顺序原则上是：

```text
正式规范和当前事实
-> 业务闭环与完成条件
-> 所需能力和现有能力差异
-> 复用 / 组合 / 适配 / 扩展 / 新建裁决
-> 函数、DTO、物理位置和接口合同
-> 详细设计、施工范围和验证合同
```

非平凡代码设计必须足以让执行智能体机械施工，但产物形态按复杂度决定。可以用业务图、单函数图、表格或正文表达；同一事实只保留一个权威定义，其它材料引用它。设计包至少回答：

1. 做什么、不做什么、何时算完成；
2. 当前事实和可复用能力证据是什么；
3. 哪些函数、类型、字段、文件和调用关系会变化；
4. 每项数据从哪里来、由谁拥有、何时有效和如何发布；
5. 正常、拒绝、空结果、失败、撤销、并发和读回如何处理；
6. 如何证明实现符合目标，以及哪些范围没有被证明。

计划智能体应在交付前从头复核设计包，确认没有把关键选择留给执行者。高风险或大范围设计宜使用独立只读复核；不再强制每个计划生成同名“四矩阵”或固定数量文档，只要上述合同可追溯且完整闭合。

计划智能体对新包承担完整创建质量责任。设计、验证和发布完成后，由计划智能体直接把精确计划版本、blob、状态和具名依赖登记到计划索引。原则上只登记能够立即进入 S0 的 `可执行` 计划；只有直接上游已经 `可执行` 或正在施工、最终 ABI 与所有权已经冻结，且其结果是唯一剩余门禁时，才可额外登记一份紧邻后继为 `待激活`。其它未成熟设计不得进入计划索引。登记发布后通知执行智能体重新扫描正式状态，消息本身不构成开工许可。

### 2.1 目标模式、实现优先与有限前视

用户明确指定一个实现方案、闭环或其它长期结果为目标时，交互智能体必须建立并维护一个活动目标。活动目标至少记录：目标身份、完成条件、当前正式基线、已完成设计叶、当前设计叶、当前执行段、下一最早缺口和真实阻断。聊天摘要、智能体名称或单次回执不能替代正式方案、计划索引和 Git 事实。

目标模式以最早代码结果为推进单位：

```text
交互智能体设定活动目标
-> 找出当前最早代码缺口
-> 计划智能体将它闭合为一份可执行计划
-> 执行智能体施工并发布代码结果
-> 执行智能体发送施工完成消息
-> 交互智能体按顶层方案目标核验施工结果并接受、退回补齐或纠偏
-> 再形成下一份计划
```

固定规则：

1. `计划/计划索引.md` 是执行队列，不承载完整设计库存。同一活动目标、同一依赖链中只保留一份当前 `可执行` 计划和至多一份紧邻 `待激活` 后继。
2. 紧邻后继只有在直接上游已经 `可执行` 或正在施工，最终函数、DTO、ABI、所有权、生产文件和机器语义已经冻结，且上游真实结果是唯一门禁时才可登记。缺机器语义、最终接口、提供者设计、物理位置或多层未实现依赖的内容不得进入索引。
3. 第二层及更远下游只记录在路线输入、业务设计、能力矩阵或缺口清单中。它们可以用于上层需求校准，但不是计划，不取得 `待激活` 身份。
4. 当前没有 `可执行` 计划时，计划智能体的唯一设计优先级是闭合最早未满足提供者；不得继续发布依赖同一缺口的消费者计划。
5. 当前计划发布登记后，同一依赖链的计划设计暂停扩展；除第 2 项允许的一份直接后继外，等待代码结果或执行侧具名漂移后再继续。独立且不共享 ABI、生产文件、所有权或验证资源的其它目标，只有用户明确要求时才可并行设计。
6. 计划智能体对设计质量自行审查、验证、发布和登记；交互智能体不重复计划终审，但必须核对当前代码结果和顶层目标，及时派发最早代码缺口，不能用远端设计进度代替实现进度。
7. 计划智能体提出 Git 发布租约申请时，交互智能体应尽快核对唯一租约、HEAD、index、目标切片和活动所有者并明确 `GRANTED` 或具名等待原因。租约等待不得静默搁置。
8. 一份计划发布登记后，交互智能体应通知执行智能体重扫正式索引；`待激活` 通知不授权施工，`可执行` 也仍须通过执行 S0。
9. 交互智能体结束一次对话回合不撤销活动目标；只要没有完成、用户改向或真实停工条件，下一次被唤醒时应从正式 Git、计划索引和智能体回执恢复推进。
10. 同一结构 owner、同一公开 ABI 和同一组生产文件上的 DTO、服务、装配及首次权威读回默认合并为一份结果计划。只有语义尚未冻结、文件所有权不同、事务边界独立或验证资源确实不能共用时才拆分；不得仅按头文件、身份 wrapper、helper 或单个 getter 机械分叶。
11. 对外完成度以最终清单中的具名公开服务能够由合法普通应用消费者取得、调用并权威读回为单位。计划退出、提交、构建、探针数量和局部 helper 通过只能作为证据，不能替代该服务闭环或降低下一缺口优先级。
12. 本规则生效前已登记的 `待激活` 项不自动视为合规或可执行。计划索引所有者应按上述门禁复核：只保留允许的一份直接后继，其余迁出执行队列并保留必要的路线或历史记录。

有限前视只用于降低直接交接延迟，不扩大代码并发、Git 发布、文件所有权或机器语义裁决权限。设计完成仍不等于实现、构建、运行或集成验收完成。

## 3. 计划支撑与执行期问题修订

计划支撑智能体不再承担新计划终审、计划智能体设计包复核或正常登记。没有执行智能体的具名问题退回时保持待命，不主动接管新计划或重复创建侧检查。

执行智能体遇到现行规范、流程图、详细设计、计划和实际接口之间无法自行裁决的问题时，必须固定计划身份、代码基线、具名冲突、受影响函数 / 文件、已经发生的修改和期望裁决，交给计划支撑智能体。正常代码错误、编译错误、环境问题和普通验证波动继续由执行智能体处理。

计划支撑智能体先依据现行正式规范和当前事实给出唯一可施工裁决；需要落盘时，只在来源计划原目标内修改受影响计划、详细设计、目标流程图、接口合同及对应索引项。修订必须消除执行者遇到的歧义，冻结新的精确版本和重新 S0 门禁，并在发布后通知执行智能体重新读取正式状态。它不得实现代码，也不得借一次执行问题重做或扩大整个新目标。

如果问题只能通过改变正式机器语义、扩大原目标或建立独立新业务目标解决，计划支撑智能体不得自行裁决；应保持受影响计划 `待激活`，列出最小问题并等待用户决定。接口声明或显式“未实现”骨架只证明边界存在，不证明真实能力完成。

## 4. 执行生命周期

执行智能体从计划索引自主选择一份依赖满足的 `可执行` 计划，并完成 S0：

```text
刷新正式仓库和远端
+ 核对计划 / 索引精确版本
+ 核对真实接口和允许范围
+ 核对目标切片、Git index 和验证资源
```

S0 通过后直接实施，不等待聊天接受。执行者可以在计划范围内修复自身代码错误、调整机械实现和补充被计划授权的自检；不得临场发明机器语义、扩大白名单或修改设计和索引。

问题分流：

- 代码实现错误：执行智能体修复并继续。
- 环境或验证资源问题：保留证据，重试或按风险收口；不自动触发改设计。
- 真实接口 / 计划 / 设计漂移：停止受影响范围，向计划支撑智能体提交事实和修订请求。
- 无关 dirty 或无关规则 / 文档工作：只要所有者明确且无语义或资源冲突，可以继续。

执行完成或安全收口后提交结果和结构化摘要。若索引仍有其它可执行计划，执行智能体重新 S0 后可以继续；收到新计划通知时也必须重新读取正式状态，而不是沿用旧候选判断。

### 4.1 施工结果回传、目标核验与纠偏

执行智能体完成一份计划的施工、验证和正式发布后，必须向交互智能体发送完成消息。消息至少给出计划身份和版本、结果提交、plan blob、实际变更范围、验证结论、未证明边界、剩余问题、main/origin 和 index 状态；消息是核验入口，不替代正式 Git、计划、记录或机器事实。

交互智能体收到施工完成消息后，按用户设定的顶层实现方案和该计划完成条件核验正式结果，重点比较：

```text
方案目标与计划承诺
-> 实际提交和接口 / 事实形状
-> 验证证据和非成功分支
-> 完成声明边界与后继依赖
```

核验结果只能是：

- 达到本计划目标：接受施工结果，通知计划索引所有者登记退出或推进相应门禁；
- 计划内实现缺口：退回执行智能体在原计划范围内补齐；
- 真实设计漂移：转交计划支撑智能体在原目标内裁决和修订；
- 顶层方案或机器语义缺口：由交互智能体依据正式规范自行裁决；无法裁决且会实质改变目标时才请求用户决定。

交互智能体的核验只针对施工结果是否达到方案目标，不接管计划智能体的计划设计验收，也不把编译、自检或消息摘要单独升级为业务闭环完成。

## 5. 当前事实维护与集成验收

流程图与知识图谱维护智能体只描述已发布代码事实；能力证据目录维护智能体（兼代码知识库维护）只基于已发布代码、图谱、规范和验证维护能力证据、函数用途卡及知识当前性状态。两者不能把候选、名称相似、接口存在或知识条目写成业务能力完成，也不能修改目标设计或计划状态。

集成验收与回归智能体只验证交互智能体给出的已提交并推送基线，并按 `.codex/skills/hai-zhong-yu-chao-integration-acceptance/SKILL.md` 从合法消费者、正式入口、结构化结果、权威终态和独立读回组织服务导向验收。验收目标必须具名并提供范围、输入、环境、命令、矩阵和证据路径。失败时固定证据并归因，不临场改代码或降低标准；PASS 只证明该提交的具名服务切片通过该矩阵。

## 6. 所有权与消息

文件、语义、接口、聚合索引和验证资源都按明确切片分配所有者。不同切片可以并行；重叠时先暂停受影响切片并交接。交互智能体可以协调任何用户授权切片，但不能覆盖正在写入的所有者现场。

默认消息方向：

```text
交互 -> 计划 / 流程图维护 / 能力目录维护 / 集成验收
计划 -> 执行
执行 -> 计划支撑 -> 执行
流程图维护 / 能力目录维护 / 集成验收 -> 交互
```

交互智能体可以向相关所有者发送暂停、交接、刷新和恢复通知。消息使用自然、简洁、结构化的内容即可，至少说明目标、基线、事实、结果、剩余问题和希望接收方做什么；固定消息名是兼容标记，不是强制模板。任何消息都不能代替正式计划、索引、S0、Git 或机器事实。

## 7. 新函数与接口位置

新建或移动函数时，设计者按以下原则裁决，而不是让执行者按方便选择：

1. 先确定函数负责的事实和能力合同；
2. 找到该事实的唯一领域或结构所有者；
3. 优先扩展职责匹配且不会形成循环依赖的现有模块；
4. 只有现有模块无法合理承载时才建立新模块；
5. 冻结最小可见性、声明 / 定义位置、工程登记、允许调用方和依赖方向。

具体记录粒度以能消除实施歧义为准，不为每个显然的局部辅助函数重复整套表格。

## 8. 子智能体与停止条件

可以把边界明确、彼此独立的只读或写入工作交给子智能体并行。写入切片必须预先分配，子智能体不得自行暂存、提交或推送；顶层所有者统一复核和发布。

仅在目标或关键语义无法裁决、权限需要扩大、所有权或资源冲突、正式依据发生实质漂移、或必需验证无法安全归因时停止受影响切片。普通格式问题、可在原目标内补齐的设计材料、一次性工具波动和无关 dirty 不构成机械停工理由。
