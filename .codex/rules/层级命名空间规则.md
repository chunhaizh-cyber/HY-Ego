# 层级命名空间规则

日期：2026-10-28
状态：代理协作 / 工程表达规则；不改变项目机器语义或代码 ABI

本规则只解决不同体系都使用 `L0`、`L1` 等裸层号造成的歧义。机器逻辑仍以 `规范/规范目录.md` 及其登记规范为准，流程图身份和代码事实仍由各自正式载体承接。

## 1. 四个保留命名空间

| 写法 | 唯一含义 | 层号说明 |
| --- | --- | --- |
| `DATA-L1`—`DATA-L3` | 当前已定义的基础数据服务架构层级 | `DATA-L1` 为纯事实内核，`DATA-L2` 为带结构类型语义的强类型结构服务，`DATA-L3` 为世界树与概念空间结构聚合 |
| `DATA-L4`、`DATA-L5` | 保留但当前未定义的基础数据层号 | 不得为了凑层数赋予职责，也不得用“更高层”推导业务解释、接口或施工顺序 |
| `BIZ-L0`—`BIZ-Ln` | 目标业务流程图的自上而下分解深度 | 表示目标业务或目标函数身份的分解深度，不证明代码已实现 |
| `CF-L0`—`CF-Ln` | 当前代码调用图从具名根入口展开的深度 | 表示已发布源码的静态可达调用深度，不等于业务层级、架构层级或运行成功 |

三套层号彼此独立，数值相同不表示同层、对应、依赖或已经接线。例如，`BIZ-L3` 目标函数可以调用 `DATA-L2` 服务，其当前实现也可能位于 `CF-L5`；这三项关系必须由显式映射或调用证据证明，不能从数字推导。业务层位于 `DATA` 命名空间之外，不再用“`DATA-L5` 之外”表达。

## 2. 书写规则

1. 新建或修订的人读规范、设计、计划、流程图、映射、回执和协作消息，只要层号可能属于上述任一体系，就必须写完整前缀；不得用裸 `L1`、`L2` 或 `L1—L5` 让读者猜测命名空间。
2. 表达跨体系关系时分别保留双方完整身份，例如 `BIZ-L3 -> DATA-L2`、`CF-L4 对应 BIZ-L3`，不得缩写为“L3 调 L2”。
3. `DATA-Ln` 是数据架构层号；具体机器职责由 0050、4015、4030、4190 等正式规范定义。本规则只负责无歧义书写，不单独产生或改变机器语义。
4. `BIZ-Ln` 是目标设计身份；`CF-Ln` 是当前代码事实身份。两者都不能单独证明计划可执行、代码实现、构建通过或业务闭环。
5. 其它领域若也有等级、成熟度或阶段编号，必须写出领域名和含义，例如“相机材料成熟度 0—3”“启动阶段 14”，不得借用这三个保留前缀。

## 3. 兼容边界

- 现有 C++ 模块、命名空间、类型、函数、字段、文件名和公开 ABI 中已经存在的 `L1`、`L2` 等名称不机械改名；引用真实代码身份时保留原文，并在需要消歧时注明其属于 `DATA-Ln`。
- `DATA-L4`、`DATA-L5` 仅保留命名，不得因为历史材料曾使用五层就恢复职责；后继若确有独立结构层，必须先修订正式逻辑规范。
- 现有 `流程图/目标业务流程图/L2/`、`L3/`、`L4/` 以及 `流程图/代码流程图/L0/` 等物理目录暂不迁移；目录中的正式文件身份分别以 `BIZ-Ln-*` 和 `CF-Ln-*` 为准。
- 历史文件不因本规则全仓改写。后续修订触及含歧义语句时就地消歧；不得为统一显示名制造大范围无语义变更。

## 4. 最低检查

修改涉及层级的文档时，至少核对：

```text
数据服务层级是否统一写为 DATA-Ln
目标业务分解是否统一写为 BIZ-Ln
当前代码调用深度是否统一写为 CF-Ln
跨体系关系是否有显式映射或代码证据
DATA-L4 / DATA-L5 是否被错误写成已有职责
精确代码身份和历史物理路径是否被错误机械改名
```

本规则只证明工程表达已消歧，不证明任何数据服务、目标业务或当前代码能力已经完成。
## ARCH-Ln：全局架构层级命名空间

`ARCH-Ln` 只表达全项目架构职责与合法依赖方向，不替代 `DATA-Ln`、`BIZ-Ln` 或 `CF-Ln`。自 2026-08-24 起，项目保留四个命名空间：`ARCH-Ln`、`DATA-Ln`、`BIZ-Ln`、`CF-Ln`；文件内只列后三者的历史示例不得解释为排除 `ARCH-Ln`。

| 架构层 | 唯一口径 | 与现有命名空间的关系 |
| --- | --- | --- |
| `ARCH-L1` | 中性事实内核：节点、外部关系、字段关系、直接值、锁内原子发布及current-only恢复目标；无公开owner和事实代次 | 对应现行 `DATA-L1` |
| `ARCH-L2` | 通用基础结构：场景、存在、特征、状态、动态、因果、语言、词条、概念、材料及概念名称关系等既有结构；二次至n次特征并入特征结构，精确字段按各对象现行规范；不吞并ARCH-L4专属治理身份 | 对应现行 `DATA-L2` |
| `ARCH-L3` | 世界树、概念树、概念空间等聚合服务；组合 `ARCH-L2` 已有结构，不取得第二写入权 | 对应现行 `DATA-L3` |
| `ARCH-L4` | 需求、任务、方法；内部区分结构记录面与业务应用面，保存专属身份、引用、执行实例、冻结、结果和结算，不恢复任务/筹办轮次 | 不得命名为 `DATA-L4`；专属治理记录按对象合同，世界材料经 `ARCH-L2`，不建第二权威 |
| `ARCH-L5` | 自然语言理解、表达和名称绑定裁决；为下层机器对象形成词条、名称、别名、定义和表达绑定请求 | 不得命名为 `DATA-L5`；不得直接改写 `ARCH-L1..ARCH-L4` 字段 |

依赖方向固定为：

```text
ARCH-L5 -> ARCH-L4 / ARCH-L3 / ARCH-L2
ARCH-L4 -> ARCH-L3 / ARCH-L2
ARCH-L3 -> ARCH-L2 -> ARCH-L1
ARCH-L4结构记录面 -> ARCH-L1（仅本域结构保存，不等于业务应用面直写）
具名编排 -> ARCH-L1（仅0050第3.3节/4030的中性读取与已校验片段组合发布）
```

禁止反向依赖。ARCH-L3经结构类公开服务取得和校验领域结构；具名编排按0050第3.3节及4030受限读取中性材料、组合已校验片段发布，不自行编码领域裸写集或解释私有schema。例外不恢复L1领域owner、端口或上层回调，不建立并列权威。ARCH-L5经下层公开服务提交绑定请求，下层对象允许尚无语言名称时建立。模拟不扩大写权。

### 与 DATA / BIZ / CF 的独立关系

1. `ARCH-Ln` 回答“该能力在全局架构中由哪一层负责”。
2. `DATA-Ln` 只回答“当前基础数据服务如何分层”，目前只定义 `DATA-L1..DATA-L3`；`DATA-L4`、`DATA-L5` 继续未定义且禁止使用。
3. `BIZ-Ln` 只表达目标、能力或业务分解层级，不可据此推断代码或数据 owner。
4. `CF-Ln` 只表达当前代码调用图深度，不可据此推断架构职责。
5. 同一对象可同时拥有独立的 `ARCH`、`DATA`、`BIZ`、`CF` 描述，但每个层号必须带命名空间，不得裸写 `L1`、`L2`、`L3`。

ARCH-L4结构记录面机械保存、读取和校验已裁决的身份、关系、生命周期、引用及当前结构，可以使用同一DATA-L1，不因此进入DATA-L2。业务应用面决定为何建立、选择、推进、结束和判定，经记录面或下层公开合同提交请求。底座不保存业务历史、公共请求账或事实代次；对象确需来源或历史按其专属合同保存，不恢复任务/筹办轮次。

现有 C++ 中的 `L2需求`、`L2任务`、`L2方法` 等名称是 `ARCH-L4` 结构记录面的迁移期兼容实现身份，不自动证明其属于 `DATA-L2`。讨论其业务治理职责时必须标为 `ARCH-L4`；讨论其复用的存在、特征、状态、动态结构时必须标为 `ARCH-L2` / `DATA-L2`。兼容实现不得以 `DATA-L2` 名义新增 owner、公开业务操作或业务事实语义；未来实现退出后，既有稳定编码仍不得复用。

### 书写与最低检查

- 跨数据服务的全局架构讨论必须先写 `ARCH-Ln`；仅讨论现行数据服务物理分层时写 `DATA-Ln`。
- 需求、任务、方法的业务身份和专属记录属于 `ARCH-L4`，其虚拟存在、特征、状态和动态不得另建第二权威。
- 概念基础身份、不可变材料和概念名称关系结构属于 `ARCH-L2`，概念树或概念空间聚合属于 `ARCH-L3`，自然语言名称接受、表达与消歧裁决属于 `ARCH-L5`。
- 二次至 n 次特征仍是 `ARCH-L2` 特征结构，必须记录真实阶次和直接来源，不得虚构新架构层。
- 审查材料必须检查：命名空间是否显式、`ARCH` 与 `DATA` 是否被混同、是否出现 `DATA-L4/L5`、依赖是否逆向、L3 是否取得第二写入权、L4 是否另存状态/动态权威、L5 是否直接改写下层字段。

20261028同步说明：本规则仅映射0050 v3.41、4015 v4.1及4030 v4.0的受限依赖，不单独扩大许可，不证明现有代码符合；封存不等于领域来源认证、跨片段新节点绑定、重放幂等或引用保活。
