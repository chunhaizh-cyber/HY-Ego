# 工作区与工作树切片并行写入、串行集成发布规则

日期：2026-10-14
状态：代理协作 / Git 工程规则；不是项目机器规范

本规则只处理工作区、所有权、验证资源和 Git 发布。保留原文件路径作为现行通用入口，适用于主工作区和独立 Git / Codex 工作树。工作树专项流程读取[多工作树并发与集成规则](多工作树并发与集成规则.md)。角色职责读取 `AGENTS.md`，目标模式读取 `目标模式默认执行规则.md`，计划生命周期读取 `计划/计划索引.md`及目标计划文件。

## 1. 固定形态

```text
一个 Git 仓库及 main 集成基线
+ 主工作区，可附加具名任务工作树和独立任务分支
+ 多个可并行的非重叠写入切片
+ 每个文件和语义切片一个所有者
+ 各工作区独立 index，main 集成与远端发布共用一个租约
+ 最多两个互不冲突的活动代码切片
```

主工作区直接施工与工作树隔离施工均可采用；任务分支默认使用 `codex/` 前缀。工作树不增加角色权限、并发切片额度或同一文件 / 语义的所有者数量。

## 2. 开工检查

首次写入任何目标文件前，交互智能体仍须从当前计划或用户授权、Git/index、目标文件实际 WIP、活动切片、接口语义与构建资源确认唯一写入所有者；不得覆盖、删除、暂存或带入异主 WIP。

开工前确认：

```powershell
git rev-parse --show-toplevel
git rev-parse --git-common-dir
git worktree list --porcelain
git branch --show-current
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
git rev-list --left-right --count HEAD...origin/main
```

同时声明目标、来源（已登记计划或用户直接代码切片）、工作区路径和分支、文件 / 路径范围、语义范围、所有者、起点 HEAD、main / origin/main 集成基线和所需验证。开工门禁只有：

1. 主工作区使用 `main`，任务工作树使用本切片独占的具名分支；detached HEAD 只用于只读检查，写入前先按工作树规则建立分支；
2. 跨全部工作区核对目标文件和语义没有其它写入所有者；
3. 当前工作区的 Git index 没有被另一所有者占用；
4. 所需构建、生成、数据库、外设或运行资源没有冲突。

工作区整体 dirty 不自动阻断。来源明确且不重叠的 WIP 原地保留；来源未知、所有权不明、同文件 / 同语义或共享输出冲突时只停止受影响切片。禁止自动 stash、reset、clean、checkout、覆盖或删除他人现场。

## 3. 并行与资源

路径不同不必然独立。下列情况视为冲突：

- 一方修改的规范、设计、计划或接口正被另一方冻结消费；
- 多方写同一聚合入口、索引、目录、接口合同或证据结论；
- 多方会改写同一构建目录、生成物、数据库、缓存、端口、日志固定文件或外设状态。

其它文件和语义都独立的切片可以并行。不同工作树内的同一仓库相对路径仍是同一个所有权对象，不因物理路径不同而允许重复施工。验证资源只锁定实际资源，不锁定整个仓库；只读检查通常可以并行。

实际项目测试及验证输出隔离统一服从 `规范/代码文件建立归属与模块命名规范.md` 第 5.1.1—5.1.2 节。验证者只占用获准的实际工程构建 / 运行资源及自己的输出目录；其它任务的残留目录不自动构成 Git、index、代码段或全仓验证资源冲突。

## 4. Git 发布租约

每个工作区的 index、暂存及本地提交只有一个写入者；独立工作树之间可以分别提交各自切片。更新 `main`、集成工作树提交及向远端发布时，整个仓库任一时刻只有一个发布者。主工作区直接施工的发布流程为：

1. 暂停本切片新增写入并记录完整文件清单；
2. 确认 index 和发布租约可用；
3. `fetch` 并核对 `main` 与 `origin/main`；远端前进时先按新基线复核，不自动整合；
4. 只暂存本切片，检查 staged 文件和 staged diff；
5. 按 `AGENTS.md` 第7.1节核对该产物的编译或静态检查证据；测试仅在该节要求的明确指令范围内运行，不因进入发布阶段自动补测；
6. 精确提交并普通推送 `origin main`；
7. 复核提交、远端关系、index 和剩余 dirty 后释放租约。

其它所有者的 WIP 不得带入提交。发布者应报告剩余 WIP，不得把“本切片 clean”说成“全工作区 clean”。HEAD 前进不自动作废其它独立 WIP，其所有者在发布前按新 HEAD 复核即可。

禁止 force、force-with-lease，以及未经用户明确要求的 rebase、cherry-pick。已获准工作树切片的普通 merge 仅按专项集成流程执行，其它 merge 仍须明确授权。提交、集成或推送失败时保留现场并报告，不扩大操作范围。

纯落后、本地无提交且 index clean 时，可以在保留已知非重叠 WIP的前提下 `fetch` 后 `ff-only` 更新；存在本地提交、路径重叠或语义冲突时不得自动整合。

## 5. 代码执行与验收资源

同一时刻最多两个活动代码切片。已登记复杂代码计划整体占用一个切片。默认用户直接代码切片须已明确用户授权、起点、文件 / 语义范围、不得改变的 ABI / 机器语义、验证方式和唯一所有者，且不触及公开 DTO / 服务合同、事务、所有权、生命周期、迁移 / 物理删除、工程 / 装配入口或共享验证资源。用户对一份具名切片明确确认“不需要计划、直接实施”时，该切片可以包含已经在本窗口完成设计闭合并写入切片声明的上述变化；它仍整体占用一个代码切片，共享 ABI / owner、工程登记、装配入口、删除集和验证资源不得再被第二切片并行写入。任一共同 ABI / owner、工程登记、装配入口、删除集、构建目录、数据库、端口、固定日志或外设资源只能有一个代码切片。

每次测试前记录实际项目的工作树路径、分支、HEAD、参与构建的未提交改动、工程配置、入口及资源所有者。允许在具名 Git 工作树内使用实际项目源码和正式工程验证；不得复制项目、导出源码或另建临时工程绕过冲突。若构建会消费另一切片未提交WIP，先与所有者协调实际项目的验证窗口；不能安全区分输入或取得一致基线时，只暂停受影响测试，等待相关改动形成安全提交。联合验证必须明确标注参与的改动，不得归为单一切片或纯提交基线的证据。main集成与远端发布仍由唯一租约串行完成，各工作区提交不得带入其它所有者WIP。

集成验收只消费已提交并推送的精确基线，不抢占执行智能体正在使用的构建、运行、数据库、外设或固定输出资源，也不把未提交 WIP作为验收输入。资源冲突时等待或返回具名阻断，不接管执行计划。

设计漂移时，执行智能体停止扩大受影响范围。只有现有修改位于计划范围内、可验证且不存在破损、假成功或半结构时，才可形成明确标为 WIP 的安全提交；否则保留现场并报告。设计修订发布后必须重新 S0。

## 6. 完成边界

本规则只证明代理按切片安全写入并串行发布，不证明规范、计划或代码能力完成。报告至少包含起点、变更文件、验证、提交 / 推送结果、剩余 dirty 和未覆盖范围。
