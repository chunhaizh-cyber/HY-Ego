# 单工作区切片并行写入与串行发布规则

日期：2026-07-30

状态：Codex 代理协作 / Git 工程规则；位于 `.codex/rules/`；不是项目机器规范

## 1. 适用边界

本规则适用于 Codex、智能体、任务窗口、文件所有权、Git 和验证资源，不定义项目机器事实、领域结构或代码语义。`规范/**` 适用于项目机器逻辑，不得定义、授予或撤销智能体权限、消息路由、写入所有权或 Git 发布权。

本项目不使用 Git worktree、Codex worktree、任务分支、长期执行分支或集成分支。全部智能体使用同一个仓库工作区和 `main`；允许多个边界明确、互不重叠的文件 / 语义切片同时写入，Git index、暂存、提交和推送仍严格串行。

固定技术形态为：

```text
一个仓库工作区
+ 一个 main 分支
+ 多个可并行的非重叠写入切片
+ 每个具体文件和语义切片一个所有者
+ 一个 Git 发布租约
+ 一个活动代码执行计划段
```

## 2. 身份与开工检查

写入前必须解析：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
git rev-list --left-right --count HEAD...origin/main
```

写入者必须声明目标、文件清单或可判定路径范围、语义切片、基线和所需验证，并核对当前全部 dirty / staged 文件的所有者。开工条件为：

1. 当前分支是 `main`，不是 detached HEAD。
2. 目标文件没有另一所有者正在写。
3. 目标语义没有被另一活动切片冻结或消费。
4. Git index clean；已取得发布租约者除外。
5. 共享构建目录、代码生成输出、格式化范围或运行环境没有被另一验证租约占用。

工作区整体 dirty 不再自动阻断写入。未知来源 dirty、无法划清所有权、同文件重叠、语义依赖冲突或共享输出冲突只停止受影响切片，不冻结无关切片。禁止自动 stash、reset、clean、checkout、覆盖或删除他人现场。

## 3. 写入切片与所有权

写入切片同时包含：

```text
文件边界
+ 语义边界
+ 所有者
+ 起点 HEAD
+ 输入事实版本
+ 验证与发布边界
```

仅“文件路径不同”还不足以证明可并行。下列情况属于语义冲突：

- 一方修改规范，另一方同时依据该规范生成偏差审计、详细设计或施工合同；
- 一方修改计划 / 设计，执行智能体正在消费其冻结版本；
- 提供者接口和消费者接线尚未冻结边界；
- 多方同时修改计划索引、规范目录、冲突清单、调用图总入口等同一聚合事实；
- 多方运行会改写同一工程、生成目录、缓存、数据库或运行期事实的工具。

不存在上述冲突且文件不重叠时，不同智能体、不同顶层任务和不同写类型可以并行。任一具体文件、结构、接口、合同、索引项和证据裁决切片始终只有一个写入者。

默认职责仍按 `AGENTS.md` 和 `.codex/rules/设计执行双窗口交互规则.md` 分配。交互智能体在用户直接指令下具有完整仓库写权，可以直接取得任一明确切片；这不允许覆盖另一智能体的活动切片。发生重叠时必须先让原所有者停写并明确交接，或由用户裁决。

## 4. Git 发布租约

并行写入不等于并行发布。任一时刻只有一个智能体可以持有 Git 发布租约并执行暂存、提交或推送。

发布流程固定为：

1. 暂停本切片新增写入，记录起点 HEAD 和完整文件清单。
2. 确认 Git index clean，并确认没有另一发布租约。
3. `fetch` 后核对 `main` 与 `origin/main`。若基线已前进，先按新 HEAD 复核本切片；不得自动 merge、rebase 或覆盖。
4. 只暂存本切片文件，检查 `git diff --cached --name-only` 和 staged diff。
5. 运行该产物要求的验证。
6. 精确提交并普通推送 `origin main`。
7. 确认 index clean、`main == origin/main` 后释放发布租约。

其它所有者的未暂存 WIP 可以原地保留，不得带入提交。发布者必须报告这些 WIP 仍存在，不得宣称整个工作区 clean。HEAD 前进不自动作废其它非重叠 WIP；其所有者在发布前必须刷新并复核新基线。

禁止 force、force-with-lease，以及未经用户明确要求的 merge、rebase、cherry-pick。提交 / 推送只证明本切片进入 `main`，不证明能力或项目阶段完成。

## 5. 验证资源租约

只读检查可以并行。下列操作需要独占相应资源：

- 会写同一构建输出目录的构建；
- 会修改源文件的格式化、代码生成或批量修复；
- 会写同一数据库、缓存、快照、日志固定文件或运行期端口的测试；
- 会改变同一外设或系统级运行状态的验证。

验证租约只锁定其实际资源，不锁定整个仓库。能够使用独立输出目录且不会改变项目事实的验证可以并行。

集成验收与回归智能体不得抢占执行智能体正在使用的构建、运行、数据库、外设、端口或固定输出资源，也不得验收执行智能体未提交的活动计划段。交互智能体应在目标提交已经进入 `main` 后再发送验收请求；资源冲突时集成验收返回 `INTEGRATION-ACCEPTANCE-BLOCKED`，不停止或接管执行计划。

## 6. 计划形成、登记与执行

计划智能体、计划支撑智能体、执行智能体、流程图与知识图谱维护智能体、能力证据目录维护智能体和集成验收与回归智能体仍按各自默认职责工作，但不再因无关 dirty 或无关写入者停工：

- 计划智能体可以形成其拥有的新设计包；计划索引仍由计划支撑智能体默认独占。
- 计划支撑智能体可以登记或修订其拥有的包；若其修改会改变执行智能体正在消费的设计事实，必须先停止受影响执行切片。
- 执行智能体同一时刻只能有一个活动代码计划段；它可以与不触碰计划白名单、冻结规范 / 设计 / 接口、代码调用边界和验证资源的文档或规则切片并行。
- 流程图与知识图谱维护智能体独占 `流程图/主程序可达调用关系/**` 中除 `能力证据目录/**` 外的当前调用事实，以及 `流程图/代码流程图/**`；可以按冻结基线拆出互不重叠的函数制图和调用聚合切片并行。
- 能力证据目录维护智能体独占 `流程图/主程序可达调用关系/能力证据目录/**`；只消费已经发布的函数身份、调用图、现状流程图、源码、规范与验证证据，不与尚未发布的制图批次混合基线。两类维护者不得共同修改同一聚合文件，Git 发布仍串行。
- 集成验收与回归智能体只消费交互智能体冻结的已提交 `main` 基线和验收矩阵，独占 `验证记录/集成验收/**`；所需构建 / 运行输入与目标提交一致且取得验证资源租约后才执行，完成后只发布专属证据。其 PASS、FAIL、DRIFT 或 BLOCKED 不修改计划索引、设计包、代码或执行记录。
- 交互智能体修改会影响活动执行计划段的规则、规范、设计或接口时，执行智能体必须暂停受影响切片并重新 S0；无关切片继续。

计划包通知、索引登记和执行消息只转移相应切片的默认所有权，不构成全仓写入锁。`PLAN-PACKAGE-READY-NOTICE` 后原计划智能体停止该包写入；计划支撑复核后接管该包，并在其原目标和登记范围内拥有补齐全部项目设计材料、建立计划内提供者设计包 / 施工计划及维护相应索引门禁的切片所有权。缺少流程图、详细设计、接口或必需函数不触发向计划智能体转交该切片。

全项目当前代码图谱和能力证据目录的维护所有权不随 `PLAN-PACKAGE-READY-NOTICE`、计划登记或执行消息转移。计划智能体和计划支撑智能体只读引用这些专属目录；需要在设计包内表达目标实现时写入其自身明确拥有的目标流程图、详细设计或知识图谱路径，不得并发改写共享当前事实。两个维护智能体发现当前事实与规范或设计不一致时只登记现状差异并通知交互智能体，不直接修改规范、设计、计划或索引。

## 7. DESIGN-DRIFT-WIP

施工后确认设计缺口时，受影响代码切片与设计切片存在真实语义依赖，仍使用安全断点闭环：

```text
执行智能体停止扩大范围并请求设计包修订
-> 计划支撑只读确认缺口
-> 执行智能体把白名单内改动形成可验证安全 DESIGN-DRIFT-WIP
-> 取得发布租约，精确提交并推送
-> 释放代码切片并进入 DESIGN-DRIFT-WAIT
-> 计划支撑修订设计包和相应索引项
-> 发布后通知执行智能体重新 S0
```

安全断点不得含语法破损、临时旁路、假成功、半结构或执行智能体自行补造的机器语义。无法形成安全断点时保留现场并报告 `DIRTY-BLOCKED`，不得提交破损 `main`。

## 8. 终止与恢复

| 终止码 | 条件 |
| --- | --- |
| `NO-CANDIDATE` | 当前没有可选择计划 |
| `USER-PAUSED` | 用户在相应任务明确暂停 |
| `DESIGN-DRIFT-WAIT` | 已发布安全断点，等待设计修订 |
| `DIRTY-BLOCKED` | dirty 来源未知、无法归属或无法安全收口 |
| `MAIN-DRIFT` | 分支、远端、计划段起点或提交关系不成立 |
| `SLICE-OCCUPIED` | 目标文件或语义切片已有所有者 |
| `RELEASE-OCCUPIED` | Git index 或发布租约正被其它智能体占用 |
| `VALIDATION-OCCUPIED` | 必需构建 / 运行资源正被其它验证占用 |
| `RULE-BLOCKED` | 智能体规则或消息路由冲突 |
| `ENVIRONMENT-BLOCKED` | 必要工具、权限或环境不可用 |

纯落后且本地没有提交、index clean 时，可以在保留已知非重叠 WIP的前提下 `fetch` 后 `ff-only` 更新；更新后各所有者必须复核自己的切片。存在本地提交、路径重叠或语义冲突时不得自动整合。

## 9. 旧 worktree 退出

1. 不创建新的 Git / Codex worktree。
2. 历史 worktree 只读核对后退出，不继续施工。
3. 历史材料中的 worktree、任务分支和集成分支只作历史证据。

## 10. 完成边界

本规则只证明代理可以在单工作区按切片并行写入，并按发布租约串行进入 `main`。它不证明任何项目规范、设计、计划或代码能力已经完成。
