# 单工作区串行执行与发布规则

日期：2026-07-25

状态：Codex 代理协作 / Git 工程规则；位于 `.codex/rules/`；不是项目机器规范

## 1. 目标

本项目不再使用 Git worktree、Codex worktree 模式、任务 worktree、长期执行 worktree 或集成 worktree。全部智能体读取同一个仓库工作区，全部写入和 Git 收口严格串行。

本规则只定义单工作区、唯一写入占用、活动计划段、Git 身份、提交、验证和发布条件。智能体类型、设计包所有权、S0 和消息路由继续由 `AGENTS.md` 与 `.codex/rules/设计执行双窗口交互规则.md` 定义；机器逻辑继续以 `规范/规范目录.md` 登记的正式规范为准。

固定技术形态为：

```text
一个仓库工作区
+ 一个 main 分支
+ 四个独立顶层智能体任务
+ 任一时刻一个写入智能体
+ 任一时刻一个活动执行计划段
+ 每次写入完成后验证、精确提交并非强制推送 origin/main
```

worktree、任务分支、长期执行分支和集成分支不再构成计划准入、执行身份、并行条件或完成证据。历史计划、设计、施工记录和聊天材料中的上述字段只保留历史意义；不得因此创建 worktree、切换任务分支或阻断与当前单工作区规则一致的施工。

## 2. 单工作区身份

当前唯一工作区必须由 Git 实际解析：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
git rev-list --left-right --count HEAD...origin/main
```

写入开始前必须同时满足：

1. 当前目录属于本仓库唯一主工作区。
2. 当前分支是 `main`，不得 detached HEAD。
3. `main == origin/main`，本地和远端分歧为 `0 0`。
4. worktree / index 均 clean；此处 `worktree` 仅指 Git 状态术语中的工作目录，不表示 Git 多工作树功能。
5. 当前没有另一智能体持有写入占用。
6. 当前没有另一活动执行计划段。

任一条件不成立时不得自动 stash、reset、clean、切分支、覆盖或删除现场；必须固定 HEAD、dirty 文件、当前所有者和来源并报告具名阻断。

## 3. 唯一写入占用

四智能体可以同时保持用户可见任务，但同一时刻只有一个智能体可以修改仓库：

| 写入范围 | 唯一允许智能体 |
| --- | --- |
| `AGENTS.md`、`.codex/rules/**`、`.codex/skills/**` | 交互智能体 |
| `PLAN-PACKAGE-READY-NOTICE` 前的新计划及其相关设计文件，不含 `计划/计划索引.md` | 计划智能体 |
| `计划/计划索引.md` 的新计划登记、状态与依赖维护 | 计划支撑智能体 |
| `PLAN-PACKAGE-READY-NOTICE` 后当前登记包内按需新建或修改的必要设计文件 | 计划支撑智能体 |
| 执行侧具名请求且计划支撑复核成立的既有设计包修订 | 配对计划支撑智能体 |
| 当前计划允许的代码、工程、自检、专属施工记录和验证记录 | 执行智能体 |

三个自动窗口的同文件排斥固定为：

| 文件类别 | 计划智能体 | 计划支撑智能体 | 执行智能体 |
| --- | --- | --- | --- |
| `计划/计划索引.md` | 禁止写 | 唯一写入者 | 禁止写 |
| 新计划及其新建 / 修订的相关设计文件 | 写入直到 `PLAN-PACKAGE-READY-NOTICE` | 通知前只读；接管登记后可在当前包原目标内按需新建 / 修改必要文件 | 禁止写 |
| 执行退回后由计划支撑接管的既有设计文件 | 禁止写 | 具名接管后唯一写入者 | 只读并等待修订 |
| 当前计划代码、工程、自检、专属施工 / 验证记录 | 禁止写 | 禁止写 | 唯一写入者 |
| 规范目录、冲突清单、知识图谱总入口等共享设计入口 | 仅在计划写入轮次内写 | 仅在计划支撑修订轮次内写 | 禁止写 |

计划智能体与计划支撑智能体可能在不同生命周期修改同一设计文件，但不得在同一写入轮次并发修改。`PLAN-PACKAGE-READY-NOTICE`、`PLAN-AVAILABLE-NOTICE`、执行具名终止回执和 `PLAN-WRITE-RELEASE` 共同形成串行写入权交接；接收消息不等于立即取得写权，仍须确认工作区 / index clean、`main == origin/main`、没有其它窗口 active 写入或活动计划段。

写入占用遵守：

1. 取得占用前刷新并重读 `origin/main`，确认单工作区 clean 且没有其它写入者。
2. 占用期间其它三个智能体只能只读，不得修改、暂存、提交或推送。
3. 当前智能体只修改自身权限和当前切片允许的文件。
4. 完成验证后只暂存本轮文件，检查 staged diff，提交并非强制推送 `origin/main`。
5. 推送成功且工作区 / index 恢复 clean 后释放占用。
6. 验证失败、远端前进、出现无关 dirty 文件或无法精确暂存时保持现场并停止，不得把占用转给其它智能体。

用户消息、通知和任务 active 状态不自动取得或释放写入占用。占用只由当前 Git 现场、本轮智能体权限、活动计划段和已完成的提交 / 推送事实共同证明。

## 4. 计划形成与执行串行关系

计划、计划支撑和执行智能体不并行写仓库：

```text
计划智能体取得写入占用
-> 形成一份完整设计包
-> 验证、提交并推送 origin/main
-> 工作区恢复 clean，释放占用
-> 向唯一登记计划支撑智能体发送 PLAN-PACKAGE-READY-NOTICE
-> 计划支撑智能体刷新 origin/main 并复核精确设计包
-> 取得写入占用，在当前计划原目标和登记范围内按需新建 / 修改必要设计文件
-> 若设计包变化，形成、验证、提交并推送新的精确版本 / blob
-> 把最终精确版本登记到计划索引
-> 验证、提交并推送 origin/main
-> 工作区恢复 clean，释放占用
-> 向来源计划智能体发送 PLAN-INDEX-RESULT
-> 向唯一登记执行智能体发送 PLAN-AVAILABLE-NOTICE
-> 执行智能体刷新 origin/main，自主选择计划并完成 S0
-> 取得写入占用并实施一个计划段
-> 验证、提交并推送 origin/main
-> 工作区恢复 clean，释放占用
-> 执行智能体继续门禁返回不保留活动计划段的具名终止码
-> 计划支撑智能体复核三个窗口均无写入占用
-> 向计划智能体发送 PLAN-WRITE-RELEASE
```

计划智能体发送 `PLAN-PACKAGE-READY-NOTICE` 后必须停写；计划支撑智能体完成工作区与占用复核后，取得该登记包的唯一写权，可以按需新建或修改必要设计文件，但不得独立发起无关新计划或扩大用户目标。登记成功时计划智能体继续只读等待，只有计划支撑智能体在执行 clean 终止后发送 `PLAN-WRITE-RELEASE`，计划智能体才能开始下一份设计包。登记拒绝时，`PLAN-INDEX-RESULT` 可以把同一设计包修正写入权退回计划智能体。计划支撑智能体只有在工作区 clean 且没有执行活动计划段占用时才能登记索引。执行智能体已有活动计划段时，计划智能体和计划支撑智能体不得写中央文件。

预冻结接口合同仍可消除业务依赖，但不再产生并行代码施工。提供者和消费者按计划索引、真实依赖、共享文件和接口所有权顺序串行实施。计划中的“可并行”“独立 worktree”“任务分支”“集成顺序”等旧技术描述不再授权并行写入；业务合同、允许 / 禁止文件、接口和验证要求仍然有效。

## 5. 执行智能体与活动计划段

本仓库固定使用以下永久执行智能体：

```text
窗口标题：执行当前计划任务
顶层任务：019f98fc-2b14-7030-a602-2005bc8f4552
工作目录：当前唯一主工作区
分支：main
```

执行智能体不创建或接管其它工作区、分支或执行通道。每个活动计划段必须冻结：

```text
计划路由、版本和 plan blob
计划索引 blob
计划段起点 main 提交
允许 / 禁止文件和结构所有权
实际接口或预冻结合同
验证矩阵
结果提交或计划允许的 WIP 断点提交
```

同一时刻只能有一个活动计划段。执行智能体完成 S0 PASS 后直接施工，不等待其它智能体接受。计划段完成或形成合法 WIP 时：

1. 运行计划规定的全部验证。
2. 只暂存本计划允许文件。
3. 提交正文包含 `Plan-Id`、`Plan-Blob`、`Plan-Segment-Start` 和 `Plan-Segment-Result`。
4. 非强制推送 `origin/main`。
5. 确认 `main == origin/main` 且工作区 / index clean。
6. 向配对计划支撑智能体发送 `EXECUTION-SUPPORT-NOTICE`。
7. 重读计划索引并运行继续门禁；存在下一候选时重新 S0，不把单计划完成当作执行任务完成。

执行计划中的“任务分支提交”“分支完成待集成”“集成分支”或“候选进入 main”旧措辞，在本规则生效后统一解释为“当前计划结果提交已经直接进入 main 并非强制推送”。不得为了满足旧技术措辞重新建立分支或 worktree。

## 6. 计划支撑与执行问题

执行智能体把选择、S0、完成、DRIFT、失败、WIP 和计划修订请求只发送给配对计划支撑智能体。计划支撑智能体先只读复核：

- 纯代码、环境、Git 或单工作区占用问题不取得设计包写权。
- 只有执行智能体明确请求设计包修订，且问题确属计划、规范、流程图、详细设计、知识图谱、接口合同、范围、依赖或验证合同缺口时，才可等待执行计划段 clean 收口后取得单工作区写入占用。
- 修订完成后验证、提交并推送 `origin/main`，释放占用，再发送 `PLAN-SUPPORT-NOTICE`。

执行智能体活动计划段仍 dirty 时，计划支撑智能体不得修改中央设计文件，即使修订请求成立。

## 7. 验证与发布

所有角色的正式产物直接进入 `main`，但不能降低验证等级：

1. 协作规则或设计包至少运行 `git diff --check` 和 `python .\tools\check_specs.py --strict`。
2. 代码执行运行目标计划规定的完整任务验证。
3. 涉及工程、入口、统一运行器、事务、恢复、并发或生产装配时，必须在同一计划段提交前完成计划规定的集成级验证；不再另建集成 worktree 延后补验。
4. 验证失败不得修改测试、删除验收项、复用旧二进制或发明接口收口。
5. 推送只允许普通非强制 `git push origin main`，禁止 force、force-with-lease、未经用户明确要求的 merge、rebase 和 cherry-pick。

提交 / 推送只证明本轮产物进入 `main`，不自动证明计划、能力或项目阶段完成。

## 8. 阻断与恢复

| 终止码 | 单工作区条件 |
| --- | --- |
| `NO-CANDIDATE` | 当前没有可选择计划 |
| `USER-PAUSED` | 用户在执行智能体自身任务明确暂停 |
| `DIRTY-BLOCKED` | 工作区 / index 存在无法归属并合法收口的改动 |
| `MAIN-DRIFT` | `main`、`origin/main`、计划段起点或当前提交关系不符合本规则 |
| `WRITE-OCCUPIED` | 另一智能体或活动计划段尚未释放写入占用 |
| `RULE-BLOCKED` | 智能体类型、消息路由或协作规则冲突 |
| `ENVIRONMENT-BLOCKED` | 必要工具、权限或环境不可用 |

远端前进时，当前智能体停止新增写入。工作区 clean 且本地没有未推送提交时，可以按 `fetch -> 0/0 或纯落后确认 -> ff-only` 更新；已有本地提交或 dirty state 时不得自动合并、变基或覆盖。

## 9. 旧 worktree 退出

本规则生效后：

1. 不再创建新的 Git worktree 或 Codex worktree 任务。
2. 现有额外 worktree 只读核对 dirty state 和未提交事实后退出；不得从中继续施工。
3. clean 且无独有未保存事实的额外 worktree 可以移除；远端历史分支不自动删除。
4. 既有执行顶层任务迁回当前唯一主工作区后，重新读取本规则、Git、计划索引和实际接口，再决定是否进入 S0。
5. 历史记录中的 worktree 路径、任务分支和集成分支只作历史证据。

## 10. 完成边界

本规则只证明单工作区、单写入占用和唯一执行代码写入者已经建立。它不证明任何计划已经实施、代码已经构建、候选已经验证或项目能力已经完成。
