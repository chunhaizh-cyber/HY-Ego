# 单工作区切片并行写入与串行发布规则

日期：2026-09-02
状态：代理协作 / Git 工程规则；不是项目机器规范

本规则只处理工作区、所有权、验证资源和 Git 发布。角色职责读取 `AGENTS.md`，计划生命周期读取 `设计执行双窗口交互规则.md`。

## 1. 固定形态

```text
一个仓库工作区
+ main 分支
+ 多个可并行的非重叠写入切片
+ 每个文件和语义切片一个所有者
+ 一个 Git 发布租约
+ 最多两个互不冲突的活动代码切片
```

不创建新的 Git / Codex worktree、任务分支、长期执行分支或集成分支。历史 worktree 规则只作兼容说明。

## 2. 开工检查

文件写入占用统一登记在 `D:\TEMP\再用文件\再用文件列表.md`。不再通过消息询问或确认文件是否正在使用。每个交互智能体必须在该文件中建立并只维护自己的模块；其本人以及由其分配的写入切片都由该模块登记。登记文件自身是共享协调入口，不把自身登记为待修改文件。登记文件不存在、不可读或无法安全更新时，停止新的文件写入。

首次写入任何目标文件前，交互智能体必须：

1. 重新读取整个登记文件，按“规范化仓库根绝对路径 + 仓库根相对完整路径”在全部模块中查找目标。仓库根以 `git rev-parse --show-toplevel` 为准；相对路径统一使用 `/`、按 Windows 大小写不敏感比较且不得包含 `.` 或 `..` 路径段。只写文件名或目录简称的登记无效；
2. 目标已有登记时，只有“同一交互智能体模块、同一修改切片、同一实际写入所有者”的原登记可以继续使用；其它任何重复都视为占用冲突，停止该文件写入并协调交接。不得用消息回复替代登记、覆盖登记或据此直接修改；
3. 目标没有登记时，先在自己的模块中加入仓库、待修改文件、修改切片、实际写入所有者和登记时间，再开始修改；
4. 多文件切片逐文件登记。新增文件登记目标路径，删除文件登记原路径，移动文件同时登记原路径和目标路径；
5. “修改完成”是指该文件已经完成所需验证并发布，或者已经安全收口、放弃或完成交接，不再需要保护现存 WIP；达到该条件后立即从自己的模块删除对应条目。未提交或仍待验证 / 发布的 WIP 不得提前删除登记；模块已无条目时保留模块标题即可；
6. 每次更新登记文件前重新读取最新内容，只改自己的模块；更新后立即读回确认自己的登记存在且其它模块完整保留。发现并发变化、内容被覆盖或无法确认时，本次登记无效，停止目标文件写入并基于最新内容重试。

登记只证明当前文件写入占用，不代替语义 / ABI / 资源冲突检查，也不代替正式计划、计划索引、S0、Git 或发布租约。目标未登记只表示当前没有已登记写入者，不表示可以覆盖已有 dirty、未提交 WIP 或来源不明的现场。

完成文件占用登记后，再确认：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
git rev-list --left-right --count HEAD...origin/main
```

同时声明目标、来源（已登记计划或用户直接代码切片）、文件 / 路径范围、语义范围、所有者、起点 HEAD 和所需验证。开工门禁只有：

1. 当前是 `main`，不是 detached HEAD；
2. 目标文件和语义没有其它写入所有者；
3. Git index 没有被另一发布者占用；
4. 所需构建、生成、数据库、外设或运行资源没有冲突。

工作区整体 dirty 不自动阻断。来源明确且不重叠的 WIP 原地保留；来源未知、所有权不明、同文件 / 同语义或共享输出冲突时只停止受影响切片。禁止自动 stash、reset、clean、checkout、覆盖或删除他人现场。

## 3. 并行与资源

路径不同不必然独立。下列情况视为冲突：

- 一方修改的规范、设计、计划或接口正被另一方冻结消费；
- 多方写同一聚合入口、索引、目录、接口合同或证据结论；
- 多方会改写同一构建目录、生成物、数据库、缓存、端口、日志固定文件或外设状态。

其它文件和语义都独立的切片可以并行。验证资源只锁定实际资源，不锁定整个仓库；只读检查通常可以并行。

仓库外临时验证根、逐任务隔离、完成后清理和残留分账统一服从 `规范/代码文件建立归属与模块命名规范.md` 第 5.1.2 节。验证者只占用自己的任务子目录；其它任务的残留目录不自动构成 Git、index、代码段或全仓验证资源冲突。

## 4. Git 发布租约

任一时刻只有一个发布者可以暂存、提交或推送。发布流程为：

1. 暂停本切片新增写入并记录完整文件清单；
2. 确认 index 和发布租约可用；
3. `fetch` 并核对 `main` 与 `origin/main`；远端前进时先按新基线复核，不自动整合；
4. 只暂存本切片，检查 staged 文件和 staged diff；
5. 运行该产物需要的验证；
6. 精确提交并普通推送 `origin main`；
7. 复核提交、远端关系、index 和剩余 dirty 后释放租约。

其它所有者的 WIP 不得带入提交。发布者应报告剩余 WIP，不得把“本切片 clean”说成“全工作区 clean”。HEAD 前进不自动作废其它独立 WIP，其所有者在发布前按新 HEAD 复核即可。

禁止 force、force-with-lease，以及未经用户明确要求的 merge、rebase、cherry-pick。提交或推送失败时保留现场并报告，不扩大操作范围。

纯落后、本地无提交且 index clean 时，可以在保留已知非重叠 WIP的前提下 `fetch` 后 `ff-only` 更新；存在本地提交、路径重叠或语义冲突时不得自动整合。

## 5. 代码执行与验收资源

同一时刻最多两个活动代码切片。已登记复杂代码计划整体占用一个切片；用户直接代码切片只有在已明确用户授权、起点、文件 / 语义范围、不得改变的 ABI / 机器语义、验证方式和唯一所有者，且不触及公开 DTO / 服务合同、事务、所有权、生命周期、迁移 / 物理删除、工程 / 装配入口或共享验证资源时才可占用另一个切片。任一共同 ABI / owner、工程登记、装配入口、删除集、构建目录、数据库、端口、固定日志或外设资源只能有一个代码切片。

两个切片各自在 S0 中以正式 HEAD 加自身允许改动验证；若常规构建会读取另一切片未提交 WIP，必须使用各自在 `D:\TEMP` 下的隔离验证根，或等待另一切片形成安全提交。暂存、提交和推送仍由唯一 Git 发布租约串行完成；发布者只冻结本切片新增写入，其他已声明且不冲突的切片可保留现场，但不得被带入 staged diff 或验证输入。

集成验收只消费已提交并推送的精确基线，不抢占执行智能体正在使用的构建、运行、数据库、外设或固定输出资源，也不把未提交 WIP作为验收输入。资源冲突时等待或返回具名阻断，不接管执行计划。

设计漂移时，执行智能体停止扩大受影响范围。只有现有修改位于计划范围内、可验证且不存在破损、假成功或半结构时，才可形成明确标为 WIP 的安全提交；否则保留现场并报告。设计修订发布后必须重新 S0。

## 6. 完成边界

本规则只证明代理按切片安全写入并串行发布，不证明规范、计划或代码能力完成。报告至少包含起点、变更文件、验证、提交 / 推送结果、剩余 dirty 和未覆盖范围。
