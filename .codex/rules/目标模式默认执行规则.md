# 目标模式默认执行规则

日期：2026-09-20
版本：v0.4
状态：代理协作 / 目标模式规则

本规则定义交互智能体在目标模式下维护长期目标、选择当前工作和衔接计划执行的默认方法。不定义项目机器语义、领域对象、公开 ABI、计划合同或代码完成事实。

## 1. 目标记录位置与权威分层

目标相关记录统一放在仓库根目录的`目标/`下：

```text
目标/
├─ 目标总账.md       # 目标身份、层级、状态和当前关联
├─ 当前目标.md       # 当前活动目标及下一动作
├─ 目标路线.md       # 上位目标、阶段目标和小目标关系
├─ 变更记录.md       # 目标状态和路线变化原因
├─ 已完成/            # 已满足自身完成条件的目标记录
├─ 已作废/            # 被明确撤销、替代或永久不再推进的目标记录
└─ 无法完成/          # 已确认在当前约束下无法完成的目标记录
```

根目录四个文件是当前目标导航入口；三个子目录是终态目标的归档位置。目标文件移动到终态目录后，原位置不得继续保留第二份现行权威副本。

每个目标记录至少包含：目标编号、名称、类型、版本、创建和更新时间、直接上位目标、直接下位目标、目标问题、优先级理由、目标结果、完成条件、明确排除范围、当前状态、关联计划或代码切片、设计承载方式、所有者、依赖、阻断、已验证证据、未验证范围、剩余风险、下一动作和转入条件。

目标记录只记录治理目标和可核对的证据引用，不复制机器语义、公开 ABI 或计划正文。

### 1.1 终态目录规则

- `已完成/`：仅存放自身完成条件和必要证据均满足的目标；代码提交、构建通过或局部验收通过不能单独触发移动。
- `已作废/`：目标被用户或正式治理明确撤销、替代或永久不再推进；必须记录作废原因、替代目标和影响范围。
- `无法完成/`：已确认在当前约束、权限、合同或资源条件下无法完成；必须记录失败事实、尝试范围、阻断原因和是否允许未来重新形成新目标。

目标暂停、阻断或转向但仍可能继续的目标留在根目录，不得提前移动到三个终态目录。目标恢复时以目标记录和变更记录为依据，不以聊天内容恢复。

## 2. 权威分层

目标模式的导航顺序为：

```text
目标账 / 路线账
-> 当前活动目标与阶段目标
-> 计划设计或直接代码切片声明
-> 计划/计划索引.md
-> 代码执行与集成验收
```

1. 目标账回答项目要达成什么、当前目标为什么优先、目标之间如何依赖和收束。
2. 计划索引只回答复杂代码计划的路径、版本、状态和具名依赖；它是执行队列，不是目标库存、路线图或项目总目标账。
3. 计划文件冻结机器合同、文件范围、实施顺序和验证边界；计划索引不得替代计划正文。
4. 代码、Git、施工记录和验收记录只证明实现与验证事实，不反向产生上位目标或路线方向。

目标账尚未建立或当前目标无法从正式材料确认时，不得用计划索引、历史计划、聊天回执或代码现状自行补造项目总目标；应报告目标路由缺口，并将可确认范围降为只读分析。

## 3. 目标模式默认职责

交互智能体在目标模式下必须明确：

- 上位目标、阶段目标和当前小目标；
- 当前小目标的完成条件；
- 当前小目标与上位目标的关系；
- 当前采用的计划、直接代码切片或设计工作包；
- 依赖、所有权、验证资源和已知阻断；
- 下一合法目标及其触发条件。

活动目标不是计划状态。计划`可执行`只表示计划可被执行者选择，不表示目标已开始、代码已完成、能力已接通或项目阶段已完成。

### 3.1 用户目标输入与确认门

当用户提出一个新的目标时，交互智能体必须先基于当前规范、目标路线、代码事实和已有目标，输出自己的目标理解，至少说明：

- 拟记录的目标名称、目标类型和目标边界；
- 上位目标及与现有目标的关系；
- 目标结果、完成条件和明确排除范围；
- 初步判断的目标路线、拆解方向和主要风险；
- 需要用户确认的仅限于目标含义、范围或优先级的实质问题。

在用户确认前：

1. 只允许进行必要的只读核对、比较和说明；
2. 不得创建、移动或修改目标文件；
3. 不得把聊天中的目标理解当作正式目标记录、计划授权或代码实施许可；
4. 可以指出用户目标与现行规范、当前事实或已有路线之间的冲突，但不得自行用目标文件掩盖冲突。

用户确认目标理解后，交互智能体才可以在`目标/`下创建或更新目标文件，并将确认后的目标作为活动目标推进。该确认只确认目标含义和范围，不自动确认缺失的机器语义、公开 ABI、计划合同、代码完成或验收结论。

### 3.2 确认后的自主推进

目标文件建立后，后续目标拆解、阶段排序、计划衔接、证据整理和普通工程选择由交互智能体依据现行规范、正式设计、计划规则、当前代码事实和 Git 规则自主裁决，不需要用户逐步确认。

只有出现以下情况时，才暂停受影响范围并请求用户进一步裁决：

1. 现行规范没有覆盖该机器语义、目标边界或裁决依据；
2. 两个或多个现行规范、正式设计或有效规则发生实质冲突；
3. 拟议目标、拆解、计划或实施动作违反现行规范；
4. 选择会实质改变用户已确认目标、公开合同、所有权、数据安全或破坏性范围，且现行规范无法裁决；
5. 目标需要新的权限、扩大授权或无法安全处理的破坏性动作。

普通文档组织、目标拆分粒度、计划承载方式、验证顺序和可逆工程选择，只要不触发上述条件，不得反复要求用户确认。

## 4. 目标分解与设计承载

目标分解负责目标层治理，不自动替代机器语义设计。目标模式按目标风险和变更性质选择以下三类路径：

### 3.1 规范或复杂机器语义目标

涉及正式规范、机器语义、公开 DTO / ABI、函数合同、事务、并发、幂等、所有权、生命周期、迁移、物理删除、发布未知、恢复或验证合同的目标，必须先完成设计闭合。

设计闭合至少要明确：目标、范围、当前事实、能力复用、函数 / DTO / 物理位置、数据来源、控制分支、事务、版本、所有权、生命周期、失败和撤销、发布与读回、验证矩阵及完成边界。

设计闭合不要求必须单独建立“详细设计”文件。设计内容可以：

- 保存在独立的正式详细设计中；
- 直接完整写入目标计划；
- 在规范、有效设计和计划中按权威顺序组合承载，但计划必须明确引用位置和缺口。

目标记录必须注明设计承载方式、具体路径或章节，以及是否存在未闭合设计缺口。计划或设计没有闭合机器语义时，不得标记为`可执行`，也不得让执行者临场补齐。

### 3.2 复杂代码目标但机器语义已冻结

若正式规范、现行接口和有效设计已经唯一冻结机器语义，复杂代码计划可以直接承载实施合同，不强制重复建立独立详细设计文件。计划仍必须具备可执行计划的完整范围、顺序、失败边界和验证矩阵。

### 3.3 边界明确的局部代码目标

只有同时满足`AGENTS.md`直接代码切片门禁，且不新增或改变公开 DTO / 服务合同、事务、所有权、生命周期、迁移 / 物理删除、工程 / 装配入口或共享验证资源时，才可以不建立计划或详细设计文件，改用目标记录加直接代码切片声明。目标记录不得把该例外扩展为复杂目标的通用免设计规则。

## 5. 默认推进顺序

1. 从目标账确认当前活动目标、阶段位置和优先级。
2. 将当前目标拆成最小可交付目标，判断属于设计、计划、执行、验收或治理修订。
3. 根据第 4 节选择设计承载方式；对复杂机器语义先闭合设计内容，对已冻结语义的复杂代码可由计划承载设计，对直接局部切片使用切片声明。
4. 计划完成创建侧验证并正式登记后，执行者才从计划索引选择`可执行`计划，并重新完成 S0。
5. 执行或验收回传后，交互智能体按目标完成条件复核结果，更新目标状态或路由至设计修订、下一目标或真实停工。
6. 更远下游目标只保留为路线输入，不得为了填充计划索引提前登记或执行。

目标模式不得因为存在可执行计划，就自动把该计划解释为项目最高优先级；优先级必须由目标账或用户本轮目标裁决。

## 6. 目标状态与结果边界

目标治理状态为：`候选`、`当前`、`阻断`、`暂停`、`转向`、`完成`。

- `候选`：属于路线但尚未取得当前执行位置；
- `当前`：正在推进且已有明确下一动作；
- `阻断`：存在具名且影响当前目标的权限、所有权、合同、资源或验证阻断；
- `暂停`：用户或正式治理决定暂不推进，不等于失败；
- `转向`：原目标被新目标取代或重新拆分，保留原因和影响范围；
- `完成`：自身完成条件和所需证据均满足。

计划发布、代码提交、构建通过或局部验收通过，不得单独把上位目标标为完成。

## 7. 禁止混用

目标模式不得：

1. 通过修改计划索引伪造上位目标、路线依赖或项目阶段完成；
2. 把路线输入、候选方向或长期愿景登记成`可执行`计划；
3. 用历史索引、归档计划或任务队列替代当前目标账；
4. 因计划索引为空就宣称项目没有目标；
5. 因存在一个`可执行`计划就跳过目标复核、所有权检查或 S0；
6. 用目标模式的排序意见改变已冻结计划的机器语义、公开 ABI、所有权、事务、生命周期或验证边界；
7. 把目标治理状态当作代码能力、业务事实或集成验收结论。

## 8. 缺口和停工

以下情况只停止受影响目标：上位目标或当前目标存在无法自行裁决的实质歧义；缺少完成条件；计划、接口、规范和代码出现会改变实现的漂移；所有权、Git 发布租约、共享验证资源或权限真实冲突；必需验证持续失败且无法安全归因或修复。

普通文档缺口、格式问题、无关 dirty 或可恢复工具波动不得自动改变上位目标状态。

## 9. 目标记录维护

1. 进入目标模式时，先读`目标/目标总账.md`、`目标/当前目标.md`和`目标/目标路线.md`，再读相关计划和 Git 事实。
2. 目标发生新增、拆分、合并、暂停、阻断、转向、完成、作废或无法完成时，必须同步更新目标记录和`目标/变更记录.md`。
3. 目标记录的状态更新必须保留变更前状态、变更后状态、日期、原因、证据和后续动作。
4. 目标记录与计划状态冲突时，目标记录负责目标路线，计划索引负责计划资格；不得互相冒充。
5. 当前目标只能有一个明确的主推进目标；可以存在候选目标和独立并行目标，但必须记录优先级、所有者和资源边界。

## 10. 与其它规则的关系

本规则不放宽`AGENTS.md`的角色、所有权、停工和发布要求，不放宽`.codex/rules/单工作区串行执行与发布规则.md`，也不改变`计划/计划索引.md`的计划状态定义。

目标账的正式路径、字段、写入所有者和版本方式尚未由本规则预设；建立或修改目标账须另行形成治理设计并按正式审查流程批准。
