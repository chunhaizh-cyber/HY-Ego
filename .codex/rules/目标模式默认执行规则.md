# 目标模式默认执行规则

日期：2026-09-20
版本：v0.6
状态：代理协作 / 目标模式规则

本规则定义交互智能体在目标模式下维护长期目标、选择当前工作和衔接计划执行的默认方法。不定义项目机器语义、领域对象、公开 ABI、计划合同或代码完成事实。

## 1. 目标记录位置与权威分层

目标相关记录统一放在仓库根目录的`目标/`下：

```text
目标/
├─ 活动/              # 每个非终态目标的唯一权威记录：GOAL-ID.md
├─ 目标总账.md        # 目标索引、简要状态和定位，不复制目标正文
├─ 当前目标.md        # 当前主目标 ID、事实截止、下一动作和推进健康信号
├─ 目标路线.md        # 仅保存目标之间的边和路线说明
├─ 变更记录.md        # 只追加目标账事务事件
├─ 已完成/            # 已满足自身完成条件的目标记录
├─ 已作废/            # 被明确撤销、替代或永久不再推进的目标记录
└─ 无法完成/          # 已确认在当前约束下无法完成的目标记录
```

`活动/GOAL-ID.md`是非终态目标的唯一权威记录。根目录四个文件是导航和事件入口，不得复制目标正文、完整证据或机器合同；三个终态目录保存从`活动/`移动出的目标唯一权威记录。目标进入终态目录后，`活动/`和根目录不得保留第二份现行权威副本。

每个目标记录至少包含：目标编号、名称、类型、单调递增的记录版本、创建和更新时间、直接上位目标、直接下位目标、目标问题、优先级理由、目标结果、完成条件、完成证据下限、明确排除范围、当前状态、关联计划或代码切片、设计承载方式、所有者、依赖、阻断、已验证证据、未验证范围、剩余风险、下一动作和转入条件。

每个活动目标还必须记录其状态证据上下文：状态事实截止（状态计算所依据的精确 Git HEAD）、关联计划身份、关联计划观察版本与 blob、最后实质进展提交或验收记录、阻断证据来源、阻断解除条件以及自动复核触发条件。未记录这些字段的目标不得据称其状态已按当前事实复核。

目标记录只记录治理目标和可核对的证据引用，不复制机器语义、公开 ABI 或计划正文。

### 1.1 终态目录规则

- `已完成/`：仅存放自身完成条件和必要证据均满足的目标；代码提交、构建通过或局部验收通过不能在未满足目标类型证据下限时单独触发移动。
- `已作废/`：目标被用户或正式治理明确撤销、替代或永久不再推进；必须记录作废原因、替代目标和影响范围。
- `无法完成/`：已确认在当前约束、权限、合同或资源条件下无法完成；必须记录失败事实、尝试范围、阻断原因和是否允许未来重新形成新目标。

目标暂停或阻断但仍可能继续的目标留在`活动/`，不得提前移动到三个终态目录。转向必须在同一状态事务中指向替代目标并处置为`作废`。目标恢复时以目标记录和变更记录为依据，不以聊天内容恢复。

### 1.2 目标账基础治理合同与迁移

本规则冻结目标账的基础治理合同：交互智能体默认拥有目标记录写入权；每个目标使用稳定目标编号和单调递增记录版本；目标状态、关系或当前主目标变化必须以同一目标账事务更新所有受影响的权威记录、导航记录和事件记录。除正式授权的其它角色外，任何智能体不得写入目标账。

现有把目标正文直接写在根目录`当前目标.md`的旧记录，只在迁移完成前作为过渡权威记录。首次对该目标作状态事务时，必须在同一事务内建立`活动/GOAL-ID.md`、将`当前目标.md`收缩为导航指针、同步更新总账、路线和变更记录；迁移本身不得改变目标含义、状态或证据结论。旧记录若把“当前小目标”等路线位置误填为类型，迁移时必须按第 6 节补录目标类型，但不得借此夸大完成证据。本规则的发布不自动改变任何既有目标状态。

新增字段或视图只有在改变目标身份、权威归属、生命周期、事务集合或证据含义时，才必须先形成额外治理设计；普通索引展示和不改变语义的字段整理可在本规则内处理。

## 2. 权威分层

目标模式的导航顺序为：

```text
目标账 / 路线账
-> 当前活动目标与阶段目标
-> 计划设计或直接代码切片声明
-> 计划/计划索引.md
-> 代码执行与集成验收
```

1. 目标账回答项目要达成什么、当前目标为什么优先、目标之间如何依赖和收束。
2. 计划索引只回答复杂代码计划的路径、版本、状态和具名依赖；它是执行队列，不是目标库存、路线图或项目总目标账。
3. 计划文件冻结机器合同、文件范围、实施顺序和验证边界；计划索引不得替代计划正文。
4. 代码、Git、施工记录和验收记录只证明实现与验证事实，不反向产生上位目标或路线方向；但它们可以证明既有目标的完成条件满足、阻断解除、证据过期或下一动作已不再合法，必须触发既有目标状态重算。

目标账尚未建立或当前目标无法从正式材料确认时，不得用计划索引、历史计划、聊天回执或代码现状自行补造项目总目标；应报告目标路由缺口，并将可确认范围降为只读分析。

## 3. 目标模式默认职责

交互智能体在目标模式下必须明确：

- 上位目标、阶段目标和当前小目标；
- 当前小目标的完成条件；
- 当前小目标与上位目标的关系；
- 当前采用的计划、直接代码切片或设计工作包；
- 依赖、所有权、验证资源和已知阻断；
- 下一合法目标及其触发条件。

活动目标不是计划状态。计划`可执行`只表示计划可被执行者选择，不表示目标已开始、代码已完成、能力已接通或项目阶段已完成。

### 3.1 用户目标输入与确认门

当用户提出一个新的目标时，交互智能体必须先基于当前规范、目标路线、代码事实和已有目标，输出自己的目标理解，至少说明：

- 拟记录的目标名称、目标类型和目标边界；
- 上位目标及与现有目标的关系；
- 目标结果、完成条件和明确排除范围；
- 初步判断的目标路线、拆解方向和主要风险；
- 需要用户确认的仅限于目标含义、范围或优先级的实质问题。

在用户确认前：

1. 只允许进行必要的只读核对、比较和说明；
2. 不得创建、移动或修改目标文件；
3. 不得把聊天中的目标理解当作正式目标记录、计划授权或代码实施许可；
4. 可以指出用户目标与现行规范、当前事实或已有路线之间的冲突，但不得自行用目标文件掩盖冲突。

用户确认目标理解后，交互智能体才可以在`目标/活动/GOAL-ID.md`下创建或更新目标文件，并将确认后的目标作为活动目标推进。该确认只确认目标含义和范围，不自动确认缺失的机器语义、公开 ABI、计划合同、代码完成或验收结论。

### 3.2 确认后的自主推进

目标文件建立后，后续目标拆解、阶段排序、计划衔接、证据整理和普通工程选择由交互智能体依据现行规范、正式设计、计划规则、当前代码事实和 Git 规则自主裁决，不需要用户逐步确认。

只有出现以下情况时，才暂停受影响范围并请求用户进一步裁决：

1. 现行规范没有覆盖该机器语义、目标边界或裁决依据；
2. 两个或多个现行规范、正式设计或有效规则发生实质冲突；
3. 拟议目标、拆解、计划或实施动作违反现行规范；
4. 选择会实质改变用户已确认目标、公开合同、所有权、数据安全或破坏性范围，且现行规范无法裁决；
5. 目标需要新的权限、扩大授权或无法安全处理的破坏性动作。

普通文档组织、目标拆分粒度、计划承载方式、验证顺序和可逆工程选择，只要不触发上述条件，不得反复要求用户确认。

### 3.3 单一可见窗口与最小充分模型路由

目标模式默认只保留一个用户可见的目标主窗口。主窗口持续维护目标理解、目标路线、当前优先级、所有权、依赖、证据和下一动作，并负责整合后台结果；不得为不同模型长期建立多个并列可见窗口。只有用户明确要求建立独立任务，或工作必须由用户在另一个任务中持续接管时，才可以创建新的用户可见任务。

主窗口默认使用`gpt-5.6-terra / medium`。每次派发必须选择满足目标风险、证据要求和裁决权限的最低充分模型与推理强度，不得因为模型更强就无条件升级，也不得为了节省额度把需要正式裁决的工作降给无权裁决的模型。默认路由为：

| 工作类型 | 默认模型与推理强度 | 结果权限 |
| --- | --- | --- |
| 目标协调、普通证据整合、路线维护 | `gpt-5.6-terra / medium` | 主窗口可依据正式材料作目标层裁决 |
| 机械性只读检索、清单整理、路径核对、格式检查 | `gpt-5.6-luna / low` | 只形成候选事实和证据，不作规范或目标裁决 |
| 边界明确的普通实施、诊断和验证 | `gpt-5.6-terra / medium` | 只在已分配切片和现行合同内实施或判断 |
| 目标含义审查、规范缺失或冲突、公开 ABI、事务、所有权、生命周期及高风险设计裁决 | `gpt-5.6-sol / high`；确有复杂度证据时用`xhigh` | 形成裁决输入；正式结论仍须服从项目权威顺序和角色权限 |
| 极难且质量优先、其他档位已出现具名失败的任务 | `gpt-5.6-sol / max` | 仅作为例外升级，不作为常态默认值 |

若运行环境不提供表中指定档位，主窗口必须记录实际替代项，并选择不低于该任务证据要求的最接近可用档位；模型不可用不能成为降低规范门禁、角色权限或验证要求的理由。

后台子智能体是主窗口内的临时有界执行者，不是新的目标所有者或长期窗口。每次派发至少冻结以下任务包：

- 目标编号、目标版本及其与当前小目标的关系；目标文件尚未获准建立时，明确标记为候选目标只读核对；
- 任务目的、预期产物和允许形成的结论层级；
- 必须读取的规范、规则、设计、计划和当前事实路径；
- 分支、起点 HEAD、允许文件或语义范围、禁止范围和唯一所有者；
- 依赖、共享 ABI、装配入口、验证资源和 Git 发布租约约束；
- 指定模型、推理强度、验证方法、回传证据和停止条件。

后台任务默认只读。只有任务包明确授予写入权，且满足`AGENTS.md`与单工作区发布规则的所有权和切片门禁时，才可以写入获准切片。并行时最多保留两个互不冲突的活动代码切片；共享同一公开 ABI、owner、工程或装配入口、迁移删除集、生产文件或验证资源的工作不得并行。后台子智能体不得自行扩大范围、改变目标状态或目标路线、修改任务包中的冻结合同、暂存、提交或推送；Git 发布始终由取得唯一发布租约的主窗口串行完成。

低成本模型的输出必须由主窗口按原始证据读回。出现证据不足、规范歧义或冲突、实际接口漂移、越出冻结合同、持续验证失败，或者结论会改变公开 ABI、事务、所有权、生命周期、数据安全和破坏性范围时，受影响任务停止并只上调一个必要档位。没有具名失败、歧义或风险升级依据时，不得让多个模型重复执行同一任务，也不得以投票方式替代权威材料和正式验证。

主窗口对委派结果负最终整合责任：核对任务包、原始证据、Git 基线、验证边界和角色权限后，才可以更新目标路线或接受下一动作。不同模型或子智能体之间不以隐藏推理、聊天摘要或口头结论交接权威状态，只通过目标编号、正式路径、精确 Git 基线、范围、证据和停止条件交接。

## 4. 目标分解与设计承载

目标分解负责目标层治理，不自动替代机器语义设计。目标模式按目标风险和变更性质选择以下三类路径：

### 4.1 规范或复杂机器语义目标

涉及正式规范、机器语义、公开 DTO / ABI、函数合同、事务、并发、幂等、所有权、生命周期、迁移、物理删除、发布未知、恢复或验证合同的目标，必须先完成设计闭合。

设计闭合至少要明确：目标、范围、当前事实、能力复用、函数 / DTO / 物理位置、数据来源、控制分支、事务、版本、所有权、生命周期、失败和撤销、发布与读回、验证矩阵及完成边界。

设计闭合不要求必须单独建立“详细设计”文件。设计内容可以：

- 保存在独立的正式详细设计中；
- 直接完整写入目标计划；
- 在规范、有效设计和计划中按权威顺序组合承载，但计划必须明确引用位置和缺口。

目标记录必须注明设计承载方式、具体路径或章节，以及是否存在未闭合设计缺口。计划或设计没有闭合机器语义时，不得标记为`可执行`，也不得让执行者临场补齐。

### 4.2 复杂代码目标但机器语义已冻结

若正式规范、现行接口和有效设计已经唯一冻结机器语义，复杂代码计划可以直接承载实施合同，不强制重复建立独立详细设计文件。计划仍必须具备可执行计划的完整范围、顺序、失败边界和验证矩阵。

### 4.3 边界明确的局部代码目标

只有同时满足`AGENTS.md`直接代码切片门禁，且不新增或改变公开 DTO / 服务合同、事务、所有权、生命周期、迁移 / 物理删除、工程 / 装配入口或共享验证资源时，才可以不建立计划或详细设计文件，改用目标记录加直接代码切片声明。目标记录不得把该例外扩展为复杂目标的通用免设计规则。

## 5. 默认推进顺序

1. 从目标账确认当前活动目标、阶段位置和优先级。
2. 将当前目标拆成最小可交付目标，判断属于设计、计划、执行、验收或治理修订。
3. 根据第 4 节选择设计承载方式；对复杂机器语义先闭合设计内容，对已冻结语义的复杂代码可由计划承载设计，对直接局部切片使用切片声明。
4. 计划完成创建侧验证并正式登记后，执行者才从计划索引选择`可执行`计划，并重新完成 S0。
5. 执行或验收回传后，交互智能体按目标完成条件复核结果，更新目标状态或路由至设计修订、下一目标或真实停工。
6. 更远下游目标只保留为路线输入，不得为了填充计划索引提前登记或执行。

目标模式不得因为存在可执行计划，就自动把该计划解释为项目最高优先级；优先级必须由目标账或用户本轮目标裁决。

## 6. 目标类型、状态与结果边界

目标类型与最低完成证据如下。每个目标必须在其权威记录中写明实际完成条件、证据路径和未验证边界；计划或正式规范规定更强证据时，以更强要求为准。

| 类型 | 最低完成证据 | 不得据此声称的范围 |
| --- | --- | --- |
| 设计目标 | 现行规范、有效设计或计划已闭合目标所需机器语义，并完成规定的治理审查 | 代码已实施、构建、运行或能力可用 |
| 代码实施目标 | 冻结范围内的代码和必需施工记录已按计划或直接切片要求发布，且规定的静态检查已完成 | 构建、启动、恢复、行为正确或集成能力 |
| 构建验证目标 | 指定基线、配置和范围的可复现构建已通过 | 运行、恢复、业务行为或集成能力 |
| 运行验证目标 | 指定程序入口、环境和行为验证已通过 | 跨进程恢复、未覆盖异常分支或集成能力 |
| 恢复验证目标 | 规定的重启、重放或持久恢复验证已通过 | 未覆盖的业务闭环或更广集成能力 |
| 集成能力目标 | 具名正式集成验收已按其现行清单通过 | 验收范围外的系统或业务目标 |
| 治理目标 | 规定的记录、规则、索引或审查产物已一致发布并完成所需检查 | 任意机器能力或代码行为 |

活动生命周期状态为：`候选`、`当前`、`阻断`、`暂停`、`转向`；终态结果为：`完成`、`作废`、`无法完成`。

- `候选`：属于路线但尚未取得当前执行位置；
- `当前`：正在推进且已有明确下一动作；
- `阻断`：存在具名且影响当前目标的权限、所有权、合同、资源或验证阻断；
- `暂停`：用户或正式治理决定暂不推进，不等于失败；
- `转向`：原目标被新目标取代或重新拆分，保留原因、替代目标和影响范围，并应进入其终态处置；
- `完成`：自身完成条件和目标类型规定的必要证据均满足；
- `作废`：被明确撤销、替代或永久不再推进；
- `无法完成`：已确认在当前约束下无法达成，且满足第 1.1 节记录要求。

合法状态迁移仅为：

```text
候选 -> 当前 / 作废
当前 -> 阻断 / 暂停 / 转向 / 完成
阻断 -> 当前 / 暂停 / 转向 / 无法完成
暂停 -> 当前 / 作废
转向 -> 作废
```

终态目标不在原记录上重新打开。若未来需要继续，应建立新的目标身份，并在其来源字段引用原目标。计划发布、代码提交、构建通过或局部验收通过，只能作为与目标类型和完成条件匹配的证据，不得单独把上位目标标为完成。

## 7. 禁止混用

目标模式不得：

1. 通过修改计划索引伪造上位目标、路线依赖或项目阶段完成；
2. 把路线输入、候选方向或长期愿景登记成`可执行`计划；
3. 用历史索引、归档计划或任务队列替代当前目标账；
4. 因计划索引为空就宣称项目没有目标；
5. 因存在一个`可执行`计划就跳过目标复核、所有权检查或 S0；
6. 用目标模式的排序意见改变已冻结计划的机器语义、公开 ABI、所有权、事务、生命周期或验证边界；
7. 把目标治理状态当作代码能力、业务事实或集成验收结论。

## 8. 缺口和停工

以下情况只停止受影响目标：上位目标或当前目标存在无法自行裁决的实质歧义；缺少完成条件；计划、接口、规范和代码出现会改变实现的漂移；所有权、Git 发布租约、共享验证资源或权限真实冲突；必需验证持续失败且无法安全归因或修复。

普通文档缺口、格式问题、无关 dirty 或可恢复工具波动不得自动改变上位目标状态。

### 8.1 事实刷新、推进健康与自动恢复

`正常`、`等待具名事件`、`停滞`和`证据过期`是依据目标记录与当前正式事实计算出的推进健康信号，不是目标生命周期状态，也不是后台定时器。`停滞`表示目标仍有效且不存在真实停工条件，但没有可推进的已记录下一动作，或目标记录已经落后于当前事实；它不等于失败、暂停或无法完成。

每次进入目标模式，以及收到计划或计划索引变更、施工或验收回传、相关代码提交或推送、所有权或发布租约释放、构建或验收记录发布、用户“同步”“继续”或“检查进展”事件时，交互智能体必须对受影响目标进行事实刷新：

1. 读取当前`origin/main`事实截止；远端可达时先刷新远端引用，不可达时记录只能以本地远端引用为准；
2. 读取目标权威记录、目标总账、当前目标和目标路线；
3. 读取关联计划、计划索引及最新相关施工、验证和验收事实；
4. 比较目标记录的状态事实截止、关联计划观察版本 / blob 与当前事实；
5. 重新计算目标类型完成条件、阻断、暂停、转向、推进健康信号和唯一合法下一动作。

目标账状态事务在发布前必须再次完成上述刷新。若状态事实截止已经前进、关联计划位置或版本已变、所有权已变化，或新增证据会改变状态或下一动作，不得按旧现场原样提交。

当目标含义、完成条件和权限边界均未改变，具名阻断已由正式事实机械确认解除，不涉及新的机器语义、公开合同、权限扩大或破坏性范围，且存在唯一合法下一动作时，交互智能体应自动恢复：将目标从`阻断`恢复为`当前`，或直接裁决为`完成`；更新事实截止、解除证据和下一动作；写入目标账状态事务后继续合法的设计、计划、代码或验收步骤，不等待用户再次输入“继续”。

用户明确`暂停`、规范缺失或冲突、目标含义或优先级变化、需要新权限或破坏性动作、存在多个同等合法但方向不同的路线，以及无法安全归因的持续验证失败，不得自动恢复，仍按本规则和`AGENTS.md`停止受影响范围并请求裁决。

### 8.2 目标账状态事务

一次目标状态、关系、当前主目标或终态处置变化必须形成一个不可拆分的目标账事务。事务至少包含目标唯一权威记录、`目标总账.md`、`当前目标.md`、`变更记录.md`，并在关系变化时包含`目标路线.md`，在终态处置时包含从`活动/`到相应终态目录的移动。未受影响的导航文件不得为了凑齐事务而复制或伪造状态。

同一事务必须在一个提交中完成，使用同一状态事实截止，并在`变更记录.md`中记录变更前后状态、日期、原因、事实截止、证据、未验证范围和后续动作。任一受影响文件无法更新、移动或核对时，不得发布部分目标状态，也不得以多份并行权威替代失败记录。

## 9. 目标记录维护

1. 进入目标模式时，先读`目标/目标总账.md`、`目标/当前目标.md`、`目标/目标路线.md`和当前主目标唯一权威记录，再按第 8.1 节读取相关计划和 Git 事实。
2. 新增目标在用户确认后建立为`活动/GOAL-ID.md`；`目标总账.md`只登记其索引和简要状态，`当前目标.md`只登记当前主目标 ID、事实截止、下一动作和健康信号，`目标路线.md`只维护边，`变更记录.md`只追加事件。
3. 目标发生新增、拆分、合并、暂停、阻断、转向、完成、作废或无法完成时，必须按第 8.2 节完成目标账状态事务。
4. 目标记录与计划状态冲突时，目标记录负责目标路线和完成条件，计划索引负责计划资格；不得互相冒充。计划索引为空只说明没有当前可选的复杂代码计划，目标模式必须转入合法的设计、计划形成、验收或具名等待动作，不得因此把有效目标判为停滞。
5. 当前目标只能有一个明确的主推进目标；可以存在候选目标和独立并行目标，但必须记录优先级、所有者和资源边界。

## 10. 与其它规则的关系

本规则不放宽`AGENTS.md`的角色、所有权、停工和发布要求，不放宽`.codex/rules/单工作区串行执行与发布规则.md`，也不改变`计划/计划索引.md`的计划状态定义。

本规则已经冻结目标账的基础路径、最低字段、默认写入所有者、版本、事实截止、状态事务和终态移动合同。它不预设项目机器语义、计划合同或代码完成事实；改变目标账基础合同的复杂扩展仍须形成治理设计并按正式审查流程批准。
