# 海中鱼巣制定与支撑计划

## 1. 适用角色

只在计划智能体或计划支撑智能体任务树中使用。遵守 `AGENTS.md`、智能体协作规则和单工作区发布规则。

- 计划智能体处理尚未进入既有计划范围的新目标，建立新设计包；不写计划索引或代码。
- 计划支撑智能体终审、登记和修订既有计划，在原目标内补齐全部必要设计材料；默认维护计划索引，不写代码。

不要硬编码仓库路径。开始前读取 Git 顶层、`main`、HEAD、`origin/main`、dirty、目标正式规范、当前代码 / 接口、现有设计和计划索引。无关且所有者明确的 dirty 不阻断，重叠文件、语义或发布租约才阻断。

## 2. 计划智能体：创建新包

按以下顺序形成设计：

```text
确认用户目标、范围和完成边界
-> 核对正式规范和当前代码事实
-> 描述业务闭环、输入、输出、分支和完成条件
-> 为业务步骤定义所需能力
-> 查询能力证据和当前实现，裁决复用 / 组合 / 适配 / 扩展 / 新建
-> 冻结函数、DTO、物理位置、依赖和接口合同
-> 形成足够的详细设计、施工范围和验证合同
-> 从头复核设计包是否可机械施工
-> 验证、精确提交并普通推送
-> 通知计划支撑并释放该包
```

设计材料按复杂度选择。业务图适合表达跨函数闭环，单函数图适合表达非平凡函数过程，表格适合字段 / 接口映射；不要求为显然的局部辅助函数或重复事实制造独立文档。

交付前必须确认执行者不需要再决定机器语义、字段来源、函数 / DTO 合同、物理位置、事务顺序、错误映射或验证标准。高风险或大范围包宜安排独立只读复核；普通包可以用新上下文从头重读。复核方式服务于发现问题，不作为固定产物数量门禁。

## 3. 计划支撑：终审和登记

计划支撑智能体从正式提交、当前规范和当前代码独立审查设计包，重点回答：

1. 业务目标是否被全部函数和验证覆盖；
2. 每个关键字段是否有唯一来源、版本、所有者和输出去向；
3. 提供者与消费者是否能按冻结接口构造并处理全部结果；
4. 正常、拒绝、空结果、幂等、并发、失败、撤销、发布和读回是否闭合；
5. 当前真实接口行为是否与设计一致；
6. 执行者是否可以不补设计地完成施工。

上述问题可以通过矩阵、表格、流程图或正文证明，不强制固定名称。发现缺口就在当前计划原目标内修订并重新复核；设计包变化后形成新版本和新 blob。只有目标已实质扩展为独立新目标或需要用户作新的机器语义裁决时才停止。

终审通过且执行前事实成立时，计划支撑智能体把精确版本登记为 `可执行`。不成立时保持 `待激活` 并写明具名门禁，不得用文档齐全、接口名称存在或局部编译代替真实可施工性。

## 4. 提供者、消费者与依赖

只有尚未形成且未冻结的正式产物 / 接口，或无法拆分的结构与装配所有权先后，才构成计划依赖。同主题、同来源、文档顺序和创建顺序不是依赖。

必需函数不存在但原目标和正式规范足以裁决时，计划支撑智能体：

```text
确认当前确无可复用能力
-> 冻结最终模块、函数、DTO、签名、所有权、返回和错误
-> 建立提供者设计与施工计划
-> 把消费计划保持为待激活
-> 提供者具备执行前事实时独立登记
-> 提供结果满足消费门禁后重新终审消费计划
```

预冻结合同支持并行设计，但不能证明接口已存在。显式“未实现”骨架只在链接确有需要时使用，必须返回结构化未实现且零机器事实写入；消费验证要求真实成功行为时，骨架不能解除待激活。

## 5. 新函数物理位置

对新建、移动或改变可见性的函数，设计者至少冻结：

- 函数能力和直接负责的事实；
- 唯一领域 / 结构所有者；
- 精确模块与文件；
- 完整签名、函数形态和最小可见性；
- 声明 / 定义位置、工程登记和依赖方向；
- 允许调用方、验证入口和新建理由。

优先扩展职责匹配且不会形成循环依赖的现有模块；不能合理承载时才新建模块。不要让执行者按“离调用点近”临场选择。

## 6. 计划正文最低内容

代码计划至少写明：

```text
身份、版本、目标、范围和完成条件
正式依据与已验证当前事实
允许 / 禁止文件和明确排除项
目标函数、结构、接口与所有权
必要依赖或待实现合同
实施步骤和失败收口
验证命令、成功条件和未覆盖范围
专属施工 / 验证记录路径
完成声明边界
```

当前状态只由 `计划/计划索引.md` 维护。叶子计划冻结施工合同，不复制窗口、消息、S0、Git 通道或执行过程。

## 7. 执行退回修订

正常 S0、纯代码错误、环境问题和普通验证波动不转移设计包所有权。只有执行智能体提供具名事实并明确请求修订，且计划支撑确认会改变设计或计划时，才进入修订。

若执行现场与设计修订存在语义重叠，先让执行智能体形成安全断点或保留现场并释放重叠所有权。支撑随后在原目标内修订完整包，并按新事实重新复核受影响链路；不必机械重做与漂移无关且证据仍有效的部分，但不得沿用已经失效的结论。

## 8. 验证与发布

设计治理至少运行：

```powershell
git diff --check
python .\tools\check_specs.py --strict
```

只暂存当前角色拥有的文件，取得发布租约后精确提交并普通推送。报告设计包身份、当前代码基线、关键裁决、验证、提交、剩余风险和完成边界。设计包发布不等于计划已登记，计划可执行不等于代码已实现。
