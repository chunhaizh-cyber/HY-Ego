# 海中鱼巣根因追踪

## 角色与入口

严格服从仓库根目录 `AGENTS.md`。用 Git 顶层、复杂计划索引或当前直接代码切片声明，以及当前唯一工作区的 Git 事实解析仓库、分支、提交和角色，不硬编码路径或分支。把每个弹窗、逻辑错误日志、验证失败、异常状态或崩溃邻近现象按只读证据链追踪：

```text
现象
-> 直接生成点
-> 入口拒绝 / 服务边界 / 写入结构
-> 上游输入与生命周期
-> 违反规范或计划的第一个点
-> 最小修复方向与复验合同
```

不得用隐藏弹窗、降级日志、吞掉失败或静默回退解释为已解决。

## 专用步骤

1. 解析 Git 顶层并读取 `AGENTS.md`。
2. 按现象限载读取：

```text
计划/计划索引.md
规范/规范目录.md
相关正式规范、有效设计、现行计划、目标代码文件头部规则
```

3. 核对当前提交、dirty state 和现象证据的来源时间；不同运行或不同提交的证据必须分账。
4. 按层搜索并先列同层候选，再向下钻取：

```text
L0 现象层：弹窗、日志、退出码、验收输出、用户可见异常。
L1 直接生成层：弹窗 / 日志 / 验收失败调用点。
L2 本地事实层：入口拒绝、服务写入、仓库返回、结构读取。
L3 上游请求层：调用者、输入包、任务 / 方法 / 动态 / 状态来源。
L4 生命周期层：节点、关系、状态、任务、方法、动作、因果的创建和失效顺序。
L5 规范契约层：AGENTS、规则总纲、详细设计、计划切片。
```

5. 使用 `rg`、范围受限的文件读取、路径限定 diff 和现有日志；日志与弹窗只证明症状，不是机器事实。怀疑入口拒绝过严时，先证明上游状态有效，不建议直接放宽。
6. 找到“第一个违反现行合同的点”，区分已证实根因、候选根因和仍需复现的假设；写出预期行为、最小修复方向及原现象复验条件。

## 输出

```text
当前现象
直接生成点
当前层级
同层候选
选中分支
已确认事实
已排除
第一违反点
候选根因 / 已证实根因
最小修复方向
设计需补齐的合同
独立执行任务的复验矩阵
禁止宣称
```

需要持久化时，诊断阶段仍保持只读。诊断结束后的独立写步骤中，交互智能体可按用户直接指令取得明确切片，直接修订规则、规范、设计、计划、索引或代码；自动计划、执行和支撑窗口仍按各自默认消息与所有权工作。进入写阶段前固定 HEAD、dirty 所有者、文件和语义范围；只停止同文件 / 同语义或验证资源冲突的切片，无关写入可以继续。修复后按产物类型完成验证和串行发布，不得恢复整文件覆盖用户意图，也不得用诊断结论伪造机器事实。

## 停止边界

- 本技能的诊断阶段不得修改任何项目文件或 Git 状态，不得构建或运行程序，也不得形成活动计划段；用户要求落盘或修复时，在诊断结束后退出本技能并进入独立交互写阶段。
- 不绕过领域服务，不建议先写错误结构再靠后续校验修复。
- 没有正式设计和已列入计划索引的复杂计划时，不得把新功能修复方向交给代码切片所有者；唯一例外是完全符合 `AGENTS.md` 直接代码切片门禁的用户明确局部修复。交互智能体若直接实现新功能，必须先自行补齐并登记正式规范、设计和计划依据。
- 不从一次根因定位声明旧能力迁移、系统完成或外设生产接通。
