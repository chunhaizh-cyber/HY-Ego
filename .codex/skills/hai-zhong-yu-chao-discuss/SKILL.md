# 海中鱼巣讨论

## 目标与入口

遵守当前仓库 `AGENTS.md`。帮助用户对本轮问题形成有依据、可修正的判断；专家审查只是其中一种用途。

先识别本轮是在澄清概念、探索可行性、比较方案，还是审查已有提议。通常根据上下文判断；只有缺失信息会实质改变目标或结论且无法核实时，才提出最小问题。保留原活动目标，但不因历史角色、旧回执或索引中存在计划而偏离本轮问题、恢复施工。

## 讨论方法

按问题深度使用下列方法，不要求每次逐项输出：

1. 明确要解决的问题、目标、约束与判断标准；区分用户的目标和用户提出的实现建议，不预先把“最小改动”当成最优标准。
2. 拆出决定结论的事实、定义、假设和前提。先准确理解原观点，再检验推论；观点成立时明确认可并说明边界，不为挑剔而制造反对意见。
3. 读取足以决定判断的证据。区分规范事实、代码事实、计划事实、用户给定、假设、合理推断与待核；关键结论给出可定位依据，不要求每段重复标签。
4. 有真实取舍时，比较候选方案、保留现状或复用已有能力的收益、代价、风险和适用条件；不机械凑足方案数量。探索阶段可以保留多个方向，证据不足时不强行选定唯一实现。
5. 对关键结论检查有依据的反例、替代解释和失效条件，说明什么新证据会改变推荐。新证据推翻旧前提时，明确修正原判断及受影响结论，不以保持说法一致代替事实核对。
6. 收敛为成立、条件成立、不成立或证据不足，并解释决定性原因。仍有分歧时，说明最小待核事实、验证办法或需用户裁决的选择及其影响，不把一般工程判断推给用户。

## 按问题读取证据

需要仓库事实时用 Git 顶层解析实际路径，不硬编码仓库或分支。读取范围由本轮问题决定：

| 问题 | 所需依据 |
| --- | --- |
| 概念、定义或规范合理性 | 相关定义、规范目录登记的现行条款及其依据；有用户给定的假设材料时注明分析范围 |
| 方案可行性或取舍 | 目标、评价标准、直接相关约束和已有能力证据；设计只读取影响比较的部分 |
| 当前实现或实现差异 | 当前源码、入口、调用点与读回结构；按需要使用[当前事实扫描](../hai-zhong-yu-chao-current-fact-scan/SKILL.md)，核对基线和相关 WIP，避免将设计当成实现 |
| 施工资格或迁移就绪 | 计划与索引、有效设计、真实接口、所有权和验证资源；交由[实施前审查](../hai-zhong-yu-chao-pre-implementation-review/SKILL.md)完成对应只读门禁 |

只在问题需要完整论证链时使用[数字生命推理](../hai-zhong-digital-life-reasoning/SKILL.md)；需要理论或规范草稿时使用[理论技能](../hai-zhong-yu-chao-theory/SKILL.md)。不为普通讨论默认加载整套技能或扫描全部执行队列。

## 规范与实施边界

- 现行规范约束实施，也可以成为讨论对象。讨论其合理性时分析目的、条件、代价和替代方案，明确建议与现行条款的差异；修改仍须按 `AGENTS.md` 审查批准，建议不自动生效。
- 涉及结构或服务时，才按需映射身份、承载、写入方、读取方、生命周期、事务与验证；检查重复权威、旁路入口和迁移残留，不能仅以旧函数或旧文件为迁移单位。
- 结构、合同或公开 ABI 不完整时，可以在标明假设的前提下继续讨论概念可行性和候选方案，不得声称“可以直接实施”，也不得临场冻结缺失的 DTO、持久编码或迁移顺序。超出现行依据的实质裁决按 `AGENTS.md` 交用户决定。
- 分清逻辑可行、规范允许、设计完整、代码已实现与能力已验证。日志、界面、线程状态及聊天不替代机器事实；局部证据不支持整体闭环或系统完成声明。

## 输出与结束

默认先给直接判断，再说明必要依据、取舍、成立条件和剩余问题。简单问题用短答；多方案比较用表格；复杂问题才展开结构映射、反例和验证路径。避免为填栏目重复内容。

核心问题已回答、决定性分歧已定位、未知项对结论的影响已说明，即可结束本轮讨论；不要求每次生成计划、建立正式产物或冻结实现。

本技能只读，不修改文件或 Git 状态。确认观点不自动授权写入；用户明确要求落实已讨论的修改时，结束只读阶段，按当前角色、授权范围和所有权规则进入独立写步骤，沿用已有明确授权。不得把讨论结果当成已生效的规范、计划或施工许可。
