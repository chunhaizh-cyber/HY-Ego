# 代码编写与既有函数复用知识

本文给出从目标业务到既有函数复用或新代码建立的工程判断方法。它不授权实施，也不替代目标计划允许的文件范围和公开合同。

## 1. 先固定目标，不从函数名倒推需求

开始查找函数前，先写清本次调用需要的合同：

```text
业务目的
-> 输入参数及其权威来源
-> 成功结果和非成功结果
-> 读取或写入的事实
-> 副作用、事务和并发边界
-> 生命周期和允许调用阶段
-> 合法调用者与依赖方向
```

如果参数来源、结果形状或事实所有者尚未确定，应先形成具名接口或设计缺口。不能先选一个名字相似的函数，再反向修改业务需求迎合它。

## 2. 查找顺序

按以下顺序查找并互证：

1. 在 `知识库/函数用途/` 查询稳定函数身份或用途卡。
2. 在 `流程图/主程序可达调用关系/能力证据目录/` 查询候选能力和提供函数。
3. 在 `流程图/主程序可达调用关系/` 查询函数身份、调用者、被调者和可达性。
4. 有现状流程图时，在 `流程图/代码流程图/` 查执行分支和逐行映射；没有图不等于函数不存在。
5. 读取目标函数的当前源码、声明、直接调用点和相关 DTO。
6. 读取 `规范/规范目录.md` 登记的直接相关规范、有效详细设计和现行计划。
7. 读取已发布施工、检查或集成验收记录，只把它们作为具名验证证据。

知识条目绑定的提交早于当前代码时，必须先对目标函数、合同、直接调用者和直接被调者做差异核对。未发布的流程图、记录或源码 WIP 不能进入正式复用结论。

## 3. 每次复用必须回答的十个问题

| 问题 | 最低证据 |
| --- | --- |
| 这个函数的稳定身份是什么 | 完整签名、模块、源文件和定义位置 |
| 它实际负责什么 | 当前源码主路径、调用图和正式依据 |
| 它明确不负责什么 | 公开边界、错误分支和上层/下层所有权 |
| 每个参数从哪里来 | 调用点、DTO 字段和权威事实来源 |
| 成功返回什么 | 结果类型、成功载荷和读回材料 |
| 非成功怎样表达 | 逻辑拒绝、资源失败、内部错误和发布未知 |
| 读取或修改哪些状态 | owner、仓库、服务、缓存及事实代次 |
| 有哪些副作用 | 写入、线程、锁、日志、外部资源和发布动作 |
| 在什么生命周期可调用 | 构造、运行、停止、恢复、退出及重复调用规则 |
| 谁可以调用 | 模块可见性、服务边界、依赖方向和合法消费者 |

任一关键问题缺少证据时，只能登记“候选待复核”或具名缺口，不能声明直接复用已经成立。

### 3.1 先区分对外、内部和非服务函数

`public`只说明 C++ 访问性，不自动说明函数是对外服务。复用前必须给函数标出以下一种边界类别：

```text
对外服务函数：正式允许消费者调用的数据 / 业务操作
内部服务函数：只实现公开操作的校验、映射、定位、提交或读回 helper
服务取得函数：只返回上下文 / 聚合持有的同实例服务
服务装配函数：只建立、绑定或持有 owner / 服务 / 聚合
非服务函数：入口、编排、谓词、纯值转换、线程或信号辅助
```

上层只能把“对外服务函数”列入基础数据服务接口清单。内部函数不得跨层复用；取得函数只提供访问路径；装配函数只建立生命周期；非服务函数不能因返回了服务结果就冒充服务接口。若一个公开函数只供装配或特定 provider 使用，知识卡还必须写明受限调用语境。

### 3.2 已落地示例：按结果规格召回方法

若目标需要“按预期结果寻找现有方法”，当前知识首先定位到`L2方法结构服务::按结果规格读取当前方法候选`，但复用结论不能停在函数名或候选命中：

```text
固定当前结果规格键和非零扫描/候选预算
-> 经普通应用的L2方法结构聚合取得同一服务
-> 调用按结果规格读取当前方法候选
-> 对每个候选身份调用读取普通方法，回读同截止完整方法事实
-> 由任务领域核对条件、参数、禁止项、适用范围、动作入口和授权
-> 决定选择、拒绝或证据不足
```

这里可直接复用的是“有界召回”和“完整方法读回”两项DATA能力；候选优劣、任务冻结、动作执行和结果结算仍属于上层职责。不得直接依赖`L2方法结构内部`的索引负载、写集或读回helper，也不得把候选列表写成已选择或可执行方法。当前函数证据见[函数用途/L2方法结构服务/README.md](函数用途/L2方法结构服务/README.md)。

### 3.3 已落地示例：按世界事实召回概念支持

若目标需要“查询一个已发布世界事实支持哪些当前概念”，当前知识定位到`L2概念结构服务::按世界事实读取概念支持关系组`，但支持关系命中仍只是候选证据：

```text
固定闭合强类型世界事实引用和非零扫描/数量预算
-> 经普通应用的L2概念结构聚合取得同一概念服务
-> 调用按世界事实读取概念支持关系组
-> 对每项关系调用读取普通概念，回读本体根、定义和治理生命周期
-> 由DATA外业务结合本次目标、语境和授权判断采用、并列保留或拒绝
```

这里可直接复用的是“有界支持关系召回”和“完整普通概念读回”；服务不判断归类正确性、不选择唯一概念、不建立新概念，也不把支持统计升级为业务语义。不得调用内部支持登记根扫描或物理支持项重建函数。当前函数证据见[函数用途/L2概念结构服务/README.md](函数用途/L2概念结构服务/README.md)。

### 3.4 已落地示例：读取存在的当前场景成员关系

若目标需要“查询一个已发布存在当前属于哪些场景成员关系”，应复用场景服务的反向读取，而不是从存在名称、缓存或L1关系表猜测：

```text
经普通应用的L2结构聚合取得同一存在服务和场景服务
-> 从存在服务读取同一L1的当前事实截止
-> 以L2存在当前场景成员引用读取请求有效复核请求值形状
-> 调用场景服务::读取存在当前场景成员引用
-> 以结果::成功复核同截止、稳定有序且无重复的引用组
-> 按需要逐场景调用完整读取或场景树读取
-> 由DATA外业务判断这些结构关系对当前目标意味着什么
```

这里可直接复用的是“当前场景成员关系反向读取”和相关纯值守卫；它不保证一个存在只属于一个场景，不等于场景宿主关系，也不裁决存在是否真实、自我或当前业务主体。数据头中的守卫和`成功()`是非服务函数，不能替代公开场景服务的权威读回。当前证据见[函数用途/L2场景结构服务/README.md](函数用途/L2场景结构服务/README.md)与[函数用途/L2存在结构服务/README.md](函数用途/L2存在结构服务/README.md)。

### 3.5 已落地示例：按身份读取不可变材料

若目标需要“在某一正式截止核验既有材料”，应复用唯一材料服务的公开读取和登记读取，而不是从摘要路径、缓存或L1三槽自行重建：

```text
经普通应用上下文取得同一不可变材料服务
-> 从合法上游结果取得材料身份、读取类别和非零事实截止
-> 调用读取不可变材料，复核结果头、类别、截止和完整材料负载
-> 调用读取不可变材料登记，复核材料格式身份属于同截止正式登记
-> 只把格式、长度、摘要、来源、生命周期和物理定位作为材料事实
-> 由DATA外业务解释材料承载的文本、规则、签名或其它语义
```

这里可直接复用的是“单一当前/历史材料读回”和“材料登记读回”。物理路径不是身份，摘要相同不能替代完整字节证据，结果`成功()`也不能替代服务调用。当前语言和概念服务已经按这一方向消费材料读取；正式项目源码仍没有材料写入/退出的模块外生产调用点，因此不得把公开写退能力写成真实BIZ已接线。当前证据见[函数用途/不可变材料服务/README.md](函数用途/不可变材料服务/README.md)。

### 3.6 已落地示例：识别并物理退出旧能力

发现名字和目标相似、且仍登记在工程中的模块时，不能据此判断可以复用。已经确认退出的模块也不能因 Git 历史中存在而恢复。以历史 `L1自我结构登记服务` 为例，应按以下顺序裁决：

```text
确认目标源码和工程登记仍存在
-> 搜索模块外生产import、构造和公开入口调用点
-> 区分历史验证与当前HEAD验证
-> 对照现行正式规范是否保留该业务责任
-> 若当前零调用且规范明确退出，则形成完整物理退役切片
-> 删除源码、工程登记和绑定当前源码的用途卡
-> 保留正式禁止恢复条款、施工/验证记录和 Git 历史
-> 重新扫描调用边、工程引用和受影响兼容入口知识
```

该服务曾在旧生产链中通过构建和运行验证，退出前仍有工程编译登记但模块外生产调用为 0；现行7130明确禁止恢复旧关系21、自我结构登记服务和旧完整自我闭包。`a71e7920` 已把数据头、服务模块和工程登记物理退役，绑定不存在源码的用途卡不再作为当前知识保留。当前自我形成必须沿存在单例角色、场景成员、场景宿主和 L5 外真实自我提供者设计。退役证据见[施工记录](../施工记录/20260824_L1-SELF-STRUCTURE-REGISTRY-RETIREMENT_施工记录.md)和[验证记录](../验证记录/20260824_L1-SELF-STRUCTURE-REGISTRY-RETIREMENT_验证记录.md)。

### 3.7 已落地示例：区分已接线单源实现与未接线候选provider

源码正文完整、函数身份齐全、甚至已有详细设计和待激活计划，都不能证明它已经成为当前生产能力。业务初始化源码必须分两类核对：

```text
查源码是否进入正式Git
-> 查所属模块是否登记工程或被已登记模块包含
-> 查普通应用或其它正式生产模块是否import、构造和调用
-> 查正式入口是否按阶段接受结果并继续后继
-> 查已执行验证是否覆盖当前HEAD和真实生产语境
-> 分账为已接线实现、未接线候选、已退出或证据不足
```

当前`初始化.系统世界树根.inl`和`消费.自我世界树根.inl`由普通应用包含并分别进入I1、I2静态调用链，可以作为已接线单源实现理解，但正式启动阶段14、16/17仍按用途卡登记`NOT_RUN`。`初始化.四本体根.inl`及`提供者.方法登记根生产初始化.ixx`虽有完整候选正文，当前却未工程登记、无生产import、构造或调用点，只能作为待激活设计的实现候选；不得列为阶段18/19当前能力、直接复用入口或运行已验证。证据见[函数用途/业务初始化数据合同/README.md](函数用途/业务初始化数据合同/README.md)。

## 4. 六种裁决结果

### 4.1 直接复用

输入、输出、状态、副作用、事务、生命周期和调用方向均与目标合同一致，调用者直接使用现有公开能力。

### 4.2 组合复用

多个现有公开能力按已确定的上层业务顺序组合。组合层只负责业务协调，不复制下层 CRUD、事实所有权或事务内部实现。

### 4.3 适配复用

现有能力的事实语义一致，但 DTO 或调用形状不同。适配层只做可证明的值式转换，不增加第二 owner、不生成新事实、不隐藏错误结果。

### 4.4 扩展现有能力

现有 owner 和服务职责正确，但公开合同缺少一个属于同一职责的入口。先形成明确接口缺口和实施范围，再由合法计划扩展原服务。

### 4.5 新建能力

当前仓库没有职责相符的 owner、服务或函数，且新能力的事实所有权、物理归属和依赖方向已经确定。不得因为不会找现有函数而直接选择新建。

### 4.6 证据不足

当前知识、代码或正式材料不能唯一确定复用方式。保留目标合同和缺失证据，不临场发明接口、默认参数、错误语义或第二数据入口。

## 5. 禁止的复用方式

- 仅凭函数名、注释、聊天记忆或日志文本判断用途；
- 只因参数类型能转换就认为业务语义等价；
- 绕过正式聚合服务，直接调用更低层仓库或 owner；
- 复制已有 CRUD、幂等、事务、读回或错误处理形成第二实现；
- 用缓存、上下文副本或请求字段替代正式事实读回；
- 把测试钩子、自检函数、旧兼容入口或当前不可达函数当生产能力；
- 把“已实现待验证”“候选待复核”升级为“已完成”或“可直接复用”；
- 用过期用途卡替代当前源码和调用点核对。

## 6. 实施后的知识材料

### 6.1 源码注释与知识库分工

源码注释用于解释代码本身不容易表达的内容：设计原因、不变量、锁和事务前置、特殊生命周期、外部协议限制以及看似可以简化但实际不能简化的原因。公开服务入口或复杂内部函数的合同不能从签名直接看出时，应在声明或定义附近保留简洁说明。

不得用逐行翻译代码的注释制造噪声，也不得只在注释中定义机器语义。完整用途、非职责、调用语境、依据和验证状态进入函数用途卡；正式机器语义进入规范；代码变化时同步检查相关注释和知识变更清单。注释与当前实现冲突时属于代码知识漂移，不能继续作为调用依据。

### 6.2 代码结果需要提供的知识材料

每次代码结果应能列出：

```text
新增函数
修改函数
退出函数
签名或可见性变化
用途与非职责变化
参数来源或结果形状变化
直接调用边变化
事实读写、副作用、事务或生命周期变化
对应规范、设计、计划和验证证据
结果提交
```

这份材料用于更新函数用途卡。记录它不等于知识库已经更新；只有基于已发布代码完成用途卡当前性核对后，相关知识条目才可以标记为闭合。

## 7. 在一次代码切片中实际应用

本节把前述方法压缩为一次执行 S0、施工和发布后维护都能直接使用的检查表。它只提供工程证据组织方式；执行许可、文件白名单和机器语义仍由正式计划与规范决定。

### 7.1 S0 形成复用裁决

执行者至少留下以下结果，不能只写“已阅读知识库”：

| 检查项 | 必须形成的证据 |
| --- | --- |
| 目标合同 | 目标函数的参数、结果、权威来源、非成功、事实读写、副作用、事务、生命周期和合法调用方 |
| 知识命中 | 命中的用途卡、能力条目和函数身份；没有命中时明确写无 |
| 当前性 | 用途卡绑定的提交或 source blob 与正式 HEAD 的比较结果，以及直接调用点是否变化 |
| 合同互证 | 当前源码、正式规范、有效设计和现行计划是否支持同一职责与依赖方向 |
| 复用裁决 | 直接复用、组合、适配、扩展、新建或证据不足中的唯一结论 |
| 排除项 | 名称相似但职责、owner、事实来源、事务或生命周期不一致的函数及排除理由 |
| 漂移处理 | 等价能力、第二 owner、第二入口、循环依赖或公开合同冲突是否需要退回计划支撑 |

最小记录形态：

```text
目标合同：<具名参数、结果、事实和生命周期>
知识命中：<用途卡 / 能力条目 / 函数身份，或无>
当前性：<提交或source blob比较 + 调用点比较>
裁决：<六选一>
采用函数：<完整签名、模块、文件、合法调用语境>
排除函数：<完整签名 + 排除理由>
未证明范围：<构建、运行、集成、业务闭环或其它NOT_RUN>
```

“采用函数”为空并不自动授权新建；只有目标计划已经冻结新建结论，或设计治理补齐 owner、合同和依赖方向后，执行者才可按计划施工。

### 7.2 施工中按裁决约束实现

施工时逐项守住 S0 裁决：

1. 直接复用只调用已确认的公开能力，不复制其内部校验、事务或读回；
2. 组合复用只在上层编排业务顺序，不取得下层 owner；
3. 适配只做可证明的值式转换，不吞掉错误或生成第二事实；
4. 扩展只改计划允许的原 owner 和公开合同，不另建平行服务；
5. 新建只落在已冻结的物理位置和依赖方向；
6. 发现裁决依据变化时停止受影响实现，重新比较知识基线、源码和调用点。

施工记录中的“代码知识变更清单”按 `.codex/rules/执行智能体代码知识使用与回写规则.md` 填写。函数实现已提交但清单缺失时，只能说明代码结果存在，不能说明知识应用闭环。

### 7.3 发布后由知识维护者闭合

代码结果发布后，知识维护者按以下顺序处理：

```text
固定结果提交和知识变更清单
-> 从结果提交读取新增、修改、退出函数和直接调用边
-> 比较受影响用途卡的source blob、合同和生产调用语境
-> 新建、更新、标记待复核或标记退出
-> 刷新当前生产源码覆盖账与当前代码知识状态
-> 验证链接、编码、覆盖统计和文档检查
-> 只发布知识所有权范围
```

闭合判定必须同时满足：结果提交可读；变更函数均已处理；受影响用途卡绑定新提交或新 source blob；聚合状态不再把已变更条目写成当前；知识提交已进入正式主线。仅有施工记录、聊天回传或本地知识 WIP 都不算发布后闭合。

### 7.4 当前应用证据怎么查

当前知识是否真正应用，不从本指南自证。按以下顺序查：

1. `AGENTS.md` 和执行技能是否要求执行前读取知识；
2. `.codex/rules/执行智能体代码知识使用与回写规则.md` 是否仍为正式规则；
3. 目标代码提交的专属施工记录是否包含函数级“代码知识变更清单”；
4. `当前代码知识状态.md` 是否把该代码提交登记为已回写、待复核或尚未处理；
5. 对应用途卡的 source blob 是否与当前正式源码一致。

规则存在只证明流程已定义；记录存在只证明执行者留下交接；用途卡与当前源码完成互证并正式发布，才证明该批知识已经实际回写。构建、运行和集成验收仍须读取各自具名证据，不能由知识回写替代。
