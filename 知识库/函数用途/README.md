## 3. 知识状态

| 状态 | 含义 |
| --- | --- |
| 当前 | 条目绑定的目标函数、合同和相关调用边已与目标正式代码基线互证 |
| 待复核 | 条目基线早于当前代码，或相关代码发生变化但尚未完成影响核对 |
| 过期 | 已确认条目描述与当前代码或正式规范冲突，不得继续用于复用裁决 |
| 已退出 | 绑定函数已从正式生产代码退出；条目只作历史证据 |

“当前”只对条目明确绑定的代码基线成立，不等于功能已经完成全部构建、运行、并发、恢复或集成验证。

## 4. 服务边界类别

| 类别 | 判定标准 | 复用规则 |
| --- | --- | --- |
| 对外服务函数 | 正式服务合同允许上层消费者调用的数据或业务操作 | 只能通过授权服务 / 聚合边界并按公开 DTO、状态和生命周期调用 |
| 内部服务函数 | 只支撑对外服务实现的映射、校验、定位、提交、读回或锁内 helper | 不是稳定消费 ABI；外部代码不得因其可见或名字合适而直接依赖 |
| 服务取得函数 | 返回上下文或聚合持有的同实例服务引用 | 只负责取得，不等于执行数据服务，也不证明消费者已接线 |
| 服务装配函数 | 建立、绑定或持有 owner、服务和聚合实例 | 只负责装配生命周期；除非正文明确执行初始化，否则不冒充业务操作 |
| 非服务函数 | 入口、编排、结果谓词、纯值映射、信号 / 线程辅助等 | 按其真实职责复用，不登记为基础数据服务接口 |

边界类别由正式合同、导出边界、调用语境和事实责任共同决定，不能只看 C++ 的`public` / `private`。`public`构造或 getter 可能只是装配 / 取得函数；模块内部 helper 即使技术上可定位，也不是对外服务。

## 5. 建立和更新

1. 从已发布代码和完整签名建立稳定身份。
2. 读取声明、定义、DTO、生产调用点、直接调用边和事实承载。
3. 对照正式规范、有效设计、现行计划及具名验证证据。
4. 写清用途和非职责，不能只改写函数名。
5. 分别登记实现状态、验证状态和 NOT_RUN，不合并成一个“完成”。
6. 记录绑定提交；后续代码变化时按受影响函数和调用边增量复核。

## 6. 与其它目录的分账

- `能力证据目录`：按业务能力聚合多个提供函数，回答“有哪些候选能力”。
- `代码流程图`：描述单函数控制流及逐行映射，回答“函数怎样执行”。
- `函数用途卡`：描述单函数职责、调用合同和合法语境，回答“函数为什么存在、如何使用”。
- `施工记录/验证记录`：记录具名变更和已执行验证，回答“某次施工实际做了什么、验证了什么”。

不得在用途卡中复制整段源码、整份流程图或整份能力目录。使用稳定身份和证据链接保持可追溯，减少多处文本漂移。
