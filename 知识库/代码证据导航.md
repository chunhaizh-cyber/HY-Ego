# 代码证据导航

本文件把“想知道某个函数有什么用”拆成可定位的证据入口。路径均相对于仓库根目录。

## 1. 先判断要回答哪类问题

| 问题 | 首要入口 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- | --- |
| 项目有哪些候选能力 | `流程图/主程序可达调用关系/能力证据目录/` | 冻结基线上的能力分类、提供函数和证据缺口 | 当前业务一定可复用、当前 HEAD 仍一致 |
| 某函数在哪里、谁调用它 | `流程图/主程序可达调用关系/00_main可达函数身份表.*`、`01_main可达项目调用边表.*` | 冻结基线上的稳定函数身份和调用边 | 函数业务语义、运行正确性 |
| 某函数怎样执行 | `流程图/代码流程图/` 中的现状流程图和逐行映射 | 已制图函数的控制分支与代码行映射 | 未制图函数不存在、流程已运行验证 |
| 业务节点需要什么 | `流程图/目标业务流程图/` 及三张映射 | 目标业务节点、目标函数和消费需求 | 当前代码已接通 |
| 数据服务最终需要提供什么 | `计划/数据服务最终需求清单.md` | BIZ 对基础数据服务的最终公开需求 | DATA 已实现或真实 ABI 已匹配 |
| 什么机器语义必须遵守 | `规范/规范目录.md` 及其登记规范 | 正式机器逻辑和施工约束 | 当前代码已符合 |
| 哪些文件允许修改 | `计划/计划索引.md`、目标计划 | 当前计划状态、范围和门禁 | 目标能力已完成 |
| 某次施工做了什么 | `施工记录/`、`验证记录/`、Git 提交 | 具名提交的变更和验证证据 | 其它提交、其它配置或完整业务闭环 |
| 某函数能否用于当前目标 | 本知识库用途卡加当前源码、调用点和正式合同 | 经互证后的复用候选 | 未经设计/计划授权的实施许可 |

## 2. 当前源码核对的最小集合

对目标函数至少读取：

1. 声明与完整定义；
2. 参数和返回 DTO 的定义；
3. 所有生产调用点；
4. 直接被调函数中承担事实读写、事务、锁、线程或外部资源的部分；
5. 相关公开服务 getter、owner 或聚合装配路径；
6. 目标代码相对知识条目绑定提交的 Git 差异；
7. 相关正式规范、有效设计、现行计划和已发布验证证据。

模板、隐式构造、lambda、测试钩子和重载必须以完整签名区分，不能只按短函数名合并。

## 3. 证据冲突的处理

```text
用途卡与当前代码不一致
-> 以当前代码记录实现事实
-> 以正式规范判断代码是否漂移
-> 用有效设计和计划判断预期修改范围
-> 将用途卡标记待复核或过期
```

流程图、能力目录或施工记录落后于代码时，不删除历史证据，也不把旧描述强套到新代码。先记录冻结基线和差异，再由相应维护切片更新投影。

## 4. 常用只读定位方式

```powershell
rg -n --encoding UTF8 "完整函数名|稳定函数身份" 知识库 流程图 海中鱼巣 规范 计划
git log --oneline --all -- "目标文件"
git diff --name-only <知识基线>..HEAD -- "目标文件"
git show <提交>:<仓库相对路径>
```

这些命令只帮助定位证据。最终结论仍需区分正式规范、当前代码、计划目标、验证记录和知识投影。
